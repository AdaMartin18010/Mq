## 1.33.1 能力全景与闭环模型

消息系统的运维能力可归纳为四大能力域，它们构成一个闭环【论证】：

```text
        ┌────────── 监测（看见）──────────┐
        │  指标/日志/追踪 → 统一数据管道   │
        └──────────────┬─────────────────┘
                       ▼
        ┌────────── 告警（判断）──────────┐
        │  分级/抑制/静默 → SLO 燃尽告警   │
        └───────┬──────────────┬─────────┘
                ▼              ▼
   ┌─── 自动伸缩（调容量） ──┐  ┌─── 自愈（修故障） ───┐
   │  lag/CPU 驱动扩缩容    │  │  检测→处置→验证→学习  │
   └───────────────────────┘  └──────────────────────┘
                       │
                       ▼
              效果回流监测（闭环校准）
```

能力域之间的关系【论证】：监测是地基（没有指标，告警/伸缩/自愈都是盲动）；告警是判断层（把指标翻译为行动信号）；伸缩与自愈是两类行动——伸缩处理"量变"，自愈处理"质变"。
四者成熟度不均衡是常态：多数团队监测强、告警中等、伸缩弱、自愈最弱【估算】。

与项目现有文档的映射：概念与机制分散于 03-02/03-05/03-06/03-07/03-25 与 02-39/02-45；本文提供体系化总览与完备性对照，落地操作见 03-63，测试验证见 TEST-07。

## 1.33.2 监测（Monitoring）：指标体系

监测层的完备性标准：覆盖**四大黄金信号**（延迟、流量、错误、饱和度）+ **MQ 特有语义指标**【论证：Google SRE 方法 + 各系统 exporter 实践】。

### 六系统核心指标矩阵

| 系统 | 流量 | 延迟 | 错误 | 饱和度 | 特有语义指标 |
| ------ | ------ | ------ | ------ | -------- | -------------- |
| Kafka | produce/consume rate、request rate | request handler idle、P99 per api | failed produce/consume、UnderReplicatedPartitions | request queue、网络/磁盘 IO | consumer lag、ISR shrink、offline partitions |
| Pulsar | entry rate、dispatch rate | publish/delivery latency | replication backlog | direct memory、bookie 写入 | backlog quota、subscription backlog |
| RabbitMQ | publish/deliver rate、connections/channels | queue deliver latency | unroutable/dropped、connection churn | fd/内存/磁盘 alarm | queue depth、consumer util、GC（quorum） |
| NATS | in/out msgs、connections | RTT（core）、consumer ack floor 滞后 | slow consumers、errors | JetStream 存储/内存占用 | stream/consumer 状态、ack floor 差 |
| Redis Stream | ops/sec、XADD rate | command latency | rejected connections、evicted keys | memory/maxmemory、CPU | PEL 长度、group lag |
| MQTT | connected clients、message rate | end-to-end delivery delay | auth failures、quota exceeded | inflight/quota | session 数、订阅数、offline queue |

### 数据管道与工具链

```yaml
# 采集层（exporter）→ 存储（Prometheus）→ 展示（Grafana）→ 消费（告警/伸缩/自愈）
kafka → kafka-exporter(jmx) / pulsar → pulsar-metrics / rabbitmq → built-in prometheus endpoint
nats  → nats-server -m :8222 (自暴露) / redis → redis-exporter / mqtt → broker 自带或 exporter
```

要点【论证】：① exporter 版本与 broker 大版本匹配（指标名会变）；② 指标基数控制（topic/queue 级指标高基数，用 topk 聚合）；③ 业务语义指标（lag、PEL、backlog）必须与应用发布节奏对齐采集间隔（15-30s 为常见下限）。

**Exporter 对照（2026-11 生态口径【论证】）**：

| 系统 | 推荐采集方式 | 暴露端点 |
| ------ | -------------- | ---------- |
| Kafka | JMX exporter（官方推荐）或社区 kafka-exporter | :9404 / :9308 |
| Pulsar | broker 内置 `/metrics` + BookKeeper exporter | :8080/metrics |
| RabbitMQ | `rabbitmq_prometheus` 插件（内置） | :15692/metrics |
| NATS | server `-m` 自暴露 | :8222/metrics |
| Redis | redis-exporter（社区官方） | :9121/metrics |
| MQTT | broker 相关（EMQX 内置 / mosquitto 需插件） | 依 broker |

### 追踪与日志维度（可观测性三支柱补齐）

监测≠只有指标。完备可观测性三支柱在 MQ 场景的落点【论证】：

| 支柱 | MQ 场景落点 | 工具 |
| ------ | ------------- | ------ |
| Metrics | 上文指标体系（黄金信号+语义指标） | Prometheus + exporter |
| Tracing | 生产→broker→消费全链路透传 trace-id（header/属性） | OpenTelemetry + Kafka/Pulsar instrumentation |
| Logging | broker 审计日志、应用消费日志（含失败上下文） | Loki/ELK + 结构化日志 |

三支柱联动判据【论证】：一条告警（Metrics 触发）应能 5 分钟内定位到具体 trace（Tracing）与失败日志（Logging）——做不到说明三支柱未打通。本项目 02-23 消息追踪设计与 03-06 可观测性体系给出实现细节，本文不重复。

## 1.33.3 告警（Alerting）：从阈值到 SLO

告警层的完备性标准：分级、降噪、可行动、与 SLO 对齐【论证】。

### 告警分级与响应矩阵

| 级别 | 判据示例 | 响应时限 | 示例场景 |
| ------ | ---------- | ---------- | ---------- |
| P0 | 数据丢失/一致性破坏/集群不可用 | 立即（15 分钟内响应） | offline partitions、quorum 丢失 |
| P1 | 有损降级（重试风暴、lag 持续增长） | 30 分钟 | URP>0 超 10 分钟、consumer 全断 |
| P2 | 容量预警（饱和度 >80%、连接数近上限） | 工作日 | 磁盘 75%、backlog 增速 > 消费增速 |
| P3 | 趋势与卫生（单 broker 不均衡、版本 EOL 临近） | 排期 | ISR 频繁伸缩、证书 30 天到期 |

### SLO 燃尽告警（Burn Rate）

多窗口多 burn-rate 规则【论证：Google SRE Workbook】：

```yaml
# 示例：可用性 SLO 99.9%（30 天窗口）
# 快速燃尽（1h 窗口烧 2% 预算）+ 慢速燃尽（6h 窗口烧 1% 预算）同时触发才告警
groups:
- name: slo-burn
  rules:
  - alert: SLOBurnRateCritical
    expr: |
      (
        sum(rate(kafka_request_failed_total[1h]))
        / sum(rate(kafka_request_total[1h]))
      ) > (14.4 * 0.001)   # 2%预算/1h ≈ 14.4×基础错误率
      and
      (
        sum(rate(kafka_request_failed_total[6h]))
        / sum(rate(kafka_request_total[6h]))
      ) > (6 * 0.001)
    labels: {severity: p1}
```

告警治理清单（防告警疲劳）【论证】：

- [ ] 每条告警有 runbook 链接（无 runbook 的告警不允许入库）
- [ ] 抑制规则：父级故障抑制子级（broker down 抑制该 broker 的 topic 级告警）
- [ ] 静默管理：静默必须带到期时间与 owner
- [ ] 质量度量：每周告警重复率（同根因多条）、有效率（触发后有人处理）、静默覆盖率

### SLO 定义方法（告警的锚）

告警阈值不应拍脑袋，从 SLO 反推【论证：Google SRE】：

```text
1. 选 SLI：如"produce 请求成功率"（成功数/总数）
2. 定 SLO：如 99.9%（30 天滚动）
3. 算错误预算：0.1% × 总请求
4. 定燃尽容忍：1 小时烧 2% 预算 → 快速窗口阈值 = 14.4 × 基础错误率
5. 配多窗口规则（见下）；阈值随流量规模定期复核
```

## 1.33.4 自动伸缩（Auto-scaling）：触发模型

伸缩处理"量变"：负载增长时自动加容量。MQ 场景的伸缩有两个方向，触发源不同【论证】：

| 方向 | 触发源 | 动作 | 关键判据 |
| ------ | -------- | ------ | ---------- |
| 消费者扩容 | consumer lag / 处理延迟 | 加 consumer 实例 | lag 持续 > 阈值且现有消费者利用率 > 70% |
| 生产者扩容 | 发送延迟/超时率 | 加分区/加 broker | produce P99 升高、分区打满 |
| Broker 扩容 | 磁盘/IO/请求饱和度 | 加节点 + 再平衡 | 磁盘 <30%、CPU >70% 持续、URP 风险 |
| 缩容 | 低负载持续期 | 减实例/减节点 | lag≈0 且利用率 <30% 持续 N 小时（缩容比扩容保守 2 倍） |

KEDA 按 lag 伸缩（Kafka 示例，模板见 config-templates/keda-scaledobject-kafka.yaml）：

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: orders-consumer
spec:
  scaleTargetRef: { name: orders-consumer }
  minReplicaCount: 2
  maxReplicaCount: 30
  cooldownPeriod: 300      # 缩容冷却，防抖动
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka:9092
      consumerGroup: orders-processor
      topic: orders.order.created
      lagThreshold: "1000" # 每副本目标 lag
      offsetResetPolicy: latest
```

设计要点【论证】：① 分区数是消费者并行度上限——扩 consumer 前先确认分区够（分区 < consumer 数时扩容无效，需先扩分区）；② cooldown 与 rebalance 叠加：缩容触发 Kafka 重平衡，冷却期必须 > 重平衡时长【估算】；③ lag 指标采集延迟决定扩容反应速度，采太密会抖、太疏会迟（30s 起步调参）；④ 缩容必须分级（先退到 min，再评估）。

## 1.33.5 自愈（Self-healing）：分级自治

自愈处理"质变"：故障检测后自动处置。自治能力按成熟度分级【论证】：

| 自治级别 | 名称 | 特征 | 示例 |
| ---------- | ------ | ------ | ------ |
| L0 | 人工 | 检测+处置全靠人 | 仅监控无动作 |
| L1 | 辅助 | 自动检测+告警，人工处置 | 全量告警 runbook |
| L2 | 部分自治 | 预设场景自动处置，人工确认 | 磁盘清理、死进程拉起 |
| L3 | 条件自治 | 宽条件自动处置+窄条件升级 | broker 宕机自动替换、consumer 卡死重启 |
| L4 | 高度自治 | 学习优化处置策略 | 自适应限流、预测性扩容 |

### 自愈场景矩阵（按风险分级处置）

| 场景 | 检测信号 | 自动处置 | 自治级别建议 |
| ------ | ---------- | ---------- | -------------- |
| broker/节点进程消失 | 进程/探针消失 | 自动拉起（systemd/k8s 重启） | L2（通用安全） |
| 磁盘使用 >85% | disk usage | 清理日志/旧 segment；紧急扩容 | L2（清理需白名单路径） |
| consumer 卡死（有心跳无进展） | poll interval 超阈值 | 重启 consumer 实例 | L2-L3 |
| leader 不均衡 | preferred leader 失衡 | 触发 preferred leader election | L2（Kafka 自带 cron） |
| 死信突增 | DLQ 深度阈值 | 隔离下游+告警（不自动重投） | L3（重投必须人工） |
| quorum 丢失 | Raft majority 丢失 | **不自动处置**，立即告警 | L1（人工裁决） |
| 脑裂疑似的分区恢复 | 网络分区恢复信号 | 延迟恢复+数据校验流程 | L1（需人工核对数据） |

安全护栏（自治的边界）【论证】：① **数据面故障不自动"修数据"**——任何涉及消息丢失/重复的处置必须人工确认；② 自动处置必须幂等且带熔断（处置 N 次无效→升级人工）；③ 所有自动动作留审计日志；④ quorum/脑裂/数据一致性三类场景永不自动处置。

## 1.33.6 六系统能力完备性矩阵

| 能力域 | Kafka | Pulsar | RabbitMQ | NATS | Redis | MQTT(Broker) |
| -------- | :---: | :---: | :---: | :---: | :---: | :---: |
| 指标导出 | ✅ jmx/exporter | ✅ 内置+BK | ✅ 内置 endpoint | ✅ 自暴露 :8222 | ⚠️ 需 exporter | ⚠️ broker 相关 |
| 告警生态 | ✅ 规则成熟 | ✅ | ✅ | ✅ | ✅ | ⚠️ |
| lag 驱动伸缩 | ✅ KEDA 原生 | ✅ KEDA 原生 | ✅ KEDA 队列触发器 | ✅ KEDA JetStream | ⚠️ 需自定义 | ⚠️ 连接数为主 |
| 自愈原语 | ✅ controller 平衡 | ✅ 自动负载均衡 | ✅ quorum 自选举 | ✅ Raft 自愈合 | ⚠️ 哨兵/集群 | ⚠️ broker 相关 |
| 平台级自治 | ⚠️ 需运维工程 | ✅ 存算分离易自治 | ⚠️ | ✅ 轻量易自治 | ⚠️ | ⚠️ |

✅=生态成熟可直接落地；⚠️=需自行工程补齐（以 2026-11 官方文档生态为准【论证】）。

差距处理路径：⚠️ 格的能力，优先用平台层（K8s/KEDA）补齐而非 broker 内建；补齐的用例与验证见 TEST-07（TC-OBS-08~10）。

### 常见问题（FAQ）

| 问题 | 回答口径 |
| ------ | ---------- |
| "先建监控还是先上自愈" | 先监测→告警→（跑稳 1 个月）→伸缩→自愈；无监测数据支撑的自治是盲动【论证】 |
| "告警太多了怎么办" | 先做治理（抑制/静默/分级），再砍告警；告警多通常是信号设计问题而非阈值问题 |
| "KEDA 和 HPA 用哪个" | 消息积压场景 KEDA（lag 语义）；CPU 型消费者 HPA 兜底；两者可共存（02-49） |
| "云托管 MQ 还需要这些吗" | 监测/告警仍需（云管不了你的消费端）；伸缩/自愈大半由云接管（03-12 云服务对比） |
| "自愈敢不敢开 L3" | 满足三前提再开：幂等消费落地 + 冗余容量 + TC-OBS-09/10 演练通过（03-63.5） |
