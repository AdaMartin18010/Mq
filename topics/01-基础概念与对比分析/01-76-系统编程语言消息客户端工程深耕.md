## 1.76.1 合并理由与写作边界

C 语言在消息队列客户端侧呈现“单极化”特征：Kafka 用 `librdkafka`，Redis 用 `hiredis`，MQTT 可用 Eclipse Paho C 或 NanoMQ 内置的 `nng` MQTT 协议栈，AMQP/Pulsar/NATS 也都有 C 绑定但生态规模远小于前者。若单独写一篇《C 消息客户端工程深耕》，势必大量重复 01-52 的表格罗列，且难以达到密度标准。

Rust 侧同样高度依赖 C 资产：`rdkafka` 是 `fede1024/rust-rdkafka` 对 `librdkafka` 的安全封装；`redis` crate 虽为纯 Rust，但其协议实现思路与 `hiredis` 同源。把两门语言放在同一篇，可以用“内存所有权”这条主线贯穿：Rust 用编译期所有权把消息生命周期类型化，C 用显式 `destroy/free` 手工化同一生存期。两者对照，恰好形成从“自动证明”到“人工责任”的完整谱系。

## 1.76.2 Rust 消息客户端生态

| crate | 维护方 | 最新稳定版（2026-11） | 运行时 | 备注 |
| ---- | ---- | ---- | ---- | ---- |
| `rdkafka` | fede1024 / 社区 | 0.25.x（基于 librdkafka v1.9.2+） | Tokio / async-std / smol | 功能最全，Kafka 首选 |
| `async-nats` | nats-io | 0.53.0 | Tokio | 官方 Rust 客户端，JetStream/KV/Object Store |
| `lapin` | amqp-rs | 4.12.3 | Tokio / async-std | AMQP 0-9-1，RabbitMQ |
| `rumqttc` | bytebeamio | 0.25.1 | Tokio | MQTT 5 / 3.1.1 |
| `pulsar` | streamnative | 6.9.0 | Tokio | 纯 Rust Pulsar 客户端 |
| `redis` | redis-rs | 1.8.2 | Tokio / async-std | Redis Stream / PubSub / KV |

【论证】Tokio 在 Rust 消息客户端中占据主导地位，原因有三：

1. `rdkafka` 的 `StreamConsumer` / `FutureProducer` 默认依赖 Tokio 的 `AsyncRuntime` trait；
2. `async-nats`、`lapin`、`rumqttc`、`redis` 均以 Tokio 为第一运行时；
3. 这些 crate 的 `Stream` 消费模型天然依赖 Tokio 的任务调度与背压。

但 `rdkafka` 允许关闭 default features 以移除 Tokio，通过实现 `AsyncRuntime` 接入其他运行时。选型时若使用非 Tokio 运行时，需先验证目标 crate 的 runtime 抽象是否完整。

## 1.76.3 所有权模型×消息语义

### 借用检查与零拷贝消费

`rdkafka` 的 `Message` trait 提供 `payload()` 返回 `Option<&[u8]>`，消息数据在 `commit` 之前由 librdkafka 持有，Rust 借用检查器确保不会在释放后使用：

```rust
use rdkafka::consumer::{Consumer, StreamConsumer};
use rdkafka::Message;

async fn consume(consumer: &StreamConsumer) -> anyhow::Result<()> {
    let msg = consumer.recv().await?;
    if let Some(payload) = msg.payload() {
        // payload 是借用，msg 存活期间有效
        process(payload).await?;
    }
    consumer.commit_message(&msg, rdkafka::util::Timeout::Never)?;
    // msg 在这里 drop，内存归还给 librdkafka
    Ok(())
}
```

【论证】零拷贝消费的关键是“不把所有权从 C 缓冲区搬到 Rust 堆”。`Message` 的 borrowed payload 模式让 Rust 编译器承担了一部分生命周期验证工作，避免 C 侧常见的 use-after-free。【估算】在 1KB 消息、百万级吞吐场景下，Rust 侧相比每次复制 payload 可减少约 30-50% 的用户态 CPU 占用（具体取决于处理逻辑）。

### async trait 与 Stream trait 消费

```rust
use futures::StreamExt;
use rdkafka::consumer::Consumer;

let mut stream = consumer.stream();
while let Some(result) = stream.next().await {
    match result {
        Ok(msg) => {
            process(msg.payload()).await;
            consumer.commit_message(&msg, Default::default())?;
        }
        Err(e) => tracing::error!("kafka error: {}", e),
    }
}
```

【论证】`Stream` 消费把“拉取-处理-提交”表达为惰性数据流，背压由 `StreamExt::buffered`/`throttle` 等组合子显式控制。这与 [01-66](./01-66-背压机制全谱系.md) 中“响应式背压”一致，但 Rust 通过所有权确保每个消息在提交或失败前不被丢弃。

### 错误类型设计与重试语义的类型化表达

```rust
use thiserror::Error;
use std::time::Duration;
use tokio::time::sleep;

#[derive(Error, Debug)]
enum ProcessError {
    #[error("transient downstream failure")]
    Transient,
    #[error("permanent schema violation")]
    Permanent,
}

async fn retry<F, T, E>(mut f: F, max: u32) -> Result<T, E>
where
    F: FnMut() -> futures::future::BoxFuture<'static, Result<T, E>>,
    E: std::fmt::Debug,
{
    for i in 0..max {
        match f().await {
            Ok(v) => return Ok(v),
            Err(e) if i < max - 1 => {
                tracing::warn!("retry {}/{}: {:?}", i + 1, max, e);
                sleep(Duration::from_millis(100 * 2u64.pow(i))).await;
            }
            Err(e) => return Err(e),
        }
    }
    unreachable!()
}
```

【论证】把“可重试 / 不可重试”编码到错误类型中，是避免死信队列误用、防止无限重试放大的关键。`thiserror` 让错误层级清晰，而 backoff 策略应与服务级 SLO 对齐，不能简单按固定间隔重试。

## 1.76.4 C 消息客户端生态

### librdkafka：事实标准

`librdkafka` 是 C/C++ 侧 Kafka 的事实标准，Confluent 维护。其配置面与 01-72 中的压缩、acks、linger 等参数直接对应：

```c
rd_kafka_conf_t *conf = rd_kafka_conf_new();
rd_kafka_conf_set(conf, "bootstrap.servers", "localhost:9092", errstr, sizeof(errstr));
rd_kafka_conf_set(conf, "compression.type", "lz4", errstr, sizeof(errstr));
rd_kafka_conf_set(conf, "acks", "all", errstr, sizeof(errstr));
```

【论证】librdkafka 的线程模型是“后台 I/O 线程 + 应用线程调用 poll”。生产者 `rd_kafka_producev` 把消息放入队列后由后台线程发送；消费者 `rd_kafka_consumer_poll` 从本地队列拉取。理解这一模型才能正确设置 `queue.buffering.max.messages`、`fetch.min.bytes` 等参数。

### NanoMQ / nng 的 MQTT

NanoMQ 是面向边缘的 MQTT broker，其底层 `nng`（nanomsg-next-generation）提供了 MQTT 协议栈的 C 实现。C 侧使用 nng 的 MQTT 客户端时，消息生命周期与 nng 的 `nng_msg` 结构绑定：

```c
nng_msg *msg;
nng_recvmsg(sock, &msg, 0);
// 处理 nng_msg_body(msg)
nng_msg_free(msg);  // 必须显式释放
```

【论证】nng 的 MQTT 支持适合资源受限设备，但近年 NanoMQ 曝出多起 CVE（如 CVE-2026-61633、CVE-2026-73863），边缘部署需及时跟进补丁。

### hiredis 与 Redis Stream

`hiredis` 是 Redis 官方 C 客户端，通过 `XADD`/`XREADGROUP` 支持 Stream：

```c
redisReply *r = redisCommand(c,
    "XREADGROUP GROUP mygroup consumer1 COUNT 10 BLOCK 5000 STREAMS mystream >");
if (r->type == REDIS_REPLY_ARRAY) {
    for (size_t i = 0; i < r->elements; i++) {
        process_stream_entry(r->element[i]);
    }
}
freeReplyObject(r);
```

【论证】C 侧没有借用检查，消息数据所有权完全由程序员管理：`redisCommand` 返回的 `redisReply` 必须在处理完毕后调用 `freeReplyObject`，否则即内存泄漏；若提前释放又访问其字段，则是 use-after-free。

### C 的内存管理与消息生命周期

| 对象 | 获取 | 释放 | 常见错误 |
| ---- | ---- | ---- | ---- |
| `rd_kafka_message_t` | `rd_kafka_consumer_poll` | `rd_kafka_message_destroy` | 释放后访问 payload |
| `rd_kafka_t` | `rd_kafka_new` | `rd_kafka_destroy` | 未等待后台线程退出 |
| `nng_msg` | `nng_recvmsg` | `nng_msg_free` | 重复释放/未释放 |
| `redisReply` | `redisCommand` | `freeReplyObject` | 未释放导致 OOM |

## 1.76.5 Rust×C 同功能消费对照

以下两段代码实现同一功能：从 Kafka 消费一条消息并打印 payload。

### Rust（rdkafka StreamConsumer）

```rust
use rdkafka::consumer::{Consumer, StreamConsumer};
use rdkafka::ClientConfig;
use rdkafka::Message;
use futures::StreamExt;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let consumer: StreamConsumer = ClientConfig::new()
        .set("group.id", "rust-group")
        .set("bootstrap.servers", "localhost:9092")
        .set("enable.auto.commit", "false")
        .create()?;

    consumer.subscribe(&["orders".to_string()])?;

    let mut stream = consumer.stream();
    while let Some(Ok(msg)) = stream.next().await {
        if let Some(payload) = msg.payload() {
            println!("{}", String::from_utf8_lossy(payload));
        }
        consumer.commit_message(&msg, Default::default())?;
    }
    Ok(())
}
```

### C（librdkafka）

```c
#include <librdkafka/rdkafka.h>
#include <stdio.h>

int main() {
    rd_kafka_conf_t *conf = rd_kafka_conf_new();
    rd_kafka_conf_set(conf, "bootstrap.servers", "localhost:9092", NULL, 0);
    rd_kafka_conf_set(conf, "group.id", "c-group", NULL, 0);
    rd_kafka_conf_set(conf, "enable.auto.commit", "false", NULL, 0);

    rd_kafka_t *rk = rd_kafka_new(RD_KAFKA_CONSUMER, conf, NULL, 0);
    rd_kafka_subscribe(rk, topics);

    while (run) {
        rd_kafka_message_t *msg = rd_kafka_consumer_poll(rk, 1000);
        if (!msg) continue;
        if (!msg->err) {
            printf("%.*s\n", (int)msg->len, (char *)msg->payload);
            rd_kafka_commit_message(rk, msg, 0);
        }
        rd_kafka_message_destroy(msg);  // 手工释放
    }
    rd_kafka_destroy(rk);
    return 0;
}
```

### 对照维度

| 维度 | Rust `rdkafka` | C `librdkafka` |
| ---- | ---- | ---- |
| 内存安全 | 编译期所有权 + RAII | 完全手工管理 |
| 零拷贝 | `Message` 借用 payload | 直接访问 `rd_kafka_message_t` 指针 |
| 错误处理 | `Result` + `?` / `thiserror` | 错误码 + 字符串日志 |
| 并发模型 | Tokio async / Stream | 后台线程 + 应用 poll |
| 构建复杂度 | 需编译 librdkafka（cmake），MSRV 1.70+ | 需 C 编译器、链接库、头文件 |
| 性能量级 | 接近 C，额外开销主要来自借用检查运行时零成本 | 基线最快，但 bug 修复成本高 |

【估算】在同等优化条件下，Rust `rdkafka` 的吞吐通常能达到 C `librdkafka` 的 90-98%，p99 延迟差异在 5-15% 以内；但 Rust 侧因编译期保证，可将内存安全类 bug 的修复成本降低一个数量级以上。

## 1.76.6 典型陷阱

### rdkafka 的 rebalance 回调 Send 约束

`rdkafka` 允许自定义 `ConsumerContext`，其中的 rebalance 回调会被 librdkafka 后台线程调用，因此回调闭包必须实现 `Send`：

```rust
use rdkafka::consumer::ConsumerContext;

struct MyContext;
impl ConsumerContext for MyContext {
    fn rebalance(&self, _: &rdkafka::consumer::BaseConsumer<Self>, rebalance: &rdkafka::consumer::Rebalance) {
        // 这里不能捕获 Rc、RefCell 等非 Send 类型
        tracing::info!("rebalance: {:?}", rebalance);
    }
}
```

【论证】如果闭包捕获了 `Rc<T>` 或 `!Send` 的锁，编译器会直接报错。这是 Rust 把“跨线程调用安全”前置到编译期的典型体现。

### Tokio runtime 与 librdkafka 后台线程

`rdkafka` 内部会启动 librdkafka 的 C 线程执行 I/O 和回调，再通过 channel 与 Tokio runtime 交互。注意：

1. 不要在 Tokio 的 `block_in_place` 中长时间调用同步的 `BaseConsumer::poll`，会占用 worker 线程；
2. `StreamConsumer` 的 `recv()` 是 async，但底层仍依赖 librdkafka 线程；
3. 程序退出时先 drop consumer，再 drop runtime，否则可能出现 segment fault。

## 1.76.7 DSL 转换与工程检查

### AsyncAPI → Rust 类型示例

```yaml
channels:
  telemetry:
    messages:
      sensorReading:
        payload:
          type: object
          properties:
            device_id:
              type: string
              format: uuid
            temperature:
              type: number
              minimum: -40
              maximum: 80
```

```rust
use serde::Deserialize;
use uuid::Uuid;

#[derive(Debug, Deserialize)]
struct SensorReading {
    device_id: Uuid,
    temperature: f64,
}

fn validate_domain(r: &SensorReading) -> Result<(), &'static str> {
    if r.temperature < -40.0 || r.temperature > 80.0 {
        return Err("temperature out of range");
    }
    Ok(())
}
```

【论证】Rust 的类型系统可以把 AsyncAPI 的 `format: uuid` 直接映射为 `Uuid` 类型，把 `minimum/maximum` 映射为运行期校验。与 Go 类似，字段存在性由反序列化层保证，值域约束仍需显式校验。

### 工程检查清单

| 检查项 | 方法 / 阈值 | 通过标准 |
| ---- | ---- | ---- |
| Send 约束 | `cargo check` 通过 rebalance 回调 | 无 `Rc`/`RefCell` 跨线程捕获 |
| 内存生命周期 | `valgrind` / AddressSanitizer | 无泄漏/use-after-free |
| 运行时顺序 | 先 drop consumer，再 drop runtime | 退出无 segfault |
| 错误分类 | 可重试错误 vs 永久错误类型化 | 无限重试不放大 |
| 背压 | `StreamExt::buffered(n)` 或手动 ack | 下游阻塞时上游不积压 |
| 契约校验 | AsyncAPI/JSON Schema + serde | 非法消息进 DLQ |
