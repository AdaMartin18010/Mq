## 1.53.1 为什么需要独立的流处理引擎

消息队列解决的是"事件在哪里、按什么顺序、可靠地流动"的问题；而流处理引擎解决的是"事件到达后如何持续计算"的问题。两者在数据链路中分层不同：

```text
┌─────────────────────────────────────────────────────────────┐
│                      流处理链路分层                          │
└─────────────────────────────────────────────────────────────┘

  数据源          MQ 层（传输/排序/持久化）        流处理层           消费层
┌────────┐      ┌──────────────────────┐      ┌─────────────┐     ┌──────────┐
│ 数据库  │ ──→  │ Kafka / Pulsar /     │ ──→  │ Kafka       │ ──→ │ 应用/看板 │
│ CDC     │      │ RabbitMQ / NATS      │      │ Streams /   │     │ 湖仓      │
│ IoT     │      │ （保证分区顺序+持久化） │      │ Flink /     │     │           │
│         │      │                      │      │ Bytewax     │     │           │
└────────┘      └──────────────────────┘      └─────────────┘     └──────────┘
```

MQ 本身提供的是有界/无界事件的存储与投递；流处理引擎在此基础上提供：

1. **有状态计算**：窗口聚合、会话分析、模式匹配、join。
2. **时间语义**：事件时间（event time）、处理时间（processing time）、水位线（watermark）。
3. **容错与一致性**：checkpoint、savepoint、exactly-once 语义。
4. **弹性与可观测性**：独立扩缩容、指标、延迟与吞吐量化。

【论证】是否需要独立引擎，取决于状态复杂度与团队边界：若只是"读到消息就写数据库"，MQ 消费者足够；若涉及跨事件窗口、乱序处理、大规模状态，则需要引入专用流处理引擎。

## 1.53.2 Kafka Streams

Kafka Streams 是 Apache Kafka 官方提供的 Java/Scala 流处理库，与 Kafka 深度集成，设计目标是把"流处理作为微服务的一部分"随应用进程一起部署。

### DSL 与 Processor API

Kafka Streams 提供两级 API：

| API | 抽象层次 | 适用场景 | 典型算子 |
| --- | --- | --- | --- |
| **DSL** | 高阶声明式 | 过滤、映射、聚合、join、窗口 | `filter`, `map`, `groupByKey`, `aggregate`, `join` |
| **Processor API** | 低阶命令式 | 自定义状态管理、复杂事件处理、精确控制 punctuate | `process()`, `init()`, `punctuate()` |

DSL 示例：按用户 ID 统计 5 分钟滚动窗口订单金额。

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, Order> orders = builder.stream("orders",
    Consumed.with(Serdes.String(), orderSerde));

orders.groupByKey()
    .windowedBy(TimeWindows.of(Duration.ofMinutes(5)))
    .aggregate(
        () -> 0.0,
        (key, order, total) -> total + order.amount(),
        Materialized.with(Serdes.String(), Serdes.Double())
    )
    .toStream()
    .to("order-5min-revenue", Produced.with(windowedSerde, Serdes.Double()));
```

Processor API 示例：自定义定时 flush 逻辑。

```java
public class CustomProcessor extends AbstractProcessor<String, Order> {
    private KeyValueStore<String, Double> store;

    @Override
    public void init(ProcessorContext context) {
        super.init(context);
        store = (KeyValueStore<String, Double>) context.getStateStore("revenue-store");
        context.schedule(Duration.ofMinutes(1), PunctuationType.WALL_CLOCK_TIME, this::flush);
    }

    @Override
    public void process(String key, Order order) {
        double current = store.getOrDefault(key, 0.0);
        store.put(key, current + order.amount());
    }

    private void flush(long timestamp) {
        // 自定义 flush 或 sink 逻辑
    }
}
```

### 状态存储与 changelog

Kafka Streams 的状态默认存储在本地 RocksDB 中，每个任务的状态变更会写回到 Kafka 的 **changelog topic** 中实现容错：

```text
┌─────────────────────────────────────────────┐
│            Kafka Streams Task               │
│  ┌─────────────┐      ┌─────────────────┐  │
│  │  输入分区    │ ──→  │  RocksDB 状态    │  │
│  │  (source)   │      │  (key-value)    │  │
│  └─────────────┘      └────────┬────────┘  │
│                                │           │
│                                ▼           │
│                       ┌─────────────────┐  │
│                       │ changelog topic │  │
│                       │ （容错/恢复）    │  │
│                       └─────────────────┘  │
└─────────────────────────────────────────────┘
```

关键参数：

- `state.dir`：本地状态目录，生产环境应使用持久化卷。
- `processing.guarantee`：可设为 `exactly_once_v2` 开启事务语义。
- `num.stream.threads`：每个应用实例内的并行线程数。

### Exactly-once 语义与 KIP-890

Kafka Streams 的 exactly-once 依赖 Kafka 事务协议（producer idempotency + transactional API）。Kafka 4.0 引入了 **KIP-890: Transactions Server-Side Defense**，在服务端强化了事务 epoch bump 语义，减少因网络重试/延迟导致的"悬挂事务"与重复风险。

```properties
# Kafka Streams exactly-once v2 配置
processing.guarantee=exactly_once_v2
producer.idempotence=true
producer.transactional.id=streams-app-${application.id}-${task.id}
```

【定理】Kafka producer idempotency 保证同一分区内单 producer 会话的"恰好一次"投递（KIP-98/KIP-360）；Kafka Streams 通过 transactional.id 与 Kafka 事务协议把消费者偏移与生产者输出绑定，实现端到端 exactly-once。

【论证】KIP-890 在服务端增加了对事务 epoch 的校验，是 4.0 以后提升 exactly-once 健壮性的关键补充，而非替代原有事务协议。选型时若对事务一致性要求极高，建议将 broker 升级至 4.0+。

## 1.53.3 Apache Flink

Apache Flink 是独立于消息系统的通用流处理框架，支持 DataStream、Table API 和 SQL，是当前复杂事件处理（CEP）和大规模实时 ETL 的主流选择。Flink 2.0.0 于 2025-03-24 发布，2.3.0 为当前最新稳定版。

### DataStream / Table API 与事件时间

| API | 抽象 | 适用人群 | 与 SQL 关系 |
| --- | --- | --- | --- |
| **DataStream API** | 命令式数据流 | Java/Scala/Python 开发者 | 可调用 Table API 互转 |
| **Table API** | 关系式声明式 | 熟悉 DataFrame/SQL 的开发者 | Flink SQL 的运行时 |
| **Flink SQL** | 标准 SQL 扩展 | 数据工程师/分析师 | 通过 calcite 解析为 dataflow |

Flink 的核心时间语义：

- **Event Time**：数据本身携带的时间戳，最符合业务语义，但需处理乱序。
- **Processing Time**：机器处理时间，低延迟但结果不稳定。
- **Ingestion Time**：数据进入 Flink 的时间，介于两者之间。

水位线（Watermark）示例：

```java
DataStream<Event> withTimestamps = stream
    .assignTimestampsAndWatermarks(
        WatermarkStrategy
            .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(30))
            .withTimestampAssigner((event, ts) -> event.eventTimeMs())
    );
```

### Checkpoint、Savepoint 与状态后端

Flink 通过分布式快照实现容错：

- **Checkpoint**：周期性自动触发，用于故障恢复。
- **Savepoint**：手动触发，用于升级、迁移、A/B 测试。
- **State Backend**：RocksDB（大状态、增量 checkpoint）、ForSt（Flink 2.0 引入的远程状态后端）、HashMap（小状态、内存）。

```java
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

env.enableCheckpointing(60000);                    // 每分钟 checkpoint
env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);
env.getCheckpointConfig().setMinPauseBetweenCheckpoints(30000);
env.setStateBackend(new EmbeddedRocksDBStateBackend(true)); // 增量 checkpoint
```

Flink 2.0 进一步推动了 **Disaggregated State**（状态与计算分离），目标是在云原生环境下实现更弹性的扩缩容与更快的恢复。

### 与 Kafka / Pulsar 的集成

Flink 通过 connector 与多种 MQ 集成。Kafka connector 支持 source/sink 两种模式，并支持精确一次写入：

```java
KafkaSource<Order> source = KafkaSource.<Order>builder()
    .setBootstrapServers("kafka.internal:9092")
    .setTopics("orders")
    .setGroupId("flink-orders-group")
    .setStartingOffsets(OffsetsInitializer.earliest())
    .setValueOnlyDeserializer(new OrderDeserializationSchema())
    .build();

KafkaSink<Result> sink = KafkaSink.<Result>builder()
    .setBootstrapServers("kafka.internal:9092")
    .setRecordSerializer(KafkaRecordSerializationSchema.builder()
        .setTopic("order-analytics")
        .setValueSerializationSchema(new ResultSerializationSchema())
        .build())
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .setTransactionalIdPrefix("flink-sink-")
    .build();
```

Pulsar connector 同样支持 source/sink 与精确一次语义，适合已在 Pulsar 上构建统一事件总线的企业。

## 1.53.4 轻量替代：Bytewax 与 Arroyo

并非所有场景都需要 Kafka Streams 或 Flink 的完整能力。对于中小规模、Python 友好或 Rust 高性能场景，可考虑以下轻量引擎。

### Bytewax

Bytewax 是基于 Rust Timely Dataflow 的 Python 流处理框架，定位是"Python 生态中的轻量 Flink"。

```python
from bytewax.dataflow import Dataflow
from bytewax.connectors.kafka import KafkaSource, KafkaSink
from bytewax import operators as op

flow = Dataflow("orders-count")
orders = op.input("orders-input", flow, KafkaSource(["kafka.internal:9092"], ["orders"]))

# 按 user_id 分组并统计
keyed = op.key_on("key", orders, lambda x: x["user_id"])
counts = op.count_window("count", keyed, timedelta(minutes=5))
op.output("out", counts, KafkaSink(["kafka.internal:9092"], "order-counts"))
```

特点：

- Python 原生，适合数据科学团队。
- Rust 核心提供较低调度开销。
- 社区规模与生态成熟度不及 Flink，适合从 0 到 1 的实时管道。

### Arroyo

Arroyo 是用 Rust 编写的分布式流处理引擎，主打低延迟与高吞吐，采用 SQL 优先接口。截至 2025-12-01 发布 0.15.0，采用 Apache 2.0 许可证。

```sql
-- Arroyo SQL 示例
CREATE TABLE orders (
  order_id BIGINT,
  user_id BIGINT,
  amount DECIMAL(10,2),
  event_time TIMESTAMP
) WITH (
  connector = 'kafka',
  topic = 'orders',
  format = 'json'
);

CREATE TABLE revenue WITH (
  connector = 'kafka',
  topic = 'user-revenue',
  format = 'json'
) AS
SELECT user_id,
       SUM(amount) AS total,
       TUMBLE(event_time, INTERVAL '5' MINUTE) AS window
FROM orders
GROUP BY user_id, TUMBLE(event_time, INTERVAL '5' MINUTE);
```

特点：

- 单一二进制部署，运维简单。
- 与 Kafka/Redpanda 兼容。
- 版本尚处 0.x，生产环境需评估稳定性与社区支持。

## 1.53.5 对比矩阵与选型决策树

### 对比矩阵

| 维度 | Kafka Streams | Apache Flink | Bytewax | Arroyo |
| --- | --- | --- | --- | --- |
| **核心语言** | Java/Scala | Java/Scala/Python/SQL | Python（Rust 核心） | Rust + SQL |
| **与 MQ 耦合度** | 只读 Kafka | 多源（Kafka/Pulsar/RabbitMQ 等） | Kafka 为主 | Kafka/Redpanda 为主 |
| **状态管理** | 本地 RocksDB + changelog topic | RocksDB/ForSt + 远程状态 | 本地/内存 | 内建状态后端 |
| **事件时间/水位线** | 支持（窗口时间语义较简化） | 完整支持 | 基础支持 | SQL 窗口支持 |
| **Exactly-once** | 支持（依赖 Kafka 事务） | 支持（checkpoint + 两阶段提交） | 支持 | 支持 |
| **部署模式** | 嵌入应用进程 | K8s/YARN/Standalone | Python 进程/K8s | 单二进制/K8s |
| **SQL 支持** | 无原生 SQL（需 ksqlDB） | Flink SQL | 无 | SQL 优先 |
| **典型场景** | 事件驱动微服务、Kafka 原生 ETL | 复杂 CEP、大规模实时 ETL | Python 数据管道、轻量聚合 | 低延迟 SQL 流处理 |
| **运维复杂度** | 低 | 高 | 低 | 低中 |

### 与 MQ 耦合度说明

```text
┌────────────────────────────────────────────────────────────┐
│                    与 MQ 耦合度光谱                         │
└────────────────────────────────────────────────────────────┘

  高度耦合                          中度解耦                   完全独立
     │                                │                         │
     ▼                                ▼                         ▼
┌──────────┐                    ┌──────────┐              ┌──────────┐
│ Kafka    │  ───────────────→  │ Flink    │  ─────────→  │ Spark    │
│ Streams  │   只读 Kafka        │ 多源      │   任意 MQ    │ Streaming│
│ ksqlDB   │                    │ Arroyo   │              │          │
└──────────┘                    └──────────┘              └──────────┘
```

- **高度耦合**：选型时应确认长期锁定 Kafka 生态可接受；优势是部署简单、语义一致。
- **中度解耦**：适合异构 MQ 环境或未来可能替换消息系统的企业。
- **完全独立**：适合批流统一或已有 Spark 生态的企业。

### 选型决策树

```text
开始
 │
 ├─ 是否只需要在 Kafka 上做过滤/聚合/微服务化？
 │    ├─ 是 ──→ Kafka Streams（Java 团队）或 ksqlDB（SQL 团队）
 │    └─ 否
 │
 ├─ 是否需要复杂窗口、CEP、多源 join、大规模状态？
 │    ├─ 是 ──→ Apache Flink
 │    └─ 否
 │
 ├─ 团队主力是 Python 且状态规模不大？
 │    ├─ 是 ──→ Bytewax
 │    └─ 否
 │
 └─ 是否希望 SQL 优先、低运维、单二进制？
      ├─ 是 ──→ Arroyo（评估 0.x 稳定性）
      └─ 否 ──→ 回到 Flink 或 Kafka Streams
```
