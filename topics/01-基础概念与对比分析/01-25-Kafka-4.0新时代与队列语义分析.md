## 1.25.1 Kafka 4.0：ZooKeeper 时代的终结

**Kafka 4.0.0 于 2025-03-18 发布**，这是 Kafka 三年来第一个大版本，其最核心的变化不是新增功能，而是**做减法**：

| 变化 | 内容 | 影响 |
| ------ | ------ | ------ |
| **ZooKeeper 彻底移除** | 不是弃用（deprecated），是移除（removed）。4.x 所有集群只能以 KRaft 模式运行 | 集群架构简化为单一组件；ZK 运维经验不再适用；迁移必须先经过 3.9 |
| **旧消息格式移除** | v0/v1 消息格式退出支持 | 升级前必须确认无遗留旧格式数据 |
| **MirrorMaker 1 移除** | 旧版 MM1 退出，仅保留 MirrorMaker 2（基于 Connect） | 跨集群复制方案收敛到 MM2 |
| **Scala 2.12 支持移除** | 仅支持 Scala 2.13 | 构建依赖更新 |
| **Java 基线提高** | Broker/Connect/工具要求 Java 17+；客户端与 Kafka Streams 要求 Java 11+ | 老 JVM 环境必须先升级 JDK |

**架构意义**：Kafka 的"控制面"（元数据共识）与"数据面"（日志复制）现在都运行在同一套 Raft 协议族上，消除了运行两套分布式系统（Kafka + ZK）带来的协调成本。官方与社区实测表明 KRaft 模式可支撑**百万级分区**的元数据规模，而 ZK 模式在数万分区后元数据延迟显著恶化。

## 1.25.2 4.0 升级门槛与迁移路径

```text
升级决策树
├── 当前运行在 ZooKeeper 模式？
│   ├── 是 → 必须先升级至 3.9.x（最后的 ZK 版本，迁移工具最成熟）
│   │         → 在 3.9 上执行 ZK→KRaft 迁移（kafka-metadata-quorum 工具）
│   │         → 验证 KRaft 稳定运行后 → 再升级至 4.x
│   └── 否（已是 KRaft 3.x）→ 可直接滚动升级至 4.x
├── JDK 达标？
│   ├── Broker 节点 Java 17+ / 客户端 Java 11+ → 通过
│   └── 否则先升级 JDK
├── 客户端兼容性检查
│   ├── 是否存在 0.10.x 之前的远古客户端 → 先升级客户端
│   └── 检查 __consumer_offsets 等内部 topic 格式
└── MirrorMaker 1 用户 → 先迁移至 MM2
```

**关键检查命令**：

```bash
# 检查当前集群模式（3.9 之前为 ZK 模式则显示 zookeeper.connect 配置）
grep -E "zookeeper.connect|process.roles" config/server.properties

# 3.9 上查看 KRaft 迁移状态
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status

# 4.x 集群状态
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

## 1.25.3 KIP-848：新一代消费者组协议

Kafka 4.0 将 **KIP-848（新一代消费者组协议）转为 GA**，这是自消费者组机制诞生以来最大的一次重设计：

| 维度 | 旧协议（Classic） | 新协议（KIP-848） |
| ------ | ------------------ | ------------------- |
| **再均衡方式** | 全局 stop-the-world 再均衡 | 增量式、按分区转移，无全局停顿 |
| **组成员管理** | 消费者直接协商 | 由 Group Coordinator 集中决策 |
| **元数据同步** | 心跳线程同步完整分配信息 | 服务端推送增量变更 |
| **弹性** | 扩容/缩容触发全组再均衡 | 单分区粒度转移，影响面小 |

**运维影响**：消费者组再均衡导致的消费暂停时间从秒级降到接近零，这对微服务场景（频繁部署重启消费者）是实质性改善。

## 1.25.4 KIP-932：Queues for Kafka 与 Share Groups

**这是 Kafka 近十年最重要的语义扩展**：传统上 Kafka 是"日志"（log）——每条消息可被多个独立消费者组读取；KIP-932 引入 **Share Groups（共享组）**，在日志之上叠加"队列"（queue）语义。

### 核心机制

```text
传统消费者组（Consumer Group）          Share Group（KIP-932）
┌─────────┐ ┌─────────┐                 ┌─────────┐ ┌─────────┐
│ C1      │ │ C2      │                 │ S1      │ │ S2      │
│ P0 P1   │ │ P2 P3   │                 │ ↓       │ │ ↓       │
└────┬────┘ └────┬────┘                 │ 同一分区内│ │ 不同记录 │
     │ 一个分区同一时刻只归一个消费者      │ 多消费者协作│ │          │
     │                                    └────┬────┘ └────┬────┘
┌────┴──────────────────┐              ┌────────┴─────────────┐
│ Topic: 4 partitions   │              │ Topic: 4 partitions  │
└───────────────────────┘              │ Broker 跟踪每条记录的  │
                                       │ 获取-确认-重试状态      │
                                       │ (__share_group_state)  │
                                       └────────────────────────┘
```

**三个关键差异**：

1. **突破消费者数 ≤ 分区数限制**：传统组中一个分区同一时刻只能被一个消费者消费，并行度受分区数限制；Share Group 允许同一分区的不同记录被不同消费者并发处理。
2. **按记录确认（per-record acknowledgment）**：Broker 端跟踪每条记录的投递状态（`__share_group_state` 内部主题），消费失败自动重投——这是"队列"语义的核心。
3. **不引入真正的"队列"对象**：Topic 仍然是日志，保留期内的数据仍可供其他消费组按流方式读取。队列语义只是消费侧的另一种模式。

### 发布节奏

| 版本 | KIP-932 状态 |
| ------ | ------------ |
| Kafka 4.0 | Early Access：默认禁用，须显式在服务端开启，不建议生产使用 |
| Kafka 4.1 | Preview：可评估测试，API 趋于稳定 |
| Kafka 4.2（路线图） | 计划 GA：生产可用 |

### 客户端示例（4.1 Preview API）

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "share-group-1");
// Share Group 消费者：使用 KafkaShareConsumer
KafkaShareConsumer<String, String> consumer = new KafkaShareConsumer<>(
    props, new StringDeserializer(), new StringDeserializer());
consumer.subscribe(Collections.singleton("orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
    for (ConsumerRecord<String, String> r : records) {
        process(r);
        // 逐条确认；未确认的记录由 Broker 自动重投
        consumer.commitSync(Collections.singletonMap(
            new TopicPartition(r.topic(), r.partition()),
            new ShareAcknowledgementBatch(...)));
    }
}
```

### 边界与限制（Early Access / Preview 阶段）

- **无顺序保证**：Share Group 明确不保证分区顺序；需要顺序时仍须使用传统消费者组 + key 路由
- **服务端状态开销**：`__share_group_state` 主题带来额外的写入放大，高吞吐场景需压测验证
- **生态滞后**：监控工具（如 KMinion）、Spring Kafka 等框架的支持在逐步跟进，采用前需确认所用框架版本

## 1.25.5 分层存储与其他 4.x 演进

**分层存储（Tiered Storage，KIP-405）在 4.x 成熟稳定**：热数据保留在本地磁盘，冷数据自动卸载到对象存储（S3 等），对长期保留场景（合规审计、事件溯源重放）显著降低存储成本。4.x 的主要演进方向：

| 方向 | 说明 |
| ------ | ------ |
| **分层存储深化** | 与 Confluent Tableflow 等"流→湖仓"管道配合，Kafka 数据直接落地 Iceberg 表 |
| **Stream Groups** | 4.1 引入的流式消费组抽象，简化流处理场景的组管理 |
| **ELR** | 4.1 起新集群默认开启早期领导者重平衡，缩短分区不可用窗口 |
| **Queues（KIP-932）** | 见 1.25.4，4.x 周期的旗舰特性 |

## 1.25.6 对选型的影响：Kafka 与 RabbitMQ/SQS 的边界变化

KIP-932 改变了经典的"Kafka 做流、RabbitMQ/SQS 做队列"二分法。更新后的决策逻辑：

```text
需要队列语义（ competing consumers + 自动重试 + 逐条确认）？
├── 是 → 且已重度使用 Kafka 生态？
│   ├── Kafka 4.2+（Share Groups GA 后）→ 同一平台兼得队列与流
│   ├── Kafka 4.0/4.1 → 生产仍建议 RabbitMQ / SQS，KIP-932 仅用于评估
│   └── 极致运维简单 → 云托管 SQS / Pub/Sub
└── 否（纯日志/流处理/多消费者独立读取）→ Kafka 依旧是最优解
```

| 场景 | 4.0 之前的答案 | 4.2（Share Groups GA）后的答案 |
| ------ | -------------- | ------------------------------ |
| 任务队列（订单异步处理） | RabbitMQ / SQS | Kafka Share Group 成为可行选项 |
| 事件溯源 + 审计重放 | Kafka（唯一选择） | Kafka（不变） |
| 微服务消息总线 | RabbitMQ / NATS | Kafka Share Group / NATS 均可 |
| 需要严格消息顺序 | Kafka 分区级有序 | 不变（Share Group 不保序） |
