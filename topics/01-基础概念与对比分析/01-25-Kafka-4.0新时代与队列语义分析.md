## 1.25.1 Kafka 4.0：ZooKeeper 时代的终结

**Kafka 4.0.0 于 2025-03-18 发布**，这是 Kafka 三年来第一个大版本，其最核心的变化不是新增功能，而是**做减法**：

| 变化 | 内容 | 影响 |
| ------ | ------ | ------ |
| **ZooKeeper 彻底移除** | 不是弃用（deprecated），是移除（removed）。4.x 所有集群只能以 KRaft 模式运行 | 集群架构简化为单一组件；ZK 运维经验不再适用；迁移必须先经过 3.9 |
| **旧消息格式移除** | v0/v1 消息格式退出支持 | 升级前必须确认无遗留旧格式数据 |
| **MirrorMaker 1 移除** | 旧版 MM1 退出，仅保留 MirrorMaker 2（基于 Connect） | 跨集群复制方案收敛到 MM2 |
| **Scala 2.12 支持移除** | 仅支持 Scala 2.13 | 构建依赖更新 |
| **Java 基线提高** | Broker/Connect/工具要求 Java 17+；客户端与 Kafka Streams 要求 Java 11+ | 老 JVM 环境必须先升级 JDK |

**架构意义**：Kafka 的"控制面"（元数据共识）与"数据面"（日志复制）现在都运行在同一套 Raft 协议族上，消除了运行两套分布式系统（Kafka + ZK）带来的协调成本。官方与社区实测表明 KRaft 模式可支撑**百万级分区**的元数据规模，而 ZK 模式在数万分区后元数据延迟显著恶化。

## 1.25.2 4.0 升级门槛与迁移路径

```text
升级决策树
├── 当前运行在 ZooKeeper 模式？
│   ├── 是 → 必须先升级至 3.9.x（最后的 ZK 版本，迁移工具最成熟）
│   │         → 在 3.9 上执行 ZK→KRaft 迁移（kafka-metadata-quorum 工具）
│   │         → 验证 KRaft 稳定运行后 → 再升级至 4.x
│   └── 否（已是 KRaft 3.x）→ 可直接滚动升级至 4.x
├── JDK 达标？
│   ├── Broker 节点 Java 17+ / 客户端 Java 11+ → 通过
│   └── 否则先升级 JDK
├── 客户端兼容性检查
│   ├── 是否存在 0.10.x 之前的远古客户端 → 先升级客户端
│   └── 检查 __consumer_offsets 等内部 topic 格式
└── MirrorMaker 1 用户 → 先迁移至 MM2
```

**关键检查命令**：

```bash
# 检查当前集群模式（3.9 之前为 ZK 模式则显示 zookeeper.connect 配置）
grep -E "zookeeper.connect|process.roles" config/server.properties

# 3.9 上查看 KRaft 迁移状态
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status

# 4.x 集群状态
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

## 1.25.3 KIP-848：新一代消费者组协议

Kafka 4.0 将 **KIP-848（新一代消费者组协议）转为 GA**，这是自消费者组机制诞生以来最大的一次重设计：

| 维度 | 旧协议（Classic） | 新协议（KIP-848） |
| ------ | ------------------ | ------------------- |
| **再均衡方式** | 全局 stop-the-world 再均衡 | 增量式、按分区转移，无全局停顿 |
| **组成员管理** | 消费者直接协商 | 由 Group Coordinator 集中决策 |
| **元数据同步** | 心跳线程同步完整分配信息 | 服务端推送增量变更 |
| **弹性** | 扩容/缩容触发全组再均衡 | 单分区粒度转移，影响面小 |

**运维影响**：消费者组再均衡导致的消费暂停时间从秒级降到接近零，这对微服务场景（频繁部署重启消费者）是实质性改善。

## 1.25.4 KIP-932：Queues for Kafka 与 Share Groups

**这是 Kafka 近十年最重要的语义扩展**：传统上 Kafka 是"日志"（log）——每条消息可被多个独立消费者组读取；KIP-932 引入 **Share Groups（共享组）**，在日志之上叠加"队列"（queue）语义。

### 核心机制

```text
传统消费者组（Consumer Group）          Share Group（KIP-932）
┌─────────┐ ┌─────────┐                 ┌─────────┐ ┌─────────┐
│ C1      │ │ C2      │                 │ S1      │ │ S2      │
│ P0 P1   │ │ P2 P3   │                 │ ↓       │ │ ↓       │
└────┬────┘ └────┬────┘                 │ 同一分区内│ │ 不同记录 │
     │ 一个分区同一时刻只归一个消费者      │ 多消费者协作│ │          │
     │                                    └────┬────┘ └────┬────┘
┌────┴──────────────────┐              ┌────────┴─────────────┐
│ Topic: 4 partitions   │              │ Topic: 4 partitions  │
└───────────────────────┘              │ Broker 跟踪每条记录的  │
                                       │ 获取-确认-重试状态      │
                                       │ (__share_group_state)  │
                                       └────────────────────────┘
```

**三个关键差异**：

1. **突破消费者数 ≤ 分区数限制**：传统组中一个分区同一时刻只能被一个消费者消费，并行度受分区数限制；Share Group 允许同一分区的不同记录被不同消费者并发处理。
2. **按记录确认（per-record acknowledgment）**：Broker 端跟踪每条记录的投递状态（`__share_group_state` 内部主题），消费失败自动重投——这是"队列"语义的核心。
3. **不引入真正的"队列"对象**：Topic 仍然是日志，保留期内的数据仍可供其他消费组按流方式读取。队列语义只是消费侧的另一种模式。

### 发布节奏

| 版本 | KIP-932 状态 |
| ------ | ------------ |
| Kafka 4.0 | Early Access：默认禁用，须显式在服务端开启，不建议生产使用 |
| Kafka 4.1 | Preview：可评估测试，API 趋于稳定 |
| Kafka 4.2 | GA：生产可用，官方标记为 production-ready |

### 客户端示例（4.1 Preview API）

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "share-group-1");
// Share Group 消费者：使用 KafkaShareConsumer
KafkaShareConsumer<String, String> consumer = new KafkaShareConsumer<>(
    props, new StringDeserializer(), new StringDeserializer());
consumer.subscribe(Collections.singleton("orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
    for (ConsumerRecord<String, String> r : records) {
        process(r);
        // 逐条确认；未确认的记录由 Broker 自动重投
        consumer.commitSync(Collections.singletonMap(
            new TopicPartition(r.topic(), r.partition()),
            new ShareAcknowledgementBatch(...)));
    }
}
```

### 边界与限制（Early Access / Preview 阶段）

- **无顺序保证**：Share Group 明确不保证分区顺序；需要顺序时仍须使用传统消费者组 + key 路由
- **服务端状态开销**：`__share_group_state` 主题带来额外的写入放大，高吞吐场景需压测验证
- **生态滞后**：监控工具（如 KMinion）、Spring Kafka 等框架的支持在逐步跟进，采用前需确认所用框架版本

## 1.25.5 分层存储与 4.x 后续演进

**分层存储（Tiered Storage，KIP-405）在 4.x 成熟稳定**：热数据保留在本地磁盘，冷数据自动卸载到对象存储（S3 等），对长期保留场景（合规审计、事件溯源重放）显著降低存储成本。

### Kafka 4.2：KIP-932 GA 与队列语义成熟

**Kafka 4.2.0 于 2026-02-17 发布**，旗舰变化是 **KIP-932（Queues for Kafka / Share Groups）转为 production-ready**，标志着 Kafka 正式具备原生队列语义。Confluent 亦在同窗口期将 Queues for Kafka 在 Confluent Cloud 与 Confluent Platform 中转为 GA。

> **生态格局注记（批次 87，2026-11 核实）**：[IBM 于 2026-03-17 完成 110 亿美元收购 Confluent](https://newsroom.ibm.com/2026-03-17-ibm-completes-acquisition-of-confluent,-making-real-time-data-the-engine-of-enterprise-ai-and-agents)（2025-12-08 宣布，$31/股）。短期 Confluent 独立运营且 Kafka Apache 项目治理不变（Apache 软件基金会独立于收购方）【论证】；中期需跟踪：WarpStream/Tableflow 产品线归属整合（见 [01-70](01-70-流表一体与开放表格式收敛深度解析.md)）、许可证策略变化（见 [01-34](01-34-消息系统许可证与选型合规分析.md)）、Confluent 社区版限制条款修订——以上列入版本追踪清单季度复核项。

4.2 中围绕 Share Groups 的配套增强：

| KIP | 作用 |
| ----- | ------ |
| **KIP-1222** | 新增 `RENEW` 确认类型，允许消费者显式延长获取锁超时，适应长任务处理 |
| **KIP-1224** | Group Coordinator 与 Share Coordinator 支持自适应批处理，降低 5ms 延迟地板 |
| **KIP-1206** | `ShareAcquireMode` 支持 `batch_optimized`（软限制）与 `record_limit`（硬限制）两种最大获取记录数策略 |
| **KIP-1226** | 引入 Share Partition Lag 持久化与指标，便于观察消费进度与后续自动扩缩容 |
| **KIP-1227** | Admin API 暴露 consumer/share group 成员的 rack ID |

其它 notable 变化：KIP-1147 统一 CLI 参数（`--bootstrap-server` / `--command-config`），KIP-1188 引入 allowlist 连接器客户端配置覆盖策略以封堵安全漏洞，KIP-1034 为 Kafka Streams 异常处理器加入死信队列（DLQ）支持。

### Kafka 4.3：Share Groups 调优与 Classic Rebalance 弃用启动

**Kafka 4.3.0 于 2026-05-22 发布**，包含 25 个 KIP、600+ 次提交。该版本以"调优与弃用铺垫"为主，没有单一旗舰特性，但对运维意义重大：

| KIP | 作用 |
| ----- | ------ |
| **KIP-1240** | 为 Share Groups 新增一组 broker/group 级配置，细化行为控制 |
| **KIP-1274（第一阶段）** | 在 `classic` rebalance 协议启动时打印建议迁移日志，Classic 协议将在未来版本弃用 |
| **KIP-1066** | 引入 `cordoned.log.dirs` 配置，可对日志目录进行隔离，便于缩容或下线 broker/log dir |
| **KIP-1023** | 新增 `follower.fetch.last.tiered.offset.enable`，允许 follower 从 tiered offset 开始抓取，加速新 follower 启动 |
| **KIP-1196** | Group/Share Coordinator 增加 `append.max.buffer.size` 配置与 buffer 使用率指标 |

### Kafka 4.4：Share Groups DLQ 与控制器可注销

**Kafka 4.4.0 于 2026-10-22 发布**，包含 25 个 KIP、963 次提交。对队列语义而言，最关键的补全是 **死信队列（DLQ）**：

| KIP | 作用 |
| ----- | ------ |
| **KIP-1191** | Share Groups 支持死信队列；超过最大投递次数或被 reject 的记录可写入 DLQ topic（须将 `share.version` 升级到 2） |
| **KIP-1312** | 支持从集群元数据中注销控制器，`kafka-cluster.sh unregister-controller` 与 `Admin#unregisterController` 提供运维手段 |
| **KIP-1241** | 引入 `remote.copy.lag.bytes` / `remote.copy.lag.ms`，允许通过延迟上传降低分层存储冗余 |
| **KIP-1220** | `kafka-cluster.sh api-versions` 替代 `kafka-broker-api-versions.sh` |
| **KIP-1209** | Kafka Connect 支持 `internal.topics.automatic.creation.enable` 控制内部 topic 自动创建 |

KIP-1191 补齐了 KIP-932 在" poison message "场景下的最后一块拼图：4.2 之前只能通过 reject/重投次数人工处理，4.4 起可自动转储到 DLQ topic，与 RabbitMQ/SQS 的 DLQ 行为对齐。

### 版本支持策略

Apache Kafka 社区采用时间驱动发布计划：目标每年 3 个大版本、约每 4 个月一次 minor release；补丁版本仅对"支持的 release"发布。官方 EOL 策略表述为"尽力为最近 3 个 release 提供 bugfix release"。

截至 2026-10-22（4.4.0 发布），Apache Kafka 官方下载页"Supported releases"栏目列出 **4.4.x、4.3.x、4.2.x**；4.1.x 与更早版本进入归档。这意味着生产集群若运行 4.1 及以下，应规划升级到仍在支持窗口的版本。

## 1.25.6 对选型的影响：Kafka 与 RabbitMQ/SQS 的边界变化

KIP-932 改变了经典的"Kafka 做流、RabbitMQ/SQS 做队列"二分法。更新后的决策逻辑：

```text
需要队列语义（ competing consumers + 自动重试 + 逐条确认）？
├── 是 → 且已重度使用 Kafka 生态？
│   ├── Kafka 4.2+（Share Groups GA 后）→ 同一平台兼得队列与流
│   ├── Kafka 4.4+（KIP-1191 DLQ）→ 更适合任务队列/工单队列等需要死信队列的场景
│   ├── Kafka 4.0/4.1 → 生产仍建议 RabbitMQ / SQS，KIP-932 仅用于评估
│   └── 极致运维简单 → 云托管 SQS / Pub/Sub
└── 否（纯日志/流处理/多消费者独立读取）→ Kafka 依旧是最优解
```

| 场景 | 4.0 之前的答案 | 4.2（Share Groups GA）后的答案 |
| ------ | -------------- | ------------------------------ |
| 任务队列（订单异步处理） | RabbitMQ / SQS | Kafka Share Group 成为可行选项 |
| 事件溯源 + 审计重放 | Kafka（唯一选择） | Kafka（不变） |
| 微服务消息总线 | RabbitMQ / NATS | Kafka Share Group / NATS 均可 |
| 需要严格消息顺序 | Kafka 分区级有序 | 不变（Share Group 不保序） |
| 需要死信队列（poison message） | RabbitMQ / SQS | Kafka 4.4+（KIP-1191 DLQ） |

**4.x 版本选择速查**（截至 2026-11）：

| 需求 | 建议版本 | 说明 |
| ------ | -------- | ---- |
| 新建集群 | 4.4.x | 官方当前支持线之首，含 KIP-1191 DLQ |
| 需要队列语义（Share Groups） | ≥ 4.2 | KIP-932 production-ready 起始版本 |
| 运行 4.2 / 4.3 | 规划滚动升级 | 补丁支持以官方"最近三个 release"策略为准 |

> 升级前务必核对 [官方下载页支持窗口](https://kafka.apache.org/community/downloads/)：官方仅为最近三个 release 线提供补丁（当前 4.4.x / 4.3.x / 4.2.x）。

> **动态系统论视角**：Kafka 4.x 的演进（ZK 移除、KRaft、Share Groups、DLQ）反映了消息系统在技术债务与路径依赖下的动态演化。若需从时间维度、锁定效应、配置演化延迟等角度理解其演化动力学，参见 [04-02 时间维度演化分析](../04-动态系统论与演化分析/04-02-时间维度演化分析.md)。
