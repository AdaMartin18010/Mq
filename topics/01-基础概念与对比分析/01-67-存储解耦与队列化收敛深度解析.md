## 1.67.1 背景：本地磁盘日志的三重瓶颈

经典消息存储（Kafka segment、Pulsar ledger、RabbitMQ queue index）以本地磁盘为权威副本，带来三重结构性瓶颈：

1. **容量瓶颈**：保留期与磁盘成本线性绑定——3 副本 × 30 天 × 10TB/日 = 900TB 裸容量【估算】；
2. **弹性瓶颈**：分区/副本迁移以 GB 级数据拷贝为前提，扩缩容分钟-小时级（01-61 §1.61.6）；
3. **多租户瓶颈**：峰值预留按最坏情况采购，平均利用率常低于 30%【估算】。

对象存储（S3 类）以 3-5 倍成本差与无限弹性成为国际主流答案（01-29 成本对比论证）。2024-2026 年形成四条工程路线，收敛方式各异。

## 1.67.2 存储解耦四路线对比

| 路线 | 代表 | 开源 | 权威副本位置 | 本地角色 | 状态（核实至 2026-11） |
| ---- | ---- | ---- | ---- | ---- | ---- |
| A. Kafka 内建分层 | Apache Kafka（KIP-405） | ✅ Apache-2.0 | 本地（热段）+S3（冷段） | 权威（近期） | production-ready 自 Kafka 3.9（01-61 已核实） |
| B. 独立存储引擎 | AutoMQ | ✅（Apache-2.0 系） | **S3 即权威** | 仅缓存（无状态 broker） | 活跃开源，Kafka 协议兼容 |
| C. 商业云原生 | Bufstream | ❌（Buf 商业） | S3（+etcd 协调） | 缓存 | [Jepsen 0.1 报告](https://jepsen.io/analyses/bufstream-0.1.0)（2024-11）：3 safety+2 liveness，0.1.3 全修复；支持 Iceberg 元数据 |
| D. 托管吸收 | WarpStream → Confluent | ❌ | S3 | 缓存 | 2024 年被 Confluent 收购，技术并入 Confluent Cloud 弹性存储栈【论证】 |

```text
路线 A（内建分层）          路线 B/C/D（S3 权威）
┌──────────────┐           ┌──────────────┐
│ broker 本地   │ 权威热段   │ 无状态 broker │ 仅缓存+协调
│ segment(log) │ ──►S3 冷段 │ (可丢弃重建)  │
└──────┬───────┘           └──────┬───────┘
       │ ISR/LEO 语义保留          │ 段上传 S3 + 元数据协调(etcd/KRaft)
```

关键差异【论证】：路线 A 的 Kafka 语义原封不动（本地仍是权威），S3 只是"更深的段"；路线 B/C/D 把权威移交 S3，**ISR、LEO、分区迁移等概念被重新定义或删除**——语义变化集中在后者。

## 1.67.3 读写路径与故障模式

**读路径（S3 权威路线的差异点）**：冷数据 fetch 变为对象 GET，尾部延迟从磁盘毫秒级升至 S3 十-百毫秒级 P99【估算】；热点靠本地缓存/页缓存拦截。配置面关注：缓存容量、预取策略、远端并发上限。

```properties
# Kafka 内建分层存储关键参数（KIP-405，对照 config-templates 风格）
remote.log.storage.system.class=org.apache.kafka.server.log.remote.storage.NoOpRemoteStorageManager  # 生产中替换为 S3 RLSM 实现
remote.log.storage.manager.class.path=/opt/kafka/remote-storage
rlmm.config.remote.storage.manager.class=org.apache.kafka.rsm.s3.S3RemoteStorageManager
rlmm.config.s3.bucket.name=kafka-tiered
rlmm.config.s3.region=cn-north-1
log.retention.ms=604800000          # 与 remote.log.retention.ms 分层对账
remote.log.retention.ms=2592000000
```

**故障模式矩阵**：

| 故障 | 路线 A 行为 | S3 权威路线行为 | 测试要点 |
| ---- | ---- | ---- | ---- |
| S3 不可用 | 冷段读失败，热段读写不受影响 | **新写无法归档、缓存未命中读失败**；可用性耦合 S3 SLA | 分区故障注入：S3 断连 60s 期间的生产/消费断言 |
| broker 全损 | 副本重选（ISR 语义） | broker 无状态重建，缓存冷启动（读放大） | 冷启动恢复时间 RTO 测量 |
| 段上传中断 | 不适用（本地权威） | 孤儿段/元数据不一致风险 | 上传中途 kill broker，重启后段清单对账 |

## 1.67.4 语义变化矩阵：分层存储之后什么变了

对照 [01-61](01-61-Kafka存储与复制内幕深度解析.md) 的经典语义：

| 语义 | 内建分层（KIP-405） | S3 权威路线 | 依据 |
| ---- | ---- | ---- | ---- |
| 交付语义（acks/ISR） | **不变**（热路径本地完成） | 需重读实现：多数采用"写本地缓存即 ack+异步上传"，acks=all 的实际 durability 边界后移【论证】 | 各路线文档 |
| 顺序性 | 不变 | 不变（段内偏移仍单调） | 段结构保留 |
| exactly-once 事务 | 不变 | **需重新论证**：事务标记与数据段的上传原子性；Jepsen 已证 Kafka 事务协议本身不健全（见 [conformance-matrix](../..//Testing/06-契约语义测试/02-语义矩阵/conformance-matrix.md)），S3 路线叠加上传原子性问题 | Jepsen 2024-11【定理】 |
| retention | 双层：local + remote 各自保留期 | 单层（S3 生命周期策略） | 配置对照上表 |
| fetch 延迟尾部 | 冷读 S3 延迟 | 缓存未命中= S3 延迟（更严重） | 延迟预算重估【估算】 |
| 副本迁移/再平衡 | 不变（GB 级拷贝仍在） | **质变**：broker 无状态，再平衡=元数据操作（秒级） | AutoMQ/Bufstream 架构文档 |

**结论**【论证】：内建分层是"保守解"——零语义变化、弹性收益有限；S3 权威路线是"激进解"——弹性质变，但交付语义与事务语义的工程论证责任转移给了实现方，**选型时必须索取该实现的 Jepsen/一致性证据**（参照 01-67.9 与 conformance-matrix 的第三方证据纪律）。

## 1.67.5 队列化收敛：Share Groups / RabbitMQ Streams / Kora

"队列语义长在日志上"的三大国际信号：

**1. Kafka Share Groups（KIP-932，GA 于 Kafka 4.2——版本事实已核实）**：无分区分配的竞争消费——records 直接投递给共享组成员，天然队列语义（无序、竞争、自动再平衡）。**KIP-1191 为 share groups 增加 DLQ 能力（Kafka 4.4 落地——已核实）**。与 classic consumer group 的根本差异：

```text
classic group:  partition→member 静态映射（顺序性=分区序）
share group:    records→任意空闲成员 动态分发（顺序性放弃、弹性增益）
                ├─ share partition state: acquired/archived
                └─ delivery count → KIP-1191 DLQ 触发器
```

**2. RabbitMQ Streams**：队列的日志化反向运动——基于追加日志的 stream 队列，提供 replay/retention（传统队列无回放能力）；super stream 提供分区。形成"日志派学队列、队列派学日志"的双向收敛。

**3. Confluent Kora**：Confluent 自研 Kafka 引擎（闭源，用于 Confluent Cloud），公开技术细节有限【估算标注】——其在 2025 年后的分享显示：分层存储+无状态 broker 已是云厂商默认架构。国际市场信号：WarpStream 被收购、AutoMQ/Bufstream 获投资，方向一致性明确【论证】。

## 1.67.6 十二语义维度对照（TEST-14 清单）

| 维度 | share groups | RabbitMQ streams | 经典队列（对照） |
| ---- | ---- | ---- | ---- |
| 交付语义 | 至少一次（ack 确认制） | 至少一次 | 视系统（01-42） |
| 顺序性 | **放弃**（跨成员无序） | 分区（stream）内有序 | 单队列有序 |
| 幂等去重 | 应用层（无分区键语义） | 应用层 | 应用层 |
| 重试退避 | delivery count + DLQ（4.4） | 消费者重连重放 | 依实现 |
| 死信 | KIP-1191 DLQ（4.4 原生） | 无原生（应用重放） | DLX（RabbitMQ classic） |
| 事务 | 事务语义对 share groups 的组合=挂账（官方文档尚浅） | 无 | Kafka 事务（01-63） |
| 背压 | 动态分发天然削峰 | 游标控制流速 | prefetch/QoS |
| TTL过期 | 段级保留期 | TTL 有限支持 | per-message TTL |
| 延迟消息 | 无原生 | 无原生 | 无原生（02-16） |
| 消息过滤 | 无（share 内全量） | 无 | routing key |
| 流控 | 分发即流控 | credit | credit |
| 持久化 | 段持久化 | 日志持久化 | 依实现 |

**收敛判据**【论证】：当应用"不需要顺序、接受至少一次"（即传统队列场景占主导）时，share groups 使 Kafka 单一系统覆盖队列场景——这是 01-25 二分法瓦解后的终局形态之一。

## 1.67.7 测试含义：分层存储正确性维度

为 TC-SEM 扩展注册的测试维度（输入 [04-行为用例](../..//Testing/06-契约语义测试/04-行为用例/README.md)）：

1. **双层保留对账**：local retention < remote retention 时，冷热边界的消费一致性（边界 offset 不断流）；
2. **Offload 失败恢复**：上传中途故障，重启后段清单与本地一致性（无重复段/无空洞）；
3. **冷读一致性**：force.remote.read=true 下冷数据读回与本地校验和一致；
4. **S3 故障注入**：S3 断连窗口的生产不中断断言（热路径）+ 冷读失败降级标记；
5. **share groups 语义**：delivery count 递增、DLQ（4.4）触发、组成员进出时的不丢不重；
6. **RTO 测量**：broker 全损重建到可服务的时间（04 系列反脆弱度量的输入）。
