## 1.60.1 WASM 数据转换

### 国际现状

消息系统内嵌 WASM 运行时的趋势在 2025–2026 年进一步收敛为**"边缘-轻计算"**定位：不在 broker 内做重量级流处理，而是做协议适配、数据脱敏、路由标记、schema 校验等毫秒级转换。

- **Redpanda Data Transforms**：基于 `wasm32-wasi` 目标编译，SDK 提供 Rust/Go 支持【论证】。v25.3 为 2025-11 发布的主流支持版本，v25.2 支持期至 2026-11-19（官方版本生命周期页）【定理】。Transforms 运行在 broker 进程内的 WASM 沙箱中，可订阅 topic、处理记录并写出到新 topic，适合低延迟、有状态需求弱的场景。
- **Apache Pulsar Functions WASM 支持**：社区存在实验性 PR（如 `support WASM functions`）和第三方 `pulsar-function-wasm` 项目，但截至 2026-11 尚未进入 Pulsar 官方 Functions runtime 的正式发布通道【论证】。Pulsar 官方 runtime 仍为 process/thread/kubernetes 三种。
- **Envoy WASM filter**：Envoy 的 WASM 扩展机制已成熟，可用于 Kafka 协议过滤、MQTT 报文解析等 L7 场景。GitHub 上可见开发者询问如何扩展 Envoy L7 协议以支持 MQTT Request/Response 的 WASM filter 能力【论证】。 Envoy WASM 目前更常用于 HTTP/gRPC，对二进制消息协议的解析需要自定义协议解析器。

| 实现 | 成熟度 | 运行位置 | 典型场景 |
| ------ | -------- | ---------- | ---------- |
| Redpanda Data Transforms | GA（v25.x 支持） | Broker 进程内 WASM 沙箱 | 轻量 ETL、脱敏、路由 |
| Pulsar Functions WASM | 实验/第三方 | Function worker | 多语言 function |
| Envoy WASM filter | GA（HTTP 成熟，二进制消息需定制） | Sidecar/代理 | 协议转换、安全过滤 |

- Pulsar WASM function 讨论：[Apache Pulsar 邮件列表 PR](https://lists.apache.org/thread/l9ht3dqj98rfhpl5g944qyxlvr9zv1gl?find_parent=true)

**中**。Redpanda 已实现生产可用，但 Pulsar/Envoy 对二进制消息协议的 WASM 支持仍分散在实验/定制阶段；可写但需明确边界，避免与 1.31/1.54 重复。

## 1.60.2 eBPF 内核级观测

### 国际现状

2026 年 eBPF 在消息系统观测上的共识是**"无插桩协议解析"**：不修改 broker 或客户端代码，通过 kprobe/uprobe/TC 等钩子捕获 Kafka、MQTT、AMQP 等协议流量并导出为 metrics/traces/logs。

- **Cilium Kafka-aware network policy**：Cilium 从早期版本即支持 Kafka 协议感知策略，2025-05 博客明确其 L7 策略覆盖 HTTP、gRPC、Kafka、DNS【定理】。通过 `CiliumNetworkPolicy` 可针对 Kafka API key/topic 做细粒度访问控制。
- **Pixie / DeepFlow**：Pixie 使用 eBPF 做 Kubernetes 应用自动观测，支持 HTTP、gRPC、SQL、DNS 等协议自动解析；对 Kafka 协议的支持依赖社区演进。DeepFlow 明确支持 HTTP(S)、Kafka、MQTT、DNS 的零代码采集，通过 eBPF + Wasm 做协议解析【论证】。
- **OpenTelemetry eBPF Instrumentation (OBI)**：Grafana 于 2025 年把 Beyla 捐赠给 OpenTelemetry，形成 OBI 项目。2026-10-30 官方宣布 OBI 达到 **v1.0.0**【定理】。OBI 可自动生成 OpenTelemetry traces/metrics，目标是替代部分手动 SDK 插桩。

```yaml
# Cilium Kafka-aware L7 策略示例
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: kafka-topic-policy
spec:
  endpointSelector:
    matchLabels:
      app: kafka-client
  egress:
    - toEndpoints:
        - matchLabels:
            app: kafka-broker
      toPorts:
        - ports:
            - port: "9092"
              protocol: TCP
          rules:
            kafka:
              - role: produce
                topic: orders
              - role: consume
                topic: payments
```

- Cilium L7 策略博客：[Application-Aware Security Policies with Cilium Layer 7 Network Policies](https://cilium.io/blog/2025/05/20/cilium-l7-policies/)
- DeepFlow 协议支持：[DeepFlow GitHub](https://github.com/deepflowio/deepflow)

## 1.60.3 机密计算中的消息

### 国际现状

机密计算（Confidential Computing）在消息系统领域仍处于**"云 VM/容器级可用、broker 级原生支持不足"**的阶段。核心矛盾不是能否部署 broker，而是**传输加密无法解决内存中明文**的问题。

- **硬件成熟度**：Intel TDX、AMD SEV-SNP 已在主流云厂商 GA。Azure 新一代 Intel TDX 机密 VM（DCesv6/ECesv6）于 2026-02-26 GA；Google Cloud Confidential GKE Nodes（SEV-SNP/TDX）于 2025-05 GA；AWS Nitro Enclaves 持续可用【论证】。
- **Kafka 机密计算现状**：Apache Kafka 官方没有 TEE 原生特性；主流做法是**在机密 VM 或机密容器内运行 Kafka broker**，依赖 OS/ hypervisor 层面的内存加密。Confluent/云厂商未在 2026-11 前发布 broker 内嵌 TEE 支持的官方公告【论证】。
- **内存中明文问题**：TLS 保护传输、磁盘加密保护静态数据，但消息在 broker 内存中被反序列化、索引、复制时仍以明文存在。TEE 可减少云管理员/ hypervisor 的内存读取风险，但无法消除侧信道攻击（2025-10 TEE.fail、2026-09 DDRop 等研究针对 Intel TDX/AMD SEV-SNP 的物理/总线攻击）【论证】。

```yaml
# 机密 VM 上运行 Kafka broker 的最小信任边界示意
信任边界:
  - 外部: 客户端 TLS 终止后，明文进入 TEE
  - TEE 内: Kafka 进程 + JVM + 明文消息
  - 不可信: hypervisor、宿主机 OS、云运维人员
残留风险:
  - 侧信道 / 微架构攻击
  - TEE 内部恶意代码或配置错误
  - 明文落盘/交换页（需内存加密 + 禁用 swap）
```

- Google Cloud Confidential GKE Nodes：[Qovery 2026-11 合规就绪分析](https://www.qovery.com/blog/bsi-c5-post-quantum-confidential-computing-readiness)
- TEE.fail / DDRop 研究综述：[DDRop and the $200 Interposer](https://classicdba.com/security-grc/ddrop-and-the-200-interposer-what-a-physical-ddr5-attack-means-for-confidential-computing-and-ai-data-privacy-october-20)

## 1.60.4 绿色软件指标

### 国际现状

消息系统作为数据中心常驻服务，其能耗测量在 2025–2026 年从**倡议阶段**进入**标准化尝试阶段**，但仍缺少被行业广泛采纳的 broker 专项基准。

- **Green Software Foundation SCI**：Software Carbon Intensity（SCI）spec 已 ISO/IEC 21031 认证，公式为

```text
SCI = (E * I + M) / R
```

其中 `E` 为软件消耗的电量，`I` 为电网碳强度，`M` 为硬件隐含碳，`R` 为功能单位（如每千条消息、每 MB/s）【定理】。

- **Kafka 能效研究**：HAL/Inria 2026 论文《Energy-Efficient Right-Sizing of Kafka-like Message Brokers for IoT Workloads》给出基于模型的功耗预测，6 节点配置在 1,000 MB/s、4 KB 消息负载下预测功耗约 369.6W，实测 399.4W（误差 7%）【论证】。该研究为学术基准，非厂商官方测试。
- **NATS 能效基准**：公开可溯源的独立能效基准较少，厂商宣传多强调 CPU/内存占用低，但缺少按 SCI 方法论披露的完整数据【估算】。

| 指标 | 含义 | 适用场景 |
| ------ | ------ | ---------- |
| gCO2e / 1k msgs | 每千条消息二氧化碳当量 | 消息型负载 |
| gCO2e / MB/s | 每 MB 吞吐当量 | 流型高吞吐负载 |
| W / broker | 单节点功耗 | 容量规划 |

### 权威来源

- GSF SCI 规范：[Software Carbon Intensity Specification](https://sci.greensoftware.foundation/)
- GSF 官方主页：[Green Software Foundation](https://greensoftware.foundation/)
- Kafka 能效论文：[Energy-Efficient Right-Sizing of Kafka-like Message Brokers for IoT Workloads](https://inria.hal.science/hal-05512966v1/document)

### 与项目现有文档的关系

- [1.08 权威数据与基准测试](01-08-权威数据与基准测试.md) 聚焦吞吐/延迟/成本；绿色指标可作为其延伸维度。
- [1.18 性能基准测试对比](01-18-性能基准测试对比.md) 可补充能耗对比表。

### 成篇建议

**低**。SCI 框架已成熟，但消息系统专属能效基准稀缺且易被厂商营销数据污染；当前更适合在 1.08/1.18 中增加"绿色指标"小节，而非独立成篇。

## 1.60.5 MQTT over QUIC

### 国际现状

MQTT over QUIC 在 2026 年处于**厂商实现先行、标准化跟进**的状态。

- **EMQX QUIC 实现**：EMQX 从 5.0 起支持 MQTT over QUIC，提供单流/多流模式、0-RTT、连接迁移、弱网优化等特性。EMQX 5.x 默认关闭 QUIC listener，需显式启用。NanoMQ 亦通过 QUIC bridge 支持边缘到云端连接。ESP32-C3 上已有完整 MQTT over QUIC 实现案例（2025-09 EMQ 博客）【论证】。
- **OASIS 标准进展**：OASIS MQTT TC 在 2026 年持续召开 MQTT over QUIC workshop。2026-05-20 William Yang（EMQ）提交《MQTT Over QUIC — Single Stream Mode Version 1.0 Draft 1》作为 Committee Note，2026-09-24 更新至 Draft 版本【论证】。截至 2026-11，该文档为 Committee Note/草案，尚未成为正式 OASIS Standard。
- **NATS/gRPC over QUIC**：gRPC 社区对 HTTP/3/QUIC 的支持持续推进，部分实现如 `sssgun/grpc-quic` 提供 Go 语言 PoC。NATS 核心协议仍以 TCP/TLS 为主，未见官方 QUIC 传输层支持公告【论证】。

```hcl
# EMQX 启用 MQTT over QUIC listener 示意（emqx.conf）
listeners.quic.default {
  bind = "0.0.0.0:14567"
  enabled = true
  max_connections = 1024000
  idle_timeout = "60s"
}
```

## 1.60.6 数据主权与欧盟 Data Act

### 国际现状

欧盟 Data Act（Regulation (EU) 2023/2854）于 2024-01-11 生效，经过 20 个月过渡期后，**主要条款于 2025-09-12 开始适用**【定理】。该法规对消息/事件数据的影响集中在三个层面：

1. **数据可访问与可携带**：联网产品及相关服务产生的数据（包括通过消息流实时产生的事件数据），用户有权访问并指定第三方接收。
2. **云切换与互操作**：云/消息 SaaS 供应商需降低切换成本，2027-09-12 起全面禁止不合理的数据迁移费用。
3. **公平合同条款**：限制数据持有方在 B2B 合同中对数据使用的不公平限制。

```markdown
# Data Act 关键时间节点
- 2024-01-11: 法规生效
- 2025-09-12: 主要条款适用（数据访问、切换、公平合同）
- 2026-09-12: 新上市联网产品需满足 data by design 要求
- 2027-01-12: 云切换费用全面禁止
```

对消息架构的直接影响：

- **地域驻留（Data Residency）**：事件数据需在指定司法辖区存储与处理，跨区复制需明确法律依据。
- **事件溯源与审计**：用户行使数据访问权时，消息系统需提供可追溯、可导出的消费记录。
- **SaaS 消息服务切换**：使用托管 Kafka/MQTT 服务的企业需评估 vendor lock-in 与数据迁移成本。

- 欧盟 Data Act 官方公报：Regulation (EU) 2023/2854
- Data Act 时间线：[EU Data Act Timeline](https://www.complyone.io/guides/data-act/eu-data-act-timeline)

### 成篇建议

**高**。Data Act 已正式适用，对消息架构的数据驻留、事件可携带性、SaaS 切换产生直接约束；建议以"Data Act × 消息系统"为主题扩展 2.50 或新增 02-XX/03-XX 专章。
