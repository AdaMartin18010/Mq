## 1.34.1 为什么许可证是选型的一等公民

2024-2026 年，数据基础设施领域经历了密集的许可证迁移（MongoDB→SSPL 2018、Elastic→SSPL/ELv2 2021、Redis→RSALv2/SSPL 2024、HashiCorp→BSL 2023、 ensuing forks：Valkey/OpenTofu/OpenSearch）【论证：[arXiv 八年许可证变迁研究](https://arxiv.org/html/2606.24896v1)】。消息队列系统同样深度卷入：

- 选型时只看技术参数而忽略许可证，可能在三种场景爆雷【论证】：
  1. **商业分发**：把 MQ 打包进对外销售的产品（AGPL/SSPL 触发义务）
  2. **托管服务**：把 MQ 作为内部 PaaS 提供给其他团队/客户（RSALv2/BSL 的 non-compete 条款）
  3. **并购尽调**：技术资产审计时发现许可证违规，影响交易
- 许可证风险是**单边不可逆**的：用了再换比一开始就选对贵得多【论证】。

## 1.34.2 八系统许可证现状矩阵

| 系统 | 许可证 | OSI 开源 | 关键限制 | 风险级 |
| ------ | -------- | :---: | ---------- | :---: |
| Kafka | Apache-2.0 | ✅ | 无（注意商标） | 🟢 |
| Pulsar | Apache-2.0 | ✅ | 无 | 🟢 |
| RocketMQ | Apache-2.0 | ✅ | 无 | 🟢 |
| NATS | Apache-2.0 | ✅ | 无 | 🟢 |
| RabbitMQ | MPL-2.0 | ✅ | 文件级 copyleft（修改源文件需公开该文件） | 🟢 |
| MQTT 协议 | OASIS 标准 | — | 协议本身无许可问题（实现自由） | 🟢 |
| **Redis** | **三选一：RSALv2 / SSPLv1 / AGPLv3**（8.0+）；7.4-7.8 双许可证；≤7.2.4 BSD-3 | ⚠️ 视选择 | RSALv2 禁止商用化/托管；SSPL 要求服务化时公开全栈源码；AGPLv3 网络 copyleft | 🟡 |
| **Redpanda** | **BSL 1.1**（社区版）；企业功能商业许可 | ❌（source-available） | 禁止作为竞争性服务提供；Change Date 后转 Apache-2.0（按版本） | 🟡 |
| Confluent 平台组件 | Confluent Community License | ❌（source-available） | 非竞争条款：禁止提供与 Confluent 商业产品竞争的服务 | 🟡 |

> Redis 细节【论证：[redis.io/legal/licenses](https://redis.io/legal/licenses/)、[Phoronix Redis 8.0](https://www.phoronix.com/news/Redis-8.0-Goes-AGPLv3)、[acemq Redis 许可指南](https://acemq.com/guides/redis-licensing/)】：2024-03 从 BSD 转 RSALv2/SSPLv1；2025-05 Redis 8.0 加入 AGPLv3 成为三许可证（用户任选其一）；7.2.4 及更早版本保持 BSD-3；**Valkey**（Linux Foundation fork，2024-03-28，基于 7.2.4）保持 BSD-3，为 2026 年云厂商默认替代。
> Redpanda 细节【论证：[Redpanda Licensing 文档](https://docs.redpanda.com/streaming/current/get-started/licensing/overview/)、[BSL 文本](https://github.com/redpanda-data/redpanda/blob/dev/licenses/bsl.md)】：Community Edition 核心功能免费、源码可见；BSL 限制转售为服务；部分企业功能（如分层存储高级特性）需商业许可。

## 1.34.3 高风险条款深度解读

### AGPLv3（Redis 可选）

- 触发条件：**修改** Redis 并**通过网络对外提供服务**【论证：[BaseKV AGPL 解析](https://basekv.com/articles/redis-agpl-license-explained)】
- 常见误解澄清：未修改的自用（含作为闭源应用的后端）不触发源码公开义务——"通过网络协议调用属于松耦合边界，不构成衍生作品"【论证：同上】
- 真实成本：企业合规部门常将 AGPL 列为禁用/审批清单——**政策摩擦大于法律风险**【论证】

### SSPLv1（Redis/MongoDB 系）

- 触发条件：将软件作为服务提供 → 必须公开**服务全栈**源码（含管理/监控层）——比 AGPL 更宽【论证】
- 对自建自用无影响；对"内部 PaaS 平台组对外提供 Redis 服务"有实质约束【论证】

### RSALv2（Redis）

- 禁止：将软件商业化/作为托管服务提供给第三方【论证：[PocketLantern 解析](https://pocketlantern.dev/briefs/redis-8-agpl-vs-rsal-sspl-adoption-after-license-change-2025)】
- 自用与内部分发宽松——三条可选中最适合纯内部使用的条款【论证】

### BSL 1.1（Redpanda）

- 允许：内部生产使用、修改【论证：BSL 文本】
- 禁止：提供与原厂竞争的托管服务
- 每个版本有 Change Date，到期后该版本转为 Apache-2.0——**长期锁定旧版本反而降低限制**【论证：BSL 机制】

## 行业格局事件对许可证的影响（批次 87，2026-11 核实）

**[IBM 于 2026-03-17 完成收购 Confluent](https://newsroom.ibm.com/2026-03-17-ibm-completes-acquisition-of-confluent,-making-real-time-data-the-engine-of-enterprise-ai-and-agents)**（$11B，2025-12-08 宣布）对本文档三条结论的影响【论证】：

1. **Confluent 社区版限制条款**：收购协议未提及条款修改；IBM 历史上对开源收购对象（Red Hat）保持治理独立性的记录【论证：IBM-Red Hat 先例】——风险级维持 🟡，但季度复核新增"条款修订跟踪"项；
2. **云托管转嫁判断**：Confluent Cloud 与 IBM Cloud 整合后，企业采购谈判变量增多（捆绑折扣 vs 锁定加深），决策矩阵"云托管转嫁"行维持，注明 2026-03 后议价结构变化；
3. **观察哨**：Apache Kafka 项目本身属 Apache 软件基金会治理，收购不改变其 Apache-2.0 许可与 KIP 流程【定理级：基金会独立性】——开源栈选型结论不变，受影响的是 Confluent 商业组件（如 Tableflow/Schema Registry 高级特性）的长期可用性预期。

### Confluent Community License

- 非竞争条款：禁止提供替代 Confluent 商业产品的服务（如托管 ksqlDB/Schema Registry 服务）【论证：Confluent 许可证文本】
- Kafka 本体 Apache-2.0 不受影响——**区分"Kafka"与"Confluent 组件"**是合规要点【论证】

## 1.34.4 场景化合规决策

| 使用场景 | 高风险系统 | 建议 |
| ---------- | ----------- | ------ |
| 纯内部业务后端（自建自用） | 全部可用 | Redis 选 AGPLv3 或 RSALv2 均可；Redpanda BSL 可用 |
| 打包进对外销售的软件产品 | Redis（AGPL 需法律评审）、Redpanda BSL | 优先 Apache-2.0 系；Redis 用 ≤7.2.4 或 Valkey |
| 内部 PaaS 向其他团队提供托管 | Redis RSALv2/SSPL、Redpanda BSL、Confluent CC 组件 | 逐条核对 non-compete；Kafka/Pulsar/NATS 无此问题 |
| 云厂商托管服务 | 全部受限条款针对性设计 | 这就是许可证变更的动因【论证】——走商业授权或 fork |
| 强合规行业（金融/政企） | AGPL 政策摩擦 | 优先 BSD/Apache-2.0（Valkey 替代 Redis） |

决策树【论证】：

```text
是否对外分发或托管？ ─否→ 全部可用（记录所选 Redis 许可证条款）
├─ 是 → 是否修改源码？ ─否→ AGPL 不触发；SSPL/RSAL/BSL 仍受限
│         └─ 是 → AGPL/SSPL 高危 → 选 Apache-2.0 系或 Valkey
└─ 打包商业产品 → 只用 Apache-2.0/BSD/MPL（Kafka/Pulsar/NATS/RocketMQ/RabbitMQ/Valkey）
```

## 1.34.5 云托管的转嫁问题

使用云厂商托管 MQ（AWS MSK/Confluent Cloud/云 Redis）时：

- 许可证责任由云厂商承担（其已购买商业授权或自建 fork）【论证】
- 但出现 **2024 RabbitMQ CVE 补丁仅给商业客户** 的情况（见 ROADMAP 批次15 版本追踪）——社区版支持窗口收紧是许可证策略的连带风险【论证：[OSSeva RabbitMQ CVE 分析](https://www.osseva.io/blog/rabbitmq-vulnerabilities-by-version)】
- 选型问句应增加一条："该版本系列的社区支持窗口到何时？"

## 1.34.6 历史许可证事件时间线（2018-2026）

理解许可证风险要看行业史——**许可证变更几乎总是跟随商业模式压力**【论证】：

| 时间 | 事件 | 后果 |
| ------ | ------ | ------ |
| 2018 | MongoDB → SSPL（首个主流防御性变更） | OSI 不认可；云厂商 fork 威胁 |
| 2018 | Redis 模块 → RSAL（模块先行试水） | 社区争议起点 |
| 2021-01 | Elastic → SSPL/ELv2 | AWS 推 OpenSearch fork |
| 2023-08 | HashiCorp → BSL | OpenTofu fork（Linux Foundation） |
| 2024-03 | **Redis 核心 → RSALv2/SSPLv1** | **Valkey fork**（Linux Foundation，AWS/Google/Oracle 参与）【论证：[LabHub BSL 浪潮综述](https://labhub.hopto.org/blog/culture/2026-05-16-open-source-license-shifts-2026-bsl-wave-elastic-redis-hashicorp-sentry-valkey-opentofu-deep-dive?lang=en)】 |
| 2025-05 | **Redis 8 加入 AGPLv3 → 三许可** | 重回 OSI 开源（用户可选条款） |
| 2020 起 | Redpanda → BSL | 社区版 source-available 持续至今 |

模式【论证】：① 防御性变更针对云厂商托管；② 每次变更催生 fork（Valkey/OpenTofu/OpenSearch 先例）；③ fork 存续力取决于大厂背书——**"若原厂再变许可，有无可信 fork 可退"成为选型尽调的新维度**。

## 1.34.7 治理归属与条款稳定性

| 治理归属 | 代表系统 | 再变更风险 | 理由 |
| ---------- | ---------- | ----------- | ------ |
| Apache 软件基金会 | Kafka、Pulsar、RocketMQ、BookKeeper | 极低 | ASF 要求 Apache-2.0 + 商标代码分离，无核心项目改许可先例【论证：ASF 治理政策】 |
| CNCF | NATS | 极低 | CNCF 托管条款要求开放治理 + Apache-2.0【论证：CNCF 章程】 |
| 商业公司主导 | Redis、Redpanda | 中-高 | 已发生变更，有动机有先例 |
| 商业公司+社区双轨 | RabbitMQ | 低-中 | 社区支持窗口收紧已见（批次15）【论证】 |

实操推论【论证】：把"治理归属"写进选型评分表独立列（权重 ≥10%【估算】）；对商业主导项目强制"退出预案"（数据可导出 + 兼容层评估一页纸）。

## 1.34.9 常见问题（FAQ）

| 问题 | 回答口径 |
| ------ | ---------- |
| "Redis 8 是开源吗" | 是——三许可中 AGPLv3 为 OSI 认可开源，用户任选其一；但 RSALv2/SSPLv1 不是【论证：redis.io 官方页】 |
| "用了 AGPL Redis 要把我们的应用开源吗" | 未修改 Redis 且仅作后端自用：不触发；修改后对外提供服务：触发【论证：BaseKV 解析】——最终听法务 |
| "Redpanda 能商用吗" | 内部使用可以（BSL 允许）；作为服务转售或替代 Redpanda 的商业产品：不可【论证：BSL 条款】 |
| "Kafka 有许可证风险吗" | Apache-2.0 极低风险；注意 **Kafka 商标**（"Kafka"名称用于产品/服务需遵循 ASF 商标政策）【论证】 |
| "Confluent 组件和 Kafka 什么关系" | Kafka 本体 Apache-2.0；ksqlDB/部分连接器是 Confluent Community License（非竞争条款）——用组件时逐一看许可证【论证】 |
| "Valkey 和 Redis 怎么选" | 技术近兼容；Valkey BSD-3 无许可证摩擦、云厂商默认；Redis 8 功能更新快（向量集等内置）且可选 AGPLv3——按合规政策与功能需求定【论证】 |
| "MPL-2.0 的 RabbitMQ 修改过要公开吗" | 修改了某源文件→公开该文件（文件级 copyleft）；仅使用/链接不受影响【论证：MPL 条款】 |
| "BSL 的 Change Date 是什么意思" | 每个版本发布后设定期限，到期该版本自动转 Apache-2.0——锁定旧版本反而限制更少【论证：BSL 机制】 |
| "SSPL 和 AGPL 哪个更严" | SSPL：服务化须公开全栈（含管理工具）；AGPL：修改+对外服务才触发。SSPL 对托管场景更严【论证】 |
| "内网用 Redpanda 要给钱吗" | 不用——BSL 允许内部免费使用与修改；禁止的是对外提供竞争性服务【论证】 |
| "OSI 认可是什么门槛" | OSI 认可=符合开源定义。RSALv2/SSPLv1/BSL/CCL 均非 OSI 认可（source-available 而非开源）【论证】 |
| "fork 能用原厂商标吗" | 一般不能——商标与代码分离（ASF 模式）；Valkey 不能叫 Redis【论证：ASF/各 fork 实践】 |
| "许可证条款会追溯历史版本吗" | 不会——按版本适用当时的许可（Redis 7.2.4 及更早永远 BSD）【论证】 |

## 1.34.13 许可证对架构决策的反向影响（易被忽视）

许可证不只影响"能不能用"，还反向塑造架构【论证】：

| 架构决策 | 许可证触发的变体 |
| ---------- | ------------------ |
| Redis 8 统一包内置 JSON/Search/TimeSeries | 8.0 起模块随核心同许可——三许可同样覆盖模块；7.x 时代模块 RSAL 与核心 BSD 的分裂问题在 8.x 消失【论证】 |
| Redpanda 企业功能（分层存储高级特性等） | 社区版 BSL 不含部分企业功能——架构设计时确认所需特性是否在社区版，避免上线后被迫商业采购【论证：Redpanda 许可文档】 |
| Confluent Schema Registry / ksqlDB | 组件级 CC License——自建托管这些组件的内部 PaaS 可能触发非竞争条款，优先用 Apache 替代品（如 Apicurio Registry）【论证】 |
| Kafka 客户端 | Apache-2.0 无风险；但 Confluent 发行版客户端带指标上报等附加条款需注意【估算】 |

架构评审新增一问【论证】："本设计依赖的特性，其许可证是否允许我们的使用形态？"——该问句并入 02-02 决策图网与 03-04 决策框架的检查清单。

### 术语速查（附于 1.34.13）

| 术语 | 含义 |
| ------ | ------ |
| OSI-approved | 符合开源促进会开源定义（与"源码可见"不同） |
| copyleft | 衍生作品须同许可发布的义务（AGPL/MPL/SSPL 均属此类或更强） |
| source-available | 源码公开但带限制条款（非开源）：BSL/RSAL/SSPL/CCL |
| 非竞争条款 | 禁止提供与原厂竞争的服务（CCL/BSL 核心限制） |
| 网络条款 | 通过网络提供服务即触发 copyleft（AGPL/SSPL 的核心机制） |
| Change Date | BSL 版本转开源的到期日（每版本可不同） |
| SBOM | 软件物料清单——合规审计的依赖台账载体 |
