## 1.83.1 什么是 DSL：与 GPL 的形式分界

DSL（Domain-Specific Language，领域特定语言）的三个形式特征【定理级共识，Fowler《DSL》/JetBrains MPS 文档】：

1. **有限表达力**：图灵不完备是有意设计——只表达领域内可表达之事，排除领域外程序逻辑；
2. **领域语义**：每个构件映射领域概念（channel=消息通道，非通用字符串字段）；
3. **声明式倾向**：说"要什么"而非"怎么做"（partition: 6 而非 for 循环建分区）。

对照 GPL（通用编程语言）：

| 维度 | DSL | GPL |
| ---- | ---- | ---- |
| 表达力 | 领域子集 | 通用可计算 |
| 使用者 | 领域专家+工程师 | 工程师 |
| 验证 | 结构即语义（可静态判定） | 需执行/测试 |
| 演化 | 随领域模型演化 | 随通用实践演化 |
| 失败模式 | 表达不了（限制可见） | 写错（限制不可见） |

**核心洞察**【论证】：DSL 的价值不在"能表达"，而在"**不能表达的部分恰好是错误**"。消息 DSL 表达不了动态路由逻辑——这是功能缺失，更是事故预防。

## 1.83.2 语言设计四要素

任何语言的完整定义含四层【定理，编译原理】：

| 要素 | 定义 | 消息 DSL 实例（contract.yaml） |
| ---- | ---- | ---- |
| 元模型（抽象语法） | 概念的实体与关系，与表示无关 | 消息/字段/约束/状态机/invariant |
| 具体语法（表示） | 元模型的可写形式：文本/图形/表格 | YAML 键值 + mermaid 图 + 01-02 思维导图 |
| 语义 | 语法结构的含义（指称/操作/公理三种定义风格） | invariants 的判定语义（真/假可机验） |
| 语用 | 人机读写效率与错误预防 | 四行消化卡/速查表/易错点标注 |

BNF 文法示例【定理】——contract.yaml 的 messages 字段抽象语法：

```bnf
<contract>   ::= "scenario:" <name> "version:" <ver> <message>* <invariant-section>
<message>    ::= <msg-name> ":" "type:" ("command"|"event"|"query") "required:" "[" <fields> "]"
<invariant>  ::= "-" <自然语言断言，可判定为真假>
```

语义定义风格的选择【论证】：本项目 invariants 用**公理语义**（断言即规范，kg-query 直接判定）；AsyncAPI 用**指称语义**（每个构件映射协议概念）；Flink SQL 类用**操作语义**（映射执行计划）。

## 1.83.3 内部 DSL vs 外部 DSL

| 维度 | 内部 DSL（宿主语言嵌入） | 外部 DSL（独立语言） |
| ---- | ---- | ---- |
| 例 | Kotlin DSL / TypeSpec / 流畅 API | AsyncAPI / ODCS / contract.yaml |
| 解析 | 宿主编译器 | 专用 parser（YAML/JSON 解析器复用） |
| 工具 | 宿主 IDE 全功能 | 需自建（Spectral/AsyncAPI CLI） |
| 组合 | 与宿主代码自由组合（失控风险） | 组合受限于语言构件 |
| 学习成本 | 低（会宿主语言即可） | 中（新语法） |
| 元编程 | 强（宏/反射） | 弱（x- 扩展机制） |

**本项目各资产的定位判定**【论证】：contract.yaml=外部 DSL（独立 schema 校验）；x-semantics 标注=外部 DSL 的元模型扩展；01-02 思维导图=图形式具体语法；knowledge-graph=机读具体语法——**同一元模型，四种语法**，这是"一源多表征"的正当性基础。

## 1.83.4 表达力层级与思维表征的统一

Chomsky 层级对 DSL 的适用【论证】：实用 DSL 集中在正则（列表/键值）与上下文无关（嵌套结构）两层；需要上下文相关表达力的设计应立即警惕（那是程序，不是声明）。

更深层的统一【论证】——本项目的多种思维表征全是 DSL 的具体语法变体：

| 表征 | 句法结构 | 强项 | 弱项 |
| ---- | ---- | ---- | ---- |
| 概念矩阵（01-01/01-72） | 二维表 | 全面对照 | 关系表达弱 |
| 思维导图（01-02） | 树 | 层次全貌 | 交叉关联缺失 |
| 决策树（01-59/01-80） | 判定路径 | 可执行选择 | 组合爆炸 |
| 推理判定树（01-78） | 谓词逻辑 | 概念适用性判定 | 学习曲线 |
| UML（01-79） | 图（类/时序） | 结构与行为 | 渲染依赖 |
| 知识图谱（knowledge-graph） | 三元组+规则 | 机器推理 | 人类不友好 |

选择判据【论证】：人类首次接触→导图；对照选型→矩阵；执行→决策树/图谱；论证→推理树。这就是 concept/README 三层表征地图的理论根据。

## 1.83.5 DSL 设计方法论与反模式

设计循环【论证，迭代式 DSL 工程共识】：

```text
领域分析（01-58 概念卡为域模型）→ 抽象（元模型 v0）
  → 实例验证（用 8 业务场景压力测试）→ 语法具体化（YAML/图）
  → 工具化（dsl-schema/kg-query）→ 演化（02-60 策略回灌）
```

四大反模式：

1. **图灵完备诱惑**：给 DSL 加条件/循环"就够用"——瞬间退化为糟糕 GPL；
2. **语义过载**：一个字段两重含义（"时间戳"=事件时间还是处理时间）；
3. **语法噪音**：为省打字破坏可读性（缩写风暴）；
4. **无验证裸奔**：语法无 schema、语义无判定器——本项目的 dsl-schema.json + kg-query 即对此的防御。
