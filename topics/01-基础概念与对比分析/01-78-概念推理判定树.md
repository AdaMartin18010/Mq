## 1.78.1 概念关系抽取规则

### 六元组关系字段的读法

[1.58](01-58-全局核心概念卡片总表.md) 为每个概念给出**定义、关键属性、关系（上位/下位/关联）、示例、反例**六元组。其中“关系”字段已隐含逻辑关系，但尚未显式标注为蕴含/互斥/特化/组成。本文将其形式化，使概念卡成为可推理的判定树节点素材。

### 四类逻辑关系判定规则

| 关系类型 | 符号 | 判定规则（基于 1.58 六元组） | 示例 |
| --- | --- | --- | --- |
| **蕴含** | A → B | A 的“关系”字段中 B 为上位概念，或 A 的定义必须引用 B 才能成立 | `exactly-once` → `at-least-once`（1.58.1 定义：exactly-once = at-least-once ∧ at-most-once） |
| **互斥** | A ⟂ B | 同一维度下两种语义不可同时成立，或 1.58 反例字段直接提示误用 | `at-most-once` ⟂ `exactly-once`（低可靠语义与强可靠语义在同一传输路径上互斥选择） |
| **特化** | A ⊂ B | A 的“关系”字段中 B 为上位概念，且 A 是 B 的一种具体形态 | `Quorum Queue` ⊂ `Queue`（1.58.4） |
| **组成** | A ⋄ B | A 的“关系”字段中 B 为下位概念，或 B 是 A 的物理/逻辑组成部分 | `Topic` ⋄ `Partition`（1.58.1：Topic 下位为 Partition） |

【论证】上述规则是项目内部的概念关系抽取约定，不是数学公理；其目的是把 1.58 中自然语言描述的关系转化为机读判定树可消费的谓词。涉及官方规范保证的语义（如 MQTT QoS 等级、Kafka ISR 语义）才标【定理】。

## 1.78.3 三棵可执行判定树

判定树的使用方法：从根节点的**属性谓词**（如“消息是否需要可回放？”）开始，沿“是/否”分支下钻，最终到达叶子节点——叶子给出**适用概念集**。概念名全部取自 1.58。

### 消息形态判定树

```text
消息形态判定树
├── 是否需要持久化存储？
│   ├── 否 → 适用概念：{Topic}
│   └── 是 → 继续
│       ├── 是否需要多消费者独立读取同一份消息？
│       │   ├── 是 → 适用概念：{Stream, Partition, Offset}
│       │   └── 否 → 继续
│       │       ├── 是否要求每条消息只被一个消费者处理？
│       │       │   ├── 是 → 适用概念：{Queue, Classic Queue, Quorum Queue, Competing Consumers}
│       │       │   └── 否 → 适用概念：{Publish-Subscribe Channel, Consumer Group, Share Group}
│       │       └── 是否需要按 Key 保留最新值？
│       │           ├── 是 → 追加 {Compaction}
│       │           └── 否 → 追加 {Retention}
```

**读图要点**：这棵树的第一个分叉把“瞬时路由”与“持久化形态”分开；第二个分叉把“日志/流”与“队列/广播”分开；最底层用 Compaction/Retention 区分长期存储语义。它直接回答“我的消息应该被当成流、队列还是主题”。

### 可靠性概念判定树

```text
可靠性概念判定树
├── 消息是否允许丢失？
│   ├── 是 → 适用概念：{at-most-once, QoS 0}
│   └── 否 → 继续
│       ├── 消息是否允许重复投递？
│       │   ├── 是 → 适用概念：{at-least-once, QoS 1}
│       │   └── 否 → 继续
│       │       ├── 是否需要跨多个分区/Topic 原子提交？
│       │       │   ├── 是 → 适用概念：{exactly-once, Transaction, Producer Idempotence}
│       │       │   └── 否 → 适用概念：{exactly-once, Idempotency}
│       │       └── 是否需要 MQTT 协议级四次握手？
│       │           ├── 是 → 追加 {QoS 2}
│       │           └── 否 → 保持 exactly-once + Idempotency
```

**读图要点**：这棵树把“丢/重/原子”三个正交维度分层处理，避免把 QoS 等级与系统级 exactly-once 混为一谈。叶节点同时给出协议概念（QoS）与系统概念（Transaction/Idempotency），便于对接 1.59 的 L2 语义五问。

### 存储概念判定树

```text
存储概念判定树
├── 是否需要多副本冗余？
│   ├── 是 → 继续
│   │   ├── 副本同步策略是否为 ISR 机制？
│   │   │   ├── 是 → 适用概念：{ISR, Leader, Follower, High Watermark, Rebalance Protocol}
│   │   │   └── 否 → 适用概念：{Bookie, Ledger, Quorum Queue}
│   └── 否 → 适用概念：{Stream, Log Segment}
├── 是否需要长期保留（>7 天）？
│   ├── 是 → 追加 {Retention, Tiered Storage}
│   └── 否 → 追加 {Persistence}
└── 是否需要按 Key 去重/压缩？
    ├── 是 → 追加 {Compaction}
    └── 否 → 保持 Retention/Persistence
```

**读图要点**：这棵树区分“副本一致性模型”（ISR vs Quorum）、“保留时长”与“压缩策略”三个存储维度，避免把 Tiered Storage 与 Compaction 同时当作默认选项。

### 判定树执行示例

假设某团队要设计一个“订单支付状态通知”系统，属性如下：消息不可丢、不可重复、需要按订单号保序、保留 30 天。执行三棵树的判定路径如下：

| 判定树 | 路径 | 输出概念集 |
| --- | --- | --- |
| 消息形态判定树 | 持久化 → 多消费者独立读取 → 不强制单条单处理 | {Stream, Partition, Offset, Retention} |
| 可靠性概念判定树 | 不可丢 → 不可重复 → 无需跨 Topic 原子提交 | {exactly-once, Idempotency} |
| 存储概念判定树 | 多副本 → ISR 机制 → 长期保留 → 无需按 Key 压缩 | {ISR, Leader, Follower, High Watermark, Retention, Tiered Storage} |

将上述概念集带入 [1.59](01-59-全局选型决策总树.md) 后，L0 场景倾向于“任务队列/事件流混合”，L2 语义需求明确“幂等 + 顺序 + 持久化”，可快速收敛到 Kafka / Pulsar 候选集。

## 1.78.4 与 1.59 总树的关系与调用顺序

[1.59](01-59-全局选型决策总树.md) 是“选系统”的总树，其叶节点挂载到 Kafka/Pulsar/RabbitMQ 等系统专章；本文 1.78 是“选概念”的前置树，其叶节点挂载到 1.58 的概念卡。**调用顺序必须是先概念判定、后系统选型**：

```text
1.78 概念推理判定树
    ├── 确定消息形态概念集（Stream/Queue/Topic）
    ├── 确定可靠性概念集（at-most-once / at-least-once / exactly-once）
    └── 确定存储概念集（ISR / Tiered Storage / Compaction）
            ↓
1.59 全局选型决策总树
    ├── L0 场景分类
    ├── L1 负载特征
    ├── L2 语义需求（直接消费 1.78 的可靠性概念集）
    ├── L3 约束五问
    └── 叶节点：候选系统排序 + 子树挂载
```

| 1.78 输出 | 进入 1.59 的哪一层 | 作用 |
| --- | --- | --- |
| 消息形态概念集 | L0 场景分类 | 帮助判断是“日志/事件流”“任务队列”还是“实时通知” |
| 可靠性概念集 | L2 语义需求 | 直接映射到“顺序/幂等/事务/回放/背压”五问 |
| 存储概念集 | L1 负载特征 + L3 约束 | 影响“吞吐/保留/成本/运维复杂度”判定 |

【论证】这种两层解耦避免在 1.59 中重复论证概念含义；1.78 负责“概念是否适用”，1.59 负责“系统是否满足这些概念”。

## 1.78.5 机读版树结构 YAML

以下 YAML 为批次 104 知识图谱预留接口。每个节点有 `id`、`predicate`（属性谓词）、`yes`/`no` 分支或 `concepts` 叶子概念集。

```yaml
# 1.78 概念推理判定树 - 机读版
# 概念名逐字取自 1.58 全局核心概念卡片总表
version: "1.78.0"
trees:
  - name: 消息形态判定树
    root: MSG-FORM-01
    nodes:
      MSG-FORM-01:
        predicate: 是否需要持久化存储
        yes: MSG-FORM-02
        no: [Topic]
      MSG-FORM-02:
        predicate: 是否需要多消费者独立读取同一份消息
        yes: [Stream, Partition, Offset]
        no: MSG-FORM-03
      MSG-FORM-03:
        predicate: 是否要求每条消息只被一个消费者处理
        yes: [Queue, Classic Queue, Quorum Queue, Competing Consumers]
        no: [Publish-Subscribe Channel, Consumer Group, Share Group]

  - name: 可靠性概念判定树
    root: REL-01
    nodes:
      REL-01:
        predicate: 消息是否允许丢失
        yes: [at-most-once, QoS 0]
        no: REL-02
      REL-02:
        predicate: 消息是否允许重复投递
        yes: [at-least-once, QoS 1]
        no: REL-03
      REL-03:
        predicate: 是否需要跨多个分区或 Topic 原子提交
        yes: [exactly-once, Transaction, Producer Idempotence]
        no: [exactly-once, Idempotency]

  - name: 存储概念判定树
    root: STORAGE-01
    nodes:
      STORAGE-01:
        predicate: 是否需要多副本冗余
        yes: STORAGE-02
        no: [Stream, Log Segment]
      STORAGE-02:
        predicate: 副本同步策略是否为 ISR 机制
        yes: [ISR, Leader, Follower, High Watermark, Rebalance Protocol]
        no: [Bookie, Ledger, Quorum Queue]
```

【估算】YAML 中的节点 ID 采用人工编排的短码，便于知识图谱引用；实际图谱导入时可映射为 UUID 或 IRI。
