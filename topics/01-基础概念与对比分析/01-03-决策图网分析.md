## 1.3.1 消息队列选型决策树

```text
场景需求分析
├── 吞吐量优先?
│   ├── 是 → 数据规模?
│   │   ├── TB级日志流 → Kafka (100万+ TPS) / Pulsar (100万+ TPS)
│   │   └── 百万级事件 → NATS Core (200万+ TPS)
│   └── 否 → 延迟敏感?
│       ├── 是 → 延迟要求?
│       │   ├── 微秒级 → NATS Core (30-100μs)
│       │   └── 毫秒级 → MQTT (亚毫秒)
│       └── 否 → 功能完备性?
│           ├── 高 → RabbitMQ（任务队列）/Kafka（事件流）
│           └── 轻量 → NATS
├── 持久化要求?
│   ├── 强持久化 → Kafka (副本+磁盘) / JetStream (Raft) / Pulsar (BookKeeper) / RabbitMQ (磁盘+镜像)
│   └── 弱/无 → NATS Core (内存)
├── 协议兼容性?
│   ├── MQTT生态 → MQTT Broker
│   ├── Kafka生态 → Kafka
│   ├── AMQP生态 → RabbitMQ
│   └── 多协议 → Pulsar/NATS+bridges
├── 部署复杂度?
│   ├── 极简 → NATS (单二进制)
│   ├── 中等 → MQTT/RabbitMQ
│   └── 可接受复杂度 → Kafka/Pulsar
├── 应用场景?
│   ├── 任务队列/工作流 → RabbitMQ (Exchange-Queue模型)
│   ├── 事件流/日志聚合 → Kafka (分区模型)
│   ├── 微服务通信 → NATS/RabbitMQ (低延迟/灵活路由)
│   ├── IoT设备 → MQTT (轻量协议)
│   └── 边缘计算 → NATS (轻量+自愈)
└── 前沿主题入口?
    ├── 事件 API 治理/契约驱动 → 见 1.3.3 契约驱动决策
    ├── 事件溯源/CQRS → 见 1.3.3 事件溯源选型
    ├── Serverless/FaaS 集成 → 见 1.3.3 Serverless 事件
    ├── 零信任安全体系 → 见 1.3.3 零信任实施
    ├── 流处理引擎/流库 → 见 1.3.3 流引擎/流库选型
    ├── 多云/边缘联邦 → 见 1.3.3 联邦方案
    ├── 智能运维分级 → 见 1.3.3 AIOps 分级
    └── AI Agent 消息模式 → 见 1.3.3 Agent 消息模式
```

**快速判定辅助**：复杂选型可配合 [01-59 全局选型决策总树](./01-59-全局选型决策总树.md) 快速分支，术语边界先用 [01-58 全局核心概念卡片总表](./01-58-全局核心概念卡片总表.md) 对齐。

## 1.3.2 架构权衡决策网络

```text
┌─────────────┐
│   设计目标   │
└──────┬──────┘
       │
       ├─→ 一致性强度 ──→ CP系统(Kafka/JetStream) vs AP系统(Core NATS)
       │
       ├─→ 可用性要求 ──→ 副本数+故障转移策略
       │
       ├─→ 性能优先级 ──→ 延迟 vs 吞吐量 vs 资源消耗
       │
       ├─→ 复杂度预算 ──→ 运维成本+学习曲线
       │
       └─→ 安全/治理/可观测需求 ──→ 零信任/契约/AIOps 专项决策
```

**一致性-可用性权衡矩阵**:

| 一致性强度 | 高可用性 | 低可用性 |
| --- | --- | --- |
| 强一致性 | Kafka(ISR) | JetStream(Raft) |
| 弱一致性 | NATS Core | MQTT QoS0 |

**逻辑一致性检查**：本网络所有有向边均从"设计目标"向外辐射，同一语义边（如"一致性强度"）只存在一个判定方向，避免"CP→设计目标"与"设计目标→CP"双向混用。新增前沿节点（1.3.3）同样遵循"需求/约束 → 方案"的单向判定方向。

### 契约驱动决策

```text
需要事件 API 治理?
├── 否 → 保持代码先行
└── 是 → 治理深度?
    ├── 文档级 → AsyncAPI 描述 + Markdown 评审
    ├── 门禁级 → AsyncAPI + Spectral 规则 + breaking-change 检测
    └── 运行时级 → AsyncAPI + Microcks/Pact 契约测试 + 漂移检测
        → 范式选择：spec-first（新系统）/ round-trip（遗留系统）/ code-first（快速原型）
```

### 事件溯源选型

```text
需要事件溯源/CQRS?
├── 否 → 传统 CRUD + 消息通知
└── 是 → 聚合复杂度?
    ├── 高（长生命周期/多版本）→ Kurrent/EventStoreDB 等专业事件存储
    ├── 中（已有 Kafka 生态）→ Kafka 作为事件日志 + 投影到读库
    └── 低（简单审计/状态回放）→ PostgreSQL/RDBMS 事件表
        → 快照策略：高频大聚合用快照；小聚合直接重放
```

### Serverless 事件

```text
需要函数/容器事件触发?
├── 否 → 常驻服务消费
└── 是 → 部署环境?
    ├── 云厂商锁定可接受 → AWS Lambda+SQS/SNS/EventBridge 或 Azure Functions+Service Bus
    ├── 需要跨云抽象 → Knative Eventing + Broker/Trigger
    └── 需要缩容到零 + 事件源驱动 → KEDA scaler + 任意容器运行时
        → 触发模型：拉取（长轮询/可控） vs 推送（低延迟/需幂等）
```

### 零信任实施

```text
安全模型?
├── 边界信任（传统）→ TLS + ACL/防火墙
└── 零信任 → 身份层?
    ├── 仅传输层 → mTLS + 证书轮换
    ├── 工作负载身份 → SPIFFE/SPIRE + mTLS
    └── 端到端消息加密 → 应用层信封加密 + KMS + 字段级 crypto-shredding
        → 认证协议：Kafka OAUTHBEARER / MQTT 5.0 增强认证 / NATS JWT+NKey
```

### 流引擎/流库选型

```text
需要流处理?
├── 否 → 仅使用 MQ 消费即可
└── 是 → 状态复杂度?
    ├── 无状态转换/过滤 → 流库（Bytewax、Arroyo）或 MQ 原生 Streams API
    ├── 轻量状态（窗口/聚合）→ Kafka Streams / Redis Streams
    └── 复杂事件处理/大状态 → Apache Flink
        → 部署模式：库内嵌（低运维） vs 独立集群（高吞吐/高可用）
```

### 联邦方案

```text
需要跨地域/多云消息联邦?
├── 否 → 单集群部署
└── 是 → 拓扑?
    ├── 星型（总部-分支）→ NATS Leaf Nodes + 核心集群
    ├── 双活/多活 → Kafka MirrorMaker 2 / Pulsar Geo-Replication
    └── 边缘-云协同 → NATS 超级集群 + MQTT 桥接 或 Redpanda 跨集群复制
        → 一致性要求：最终一致（日志复制） vs 强一致（事务复制/同步镜像）
```

### AIOps 分级

```text
可观测数据规模?
├── 小规模 → 规则告警 + Grafana/Kibana 面板
├── 中规模 → 基线阈值 + 异常检测（统计/ML）
├── 大规模 → 因果推断 + 故障传播图
└── 超大规模 → 自治运维（自动扩缩容、自动隔离、自动回滚）
    → 输入：Metrics / Logs / Traces / 拓扑 / 变更事件
    → 输出：告警降噪/根因定位/预测性运维/自愈动作
```

### Agent 消息模式

```text
AI Agent 协作模型?
├── 紧耦合编排 → 工作流引擎/同步调用（类似 01-41 工作流编排）
└── 松耦合事件驱动 → 通信模式?
    ├── 任务分派/结果回收 → Inbox 模式（每个 Agent 一个专属队列）
    ├── 广播状态/知识 → Pub/Sub 主题（多 Agent 共享上下文）
    └── 人机协同 → 人工审批队列 + 超时 Escalation
        → 可靠性：at-least-once + 幂等；敏感操作需 human-in-the-loop
```

## 1.3.4 CAP定理应用

**CAP 定位矩阵**:

| 系统 | 主要分区行为 | CAP 归类 | 关键机制 |
| --- | --- | --- | --- |
| Kafka | 网络分区时优先保证已提交数据一致 | CP | ISR、Controller Quorum |
| MQTT | 集群继续服务，一致性由 QoS 决定 | AP | 主从集群、QoS 分级 |
| NATS Core | 集群自愈，不保证投递 | AP | Gossip、全网状 |
| NATS JetStream | 多数派可用即可服务 | CP | Raft |
| Pulsar | Broker 无状态，存储层多数派 | CP | BookKeeper Quorum |

### Kafka (CP系统)

- **一致性(C)**: ISR机制保证已提交消息的一致性
- **可用性(A)**: 在分区容忍的前提下，通过副本保证可用性
- **分区容忍(P)**: 支持跨机房部署，但网络分区时可能不可用

### MQTT (AP系统)

- **可用性(A)**: 主从模式保证服务可用
- **分区容忍(P)**: 支持多Broker集群
- **一致性(C)**: QoS级别决定一致性强度

### NATS Core (AP系统)

- **可用性(A)**: 全网状集群，节点故障自动切换
- **分区容忍(P)**: Gossip协议自动发现和恢复
- **一致性(C)**: 最多一次投递，不保证一致性

### NATS JetStream (CP系统)

- **一致性(C)**: Raft共识算法保证强一致性
- **可用性(A)**: 多数派可用即可服务
- **分区容忍(P)**: 网络分区时自动选择多数派

### Pulsar (CP系统)

- **一致性(C)**: BookKeeper Quorum机制保证强一致性
- **可用性(A)**: Broker无状态，BookKeeper多数派可用
- **分区容忍(P)**: 网络分区时优先保证一致性，Broker故障不影响存储
