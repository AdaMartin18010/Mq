## 1.64.1 协议基础：固定头、可变头与载荷

MQTT 5.0 报文采用统一的三段式结构【定理：[OASIS MQTT v5.0 §2](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)】：

```text
+-------------+-------------------+-------------+
| Fixed Header| Variable Header   | Payload     |
| (2..5 bytes)| (packet-specific) | (optional)  |
+-------------+-------------------+-------------+
```

### 固定头（Fixed Header）

固定头由 **首字节（Packet Type + Flags）** 与 **剩余长度（Remaining Length）** 组成。首字节高 4 位为报文类型，低 4 位为标志位，标志位含义随报文类型变化：

| 报文类型 | 值 | 方向 | 低 4 位标志含义 |
| ------ | ---- | ---- | -------------- |
| CONNECT | 1 | C→S | 保留 0000 |
| CONNACK | 2 | S→C | 保留 0000 |
| PUBLISH | 3 | C↔S | DUP(3)、QoS(2-1)、RETAIN(0) |
| PUBACK | 4 | C↔S | 保留 0000 |
| PUBREC | 5 | C↔S | 保留 0000 |
| PUBREL | 6 | C↔S | 保留 0010 |
| PUBCOMP | 7 | C↔S | 保留 0000 |
| SUBSCRIBE | 8 | C→S | 保留 0010 |
| SUBACK | 9 | S→C | 保留 0000 |
| UNSUBSCRIBE | 10 | C→S | 保留 0010 |
| UNSUBACK | 11 | S→C | 保留 0000 |
| PINGREQ/PINGRESP | 12/13 | C↔S | 保留 0000 |
| DISCONNECT | 14 | C→S | 保留 0000 |
| AUTH | 15 | C↔S | 保留 0000 |

PUBLISH 首字节中 DUP 仅表示“该报文是否为重发”，并不保证首次发送未被接收；QoS 字段取值 0/1/2；RETAIN 标志控制 Broker 是否保留该消息为主题最后一条已知消息【定理】。

### 剩余长度编码（Variable Byte Integer）

剩余长度字段采用变长编码，每字节低 7 位为数据，最高位为延续位，最多 4 字节，最大值为 268,435,455 字节（约 256 MB）【定理】：

| 字节数 | 最小值 | 最大值 | 示例 |
| ------ | ------ | ------ | ---- |
| 1 | 0 (0x00) | 127 (0x7F) | 100 → `0x64` |
| 2 | 128 (0x80, 0x01) | 16,383 (0xFF, 0x7F) | 200 → `0xC8 0x01` |
| 3 | 16,384 (0x80, 0x80, 0x01) | 2,097,151 | 100,000 → `0xA0 0x8D 0x06` |
| 4 | 2,097,152 | 268,435,455 (0xFF, 0xFF, 0xFF, 0x7F) | 最大报文 |

```python
# 变长整数编码示例（非规范算法，仅示意）
def encode_variable_byte_integer(x: int) -> bytes:
    encoded = bytearray()
    while True:
        byte = x % 128
        x = x // 128
        if x > 0:
            byte |= 0x80
        encoded.append(byte)
        if x == 0:
            break
    return bytes(encoded)

assert encode_variable_byte_integer(200) == bytes([0xC8, 0x01])
```

### 可变头（Variable Header）

可变头包含 **报文标识符（Packet Identifier）** 与 **属性（Properties）** 两部分。报文标识符用于需要确认的报文（PUBLISH QoS>0、PUBACK、PUBREC、PUBREL、PUBCOMP、SUBSCRIBE、SUBACK、UNSUBSCRIBE、UNSUBACK），取值 1..65535，0 为保留值【定理】。

属性以 **属性长度（Properties Length，变长整数）** 开头，后接零个或多个属性。每个属性由 **属性标识符（Property Identifier）** 与属性值组成。MQTT 5.0 全部属性如下表：

| 标识符 | 名称 | 类型 | 允许出现的报文 |
| ------ | ---- | ---- | -------------- |
| 0x01 | Payload Format Indicator | Byte | PUBLISH, Will Properties |
| 0x02 | Message Expiry Interval | Four Byte Integer | PUBLISH, Will Properties |
| 0x03 | Content Type | UTF-8 Encoded String | PUBLISH, Will Properties |
| 0x08 | Response Topic | UTF-8 Encoded String | PUBLISH, Will Properties |
| 0x09 | Correlation Data | Binary Data | PUBLISH, Will Properties |
| 0x0B | Subscription Identifier | Variable Byte Integer | PUBLISH, SUBSCRIBE |
| 0x11 | Session Expiry Interval | Four Byte Integer | CONNECT, CONNACK, DISCONNECT |
| 0x12 | Assigned Client Identifier | UTF-8 Encoded String | CONNACK |
| 0x13 | Server Keep Alive | Two Byte Integer | CONNACK |
| 0x15 | Authentication Method | UTF-8 Encoded String | CONNECT, CONNACK, AUTH |
| 0x16 | Authentication Data | Binary Data | CONNECT, CONNACK, AUTH |
| 0x17 | Request Problem Information | Byte | CONNECT |
| 0x18 | Will Delay Interval | Four Byte Integer | Will Properties |
| 0x19 | Request Response Information | Byte | CONNECT |
| 0x1A | Response Information | UTF-8 Encoded String | CONNACK |
| 0x1C | Server Reference | UTF-8 Encoded String | CONNACK, DISCONNECT |
| 0x1F | Reason String | UTF-8 Encoded String | CONNACK, PUBACK, PUBREC, PUBREL, PUBCOMP, SUBACK, UNSUBACK, DISCONNECT, AUTH |
| 0x21 | Receive Maximum | Two Byte Integer | CONNECT, CONNACK |
| 0x22 | Topic Alias Maximum | Two Byte Integer | CONNECT, CONNACK |
| 0x23 | Topic Alias | Two Byte Integer | PUBLISH |
| 0x24 | Maximum QoS | Byte | CONNACK |
| 0x25 | Retain Available | Byte | CONNACK |
| 0x26 | User Property | UTF-8 String Pair | 几乎所有报文 |
| 0x27 | Maximum Packet Size | Four Byte Integer | CONNECT, CONNACK |
| 0x28 | Wildcard Subscription Available | Byte | CONNACK |
| 0x29 | Subscription Identifier Available | Byte | CONNACK |
| 0x2A | Shared Subscription Available | Byte | CONNACK |

### 载荷（Payload）

载荷仅出现在 CONNECT、PUBLISH、SUBSCRIBE、SUBACK、UNSUBSCRIBE、UNSUBACK 中。CONNECT 载荷顺序固定为：ClientID → Will Properties → Will Topic → Will Payload → User Name → Password；若 Connect Flags 未启用对应标志，则对应字段不得出现【定理】。

### UTF-8 字符串约束

MQTT 5.0 中 UTF-8 Encoded String 以 2 字节大端长度前缀开头，后接 UTF-8 字节序列，长度不包含自身 2 字节。规范禁止以下内容【定理】：

- U+0000（NULL）字符；
- U+D800..U+DFFF 代理对（surrogate）码点；
- U+007F..U+009F 控制字符；
- Unicode 规范定义的 non-character 码点（如 U+FFFF、U+10FFFF 等）。

序列 `0xEF 0xBB 0xBF`（UTF-8 BOM）必须被解释为 U+FEFF，不得跳过或剥离。该约束直接影响 User Property、Topic Name、Topic Filter、ClientID 等字段的合法性校验。

## 1.64.2 会话状态机：CONNECT/CONNACK 与 Clean Start

### CONNECT 字段全表

CONNECT 报文的可变头字段如下：

| 字段 | 长度 | 说明 |
| ---- | ---- | ---- |
| Protocol Name | 2+4 字节 | 必须为 "MQTT"（MQTT 3.1.1 起） |
| Protocol Version | 1 字节 | MQTT 5.0 = 5 |
| Connect Flags | 1 字节 | User Name/Password/Will Retain/Will QoS/Will Flag/Clean Start/Reserved |
| Keep Alive | 2 字节 | 心跳间隔秒数，0 表示禁用 |
| Properties | 变长 | 见 §1.64.1 属性表 |
| Payload | 变长 | ClientID/Will/User Name/Password |

Connect Flags 低 7 位语义：

```text
  7   6   5    4   3   2    1   0
+---+---+---+---+---+---+---+---+
| U | P | W | W | W | W | C | R |
| S | W | R | Q | Q | F | S | s |
| R | D | e | o | o | l | t | v |
|   |   | t | S | S | g | a | d |
+---+---+---+---+---+---+---+---+
```

- **Clean Start（bit 1）**：1 表示以全新会话连接，0 表示尝试恢复已有会话；
- **Will Flag（bit 2）**：1 表示启用遗嘱消息；
- **Will QoS（bits 3-4）**：遗嘱消息 QoS；
- **Will Retain（bit 5）**：遗嘱消息是否保留；
- **Password Flag（bit 6）**、**User Name Flag（bit 7）**：是否携带认证字段。

### CONNECT/CONNACK Properties 逐字段说明

| 属性 | CONNECT | CONNACK | 语义要点 |
| ---- | ------- | ------- | -------- |
| Session Expiry Interval | 设置 | 回显/限制 | 0 表示断连即清除；0xFFFFFFFF 表示永不过期 |
| Receive Maximum | 客户端窗口 | 服务端窗口 | 对端允许的最大 QoS 1/2 并发数，必须 ≥1 |
| Maximum Packet Size | 声明 | 限制 | 本端可接收的最大报文字节数 |
| Topic Alias Maximum | 0 | 服务端上限 | 会话内允许使用的最大 Topic Alias 数量 |
| Request Response Information | 请求 | — | 请求服务端返回响应主题前缀 |
| Response Information | — | 返回 | 服务端建议的响应主题前缀 |
| Request Problem Information | 请求 | — | 0 表示不接收 Reason String/User Property（除 Will） |
| Server Keep Alive | — | 覆盖 | 服务端可要求客户端使用更短心跳 |
| Assigned Client Identifier | — | 分配 | 服务端为 0 长度 ClientID 分配唯一 ID |
| Authentication Method/Data | 发起 | 继续 | 增强认证方法名与挑战数据 |
| User Property | 可携带 | 可携带 | 连接级自定义元数据 |

### 会话过期与遗嘱消息状态机

MQTT 5.0 将 MQTT 3.1.1 的 Clean Session 拆分为 **Clean Start 标志位** 与 **Session Expiry Interval 属性**，使会话生命周期可精确到秒级。会话状态包括：订阅、未完成的 QoS 1/2 消息、Will 消息、已接收但未确认的入站消息【定理】。

```text
Client                          Server
  |                               |
  |-- CONNECT (Clean Start=0/1) ->|
  |                               |  查找/创建 Session
  |<- CONNACK (Session Present) --|  Session Present=1 表示恢复了旧会话
  |                               |
  |-- DISCONNECT (Expiry=0) ----->|  正常断开，立即清除会话
  |                               |
  |   网络异常断开                |  启动 Session Expiry 倒计时
  |                               |  倒计时结束：丢弃会话状态
  |                               |  倒计时期间重连：恢复会话
```

遗嘱消息（Will Message）触发条件为 **网络连接异常关闭且 Session 尚未过期**；若客户端正常发送 DISCONNECT，则 Will 不发送【定理】。Will Delay Interval 可进一步推迟 Will 发送，若延迟期间客户端重新连上，则取消 Will。

### Clean Start 与 Session Expiry 组合语义表

| Clean Start | Session Expiry | 语义 | 等价于 3.1.1 |
| ----------- | -------------- | ---- | ------------ |
| 1 | 0（或未设置） | 新建会话，断连即清除 | Clean Session=1 |
| 1 | >0 | 新建会话，但断开后保留指定秒数 | 无精确等价 |
| 0 | 0 | 尝试恢复会话，但断连即清除 | 行为混杂（不推荐） |
| 0 | >0 | 尝试恢复会话，断开后保留指定秒数 | Clean Session=0 |
| 0 | 0xFFFFFFFF | 尝试恢复会话，永久保留 | Clean Session=0 永久版 |

【论证】工程实践中，移动/车载设备常用 `Clean Start=0 + Session Expiry=300` 实现秒级闪断恢复；一次性 Web 仪表盘常用 `Clean Start=1 + Session Expiry=0` 避免残留订阅。

## 1.64.3 消息流控制：QoS 时序与流控机制

### QoS 0/1/2 报文交换时序

【定理】MQTT 5.0 定义三种 QoS，其报文交换如下：

**QoS 0 —— 最多一次（At most once）**

```text
Client          Server
  |---- PUBLISH --->|
  |                 |-- 转发给匹配订阅者 -->
```

无确认、无状态、可能丢失，适用于可容忍丢失的遥测心跳。

**QoS 1 —— 至少一次（At least once）**

```text
Client          Server
  |---- PUBLISH (pid=1) --->|
  |<--- PUBACK (pid=1) -----|
```

PUBLISH 与 PUBACK 都携带相同 Packet Identifier；若 PUBACK 的 Reason Code ≥0x80，发布方可知投递失败原因。

**QoS 2 —— 恰好一次（Exactly once，协议级）**

```text
Client          Server
  |---- PUBLISH (pid=1) --->|
  |<--- PUBREC (pid=1) -----|
  |---- PUBREL (pid=1) --->|
  |<--- PUBCOMP (pid=1) ----|
```

四次握手确保消息在协议层只被投递一次；应用层仍可能因消费端重试或崩溃导致重复处理，需业务幂等【论证】。

### 消息标识符复用规则

Packet Identifier 取值范围 1..65535，同一方向上的 inflight 报文不得复用同一标识符【定理】。具体规则：

- QoS 1 PUBLISH：从发送 PUBLISH 到收到 PUBACK 期间，该 pid 占用；
- QoS 2 PUBLISH：从发送 PUBLISH 到收到 PUBCOMP 期间，该 pid 占用；
- SUBSCRIBE/UNSUBSCRIBE：从发送到收到对应 SUBACK/UNSUBACK 期间占用。

一个连接上同时存在的 inflight 标识符数量受 **Receive Maximum** 限制。超过时发送方不得再发新的 QoS 1/2 PUBLISH，否则对端将发送 DISCONNECT（Reason Code 0x93 Receive Maximum exceeded）。

### Inflight 窗口与 Receive Maximum 流控

Receive Maximum 是 MQTT 5.0 引入的连接级背压机制。CONNECT 中客户端声明自己愿意并发处理的 QoS 1/2 发布数；CONNACK 中服务端声明其 Receive Maximum，客户端必须遵守二者较小值【定理】。

```python
# paho-mqtt 设置 Receive Maximum 示例（MQTTv5）
from paho.mqtt.properties import Properties
from paho.mqtt.packettypes import PacketTypes

props = Properties(PacketTypes.CONNECT)
props.ReceiveMaximum = 32  # 本端最多同时处理 32 条 QoS 1/2 消息
client.connect("broker.example.com", 1883, properties=props)
```

Receive Maximum 仅限制 QoS 1/2 的 PUBLISH，不限制 QoS 0。若需对 QoS 0 限流，必须依赖应用层或传输层背压（如 TCP 窗口、WebSocket 缓冲）。

### Topic Alias 机制

Topic Alias 用 16 位无符号整数（1..Topic Alias Maximum）替代完整 Topic Name，减少重复主题传输开销。规则如下【定理】：

- 首次 PUBLISH 携带非空 Topic Name 与 Topic Alias 属性，建立映射；
- 后续 PUBLISH 可置空 Topic Name 但携带相同 Topic Alias，Broker 按已建立映射解析；
- 客户端发送时可用别名值 1..Topic Alias Maximum；
- 服务端发送时也可使用别名，但别名空间独立；
- 映射关系仅在单个连接会话内有效，重连后失效。

```python
# 建立 Topic Alias 后复用
props_first = Properties(PacketTypes.PUBLISH)
props_first.TopicAlias = 1
client.publish("factory/line01/sensor/temperature", payload="23.5", qos=1, properties=props_first)

props_next = Properties(PacketTypes.PUBLISH)
props_next.TopicAlias = 1
client.publish("", payload="23.6", qos=1, properties=props_next)  # Topic Name 为空
```

## 1.64.4 主题与订阅：通配符、共享订阅与订阅选项

### 通配符语法

MQTT 主题层级以 `/` 分隔，主题名与主题过滤器的匹配规则由规范严格定义【定理】：

- `#`：多级通配符，必须位于过滤器的最后一个层级，可匹配零个或多个层级；
- `+`：单级通配符，匹配恰好一个层级；
- 通配符不能出现在主题名（Topic Name）中，只能出现在主题过滤器（Topic Filter）中；
- 主题名/过滤器长度最大 65,535 字节；层级数无规范上限，但 Broker 可施加策略限制。

| 主题过滤器 | 是否匹配 `a/b/c` | 是否匹配 `a/b` | 说明 |
| ---------- | ---------------- | -------------- | ---- |
| `a/b/c` | 是 | 否 | 精确匹配 |
| `a/+/c` | 是 | 否 | 中间层级任意 |
| `a/#` | 是 | 是 | 多级匹配 |
| `a/+/+` | 是 | 否 | 必须有两层 |
| `#` | 是 | 是 | 匹配所有主题 |
| `+/b/c` | 是 | 否 | 首层任意 |

### 共享订阅（$share）

MQTT 5.0 引入共享订阅实现消费者组负载均衡，语法固定为：

```text
$share/{ShareName}/{TopicFilter}
```

同一 ShareName 与 TopicFilter 的多个订阅者构成一个共享组，每条匹配消息只投递给组内一个会话。共享订阅不保证顺序，组内某个会话离线后，消息由其余会话接管。

```python
# 三个客户端加入同一共享组
client1.subscribe("$share/group1/sensors/+/temperature")
client2.subscribe("$share/group1/sensors/+/temperature")
client3.subscribe("$share/group1/sensors/+/temperature")
```

### 订阅标识符与订阅选项

订阅时可携带 **Subscription Identifier（0x0B）**，当消息因该订阅匹配而投递时，Broker 在 PUBLISH 属性中回显该标识符，便于客户端识别消息来源。同一连接内不同订阅可使用相同标识符，规范允许但不便于追踪。

SUBSCRIBE 载荷中每个 Topic Filter 还附带 1 字节 **订阅选项（Subscription Options）**：

```text
bits:  7   6   5   4   3   2   1   0
       R   R   R   NL  RAP  RH  RH  QoS  QoS
```

| 字段 | 位 | 含义 |
| ---- | ---- | ---- |
| Maximum QoS | 0-1 | 该订阅允许接收的最大 QoS（0/1/2） |
| No Local | 2 | 1 表示不接收本客户端发布的消息 |
| Retain As Published | 3 | 1 表示保留消息原 RETAIN 标志，不强制置 0 |
| Retain Handling | 4-5 | 控制订阅时是否下发保留消息 |
| Reserved | 6-7 | 保留 0 |

Retain Handling 三种取值：

| 值 | 行为 |
| ---- | ---- |
| 0 | 订阅建立时立即发送匹配主题的保留消息 |
| 1 | 仅当订阅之前不存在时发送保留消息 |
| 2 | 订阅建立时不发送保留消息 |

完整订阅选项矩阵：

| QoS | No Local | RAP | Retain Handling | 典型场景 |
| ---- | -------- | --- | --------------- | -------- |
| 0 | 0 | 0 | 0 | 普通遥测，不保留 |
| 1 | 0 | 0 | 0 | 命令下发，保留最新指令 |
| 1 | 1 | 0 | 0 | 群聊：不接收自己发的消息 |

## 1.64.5 请求响应与错误：Response Topic、Correlation Data 与 Reason Code

### Response Topic 与 Correlation Data

MQTT 5.0 在 PUBLISH 报文中引入 **Response Topic（0x08）** 与 **Correlation Data（0x09）**，支持无服务器地址硬编码的请求-响应模式【定理】：

- 请求方在 PUBLISH 中设置 `Response Topic`，响应方将响应发布到该主题；
- `Correlation Data` 为不透明二进制，由响应方原样回传，用于请求方匹配异步响应；
- 响应主题通常位于请求方私有命名空间，避免响应被其他客户端窃听；
- 配合 `Request Response Information` 属性，服务端可在 CONNACK 中返回推荐的响应主题前缀。

```python
# 请求方
req_props = Properties(PacketTypes.PUBLISH)
req_props.ResponseTopic = f"response/{client_id}/result"
req_props.CorrelationData = b"req-2026-001"
client.publish("cmd/device-001/reboot", payload="{}", qos=1, properties=req_props)

# 响应方（在消息回调中）
def on_message(client, userdata, msg):
    if msg.properties.ResponseTopic:
        resp_props = Properties(PacketTypes.PUBLISH)
        resp_props.CorrelationData = msg.properties.CorrelationData
        client.publish(msg.properties.ResponseTopic, payload='{"status":"ok"}', qos=1, properties=resp_props)
```

## 1.64.6 用户属性与载荷：User Properties、消息过期与内容类型

### User Properties 应用

User Properties（0x26）是 MQTT 5.0 最重要的扩展机制，以 UTF-8 字符串键值对形式出现在除 PINGREQ/PINGRESP 外几乎所有报文中。常见用途：

- 分布式追踪：注入 `traceparent` / `tracestate`；
- 业务元数据：订单号、设备版本、租户 ID；
- 路由提示：优先级、目标区域；
- 审计：来源 IP、客户端 SDK 版本。

```python
# 将 W3C Trace Context 注入 MQTT User Properties
from paho.mqtt.properties import Properties
from paho.mqtt.packettypes import PacketTypes

props = Properties(PacketTypes.PUBLISH)
props.UserProperty = [
    ("traceparent", "00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01"),
    ("tracestate", "congo=tucucumu"),
    ("tenant-id", "tenant-42"),
]
client.publish("events/orders/created", payload=payload, qos=1, properties=props)
```

User Properties 与 OpenTelemetry trace context 的映射细节见 [1.50 OpenTelemetry 消息语义约定与全链路追踪](01-50-OpenTelemetry消息语义约定与全链路追踪.md) §1.50.2。

### 消息过期与内容类型

- **Message Expiry Interval（0x02）**：以秒为单位的四字节整数，0xFFFFFFFF 表示永不过期；超过该间隔未投递的 QoS 1/2 消息将被 Broker 丢弃。
- **Content Type（0x03）**：UTF-8 字符串，描述 payload 媒体类型，如 `application/json`、`application/octet-stream`。
- **Payload Format Indicator（0x01）**：0 表示未指定（默认），1 表示 payload 为 UTF-8 编码字符数据；设置为 1 时 Broker 可校验 payload 是否为合法 UTF-8，失败返回 0x99 Payload format invalid。

| 属性 | 类型 | 示例值 | 用途 |
| ---- | ---- | ------ | ---- |
| Payload Format Indicator | Byte | 1 | 声明 payload 为 UTF-8 |
| Message Expiry Interval | 4-byte int | 300 | 5 分钟后过期 |
| Content Type | UTF-8 | `application/json` | payload 语义说明 |
| User Property | string pair | `trace-id=abc` | 自定义元数据 |

## 1.64.7 增强认证：AUTH 报文与挑战响应

MQTT 5.0 在 CONNECT/CONNACK 之外新增 **AUTH 报文**，支持多轮 challenge-response 认证（如 SCRAM、Kerberos、自定义令牌交换）【定理】。

### AUTH 报文字段

| 字段 | 长度 | 说明 |
| ---- | ---- | ---- |
| Reason Code | 1 字节 | 0x18 Continue authentication 或 0x19 Re-authenticate |
| Properties | 变长 | Authentication Method + Authentication Data + 可选 User Property |

### 增强认证流程

```text
Client                              Server
  |-- CONNECT (Auth Method=SCRAM-SHA-256, Data=client-first) -->|
  |<-- CONNACK (Reason=0x18, Data=server-first) ----------------|
  |-- AUTH (Reason=0x18, Data=client-final) ------------------->|
  |<-- CONNACK (Reason=0x00 Success) ---------------------------|
```

若认证失败，服务端可在任意一轮返回 Reason Code ≥0x80（如 0x86 Bad User Name or Password、0x8C Bad authentication method）并关闭连接。

### 重认证流程

已连接客户端可在任意时刻发送 AUTH（Reason Code 0x19 Re-authenticate）发起重认证，服务端以 AUTH 0x18 响应，完成后再继续正常数据交换。重认证期间，已建立的会话与 inflight 消息可继续传输，但认证结果可能影响后续发布/订阅权限【论证】。

```python
# paho-mqtt 增强认证示意（需库支持回调）
props = Properties(PacketTypes.CONNECT)
props.AuthenticationMethod = "SCRAM-SHA-256"
props.AuthenticationData = b"n,,n=user,r=client-nonce"
client.connect("broker.example.com", 1883, properties=props)
```

## 1.64.8 Broker 实现对照与 Kafka 桥接

### 主流 Broker 对 MQTT 5.0 的支持现状

| Broker | 当前稳定版本（核实至 2026-11） | MQTT 5.0 支持 | 特色能力 | 授权模式 |
| ------ | ---------------------------- | ------------- | -------- | -------- |
| **EMQX** | 开源版 5.x / 企业版 6.3.x（2026-11） | 完整 | 分布式集群、MQTT over QUIC/WebSocket、规则引擎、百万级连接 | Apache 2.0 / BSL（5.9+） |
| **Eclipse Mosquitto** | 2.1.2（2026-02） | 完整 | 轻量、嵌入式友好、桥接、持久化 | EPL/EDL |
| **HiveMQ** | 企业版 4.55 LTS（2026-09）/ CE 持续更新 | 完整 | 企业扩展系统、集群、监控、合规插件 | 商业 / Apache 2.0（CE） |

【论证】上表版本信息来自各项目官方发布渠道：Mosquitto 2.1.2 于 2026-02-09 发布并声明支持 MQTT 5.0/3.1.1/3.1；HiveMQ 4.55 于 2026-09-01 成为最新 LTS；EMQX 6.3.3 于 2026-11-11 出现在 GitHub releases。实际选型应以部署时的官方 changelog 为准。

### 与 Kafka 桥接模式

MQTT Broker 与 Kafka 的桥接解决“设备协议入口 + 后端流处理”的分层问题：

| 桥接模式 | 实现位置 | 语义特点 | 适用场景 |
| -------- | -------- | -------- | -------- |
| **内置规则引擎桥接** | EMQX 规则引擎 / HiveMQ 扩展 | 按主题映射到 Kafka Topic，可转换 payload | 大规模 IoT 入湖 |
| **Mosquitto 桥接** | `bridges` 配置 | MQTT-MQTT 桥接为主，需配合 Kafka Connect | 边缘网关聚合 |
| **Kafka Connect Source** | 独立 Connector | 拉取 MQTT 主题写入 Kafka | 已有 Kafka Connect 生态 |
| **自定义 Gateway** | 自研服务 | 灵活处理协议转换、QoS 映射、Schema | 复杂路由与合规要求 |

```conf
# Mosquitto MQTT-MQTT 桥接示例（边缘 → 云端）
connection cloud-bridge
address broker.cloud.example.com:1883
bridge_protocol_version mqttv50
topic # out 1
remote_clientid edge-gateway-01
remote_username gateway
remote_password secret
cleansession false
```

【论证】MQTT 会话级持久化不等于 Kafka 的日志重放能力：MQTT 的 QoS 1/2 保证消息到达订阅会话，会话过期后消息即丢失；Kafka 的分区日志支持按 offset/time 任意重放。因此“MQTT 桥接 Kafka”通常采用 **MQTT 负责实时采集、Kafka 负责持久化与回溯** 的分层架构，而非互相替代。
