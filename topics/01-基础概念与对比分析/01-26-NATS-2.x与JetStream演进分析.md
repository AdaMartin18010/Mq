## 1.26.1 NATS 架构回顾

NATS 采用 **Core NATS + JetStream** 的双层模型：Core 负责高性能、低延迟的消息路由，JetStream 在其之上提供持久化、流式存储与至少一次投递。

```text
┌─────────────────────────────────────────────────────────────┐
│                      NATS 2.x 双层架构                        │
├─────────────────────────────────────────────────────────────┤
│  应用层：pub/sub、request/reply、services、queue groups       │
├─────────────────────────────────────────────────────────────┤
│  Core NATS 层：无状态消息总线，at-most-once，纯内存路由        │
├─────────────────────────────────────────────────────────────┤
│  JetStream 层：Stream、Consumer、KV、Object Store            │
│               at-least-once，Raft 复制，磁盘持久化             │
├─────────────────────────────────────────────────────────────┤
│  传输层：NATS 文本协议 / TLS / WebSocket / MQTT / Leafnode     │
└─────────────────────────────────────────────────────────────┘
```

### Core NATS 层

Core NATS 是 NATS 的原始形态，核心语义为**发布-订阅**与**请求-响应**：

- **at-most-once**：消息只投递给当前在线订阅者，不持久化、不重放。
- **subject**：点分字符串，如 `orders.us.1001`，支持 `*` 与 `>` 通配符。
- **queue group**：同一 queue 名称的订阅者之间负载均衡。
- **request/reply**：通过 `reply-to` subject 实现同步/异步 RPC。

### JetStream 持久层

JetStream 将 Core NATS 的**空间解耦**扩展为**时间解耦**：

- **Stream**：服务器端消息存储，绑定一个或多个 subject，按策略保留。
- **Consumer**：服务器端有状态视图，维护消费进度、重试、投递策略。
- **Client**：连接到 Consumer 并 ack 消息的应用；未 ack 则触发重投。

### 双层模型的意义

Core NATS 适合实时控制、RPC 等低延迟场景；JetStream 适合事件溯源、任务队列、配置/状态缓存等需要持久化与重放的场景。两者共享同一二进制与协议，可按 subject 灵活选择。

## 1.26.2 NATS 2.10~2.15 演进

### 版本时间线

| 版本 | 首发时间 | 最终补丁 | 补丁终止 | 状态 | 关键说明 |
| ------ | ---------- | ---------- | ---------- | ------ | ---------- |
| **NATS 2.15** | 2026-09-17 | 维护中 | — | [Latest](https://docs.nats.io/release-notes/) | 可靠性/运维强化：Desired State Reconciliation、Stream Backup v2、Source Recreate Indexing、`sync: always` 性能、默认 `max_consumers=1000` |
| **NATS 2.14** | 2026-04-30 | 维护中 | — | [Maintained](https://docs.nats.io/release-notes/) | Fast batch publish、recurring schedules、scheduled subject sampling、可靠 WQ/Interest sourcing、source dedup 优化 |
| **NATS 2.13** | — | — | — | [Skipped](https://docs.nats.io/release-notes/) | 从未发布 |
| **NATS 2.12** | 2025-09-22 | v2.12.15，2026-08-12 | 2026-08-12 | [End of life](https://docs.nats.io/release-notes/) | Atomic batch publish、delayed message scheduling、distributed counters、Prioritized pull policy、mirror promotion、offline assets |
| **NATS 2.11** | 2025-03-19 | v2.11.17，2026-04-27 | 2026-04-27 | [End of life](https://docs.nats.io/release-notes/) | Per-message TTL、consumer priority groups、consumer pause、distributed message tracing、stream multi-get |
| **NATS 2.10** | 2023-09 | v2.10.26，2025-03 | 2025-03 | End of life | Subject transforms、S2 压缩、Auth Callout、consumer multi-subject 过滤、MQTT QoS 2 |

> 生产环境优先使用 2.14 或 2.15；2.13 跳过未发布，升级路径不存在 2.13 这一环。

### 支持策略与 API level 门控

NATS Server 自 2.11 起采用**约六个月一次小版本**的节奏，并实行**最新 + 上一小版本双线补丁**策略：当新的小版本发布时，最老的补丁线停止维护【论证】[release-notes](https://docs.nats.io/release-notes/)。2.13 被跳过，因此 2.12 之后直接是 2.14；2.11 的补丁持续到 2.14 发布后才终止【论证】[release-notes](https://docs.nats.io/release-notes/)。

JetStream 功能按 **API level** 门控。服务器在内部维护一个 API level 数值，新功能会抬高该 level；客户端可在请求头中携带 `Nats-Required-Api-Level`，要求服务器至少支持到指定 level，否则请求会被拒绝【论证】[jetstream-api-headers](https://docs.nats.io/reference/jetstream/api/headers)。这保证了滚动升级期间：旧客户端不会被新语义误伤，新功能必须客户端与服务端同时就绪才能启用。

### NATS 2.10/2.11 关键特性

- **JetStream Subject Transforms（2.10）**：创建 stream 时重写流入 subject，常与 mirror/source 配合做数据分发。
- **S2 压缩（2.10）**：route、leafnode、JetStream 文件存储均支持 S2 压缩，降低跨 AZ/广域网带宽。
- **Auth Callout（2.10）**：通过外部认证提供者动态签发用户权限，适合与企业 IdP/SSO 集成。
- **Consumer 多 Subject 过滤（2.10）**：一个 consumer 可同时订阅多个 subject filter，简化消费侧逻辑。
- **单消息 TTL（2.11）**：通过 `Nats-TTL` header 为单条消息设置过期时间；KV delete marker 也可配置 TTL，避免墓碑消息无限堆积。
- **Consumer Priority Groups（2.11）**：支持 **Pinning**（单活跃客户端，故障时热备接管）与 **Overflow**（按 pending ack/消息数溢出到备用客户端）。
- **Consumer Pause（2.11）**：通过 `PauseUntil` 或 `$JS.API.CONSUMER.PAUSE` 暂停投递，到时间自动恢复；心跳保持，客户端无感知。
- **分布式消息追踪（2.11）**：设置 `Nats-Trace-Dest` header 追踪消息在 cluster/gateway/leafnode/import/export 路径上的流转；`Nats-Trace-Only: true` 支持干跑追踪。
- **Stream Multi-Get（2.11）**：无需创建 consumer，可按多个 subject filter、序列号或时间边界批量拉取消息。

### NATS 2.12 关键特性

2.12 是 NATS 宣布进入 6 个月固定节奏后的第一个版本，核心关键词是**批处理、调度、计数与降级安全**【论证】[nats-server-2.12-release](https://nats.io/blog/nats-server-2.12-release/)。

- **Atomic batch publish**：将 N 条消息 staging 后一次性原子提交，整批要么全部持久化，要么全部失败；可与 delayed scheduling、counters 组合使用。
- **Delayed Message Scheduling**：支持按未来时间戳调度单条消息投递，适用于任务延迟队列。
- **Distributed Counters**：Stream 可配置为分布式计数器，每个 subject 保存一个可原子增减的 `big.Int` 值；计数器 stream 仍可被 mirror/source，并支持跨源聚合。
- **Prioritized pull consumer policy**：在 2.11 Priority Groups 的 Overflow 基础上新增 Prioritized 策略：本地客户端无拉取时立即让远程客户端接管，实现更快故障转移，但可能增加跨区消费概率。
- **Mirror promotion**：允许删除 stream 的 mirror 配置，将其提升为普通 stream（需先删除原主 stream），用于灾备切换。
- **Offline assets**：从 2.12 降级到 2.11.9+ 时，使用新特性的 asset 会被标记为 offline，数据保持不变但不可操作，防止旧服务器误解析新格式。

### NATS 2.13 状态说明

2.13.x 被官方整体跳过，从未发布【论证】[release-notes](https://docs.nats.io/release-notes/)。因此实际升级路径为 2.12 → 2.14，文档与自动化脚本均不应引用 2.13。

### NATS 2.14 关键特性

2.14 在 2.12 发布约 7 个月后推出（官方归因于 AI 安全审查与披露响应活动导致略有延迟），重点扩展了**高吞吐发布、服务端调度与 source/mirror 正确性**【论证】[nats-server-2.14-release](https://nats.io/blog/nats-server-2.14-release/)。

- **Fast batch publish**：面向吞吐与流控的批量发布模式。消息持续持久化，服务端按 batch sequence 追踪顺序并报告 gap；可配置 `gap:fail`（严格有序）或 `gap:ok`（容忍 gap）。相比 async publish，同 stream 并发发布者可达数百且仍受流控。
- **Recurring schedules**：在 2.12 延迟调度的基础上扩展为循环调度，支持 `@every 5s` 与 cron 表达式，并可与 TTL 组合控制调度生命周期。
- **Scheduled subject sampling**：调度触发时从源 subject 读取最新值再发布到目标 subject，典型场景是边缘高频传感器数据的服务端下采样。
- **Reliable WorkQueue/Interest mirroring & sourcing**：从 WQ 或 Interest retention stream 进行 source/mirror 时，内部消费者由 ephemeral 自动切换为 durable，断线期间数据不会被兴趣策略误删；同时支持“自带 consumer”进行 sourcing。
- **Deduplication changes for sources**：含 source 的 stream 可完全关闭 dedup；多源汇聚场景下，目标 stream 自身也参与去重，避免源端重复 ID 导致 sourcing 卡住。

### NATS 2.15 关键特性

2.15 是 2026 年 9 月的最新版，与前几版不同，**几乎不增加新功能，而是全面聚焦可靠性与运维**【论证】[nats-server-2.15-release](https://nats.io/blog/nats-server-2.15-release/)。

- **Desired State Reconciliation**：重写 stream/consumer 扩缩容、迁移与 peer 增删流程。meta 层提出 desired state，由 asset 层自身驱动安全单步迁移，避免旧实现中跨层 peer set 不一致导致的数据风险。
- **Stream backup and restore v2**：备份改为逐条消息流式打包，可被 NATS CLI 过滤、修改、obfuscation，且不再独占 stream 锁，可并发写入。
- **Stream sources recreation & indexing**：持久化 source 元数据，能在被 source 的 stream 删除重建后自动从正确序列号重新开始 sourcing，并避免 leader 切换时反向扫描。
- **`sync: always` 性能提升 for replicated streams**：针对单节点边缘场景的 `sync: always`，通过 Raft 层更积极的 batching 与避免 stream 层逐消息 sync，复制流吞吐从数百 msg/s 提升到数万 msg/s，尾延迟降低 40% 以上（官方在 3 台 AWS c5.xlarge 跨 AZ 测试）【估算】[nats-server-2.15-release](https://nats.io/blog/nats-server-2.15-release/)。
- **默认 `max_consumers=1000`**：新增 stream 级默认消费上限，防止无节制创建 consumer 拖垮整个集群；可通过 `max_consumers`、account limits 或 `default_max_consumers: -1` 恢复旧行为。

## 1.26.3 JetStream 深度机制

### Stream：消息存储

Stream 是 JetStream 的核心存储单元，每个消息被分配单调递增的 sequence number。关键配置项：

| 配置项 | 说明 | 常用值 |
| -------- | ------ | -------- |
| `subjects` | 捕获的 subject 集合 | `orders.>`, `events.*` |
| `retention` | 保留策略 | `limits`, `interest`, `workqueue` |
| `storage` | 存储介质 | `file`, `memory` |
| `replicas` | Raft 副本数 | 1/3/5 |
| `max_msgs` / `max_bytes` | 容量上限 | 按业务设定 |
| `discard` | 超限行为 | `old`, `new` |
| `subject_transform` | subject 重写 | 2.10+ |

保留策略：`limits`（按容量/时间保留，适合事件日志）、`interest`（所有 consumer ack 后删除）、`workqueue`（任一 consumer ack 后删除，适合任务队列）。

### Consumer：消费视图

Consumer 分为 **push** 与 **pull** 两种模式：

| 模式 | 投递方向 | 适用场景 | 2.11+ 增强 |
| ------ | ---------- | ---------- | ----------- |
| **Push** | 服务器主动推送 | 低延迟实时处理 | 支持 pause |
| **Pull** | 客户端按需拉取 | 批处理、背压控制 | priority groups、multi-get |

```bash
# 创建 Stream（捕获 orders 下所有 subject，文件存储，3 副本）
nats stream add ORDERS \
  --subjects "orders.>" \
  --storage file \
  --replicas 3 \
  --retention limits \
  --discard old \
  --max-msgs 1000000 \
  --max-age 7d

# 创建 Durable Pull Consumer，从最新位置开始，显式 ack
nats consumer add ORDERS order-processor \
  --pull \
  --deliver-policy last \
  --ack-policy explicit \
  --max-deliver 3 \
  --filter-subject "orders.us.>"

# 拉取一批消息并 ack
nats consumer next ORDERS order-processor --count 10 --ack
```

### Key-Value Store

KV Bucket 本质是名为 `KV_<bucket>` 的 Stream，subject 为 `$KV.<bucket>.>`。每个 key 是 subject 的最后一个 token，value 是该 subject 上的最新消息。

```go
package main

import (
    "fmt"
    "github.com/nats-io/nats.go"
)

func main() {
    nc, _ := nats.Connect(nats.DefaultURL)
    js, _ := nc.JetStream()

    // 创建 KV bucket（3 副本，保留 10 个历史版本）
    kv, _ := js.CreateKeyValue(&nats.KeyValueConfig{
        Bucket:   "INVENTORY",
        Replicas: 3,
        History:  10,
        TTL:      24 * time.Hour,
    })

    // 写入、读取、watch
    kv.Put("widget-blue", []byte(`{"stock":41}`))
    entry, _ := kv.Get("widget-blue")
    fmt.Printf("value=%s revision=%d\n", entry.Value(), entry.Revision())

    watcher, _ := kv.Watch("*")
    for update := range watcher.Updates() {
        if update != nil {
            fmt.Printf("key=%s value=%s\n", update.Key(), update.Value())
        }
    }
}
```

### Object Store

Object Store 用于存储超过单条消息大小的二进制对象（如 PDF、图片），底层是 `OBJ_<bucket>` Stream。对象被切分为 chunk，随后追加一条 metadata 消息；读取时按 metadata 重组并校验 SHA-256。

```bash
# 创建 Object Store bucket
nats object add INVOICES --description "Invoice PDFs" --replicas 3

# 上传文件
nats object put INVOICES invoice-ord_8w2k.pdf --file ./invoice-ord_8w2k.pdf

# 下载文件
nats object get INVOICES invoice-ord_8w2k.pdf --file ./downloaded.pdf
```

## 1.26.4 NATS 与其他系统对比

### NATS Core 与 JetStream 对比

| 维度 | NATS Core | NATS JetStream |
| ------ | ----------- | ---------------- |
| **投递语义** | at-most-once | at-least-once |
| **持久化** | 无 | 文件/内存，Raft 复制 |
| **顺序保证** | 无 | Stream 内按序 |
| **重放能力** | 无 | 支持按时间/序列号重放 |
| **延迟** | 30-100μs | 亚毫秒-毫秒 |
| **吞吐量** | 200万+ TPS | 20-50万 TPS |
| **适用场景** | 实时控制、RPC | 事件流、队列、状态存储 |

### NATS 与 Kafka、RabbitMQ、Pulsar 选型矩阵

| 维度 | NATS (Core+JetStream) | Kafka (KRaft) | RabbitMQ | Pulsar |
| ------ | ----------------------- | --------------- | ---------- | -------- |
| **核心定位** | 统一连接层 + 轻量流 | 高吞吐日志 | 通用消息队列 | 多租户流平台 |
| **协议** | NATS 文本协议 | 自定义二进制 | AMQP 0-9-1 | 自定义 + 多协议 |
| **持久化** | JetStream（可选） | 强制磁盘持久化 | 可选 | BookKeeper |
| **一致性** | Raft（JetStream） | KRaft/ISR | 镜像队列/Quorum | BookKeeper Quorum |
| **多租户** | Accounts + 权限 | 有限 | vhosts | 原生租户/命名空间 |
| **部署复杂度** | 低（单二进制） | 中-高 | 中 | 高 |
| **典型延迟** | Core <100μs；JS 亚毫秒 | 5-100ms | 1-10ms | 5-50ms |
| **MQTT 支持** | 原生内置（2.2+） | 需外部桥接 | 需插件 | 需协议适配器 |
| **边缘/IoT** | 优秀（leafnode、小体积） | 差 | 中 | 中 |
| **超大规模分区** | 中 | 优秀 | 受限 | 优秀 |

### MQTT 与 NATS 集成方式

NATS Server 自 2.2 起内置 MQTT 监听器，2.10 支持 QoS 2。MQTT topic 中的 `/` 会被转换为 NATS subject 的 `.`，因此 MQTT 设备可直接接入 NATS 骨干。

```conf
# nats-server.conf：启用 JetStream 与 MQTT
jetstream {
    store_dir: /data/jetstream
    max_memory_store: 1GB
    max_file_store: 100GB
}

mqtt {
    port: 1883
    tls {
        cert_file: /etc/nats/server.crt
        key_file: /etc/nats/server.key
    }
    # QoS 1/2 的会话与保留消息依赖 JetStream
    ack_wait: 1m
    max_ack_pending: 100
}

accounts {
    MQTT {
        jetstream: enabled
        users [
            { user: sensor, password: $2y$10$... }
        ]
    }
}
```

## 1.26.5 部署与运维要点

### 集群拓扑

生产环境推荐 **3 或 5 节点**组成 JetStream 集群，通过 `--cluster` 与 `--routes` 互联；跨地域场景叠加 **gateway** 与 **leafnode** 实现中心-边缘扩展。

```text
中心集群（3-5 节点，full mesh）
    ├─ Gateway ── 其他数据中心
    └─ Leafnode ── 边缘网关 / IoT 现场
```

### 存储与备份

文件存储节点独立保存数据，Raft 保证一致性；JetStream 定期生成快照加速恢复。2.15 起 backup v2 支持热备份与 CLI 级过滤；关键 bucket 仍建议异地复制。

### 监控指标

| 指标类别 | 关键指标 | 告警阈值建议 |
| ---------- | ---------- | -------------- |
| **可用性** | `/healthz`、`/jsz` 状态 | 任何节点非 OK |
| **延迟** | publish latency、consumer pending | P99 > 10ms |
| **容量** | stream bytes、msg count | >80% 上限 |
| **一致性** | Raft 选举频率 | >1 次/小时 |
| **MQTT** | 连接数、QoS 会话积压 | 按设备规模设定 |

### 升级注意事项

1. **2.9 → 2.10**：磁盘存储格式变化，升级后若需回滚必须回到 **2.9.22+**。
2. **2.10 → 2.11/2.12/2.14/2.15**：支持滚动升级，但建议先升级到当前小版本的最新补丁版再跨大版本。
3. **2.12+ 新功能**：atomic batch、delayed scheduling、counters、priority groups 等需要客户端与服务端均支持对应 API level。
4. **2.15 默认 `max_consumers=1000`**：升级前检查现有 stream 的 consumer 数量，必要时显式调高 `max_consumers` 或 account limits。
5. **混合版本**：滚动升级期间避免同时存在相差两个及以上小版本的节点管理同一 JetStream asset。
