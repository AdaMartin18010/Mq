## 1.26.1 NATS 架构回顾

NATS 采用 **Core NATS + JetStream** 的双层模型：Core 负责高性能、低延迟的消息路由，JetStream 在其之上提供持久化、流式存储与至少一次投递。

```text
┌─────────────────────────────────────────────────────────────┐
│                      NATS 2.x 双层架构                        │
├─────────────────────────────────────────────────────────────┤
│  应用层：pub/sub、request/reply、services、queue groups       │
├─────────────────────────────────────────────────────────────┤
│  Core NATS 层：无状态消息总线，at-most-once，纯内存路由        │
├─────────────────────────────────────────────────────────────┤
│  JetStream 层：Stream、Consumer、KV、Object Store            │
│               at-least-once，Raft 复制，磁盘持久化             │
├─────────────────────────────────────────────────────────────┤
│  传输层：NATS 文本协议 / TLS / WebSocket / MQTT / Leafnode     │
└─────────────────────────────────────────────────────────────┘
```

### Core NATS 层

Core NATS 是 NATS 的原始形态，核心语义为**发布-订阅**与**请求-响应**：

- **at-most-once**：消息只投递给当前在线订阅者，不持久化、不重放。
- **subject**：点分字符串，如 `orders.us.1001`，支持 `*` 与 `>` 通配符。
- **queue group**：同一 queue 名称的订阅者之间负载均衡。
- **request/reply**：通过 `reply-to` subject 实现同步/异步 RPC。

### JetStream 持久层

JetStream 将 Core NATS 的**空间解耦**扩展为**时间解耦**：

- **Stream**：服务器端消息存储，绑定一个或多个 subject，按策略保留。
- **Consumer**：服务器端有状态视图，维护消费进度、重试、投递策略。
- **Client**：连接到 Consumer 并 ack 消息的应用；未 ack 则触发重投。

### 双层模型的意义

Core NATS 适合实时控制、RPC 等低延迟场景；JetStream 适合事件溯源、任务队列、配置/状态缓存等需要持久化与重放的场景。两者共享同一二进制与协议，可按 subject 灵活选择。

## 1.26.2 NATS 2.10/2.11 演进

### 版本时间线

| 版本 | 发布时间 | 状态 | 关键说明 |
| ------ | ---------- | ------ | ---------- |
| **NATS 2.10.0** | 2023-09 | 稳定系列 | 引入 subject transforms、S2 压缩、Auth Callout、QoS 2 MQTT、consumer 多 subject 过滤 |
| **NATS 2.10.26** | 2025-03 | 长期维护终点 | 2.10.x 最后一个补丁版，官方称为史上最稳定的 2.10 版本 |
| **NATS 2.11.0** | 2025-03-20 | 当前推荐 | 引入单消息 TTL、consumer priority groups、consumer pause、分布式消息追踪、stream multi-get |

> 注：NATS 2.10 首发于 2023 年，但其补丁系列持续演进到 2025 年；2.11 是 2025 年重大功能版本。本文以 2.10/2.11 功能集作为 NATS 2.x 现阶段的代表。

### NATS 2.10 关键特性

- **JetStream Subject Transforms**：创建 stream 时重写流入 subject，常与 mirror/source 配合做数据分发。
- **S2 压缩**：route、leafnode、JetStream 文件存储均支持 S2 压缩，降低跨 AZ/广域网带宽。
- **Auth Callout**：通过外部认证提供者动态签发用户权限，适合与企业 IdP/SSO 集成。
- **Consumer 多 Subject 过滤**：一个 consumer 可同时订阅多个 subject filter，简化消费侧逻辑。
- **MQTT QoS 2 支持**：原生 MQTT 监听器支持 QoS 0/1/2，保留消息改用 KV 语义实现。

### NATS 2.11 关键特性

- **单消息 TTL（Per-Message TTL）**：通过 `Nats-TTL` header 为单条消息设置过期时间；KV delete marker 也可配置 TTL，避免墓碑消息无限堆积。
- **Consumer Priority Groups**：支持 **Pinning**（单活跃客户端，故障时热备接管）与 **Overflow**（按 pending ack/消息数溢出到备用客户端）。
- **Consumer Pause**：通过 `PauseUntil` 或 `$JS.API.CONSUMER.PAUSE` 暂停投递，到时间自动恢复；心跳保持，客户端无感知。
- **分布式消息追踪**：设置 `Nats-Trace-Dest` header 追踪消息在 cluster/gateway/leafnode/import/export 路径上的流转；`Nats-Trace-Only: true` 支持干跑追踪。
- **Stream Multi-Get**：无需创建 consumer，可按多个 subject filter、序列号或时间边界批量拉取消息。

## 1.26.3 JetStream 深度机制

### Stream：消息存储

Stream 是 JetStream 的核心存储单元，每个消息被分配单调递增的 sequence number。关键配置项：

| 配置项 | 说明 | 常用值 |
| -------- | ------ | -------- |
| `subjects` | 捕获的 subject 集合 | `orders.>`, `events.*` |
| `retention` | 保留策略 | `limits`, `interest`, `workqueue` |
| `storage` | 存储介质 | `file`, `memory` |
| `replicas` | Raft 副本数 | 1/3/5 |
| `max_msgs` / `max_bytes` | 容量上限 | 按业务设定 |
| `discard` | 超限行为 | `old`, `new` |
| `subject_transform` | subject 重写 | 2.10+ |

保留策略：`limits`（按容量/时间保留，适合事件日志）、`interest`（所有 consumer ack 后删除）、`workqueue`（任一 consumer ack 后删除，适合任务队列）。

### Consumer：消费视图

Consumer 分为 **push** 与 **pull** 两种模式：

| 模式 | 投递方向 | 适用场景 | 2.11 增强 |
| ------ | ---------- | ---------- | ----------- |
| **Push** | 服务器主动推送 | 低延迟实时处理 | 支持 pause |
| **Pull** | 客户端按需拉取 | 批处理、背压控制 | priority groups、multi-get |

```bash
# 创建 Stream（捕获 orders 下所有 subject，文件存储，3 副本）
nats stream add ORDERS \
  --subjects "orders.>" \
  --storage file \
  --replicas 3 \
  --retention limits \
  --discard old \
  --max-msgs 1000000 \
  --max-age 7d

# 创建 Durable Pull Consumer，从最新位置开始，显式 ack
nats consumer add ORDERS order-processor \
  --pull \
  --deliver-policy last \
  --ack-policy explicit \
  --max-deliver 3 \
  --filter-subject "orders.us.>"

# 拉取一批消息并 ack
nats consumer next ORDERS order-processor --count 10 --ack
```

### Key-Value Store

KV Bucket 本质是名为 `KV_<bucket>` 的 Stream，subject 为 `$KV.<bucket>.>`。每个 key 是 subject 的最后一个 token，value 是该 subject 上的最新消息。

```go
package main

import (
    "fmt"
    "github.com/nats-io/nats.go"
)

func main() {
    nc, _ := nats.Connect(nats.DefaultURL)
    js, _ := nc.JetStream()

    // 创建 KV bucket（3 副本，保留 10 个历史版本）
    kv, _ := js.CreateKeyValue(&nats.KeyValueConfig{
        Bucket:   "INVENTORY",
        Replicas: 3,
        History:  10,
        TTL:      24 * time.Hour,
    })

    // 写入、读取、watch
    kv.Put("widget-blue", []byte(`{"stock":41}`))
    entry, _ := kv.Get("widget-blue")
    fmt.Printf("value=%s revision=%d\n", entry.Value(), entry.Revision())

    watcher, _ := kv.Watch("*")
    for update := range watcher.Updates() {
        if update != nil {
            fmt.Printf("key=%s value=%s\n", update.Key(), update.Value())
        }
    }
}
```

### Object Store

Object Store 用于存储超过单条消息大小的二进制对象（如 PDF、图片），底层是 `OBJ_<bucket>` Stream。对象被切分为 chunk，随后追加一条 metadata 消息；读取时按 metadata 重组并校验 SHA-256。

```bash
# 创建 Object Store bucket
nats object add INVOICES --description "Invoice PDFs" --replicas 3

# 上传文件
nats object put INVOICES invoice-ord_8w2k.pdf --file ./invoice-ord_8w2k.pdf

# 下载文件
nats object get INVOICES invoice-ord_8w2k.pdf --file ./downloaded.pdf

# 查看 bucket 状态
nats object info INVOICES
```

## 1.26.4 NATS 与其他系统对比

### NATS Core 与 JetStream 对比

| 维度 | NATS Core | NATS JetStream |
| ------ | ----------- | ---------------- |
| **投递语义** | at-most-once | at-least-once |
| **持久化** | 无 | 文件/内存，Raft 复制 |
| **顺序保证** | 无 | Stream 内按序 |
| **重放能力** | 无 | 支持按时间/序列号重放 |
| **延迟** | 30-100μs | 亚毫秒-毫秒 |
| **吞吐量** | 200万+ TPS | 20-50万 TPS |
| **适用场景** | 实时控制、RPC | 事件流、队列、状态存储 |

### NATS 与 Kafka、RabbitMQ、Pulsar 选型矩阵

| 维度 | NATS (Core+JetStream) | Kafka (KRaft) | RabbitMQ | Pulsar |
| ------ | ----------------------- | --------------- | ---------- | -------- |
| **核心定位** | 统一连接层 + 轻量流 | 高吞吐日志 | 通用消息队列 | 多租户流平台 |
| **协议** | NATS 文本协议 | 自定义二进制 | AMQP 0-9-1 | 自定义 + 多协议 |
| **持久化** | JetStream（可选） | 强制磁盘持久化 | 可选 | BookKeeper |
| **一致性** | Raft（JetStream） | KRaft/ISR | 镜像队列/Quorum | BookKeeper Quorum |
| **多租户** | Accounts + 权限 | 有限 | vhosts | 原生租户/命名空间 |
| **部署复杂度** | 低（单二进制） | 中-高 | 中 | 高 |
| **典型延迟** | Core <100μs；JS 亚毫秒 | 5-100ms | 1-10ms | 5-50ms |
| **MQTT 支持** | 原生内置（2.2+） | 需外部桥接 | 需插件 | 需协议适配器 |
| **边缘/IoT** | 优秀（leafnode、小体积） | 差 | 中 | 中 |
| **超大规模分区** | 中 | 优秀 | 受限 | 优秀 |

### MQTT 与 NATS 集成方式

NATS Server 自 2.2 起内置 MQTT 监听器，2.10 支持 QoS 2。MQTT topic 中的 `/` 会被转换为 NATS subject 的 `.`，因此 MQTT 设备可直接接入 NATS 骨干。

```conf
# nats-server.conf：启用 JetStream 与 MQTT
jetstream {
    store_dir: /data/jetstream
    max_memory_store: 1GB
    max_file_store: 100GB
}

mqtt {
    port: 1883
    tls {
        cert_file: /etc/nats/server.crt
        key_file: /etc/nats/server.key
    }
    # QoS 1/2 的会话与保留消息依赖 JetStream
    ack_wait: 1m
    max_ack_pending: 100
}

accounts {
    MQTT {
        jetstream: enabled
        users [
            { user: sensor, password: $2y$10$... }
        ]
    }
}
```

## 1.26.5 部署与运维要点

### 集群拓扑

生产环境推荐 **3 或 5 节点**组成 JetStream 集群，通过 `--cluster` 与 `--routes` 互联；跨地域场景叠加 **gateway** 与 **leafnode** 实现中心-边缘扩展。

```text
中心集群（3-5 节点，full mesh）
    ├─ Gateway ── 其他数据中心
    └─ Leafnode ── 边缘网关 / IoT 现场
```

### 存储与备份

文件存储节点独立保存数据，Raft 保证一致性；JetStream 定期生成快照加速恢复。生产环境应使用 `nats stream backup` 定期备份，关键 bucket 建议异地复制。

### 监控指标

| 指标类别 | 关键指标 | 告警阈值建议 |
| ---------- | ---------- | -------------- |
| **可用性** | `/healthz`、`/jsz` 状态 | 任何节点非 OK |
| **延迟** | publish latency、consumer pending | P99 > 10ms |
| **容量** | stream bytes、msg count | >80% 上限 |
| **一致性** | Raft 选举频率 | >1 次/小时 |
| **MQTT** | 连接数、QoS 会话积压 | 按设备规模设定 |

### 升级注意事项

1. **2.9 → 2.10**：磁盘存储格式变化，升级后若需回滚必须回到 **2.9.22+**，否则旧版本无法读取新格式。
2. **2.10 → 2.11**：支持滚动升级，但建议先升级到 2.10.22+ 再跨大版本。
3. **混合版本**：滚动升级期间避免同时存在 2.9 与 2.10 节点管理同一 JetStream asset。
4. **新功能启用**：per-message TTL、priority groups 等需要客户端与服务器均为 2.11+。
