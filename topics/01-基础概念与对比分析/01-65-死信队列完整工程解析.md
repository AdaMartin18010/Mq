## 1.65.1 DLQ 语义模型

### 进入条件分类

死信队列并非一个独立的消息语义，而是对"已判定为不可正常投递/处理的消息"的归属约定。从工程实践看，触发进入 DLQ 的条件可分为四类：

- **poisonous（毒消息）**：消息体本身合法，但业务处理必然失败，例如无法解析的 schema、违反业务不变量的字段、触发下游致命缺陷的输入。【论证】无论重试多少次都会失败，应尽早进入 DLQ，避免占用重试资源。
- **expired（超时/过期）**：消息在队列中停留超过 TTL，或业务有效期已过。典型场景如限时订单、缓存刷新事件、定时任务触发窗口。【论证】过期后继续投递已失去业务意义，转入 DLQ 或丢弃。
- **rejected（显式拒绝）**：消费者调用 `reject`/`nack` 且 `requeue=false`，明确告知 broker 该消息无法处理。【定理】在 AMQP 0-9-1 中，`basic.reject` 或 `basic.nack` 配合 `requeue=false` 是标准死信触发条件之一。
- **exceeded retries（重试耗尽）**：消息经多次重投仍未被确认，达到策略上限后进入 DLQ。这是最常见的 DLQ 入口，也是与重试机制直接耦合的点。

上述四类并非互斥。一条消息可能先因 `nack` 进入重试，重试耗尽后再因 `exceeded retries` 进入 DLQ；也可能先因 TTL 过期被 dead-lettered，再因目标队列超限被二次 dead-lettered。因此 DLQ 设计必须考虑**多次死信的溯源能力**。

### DLQ 与重试的关系矩阵

重试与 DLQ 是同一错误处理连续体的两端：重试解决"暂时性失败"，DLQ 解决"持久性或未知失败"。二者的关系可用下表刻画：

| 维度 | 重试（Retry） | 死信队列（DLQ） |
| --- | --- | --- |
| 目标 | 利用时间差等待下游恢复 | 隔离不可处理消息，防止阻塞主流程 |
| 触发条件 | 可重试异常（网络/超时/依赖不可用） | 不可重试异常（毒消息/业务规则失败/重试耗尽） |
| 顺序影响 | 同分区/同队列内可能乱序或阻塞后续消息 | 死信消息脱离原流，不再保证原序 |
| 常见策略 | 固定间隔/指数退避/线性退避 | 单次进入或分层 retry topic → DLQ |
| 可观测性 | 重试次数、重试间隔、重试成功率 | 死信深度、最老死信年龄、错误类型分布 |
| 人工介入 | 通常自动 | 常需人工复核、分析、补发或丢弃 |

【论证】该矩阵是工程权衡的抽象：若把重试次数设得无限大，则 DLQ 失去意义；若把重试次数设得过小，则暂时性抖动会被误判为毒消息。合理阈值应大于下游故障恢复时间的 P99，并留出安全余量。

### 死信是否保序/保真问题

DLQ 是否需要保留原消息的顺序和 exactly-once 语义，是设计时的核心问题：

- **保序（Ordering）**：【论证】进入 DLQ 的消息通常已脱离原分区/队列的消费上下文。Kafka 自定义 DLQ topic 若按原 key 分区可保留同 key 顺序，但跨 key 无保证；RabbitMQ DLX 重新发布到 exchange 后路由到队列，不继承原队列顺序；Pulsar DLQ topic 是独立 topic，顺序由原 topic 的 key 分保决定。因此**死信再处理不应依赖与原流严格一致的顺序**。
- **保真（Fidelity）**：【论证】DLQ 记录至少应包含原始消息的 key、value、headers、错误上下文（topic/queue、分区、offset、错误类型、堆栈、时间戳）。KIP-1191 定义了 `__dlq.errors.*` 标准头；RabbitMQ 会在消息头中追加 `x-death` 数组。是否复制完整 value 涉及安全与容量权衡——KIP-1191 的 `errors.deadletterqueue.copy.record.enable` 默认 false，仅写上下文头，避免敏感数据二次扩散。
- **恰好一次（Exactly-once）**：【论证】DLQ 写操作在多数系统中并非原子化。KIP-1191 明确说明：broker 不保证 DLQ 写与 share-group 状态写原子一致，极端情况下可能写入多条 DLQ 记录；RabbitMQ DLX 重新发布是独立操作，可能因网络或 exchange 不可达而丢失；Pulsar DLQ 由客户端/服务端在重试耗尽后写入，也存在重复可能。因此**消费 DLQ 的应用必须幂等**。

## 1.65.2 Kafka：无原生 DLQ 到 KIP-1191 共享组 DLQ

Kafka 传统消费组（consumer group）没有 broker 级 DLQ。消息处理失败后，消费者可选择：

1. 不提交 offset，导致该分区无限阻塞（poison pill 问题）；
2. 提交 offset并丢弃，可能丢失数据；
3. 应用层捕获异常，将记录转发到独立的 `dlq-<topic>`，再提交 offset。

第三种是 Kafka 生态长期以来的主流模式。Kafka 4.2 引入的 Share Groups（KIP-932）在 broker 层维护 delivery count，但 4.2/4.3 仅将超限记录标记为 Archived，不会自动转移。直到 **Kafka 4.4 的 KIP-1191** 才正式引入 broker 管理的死信队列。

### KIP-1191 Share Groups DLQ 机制

【论证】根据 [KIP-1191](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1191%3A+Dead-letter+queues+for+share+groups) 与 [Kafka 4.4 发行说明](https://www.confluent.io/blog/introducing-apache-kafka-4-4-0/)，Share Groups DLQ 的核心规则如下：

- 必须将集群特性版本升级到 `share.version=2`（Kafka 4.4 新集群默认满足）。
- 通过 group 配置 `errors.deadletterqueue.topic.name` 指定 DLQ topic，默认空即不启用。
- 通过 group 配置 `errors.deadletterqueue.copy.record.enable` 控制是否复制原记录 value，默认 false。
- 通过 broker 配置 `errors.deadletterqueue.topic.name.prefix` 限制 DLQ topic 名前缀，默认 `dlq.`。
- 通过 broker 配置 `errors.deadletterqueue.auto.create.topics.enable` 控制是否自动创建 DLQ topic，默认 false。
- 最大投递次数由 `share.delivery.count.limit` 控制，默认 5，有效范围 `[2, ...]`。
- DLQ 记录会带 `__dlq.errors.topic/partition/offset/group/delivery.count` 等上下文头。
- DLQ 写非原子，极端情况可能重复；写入失败时记录仍会进入 Archived 状态。

```bash
# Kafka 4.4+ Share Group DLQ 配置示例
# 1. 创建业务 topic 与 DLQ topic（DLQ 名必须匹配前缀 dlq.）
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic dlq.orders --partitions 6 --replication-factor 3

# 2. 创建或修改 share group 配置（group id = payment-share）
kafka-configs.sh --bootstrap-server localhost:9092 \
  --group payment-share \
  --describe

kafka-configs.sh --bootstrap-server localhost:9092 \
  --group payment-share \
  --alter \
  --add-config "errors.deadletterqueue.topic.name=dlq.orders,errors.deadletterqueue.copy.record.enable=true"
```

```java
// Kafka 4.4+ Share Consumer 示例（自动进入 DLQ 无需应用侧写）
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "payment-share");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
// 必须指定 share 消费者协议
props.put("group.protocol", "share");

KafkaShareConsumer<String, String> consumer = new KafkaShareConsumer<>(props);
consumer.subscribe(List.of("orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
    for (ConsumerRecord<String, String> record : records) {
        try {
            process(record);
            consumer.commitSync();
        } catch (UnrecoverableException e) {
            // 显式 reject，broker 会立即写入 DLQ
            consumer.reject(record);
        }
    }
}
```

### Spring Kafka ErrorHandler 模式

在 Kafka 4.4 之前的生产环境中，Spring Kafka 的 `DefaultErrorHandler` 配合 `DeadLetterPublishingRecoverer` 是事实标准：

```java
@Configuration
public class KafkaDlqConfig {

    @Bean
    DefaultErrorHandler errorHandler(KafkaOperations<Object, Object> template) {
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
            template,
            // 死信 topic 命名策略：dlq.<original-topic>
            (record, ex) -> new TopicResolutionSupport() {}
                .resolve(record, ex, "dlq", "")
        );
        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer);
        handler.setBackOffFunction((record, ex) -> {
            if (ex.getCause() instanceof RetryableException) {
                return new FixedBackOff(2000L, 3); // 间隔 2s，最多 3 次
            }
            return new FixedBackOff(0L, 0); // 非可重试立即进 DLQ
        });
        return handler;
    }
}
```

【论证】Spring Kafka 模式属于应用层 DLQ，优点是可精细控制重试/死信策略、可 enrich 错误信息；缺点是每个消费者都要实现，且失败写 DLQ 本身也需要处理（如 Fallback 到日志或本地存储）。

### 自定义 DLQ Topic 模式

对于不使用 Spring 或 Share Groups 的场景，典型分层模式为：

```text
orders
  ↓ 消费失败
orders.retry.10s  →  TTL/延迟后回到 orders 或进入下一层
  ↓ 仍失败
orders.retry.30s
  ↓ 仍失败
orders.retry.5m
  ↓ 仍失败
orders.dlq
```

```java
// 简化的应用层 DLQ 转移（Kafka 传统消费组）
void onRecord(ConsumerRecord<String, String> record) {
    try {
        processor.apply(record);
        consumer.commitSync();
    } catch (Exception e) {
        ProducerRecord<String, String> dlq = new ProducerRecord<>(
            "orders.dlq",
            record.key(),
            record.value(),
            enrichHeaders(record.headers(), e)
        );
        producer.send(dlq, (md, ex) -> {
            if (ex == null) consumer.commitSync();
            else log.error("DLQ write failed", ex); // 需 fallback
        });
    }
}
```

Kafka 三种 DLQ 模式对比如下：

| 模式 | 适用版本 | 实现位置 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| 应用层自定义 DLQ topic | 全版本 | 应用代码 | 最灵活，可控 enrich | 每个应用重复实现，DLQ 写失败需兜底 |
| Spring Kafka ErrorHandler | 全版本（依赖 Spring） | 框架层 | 与监听注解集成，配置化 | 仍属应用层，异常链路复杂 |
| KIP-1191 Share Groups DLQ | Kafka 4.4+ | Broker | 统一配置，自动转储，带标准头 | 仅 share group，传统消费组不支持；DLQ 写非原子 |

## 1.65.3 RabbitMQ：DLX 绑定与 First Death 问题

RabbitMQ 是六系统中 DLQ 机制最原生的：通过 `x-dead-letter-exchange` 将队列与死信 exchange 绑定，消息成为死信后自动重新发布到该 exchange。

### DLX 绑定语义

【定理】AMQP 0-9-1 扩展下，RabbitMQ 中消息被 dead-lettered 的条件为：

1. 消费者调用 `basic.reject` 或 `basic.nack` 且 `requeue=false`；
2. 消息 TTL 过期（per-message TTL 或队列级 `x-message-ttl`）；
3. 队列长度超限（`x-max-length` 或 `x-max-length-bytes`），队首消息被逐出。

```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()

# 1. 声明死信 exchange 与死信队列
channel.exchange_declare(exchange="orders.dlx", exchange_type="topic", durable=True)
channel.queue_declare(queue="orders.dlq", durable=True,
                      arguments={"x-message-ttl": 259200000})  # DLQ 内保留 3 天
channel.queue_bind(queue="orders.dlq", exchange="orders.dlx", routing_key="orders.#")

# 2. 声明主队列并绑定 DLX
channel.queue_declare(
    queue="orders",
    durable=True,
    arguments={
        "x-dead-letter-exchange": "orders.dlx",
        "x-dead-letter-routing-key": "orders.dead",
        "x-message-ttl": 300000,        # 业务消息 5 分钟有效期
        "x-max-length": 100000,         # 队列长度上限
        "x-overflow": "drop-head"       # 超限逐出队首
    }
)
```

### dead-lettered 的路由重建

【论证】消息进入 DLX 时，RabbitMQ 会尝试使用原 routing key（若声明时未指定 `x-dead-letter-routing-key`）或指定的 `x-dead-letter-routing-key` 进行路由。若同时设置了 per-message TTL 和队列级 TTL，以较小者为准。DLX 本身只是一个普通 exchange，因此可以复用 topic/direct/fanout/headers 全部路由能力。

RabbitMQ 还会在消息头中追加 `x-death` 数组，记录每一次 dead-lettered 事件：

| 字段 | 含义 |
| --- | --- |
| `reason` | 死信原因：`rejected`、`expired`、`maxlen` |
| `queue` | 发生死信的队列名 |
| `time` | 死信发生时间戳 |
| `exchange` | 消息来源 exchange |
| `routing-keys` | 消息携带的 routing key 列表 |
| `count` | 同一原因/队列组合下的死信次数 |

### TTL+DLX 组合与延迟队列陷阱

TTL+DLX 常被用来实现延迟队列：消息进入一个无消费者的延迟队列，TTL 到期后通过 DLX 路由到目标队列。该模式有两个常见陷阱：

- **First Death 问题**：【论证】当消息因 TTL 过期被 dead-lettered 后，如果再次进入另一个带 TTL 的队列，RabbitMQ 会读取消息头中的 `x-death` 信息。若消息曾经被 dead-lettered 过，后续 TTL 计算可能受 `x-death` 影响而提前过期，导致延迟不准确。实现多级延迟时应清除或重置相关头，或改用 rabbitmq_delayed_message_exchange 插件。
- **队首阻塞**：【论证】RabbitMQ 队列中，只有队首消息的 TTL 到期后才会被移除。如果队首消息 TTL 很长，后续短 TTL 消息会被阻塞，无法及时进入 DLX。这是 TTL 延迟队列的固有缺陷，不适合需要精确延迟分级的场景。

```python
# 延迟队列模式：延迟 30 秒后进入目标队列
channel.queue_declare(
    queue="orders.delay.30s",
    durable=True,
    arguments={
        "x-dead-letter-exchange": "orders.target",
        "x-dead-letter-routing-key": "orders.ready",
        "x-message-ttl": 30000
    }
)
```

## 1.65.4 Pulsar：DeadLetterPolicy 阈值语义

Pulsar 在订阅级（subscription-level）提供 DLQ，且与 retry letter topic（RLQ）天然联动。DLQ 仅对 **Shared** 订阅类型生效，Exclusive/Failover 不支持。

### negative ack 与 redelivery count

【论证】Pulsar 消费者可通过 `negativeAcknowledge(msg)` 触发重投，也可通过 `reconsumeLater(msg, delay, unit)` 主动进入 RLQ。`DeadLetterPolicy.maxRedeliverCount` 定义了消息在 DLQ 前最多被重投的次数。需要区分：

- **negativeAcknowledge**：立即或在 `negativeAckRedeliveryDelay` 后重投，不进入 RLQ。
- **reconsumeLater**：将消息写入 `<topic>-<subscription>_RETRY`，按指定延迟调度，重试耗尽后进入 DLQ。
- **acknowledgement timeout**：若开启 `ackTimeout`，超时未确认也会触发重投，计入 redelivery count。

```java
Consumer<byte[]> consumer = pulsarClient.newConsumer()
    .topic("persistent://public/default/orders")
    .subscriptionName("order-sub")
    .subscriptionType(SubscriptionType.Shared)
    .ackTimeout(30, TimeUnit.SECONDS)
    .negativeAckRedeliveryDelay(5, TimeUnit.SECONDS)
    .deadLetterPolicy(DeadLetterPolicy.builder()
        .maxRedeliverCount(3)
        .retryLetterTopic("persistent://public/default/orders-order-sub-RETRY")
        .deadLetterTopic("persistent://public/default/orders-order-sub-DLQ")
        .build())
    .subscribe();

while (true) {
    Message<byte[]> msg = consumer.receive();
    try {
        process(msg);
        consumer.acknowledge(msg);
    } catch (RetryableException e) {
        consumer.reconsumeLater(msg, 10, TimeUnit.SECONDS);
    } catch (NonRetryableException e) {
        consumer.negativeAcknowledge(msg); // 快速耗尽后进入 DLQ
    }
}
```

### DLQ Topic 消费与重试队列

【论证】DLQ topic 的默认命名格式为 `<topic>-<subscription>_DLQ`，可显式指定。RLQ 与 DLQ 都是普通 Pulsar topic，可独立订阅消费。再处理时常见做法：

1. 独立消费者订阅 DLQ topic，人工复核或自动分析；
2. 修复后通过生产者将消息写回原业务 topic（需保证幂等）；
3. 对可自动恢复的错误，可写回 RLQ 进行有限次再重试。

Pulsar 的 DLQ 由 broker/客户端在重试耗尽后写入，写入成功后原消息会被确认（ack），因此不会再被原订阅投递。这一语义与 Kafka Share Groups 的 "Archived" 状态类似，但 Pulsar 的 DLQ topic 是显式可消费的。

## 1.65.5 NATS JetStream：MaxDeliver 与 advisory 补偿

NATS JetStream **没有内建 DLQ**。它提供 `MaxDeliver`、`AckWait`、`BackOff` 等重投原语，以及 `advisory` 事件通知，由应用自行组装死信处理流程。

### 无原生 DLQ 的补偿模式

【论证】JetStream 消费者配置 `MaxDeliver` 控制最大投递次数；当消息被 `Nak()` 或超时未 ack 达到上限后，JetStream 停止向该消费者投递该消息，但**不会从 stream 中删除**。此时消息仍存在于 stream，只是对该消费者不可见。为了捕获这些失败，需要消费 advisory 主题并转存到死信 stream/外部存储。

```go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "time"

    "github.com/nats-io/nats.go"
    "github.com/nats-io/nats.go/jetstream"
)

func main() {
    nc, _ := nats.Connect(nats.DefaultURL)
    js, _ := jetstream.New(nc)
    ctx := context.Background()

    // 1. 创建业务 stream
    _, _ = js.CreateStream(ctx, jetstream.StreamConfig{
        Name:     "ORDERS",
        Subjects: []string{"orders.>"},
        Storage:  jetstream.FileStorage,
    })

    // 2. 创建消费者，MaxDeliver=3
    cons, _ := js.CreateConsumer(ctx, "ORDERS", jetstream.ConsumerConfig{
        Name:          "order-worker",
        Durable:       "order-worker",
        FilterSubject: "orders.created",
        MaxDeliver:    3,
        AckWait:       30 * time.Second,
        BackOff:       []time.Duration{1 * time.Second, 5 * time.Second, 30 * time.Second},
    })

    // 3. 业务消费
    cons.Consume(func(msg jetstream.Msg) {
        if err := process(msg.Data()); err != nil {
            msg.Nak() // 触发重投
            return
        }
        msg.Ack()
    })

    // 4. 监听 max-deliver advisory 并转存 DLQ
    sub, _ := js.CreateConsumer(ctx, "$JS.EVENT.ADVISORY", jetstream.ConsumerConfig{
        Name:          "dlq-capture",
        FilterSubject: "$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.>",
    })
    sub.Consume(func(msg jetstream.Msg) {
        var adv MaxDeliverAdvisory
        json.Unmarshal(msg.Data(), &adv)
        // 根据 stream_seq 从原 stream 取出消息并写入 dlq.orders
        orig, _ := js.GetMsg(ctx, adv.Stream, adv.StreamSeq)
        js.Publish(ctx, "dlq.orders", orig.Data())
        msg.Ack()
    })
}

type MaxDeliverAdvisory struct {
    Stream    string `json:"stream"`
    StreamSeq uint64 `json:"stream_seq"`
    Consumer  string `json:"consumer"`
    Deliveries uint64 `json:"deliveries"`
}

func process(data []byte) error { return nil }
```

### advisory 消费与死信转存

【论证】advisory 主题为 `$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.<consumer>`，payload 包含 `stream_seq`，可用其从原 stream 读取完整消息。转存时建议 enrich 以下元数据：

- 原始 subject、stream、consumer、delivery count；
- 失败原因（若业务在 `Term()` 时附带 reason）；
- 捕获时间戳与失败堆栈（若可获取）。

NATS 还有一种 `Term()` 确认，表示消息被永久终止，也不会再投递，但同样不会自动进入 DLQ，需要配合 advisory 或应用侧显式写死信。

## 1.65.6 MQTT：协议层约束与 Broker 扩展

【定理】MQTT 3.1.1/5.0 协议本身没有死信队列概念。MQTT 消息只有 QoS 0/1/2 投递语义，broker 不负责记录消费失败、重试次数或死信转移。

因此 MQTT 场景下的 DLQ 完全依赖 broker 扩展或应用层实现：

- **QoS 1/2 未确认**：broker 会按 QoS 规则重投，但无上限，也不会自动隔离毒消息。
- **应用层死信**：消费者在连续处理失败后，自行向约定的死信 topic（如 `dlq/<original-topic>`）发布消息。
- **Broker 扩展**：EMQX 等 broker 提供规则引擎，可基于 hook 将失败消息路由到指定主题或外部存储。

```sql
-- EMQX 规则引擎：将匹配特定错误码的消息转发到死信主题
SELECT
  payload,
  topic,
  qos,
  timestamp
FROM
  "message.dropped"
WHERE
  reason = 'no_subscribers' OR reason = 'delivery_failed'

DO
  republish(
    topic = "dlq/${topic}",
    qos = 1,
    payload = json_encode(
      map_get('payload', payload),
      'error_context',
      map_get('reason', payload)
    )
  )
```

【论证】MQTT 的 DLQ 设计需特别注意：

- 协议层无 ack 超时重试上限，必须依赖 broker 实现或消费者自律；
- 共享订阅（Shared Subscription）可让多个消费者分摊负载，但失败消息仍会在订阅组内重投；
- 大量物联网终端离线时，QoS 1/2 消息可能在 broker 积压，建议结合 `message expiry interval` 与 broker 规则引擎做过期清理或转 DLQ。

## 1.65.7 Redis Stream：Pending 列表与 XAUTOCLAIM 补偿

Redis Stream 也没有内建 DLQ。消息被消费者读取后进入 **PEL（Pending Entries List）**，直到被 `XACK`。若消费者崩溃或长期不确认，PEL 中的消息会持续挂起。

### 补偿模式

【论证】Redis Stream 的死信处理依赖对 PEL 的主动巡检：

1. 使用 `XPENDING` 获取挂起消息列表及空闲时间（idle time）；
2. 对 idle time 超过阈值的消息，使用 `XCLAIM` 或 `XAUTOCLAIM` 转移给其他消费者或死信 stream；
3. 超过最大重试次数后，写入 `dlq:<stream>` 并可选 `XDEL` 原消息。

```bash
# 1. 查看挂起消息及空闲时间
XPENDING orders order-consumer-group - + 100

# 2. 自动认领空闲超过 60 秒的消息（转移给其他消费者做重试）
XAUTOCLAIM orders order-consumer-group retry-worker 60000 0-0 COUNT 100

# 3. 对多次认领仍失败的消息，用脚本写入死信 stream（示例为 Lua 伪代码）
# Lua 脚本思路：XPENDING 获取消息后，XCLAIM 到 dlq-consumer，XADD dlq:orders，XACK 原消息
```

```python
import redis
import time

r = redis.Redis()

DLQ_THRESHOLD_IDLE_MS = 300_000   # 5 分钟未处理视为可疑
DLQ_MAX_RETRIES = 3

while True:
    # XAUTOCLAIM: 将空闲超过阈值的消息转移给当前消费者
    claimed = r.xautoclaim(
        "orders", "order-consumer-group", "dlq-probe",
        min_idle_time=DLQ_THRESHOLD_IDLE_MS,
        start="0-0", count=100
    )
    for stream_id, fields in claimed[1]:
        retry_count = int(r.hget(f"dlq:meta:{stream_id}", "retry") or 0)
        if retry_count >= DLQ_MAX_RETRIES:
            r.xadd("dlq:orders", {k: v for k, v in fields.items()})
            r.xack("orders", "order-consumer-group", stream_id)
            r.delete(f"dlq:meta:{stream_id}")
        else:
            r.hincrby(f"dlq:meta:{stream_id}", "retry", 1)
            # 重新处理或转移给正常 worker
    time.sleep(10)
```

【论证】Redis Stream 的死信处理完全应用侧负责，运维负担高。其优势是轻量、低延迟；劣势是无 broker 级重试/死信语义，且 XAUTOCLAIM 的 `start="0-0"` 扫描可能重复处理已 ack 消息，需要幂等消费。

## 1.65.8 六系统 DLQ 能力对比总表

| 系统 | 内建 DLQ | 触发条件 | 关键配置/原语 | 死信再消费 | 主要坑点 |
| --- | :---: | --- | --- | --- | --- |
| Kafka | 4.4- 否；4.4+ share group 是 | 传统组：应用侧捕获；share group：reject / 重试耗尽 | `errors.deadletterqueue.topic.name`、`share.delivery.count.limit` | 普通 topic 订阅 | 4.4 前无原生；DLQ 写非原子；仅 share group |
| RabbitMQ | 是 | nack/reject requeue=false、TTL 过期、队列超限 | `x-dead-letter-exchange`、`x-dead-letter-routing-key`、`x-message-ttl` | DLX 绑定队列消费 | First Death 头、队首 TTL 阻塞、循环死信 |
| Pulsar | 是 | 重试耗尽（negative ack / ack timeout / reconsumeLater） | `DeadLetterPolicy.maxRedeliverCount`、RLQ/DLQ topic | 独立 DLQ topic 订阅 | 仅 Shared 订阅；batch index ack 边界 |
| NATS JetStream | 否 | `MaxDeliver` 用尽 / `Term()` | `MaxDeliver`、`AckWait`、`BackOff`、advisory | 消费 advisory 后自建 DLQ stream | 无自动转存；需应用主动 claim 原消息 |
| MQTT | 否（协议层） | 应用层 / broker 扩展 | EMQX 规则引擎等 | 约定死信主题 | 协议无 ack 上限；离线终端积压 |
| Redis Stream | 否 | PEL 挂起超时 / 应用侧重试耗尽 | `XPENDING`、`XCLAIM`、`XAUTOCLAIM` | 自建 `dlq:<stream>` | 完全应用侧；扫描可能重复 |

## 1.65.9 死信再处理工程

### 重放策略

死信不是终点，而是人工/自动恢复流程的起点。常见重放策略：

| 策略 | 适用场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 批量重放 | 下游已恢复、错误已修复、可接受一定延迟 | 吞吐高、操作简单 | 可能再次触发相同错误，需前置过滤 |
| 单条重放 | 高价值消息、金融交易、需逐笔确认 | 风险可控、可审计 | 人工成本高、吞吐低 |
| 改路由重放 | 原 topic/队列已下线、业务逻辑已迁移 | 兼容架构演进 | 需要维护路由映射 |
| 丢弃归档 | 日志/埋点类、可容忍丢失 | 节省资源 | 不可逆，需预先获得业务授权 |

【论证】重放前必须进行**错误分类**：网络/依赖类暂时错误可自动重放；schema/业务规则类错误必须先修复代码；不可识别错误应进入人工复核台。建议对 DLQ 消息打标签：`retryable`、`fixed`、`manual`、`discard`。

### 死信分析工具

- **错误聚类**：按错误类型、异常类、业务字段、来源 topic/队列聚合，定位高频根因。
- **影响面评估**：统计死信数量占生产消息比例、涉及用户/订单数、金额影响（金融场景）。
- **根因追踪**：将死信与原生产链路 trace ID 关联，结合 OpenTelemetry 等追踪系统定位失败节点。
- **重放审计**：记录每次重放的操作人、时间、结果、目标 topic/队列，满足合规要求。

### 告警与 Metrics 设计

DLQ 的 metrics 应纳入统一可观测体系，核心指标：

- `dlq_messages_total`：累计进入 DLQ 的消息数（按 source、reason 分标签）；
- `dlq_messages_current`：当前 DLQ 深度；
- `dlq_oldest_message_age_seconds`：最老死信年龄；
- `dlq_replay_total` / `dlq_replay_success_total`：重放次数与成功率；
- `dlq_dlq_write_failed_total`：DLQ 写入失败次数（应用层模式）。

```yaml
# Prometheus 告警规则示例
 groups:
   - name: dlq_alerts
     rules:
       - alert: DLQHighRate
         expr: rate(dlq_messages_total[5m]) > 0.1
         for: 2m
         labels:
           severity: warning
         annotations:
           summary: "DLQ 消息增长过快"
           description: "source={{ $labels.source }} 的 DLQ 速率为 {{ $value }}/s"

       - alert: DLQBacklogOld
         expr: dlq_oldest_message_age_seconds > 3600
         for: 5m
         labels:
           severity: critical
         annotations:
           summary: "DLQ 存在超过 1 小时未处理的死信"

       - alert: DLQWriteFailed
         expr: increase(dlq_dlq_write_failed_total[5m]) > 0
         for: 1m
         labels:
           severity: critical
         annotations:
           summary: "DLQ 写入失败，可能导致消息丢失"
```

## 1.65.10 DLQ 容量与治理

### 保留策略与审计

DLQ 本身也是消息存储，必须设置保留策略，否则会成为无限增长的"垃圾堆"：

- **时间保留**：如 Kafka `log.retention.hours=168`（7 天）、RabbitMQ DLQ 队列 `x-message-ttl=259200000`（3 天）。
- **大小保留**：如 Kafka `log.retention.bytes`、RabbitMQ `x-max-length-bytes`。
- **容量隔离**：DLQ topic/队列应使用独立磁盘/分区，避免影响主业务流。
- **访问控制**：DLQ 中可能包含敏感业务数据，应限制访问权限，满足最小权限原则。

审计要求：

| 审计项 | 要求 | 示例 |
| --- | --- | --- |
| 死信来源 | 记录原始 topic/队列、分区、offset/key | Kafka `__dlq.errors.*` headers |
| 死信原因 | 记录异常类型、错误码、堆栈摘要 | 应用 enrich 的 `x-error-*` headers |
| 处理轨迹 | 记录进入 DLQ、人工复核、重放/丢弃全流程 | 操作日志 + 消息头状态转移 |
| 保留期限 | 按合规要求设定，过期前归档 | 金融 7 年，普通业务 30~90 天 |
| 访问日志 | 谁查看了 DLQ、谁执行了重放 | 审计表/API 日志 |

### 金融场景合规与冲正互链

在金融支付、证券结算等场景中，DLQ 不仅是技术组件，更是账务一致性的关键兜底。死信消息可能对应一笔未完成的交易，其处理必须满足：

- **不可丢失**：DLQ 必须多副本、持久化，写入失败要有本地/远程 fallback；
- **可追溯**：死信必须与原交易流水号、订单号、trace ID 绑定；
- **冲正互链**：对于已扣款但未完成下游确认的交易，死信处理台需触发冲正或补偿流程。详见 [1.45 产业领域消息标准纵览](01-45-产业领域消息标准纵览.md) 中金融消息标准与冲正机制章节。

【论证】建议为金融场景建立独立的人工干预台（Operations Console），集成死信查看、错误分类、单笔重放、批量重放、强制丢弃、冲正申请等功能，并与审计系统对接。

## 1.65.11 端到端设计模板

以下是一个从生产者到 DLQ 再到人工干预台的完整链路设计示例（以类 Kubernetes CRD + Kafka 语义为例，可迁移到 RabbitMQ/Pulsar 等系统）。

```yaml
# mq-dlq-policy.yaml
apiVersion: mq.example.com/v1
kind: MessageDLQPolicy
metadata:
  name: payment-order-dlq
spec:
  source:
    type: kafka
    cluster: payment-kafka
    topic: payment.orders
    consumerGroup: payment-order-consumer
  retry:
    strategy: exponential
    maxRetries: 5
    initialIntervalMs: 1000
    maxIntervalMs: 60000
    multiplier: 2.0
  dlq:
    enabled: true
    # Kafka 4.4 share group 模式：broker 自动写入
    brokerManagedTopic: dlq.payment.orders
    # 应用层兜底：当 broker DLQ 写入失败时使用
    fallbackTopic: dlq.payment.orders.fallback
    copyOriginalRecord: true
    enrichHeaders:
      - x-error-type
      - x-error-message
      - x-trace-id
      - x-business-order-no
  retention:
    timeHours: 168        # 7 天
    sizeBytes: 10737418240 # 10 GiB
  observability:
    metricsPrefix: dlq_payment_orders
    alerts:
      - name: HighDLQRate
        threshold: 0.1    # 每秒 >0.1 条告警
        duration: 2m
      - name: OldDLQMessage
        threshold: 3600   # 最老消息 >1h 告警
        duration: 5m
  replay:
    enabled: true
    approvalRequired: true  # 人工审批后重放
    maxReplayBatchSize: 100
    allowedTargets:
      - payment.orders.retry
      - payment.orders
  opsConsole:
    enabled: true
    rbacRoles:
      - role: dlq-viewer
        permissions: [read]
      - role: dlq-operator
        permissions: [read, replay, discard]
      - role: dlq-admin
        permissions: [read, replay, discard, purge]
```

该模板的关键设计点：

- **分层 retry + DLQ**：先指数退避重试，再进入 broker 管理 DLQ，最后应用层 fallback；
- **上下文 enrich**：保留业务订单号、trace ID，便于金融审计与冲正；
- **人工审批重放**：高风险操作需审批，所有操作入审计日志；
- **RBAC 隔离**：不同角色拥有不同 DLQ 操作权限，防止误操作。
