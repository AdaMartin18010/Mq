## 1.36.1 RAG 管道的消息化改造

传统 RAG 是"批处理+同步 API"形态：文档变更 → 定时全量重建索引 → 查询。事件驱动改造后【论证】：

```text
文档变更事件 (CDC) → [ingest-topic]
  → 分块/清洗 worker（竞争消费） → [chunk-topic]
  → 嵌入 worker（批处理优化）   → [embedding-topic]
  → 向量库写入 sink             ←→ [index-dlq]（失败重试/人工）
查询侧：Query → 检索（向量库） → Rerank → LLM → 流式输出
```

消息化的收益【论证】：①变更到索引的延迟从"小时级批"降到"秒级流"；②嵌入调用（成本敏感）可集中批处理与限流；③每阶段独立扩缩容（1.33/02-49 的 lag 伸缩直接适用）；④失败可回放——嵌入 worker 崩溃不丢变更。

## 1.36.2 四类事件的流式语义

| 事件 | 语义要求 | MQ 映射 |
| ------ | ---------- | --------- |
| 文档新增/更新 | 有序（同文档分片有序）、至少一次 | 按 doc-id 分区（02-27）+ 幂等 upsert |
| 文档删除 | 恰好一次传播（漏删=隐私事故） | 独立 delete-topic + 死信人工台（02-50 合规衔接） |
| 查询请求 | 低延迟 req-reply、可取消 | MQTT 5 req/res / NATS req-reply（01-35） |
| 流式输出分片 | 顺序严格、背压感知 | 专用输出通道 + 消费者拉取（02-22 流控） |

## 1.36.3 技术栈组合

| 环节 | 组件选项 | 说明 |
| ------ | ---------- | ------ |
| 变更捕获 | Debezium CDC（见 01-31） | 数据源→Kafka/Pulsar 的事实标准 |
| 流处理 | Flink / Kafka Streams（见 01-31） | 分块/富化的状态计算 |
| 嵌入缓冲 | Kafka（批量窗口）+ 限流（02-37） | 嵌入 API 成本与配额治理 |
| 向量库消费 | 专用 sink connector | 注意向量库批量写入语义 |
| LLM 输出 | SSE/WebSocket（短直连）或 MQ 中转（长任务/多订阅者） | 短平快用直连；异步多人协作场景用 MQ【论证】 |

## 1.36.4 一致性难题：索引新鲜度

核心矛盾【论证】：向量库不是日志——**它没有"消费位点"**。MQ 重放时，嵌入 worker 会重复写入（幂等 upsert 可解）；但向量库本身的删除/更新乱序需要版本向量（version vector）或按时间戳 last-write-wins【论证】。

新鲜度 SLO 设计【论证】：定义"索引滞后窗口"（如变更后 30s 可检索）→ 管道各环节 lag 预算分解（ingest<5s、chunk<10s、embed<10s、sink<5s）→ 每个环节接 1.33 监测与 2.49 伸缩。超窗即告警（TEST-07 模式可复用）。

### 删除传播的端到端流程（合规关键，02-50 衔接）

```text
删除请求 → delete-topic（高优先级独立通道，与业务通道分离）
  → 向量库 delete-by-doc-id（物理删向量）
  → 对象存储删除原文（生命周期规则兜底）
  → 审计事件留痕（删除证据，消息只传 doc-id 不含 PII）
```

删除失败的死信处理【论证】：delete-DLQ 按合规事故级别告警（P0）——未删干净的索引 = 删除权未兑现，比消费失败严重得多。

### 嵌入批处理与限流（成本敏感点，03-65 衔接）

```python
# 嵌入 worker：攒批 + 去重 + 限流三件套
batch = collect(embedding_topic, max_records=64, max_wait=2.0)   # 批量窗口
batch = [c for c in batch if not embed_cache.has(c.hash)]        # 哈希去重免重复计费
if embed_quota.remaining() < len(batch):                         # 配额限流（02-37）
    pause(); alert()
vectors = embed_api.embed(batch)
```

嵌入 API 通常是 RAG 管道最大变动成本项【估算】：治理三件套（批量/去重/限流）通常可降本一个量级【估算】。

### 成本结构表（FinOps 视角）

| 成本项 | 弹性 | 治理手段 |
| -------- | ------ | ---------- |
| 嵌入 API 调用 | 与文档量正比、单价高 | 批量+去重+限流 |
| MQ 管道资源 | 与吞吐正比 | lag 伸缩（02-49） |
| 向量库存储 | 与 chunk 数正比 | 分块策略是成本杠杆【估算】 |
| 对象存储（原文） | 静态 | 生命周期分层 |

## 1.36.5b 参考实现（Kafka Connect 风格伪配置）

```properties
# ingest：Debezium CDC → ingest-topic
connector.class=io.debezium.connector.postgresql.PostgresConnector
transforms=unwrap,route
transforms.route.type=org.apache.kafka.connect.transforms.RegexRouter
transforms.route.regex=.*\.(.*)
transforms.route.replacement=$1-ingest

# chunk：分块 worker（应用或 Kafka Streams）
chunk.size.tokens=512            # 分块大小是成本/召回的杠杆【估算】
chunk.overlap.tokens=64
chunk.hash.alg=sha256            # 嵌入去重键

# embed：攒批 + 限流（见 1.36.4）
embed.batch.max_records=64
embed.batch.max_wait_ms=2000
embed.quota.daily_usd=100

# sink：向量库写入（幂等 upsert）
sink.idempotency.key=chunk_hash
sink.conflict.strategy=timestamp_lww   # 或 version vector
```

## 1.36.5c 分块策略设计表

| 文档类型 | 分块策略 | 理由 |
| ---------- | ---------- | ------ |
| FAQ/短文档 | 整篇一块 | 语义完整优先 |
| 技术长文 | 按标题树 512 token | 结构边界对齐语义 |
| 代码文档 | 按函数/类边界 | 符号完整性 |
| 表格数据 | 按行组+表头重复 | 保留列语义 |
| 对话记录 | 按轮次窗口 | 上下文连贯 |

## 1.36.5d 常见问答（FAQ）

| 问题 | 回答口径 |
| ------ | ---------- |
| "直接用向量库 CDC 行不行" | 多数向量库无成熟 CDC——以 MQ 为中枢是事实标准做法【论证】 |
| "嵌入成本失控怎么办" | 三件套：批量/哈希去重/日配额限流；仍失控则先查重复文档与刷新生成【论证】 |
| "查询侧要加缓存吗" | 热点查询加（秒级 TTL）；注意缓存与索引新鲜度的窗口叠加 |
| "RAG 管道要独立集群吗" | 与业务 topic 同集群起步，配额隔离；规模上来后按延迟敏感拆分【估算】 |

## 1.36.6 查询侧设计（管道之外的另一半）

写入管道再快，查询侧跟不上也白搭【论证】：

```text
Query → 查询理解（改写/路由） → 混合检索（向量+关键词）
      → 重排（rerank） → 上下文拼装 → LLM → 流式输出
                 ↖ 缓存层（查询结果/检索片段）↙
```

查询侧要点【论证】：① 检索片段缓存按"查询哈希+索引版本"失效——索引更新后旧缓存自动作废（新鲜度窗口的一部分）；② 流式输出走 SSE 直连（低延迟），长任务/多订阅者场景才转 MQ 中转（与 01-35 模式④衔接）；③ 检索质量观测（命中率/人工评分）回流，驱动分块策略调优（闭环）。

## 1.36.9 管道消息 Schema（AsyncAPI 表达，02-48 衔接）

```yaml
components:
  messages:
    ChunkReady:
      headers:
        required: [trace-id, doc-id, chunk-hash]   # 02-23/去重键
      payload:
        type: object
        required: [docId, chunkHash, text, collectedAt, version]
        properties:
          docId: { type: string }
          chunkHash: { type: string }        # 嵌入去重键
          text: { type: string }
          collectedAt: { type: string, format: date-time }
          version: { type: integer }          # 冲突解决用（LWW）
    DocDeleted:
      payload:
        type: object
        required: [docId, deletedAt]
        properties:
          docId: { type: string }             # 只传键不传 PII（02-50）
          deletedAt: { type: string, format: date-time }
```

## 1.36.10 端到端时序（变更→可检索）

```text
T0 文档落库 → T0+1s CDC 事件（ingest-topic）
→ T1 分块完成（chunk-topic，含 chunk-hash）
→ T2 攒批达 64 条或 2s 超时 → 嵌入调用（带配额检查）
→ T3 向量 upsert（幂等键=chunk-hash）
→ T4 可检索；新鲜度 = T4 - T0（SLO 预算各环节见 1.36.4）
```

预算分解示例【估算】：ingest 1s + chunk 2s + embed 8s + sink 1s = 12s；若 SLO 30s，剩余 18s 为队列等待余量——余量持续为负即扩容信号（02-49 伸缩）。

## 1.36.5 选型建议

| 规模 | 推荐组合 | 理由 |
| ------ | ---------- | ------ |
| 原型/中小 | Redis Stream/ RabbitMQ + 轻量 embedder | 少件够用 |
| 生产通用 | Kafka + Flink + 向量库（CDC→索引全流） | 生态最成熟，回放能力保一致性 |
| 合规敏感 | + 02-50 crypto-shredding（删除经 MQ 传播+密钥销毁） | 删除权贯穿索引层 |
| 多模态/高带宽 | Pulsar（分层存储承载原始文档大对象） | 存算分离降成本（01-29 衔接） |

与既有文档的边界：CDC/Connect/Flink 细节见 01-31；消息模式见 02 系列；本文只管"RAG 语义×MQ 选型"的交叉层【论证】。
