## 1.51.1 联邦数据面总览

在分布式消息系统中，“联邦”通常指**多个自治集群之间通过数据面协议实现可达性或复制**，而不要求应用层改写为单一全局命名空间。它与“多活架构”有清晰分工：

| 维度 | 集群联邦（数据面） | 多活架构（应用架构层） |
| ------ | -------------------- | ------------------------ |
| 关注点 | 跨集群 topic/subject 复制、可达、灾备 | 业务双写、冲突解决、路由层设计 |
| 一致性 | 异步复制，最终一致 | 依赖应用层分片/CRDT/仲裁 |
| 环回/冲突 | 由复制工具或协议语义规避 | 由应用层主区表、去重、幂等解决 |
| 典型代表 | MM2、Cluster Linking、NATS Supercluster、Pulsar geo-rep | 单元化单主、CRDT 状态多活 |

【论证】联邦技术是“多活”或“灾备”的**基础设施子集**：没有联邦数据面就无法把消息搬到另一区域，但仅有联邦数据面并不能自动实现业务双写。02-51 强调“开源 MQ 没有开箱即用的全域双写多活”，原因正在于此。

### 集群联邦 vs 多活架构的分工

- **联邦数据面负责**：把消息/流从 A 集群可靠地搬运到 B 集群，保持分区、offset 或 subject 语义尽可能一致。
- **多活架构层负责**：决定业务写哪一区、如何处理分区时的双写冲突、如何切换流量。联邦层只保证“数据在那儿”。

这种分层意味着：

1. 评估联邦方案时，先看它解决的是**灾备/只读副本**还是**双向同步**；
2. 双向同步若缺乏应用层冲突策略，必然引入环回或覆盖风险；
3. 跨区延迟（通常 50–300ms）使同步复制在地理多活中几乎不可行【估算】。

## 1.51.2 Kafka 系联邦方案对比

Kafka 生态把集群联邦视为“geo-replication”问题，主流方案有 Apache MirrorMaker 2、Confluent Cluster Linking、Confluent Replicator，以及历史/辅助工具。

### MirrorMaker 2

Apache Kafka 自 2.4 起内置 [MirrorMaker 2](https://kafka.apache.org/documentation/#georeplication)（MM2），基于 Kafka Connect 框架运行，是开源场景下的事实标准。Kafka 4.3.2 为当前活跃补丁线（2026-10-23 发布），MM2 随 Kafka 主线持续维护【论证】[Apache Kafka Downloads](https://kafka.apache.org/downloads)。

MM2 由三类内部 connector 组成：

- **MirrorSourceConnector**：从源集群消费并生产到目标集群；
- **MirrorCheckpointConnector**：定期同步消费者组 offset；
- **MirrorHeartbeatConnector**：发送心跳 topic 检测链路健康。

默认复制策略会在目标集群把 topic 重命名为 `{source}.{topic}`，例如 `us-west.orders` → `us-east.us-west.orders`【定理：由 `DefaultReplicationPolicy` 定义】[Kafka Geo-Replication](https://kafka.apache.org/documentation/#georeplication)。

```properties
# connect-mirror-maker.properties 示例（单向灾备）
clusters = primary, secondary
primary.bootstrap.servers = broker1-primary:9092
secondary.bootstrap.servers = broker1-secondary:9092

primary->secondary.enabled = true
primary->secondary.topics = orders.*
secondary->primary.enabled = false

tasks.max = 4
primary->secondary.emit.heartbeats = true
primary->secondary.sync.group.offsets = true
```

**Offset 映射语义**【论证】：MM2 通过 `OffsetSync` 记录把源集群的 `(topic, partition, offset)` 映射到目标集群的对应 offset。消费者 failover 时可在目标集群用近似位点继续消费，但无法保证精确无重复——MM2 提供至少一次语义；Kafka 3.5.0 起在专用 MM2 集群中支持 exactly-once，需配置 `exactly.once.source.support = enabled` 与 `dedicated.mode.enable.internal.rest = true`[Kafka Geo-Replication](https://kafka.apache.org/documentation/#georeplication)。

**双向复制注意事项**【论证】：

- 同一 MM2 配置文件内同时声明 `A->B` 与 `B->A` 时，MM2 通过心跳/配置共享自动避免环回；
- 若用两套独立 MM2 配置分别跑，必须确保 topic 命名空间隔离（如 `A.orders` 与 `B.orders`），否则会出现 A 的消息复制到 B 后再被复制回 A 的无限循环；
- 同 topic 双向写仍无全局冲突解决，02-51 将其列为红线。

### Confluent Cluster Linking

[Cluster Linking](https://docs.confluent.io/cloud/current/multi-cloud/cluster-linking/index.html) 是 Confluent Cloud/Confluent Platform 提供的托管集群联邦服务。与 MM2 不同，它运行在 broker 层而非独立的 Connect 集群，目标集群创建 **mirror topic**，源分区的消息会按相同分区、相同 offset 写入目标【论证】。

```bash
# Confluent Cloud CLI 示例：创建集群链接与镜像 topic
confluent kafka link create tokyo-sydney \
  --source-bootstrap-server pkc-xxx.ap-northeast-1.aws.confluent.cloud:9092 \
  --source-cluster lkc-source-id \
  --source-api-key AP1K3Y \
  --source-api-secret ********

confluent kafka mirror create clickstream.tokyo --link tokyo-sydney
```

Cluster Linking 的核心特性包括【论证】[Cluster Linking Overview](https://docs.confluent.io/cloud/current/multi-cloud/cluster-linking/index.html)：

- **topic 级链接**：可单独选择要镜像的 topic；
- **跨云/混合云**：支持 Confluent Cloud ↔ Confluent Cloud、Confluent Platform ↔ Confluent Cloud、外部 Kafka 3.0+ 作为源；
- **offset 与 ACL 同步**：可选同步消费者组 offset 与 ACL；
- **failover/promote**：mirror topic 可提升为可写 topic。

**限制**：不保证跨分区的 exactly-once 事务语义；mirror topic 为只读；Confluent Cloud 上每个目标集群默认最多接收 10 条 cluster link（可联系支持提升）。

### Confluent Replicator 与其他替代

**Confluent Replicator** 是 Confluent Platform 中的 Kafka Connect connector，功能与 MM2 重叠但面向 Confluent 生态：

- 支持 topic 配置自动同步、消费者 offset 转换（timestamp preservation）；
- 通过 provenance header 防止双向环回；
- 需要 Confluent Platform 企业版 Kafka Connect 许可。

【论证】当前 Confluent 文档将 Replicator 与 MM2 并列描述，并未宣布 Replicator 停止维护，但 Confluent Cloud 场景下官方更推荐使用 Cluster Linking；自管场景仍可用 Replicator[Confluent Replicator](https://docs.confluent.io/platform/current/multi-dc-deployments/replicator/index.html)。

**Uber uReplicator**：GitHub 仓库 `uber/uReplicator` 近年无活跃发布，Wiki 最后主要更新停留在 2021 年， Issues 回复停留在 2022 年，属于**维护极低/接近归档**状态【论证】[uReplicator Wiki](https://github.com/uber/uReplicator/wiki/uReplicator-User-Guide)。新项目不应采用。

**Redpanda 数据迁移工具**：Redpanda v26.2 当前最新（2026-07 GA，v26.2.6 发布于 2026-10-22）【论证】[Redpanda Releases](https://docs.redpanda.com/streaming/current/reference/releases/)。Redpanda 提供：

- 与 Kafka API 兼容，可直接使用 MM2 做迁移；
- **Shadowing**（企业版）：内置跨集群灾备复制，shadow topic 保持与源集群相同 offset，支持 topic 配置、消费者组 offset、ACL、Schema Registry 内容的影子复制[Redpanda Shadowing](https://www.redpanda.com/blog/25-3-enterprise-disaster-recovery)。

```bash
# Redpanda 创建 shadow link 示例
rpk shadow create my-dr-link --config-file shadow-link.yaml
rpk shadow status my-dr-link
```

### Kafka 系联邦方案能力对照表

| 能力 | Apache MM2 | Confluent Cluster Linking | Confluent Replicator | Redpanda Shadowing |
| ------ | :----------: | :-------------------------: | :--------------------: | :------------------: |
| 方向性 | 单向/双向（需正确配置） | 单向镜像，支持 promote/failover | 单向/双向 | 单向（shadow→只读） |
| Offset 语义 | 映射（OffsetSync），可近似 failover | 同分区同 offset 镜像 | Timestamp + offset 转换 | 与源集群 offset 一致 |
| Schema 同步 | 需额外 Schema Registry 双向同步 | 支持 Schema Registry 同步 | 支持 Schema 迁移 | v26.2 支持 SR shadow |
| 运维复杂度 | 中（自建 Connect 集群） | 低（托管/ broker 内建） | 中-高（需企业 Connect） | 低（broker 内建，企业版） |
| 许可 | Apache 2.0 | Confluent Cloud 按量/企业许可 | Confluent Platform 企业许可 | Redpanda Enterprise |
| 适用场景 | 开源跨云灾备、聚合 | 云原生多云/混合云 | 自管 Confluent 生态 | Redpanda 生态灾备 |

## 1.51.3 NATS 联邦

NATS 的联邦由 Core NATS 的 **Supercluster** 与 **Leafnode** 组合实现，JetStream 则提供持久化层的跨域复制。详见项目内 [01-26 NATS 2.x 与 JetStream 演进分析](01-26-NATS-2.x与JetStream演进分析.md)。

### Supercluster 与 Gateway

NATS Supercluster 通过 **Gateway** 把多个独立集群连接成一个逻辑系统。Gateway 与集群内 **Route** 的关键区别【论证】[NATS Superclusters](https://docs.nats.io/learn/topologies/super-clusters)：

- Route 假设节点邻近，会洪泛消息；
- Gateway 只转发远端有 subscriber 兴趣的消息，并优先本地队列组（geo-affinity）。

```hcl
# east 集群的 gateway 配置示例
gateway {
  name: "east"
  listen: "0.0.0.0:7222"
  gateways: [
    { name: "west", urls: ["nats://gw-west-1:7222", "nats://gw-west-2:7222"] }
  ]
}
```

Supercluster 适合“服务网格化多活”：请求就近服务，故障时跨区回落。它本身不持久化消息，跨区请求/响应天然受 geo-affinity 约束，因此不存在 Kafka 式的 topic 环回复制问题。

### Leafnode 边缘汇聚

**Leafnode** 是一种从边缘向中心“出站拨号”的 NATS server。工厂、车辆、门店等边缘节点无需公网入向端口，只要出站能连到 hub 的 7422 端口即可形成双向 subject 桥接【论证】[NATS Leaf Nodes](https://docs.nats.io/learn/topologies/leaf-nodes)。

```hcl
# factory-1.conf：边缘 leaf node
server_name: factory-1
listen: "127.0.0.1:4300"
leafnodes {
  remotes: [
    {
      urls: ["nats://hub-1:7422", "nats://hub-2:7422"]
      credentials: "/etc/nats/factory.creds"
      account: "FACTORY"
    }
  ]
}
```

生产部署要点：

- 用 `account` 与 `credentials` 做身份与命名空间隔离；
- 若 leaf 本地启用 JetStream，必须配置独立 **JetStream domain**，避免与 hub 的 JetStream 冲突；
- leaf 本地客户端对 hub 不可见，hub 只看到一条 leaf 连接。

### JetStream 跨域复制

当 Supercluster/leafnode 需要持久化灾备时，使用 JetStream 的 **Mirror** 与 **Source**：

- **Mirror**：目标 stream 是源 stream 的只读副本，常用于 DR；
- **Source**：目标 stream 从多个源 stream 聚合数据，适合边缘汇聚到中心。

NATS 2.15（2026-09-17 GA）增强了 source 重建索引、`sync: always` 性能与 Stream Backup v2，适合边缘弱网环境【论证】[NATS 2.15 Release](https://nats.io/blog/nats-server-2-15-release/)。

```bash
# 查看 JetStream 跨集群状态
nats server report jetstream --cluster
nats stream info ORDERS --json | jq '.cluster.leader, .cluster.replicas[].name'
```

## 1.51.4 Pulsar 跨地域复制

Apache Pulsar 的地理复制内建在架构中：

- **Geo Replication** 在 **tenant/namespace** 级配置，把一个 namespace 的消息异步复制到多个集群；
- 生产者可向任一集群写入，消息通过 broker 间的复制 cursor 传播到其他集群；
- 消费者可在本地集群订阅，读到就近副本。

```bash
# 注册对端集群并启用 namespace 级 geo-replication
pulsar-admin clusters create cluster-b --url http://pulsar-b:8080 --broker-url pulsar://pulsar-b:6650
pulsar-admin namespaces set-clusters my-tenant/my-ns --clusters cluster-a,cluster-b
pulsar-admin topics stats persistent://my-tenant/my-ns/orders | grep -A3 replication
```

Pulsar geo-replication 的边界【论证】[Pulsar Geo-Replication](https://pulsar.apache.org/docs/administration-geo/)：

- 适合“每消息单源生产、多区消费”或灾备；
- 不提供同 key 双写冲突解决；
- 跨区复制为异步，RPO 取决于网络与复制 backlog。

与 Kafka MM2 相比，Pulsar 把“联邦”内嵌到 namespace 元数据与 broker 协议中，不需要额外的 Connect 集群；但迁移到 Pulsar 联邦模型通常需要应用使用 Pulsar client。多活架构模式与故障演练细节见 [02-51 多活消息架构设计](../02-场景驱动架构设计/02-51-多活消息架构设计.md) 与 [03-64 跨地域消息运维实践指南](../03-架构与运维实践/03-64-跨地域消息运维实践指南.md)。

## 1.51.5 边缘消息栈

边缘场景的核心约束：资源有限、网络不稳定、安全域隔离。边缘消息栈通常由“轻量 broker + 规则引擎 + 存储转发模式”组成。

### 边缘规则引擎：LF Edge eKuiper

[eKuiper](https://ekuiper.org/) 是 LF Edge 孵化的轻量级流处理引擎，定位为在边缘侧对 MQTT/HTTP/文件等源做过滤、转换、聚合后再上行，减少带宽与云端压力。当前活跃稳定线为 **v2.4.x**，v2.5.0 处于 alpha 阶段（2026-11 时尚未 GA），生产环境建议使用 v2.4.x【论证】[eKuiper Releases](https://github.com/lf-edge/ekuiper/releases)。

```yaml
# eKuiper 规则示例：边缘过滤高温告警后上云
sql: SELECT device_id, temperature FROM mqtt_stream WHERE temperature > 60
actions:
  - mqtt:
      server: "tcp://cloud-broker:1883"
      topic: "alerts/high-temp"
      qos: 1
```

eKuiper 的关键边缘能力：

- 规则使用类 SQL 表达，支持窗口聚合、lookup、schema 等；
- 支持 sink 缓存（`enableCache`）与断网重发；
- 规则可热更新，适合 OTA 下发。

### 轻量边缘 broker 对比

| 维度 | Eclipse Mosquitto | NanoMQ | EMQX Edge |
| ------ | ------------------- | -------- | ----------- |
| 实现语言 | C | C | Erlang/Elixir |
| 典型内存占用 | 极低（数百 KB 级）【估算】 | 低（数 MB） | 中（数十 MB 起） |
| MQTT 版本 | 3.1/3.1.1/5.0 | 3.1.1/5.0 | 3.1.1/5.0 |
| 桥接能力 | 基础 bridge | 多协议桥接（MQTT/WebSocket/QUIC） | 与 EMQX Cloud/Enterprise 深度集成 |
| 规则引擎 | 无 | 无（通常与 eKuiper 配合） | 内置轻量规则 |
| 适用场景 | 资源极受限传感器网关 | 边缘计算/车载（SDV） | 中大型边缘节点 |

【估算】资源数字来自各官方文档与社区基准，实际占用与连接数、QoS 保持消息数强相关。

NanoMQ 近年的安全公告较多（如 CVE-2025-59946、CVE-2026-25627 等），生产部署需跟进到最新补丁版本【论证】[NanoMQ CVEs](https://app.opencve.io/cve/?vendor=nanomq)。

### 边缘-云同步协议模式

边缘 broker 与云端协同时，通常采用以下三种模式【论证】：

1. **存储转发（Store-and-Forward）**：边缘有本地持久化，网络恢复后按顺序上传；适合不可丢失的遥测或审计事件。
2. **断连缓存（Disconnect Buffering）**：在内存或本地文件缓存最近 N 条消息；网络抖动时保证连续性，但掉电可能丢失。
3. **上行去重（Upstream Deduplication）**：边缘在上传前按消息 ID 去重，云端按业务 key 幂等接收；避免断线重连导致的重复。

```text
┌─────────────┐    MQTT/QUIC    ┌──────────────┐
│  边缘设备    │ ───────────────> │  边缘 broker  │
└─────────────┘                  │ (NanoMQ/     │
                                 │  Mosquitto)  │
                                 └──────┬───────┘
                                        │ eKuiper 过滤/聚合
                                        ▼
                                 ┌──────────────┐
                                 │  本地持久化   │
                                 │ (SQLite/文件) │
                                 └──────┬───────┘
                                        │ 网络恢复后上传
                                        ▼
                                 ┌──────────────┐
                                 │   云端 Kafka  │
                                 │ /Pulsar/EMQX  │
                                 └──────────────┘
```

## 1.51.6 选型决策矩阵

| 业务场景 | 推荐联邦方案 | 关键理由 |
| ---------- | -------------- | ---------- |
| 跨云容灾（只读 failover） | Confluent Cluster Linking / Redpanda Shadowing / Pulsar geo-rep | 托管/ broker 内建，低运维，offset 一致 |
| 数据中心数据汇聚到总部 | Kafka MM2 / Pulsar geo-rep / NATS JetStream Source | 单向聚合成熟， topic/namespace 级可控 |
| 边缘 IoT 上行 | NATS Leafnode + JetStream Source / NanoMQ + eKuiper | 出站拨号穿透防火墙，边缘过滤减少上行带宽 |
| 合规数据驻留 | 分区联邦 + 本地 broker（如 Mosquitto 本地聚合，仅脱敏后跨境） | 原始 PII 不出区；eKuiper 在边缘脱敏后再同步 |
| 服务网格多活 | NATS Supercluster | geo-affinity 保持请求本地优先，跨区自动回落 |

选型提示【论证】：

- 需要“写入任一区、全局一致”的场景，没有现成联邦方案能直接满足，必须引入应用层单元化或 CRDT（见 02-51）；
- 跨区复制带宽通常按 `生产速率 × 复制目标区数 × 冗余系数` 估算，建议把复制滞后 >60s 作为告警起点【估算】；
- 合规场景先审“哪些 topic 能出区”，再决定联邦拓扑，而不是先建拓扑再补审批。
