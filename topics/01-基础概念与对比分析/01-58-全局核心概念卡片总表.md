## 1.58.0 卡片结构与用法

### 六元组字段说明

| 字段 | 含义 | 阅读提示 |
| ------ | ------ | ---------- |
| **概念** | 中文术语（必要时附英文） | 同义词在 1.23 术语词汇表中统一 |
| **定义** | 基于官方规范或项目内权威论证的精确定义 | 标注【定理】/【论证】/【估算】 |
| **关键属性** | 该概念区别于其他概念的核心特征 | 用于快速核对选型假设 |
| **关系** | 上位/下位/关联概念 | 与 1.11 概念关系网络图互参 |
| **示例** | 典型系统或命令示例 | 优先使用真实配置/命令 |
| **反例** | 常见误用或不适用场景 | 本表特色，防止概念混淆 |

### 示例：从 AsyncAPI 契约定位概念

```yaml
asyncapi: '3.0.0'
info:
  title: Order Events API
  version: '1.0.0'
channels:
  orderCreated:
    address: orders.created
    messages:
      orderCreatedMessage:
        $ref: '#/components/messages/OrderCreated'
operations:
  sendOrderCreated:
    action: send
    channel:
      $ref: '#/channels/orderCreated'
components:
  messages:
    OrderCreated:
      payload:
        schemaFormat: application/vnd.apache.avro+json;version=1.9.1
        schema: {}
```

上例同时涉及：Channel、Operation、Message、Schema、Binding（可附加 `bindings.kafka`）等契约 DSL 概念。

### 示例：命令行核对 Kafka 关键概念

```bash
# 查看 ISR、Leader、Replicas 等副本状态
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# 查看消费者组分区分配与消费延迟
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group payment-workers --describe
```

## 1.58.1 跨系统基础概念

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Topic** | 消息逻辑分类标识，发布者按主题投递、订阅者按主题过滤【定理】 | 唯一命名、可分区/分片、可被多消费者订阅 | 上位：消息模型；下位：Partition/Subject/Channel；关联：Exchange | Kafka `orders` Topic | 把 Topic 当成队列名导致多个消费者各收一份 |
| **Queue** | 点对点模型中的消息容器，每条消息通常只被一个消费者处理【定理】 | FIFO、负载均衡、可持久化 | 上位：消息模型；下位：Classic Queue/Quorum Queue；关联：Consumer Group | RabbitMQ `task_queue` | 在 Pub/Sub 系统中声明 Queue 期望广播 |
| **Partition** | Topic 的物理分片，分区是顺序性与并行性的基本单元 | 顺序写入、独立 offset、可横向扩展 | 上位：Topic；关联：Consumer Group、Broker、Offset | Kafka 单 Topic 12 分区 | 把跨分区顺序当成分区内顺序 |
| **Consumer Group** | 一组协同消费者，共同消费 Topic/Stream 并实现负载均衡 | 组内互斥分配分区、自动重平衡、位点共享 | 上位：Consumer；下位：Share Group/Subscription；关联：Partition | Kafka 消费者组 `payment-workers` | 同一服务实例用不同 group.id 导致重复消费 |
| **Offset** | 消息在分区/流内的单调递增位置标识【定理：Kafka/NATS 协议语义】 | 唯一性、单调性、可提交回滚 | 上位：Message；关联：Partition、Consumer Lag、Commit | Kafka offset `15234` | 跨分区比较 offset 判断全局先后 |
| **Producer** | 向消息系统发送消息的客户端 | 幂等开关、批量发送、压缩、ACK 策略 | 关联：Topic/Queue、Transaction、ACK | Kafka Producer 发送订单事件 | 把 Producer 当 RPC 客户端同步阻塞调用 |
| **Consumer** | 从消息系统接收并处理消息的客户端 | 拉/推模式、ACK 策略、重试/死信 | 关联：Consumer Group、Offset、Poison Message | JetStream Consumer | 消费者处理完不 ACK 导致无限重投 |
| **Broker** | 消息中间件服务端节点，负责接收、路由、存储消息 | 可集群、监听端口、管理元数据 | 上位：Cluster；下位：Kafka Broker/Pulsar Broker；关联：Topic | RabbitMQ broker node | 把 Broker 当成数据库主节点直接 joins |
| **at-most-once** | 消息最多被投递一次，可能丢失但不重复【定理】 | 低开销、无重试、无 ACK | 上位：Delivery Semantics；关联：QoS 0、acks=0 | 日志采样指标上报 | 用于支付状态通知 |
| **at-least-once** | 消息至少被投递一次，可能重复但不丢失【定理】 | 需 ACK、需幂等消费、可能重复 | 上位：Delivery Semantics；关联：QoS 1、acks=1 | 订单创建事件投递 | 认为 at-least-once 等同精确一次 |
| **exactly-once** | 消息在系统语义内恰好被处理一次【论证：需端到端幂等+事务】 | 强一致性、高延迟、需状态协调 | 上位：Delivery Semantics；关联：Idempotency、Transaction | Kafka EOS 事务写 | 消费端崩溃在 ack 前仍可能重复处理；跨会话 Producer 不保证去重 |
| **QoS 0** | MQTT 最多一次投递，无确认 | 最低延迟、不可靠、无状态 | 上位：QoS；关联：at-most-once | 传感器心跳 | 用于控制指令 |
| **QoS 1** | MQTT 至少一次投递，PUBACK 确认 | 可能重复、需幂等消费 | 上位：QoS；关联：at-least-once | 设备状态上报 | 认为 QoS 1 不会重复 |
| **QoS 2** | MQTT 恰好一次协议语义，四次握手【定理：OASIS 规范】 | 最高可靠、最高延迟、会话状态 | 上位：QoS；关联：exactly-once | 关键控制指令 | QoS 2 不保证应用层恰好一次 |
| **Dead Letter** | 超过重试上限仍无法处理的消息被转储到专门队列/主题 | 隔离故障、可审计、可重放 | 上位：Message；关联：DLQ、Poison Message、Retry | RabbitMQ DLX 路由到死信队列 | 死信即永久丢弃不处理 |
| **Idempotency** | 同一操作执行多次结果与一次相同【定理：数学定义】 | 去重键、幂等键、状态机幂等 | 关联：exactly-once、Producer、Consumer | 按订单号去重的退款处理 | 用时间戳当唯一键导致重复处理 |
| **Transaction** | 一组消息操作的原子提交或回滚 | ACID 语义、协调器、两阶段提交 | 关联：exactly-once、Offset Commit、Outbox | Kafka 事务同时写多个分区 | 把本地 DB 事务与 MQ 事务混为一谈 |
| **Backpressure** | 消费端向生产端反馈流控信号，防止过载 | 阻塞/丢弃/降级、buffer 上限、反压传播 | 关联：Reactive Streams、Latency、Buffer | TCP 滑动窗口、RSocket | 无限扩大队列容量替代反压 |
| **Ordering** | 消息按发送顺序被投递和处理的保证 | 分区/队列有序 vs 全局有序 | 关联：Partition、Key、Sequence Number | Kafka 同 Key 同分区保序 | 多分区全局保序仅靠设置分区数 1 |
| **Persistence** | 消息写入非易失性存储，重启后可恢复 | 磁盘 WAL、副本同步、刷盘策略 | 关联：Replication、Durability、Retention | Kafka 落盘后 ack | 认为内存 MQ 也能持久化 |
| **Retention** | 消息在系统中的保留策略（时间/大小/消息数） | 可配置、过期删除/压缩、合规相关 | 关联：Persistence、Compaction、Tiered Storage | Kafka `retention.ms=7d` | 把 retention 当成消费者位点 |
| **Compaction** | 按 Key 保留最新值，删除旧记录以节省空间 | Key 级别、只保留最新、影响读语义 | 关联：Retention、Topic、Log | Kafka compacted topic | 在需要完整审计日志的 Topic 开启 compaction |
| **Schema** | 消息 payload 的结构化契约定义 | Avro/Protobuf/JSON Schema、演进规则 | 关联：AsyncAPI、CloudEvents、Compatibility | Confluent Schema Registry | 把 Schema 当文档不强制校验 |
| **Binding** | 消息路由规则中 Channel 与具体协议/传输的绑定 | 协议映射、安全参数、端点配置 | 关联：AsyncAPI、Channel、Operation | AsyncAPI `kafka` binding | Binding 替代 Schema 约束业务字段 |
| **Exchange** | RabbitMQ 中接收消息并按规则路由到 Queue 的路由器 | direct/topic/fanout/headers 类型 | 上位：Broker；关联：Binding、Queue | `amq.topic` exchange | 直接发布到 Queue 绕过 Exchange |
| **Stream** | 持久化的追加式消息序列，可重放、可分片 | 不可变、有序、时间/偏移索引 | 关联：Log、Partition、JetStream | Pulsar Topic 即 Stream | 把 Stream 当临时缓冲区用完即弃 |
| **Share Group** | Kafka KIP-932 引入的共享消费组，允许多消费者并发读同一分区 | cooperative 分配、软顺序、更高并发 | 关联：Consumer Group、Partition | Kafka 共享组 `share-group-A` | 共享组内保证分区级强顺序 |
| **Tiered Storage** | 热数据本地盘、冷数据卸载对象存储的分层架构 | 无状态 broker、降成本、延长保留 | 关联：Retention、S3-offload、Compaction | Kafka Tiered Storage | 分层存储无读取延迟惩罚 |
| **DLQ** | Dead Letter Queue/Topic，集中存放处理失败消息 | 故障隔离、审计、重放入口 | 同 Dead Letter；关联：Retry、Poison Message | SQS DLQ、RabbitMQ DLX | DLQ 中的消息无需人工干预 |
| **Poison Message** | 因内容/状态错误导致反复处理失败的消息 | 不可重试成功、需分析后丢弃/修复 | 关联：Dead Letter、Retry、Idempotency | 含非法 JSON 的事件 | 所有进 DLQ 的消息都是 Poison |
| **Backlog** | 已发布但尚未被消费者处理的消息累积量 | Lag 的统称、影响延迟/SLO、可监控 | 关联：Consumer Lag、Throughput、Scale | Pulsar subscription backlog | Backlog 越大吞吐量越高 |

## 1.58.2 Kafka 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **KRaft** | Kafka 基于 Raft 的内置元数据管理，替代 ZooKeeper【定理：KRaft 协议】 | 3 控制器、元数据快照、无外部 ZK | 上位：Metadata Management；关联：Controller、Quorum | Kafka 3.7+ KRaft 模式 | KRaft 与 ZooKeeper 双注册中心长期共存 |
| **Controller** | Kafka 集群中负责分区状态机与副本管理的特殊 Broker | 单一活跃、故障切换、元数据仲裁 | 上位：Broker；关联：KRaft、Leader Election | `node.id=1` 为 Controller | Controller 处理所有客户端读写请求 |
| **KIP-932** | Kafka 共享消费组协议提案，引入 Share Group 语义 | 2024 进入主干、cooperative 消费、软顺序 | 关联：Consumer Group、Share Group | `group.protocol=consumer` + share group | KIP-932 让 Kafka 变成队列语义 |
| **Producer Idempotence** | Kafka Producer 通过 PID+Sequence Number 去重【定理】 | `enable.idempotence=true`、单会话内 EOS | 关联：exactly-once、Transaction、PID | 幂等 Producer 重试不重复 | 幂等 Producer 跨会话仍可能重复 |
| **ISR** | In-Sync Replicas，与 Leader 保持同步的副本集合【定理：Kafka 协议语义】 | 动态收缩、acks=all 依赖、最小同步副本 | 关联：Leader、Follower、Replication、acks | ISR = {Leader, F1, F2} | ISR 包含所有历史副本无论是否滞后 |
| **High Watermark** | 已提交到 ISR 的最大 offset，消费者只能读到 HW 之前 | 一致性边界、Leader/Follower 同步 | 关联：ISR、Offset、Commit、LEO | Follower 同步至 HW 才对外可见 | HW 之后消息可被消费者读取 |
| **Log Segment** | Kafka 分区日志的物理分段文件（.log + .index + .timeindex） | 滚动策略、压缩、删除/保留单元 | 上位：Partition Log；关联：Retention、Compaction | `00000000000000000000.log` | 一个 Segment 包含多个分区 |
| **Rebalance Protocol** | 消费者组成员变化时重新分配分区的协议 | JoinGroup/SyncGroup、Sticky/Cooperative | 关联：Consumer Group、Partition、Coordinator | CooperativeStickyAssignor | Rebalance 期间仍可继续消费 |
| **Leader** | 分区的读写主副本 | 唯一、选举产生、负责客户端请求 | 关联：Follower、ISR、Controller | Partition 0 Leader on Broker 1 | 所有副本都可同时写入 |
| **Follower** | 从 Leader 拉取数据并同步的副本 | 只读、落后则被踢出 ISR、可晋升 Leader | 关联：Leader、ISR、Replication | Broker 2 上的 Follower | Follower 直接响应读请求 |
| **Consumer Group Coordinator** | 负责消费者组位点与成员管理的事务协调器 | 每个组一个、管理 __consumer_offsets | 关联：Consumer Group、Rebalance、Offset | GroupCoordinator 处理心跳 | Coordinator 存储业务消息内容 |
| **Record Batch** | Kafka 生产端批量发送的消息集合，压缩与高效网络单元 | `batch.size`、linger.ms、压缩类型 | 关联：Producer、Throughput、Compression | 一批 16KB 压缩后发送 | 每条消息单独 TCP 发送更高效 |

## 1.58.3 Pulsar 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Broker** | Pulsar 无状态计算层节点，处理协议与路由 | 不持久化消息、可水平扩展、依赖 BookKeeper | 关联：Bookie、Topic、Namespace | Pulsar broker `pulsar-broker-1` | Broker 直接存储消息日志 |
| **Bookie** | Apache BookKeeper 存储节点，以 Ledger 模型持久化消息 | Quorum 写入（E/WQ/AQ）、低延迟、独立扩展 | 上位：Storage；关联：Broker、Ledger、Oxia | BookKeeper ensemble E=3 WQ=2 AQ=2 | Bookie 负责消息路由 |
| **Oxia** | Pulsar 新一代元数据存储，替代 ZooKeeper | 分层架构、更高吞吐元数据、Raft 日志 | 关联：Metadata、Controller、KRaft | Oxia 管理 topic 元数据 | Oxia 替代 BookKeeper 存储消息 |
| **Tenant** | Pulsar 多租户一级隔离单元 | 认证/授权/配额、跨 namespace 共享 | 上位：Multi-tenancy；下位：Namespace | `public/retail` tenant | Tenant 等同于 Kafka Topic |
| **Namespace** | Pulsar 租户下的二级隔离与策略单元 | 策略集合、bundle、租户内组织 | 上位：Tenant；关联：Topic、Bundle | `public/default` | Namespace 是物理存储分区 |
| **Subscription Type** | 消费者订阅模式：Exclusive/Shared/Failover/Key_Shared | 并发度与顺序权衡 | 关联：Consumer Group、Ordering | Key_Shared 按 Key 保序 | Shared 订阅保证单 Key 顺序 |
| **Geo-Replication** | 跨地域数据中心异步复制 Topic 数据 | 单向/双向、命名空间级、延迟容忍 | 关联：Replication、Disaster Recovery | 北京→上海跨城复制 | Geo-Replication 是同步强一致 |
| **Ledger** | BookKeeper 中追加写的最小存储单元 | 不可变、由 Entry 组成、关闭后复制 | 关联：Bookie、Entry、Stream | Ledger ID `12345` | Ledger 可被随机更新 |

## 1.58.4 RabbitMQ 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Exchange Types** | Exchange 路由算法类型：direct/topic/fanout/headers | 声明时指定、决定绑定匹配规则 | 上位：Exchange；关联：Binding、Queue | `topic` 按路由键模式匹配 | 所有类型都按消息内容路由 |
| **Quorum Queue** | RabbitMQ 4.x 默认的 Raft 复制队列 | 领导者选举、持久化、高可用 | 上位：Queue；关联：Classic Queue、Raft | 声明 `x-queue-type: quorum` | Quorum Queue 支持 TTL 与优先级队列所有特性 |
| **Classic Queue** | RabbitMQ 传统队列类型 | 本地镜像/非镜像、部分特性已弃用 | 上位：Queue；关联：Quorum Queue | 旧版 mirrored classic queue | Classic Queue 是 4.x 默认 |
| **Federation** | 跨 RabbitMQ 集群/节点按需拉取消息复制 | 单向、基于 AMQP、Topic/Queue 级 | 关联：Shovel、Geo-Replication | 上游 `brokerA` → 下游 `brokerB` | Federation 是同步复制 |
| **vhost** | Virtual Host，RabbitMQ 逻辑隔离单元 | 独立 Exchange/Queue/权限、同集群多环境 | 关联：Tenant、Namespace | `/production` vhost | vhost 跨集群自动同步 |
| **Confirm** | Publisher Confirm 机制，Broker 异步 ack 消息入队 | 轻量、Channel 级、解决发送丢失 | 关联：ACK、Transaction、Publisher | `channel.confirmSelect()` | Confirm 保证消息已被消费 |
| **Binding** | Exchange 到 Queue 的路由绑定关系 | routing key、arguments、可动态增删 | 关联：Exchange、Queue、Exchange Types | `order.*` binding | Binding 决定消息格式 |
| **Dead Letter Exchange** | 接收被拒绝/过期/超限消息的特殊 Exchange | `x-dead-letter-exchange`、可路由到 DLQ | 关联：Dead Letter、Queue、Retry | DLX 将失败消息转给 `errors` | DLX 自动重试直到成功 |

## 1.58.5 NATS 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **JetStream** | NATS 持久化消息层，提供流存储与 exactly-once 语义 | Stream/Consumer/KV/Object Store、Raft 复制 | 上位：NATS；关联：Stream、Consumer | `nats stream add` | JetStream 替代 Core NATS 发布订阅 |
| **Stream** | JetStream 中按 subject 集合持久化存储的消息序列 | retention policy、replicas、max msgs/bytes | 关联：Subject、Consumer、Message Set | Stream `ORDERS` 存 `orders.>` | Stream 是瞬时内存队列 |
| **Consumer** | JetStream 中从 Stream 读取消息的视图 | durable/ephemeral、pull/push、ack policy | 关联：Stream、DeliverPolicy、AckPolicy | Durable consumer `PAYMENT` | Consumer 删除 Stream 数据 |
| **Leafnode** | NATS 边缘 leaf 节点，与上游 hub 建立单向/双向联邦 | 轻量边缘、本地路由、可隔离故障 | 关联：Supercluster、Gateway、Edge | 工厂 leafnode 连总部 hub | Leafnode 替代 JetStream 本地持久化 |
| **Supercluster** | 多个 NATS 集群通过 Gateway 互联形成更大联邦 | 全互联 Gateway、消息可跨集群路由 | 关联：Cluster、Gateway、Leafnode | 三地域 NATS Supercluster | Supercluster 内所有消息全局有序 |
| **KV** | JetStream Key-Value 存储抽象 | 基于 Stream、watch/put/get/delete、最终一致 | 关联：Object Store、Stream、Watch | KV bucket `config` | KV 提供强一致分布式锁 |
| **Object Store** | JetStream 对象存储抽象，用于大文件/二进制 | 分块、metadata、基于 Stream | 关联：KV、Stream、Object | Object store `backups` | Object Store 替代 S3 做热缓存 |

## 1.58.6 MQTT 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Session** | MQTT 客户端与 Broker 之间的持久化状态关联 | Clean Start/Session Expiry、未ACK消息、订阅 | 关联：ClientID、QoS、Will | 持久 Session 离线保留订阅 | Session 状态对所有客户端可见 |
| **Will** | 客户端异常断开时由 Broker 代发的遗嘱消息 | Will Topic/Will QoS/Will Retain、CONNECT 设置 | 关联：Session、Disconnect、Retain | 设备离线时发布 `device/lwt` | Will 在客户端正常断开时发送 |
| **Retain** | 主题上保留的最后一条消息，新订阅者立即收到 | 每条主题最多一条、可清除、非历史日志 | 关联：Session、Topic、Last Known Good | 保留 `room/temp=24` | Retain 保留所有历史消息 |
| **Shared Subscription** | MQTT 5.0 共享订阅，组内多个订阅者负载均衡 | `$share/group/topic`、每条消息组内一条 | 关联：Consumer Group、Queue Group | `$share/g1/sensors/+/temp` | Shared Subscription 保证消息顺序 |
| **Enhanced Auth** | MQTT 5.0 增强认证，支持 Challenge-Response | AUTH 报文、可扩展 SASL、Re-Auth | 关联：User Properties、TLS、ACL | SCRAM 认证流程 | Enhanced Auth 替代 TLS 传输加密 |
| **User Properties** | MQTT 5.0 用户自定义键值对报文属性 | UTF-8 字符串对、可跨报文携带、追踪/路由 | 关联：Headers、CorrelationData、Trace | `trace-id=abc123` | User Properties 用于发送二进制 payload |
| **Topic Alias** | MQTT 5.0 用短整数映射长主题名以减少报文大小 | 0-65535、双向协商、会话级 | 关联：Topic、Session、Bandwidth | Alias 1 → `a/b/c/d/e` | Topic Alias 跨会话持久 |

## 1.58.7 Redis Stream 域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Stream** | Redis 追加式日志结构，消息按 ID 顺序存储 | `XADD` 写入、条目为 field-value、可范围查询 | 关联：Consumer Group、XACK、Entry | `XADD mystream * temp 24` | Redis Stream 是 Redis List |
| **Consumer Group** | Redis Stream 消费组，组内成员分摊消息 | `XGROUP/XREADGROUP`、pending list、last delivered ID | 关联：Stream、Consumer、Pending Entries | `XGROUP CREATE mystream g1 $` | 同组消费者各自收到完整副本 |
| **XACK** | 消费者确认已处理 Stream 消息的命令 | 从 pending list 移除、支持 `XPENDING` 监控 | 关联：Pending Entries、Consumer Group | `XACK mystream g1 1526569495631-0` | XACK 后消息从 Stream 删除 |
| **Pending Entries** | 已投递但未 ACK 的消息集合（PEL） | 按消费者统计、可 CLAIM、可查看 idle 时间 | 关联：XACK、Consumer Group、Delivery Count | `XPENDING mystream g1` | Pending 列表无限期保留不超时 |
| **Stream ID** | 消息在 Stream 中的唯一时间序列 ID | `milliseconds-sequence`、可自动生成、可范围查询 | 关联：Offset、Stream、Entry | `1526569495631-0` | Stream ID 可跨 Stream 比较全局顺序 |

| **correlationId** | 用于关联请求与响应/因果链的标识 | 支持表达式、异步追踪、放在 header 或 payload | 关联：traceparent、Message、Operation | `correlationId: $message.header#/correlation-id` | correlationId 用于消息分区 |

## 1.58.9 模式域

| 概念 | 定义 | 关键属性 | 关系（上位/下位/关联） | 示例 | 反例 |
| ------ | ------ | ---------- | ------------------------ | ------ | ------ |
| **Command Message** | EIP 消息构造族：封装调用/指令的消息 | 意图明确、通常需 ACK、可触发动作 | 上位：EIP；关联：Event Message、Message | `CreateOrder` command | Command Message 可被任意订阅者消费 |
| **Publish-Subscribe Channel** | EIP 消息通道族：一条消息广播给多个接收者 | 1:N、解耦、无状态广播 | 上位：EIP；关联：Topic、Queue | Kafka Topic 作为 pub-sub channel | Pub-Sub Channel 保证所有订阅者只收一条 |
| **Content-Based Router** | EIP 路由族：按消息内容选择目标通道 | 路由规则、可动态、增加耦合 | 关联：Exchange、Binding、Message Filter | 按 `order.region` 路由 | 路由器修改消息内容 |
| **Message Translator** | EIP 转换族：转换消息格式/协议 | 解耦异构系统、可组合 | 关联：Schema、Transformation、Adapter | XML→JSON 转换 | Translator 改变业务语义 |
| **Competing Consumers** | EIP 端点族：多个消费者竞争同队列消息 | 负载均衡、单条单消费、提高吞吐 | 关联：Consumer Group、Queue | RabbitMQ 工作队列 | Competing Consumers 保证消息顺序 |
| **Wire Tap** | EIP 管理族：在通道上旁路复制消息用于监控 | 不影响主流程、只读监听 | 关联：Observability、Channel、Audit | 复制所有订单事件到审计 | Wire Tap 消费主消息并 ACK |
| **Outbox** | 事务内写业务表+Outbox 表，由 relay 异步投递 MQ | 保证本地事务与事件原子、 eventual delivery | 关联：Transaction、Saga、CDC | `outbox` 表 + Debezium relay | Outbox 让消息同步到达 |
| **Saga** | 长事务拆分为本地事务+补偿，通过事件协调 | 编排/协同、补偿、最终一致 | 关联：Transaction、Event Sourcing、Outbox | 订单 Saga：扣库存→创建订单→支付 | Saga 提供 ACID 强一致 |
| **CQRS** | 命令查询职责分离，读写模型独立 | 读写分离、投影、 eventual read model | 关联：Event Sourcing、Projection、Read Model | 命令写事件流，查询读物化视图 | CQRS 必须配合 Event Sourcing |
| **Event Sourcing** | 以事件流为真相源持久化状态变更 | 不可变事件、重放、投影、Upcaster | 关联：CQRS、Stream、Audit | 账户余额 = 所有存取事件投影 | Event Sourcing 适合所有 CRUD |

## 1.58.10 运维与集成域

| **SemConv** | OpenTelemetry 语义约定，标准化属性命名 | `messaging.system`/`destination.name`、稳定性级别 | 关联：OTel Span、Attribute、Observability | `messaging.kafka.destination.name` | SemConv 定义采样率 |
| **Zero Trust** | 永不信任、持续验证的安全架构 | 身份验证、最小权限、微分段、mTLS | 关联：SPIFFE、mTLS、Identity | 工作负载间强制 mTLS | Zero Trust 只需边界防火墙 |
| **SPIFFE** | 安全身份框架，为工作负载发放可验证身份 | SVID、SPIRE、x.509/JWT、平台无关 | 关联：Zero Trust、SVID、mTLS | SPIFFE ID `spiffe://acme/billing` | SPIFFE 替代网络隔离 |

| **Cluster Linking** | Confluent Kafka 集群间 topic 级联邦复制 | 双向可选、元数据同步、灾难恢复 | 关联：MirrorMaker 2、Federation、DR | Confluent Cluster Link | Cluster Linking 是 Apache Kafka 内置功能 |
| **Leader Election** | 分布式系统中选出唯一协调者/主节点的过程 | Raft/Paxos/ZAB、脑裂防护、任期/epoch | 关联：KRaft、Controller、Consensus | Kafka Controller 选举 | 简单超时选举即可保证唯一 Leader |
| **Prometheus** | 指标收集与告警系统，广泛用于 MQ 监控 | pull 模型、exporter、PromQL、告警规则 | 关联：Grafana、Metric、SLO | `kafka_consumer_lag` metric | Prometheus 主动推送指标到应用 |
| **Health Check** | 探针机制判断服务是否存活/就绪 | liveness/readiness/startup、HTTP/TCP | 关联：Kubernetes、SLI/SLO、Probe | `GET /health/ready` | Health Check 返回 200 即代表业务无延迟 |
