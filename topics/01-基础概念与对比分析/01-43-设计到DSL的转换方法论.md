## 1.43.1 总论：转换方法论框架

【论证】事件驱动架构的契约治理常见痛点是"设计语言不统一"：业务团队用 Event Storming 贴便签，集成团队讲 EIP 模式，开发团队已有 Swagger/OpenAPI，运维团队面对 BPMN 流程图，而契约最终要写成 AsyncAPI。转换方法论的目标是把这些异构设计源**显式、可重复地映射为 AsyncAPI 3.x DSL**，并建立校验回环。

### 四步转换环

```text
源设计形态识别 → 语义提取 → DSL 构件映射 → 校验回环
     ↑                                              │
     └──────────── 治理更新（正向变更）──────────────┘
```

1. **源设计形态识别**：判断输入是事件风暴墙、EIP 方案、OpenAPI 文档、代码注解还是 BPMN XML。
2. **语义提取**：抽取出领域事件、命令、聚合、通道、路由规则、错误场景等中间语义，而非直接复制字段。
3. **DSL 构件映射**：把中间语义映射到 AsyncAPI 的 `info/servers/channels/operations/messages/components/bindings` 及扩展字段 `x-`。
4. **校验回环**：用 `asyncapi validate`、Spectral lint、AsyncAPI Diff 与运行时契约测试验证转换结果。

### 转换质量检查表

| 检查项 | 通过标准 | 工具/命令 |
| ------ | -------- | ---------- |
| 文档合法性 | 通过官方 schema 校验 | `asyncapi validate asyncapi.yaml` |
| 治理规则合规 | 无 warn/error | `spectral lint asyncapi.yaml --ruleset .spectral.yaml` |
| 破坏性变更识别 | diff 报告无未评审的 breaking change | `asyncapi diff old.yaml new.yaml` |
| 示例可运行 | message examples 能通过 payload schema 校验 | `asyncapi validate` 含 examples 阶段 |
| 绑定版本完整 | 每个 protocol binding 声明 `bindingVersion` | Spectral 自定义规则 |
| 所有权可追溯 | 每个 channel/message 关联 `x-owner` 或事件目录 owner | 事件目录/Backstage 核对 |

## 1.43.2 Event Storming 产出 → AsyncAPI DSL

### 色标到 DSL 构件映射

【论证】Event Storming 的色标是领域语义的显式表达，可直接对应 AsyncAPI 构件。映射时优先保留领域语义，再决定 channel/operation 的技术命名。

| Event Storming 元素 | 颜色 | AsyncAPI DSL 映射 | 备注 |
| ------------------- | ---- | ----------------- | ---- |
| 聚合（Aggregate） | 粉色/紫色 | `info.title` 或 `x-domain`；决定 channel 的域前缀 | 一个 bounded context 对应一份 AsyncAPI 文档 |
| 领域事件（Domain Event） | 橙色 | `messages` + `operations`（action=send） | 命名用动词过去式，如 `OrderCreated` |
| 命令（Command） | 蓝色/黄色 | `operations`（action=send）+ message name 如 `PlaceOrder` | 命令与事件在 DSL 中都是 message，语义由命名与操作方向区分 |
| 策略/规则（Policy） | 绿色 | `x-policy` 扩展、consumer 重试策略或 bindings | 描述触发条件、补偿路径 |
| 外部系统（External System） | 紫色 | `externalDocs`、server 引用或 `x-system-type: external` | 明确集成方式（bridge/connector/API） |
| 热点/问题（Hotspot） | 红色 | `x-risk`、ADR 关联或错误事件契约 | 标记顺序、幂等、合规约束 |

### Mini 案例：订单域风暴墙 → AsyncAPI

**Before（风暴墙描述）**：

```text
[外部] 用户下单 → [命令] PlaceOrder → [聚合] Order → [事件] OrderCreated
[策略] 库存不足则触发 OrderCreationFailed
[外部] 支付网关 ← [命令] ChargePayment
```

**After（AsyncAPI 3.x YAML 片段）**：

```yaml
asyncapi: '3.0.0'
info:
  title: Order Service Events
  version: 1.0.0
  x-domain: order
  x-owner: order-team

servers:
  kafkaProd:
    host: kafka.example.com:9092
    protocol: kafka-secure

channels:
  orderCreated:
    address: orders.order.created.v1
    x-policy: inventory-check-required
    messages:
      orderCreatedMessage:
        $ref: '#/components/messages/OrderCreated'

operations:
  sendOrderCreated:
    action: send
    operationId: sendOrderCreated
    channel:
      $ref: '#/channels/orderCreated'
  # 命令侧对称结构省略：receivePlaceOrder 同为 operation + $ref 模式

components:
  messages:
    OrderCreated:
      name: OrderCreated
      contentType: application/json
      payload:
        $ref: '#/components/schemas/OrderCreatedEvent'
    # PlaceOrder 命令 message 同构省略
  schemas:
    OrderCreatedEvent:
      type: object
      required: [orderId, occurredAt]
      properties:
        orderId: { type: string }
        occurredAt: { type: string, format: date-time }
    # PlaceOrderCommand schema（orderId/amount/currency）从略，见 2.54 模板
```

> 完整命名规范与版本化模板参见 [2.54 事件契约模板库与命名规范](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md)。

## 1.43.3 EIP 模式 → AsyncAPI DSL 映射

【论证】EIP 65 模式族描述的是消息集成语义，AsyncAPI 描述的是事件契约语法。二者不是一一对应：有些模式可直接用 AsyncAPI 原生表达，有些需要 `x-` 扩展，有些则超出 AsyncAPI 范围、必须下沉到 broker/框架/代码实现。

### 三态映射表

| EIP 模式 | 三态 | AsyncAPI 表达方式 | 说明 |
| -------- | ---- | ----------------- | ---- |
| Message / Event Message | 【直接表达】 | `messages` 定义 + `contentType` | 核心语义 |
| Command Message | 【直接表达】 | `messages` + operation `send` | 与事件 message 共用结构，命名区分 |
| Correlation Identifier | 【直接表达】 | `correlationId` 字段或 header schema | 在 message.headers 中显式声明 |
| Splitter | 【直接表达】 | payload `oneOf` 或多消息引用 | 一条输入对应多条子消息类型 |
| Message Filter | 【直接表达】 | `oneOf` + 条件 schema，或 header 过滤 | AsyncAPI 不表达运行时丢弃逻辑，只描述过滤维度 |
| Content-Based Router | 【需 x- 扩展】 | `x-routing-predicate` 扩展 | 路由谓词需在 operation/channel 层用扩展表达 |
| Recipient List | 【需 x- 扩展】 | `x-recipient-list` + 动态目标 schema | 动态目标不在核心规范内 |
| Routing Slip | 【需 x- 扩展】 | `x-routing-slip` 描述路径清单 | 流程元数据用扩展承载 |
| Aggregator | 【需下沉实现】 | 无法用 AsyncAPI 原生表达聚合窗口 | 下沉到 Kafka Streams / Camel / 应用代码 |
| Resequencer | 【需下沉实现】 | 顺序保证由 broker/consumer 实现 | AsyncAPI 仅声明顺序需求（如 `x-ordered: true`） |
| Process Manager | 【需下沉实现】 | 状态机/编排超出 AsyncAPI 范围 | 见 [1.41 工作流编排系统与消息协同](01-41-工作流编排系统与消息协同.md) |
| Dead Letter Channel | 【需下沉实现】 | 可用 `x-dead-letter-channel` 标注死信通道地址 | 死信投递语义由 broker 实现 |

### 代表性模式 AsyncAPI 片段

**Content-Based Router（需 x- 扩展）**：

```yaml
operations:
  routeOrder:
    action: send
    channel:
      $ref: '#/channels/orders'
    x-routing-predicate:
      field: order.type
      mappings:
        - value: RETAIL
          targetChannel: orders.retail
        - value: WHOLESALE
          targetChannel: orders.wholesale
```

**Correlation Identifier（直接表达）**：

```yaml
components:
  messages:
    PaymentProcessed:
      name: PaymentProcessed
      correlationId:
        description: 关联 PlaceOrder 命令
        location: $message.header#/correlation-id
      headers:
        type: object
        required: [correlation-id]
        properties:
          correlation-id:
            type: string
            format: uuid
```

**Process Manager（需下沉实现）**：

```yaml
# AsyncAPI 只能声明编排器对外发布/接收的事件边界
channels:
  orderSagaEvents:
    address: orders.saga.v1
    x-managed-by: order-saga-orchestrator
    x-saga-step: [reserve-inventory, charge-payment, confirm-order]
```

> EIP 完整目录与六系统映射参见 [1.38 企业集成模式全目录与系统映射](01-38-企业集成模式全目录与系统映射.md)。

## 1.43.4 遗留代码逆向 → DSL

【论证】"实现先行"的团队常从代码反向生成 AsyncAPI。逆向是起点而非终点：必须把生成文档拉回治理流程，否则契约会随代码漂移、字段含义缺失、版本语义混乱。

### 工具现状（核实至 2026-11）

| 工具/生态 | 作用 | 当前状态 | 来源 |
| --------- | ---- | -------- | ---- |
| **Springwolf** | Spring Boot 注解扫描 → AsyncAPI | 活跃维护线 2.x，最新 2.9.0（2026-09-28），支持 Spring Boot 4.x、Kafka/RabbitMQ/AMQP/SNS/SQS；官方声明 2.9.0 是 2.x 最后版本，下版将迁移到 jackson 3 | [springwolf-core releases](https://github.com/springwolf/springwolf-core/releases) |
| **EventCatalog AsyncAPI 插件** | 把 AsyncAPI 文件导入事件目录 | 当前包名为 `@eventcatalog/generator-asyncapi`，npm 最新 7.0.3；旧仓库 `event-catalog/generator-asyncapi` 已于 2025-02-05 archived | [eventcatalog.dev/docs/plugins/asyncapi/intro](https://www.eventcatalog.dev/docs/plugins/asyncapi/intro)、[npm/jsDelivr](https://www.jsdelivr.com/package/npm/@eventcatalog/generator-asyncapi) |
| **AsyncAPI Generator / CLI** | 模板/校验/bundle/diff | CLI 活跃版本 6.x（GitHub releases 显示 6.3.0），支持 validate、generate fromTemplate、diff | [asyncapi/cli releases](https://github.com/asyncapi/cli/releases) |
| **社区静态扫描** | 从 broker/代码推断拓扑 | 未核实到名为 "kafka-topology-descriptor" 的成熟工具；可替代思路：Kafka AdminClient 拉取 topic 列表 + Schema Registry 拉取 schema，再用模板生成 AsyncAPI 骨架 | 【估算】 |

### Springwolf 最小示例

```java
@AsyncListener(operation = @AsyncOperation(
    channelName = "orders.order.created.v1",
    description = "订单创建事件"
))
@KafkaListener(topics = "orders.order.created.v1")
public void onOrderCreated(OrderCreatedEvent event) {
    // 处理逻辑
}
```

启动应用后访问 `/springwolf/docs` 即可获取自动生成的 AsyncAPI JSON/YAML。

### 逆向 → 正向治理四步

```text
1. 逆向生成：Springwolf / 静态扫描产出初稿 AsyncAPI
2. 人工评审：补全 description、x-owner、examples、兼容性声明
3. 锁定基线：通过 validate + spectral lint，写入版本库并打 tag
4. 正向变更：后续契约修改先改 AsyncAPI，再用 Diff 校验实现是否一致
```

> 治理细节与 CI 流水线示例参见 [1.37 AsyncAPI 组织级应用与治理](01-37-AsyncAPI组织级应用与治理.md)。

## 1.43.5 OpenAPI → AsyncAPI

### REST 资源操作到事件的转换规则

【论证】同一微服务往往同时暴露 OpenAPI（REST）与 AsyncAPI（事件）。设计事件时不能只复制资源字段，而要提取"领域变化"语义。

| REST 操作 | OpenAPI 路径示例 | 对应领域事件 | AsyncAPI channel 命名 |
| --------- | ---------------- | ------------ | --------------------- |
| POST /orders | 创建资源 | `OrderCreated` | `orders.order.created.v1` |
| PUT /orders/{id} | 全量更新 | `OrderUpdated` | `orders.order.updated.v1` |
| PATCH /orders/{id} | 部分更新 | `OrderPatched` 或 `OrderStatusChanged` | `orders.order.status-changed.v1` |
| DELETE /orders/{id} | 删除资源 | `OrderCancelled` / `OrderDeleted` | `orders.order.cancelled.v1` |

转换原则：

1. **不要直接把 HTTP 方法名照搬到事件名**：`POST orders` 不是 `OrdersPost`，而是 `OrderCreated`。
2. **资源路径 → channel 域前缀**：`/orders/{id}/payments` 可映射为 `orders.payments.*` 域。
3. **状态码 ≠ 事件**：REST 的 201/200/204 是同步结果，异步场景需显式定义成功事件与错误事件。
4. **保留幂等与追踪字段**：OpenAPI 的 idempotency-key、correlation-id 应延续到 AsyncAPI headers。

### 同一服务双契约组织方式

推荐把 OpenAPI 与 AsyncAPI 放在同一仓库，通过 `components.schemas` 共享 DTO schema，用 `oneOf` 表达事件多态：

```yaml
asyncapi: '3.0.0'
info:
  title: Order Service Async Contracts
  version: 1.0.0

channels:
  orderEvents:
    address: orders.order.events.v1
    messages:
      orderEvent:
        payload:
          oneOf:
            - $ref: 'https://example.com/schemas/order/OrderCreated.json'
            - $ref: 'https://example.com/schemas/order/OrderCancelled.json'

components:
  schemas:
    OrderSummary:
      $ref: '../openapi/components/schemas/OrderSummary.yaml'
```

> 双契约协同与 Backstage 注册示例参见 [1.37 AsyncAPI 组织级应用与治理](01-37-AsyncAPI组织级应用与治理.md) 1.37.5 节。

## 1.43.6 BPMN/工作流定义 → 消息契约

【论证】BPMN 与 AsyncAPI 处在不同抽象层：BPMN 描述流程状态机，AsyncAPI 描述事件/命令的消息边界。转换时只提取流程与外部服务交互的消息触点，不重复展开工作流本体（工作流本体见 [1.41 工作流编排系统与消息协同](01-41-工作流编排系统与消息协同.md)）。

### BPMN 元素到消息契约映射

| BPMN 元素 | 消息契约含义 | AsyncAPI 表达 |
| --------- | ------------ | ------------- |
| 任务节点（Task / Service Task） | 命令消息：请某服务执行动作 | operation `send` + command message |
| 边界事件（Boundary Event） | 领域事件：流程被外部事件触发 | operation `receive` + event message |
| 消息流（Message Flow） | channel/operation 关联 | 用 channel address 命名消息流 |
| 补偿事件（Compensation Event） | 错误/补偿事件 | `error` 事件契约或 `x-compensation-for` |
| 定时器事件（Timer Event） | 超时/调度信号 | 通常下沉到编排器实现；AsyncAPI 可标注 `x-timer-trigger` |

### Temporal/Camunda 导出契约思路

**Temporal**：

- Workflow 代码中的 Signal 定义 → AsyncAPI `receive` operation（外部系统向工作流发信号）。
- Workflow 启动入口 → AsyncAPI `receive` operation（Kafka consumer 收到事件后启动工作流）。
- Activity 中发送的消息 → AsyncAPI `send` operation。
- Query → 通常不进入 AsyncAPI，保留为同步 API/OpenAPI。

**Camunda 8 / Zeebe**：

- BPMN XML 中的 `bpmn:message` 元素 → AsyncAPI message name 与 correlation key。
- Service Task 的 Job Type → 不直接映射为 AsyncAPI operation，而是工作流内部任务契约；对外发布的事件由 task 完成后的 throw event 产生。
- 导出的契约骨架：

```yaml
channels:
  orderSagaSignals:
    address: orders.saga.signals.v1
    x-orchestrator: temporal-order-saga
    messages:
      PaymentConfirmed:
        $ref: '#/components/messages/PaymentConfirmed'
      AddressChanged:
        $ref: '#/components/messages/AddressChanged'
```

> 工作流编排系统的选型与反模式参见 [1.41 工作流编排系统与消息协同](01-41-工作流编排系统与消息协同.md)。

## 1.43.7 转换反模式

| 反模式 | 症状 | 正确做法 |
| ------ | ---- | -------- |
| **逐字段直译 REST 到事件** | 事件名如 `OrdersPost`、`OrdersPut`；payload 是完整资源快照，无领域语义 | 用动词过去式命名事件；payload 只携带变化字段 + 必要上下文 |
| **逆向生成后不治理** | Springwolf 生成的文档无 owner、无 description、版本号恒为 `1.0.0` | 逆向文档必须经过评审、补元数据、锁定基线，再进入正向变更 |
| **多源转换结果不合并去重** | Event Storming 与 OpenAPI 转换出两个同名不同义的 `OrderCreated` | 建立组织级事件目录，统一命名与 schema；冲突走评审 |
| **把下沉实现模式硬塞进 DSL** | 在 AsyncAPI 中试图完整描述聚合窗口、路由表、状态机 | 用 `x-` 扩展标注需求，实现细节交给框架/代码 |
| **忽略 bindingVersion** | 各团队 Kafka/MQTT binding 版本混杂，工具解析不一致 | Spectral 规则强制声明 `bindingVersion` |
| **缺失错误事件契约** | 只定义成功事件，失败场景无契约 | 按 [2.54](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md) 模板定义 `*Failed` 事件 |
