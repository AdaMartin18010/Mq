## 1.41.1 为什么 Saga/编舞不够时需要编排器

在 [2.47](../02-场景驱动架构设计/02-47-企业集成模式与事务消息模式.md) 中，Saga 通过“本地事务 + 补偿”实现跨服务的最终一致性。协同式（Choreography）Saga 没有中心控制器，各服务完成本地事务后发布领域事件，由感兴趣的下游服务触发下一步。这种模型在步骤少、服务自治要求高的场景下非常轻量，但当流程复杂时会出现以下痛点：

1. **流程可见性低**：业务状态散落在各服务的日志和事件订阅中，排查一条订单需要追踪多个 topic/队列。
2. **补偿逻辑分散**：每个参与者都要知道“上游失败时我该补偿什么”，补偿顺序由事件隐式表达，容易遗漏。
3. **分支与并发难以表达**：并行路径、条件分支、人工审批、定时等待等语义很难用纯事件传递表达。
4. **生命周期管理困难**：长时间等待（如 7 天未付款自动取消）、外部信号（用户修改地址）、状态查询缺少统一入口。

当流程步骤超过 **5~7 个**、存在分支/并行/人工任务或需要严格审计时，引入独立的**编排器（Orchestrator）**通常比纯 MQ 编舞更可控。编排器把流程显式建模为状态机或代码，集中管理顺序、补偿、超时和重试。

## 1.41.2 编排器与消息 Broker 的职责边界

【论证】编排器和消息 Broker 不是替代关系，而是分层关系。Broker 解决“事件如何可靠传输”，编排器解决“流程如何按业务规则推进”。混淆两者会把编排器当成高吞吐事件总线，导致延迟、瓶颈和状态爆炸。

| 职责 | 消息 Broker（Kafka/NATS/RabbitMQ 等） | 工作流编排器（Temporal/Camunda 等） |
| --- | --- | --- |
| 核心抽象 | Topic / Queue / Partition | Workflow / Activity / Task / State |
| 持久化对象 | 消息记录 | 工作流执行事件历史、状态机、定时器 |
| 主要保证 | 至少一次/最多一次投递、顺序、削峰 | 长流程持久执行、补偿、超时、可见性 |
| 重试粒度 | 单条消息消费重试 | 活动级/流程级重试与补偿编排 |
| 耦合方式 | 服务通过事件契约松耦合 | 参与者通过 activity/job/task 契约与编排器耦合 |
| 典型吞吐 | 高（十万~百万 TPS） | 中（视实现，通常千~万级工作流实例/秒） |
| 可视化 | 低（需额外链路追踪） | 高（事件历史、流程图、审计日志） |

两者协作的常见模式：

- **编排器 → Broker**：工作流的 Activity 向 Kafka/NATS 发命令或事件，触发下游服务。
- **Broker → 编排器**：Kafka consumer 收到事件后调用编排器 Client 启动工作流；或工作流监听 Signal/消息触发步骤推进。
- **编排器 + Outbox**：工作流内部更新业务库时，通过 Outbox 模式保证“状态变更 + 发消息”的原子性（参见 [2.47](../02-场景驱动架构设计/02-47-企业集成模式与事务消息模式.md)）。

## 1.41.3 Temporal 与 Cadence：durable execution 模型

### 核心概念

Temporal 是一个开源的 durable execution 平台，由 Uber Cadence 团队于 2019 年 fork 出来独立发展。其核心理念是：把长流程写成普通代码，由平台保证代码在进程崩溃、机器重启、部署更新后仍能从中断点继续执行。

| 概念 | 作用 | 是否可含副作用 |
| --- | --- | --- |
| **Workflow** | 定义流程的确定性骨架（顺序、分支、补偿、定时器） | 否，必须是确定性的 |
| **Activity** | 执行与外部系统交互的非确定性操作（调用 API、写 DB、发消息） | 是 |
| **Signal** | 向运行中的工作流发送异步消息，影响其后续行为 | — |
| **Query** | 只读查询工作流当前状态，不修改执行 | — |
| **Timer** | 持久化定时器，可跨越重启等待数天甚至数月 | — |
| **Task Queue** | 工作流任务与活动任务的内部队列，Worker 长轮询取任务 | — |

### 版本与生态

截至 2026-11，Temporal Server 最新稳定版本为 [v1.32.2](https://github.com/temporalio/temporal/releases/latest)；其上游 Cadence 的最新 GA 版本为 [v1.4.5](https://github.com/uber/cadence/releases/latest)。Temporal 官方提供 Go、Java、TypeScript、Python、.NET SDK，Replay 2026 还发布了 External Payload Storage、Serverless Workers、Workflow Streams 等能力。官方架构文档将 Temporal Server 划分为 Frontend、History、Matching、Worker 服务：History 保存事件历史，Matching 管理 Task Queue 的分发，Worker 服务处理内部系统工作流。

### 内部队列机制

Temporal 没有直接把 Kafka 暴露给用户，而是在 Server 内部实现了**Task Queue**：

- **Workflow Task Queue**：当工作流需要推进时，History 服务生成 Workflow Task，由 Matching 服务投递到对应队列。
- **Activity Task Queue**：Activity 被调度后进入 Activity Task Queue，等待 Worker 长轮询获取。
- Worker 通过长轮询（long poll）从队列取任务，任务完成后把结果写回 Server；失败则按 Retry Policy 重试（与 [2.16](../02-场景驱动架构设计/02-16-消息重试机制.md) 的重试策略互相参照）。

### 代码示例：Go 工作流骨架

```go
package app

import (
    "time"
    "go.temporal.io/sdk/workflow"
)

type OrderWorkflowInput struct {
    OrderID string
}

func OrderSagaWorkflow(ctx workflow.Context, input OrderWorkflowInput) error {
    // 统一重试策略
    ao := workflow.ActivityOptions{
        StartToCloseTimeout: 10 * time.Second,
        RetryPolicy: &temporal.RetryPolicy{
            InitialInterval:    time.Second,
            BackoffCoefficient: 2.0,
            MaximumAttempts:    3,
        },
    }
    ctx = workflow.WithActivityOptions(ctx, ao)

    // 正向操作
    err := workflow.ExecuteActivity(ctx, ReserveInventory, input.OrderID).Get(ctx, nil)
    if err != nil {
        return err
    }
    // 补偿必须幂等，并在后续失败时继续执行
    defer func() {
        if err != nil {
            _ = workflow.ExecuteActivity(ctx, ReleaseInventory, input.OrderID).Get(ctx, nil)
        }
    }()

    err = workflow.ExecuteActivity(ctx, ChargePayment, input.OrderID).Get(ctx, nil)
    if err != nil {
        _ = workflow.ExecuteActivity(ctx, RefundPayment, input.OrderID).Get(ctx, nil)
        return err
    }

    return workflow.ExecuteActivity(ctx, ConfirmOrder, input.OrderID).Get(ctx, nil)
}
```

### 与业务消息系统的集成模式

Activity 中发送 Kafka 消息是常见需求，但应注意：Activity 本身可能被重试，因此消息生产和下游幂等必须配套。

```go
func NotifyWarehouseActivity(ctx context.Context, orderID string) error {
    producer, err := kafka.NewProducer(&kafka.ConfigMap{"bootstrap.servers": "kafka:9092"})
    if err != nil {
        return err
    }
    defer producer.Close()

    msg := &kafka.Message{
        TopicPartition: kafka.TopicPartition{Topic: strPtr("warehouse-tasks"), Partition: kafka.PartitionAny},
        Key:            []byte(orderID),
        Value:          []byte(`{"order_id":"`+orderID+`","action":"pick"}`),
    }
    return producer.Produce(msg, nil)
}
```

反向集成：Kafka Consumer 收到 `OrderCreated` 事件后启动 Temporal 工作流。

```go
func StartOrderWorkflow(client client.Client, event OrderCreatedEvent) {
    options := client.StartWorkflowOptions{
        ID:        "order-" + event.OrderID,
        TaskQueue: "order-saga-queue",
    }
    _, _ = client.ExecuteWorkflow(context.Background(), options, OrderSagaWorkflow, OrderWorkflowInput{
        OrderID: event.OrderID,
    })
}
```

## 1.41.4 Camunda 8 / Zeebe：BPMN 标准与 Worker 轮询模型

### BPMN 2.0 标准

【定理】Camunda 8 的执行引擎 Zeebe 基于 **BPMN 2.0**（Business Process Model and Notation）标准。该标准由 OMG 维护，当前规范版本为 **BPMN 2.0.2**（2014-01 发布，并被 ISO/IEC 19510:2013 采纳），规范原文见 [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/)。BPMN 提供了一套图形化、可执行的流程建模符号：事件（Event）、活动（Activity）、网关（Gateway）、顺序流/消息流（Sequence/Message Flow）、泳池与泳道（Pool/Lane）。

### Camunda 8 架构要点

截至 2026-11，Camunda 8 的稳定维护线为 **8.10.0**（2026-10-13 发布），其运行时核心是 **Zeebe**：

- **事件溯源日志**：流程实例状态以追加日志形式保存在分区中，每个分区通过 Raft 复制保证高可用。
- **gRPC API + Job Worker**：服务任务不由引擎主动调用，而是被推送到 Job Queue，外部 Worker 通过 `ActivateJobs` 长轮询获取任务并处理。
- **多组件栈**：Zeebe（引擎）+ Operate（运维监控）+ Tasklist（人工任务）+ Modeler（建模）+ Connectors/Optimize 等。

### Worker 消息轮询模型

Zeebe Worker 与消息队列消费者的最大相似点是**长轮询取任务**，但语义不同：

- Broker 中消费者订阅的是业务事件；Zeebe Worker 订阅的是 BPMN 服务任务 job。
- Job 带有 `jobKey`、`processInstanceKey`、`retries`、`deadline` 等元数据；Worker 处理后必须显式 `CompleteJob` 或 `FailJob`。
- 重试、超时、补偿边界事件都在 BPMN 模型中声明，运行时按模型执行。

```java
@Configuration
public class PaymentWorker {

    @JobWorker(type = "process-payment", autoComplete = true)
    public Map<String, Object> handlePaymentJob(ActivatedJob job) {
        String orderId = job.getVariable("orderId").toString();
        boolean success = paymentService.charge(orderId);
        return Map.of("paymentSuccess", success);
    }
}
```

### 与通用 MQ 的对比

| 维度 | Zeebe / Camunda 8 | Kafka / NATS / RabbitMQ |
| --- | --- | --- |
| 建模方式 | BPMN 图形 + XML，可视化强 | 无内置流程模型，需应用层实现 |
| 任务分发 | Job Worker 长轮询 gRPC | Consumer 长轮询 / push |
| 状态持久化 | 事件溯源日志，引擎内建 | 仅消息日志，不保存流程状态 |
| 人工任务 | Tasklist 原生支持 | 需额外开发 |
| 适用场景 | 审批流程、BPM、强审计 | 高吞吐事件总线、流处理 |

【论证】Camunda 8 的许可证为 Camunda License v1.0（非 OSI 认证开源），生产自托管需关注授权条款；如果团队偏好 Apache 2.0 纯开源，可评估 Operaton、Flowable 等替代方案。

## 1.41.5 CNCF Serverless Workflow：DSL 式工作流

CNCF Serverless Workflow 是一个面向云原生、无厂商锁定的**声明式工作流规范**，2020-07-14 被 CNCF 接纳为 Sandbox 项目。2026-06 该项目更名为 **Open Workflow Specification**，新的规范仓库为 [open-workflow-specification/specification](https://github.com/open-workflow-specification/specification)，最新发布版本为 **v1.1.0**。

其 DSL 使用 YAML/JSON 描述状态机，核心元素包括：

- `events`：CloudEvents 事件触发。
- `functions`：调用 OpenAPI/AsyncAPI/gRPC/HTTP 服务。
- `states`：`event`、`operation`、`switch`、`sleep`、`parallel`、`foreach`、`callback` 等。
- `retries` / `timeouts` / `errors`：与 [2.16](../02-场景驱动架构设计/02-16-消息重试机制.md) 类似的重试与超时语义。

### DSL 示例：订单审批工作流

```yaml
id: order-approval
version: '1.0'
specVersion: '1.1.0'
name: Order Approval Workflow
start: ReceiveOrder
events:
  - name: OrderCreated
    type: com.example.order.created
    source: /orders
functions:
  - name: CheckInventory
    operation: http://inventory.example.com/check
  - name: NotifyCustomer
    operation: http://notification.example.com/send
states:
  - name: ReceiveOrder
    type: event
    onEvents:
      - eventRefs: [OrderCreated]
    transition: CheckStock

  - name: CheckStock
    type: operation
    actions:
      - functionRef: CheckInventory
        arguments:
          orderId: '${ .order.id }'
    transition: Decide

  - name: Decide
    type: switch
    dataConditions:
      - condition: '${ .inventory.available == true }'
        transition: Approve
    defaultCondition:
      transition: Reject

  - name: Approve
    type: operation
    actions:
      - functionRef: NotifyCustomer
        arguments:
          message: 'Order approved'
    end: true

  - name: Reject
    type: operation
    actions:
      - functionRef: NotifyCustomer
        arguments:
          message: 'Order rejected'
    end: true
```

【论证】Serverless Workflow 更适合需要在多云/FaaS 之间迁移、希望以声明式 YAML 而非代码定义流程的场景；其生态成熟度（运行时、IDE 工具、企业支持）低于 Temporal 和 Camunda 8。

## 1.41.6 Dapr Workflow 与 Netflix Conductor：轻量替代

### Dapr Workflow

Dapr（Distributed Application Runtime）在 v1.10+ 引入 Workflow API，当前 Dapr 运行时最新稳定版为 [v1.19.1](https://github.com/dapr/dapr/releases/latest)。Dapr Workflow 基于 **Dapr Actors** 实现 durable execution，状态持久化到配置的 state store（Redis、PostgreSQL、SQLite 等）。

其优势是**与 Dapr 现有构建块（pub/sub、state、bindings、secrets）原生集成**，无需额外部署 Temporal Server，适合已经全面采用 Dapr sidecar 的 Kubernetes 微服务体系。官方支持 .NET、Python、Go、JavaScript SDK。

```python
import dapr.ext.workflow as wf

def order_workflow(ctx: wf.DaprWorkflowContext, order):
    try:
        yield ctx.call_activity(reserve_inventory, input=order)
        yield ctx.call_activity(charge_payment, input=order)
        yield ctx.call_activity(confirm_order, input=order)
    except Exception:
        yield ctx.call_activity(release_inventory, input=order)
        raise

def reserve_inventory(ctx, order):
    # 与外部库存服务交互
    pass
```

### Netflix Conductor

Netflix Conductor 曾是微服务编排领域的代表性开源项目，采用 JSON DSL 定义工作流，支持动态任务和多种持久化后端（Redis、Cassandra、MySQL、Elasticsearch）。

但 [Netflix 已于 2023-12-13 宣布停止维护 Conductor OSS](https://github.com/Netflix/conductor)，代码仓库保留但不再更新；社区后续 fork 出 [conductor-oss.org](https://conductor-oss.org/) 继续维护。【论证】对于新项目，除非已有深厚的 Conductor 资产或依赖社区 fork，否则更建议评估 Temporal、Camunda 8 或 Dapr Workflow。

## 1.41.7 编排 vs 编舞选型矩阵

### 维度对比

| 维度 | 编舞（MQ + Saga） | 编排（Orchestrator） |
| --- | --- | --- |
| **流程可见性** | 低，状态分散在各服务 | 高，集中事件历史/流程图 |
| **服务耦合** | 事件契约耦合 | 与编排器的任务契约耦合 |
| **补偿复杂度** | 低（步骤少时）/ 高（步骤多时） | 中，集中定义补偿路径 |
| **团队规模** | 小团队、高自治 | 中大型团队、需统一规范 |
| **典型延迟** | 低（纯异步事件） | 中（多出一次调度/轮询） |
| **人工任务/定时器** | 需自行实现 | 原生支持 |
| **分支/并行** | 实现复杂 | BPMN 或代码直观表达 |

### 决策树

1. **流程步骤 ≤ 3、无人工任务、无长等待？**
   - 是 → 优先 **MQ 编舞**（Kafka / NATS / RabbitMQ + Saga 补偿）。
2. **步骤 > 5、存在条件分支/并行/人工审批？**
   - 是 → 引入 **编排器**。
3. **需要 BPMN 可视化、强审计、人工任务表单？**
   - 是 → **Camunda 8 / Zeebe**。
4. **偏好代码优先、长运行、AI/ML 管道、微服务 Saga？**
   - 是 → **Temporal**。
5. **已全面使用 Dapr/Kubernetes、流程相对简单？**
   - 是 → **Dapr Workflow**。
6. **需要多云/无厂商锁定的声明式 DSL？**
   - 是 → **Open Workflow Specification / CNCF Serverless Workflow**。

### 主流编排器快速对照

| 系统 | 模型 | 最佳场景 | 主要顾虑 |
| --- | --- | --- | --- |
| Temporal | Code-first durable execution | 长流程、微服务 Saga、AI 管道 | Worker 代码需保证确定性 |
| Camunda 8 | BPMN + Job Worker | 审批/业务流程、强审计、人工任务 | 许可证/组件栈复杂度 |
| Open Workflow Spec | YAML/JSON DSL | 多云 FaaS、声明式集成 | 生态和运行时成熟度 |
| Dapr Workflow | Actor-based sidecar | Dapr 生态、K8s 微服务 | 依赖 Dapr sidecar 与 state store |
| Netflix Conductor | JSON DSL | 历史存量、社区 fork | 官方已停止维护 |

## 1.41.8 反模式与工程禁忌

| 反模式 | 症状 | 正确做法 |
| --- | --- | --- |
| **把编排器当 Broker 用** | 用工作流任务做大规模事件扇出、日志管道，导致编排器延迟飙升 | 高吞吐事件仍走 Kafka/NATS；编排器只处理流程状态 |
| **Workflow 内大事务** | Activity 长时间占用数据库锁或分布式锁 | 每个 Activity 完成一个本地事务并提交，失败时用补偿回滚 |
| **Workflow 代码含副作用** | 在 Workflow 中调用 `time.Now()`、`rand`、`UUID`、外部 API，导致回放不一致 | 所有非确定性操作放入 Activity |
| **把大负载塞进事件历史** | 事件历史膨胀，查询和回放变慢 | 大对象使用外部存储 + claim-check 模式 |
| **补偿非幂等** | 补偿重试导致重复退款/重复释放库存 | 补偿操作本身需幂等，使用业务键去重 |
| **忽视历史大小限制** | 单实例事件历史超过上限后无法继续 | 长流程定期 `Continue-As-New`，拆分子工作流 |
