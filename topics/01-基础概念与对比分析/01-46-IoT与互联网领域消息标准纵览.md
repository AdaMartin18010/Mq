## 1.46.1 为什么需要域级消息标准

IoT 与互联网场景对消息的需求差异极大：工业现场强调**实时状态感知与命令下发**，互联网业务强调**幂等、乱序治理与版本化契约**，AI Agent 则强调**跨框架发现、长任务协作与可观测**。若每个项目都自造主题命名、payload 编码与生命周期语义，集成成本会随设备/服务数量指数上升。

域级消息标准解决三类问题：

1. **互操作性**：不同厂商设备、不同团队微服务能“说同一种事件语言”。
2. **状态可观测**：通过出生/死亡证书、任务状态机等机制，消费者能判断数据是否新鲜、任务是否存活。
3. **契约可治理**：借助 CloudEvents 信封与 AsyncAPI 契约，把隐性的“约定”变成可版本化、可校验的显性合同。

下表给出本文涉及标准的官方版本快照（核实至 2026-11）：

| 标准/规范 | 治理方 | 当前稳定版本 | 发布/维护日期 |
| ------ | ------ | ------ | ------ |
| **Sparkplug** | Eclipse Foundation (Tahu/Sparkplug Project) | 3.0.0 | 2022-10-21（PDF 2022-11-16） |
| **OPC UA Part 14 PubSub** | OPC Foundation | Release 1.05.06 | 2025-10-31 |
| **OPC UA FX (Field eXchange)** | OPC Foundation | V1.00.04 | 2026-07-27（维护发布） |
| **A2A Protocol** | Linux Foundation (a2aproject) | 1.0.0（补丁 1.0.1 于 2026-05-26） | 2026-03-12 |
| **CloudEvents** | CNCF | 1.0.2 | 2022-02-05 |
| **AsyncAPI** | AsyncAPI Initiative / Linux Foundation | 3.1.0 | 2026-01-31 |
| **AsyncAPI MQTT Binding** | AsyncAPI Initiative | 0.2.0 | 与 AsyncAPI 3.x 同步维护 |

## 1.46.2 工业 IoT：Sparkplug B

### 标准来源与版本现状

Sparkplug 是 Eclipse Foundation 下的开放规范，定义了 MQTT 主题命名空间、payload 编码与会话状态管理，目标是为 SCADA/IIoT 提供即插即用的互操作基础【定理：[Sparkplug 规范首页](https://sparkplug.eclipse.org/specification/)】。当前正式版本为 **Sparkplug 3.0.0**（2022-10-21 通过 Eclipse Foundation Specification Process 批准，规范 PDF 版本日期 2022-11-16）；后续 4.0 版本仍在工作组推进中，尚未发布正式版【论证】。

### 主题命名空间与消息类型

Sparkplug B 使用固定根命名空间 `spBv1.0`，主题层级为：

```text
spBv1.0/<group_id>/<message_type>/<edge_node_id>/<device_id>
```

其中 `<device_id>` 对 Edge Node 级消息（NBIRTH/NDATA/NDEATH/NCMD）可省略【定理：[Sparkplug 3.0 PDF §4.1](https://sparkplug.eclipse.org/specification/version/3.0/documents/sparkplug-specification-3.0.0.pdf)】。

| 消息类型 | 方向 | 语义 | 生命周期/数据 |
| ------ | ------ | ------ | ------ |
| **NBIRTH** | Edge Node → Host | Edge Node 上线，携带全部 Node 级指标 | 生命周期 |
| **DBIRTH** | Device → Host | Device 上线，携带全部 Device 级指标 | 生命周期 |
| **NDATA** | Edge Node → Host | Node 级数据变化（RBE） | 数据 |
| **DDATA** | Device → Host | Device 级数据变化（RBE） | 数据 |
| **NCMD** | Host → Edge Node | 向 Node 下发命令 | 命令 |
| **DCMD** | Host → Device | 向 Device 下发命令 | 命令 |
| **NDEATH** | Edge Node → Host（Will） | Edge Node 离线 | 生命周期 |
| **DDEATH** | Device → Host | Device 离线 | 生命周期 |
| **STATE** | Host → 所有订阅者 | Host 应用上下线状态 | 生命周期 |

### Protobuf payload 定义

Sparkplug B 的 payload 基于 Google Protocol Buffers，核心结构如下（示意性最小子集，完整定义见规范）：

```protobuf
syntax = "proto3";
package sparkplug_b;

message Payload {
  optional uint64 timestamp = 1;  // 毫秒级 UNIX 时间戳
  repeated Metric metrics   = 2;  // 数据点集合
  optional uint64 seq       = 3;  // 会话内序号，0-255 循环
  optional string uuid      = 4;  // 扩展/压缩用途
  optional bytes  body      = 5;  // 压缩或自定义二进制
}

message Metric {
  optional string name      = 1;  // 指标名，Birth 时必须携带
  optional uint64 alias     = 2;  // 别名，Birth 后可用别名替换 name
  optional uint64 timestamp = 3;
  optional uint32 datatype  = 4;  // Sparkplug 自定义数据类型枚举
  optional bool   is_historical = 5;
  optional bool   is_null       = 6;
  // 值字段为 oneof，略；详见规范
}
```

### CloudEvents/AsyncAPI 映射示例

Sparkplug 消息本身已是强规范格式，若需要与 IT 侧事件网格互操作，可在网关层拆包后包装为 CloudEvents；同时在 AsyncAPI 中描述主题模板与 QoS：

```yaml
asyncapi: '3.1.0'
info:
  title: Sparkplug UNS Events
  version: 1.0.0

servers:
  mqttProd:
    host: mqtt.factory.example.com:8883
    protocol: mqtt
    protocolVersion: '5.0'
    bindings:
      mqtt:
        clientId: scada-host
        cleanSession: false
        keepAlive: 60
        bindingVersion: '0.2.0'

channels:
  deviceData:
    address: 'spBv1.0/{group_id}/DDATA/{edge_node_id}/{device_id}'
    parameters:
      group_id:    { description: 产线/厂区分组 }
      edge_node_id: { description: 边缘网关 ID }
      device_id:   { description: 设备 ID }
    messages:
      ddataMessage:
        name: DDATA
        contentType: application/x-protobuf
        payload:
          $ref: '#/components/schemas/SparkplugPayload'

operations:
  receiveDData:
    action: receive
    channel:
      $ref: '#/channels/deviceData'
    bindings:
      mqtt:
        qos: 1
        bindingVersion: '0.2.0'

components:
  schemas:
    SparkplugPayload:
      type: object
      description: Sparkplug B Protobuf 解码后的 JSON 表示
```

CloudEvents 映射建议：

- `ce_type`：`com.example.sparkplug.DDATA`
- `ce_source`：`/factory/{group_id}/{edge_node_id}/{device_id}`
- `ce_subject`：指标别名或设备路径
- `ce_time`：Sparkplug `timestamp`
- `data`：解码后的 metrics 数组

### 选型注意

- Sparkplug 适合需要**统一命名空间 + 出生/死亡状态 + 报告例外（RBE）**的 SCADA/IIoT 场景。
- 若设备侧已实现 OPC UA 信息模型且需要与 MES/ERP 深度对齐，可考虑 OPC UA PubSub 作为补充，而非完全替代【论证】。

## 1.46.3 制造互操作：OPC UA PubSub

### 标准来源与版本现状

OPC UA PubSub（Part 14）定义了发布-订阅通信模型， Publisher 通过中间件向 Subscriber 发送数据集消息，无需维护客户端/服务器会话【定理：[OPC 10000-14: UA Part 14: PubSub](https://reference.opcfoundation.org/Core/Part14/v105/docs/)】。当前 Release **1.05.06** 发布于 2025-10-31。针对现场级控制器互联，OPC Foundation 还推出了 **OPC UA FX (Field eXchange)**，2026-07-27 发布维护版本 V1.00.04。

### MQTT 映射与 UADP/JSON 编码

OPC UA PubSub 支持多种传输：UDP、Raw Ethernet、MQTT 等。通过 MQTT 映射时，Publisher 将 **NetworkMessage** 发布到约定的 MQTT 主题，Subscriber 订阅后按编码格式解析。

| 编码 | 特点 | 典型场景 |
| ------ | ------ | ------ |
| **UADP** | OPC UA 二进制编码，紧凑、高效，支持批量数据与元数据 | 现场级实时通信、TSN |
| **JSON** | 可读、易与云/IT 系统对接，但带宽开销大 | 云端监控、数字孪生 |

MQTT 映射需要协调的关键参数：主题格式、QoS、retain、消息最大长度（部分云 MQTT Broker 限制 24 KB）、安全证书（X.509）【论证】。

### 与 Sparkplug 的取舍

| 维度 | Sparkplug B | OPC UA PubSub |
| ------ | ------ | ------ |
| 信息模型 | 轻量 tag/alias | 完整的 OPC UA 地址空间与 Companion Spec |
| 传输依赖 | MQTT 3.1.1/5.0 | MQTT、UDP、Raw Ethernet 等多传输 |
| 状态管理 | Birth/Death + Will 证书 | PubSub 连接/写入组/读取组配置 |
| 互操作重点 | OT-IT 统一命名空间、SCADA 即插即用 | 制造语义互操作、控制器级确定性 |
| 典型落点 | 边缘网关 → 云平台/SCADA | 机器 → MES/数字孪生/控制器互联 |

工程实践中常见组合是 **OPC UA 在机器层做语义建模，Sparkplug 在统一命名空间（UNS）层做状态发布**；需要高确定性控制器协作时引入 OPC UA FX【论证】。

## 1.46.4 互联网电商：订单状态机事件建模

### 订单生命周期事件目录

互联网业务没有统一工业标准，但可借鉴 **事件风暴 + CloudEvents + AsyncAPI** 形成组织级契约。以订单域为例，核心事件目录如下：

| 事件名 | topic/channel（2.54 命名规范） | 触发条件 |
| ------ | ------ | ------ |
| OrderCreated | `orders.order.created.v1` | 订单已创建 |
| OrderPaid | `orders.order.paid.v1` | 支付成功 |
| OrderFulfilled | `orders.order.fulfilled.v1` | 仓库已拣货/打包完成 |
| OrderShipped | `orders.order.shipped.v1` | 物流已揽收 |
| OrderDelivered | `orders.order.delivered.v1` | 用户已签收 |
| OrderCancelled | `orders.order.cancelled.v1` | 订单取消 |
| OrderRefunded | `orders.order.refunded.v1` | 退款完成 |

### 状态机与事件矩阵

订单状态机约束事件乱序：只有处于合法前置状态时，事件才能推进状态；否则进入异常流或人工审核。

| 当前状态 | 允许事件 | 下一状态 |
| ------ | ------ | ------ |
| created | paid / cancelled | paid / cancelled |
| paid | fulfilled / cancelled / refunded | fulfilled / cancelled / refunded |
| fulfilled | shipped / cancelled | shipped / cancelled |
| shipped | delivered / cancelled(拦截) | delivered / cancelled |
| delivered | refunded | refunded |

### 幂等与乱序处理契约

电商事件对乱序极为敏感：物流 `delivered` 可能早于 `shipped` 到达（网络分区或重试），支付回调可能重复。契约层应强制要求：

- **idempotency-key**：由生产方生成，消费方幂等去重（参见 [2.14 消息去重策略](../02-场景驱动架构设计/02-14-消息去重策略.md)）。
- **sequence-number / occurred-at**：用于业务时序判断，必要时结合状态机“拒绝非法前进”。
- **partition key**：按订单号分区保证单订单内顺序（参见 [2.13 消息顺序保证](../02-场景驱动架构设计/02-13-消息顺序保证.md)）。

### 契约模板 yaml 示例

```yaml
eventContract:
  metadata:
    id: urn:events:order:delivered:v1
    name: OrderDelivered
    domain: order
    owner: order-team
    version: 1.0.0
    compatibility: backward
    reviewers: [logistics-team, payment-team]

  header:
    required: [trace-id, idempotency-key, sequence-number, occurred-at]
    properties:
      trace-id:        { type: string, format: uuid }
      idempotency-key: { type: string, format: uuid }
      sequence-number: { type: integer, minimum: 0, description: 订单内事件单调递增序号 }
      occurred-at:     { type: string, format: date-time }

  payload:
    type: object
    required: [orderId, status, deliveredAt, carrierTrackingId]
    properties:
      orderId:          { type: string }
      status:           { type: string, enum: [delivered] }
      deliveredAt:      { type: string, format: date-time }
      carrierTrackingId: { type: string }

  stateMachine:
    from: [shipped]
    to:   delivered

  outOfOrderPolicy:
    action: reject-and-alert  # 或 buffer-until-gap-filled
    maxBufferMs: 5000
```

## 1.46.5 AI Agent：A2A 任务事件与 Agent Card

### A2A 协议当前版本与生态状态

A2A（Agent-to-Agent）是 Google 发起、现由 Linux Foundation 治理的开放协议，目标是让不同框架/厂商的 Agent 能相互发现并协作完成任务，而无需暴露内部状态或工具【定理：[A2A Protocol Specification](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)】。

- **A2A v1.0.0** 于 2026-03-12 发布，是首个标为生产就绪的版本；
- **v1.0.1** 于 2026-05-26 发布，修复 HTTP binding 媒体类型、TaskStatus 值等细节【定理：[A2A Releases](https://github.com/a2aproject/A2A/releases)】。
- 截至 2026-04，公开报道显示已有 150+ 组织支持【论证：源自公开报道，引用前请复核】。

更完整的 Agent 基础设施分析见项目内 [1.35 MQ 与 AI Agent 基础设施分析](01-35-MQ与AI-Agent基础设施分析.md)，本文聚焦消息/契约层面。

### 任务生命周期事件

A2A 的 `Task` 状态机是 Agent 协作的核心【定理：[A2A Spec §Task](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)】：

| Task 状态 | 事件语义 | MQ 承载建议 |
| ------ | ------ | ------ |
| **submitted** | 任务已提交 | `agent.tasks` 新消息，key = task-id |
| **working** | Agent 正在执行 | 周期性心跳/进度事件 |
| **input-required** | 需要人工/外部输入 | 状态变更事件，转编排器/人工队列 |
| **completed** | 成功完成 | `agent.tasks.completed` 结果事件 |
| **failed** | 失败 | `agent.dlq` + 失败分类事件 |
| **canceled** | 已取消（美式拼写） | 取消事件，消费者协作式中断 |

A2A 规范本身以 JSON-RPC 2.0 over HTTP(S) 为主，但长任务天然适合由 MQ 异步承载：Client 发送任务到队列，Worker Agent 竞争消费并回写状态事件。这种映射方式与 1.35 的“任务队列化”阶段一致。

### Agent Card 的服务发现与契约表达

Agent Card 是 A2A 的发现入口，通常托管在 `/.well-known/agent-card.json`，包含能力（skills）、端点、认证、输入/输出模态等。它既是服务发现机制，也是一种**机器可读契约**。

```json
{
  "name": "order-refund-agent",
  "description": "处理订单退款协商的专用 Agent",
  "url": "https://refund-agent.example.com/a2a",
  "version": "1.0.1",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "refund-review",
      "name": "Refund Review",
      "description": "根据订单状态判断是否符合退款条件",
      "tags": ["order", "refund"],
      "examples": ["请审核订单 ORD-2026-0001 的退款申请"]
    }
  ],
  "defaultInputModes": ["text"],
  "defaultOutputModes": ["text", "file"],
  "authentication": {
    "schemes": ["OAuth2"],
    "oauth2": {
      "tokenEndpoint": "https://auth.example.com/oauth/token",
      "scopes": ["a2a:refund"]
    }
  }
}
```

### 与 MQ 的映射提示

- 把 A2A `Task` 的 `id` 作为 MQ 消息的**幂等键/追踪键**，避免 Agent 重试导致重复计费（1.35 红线）。
- `Agent Card` 可注册到事件目录/Schema Registry，与 AsyncAPI 契约并行管理：AsyncAPI 描述“如何收发事件”，Agent Card 描述“Agent 能做什么”。
- 大 Artifact 走对象存储引用，MQ 仅传递指针（参见 1.35 结果 topic 设计）。

## 1.46.6 跨域对比表

| 维度 | 工业 IoT (Sparkplug B) | 制造互操作 (OPC UA PubSub) | 互联网电商 (订单事件) | AI Agent (A2A) |
| ------ | ------ | ------ | ------ | ------ |
| **主题命名** | `spBv1.0/<group>/<type>/<node>/<device>` | 由 PubSub Connection/WriterGroup 配置，可映射到 MQTT 主题 | `<domain>.<entity>.<verb>.v<major>` | 通过 Agent Card URL + skill id 发现，运行时 topic 由集成方定义 |
| **payload 编码** | Protobuf（Sparkplug B） | UADP（二进制）或 JSON | JSON / Avro / Protobuf 均可，推荐 Avro+Schema Registry | JSON-RPC 2.0 / Protocol Buffers 数据模型 |
| **生命周期事件** | NBIRTH/DBIRTH/NDEATH/DDEATH/STATE | PubSub 连接/数据集上线离线，依赖配置而非固定消息类型 | 订单状态机事件（created→paid→…） | Task 状态机（submitted→working→completed/failed/canceled） |
| **契约工具链** | Sparkplug 规范 + TCK；AsyncAPI MQTT binding 描述主题模板 | OPC UA 信息模型 + Companion Spec；AsyncAPI 描述 MQTT 映射 | CloudEvents + AsyncAPI + Schema Registry + 事件目录 | A2A Agent Card + AsyncAPI（事件层）+ OTel trace |
| **核心取舍** | 轻量、状态感知、SCADA 友好 | 语义丰富、制造级互操作、实时可选 | 业务语义清晰、幂等/乱序/版本治理优先 | 跨框架发现、长任务异步协作、可观测 |
