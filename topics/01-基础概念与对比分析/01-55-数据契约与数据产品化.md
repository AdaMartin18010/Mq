## 1.55.1 数据契约运动的背景与定义

在传统的数据仓库/数据湖架构中，数据生产者（应用团队）与数据消费者（分析/AI 团队）之间往往缺乏显式约定。schema 变更、字段含义漂移、数据延迟超标等问题常在下游暴露，造成"数据沼泽"与信任危机。

**数据契约（Data Contract）** 正是为了解决这个问题而提出的：它是数据生产者与消费者之间的显式、可验证的协议，定义了数据的结构、语义、质量、SLA 与生命周期。

【论证】数据契约运动的权威推动者 Andrew Jones 在 O'Reilly《Data Contracts》一书中将其定义为："a formal agreement between a data producer and a data consumer, describing the data that is being exchanged"。该定义强调契约不是文档，而是可被工具解析、测试、强制执行的工程制品。

```text
┌─────────────────────────────────────────────────────────────────────┐
│                    数据契约解决的问题                                │
└─────────────────────────────────────────────────────────────────────┘

  数据生产者                    无契约时                        数据消费者
┌──────────┐                ┌───────────────┐                ┌──────────┐
│ 应用系统  │  ──schema 变更→  │  下游默默损坏  │  ──报表异常→  │ BI/AI   │
│ 数据库   │                │  字段含义不明  │                │ 分析师   │
└──────────┘                └───────────────┘                └──────────┘

  数据生产者        数据契约（schema/语义/SLA/质量）         数据消费者
┌──────────┐                ┌───────────────┐                ┌──────────┐
│ 应用系统  │  ──契约约定──→  │  CI/CD 门禁   │  ──可信数据──→  │ BI/AI   │
│ 数据库   │                │  自动化测试   │                │ 分析师   │
└──────────┘                └───────────────┘                └──────────┘
```

## 1.55.2 三契约体系：数据契约、事件契约、API 契约

现代企业架构中至少存在三类契约，分别对应不同的交互层：

| 契约类型 | 交互对象 | 关注焦点 | 典型规范/工具 | 与 MQ 关系 |
| --- | --- | --- | --- | --- |
| **API 契约** | 服务与服务 | 请求/响应、HTTP 语义、版本 | OpenAPI/Swagger | 描述同步接口 |
| **事件契约** | 服务通过 MQ 交互 | 事件 schema、主题、版本、信封 | AsyncAPI/CloudEvents/Avro | 描述异步消息 |
| **数据契约** | 数据生产者与消费者 | 数据集 schema、语义、质量、SLA | dbt contracts/Bitol/Soda/GE | 可覆盖 MQ 主题与表 |

### 三者的关系

```text
┌─────────────────────────────────────────────────────────────────────┐
│                      三契约体系的分层                                │
└─────────────────────────────────────────────────────────────────────┘

         API 契约（同步）                  事件契约（异步）
              │                                │
              ▼                                ▼
        ┌──────────┐                    ┌──────────┐
        │ OpenAPI  │                    │ AsyncAPI │
        │ REST/gRPC│                    │ Kafka/   │
        │          │                    │ MQTT/NATS│
        └────┬─────┘                    └────┬─────┘
             │                               │
             └──────────────┬────────────────┘
                            │
                            ▼
                    ┌───────────────┐
                    │   数据契约     │
                    │ schema/语义/   │
                    │ SLA/质量规则   │
                    └───────┬───────┘
                            │
                            ▼
                    ┌───────────────┐
                    │  数据产品      │
                    │ （可验证、可发现、│
                    │  可消费）       │
                    └───────────────┘
```

【论证】事件契约是数据契约在 MQ 场景下的子集或前置表达：事件契约保证"消息长什么样"，数据契约进一步保证"这批数据在业务语义、质量、SLA 上可信"。

关于事件契约的具体模板与命名规范，见 [2.54 事件契约模板库与命名规范](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md)；关于 AsyncAPI 组织级治理，见 [1.37 AsyncAPI 组织级应用与治理](01-37-AsyncAPI组织级应用与治理.md)。

## 1.55.3 数据契约的核心要素

一份可执行的数据契约至少应包含以下四类要素：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| **Schema** | 字段名、类型、是否可空、主键 | `user_id BIGINT NOT NULL` |
| **语义（Semantics）** | 字段业务含义、枚举值、单位、PII 标记 | `amount: 订单实付金额（人民币分）` |
| **SLA** | 新鲜度、可用性、延迟、保留周期 | `freshness: < 5 min; retention: 90 days` |
| **质量规则（Quality Rules）** | 唯一性、非空、范围、referential integrity | `amount >= 0; user_id 非空且唯一` |

【论证】仅有 schema 的契约是不完整的。实践中大量数据问题源于语义漂移（如 `amount` 从"分"改为"元"）或质量衰减（如重复记录增加），因此数据契约必须同时覆盖语义与质量。

### 数据契约示例（YAML）

```yaml
# data-contract-order-events.yaml
contract:
  id: order-events-v1
  owner: order-domain@example.com
  source: order-service
  consumer: analytics-platform

schema:
  type: object
  required: [order_id, user_id, amount, created_at]
  properties:
    order_id:
      type: string
      description: 全局唯一订单号
    user_id:
      type: string
      description: 下单用户 ID
    amount:
      type: integer
      description: 订单实付金额，单位人民币分
      minimum: 0
    created_at:
      type: string
      format: date-time

sla:
  freshness: PT5M
  availability: 99.9%
  retention_days: 90

quality:
  - name: order_id_unique
    rule: column order_id is unique
  - name: amount_non_negative
    rule: column amount >= 0
  - name: user_id_not_null
    rule: column user_id is not null
```

## 1.55.4 dbt 模型契约实践

dbt 从 1.5 版本起引入 **model contracts**，并在后续版本（1.6+）中逐步成熟，到 1.9.x 已 GA。模型契约允许在 dbt 模型上显式声明 schema，并在运行时对生产环境强制执行。

```yaml
# models/staging/stg_orders.yml
models:
  - name: stg_orders
    config:
      contract:
        enforced: true
      materialized: table
    columns:
      - name: order_id
        data_type: string
        constraints:
          - type: not_null
          - type: unique
      - name: user_id
        data_type: string
        constraints:
          - type: not_null
      - name: amount
        data_type: int
        constraints:
          - type: not_null
          - type: check
            expression: "amount >= 0"
      - name: created_at
        data_type: timestamp
        constraints:
          - type: not_null
```

关键配置说明：

- `contract.enforced: true`：在目标数据平台（如 Snowflake、BigQuery、Databricks）上创建表时强制执行声明的 schema 与约束。
- `constraints`：可声明 `not_null`、`unique`、`primary_key`、`foreign_key`、`check` 等。
- 当模型 SQL 输出与契约声明不一致时，dbt 会在运行时报错，阻止破坏性变更流入生产。

【论证】dbt 模型契约把数据契约的执行点推进到数据转换层，适合以 dbt 为核心数据管道的团队。但它主要约束 schema 与部分完整性，对语义、SLA、复杂质量规则的覆盖需配合 Great Expectations、Soda 等工具。

## 1.55.5 数据质量工具：Great Expectations 与 Soda

### Great Expectations

Great Expectations（简称 GX）是 Python 生态中广泛使用的数据质量框架。当前 PyPI 最新版本为 1.25.0，支持 Python 3.10 至 3.14。

```python
# Great Expectations 示例：验证订单表
import great_expectations as gx

context = gx.get_context()
datasource = context.data_sources.add_pandas("orders_datasource")
data_asset = datasource.add_dataframe_asset(name="orders_asset")
batch_definition = data_asset.add_batch_definition_whole_dataframe("orders_batch")
batch = batch_definition.get_batch(batch_parameters={"dataframe": df})

# 定义期望
validator = batch.get_validator()
validator.expect_column_values_to_not_be_null("order_id")
validator.expect_column_values_to_be_unique("order_id")
validator.expect_column_values_to_be_between("amount", min_value=0)
validator.expect_column_values_to_match_strftime_format("created_at", "%Y-%m-%d %H:%M:%S")

# 运行并输出结果
validation_result = validator.validate()
print(validation_result.success)
```

特点：

- 丰富的内置 Expectation，覆盖完整性、唯一性、分布、格式等。
- 可生成 Data Docs 报告，便于团队协作。
- 与 dbt、Airflow、Spark 等生态集成成熟。

### Soda

Soda Core 是开源的数据质量测试与监控工具，使用 SodaCL（Soda Checks Language）定义检查，当前 Soda Core 3.5.0 于 2025-02-20 发布，采用 Apache 2.0 许可证。

```yaml
# checks.yml
checks for orders:
  - row_count > 0
  - duplicate_count(order_id) = 0
  - invalid_count(amount) = 0:
      valid min: 0
  - missing_count(user_id) = 0
  - freshness(created_at) < 5m
```

运行命令：

```bash
soda scan -d orders_datasource -c configuration.yml checks.yml
```

特点：

- SodaCL 声明式语法，学习曲线平缓。
- 支持 18+ 数据源。
- 开源版（Soda Core）提供基础检查；企业版提供监控、告警、血缘等高级能力。

### 工具对比

| 维度 | Great Expectations | Soda Core |
| --- | --- | --- |
| **许可证** | Apache 2.0 | Apache 2.0 |
| **定义方式** | Python API / YAML | SodaCL（YAML） |
| **当前版本** | 1.25.0（PyPI） | 3.5.0（2025-02-20） |
| **数据源支持** | 广泛（pandas/Spark/SQL/BigQuery 等） | 18+ 数据源 |
| **报告能力** | Data Docs 较强 | 开源版较弱，企业版强 |
| **与 dbt 集成** | 成熟 | 成熟 |
| **适用场景** | 复杂验证逻辑、Python 团队 | 快速声明式检查、SQL 团队 |

## 1.55.6 数据网格与数据产品化

数据网格（Data Mesh）由 Zhamak Dehghani 于 2019 年提出，核心思想是把数据的所有权从中心化的数据平台团队下放到业务域（domain），并把数据当作**产品**来设计、运营和治理。

【论证】Zhamak Dehghani 在 [Data Mesh Principles and Logical Architecture](https://martinfowler.com/articles/data-mesh-principles.html) 中提出数据网格的四大原则：

1. **域所有权（Domain Ownership）**：数据由最了解业务的域团队拥有。
2. **数据即产品（Data as a Product）**：数据集应像产品一样具备可发现、可寻址、可信赖、可自描述、可互操作、安全等特性。
3. **自助数据平台（Self-Serve Data Platform）**：平台团队提供基础设施，让域团队能自主发布与消费数据产品。
4. **联邦计算治理（Federated Computational Governance）**：全局标准通过自动化策略与去中心化执行实现。

```text
┌─────────────────────────────────────────────────────────────────────┐
│                    数据网格：从单体湖仓到域化产品                     │
└─────────────────────────────────────────────────────────────────────┘

单体湖仓：
┌─────────────────────────────────────────┐
│         中心化数据平台团队               │
│  ┌─────────────────────────────────┐    │
│  │      企业级数据湖/仓             │    │
│  │  （所有域数据集中在此）          │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘

数据网格：
┌─────────────┬─────────────┬─────────────┬─────────────┐
│  订单域      │  用户域      │  库存域      │  物流域      │
│ 数据产品 A   │ 数据产品 B   │ 数据产品 C   │ 数据产品 D   │
│  ┌───────┐  │  ┌───────┐  │  ┌───────┐  │  ┌───────┐  │
│  │schema │  │  │schema │  │  │schema │  │  │schema │  │
│  │ SLA   │  │  │ SLA   │  │  │ SLA   │  │  │ SLA   │  │
│  │quality│  │  │quality│  │  │quality│  │  │quality│  │
│  └───────┘  │  └───────┘  │  └───────┘  │  └───────┘  │
└─────────────┴─────────────┴─────────────┴─────────────┘
           │
           ▼
    ┌───────────────┐
    │ 联邦治理平台   │
    │（发现/目录/策略）│
    └───────────────┘
```

## 1.55.7 数据产品原则与 Netflix Data Mesh 案例衔接

一个合格的数据产品应满足以下原则：

| 原则 | 含义 | 工程落地 |
| --- | --- | --- |
| **可发现（Discoverable）** | 消费者能找到数据产品 | 数据目录（DataHub/Collibra/Atlan）注册 |
| **可寻址（Addressable）** | 有稳定的访问路径 | MQ topic、表、API、Iceberg catalog URI |
| **可信赖（Trustworthy）** | 质量、SLA、血缘可验证 | 数据契约 + 自动化质量检查 |
| **自描述（Self-describing）** | schema、语义、owner 清晰 | AsyncAPI/OpenAPI/dbt docs |
| **可互操作（Interoperable）** | 遵循组织级标准 | CloudEvents、Avro、组织命名规范 |
| **安全（Secure）** | 访问控制、脱敏、合规 | RBAC、列级加密、PII 标记 |

关于 Netflix Data Mesh 等混合架构案例，见 [2.8 混合架构案例研究](../02-场景驱动架构设计/02-08-混合架构案例.md)。该文档中的域化拆分与数据网格原则高度一致：把数据所有权与消息主题边界对齐，避免跨域直接访问数据库。

## 1.55.8 对比矩阵与落地建议

| 维度 | 数据契约（Data Contract） | 事件契约 | dbt 模型契约 | 数据网格 |
| --- | --- | --- | --- | --- |
| **关注点** | 数据集 schema/语义/SLA/质量 | 事件消息 schema/版本/主题 | 模型输出 schema 与约束 | 数据所有权与产品化 |
| **执行点** | 生产/消费边界、CI/CD | MQ Schema Registry、CI/CD | dbt 运行/建表时 | 组织治理与平台能力 |
| **主要工具** | Bitol、Soda、GE、dbt | AsyncAPI、Avro、Confluent Schema Registry | dbt | DataHub、自助平台、策略引擎 |
| **与 MQ 关系** | 可覆盖 topic 数据集 | 直接描述 MQ 消息 | 间接（MQ 数据入仓后） | MQ 是数据产品的传输与发现入口 |

### 落地建议

1. **从事件契约开始**：若企业已使用 Kafka/MQ，优先用 AsyncAPI + Avro 定义事件契约，见 [2.56 Spec-Driven 契约驱动开发体系](../02-场景驱动架构设计/02-56-Spec-Driven契约驱动开发体系.md)。
2. **扩展到数据契约**：在事件契约基础上，补充语义、SLA、质量规则，形成完整数据契约。
3. **在 dbt 中强制执行**：对数据仓库/湖仓中的模型启用 `contract.enforced: true`。
4. **用 Soda/GE 做持续质量监控**：把质量检查嵌入 CI/CD 与数据管道调度。
5. **按域组织数据产品**：结合数据网格原则，把 MQ topic、表、API 都作为域数据产品注册到数据目录。
