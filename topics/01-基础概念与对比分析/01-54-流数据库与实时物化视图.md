## 1.54.1 从流处理引擎到流数据库

传统流处理引擎（Flink、Kafka Streams）解决"如何计算"的问题，但通常需要额外搭建 serving 层（OLAP、Redis、PostgreSQL）才能被应用查询。流数据库（Streaming Database）则把"计算"与"服务"合二为一：

```text
┌─────────────────────────────────────────────────────────────────────┐
│                    流数据库 vs 传统分层架构                          │
└─────────────────────────────────────────────────────────────────────┘

传统分层：
  Kafka ──→ Flink ──→ PostgreSQL/Redis/OLAP ──→ 应用查询
  （传输）  （计算）        （serving 层）         （消费）

流数据库：
  Kafka ──→ RisingWave/Materialize ──→ 应用直接 SQL 查询物化视图
  （传输）        （计算 + serving 合一）
```

【论证】流数据库的核心价值不是替代 Flink 的复杂计算能力，而是把"实时聚合结果"直接作为可查询的数据产品，减少一个独立的 serving 层与数据同步链路。

## 1.54.2 实时物化视图与增量计算模型

### 三种计算模型对比

| 模型 | 原理 | 延迟 | 资源模式 | 典型代表 |
| --- | --- | --- | --- | --- |
| **批量重算** | 定时全量重跑 SQL | 分钟~小时 | 波峰计算 | 传统数仓 |
| **微批** | 小批量增量处理 | 秒~分钟 | 周期性调度 | Spark Structured Streaming |
| **增量物化视图** | 每条事件触发增量更新 | 毫秒~秒 | 持续计算 | RisingWave、Materialize、Flink SQL Materialized Table |

### 增量计算的关键概念

流数据库通常基于某种形式的 **differential computation / stream-to-changelog**：

- **输入流**：Kafka/Pulsar/CDC 等无界事件序列。
- **内部状态**：维护 operator 的中间结果（如 count、sum、join 状态）。
- **物化视图（Materialized View）**：把查询结果持久化，应用可直接读取。
- **补偿更新（Retraction/Correction）**：当迟到数据或 CDC delete 到达时，系统发出 `-` 记录修正之前的结果。

```text
输入事件                增量算子                物化视图
┌─────────┐           ┌─────────────┐          ┌─────────────┐
│ + A, 10 │  ───────→ │  SUM(amount)│  ──────→ │ key=A total=10 │
│ + A, 20 │  ───────→ │  +10, +20   │  ──────→ │ key=A total=30 │
│ - A, 10 │  ───────→ │  -10        │  ──────→ │ key=A total=20 │
└─────────┘           └─────────────┘          └─────────────┘
```

【定理】在 changelog 语义下，若每个输入事件都对应一个明确的 `+` 或 `-` 变更记录，则物化视图可保持与输入流在最终一致性意义下的等价。

## 1.54.3 RisingWave

RisingWave 是开源的云原生 SQL 流数据库，核心引擎用 Rust 编写，采用存算分离架构（Hummock 状态引擎 + 对象存储）。截至 2025-09 发布 2.6 版本，社区版采用 Apache 2.0 许可证。

### 架构特点

```text
┌─────────────────────────────────────────────────────────────┐
│                     RisingWave 架构                          │
└─────────────────────────────────────────────────────────────┘

  数据源层          计算层（无状态）           存储层（Hummock）
┌──────────┐      ┌─────────────────┐      ┌─────────────────┐
│ Kafka    │ ───→ │ Frontend /      │ ───→ │ S3 / GCS /      │
│ Pulsar   │      │ Compute Node    │      │ Azure Blob      │
│ CDC      │      │ （可弹性扩缩容）  │      │ （不可变 SSTable）│
└──────────┘      └─────────────────┘      └─────────────────┘
```

- **存算分离**：计算节点无状态，扩缩容无需状态迁移。
- **PostgreSQL 协议兼容**：应用可用标准 JDBC/PSQL 连接。
- **内置 Iceberg sink**：方便与湖仓集成。

### SQL 示例

```sql
-- RisingWave：从 Kafka 创建 source
CREATE SOURCE orders (
    order_id BIGINT,
    user_id BIGINT,
    amount DECIMAL(10,2),
    order_time TIMESTAMP
) WITH (
    connector = 'kafka',
    topic = 'orders',
    properties.bootstrap.server = 'kafka.internal:9092',
    scan.startup.mode = 'earliest'
) FORMAT PLAIN ENCODE JSON;

-- 创建实时物化视图
CREATE MATERIALIZED VIEW user_revenue AS
SELECT user_id,
       SUM(amount) AS total_amount,
       COUNT(*) AS order_count
FROM orders
GROUP BY user_id;

-- 应用直接查询
SELECT * FROM user_revenue WHERE user_id = 42;
```

### 开源协议与版本

- **社区版**：Apache 2.0，可自托管。
- **企业版**：包含额外治理、安全与云托管功能。
- **当前版本**：2.6（2025-09 发布）。

## 1.54.4 Materialize

Materialize 是另一款流数据库，基于 Timely Dataflow 与 Differential Dataflow，主打 SQL 物化视图与强一致性。其社区版采用 **BSL 1.1（Business Source License）**，每个版本在发布后 4 年转为 Apache 2.0。

### 架构特点

```text
┌─────────────────────────────────────────────────────────────┐
│                     Materialize 架构                         │
└─────────────────────────────────────────────────────────────┘

  Kafka / CDC / PostgreSQL
           │
           ▼
    ┌───────────────┐
    │  SQL 层        │
    │  (mzsql)       │
    └───────┬───────┘
            │
    ┌───────┴───────┐
    │ Differential  │
    │ Dataflow      │  ← 增量计算核心
    └───────┬───────┘
            │
    ┌───────┴───────┐
    │ 物化视图存储   │  ← 可直接 serving 查询
    └───────────────┘
```

### SQL 示例

```sql
-- Materialize：创建 source 与物化视图
CREATE SOURCE orders
FROM KAFKA CONNECTION kafka_conn (TOPIC 'orders')
FORMAT JSON;

CREATE MATERIALIZED VIEW user_revenue AS
SELECT user_id,
       SUM(amount::DECIMAL) AS total_amount,
       COUNT(*) AS order_count
FROM orders
GROUP BY user_id;

-- 直接查询
SELECT * FROM user_revenue WHERE user_id = 42;
```

### 许可与限制

- **社区版**：BSL 1.1，生产使用需注意许可证条款；部分企业场景需商业授权。
- **功能限制**：社区版在核心数/集群规模上可能存在上限，选型前应核对当前版本许可说明。
- **转为 Apache 2.0**：每个版本发布后 4 年自动转为 Apache 2.0。

## 1.54.5 ksqlDB 与 Flink SQL

### ksqlDB

ksqlDB 是 Confluent 推出的"Kafka 上的 SQL 数据库"，底层基于 Kafka Streams。它把 Kafka topic 抽象为 stream 或 table，支持 SQL 方式做过滤、聚合、join。

```sql
-- ksqlDB 示例
CREATE STREAM orders (
    order_id BIGINT KEY,
    user_id BIGINT,
    amount DECIMAL(10,2)
) WITH (
    KAFKA_TOPIC = 'orders',
    VALUE_FORMAT = 'AVRO'
);

CREATE TABLE user_revenue AS
SELECT user_id, SUM(amount) AS total
FROM orders
GROUP BY user_id
EMIT CHANGES;

-- 拉取查询
SELECT * FROM user_revenue WHERE user_id = 42;
```

- **许可证**：Confluent Community License（非 OSI 认定的开源许可证）。
- **耦合度**：只读 Kafka，深度绑定 Confluent 生态。
- **适用场景**：快速 SQL 探查、轻量流式聚合、已深度使用 Confluent Platform/Cloud 的企业。

### Flink SQL

Flink SQL 是 Apache Flink 的关系式接口，支持标准 SQL 语义与流批统一。

```sql
-- Flink SQL 示例
CREATE TABLE orders (
    order_id BIGINT,
    user_id BIGINT,
    amount DECIMAL(10,2),
    order_time TIMESTAMP(3),
    WATERMARK FOR order_time AS order_time - INTERVAL '30' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'kafka.internal:9092',
    'format' = 'json'
);

CREATE TABLE user_revenue (
    user_id BIGINT,
    total_amount DECIMAL(18,2),
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector' = 'jdbc',
    'url' = 'jdbc:postgresql://pg.internal:5432/analytics',
    'table-name' = 'user_revenue'
);

INSERT INTO user_revenue
SELECT user_id, SUM(amount)
FROM orders
GROUP BY user_id;
```

Flink 2.0 引入 **Materialized Tables** 概念，允许定义一个由查询与新鲜度目标驱动的表，进一步向"流数据库"体验靠拢。

## 1.54.6 与 MQ + Flink + OLAP 组合架构的取舍

企业在实时分析架构上通常面临两种选择：

| 方案 | 组成 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| **流数据库一体** | Kafka + RisingWave/Materialize | 链路短、SQL 直接查询、运维简单 | 复杂 CEP/大规模 join 能力弱于 Flink、锁定特定产品 | 实时看板、运营指标、风控特征 |
| **MQ + Flink + OLAP** | Kafka + Flink + StarRocks/Doris/ClickHouse | 复杂计算能力强、serving 层成熟、生态开放 | 链路长、数据一致性跨系统、运维复杂 | 复杂实时 ETL、大规模窗口、OLAP 深度分析 |

### 决策建议

```text
开始
 │
 ├─ 是否主要是"实时聚合 + 直接 serving 查询"？
 │    ├─ 是 ──→ 流数据库（RisingWave/Materialize/ksqlDB）
 │    └─ 否
 │
 ├─ 是否需要复杂事件处理、CEP、多流 join、大状态窗口？
 │    ├─ 是 ──→ MQ + Flink + OLAP
 │    └─ 否
 │
 ├─ 是否已深度使用 Confluent/Kafka 生态且只需 Kafka 源？
 │    ├─ 是 ──→ ksqlDB
 │    └─ 否
 │
 └─ 是否偏好开源 Apache 2.0 且希望存算分离？
      ├─ 是 ──→ RisingWave
      └─ 否 ──→ Materialize（评估 BSL 许可）
```

【论证】流数据库不是 Flink 的替代品，而是对"实时聚合 + 直接查询"这一高频模式的简化封装。对于需要复杂窗口、CEP、机器学习集成的场景，Flink 仍是更灵活的选择。

## 1.54.7 Sink 回写 MQ 的能力

流数据库不仅是 MQ 的 consumer，也常把计算结果写回 MQ，形成"读取-计算-再发布"的闭环：

```text
┌─────────────────────────────────────────────────────────────┐
│              流数据库 → MQ 回写闭环                          │
└─────────────────────────────────────────────────────────────┘

  Kafka source          RisingWave / Materialize         Kafka sink
┌──────────┐            ┌─────────────────────┐         ┌──────────┐
│ orders   │  ────────→ │ 物化视图 / 增量计算  │  ────→  │ alerts   │
│ payments │            │                     │         │ features │
│ users    │            │                     │         │ metrics  │
└──────────┘            └─────────────────────┘         └──────────┘
```

### RisingWave sink 到 Kafka 示例

```sql
CREATE SINK user_revenue_kafka
FROM user_revenue
WITH (
    connector = 'kafka',
    topic = 'user-revenue',
    properties.bootstrap.server = 'kafka.internal:9092'
) FORMAT PLAIN ENCODE JSON;
```

### Materialize sink 到 Kafka 示例

```sql
CREATE SINK user_revenue_kafka
FROM user_revenue
WITH (
    connector = 'kafka',
    topic = 'user-revenue'
) FORMAT JSON;
```

### 回写 MQ 的设计考量

- **changelog 语义**：确保下游消费者能理解 `+`/`-` 更新或 UPSERT 语义。
- **topic 分区策略**：按 key 分区以保证下游消费顺序。
- **背压处理**：sink 速率应匹配 MQ broker 吞吐，避免拖垮流数据库。
- **schema 治理**：建议配合 Schema Registry 使用 Avro/Protobuf。

## 1.54.8 对比矩阵与选型

| 维度 | RisingWave | Materialize | ksqlDB | Flink SQL |
| --- | --- | --- | --- | --- |
| **许可证** | Apache 2.0（社区版） | BSL 1.1（4 年后转 Apache 2.0） | Confluent Community License | Apache 2.0 |
| **部署形态** | 自托管 / 云托管 | 自托管 / 云托管 | Confluent Platform / Cloud | Flink 集群 / 托管服务 |
| **SQL 兼容性** | PostgreSQL 协议 | PostgreSQL 风格 | ksql 方言 | 标准 SQL + 流扩展 |
| **状态后端** | Hummock + 对象存储 | Differential Dataflow | Kafka Streams / RocksDB | RocksDB/ForSt |
| **输入源** | Kafka/Pulsar/CDC/文件 | Kafka/CDC/PostgreSQL | 仅 Kafka | 多源（Kafka/Pulsar/JDBC/文件） |
| **Sink 到 MQ** | 支持 | 支持 | 支持（Kafka topic） | 支持 |
| **复杂 CEP** | 较弱 | 中等 | 较弱 | 强 |
| **典型场景** | 实时看板、特征工程 | 实时 BI、强一致视图 | Kafka SQL 探查 | 复杂实时 ETL、湖仓入仓 |
| **运维复杂度** | 中低 | 中 | 中 | 高 |

### 选型建议

- **RisingWave**：希望 Apache 2.0、存算分离、PostgreSQL 兼容、低运维的实时分析场景。
- **Materialize**：需要强一致性物化视图、已有 PostgreSQL BI 工具链，且能接受 BSL 许可。
- **ksqlDB**：已使用 Confluent 生态，需求简单，团队熟悉 Kafka 主题模型。
- **Flink SQL**：计算逻辑复杂、需要与批处理统一、或对 vendor 锁定敏感的企业。
