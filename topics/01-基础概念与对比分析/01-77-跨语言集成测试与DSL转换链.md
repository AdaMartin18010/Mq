## 1.77.1 问题定义：多语言漂移

契约（contract.yaml）是唯一的，实现是五份的。漂移的三个典型来源【论证】：

1. **类型语义差**：同一 `int64` 在 JS 里是 Number（精度上限 2^53）、在 Python 里任意精度、在 Go 里 int64——金融金额字段跨语言必踩；
2. **可选字段处理**：proto3 optional 与 JSON null 与 Rust Option 的三方语义不完全等价；
3. **时间表示**：epoch 秒/毫秒/ISO8601/RFC3339 在生态间的默认差异（01-72 编码矩阵的跨语言面）。

后果：生产-消费跨语言时，序列化层"能解析"≠"语义一致"。**契约测试必须跨语言执行，单语言自测无法发现漂移**。

## 1.77.2 DSL 转换链的一致性验证

转换链：`contract.yaml →（生成器）→ {Python dataclass, TS interface, Go struct, Rust struct, C struct} →（序列化）→ 字节流 →（异语言反序列化）→ 对等实例`

验证方法（金样本法）【论证】：

```text
1. 金样本集：为每个场景包生成 20 条边界样本（Testing/fixtures/generators/ 已有 3 组，扩至 8 场景）
2. 正向环：语言 A 序列化 → 语言 B 反序列化 → 字段级断言（值+类型+可选性三查）
3. 矩阵执行：5 语言两两全配对（5×4=20 条有向边），每条边跑全部金样本
4. 失败归类：精度损失/时间偏移/可选性坍塌/编码差异 → 回写契约侧修复（加精度约束/统一时间格式）
```

工具落点：契约语义测试 tc-assert-check 扩展"金样本对账"模式（静态期）；E2 真实执行期由 Microcks contract test 对每语言客户端流量断言（06-行为验证层）。

**契约侧预防**（设计期）：contract.yaml 字段类型标注跨语言安全级：

```yaml
amount: { type: number, crosslang: safe }        # 全语言安全
traceId: { type: string }
bigCounter: { type: integer, crosslang: warn }   # JS 超 2^53 告警——生成器在 TS 侧输出 bigint
```

1. **静态期（已就绪）**：tc-assert-check 校验 8 场景契约完整性；contract-to-odcs 导出为语言生成器输入；

3. **实跑期（批次189 闭环，2026-11-21）**：`Testing/xlang/` harness 落地（5 语言 project+emit 客户端 + 两相 driver + ensure-lib），`--live` 由本机 5 语言工具链全配对实跑（原"多语言容器进 fixtures compose"方案由本机实跑替代），8 场景×20 有向边全 RC=0：相1 参考分歧 5 项（inventory.quantity=唯一 semantic：Node/Go 19 位奇数整数 float64 塌缩 10^18+7→10^18；余 4 项=repr 良性[整值 float .0 截断/Java 科学记数]）；相2 差异 88 行=repr_drift 80+precision_loss 8，其余分类全 0；registry TC-XLAN-A1~A4/B1~B2 → verified；证据 `results/2026-11-21/xlang-matrix/`；**设计含义回灌候选：金额/数量等大整数字段跨语言契约应建模为 string 或 ≤2^53-1 量纲（见 01-72 编码矩阵；随 L3 兑现批或知识批落地）**；
