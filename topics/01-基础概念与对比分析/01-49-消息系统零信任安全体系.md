## 1.49.1 零信任原则映射到消息

### 从边界模型到零信任模型

传统消息系统安全常以“内网可信”为前提：Broker 部署在 VPC 内部，客户端一旦进入网络即可获得较高权限。
零信任（Zero Trust）的核心是 **never trust, always verify**：无论客户端位于何处，每次连接、每次发布/订阅、每条消息敏感字段都必须经过显式验证与授权【论证】。

| 维度 | 边界安全模型 | 零信任安全模型 |
| ------ | -------------- | ---------------- |
| 信任假设 | 内网主机默认可信 | 任何主机默认不可信 |
| 认证位置 | 网络边界（防火墙/VPN） | 每次连接与每次操作 |
| 授权粒度 | 粗粒度（IP/子网） | 细粒度（身份、topic、动作、时间） |
| 凭证形态 | 长期密码/证书 | 短期 token、SVID、自动轮换 |
| 失效面 | 单点攻破即横向移动 | 按身份微分段，单点受损影响受限 |
| 审计要求 | 记录边界出入 | 记录每次认证、授权、数据访问 |

### broker/客户端/topic 三级验证

零信任在消息场景中拆成三级验证：

1. **Broker 身份验证**：客户端连接时验证 Broker 证书/签名，防止中间人伪装 Broker【定理】。
2. **客户端身份验证**：Broker 验证客户端身份，禁止匿名或仅依赖源 IP【定理】。
3. **Topic/队列级授权**：即使身份合法，也按最小权限检查对特定 topic/queue/命名空间的操作权限【论证】。

## 1.49.2 身份与认证深化

### Kafka：OIDC、OAUTHBEARER 与 delegation token

**SASL/OAUTHBEARER 与 KIP-768 OIDC 支持**:

Kafka 通过 SASL/OAUTHBEARER 支持 OAuth 2.0 bearer token 认证。KIP-255 最早定义该机制，但默认实现仅用于非生产测试，早期版本不对 JWT 签名/issuer/audience 做完整校验【论证】。
KIP-768 在 Kafka 3.1 引入内置 OIDC 支持：客户端从 IdP 获取 token，Broker 通过 JWKS 本地验证【论证】。

典型 Broker 配置（Kafka 3.1+）：

```properties
# server.properties
listeners=SASL_SSL://:9092
security.inter.broker.protocol=SASL_SSL
sasl.enabled.mechanisms=OAUTHBEARER
sasl.mechanism.inter.broker.protocol=OAUTHBEARER

# OIDC 配置
sasl.oauthbearer.jwks.endpoint.url=https://idp.example.com/.well-known/jwks.json
sasl.oauthbearer.expected.issuer=https://idp.example.com
sasl.oauthbearer.expected.audience=kafka-cluster-prod
sasl.oauthbearer.sub.claim.name=sub
```

Kafka 4.0 起要求通过 `org.apache.kafka.sasl.oauthbearer.allowed.urls` 显式放行 IdP 端点，防止 SSRF 风险【论证】。

**Delegation Token（委托令牌）**:

KIP-48 在 Kafka 1.1.0 引入 delegation token，作为 SASL/SSL 之外的轻量认证补充。
令牌是 Broker 与客户端间的共享密钥，适用于把工作分发给工作节点（如 Spark/Flink 连接 Kafka），避免在大量节点上分发 Kerberos keytab 或双向 SSL keystore【论证】。

```bash
# 创建 delegation token（需先以强身份认证）
kafka-delegation-tokens.sh --bootstrap-server localhost:9092 \
  --command-config admin-client.conf --create \
  --renewer-principal User:spark-worker

# 客户端使用 delegation token 的 JAAS 片段
KafkaClient {
  org.apache.kafka.common.security.scram.DelegationTokenLoginModule required
  tokenId="DT1"
  hmac="AAAA...";
};
```

### MQTT 5.0 增强认证

MQTT 5.0 在 CONNECT/CONNACK 之外引入 **AUTH 控制包（类型 15）**，支持多轮 challenge-response 认证流程【定理】。
该机制被称为 Enhanced Authentication，可容纳 SCRAM、OAUTHBEARER、GSSAPI/Kerberos、EXTERNAL 等 SASL 风格方案。

【定理】AUTH 包携带 `Authentication Method` 与 `Authentication Data` 两个属性：`Authentication Method` 标识方案（如 `SCRAM-SHA-256`），`Authentication Data` 承载 challenge/response 载荷；同一连接建立后还可通过 AUTH 包进行 **re-authentication**【定理】。

### NATS：JWT/NKey/account 层级

NATS 2.0+ 推荐基于 **operator → account → user** 三级层级与 **JWT + NKey** 的分布式身份模型：

- **Operator**：顶层信任锚，签名 account JWT。
- **Account**：业务/租户隔离单元，account JWT 描述账户权限与限制。
- **User**：隶属于 account，由 account 私钥签名的 user JWT 用于连接认证。
- **NKey**：基于 Ed25519 的公钥标识，用于 challenge-response 认证或签名 JWT。

`nsc` 工具管理该生命周期的完整流程：

```bash
# 1. 生成 operator
nsc generate operator --name MyOp --system-jwks-url https://jwks.example.com

# 2. 创建 account 并生成其 JWT
nsc add account --name Payments
nsc generate account --name Payments --output-file payments.jwt

# 3. 创建 user 并导出 credentials
nsc add user --account Payments --name payment-svc
nsc generate credentials --account Payments --name payment-svc > payment-svc.creds
```

NATS 服务器通过 `resolver` 拉取 account JWT，用户连接时出示 user JWT 或 NKey challenge 签名，天然支持多租户隔离与跨集群信任传播【论证】。

### RabbitMQ：OAuth 2.0/JWT 插件

RabbitMQ 提供 `rabbitmq_auth_backend_oauth2` 插件，允许客户端以 JWT-encoded OAuth 2.0 access token 作为凭证连接 AMQP/MQTT/STOMP。连接时通常将 token 放入密码字段，Broker 验证签名后将 JWT 中的 `scope` 映射为 RabbitMQ 权限（如 `rabbitmq.read:*/*`），实现按 vhost/queue/topic 的细粒度授权【论证】。

```ini
# rabbitmq.conf
auth_backends.1 = oauth2

auth_oauth2.issuer = https://idp.example.com
auth_oauth2.jwks_url = https://idp.example.com/.well-known/jwks.json
auth_oauth2.token_endpoint = https://idp.example.com/token

# scope 到权限的映射示例
auth_oauth2.scope_prefix = rabbitmq.
auth_oauth2.resource_server_id = rabbitmq
```

### 六系统认证机制矩阵

| 系统 | 传输层 | 用户名密码 | Token/JWT | OAuth/OIDC | 证书/mTLS | 增强/挑战响应 | 委托令牌 |
| ------ | -------- | ------------ | ----------- | ------------ | ----------- | --------------- | ---------- |
| **Kafka** | SSL/SASL_SSL | SASL/PLAIN/SCRAM | — | SASL/OAUTHBEARER + KIP-768 OIDC | 双向 TLS | SASL/GSSAPI | KIP-48 delegation token |
| **MQTT** | TLS | CONNECT 用户名密码 | — | 5.0 AUTH 承载 OAUTHBEARER | 客户端证书 | 5.0 AUTH challenge-response (SCRAM 等) | — |
| **NATS** | TLS | 用户名密码 | Token | JWT (account/user) | TLS + NKey | NKey challenge-response | — |
| **RabbitMQ** | TLS/AMQPS | PLAIN | — | OAuth 2.0 JWT 插件 | 客户端证书 | — | — |
| **Pulsar** | TLS | — | — | OAuth 2.0 插件 | TLS 插件 | SASL 插件 | — |
| **Redis Stream** | TLS | ACL 用户名密码 | — | — | — | — | — |

> 注：表格中的“—”表示非主要或官方未内置机制；具体版本支持需以官方文档为准。

## 1.49.3 工作负载身份：SPIFFE/SPIRE

### SVID 签发与两种形态

SPIFFE（Secure Production Identity Framework for Everyone）定义了工作负载身份标准：每个工作负载拥有唯一的 **SPIFFE ID**（形如 `spiffe://trust-domain/ns/prod/sa/payment-svc`），并通过 **SVID（SPIFFE Verifiable Identity Document）** 证明该身份【论证】。

SVID 有两种主要形态：

- **X.509-SVID**：标准 X.509 证书，SPIFFE ID 放在 Subject Alternative Name 的 URI 字段，用于 mTLS 双向认证【定理】。
- **JWT-SVID**：签名 JWT，`sub` 声明携带 SPIFFE ID，用于无法建立 mTLS 的应用层认证【定理】。

SPIRE 是 SPIFFE 的参考实现，通过节点代理（Node Agent）对工作负载进行 attestation（如 K8s pod 标签、服务账户、镜像摘要），并动态签发短生命周期 SVID（X.509-SVID 默认 TTL 约 1 小时，JWT-SVID 更短），自动轮换【论证】。

### 消息 Broker 的 SPIFFE 集成现状

截至 2026-11，**Apache Kafka 官方尚未提供内置 SPIFFE 认证插件**【论证】。常见落地方式包括：

1. **mTLS + 自定义 PrincipalBuilder**：Broker 要求客户端证书，证书 SAN URI 包含 SPIFFE ID，自定义 `principal.builder.class` 将 SPIFFE ID 映射为 Kafka principal。
2. **Sidecar/Proxy**：Envoy/Istio 等代理使用 SPIFFE 身份建立 mTLS，后端 Kafka 仅 sees 代理身份，授权需在代理层或结合 OAuth 完成。
3. **Kubernetes exec auth 插件**：社区有 `spiffe/k8s-spiffe-workload-jwt-exec-auth` 等工具，可为需要 Kafka 认证的客户端提供 JWT-SVID，但非 Kafka 官方插件【论证】。

### SPIFFE 与 mTLS 的关系

SPIFFE 解决“**我是谁**”，mTLS 解决“**通道双向可信**”，二者互补：

- 有 SPIFFE 无 mTLS：可用 JWT-SVID 做应用层认证，但传输可能被窃听。
- 有 mTLS 无 SPIFFE：可验证证书，但证书可能生命周期长、与基础设施身份解耦。
- **SPIFFE + mTLS**：X.509-SVID 作为 mTLS 客户端证书，身份由平台动态颁发与轮换，既保证双向认证又绑定到工作负载身份【论证】。

零信任消息架构推荐组合：传输层 mTLS（基于 X.509-SVID）+ 应用层 OAuth/JWT 或 ACL。

## 1.49.4 端到端消息加密

### 三层加密对比

消息系统的加密通常分三层，安全边界与责任主体不同：

| 加密层 | 保护目标 | 责任方 | 密钥管理 | 对 Broker 可见性 | 适用场景 |
| -------- | ---------- | -------- | ---------- | ------------------ | ---------- |
| **传输 TLS** | 网络传输中的数据 | 平台/运维 | TLS 证书/CA | 明文 | 所有生产连接 |
| **静态加密** | 磁盘/存储上的日志 | 云厂商/存储层 | 存储 KMS/磁盘加密 | 明文 | 云托管服务、磁盘加密 |
| **端到端 payload 加密** | 消息内容本身 | 应用/数据Owner | 应用层 KMS/DEK | 密文 | 敏感 PII、跨信任域 |

传输 TLS 与静态加密只能防“外部窃听”和“物理介质泄露”，Broker 本身仍可见消息明文。端到端 payload 加密才能在多租户或 SaaS Broker 场景下保证“Broker 不可读”【论证】。

### KMS 信封加密示例

端到端加密的典型模式是信封加密：用 KMS 保护数据加密密钥（DEK），DEK 加密消息 payload。示例如下（Python）：

```python
import json
import base64
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

# 伪代码：从 KMS 获取或生成 DEK，并用 KEK 加密后随消息传递
def encrypt_payload(plaintext: bytes, dek: bytes, aad: bytes) -> dict:
    aesgcm = AESGCM(dek)
    nonce = os.urandom(12)
    ciphertext = aesgcm.encrypt(nonce, plaintext, aad)
    return {
        "ciphertext": base64.b64encode(ciphertext).decode(),
        "nonce": base64.b64encode(nonce).decode(),
        "dek_encrypted": base64.b64encode(kms_encrypt(dek)).decode(),  # KEK 加密 DEK
        "aad": base64.b64encode(aad).decode()
    }

# 发送前将 envelope 作为消息 value
envelope = encrypt_payload(
    plaintext=b'{"user_id":"U123","phone":"138****"}',
    dek=kms_generate_data_key(),
    aad=b"orders.pii:2026-11-18T10:00:00Z"  # 绑定 topic 与时间，防重放
)
producer.send("orders.pii", value=json.dumps(envelope).encode())
```

生产环境应优先使用 KMS 服务（AWS KMS、HashiCorp Vault、Azure Key Vault 等）的 `GenerateDataKey` API，并对称密钥采用 AES-256-GCM，AAD 绑定 topic 与业务上下文【论证】。

### 字段级加密与 crypto-shredding

对于 GDPR/个保法合规，推荐使用**字段级加密**而非全消息加密：仅对 PII 字段加密，保留非敏感字段的可检索性。更进一步的 **crypto-shredding** 方案：每个数据主体使用独立 DEK，删除请求到来时销毁该 DEK，即可让历史密文永久不可解，而无需物理删除追加日志中的消息。详见 [02-50 消息数据合规设计](../02-场景驱动架构设计/02-50-消息数据合规设计.md)【论证】。

### 密钥轮换与死信队列的加密残留

密钥轮换是必要操作，但会带来两类风险：

1. **旧 DEK 残留**：若旧 DEK 未安全归档或销毁，被攻破后仍可解密历史消息。建议保留旧 DEK 只读状态并设过期销毁策略。
2. **死信队列（DLQ）残留**：加密消息消费失败后进入 DLQ，若 DEK 已轮换，DLQ 中的消息可能无法被正常重处理。设计时应确保 DLQ 消费路径保留访问历史 DEK 的能力，或在进入 DLQ 前解密并重加密为当前 DEK【论证】。

## 1.49.5 供应链安全

### 制品签名：Sigstore/Cosign 与社区实践

Sigstore/Cosign 提供基于 OIDC 的 keyless 签名与验证，适合容器镜像、二进制与 SBOM。但在消息系统主仓库中：

- **Apache Kafka**：官方发布沿用 Apache 基金会标准流程，提供 GPG 分离签名（`.asc`）与 SHA512 校验和，尚未切换到 Cosign/Sigstore【论证】。验证命令：

```bash
# Apache Kafka 官方发布验证流程（GPG + SHA512）
wget https://downloads.apache.org/kafka/4.0.0/kafka_2.13-4.0.0.tgz{,.asc,.sha512}
wget https://downloads.apache.org/kafka/4.0.0/KEYS
gpg --import KEYS
gpg --verify kafka_2.13-4.0.0.tgz.asc kafka_2.13-4.0.0.tgz
gpg --print-md SHA512 kafka_2.13-4.0.0.tgz | diff - kafka_2.13-4.0.0.tgz.sha512
```

- **Strimzi Kafka Operator**：从 0.38.0 起，容器镜像使用 Cosign keyless 签名，可通过 `--certificate-oidc-issuer` 与 `--certificate-identity-regexp` 验证【论证】。
- **NATS**：截至 2026-11，官方 GitHub release 主要提供 tarball 与 checksum，未广泛采用 Cosign；第三方生态（如 `mcp-nats`）已开始使用 Cosign 签名容器镜像【论证】。

因此，企业自建供应链 gates 时，应**按实际制品类型选择验证工具**：ASF tarballs 用 GPG+SHA512，OCI 镜像可用 Cosign，不要盲目统一。

### SBOM 生成与镜像扫描

SBOM（Software Bill of Materials）是供应链审计的基础。消息系统的容器镜像应在 CI 中生成 SBOM 并签名：

```bash
# 生成 CycloneDX/SPDX SBOM
syft packages myrepo/kafka-client:${CI_COMMIT_SHA} -o cyclonedx-json > kafka-client.sbom.json

# 使用 Cosign 对 SBOM 做 attestation
cosign attest --type cyclonedx-json \
  --predicate kafka-client.sbom.json \
  --yes myrepo/kafka-client@${DIGEST}

# 部署前镜像漏洞扫描
trivy image --severity HIGH,CRITICAL --exit-code 1 \
  myrepo/kafka-client:${CI_COMMIT_SHA}
```

镜像扫描与 SBOM 验证应与 [03-37 持续集成部署指南](../03-架构与运维实践/03-37-持续集成部署指南.md) 中的 CI/CD gates 结合，在 HIGH/CRITICAL CVE 未修复时阻断部署。

### 插件生态的供应链风险

消息系统的插件生态是供应链攻击高发面：

- **Kafka Connect**：社区 connector 来源多样，部分 Maven 仓库依赖老旧库。应只使用经过签名/校验的插件包，并在隔离容器/低权限账号中运行 Connect worker。
- **RabbitMQ 插件**：启用 `rabbitmq-plugins` 前确认插件来源，避免启用未经验证的第三方插件。
- **Schema Registry / 序列化库**：schema 解析器与 Avro/Protobuf 库也可能成为反序列化漏洞入口，需纳入 SBOM 与 CVE 扫描范围。

建议对插件实行**签名验证 + 最小启用集 + 网络 egress 限制**三重控制。

## 1.49.6 零信任网络

### 微分段与端口白名单

即使有了强身份认证，网络层仍需微分段以限制横向移动：

| 组件 | 数据端口 | 管理端口 | 允许源 | 备注 |
| ------ | ---------- | ---------- | -------- | ------ |
| Kafka Broker | 9093 (SASL_SSL) | 9094 (Controller)、JMX | 业务网段 | 关闭 9092 明文端口 |
| NATS Server | 4222 (TLS) | 8222 (HTTP 监控) | 业务网段 / 监控网段 | 8222 禁止公网 |
| RabbitMQ | 5671 (AMQPS) | 15672 (管理界面) | 业务网段 | 管理界面仅管理区 |
| MQTT Broker | 8883 (MQTTS) | 18083/8083 | 设备网段 | 禁止 1883 公网暴露 |

示例防火墙规则：

```bash
# Kafka SASL_SSL 端口仅允许业务网段
iptables -A INPUT -p tcp --dport 9093 -s 10.0.0.0/8 -j ACCEPT
iptables -A INPUT -p tcp --dport 9093 -j DROP

# NATS 监控端口仅允许监控节点
iptables -A INPUT -p tcp --dport 8222 -s 10.0.1.10/32 -j ACCEPT
iptables -A INPUT -p tcp --dport 8222 -j DROP
```

### 出口管控与固定身份

在零信任网络中，客户端到 Broker 的出口流量也应具备“固定身份”：

- 使用 egress gateway 或 sidecar，确保所有到 Broker 的连接来自已知工作负载身份。
- 在 K8s 中结合 NetworkPolicy 与 SPIFFE/SPIRE，限制只有带特定 SPIFFE ID 的 pod 能访问 Broker Service。
- Broker 端结合 SASL/OAUTHBEARER 或 mTLS，将网络身份与应用身份对齐。

### 审计日志集中化

零信任要求“每次访问都可审计”。消息系统的审计日志应至少覆盖：

- 认证事件：成功/失败登录、token 刷新、证书过期。
- 授权事件：ACL/权限拒绝、topic 创建与删除、权限变更。
- 数据访问事件：生产/消费/订阅操作（对高敏感 topic 开启）。
- 配置变更：Broker 配置热更新、账户/用户变更。

审计日志应集中到 SIEM/Loki/ELK，保留 ≥90 天，并配置异常检测告警（如认证失败突增、越权访问）。具体落地见 [03-32 安全审计指南](../03-架构与运维实践/03-32-安全审计指南.md)。
