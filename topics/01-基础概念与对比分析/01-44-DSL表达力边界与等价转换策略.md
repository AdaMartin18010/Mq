## 1.44.1 为什么关注 DSL 表达力边界

事件驱动架构进入工程化阶段后，团队往往希望用一份机器可读的契约把“事件长什么样、走哪条通道、谁能消费”全部说清。AsyncAPI 是当前最活跃的这类 DSL（Domain Specific Language）。但如果把动态路由谓词、流处理逻辑、 Saga 状态机也塞进 AsyncAPI，就会遇到两类问题：

1. **规范不支持**：AsyncAPI 的语义范围是“事件 API 的接口描述”，不是“事件处理程序的实现描述”【定理：AsyncAPI 规范对象定义】。
2. **治理失控**：用 `x-` 字段写伪代码、多份 sidecar 文档不同步，会让契约从“事实来源”变成“过期注释”。

本文先给出 AsyncAPI 3.1 各构件的表达力清单，再归纳四类规范无法承载的语义，最后提供等价转换策略与决策树，帮助团队在“契约里声明什么”与“代码/平台里实现什么”之间划清边界。

## 1.44.2 AsyncAPI 3.1 构件表达力清单

【定理】AsyncAPI 3.1.0 的文档结构由 [AsyncAPI Specification 3.1.0](https://www.asyncapi.com/docs/reference/specification/v3.1.0) 定义，当前稳定版发布于 2026-01-31。下表逐项标注规范原生可表达与不可表达的语义。

| 构件 | 可表达语义 | 不可表达语义 |
| ---- | ---------- | ------------ |
| `info` / `id` | API 元数据、应用标识、版本、责任人 | 业务Owner审批流、契约SLA |
| `servers` | 协议/主机/端口/安全方案/协议版本/变量替换 | 运行时发现、健康检查端点、连接池调参 |
| `channels` | 通道地址（topic/queue/subject）、参数模板、可发送的消息集合 | 动态路由谓词、通道创建时机、分片策略 |
| `operations` | `send`/`receive` 方向、关联通道、可用消息、安全、回复地址 | 条件分支、顺序约束、幂等实现细节 |
| `messages` | payload schema、headers、contentType、name/title、examples | 消息过滤规则、字段派生逻辑、enrichment来源 |
| `components` | 复用 schema/server/channel/operation/message/securityScheme/correlationId/bindings/traits 等 | 组件之间的运行时依赖关系 |
| `traits` | 对 operation/message 的公共属性做 JSON Merge Patch 式复用 | trait 应用条件、按环境选择 trait 的逻辑 |
| `correlationId` | 用运行时表达式定位关联字段（header/payload） | 关联字段生成算法、分布式追踪采样策略 |
| `bindings` | 协议特定参数（Kafka partition/replica、MQTT QoS/retain 等） | 未纳入官方 binding 的 broker 特性、背压/TTL/DLQ 策略 |
| `security` / `securitySchemes` | 认证类型（apiKey/oauth2/sasl/X509 等）与作用域 | 动态授权、凭据轮换、审计日志 |
| `externalDocs` | 指向外部文档的绝对 URL 与描述 | 文档版本与契约版本的同步规则 |

几点关键事实：

- 【定理】`channels` 的 `address` 可包含 `{参数}` 表达式，但表达式仅用于地址模板，不能表达“当 payload.amount > 1000 时路由到 X”这类谓词语义。
- 【定理】`correlationId.location` 只支持 `$message.header#...` 或 `$message.payload#...` 的运行时表达式，不能声明如何生成该 ID。
- 【论证】Bindings 是独立演进的：Kafka binding 当前版本 0.5.0，MQTT binding 0.2.0；每个 binding 的字段由各自规范定义，核心解析器对未知绑定“忽略”处理。因此背压、TTL、DLQ 等语义在官方 binding 未覆盖时即落入规范空白区。

## 1.44.3 DSL 表达不了的四类语义

### 1.44.3.1 行为逻辑

**定义**：消息到达后“做什么”的判定规则，包括动态路由谓词、消息过滤、条件分支、多播/广播策略。

**为什么规范不支持**：AsyncAPI `operation.action` 只有 `send`/`receive`，`channel.address` 是静态模板。规范的设计目标是描述“接口契约”，而非“处理逻辑”【定理：Operation Object 字段】。

**工程后果**：

- 若把路由规则写成 `x-routing-rule`，工具链无法校验其语法与语义，契约沦为注释。
- 路由逻辑散落在多份 sidecar 文档中，变更时难以评估影响面。

### 1.44.3.2 数据派生

**定义**：窗口聚合（tumbling/sliding/session window）、流 join、字段 enrichment、CEP 模式匹配。

**为什么规范不支持**：AsyncAPI `message.payload` 只能声明消息体的静态 schema，不能声明“把 A 事件 5 分钟窗口聚合后与 B 事件 join”这类时态/关系语义。

**工程后果**：

- 数据派生逻辑若写入契约，会导致 schema 与计算拓扑耦合，schema 演化时被迫重写业务规则。
- 消费者无法从契约判断事件是“原始事件”还是“派生事件”，易把派生语义误当成源事实。

### 1.44.3.3 非功能语义不完整

**定义**：背压策略、重试退避、TTL、死信队列策略、最大并发、隔离级别。

**为什么规范不支持（绑定覆盖不全）**：

| 非功能语义 | Kafka binding 0.5.0 | MQTT binding 0.2.0 | AsyncAPI 核心 |
| ---------- | ------------------- | ------------------ | ------------- |
| 背压 / 消费速率限制 | 无 | 无 | 无 |
| 生产者重试退避 | 无（`acks`/`retries` 不在 binding） | 无 | 无 |
| 消息 TTL | `retention.ms` 是 topic 级保留，非消息 TTL | `messageExpiryInterval`（MQTT 5） | 无 |
| 死信队列策略 | 无 | 无 | 无 |
| 最大重试次数 | 无 | 无 | 无 |
| 并发/线程模型 | 无 | 无 | 无 |

- Kafka binding 0.5.0 可声明 `partitions`、`replicas`、`topicConfiguration` 等 topic 元数据，以及 `groupId`、`clientId`、`key`、schema registry 位置，但不包含生产者调优参数【定理：AsyncAPI Kafka Binding】。
- MQTT binding 0.2.0 可声明 `qos`、`retain`、`messageExpiryInterval`（MQTT 5），但没有“重试退避”或“DLQ”字段【定理：AsyncAPI MQTT Binding】。

**工程后果**：

- 团队常在 `x-` 里各自约定重试参数，导致同一事件在不同消费者上行为不一致。
- 缺少统一表达使运行时治理（如统一退避、限流）难以通过契约驱动。

### 1.44.3.4 跨契约编排

**定义**：Saga 步骤序列、流程状态机、人工审批节点、长时间等待、补偿路径。

**为什么规范不支持**：AsyncAPI 描述的是单条消息/单个操作，而 Saga/编排需要跨多条消息、多服务、多状态的时序与事务语义。这类语义属于工作流 DSL（如 Open Workflow Specification）或代码级 durable execution（如 Temporal）的范畴。

**工程后果**：

- 在 AsyncAPI 里画“第1步→第2步→补偿”会丢失状态机语义，也无法表达超时/补偿/人工任务。
- 若把编排伪代码放进 `x-saga-steps`，工具无法执行、无法校验，最终仍要落到 Temporal/Camunda/Open Workflow 等引擎。

## 1.44.4 等价转换策略矩阵

对每类不可表达语义，下表给出五种等价手段及适用边界。

| 不可表达语义 | 推荐等价手段 | 治理要点 |
| ------------ | ------------ | -------- |
| 行为逻辑（动态路由/过滤） | 外部 `$ref` 指向 sidecar 规则文档；或下沉到框架/代码 | sidecar 文档纳入版本库，与 AsyncAPI 同步评审 |
| 数据派生（窗口/join/enrichment） | 下沉到流处理框架/代码；用 `x-processing-hint` 仅作提示 | 禁止在 DSL 里写 SQL/伪代码 |
| 非功能语义（背压/重试/TTL/DLQ） | `x-` 扩展 + 注册表；或平台声明式配置（KEDA/Spring Cloud Stream） | 统一命名空间、Spectral lint 强制取值范围 |
| 跨契约编排（Saga/状态机） | 多规范混合文档（AsyncAPI + Open Workflow）；或工作流引擎代码 | 编排文档与事件契约分开版本化，互链引用 |

### a. Specification Extensions（x- 扩展）

【定理】AsyncAPI 允许以 `x-` 前缀扩展几乎所有对象，字段名必须匹配 `^x-[\w\d\.\x2d_]+$`，值可以是 null、primitive、array 或 object【定理：Specification Extensions】。这是规范内建的“逃生舱口”，但必须配治理规则才能避免失控。

治理规则（与 [2.54](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md) 的命名规范衔接）：

- 命名空间：`x-<org>.<team>.<purpose>`，例如 `x-acme.platform.retry`。
- 注册表：在仓库 `extensions/` 下登记每个 `x-` 字段的语义、版本、Owner。
- Lint：用 Spectral 强制 `x-` 字段必须来自注册表白名单。

```yaml
# asyncapi.yaml（节选）
operations:
  receiveOrderCreated:
    action: receive
    channel:
      $ref: '#/channels/orderCreated'
    x-acme.platform.retry:
      maxAttempts: 3
      backoff: exponential
      initialIntervalMs: 500
      dlq: orders.created.dlq
```

### b. 外部 $ref 组合

把无法承载的语义拆成 sidecar 文档，通过 `$ref` 显式关联。sidecar 文档与主契约同仓库、同版本、同 CI。

```yaml
# asyncapi.yaml（节选）
channels:
  orderCreated:
    address: orders.created.v1
    x-acme.platform.routingRules:
      $ref: './routing-rules.yaml#/routingRules/orderCreated'
```

```yaml
# routing-rules.yaml
routingRules:
  orderCreated:
    - name: highValueRoute
      condition: "payload.amount > 10000"
      targetChannel: orders.created.vip.v1
      description: 高金额订单进入 VIP 处理通道
    - name: defaultRoute
      condition: "true"
      targetChannel: orders.created.v1
```

### c. 多规范混合文档

当事件契约需要与同步 API、工作流编排协同表达时，可把 AsyncAPI、OpenAPI、Open Workflow Specification 打包在同一文档目录，并通过 `externalDocs` 或元数据互链。

```text
order-service/
├── asyncapi.yaml          # 事件契约
├── openapi.yaml           # 同步查询/命令 API
└── workflow/
    └── order-approval.yaml # Open Workflow 编排定义
```

```yaml
# asyncapi.yaml（节选）
asyncapi: '3.1.0'
info:
  title: Order Service Events
  version: 1.0.0
  x-acme.platform.relatedDocuments:
    openapi: './openapi.yaml'
    workflow: './workflow/order-approval.yaml'

channels:
  orderCreated:
    address: orders.created.v1
    externalDocs:
      description: 订单审批工作流定义
      url: './workflow/order-approval.yaml'
```

Open Workflow Specification 当前版本为 1.1.0，其 DSL 直接支持 `listen`、`switch`、`fork`、`try/catch`、`emit` 等状态，适合把跨契约编排从 AsyncAPI 中剥离【论证：Open Workflow Specification 官网】。

### d. 下沉到框架/代码

当语义与运行时实现强相关、且变更频繁时，最佳等价手段是让 DSL 只描述“存在什么事件/通道”，具体行为由框架或代码承载。

**Spring Cloud Stream binding 示例**：

```yaml
# application.yml
spring:
  cloud:
    stream:
      bindings:
        orderCreated-in-0:
          destination: orders.created.v1
          group: order-service
          consumer:
            max-attempts: 3
            back-off-initial-interval: 500
            back-off-multiplier: 2.0
            default-retryable: false
        orderCreated-dlq-out-0:
          destination: orders.created.dlq
```

**Kafka Streams topology 代码入口示例**：

```java
// OrderTopology.java —— DSL 引用该文件路径即可
StreamsBuilder builder = new StreamsBuilder();
KStream<String, OrderCreated> orders = builder
    .stream("orders.created.v1", Consumed.with(Serdes.String(), orderCreatedSerde));

orders
    .filter((k, v) -> v.amount() > 10000)
    .leftJoin(customerTable, OrderEnriched::new)
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .aggregate(OrderSummary::new, OrderSummary::add)
    .toStream()
    .to("orders.summary.v1");
```

在 AsyncAPI 中，只需声明事件输入/输出契约，并用 `x-acme.platform.topology` 指向代码入口（`src/main/java/com/example/orders/OrderTopology.java`）。

### e. 平台声明式配置

对背压、并发、自动扩缩容等语义，可用 Kubernetes/KEDA 等平台的声明式资源表达，并在 AsyncAPI 的 `x-` 扩展中引用该资源。

```yaml
# keda-scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-consumer
spec:
  scaleTargetRef:
    name: order-consumer
  minReplicaCount: 2
  maxReplicaCount: 100
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: order-service
        topic: orders.created.v1
        lagThreshold: "100"
```

```yaml
# asyncapi.yaml（节选）
operations:
  receiveOrderCreated:
    action: receive
    channel:
      $ref: '#/channels/orderCreated'
    x-acme.platform.scaling:
      $ref: './keda-scaledobject.yaml'
```

KEDA 当前是 CNCF Graduated 项目，支持 Kafka、RabbitMQ、NATS、MQTT、SQS 等数十种 scaler【论证：KEDA 官网】，适合把“按事件负载扩缩容”这一非功能语义从 AsyncAPI 中剥离。

## 1.44.5 “进 DSL 还是进代码”决策树

按以下四个维度综合判断：

| 维度 | 倾向进 DSL | 倾向进代码/平台 |
| ---- | ---------- | --------------- |
| 契约稳定性 | 高（schema/通道长期不变） | 低（规则周级变更） |
| 消费者数量 | 多（>3 个团队/服务） | 少（1-2 个内部消费者） |
| 治理需求 | 高（需统一重试/DLQ/命名） | 低（团队自治即可） |
| 变更频率 | 低（季度/半年） | 高（周/迭代） |

## 1.44.6 替代/互补事件 DSL 对照表

WebSearch 核实的其他事件/流契约 DSL 如下。它们各有所长，但 AsyncAPI 在“事件发现、多协议绑定、文档/代码生成”上仍是最均衡的选择。

| DSL/技术 | 事件契约能力 | 主要优势 | 主要局限 | 何时仍选 AsyncAPI |
| -------- | ------------ | -------- | -------- | ----------------- |
| **Smithy eventStream** | 通过 `@streaming union` + `@eventHeader`/`@eventPayload` 描述事件流；协议无关，由代码生成实现【定理：Smithy Streaming 规范】 | 与 AWS SDK 生态深度整合；强类型生成 | 需要 Smithy 工具链；社区事件发现/目录生态弱于 AsyncAPI | 需要跨 AWS 服务的事件流代码生成时 Smithy 更合适；通用事件治理仍选 AsyncAPI |
| **Protobuf/Buf service streaming** | `rpc StreamOrders(...) returns (stream Order)` 描述 gRPC 服务端/客户端/双向流；强类型 schema | 高性能二进制序列化；广泛的语言支持 | 没有原生 pub/sub channel 语义；事件发现依赖额外工具 | 事件系统需要多协议（Kafka/MQTT/NATS）描述时 AsyncAPI 更合适 |
| **TypeSpec Events/Streams** | `@events` 装饰器把 union 标记为事件集合；`@data`/`@contentType` 描述 payload【定理：TypeSpec Events 库】 | 与 Azure API 生态整合；可生成 OpenAPI/AsyncAPI | 较新，生态与社区示例仍在建设中 | 以 Azure 服务为主时可用 TypeSpec 生成 AsyncAPI；通用场景直接写 AsyncAPI |
| **GraphQL subscription** | `subscription { actorUpdated { ... } }` 描述客户端订阅字段级事件流【定理：GraphQL 规范 Subscription 章节】 | 前端友好；客户端可精确选择字段 | 传输协议（WebSocket/SSE）需额外约定；缺少消息 Broker 语义 | 需要面向前端的事件订阅 API 时 GraphQL 更合适；后端异步事件总线仍选 AsyncAPI |
| **Ballerina 服务类型** | `service` + `stream` 可返回 SSE 或监听 Kafka/NATS 事件【论证：Ballerina SSE 示例】 | 语言级事件/网络原语；类型安全 | 绑定特定语言；不直接作为跨组织契约格式 | Ballerina 内部实现可引用 AsyncAPI 契约；跨团队契约仍用 AsyncAPI |

选型结论：

- 若目标是**跨团队/跨协议的事件契约、发现、文档与代码生成** → AsyncAPI 仍是首选。
- 若已深度使用 **AWS SDK / gRPC / Azure API** → 可用 Smithy/Protobuf/TypeSpec 描述事件流，再导出或映射到 AsyncAPI 用于事件目录。
- 若面向**前端实时订阅** → GraphQL subscription 是有效补充，但不替代 AsyncAPI 对后端通道的描述。

## 1.44.7 反模式

| 反模式 | 症状 | 正确做法 |
| ------ | ---- | -------- |
| **在 DSL 里写程序逻辑** | `x-sql-filter`、`x-routing-code` 字段里塞伪代码或 SQL | 过滤/路由逻辑下沉到流处理代码；DSL 只声明输入输出通道 |
| **x- 扩展无注册表失控** | 同一组织出现 `x-retry`、`x-acme.retry`、`x-PlatformRetry` 等多种写法 | 建立 `x-<org>.<domain>.<purpose>` 命名规范与注册表，Spectral 强制白名单 |
| **多份 sidecar 文档不同步** | `routing-rules.yaml` 已改，`asyncapi.yaml` 仍引用旧版本 | sidecar 与主契约同仓库、同 PR、同 CI diff；引用使用相对路径 `$ref` |
| **把编排状态机塞进 AsyncAPI** | `x-saga-steps` 描述 A→B→补偿，但无超时/人工任务语义 | 使用 Open Workflow / Temporal / Camunda 等专用编排 DSL |
| **binding 版本不声明** | Kafka binding 字段在不同工具中解释不一致 | 每个 binding 必须写 `bindingVersion`（Spectral 强制） |
