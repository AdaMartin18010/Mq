## 1.31.1 生态全景

消息队列（Kafka、Pulsar、RabbitMQ、NATS、MQTT Broker、Redis Stream）从来不是孤立的"管道"。在现代数据架构中，它们位于一条完整数据链路的中心位置：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                         数据集成与流处理生态链路                          │
└─────────────────────────────────────────────────────────────────────────┘

  数据源层                CDC / 集成层              消息队列层
┌──────────┐            ┌─────────────┐          ┌─────────────────┐
│ PostgreSQL │            │             │          │                 │
│ MySQL     │ ────────→  │  Debezium   │ ───────→ │   Apache Kafka  │
│ MongoDB   │  WAL/日志    │  Kafka Connect│  主题/分区 │   Apache Pulsar │
│ Oracle    │            │  CDC Source │          │   RabbitMQ/NATS │
│ SaaS/CRM  │            │  Connector  │          │   Redis Stream  │
└──────────┘            └─────────────┘          └────────┬────────┘
                                                          │
                              ┌───────────────────────────┼───────────────────────────┐
                              │                           │                           │
                              ▼                           ▼                           ▼
                        ┌───────────┐              ┌─────────────┐              ┌──────────────┐
                        │ 流处理层   │              │  流式湖仓层  │              │  应用消费层   │
                        │ Kafka     │              │ Apache      │              │ 微服务/实时   │
                        │ Streams   │              │ Iceberg     │              │ 推荐/风控     │
                        │ Flink     │              │ Delta Lake  │              │ 事件驱动架构  │
                        │ ksqlDB    │              │ Hudi        │              │              │
                        │ RisingWave│              │ S3/对象存储  │              │              │
                        └─────┬─────┘              └──────┬──────┘              └──────────────┘
                              │                           │
                              └───────────┬───────────────┘
                                          ▼
                                    ┌─────────────┐
                                    │ 分析/AI 层   │
                                    │ Spark/Flink  │
                                    │ Trino/Athena │
                                    │ SageMaker/   │
                                    │ Databricks   │
                                    └─────────────┘
```

这条链路的核心价值在于：

1. **解耦生产与消费**：数据库只负责事务写入，MQ 负责事件分发，流处理负责计算，湖仓负责分析。
2. **统一事件总线**：一份 CDC 数据可以同时供给实时处理、历史回放、审计合规、AI 训练多个下游。
3. **增量优先**：从批处理 ETL 转向持续流动的 Change Data Capture（CDC），显著降低数据新鲜度延迟。

## 1.31.2 CDC 与 Debezium

### CDC 的三种实现机制

CDC（Change Data Capture，变更数据捕获）是 MQ 生态的上游入口。常见实现分为三类：

| 机制 | 原理 | 优点 | 缺点 | 典型场景 |
| ------ | ------ | ------ | ------ | ---------- |
| **日志型 CDC** | 读取数据库事务日志（WAL、binlog、oplog） | 低延迟、对业务库压力小、能捕获 DELETE | 需数据库开启逻辑复制/归档 | Debezium、Flink CDC |
| **查询型 CDC** | 周期轮询表，通过时间戳/自增 ID 识别变更 | 实现简单、不依赖数据库特性 | 延迟高、无法捕获 DELETE、对源库有查询压力 | 简单同步、遗留系统 |
| **触发器 CDC** | 通过数据库触发器把变更写入审计表 | 数据库无关、可精确控制 | 影响写入性能、维护成本高 | 企业级 ETL 工具早期方案 |

**生产环境首选日志型 CDC**。Debezium 作为 Apache 孵化的开源 CDC 平台，几乎已成为基于 Kafka 的 CDC 事实标准。

### Debezium 支持的数据库

截至 Debezium 稳定版文档，官方提供以下 source connector（部分处于孵化状态）：

- 稳定可用：MongoDB、MariaDB、MySQL、PostgreSQL、SQL Server、Oracle、Db2、Cassandra、CockroachDB
- 孵化中：Vitess、Spanner、Informix、YashanDB、Ingres、Milvus

### Debezium PostgreSQL Connector 配置示例

以下是一个典型的 Debezium PostgreSQL source connector 配置，注册到 Kafka Connect 后可把 `orders` 库的变更流写入 Kafka 主题：

```json
{
  "name": "orders-postgres-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "tasks.max": "1",
    "database.hostname": "postgres.internal",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/secrets/db.properties:password}",
    "database.dbname": "orders",
    "database.server.name": "orders-db",
    "topic.prefix": "orders-db",
    "plugin.name": "pgoutput",
    "publication.autocreate.mode": "filtered",
    "table.include.list": "public.customers,public.orders",
    "snapshot.mode": "initial",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "key.converter.schemas.enable": "false",
    "value.converter.schemas.enable": "false"
  }
}
```

关键参数说明：

- `plugin.name`: PostgreSQL 逻辑解码插件，常用 `pgoutput`（PostgreSQL 10+ 内置）。
- `publication.autocreate.mode`: 是否自动创建 publication，`filtered` 只发布 `table.include.list` 指定的表。
- `snapshot.mode`: 启动时是否做全量快照，`initial` 表示无偏移时先快照再流式捕获。
- `topic.prefix`: 生成主题名的前缀，最终主题形如 `orders-db.public.orders`。

### Outbox 模式与 Debezium 的关系

微服务中常见的"双写问题"：业务数据写入数据库与发送事件到 MQ 是两个独立操作，无法保证原子性。Outbox 模式的解决思路是：

1. 业务事务中把事件写入数据库内的 `outbox` 表。
2. 事务提交后，Debezium 捕获 `outbox` 表的变更。
3. 通过 Debezium 的 **Outbox Event Router SMT** 把 outbox 行路由为 Kafka 消息。

```json
{
  "name": "outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.server.name": "order-service",
    "table.include.list": "public.outbox_events",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregate_type",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.payload": "payload",
    "transforms.outbox.table.field.event.payload.id": "id",
    "transforms.outbox.table.expand.json.payload": "true"
  }
}
```

这样每条 outbox 记录会按 `aggregate_type` 路由到对应主题（如 `outbox.event.order`），`aggregate_id` 作为消息 key，保证同一聚合的事件顺序。

## 1.31.3 Kafka Connect 与集成生态

### Kafka Connect 架构

Kafka Connect 是 Kafka 生态的集成框架，负责在 Kafka 与外部系统之间可靠地导入/导出数据。核心概念：

- **Worker**：运行 connector 任务的进程，分为 standalone 与 distributed 模式。
- **Connector**：描述数据源/目标的插件，分为 Source Connector（入 Kafka）和 Sink Connector（出 Kafka）。
- **Task**：Connector 拆分的并行单元，每个 task 消费/生产一个分区子集。
- **Converter**：把 Kafka 消息序列化/反序列化为特定格式（JSON、Avro、Protobuf）。
- **Transformation（SMT）**：在数据进入/离开 Kafka 前做轻量转换。
- **Dead Letter Queue（DLQ）**：处理无法转换或投递的"毒消息"。

```text
┌────────────────────────────────────────────────────────────┐
│                    Kafka Connect Worker                     │
│  ┌─────────────┐    ┌─────────────┐    ┌────────────────┐  │
│  │ Source Task │    │ Source Task │    │   Sink Task    │  │
│  │  (JDBC CDC) │    │  (Debezium) │    │ (S3/Iceberg)   │  │
│  └──────┬──────┘    └──────┬──────┘    └───────┬────────┘  │
│         │                  │                    │          │
│         └──────────────────┼────────────────────┘          │
│                            ▼                               │
│                      ┌─────────────┐                       │
│                      │  Kafka Cluster                       │
│                      │  (topics)    │                       │
│                      └─────────────┘                       │
└────────────────────────────────────────────────────────────┘
```

### 常用 Connector 表格

| 类型 | Connector | 典型用途 | 备注 |
| ------ | ----------- | ---------- | ------ |
| **Source** | Debezium PostgreSQL/MySQL/MongoDB | 数据库 CDC | 基于 WAL/binlog/oplog，低延迟 |
| **Source** | JDBC Source Connector | 查询型同步 | 适合无 CDC 能力的旧数据库 |
| **Source** | MQTT Connector | IoT 设备入 Kafka | 常与 HiveMQ/Eclipse Mosquitto 配合 |
| **Source** | Salesforce/ServiceNow Connector | SaaS 数据入湖 | 多为 Confluent 商业 connector |
| **Sink** | S3 Sink Connector | 对象存储归档 | 常与 Iceberg/Delta 转换层配合 |
| **Sink** | Snowflake/BigQuery/Redshift Sink | 数仓集成 | 支持流式或微批写入 |
| **Sink** | Elasticsearch/OpenSearch Sink | 搜索索引更新 | 实时同步文档 |
| **Sink** | RabbitMQ/NATS/Pulsar Sink | 跨 MQ 桥接 | 用于异构消息系统互通 |

Confluent 官方把原来的 **Confluent Hub** 升级为 **Confluent Marketplace**，集中提供经认证的 connector、转换器与 partner 集成。截至公开资料，生态内可用 connector 数量超过 120/200+（含 partner 认证与社区方案），企业级场景可直接部署托管 connector。

### Kafka Connect REST API 配置示例

以下通过 Kafka Connect REST API 注册一个 S3 Sink Connector，把 Kafka 主题数据批量写入 S3：

```bash
# 注册 S3 Sink Connector
curl -X POST http://localhost:8083/connectors \
  -H "Content-Type: application/json" \
  -d '{
    "name": "orders-s3-sink",
    "config": {
      "connector.class": "io.confluent.connect.s3.S3SinkConnector",
      "tasks.max": "4",
      "topics": "orders-db.public.orders",
      "s3.region": "us-east-1",
      "s3.bucket.name": "company-raw-data",
      "s3.part.size": "5242880",
      "flush.size": "10000",
      "rotate.interval.ms": "60000",
      "storage.class": "io.confluent.connect.s3.storage.S3Storage",
      "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
      "partitioner.class": "io.confluent.connect.storage.partitioner.TimeBasedPartitioner",
      "partition.duration.ms": "3600000",
      "path.format": "'\''year'=YYYY/'month'=MM/'day'=dd/'hour'=HH'\''",
      "locale": "en-US",
      "timezone": "UTC",
      "schema.compatibility": "NONE"
    }
  }'
```

实际生产建议：

- 对延迟敏感的 CDC 场景，优先使用 Debezium Source + Kafka 主题 + 下游实时消费者。
- 对归档/分析场景，可用 S3 Sink + 外部 Spark/Flink 作业转为 Iceberg/Delta。
- 需要 Schema 治理时，配合 Schema Registry 使用 Avro/Protobuf converter。

## 1.31.4 流式湖仓

### Kafka → Iceberg 的两种路径

把 Kafka 数据落入开放表格式（Iceberg/Delta/Hudi）有两种典型方式：

| 路径 | 组成 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| **自建管道** | Kafka Connect S3 Sink → 对象存储 → Spark/Flink 写入 Iceberg | 灵活、可控、成本低 | 需要维护 schema 映射、compaction、catalog 同步 |
| **托管 Tableflow** | Confluent Tableflow 一键把 Kafka topic 物化为 Iceberg 表 | 零运维、自动 schema 演化、自动 compaction | 商业功能、云厂商锁定、自定义转换受限 |

### Confluent Tableflow

Confluent Tableflow 是 Confluent Cloud 提供的托管能力，宣称"一键把 Kafka topic 物化为 Apache Iceberg 表"。其主要能力包括：

- 自动完成 schematization、类型转换、schema evolution。
- 自动发布 Iceberg 元数据到 catalog（如 AWS Glue Data Catalog）。
- 自动 CDC 流物化、compaction、表维护。
- 支持 Iceberg 与 Delta Lake 两种开放表格式，并集成 Databricks Unity Catalog。

下游可直接用 Athena、Redshift、EMR/Spark、Flink、Trino、Snowflake 等查询这些 Iceberg 表，实现"operational estate（Kafka 流）"与"analytical estate（湖仓）"的统一。

### Pulsar 的湖仓集成

Apache Pulsar 的分层存储（Tiered Storage）自 2.2.0 起即可把 BookKeeper 中的冷数据卸载到 S3/GCS/Azure Blob 等对象存储。StreamNative 在此基础上推出了 **Lakehouse Tiered Storage**（Private Preview），直接把 Pulsar 冷数据卸载为 Iceberg/Delta Lake/Hudi 格式。

与传统分层存储相比，Lakehouse Tiered Storage 的差异：

| 特性 | 传统 Tiered Storage | Lakehouse Tiered Storage |
| ------ | ------------------- | -------------------------- |
| 存储格式 | Pulsar 专有格式 | Iceberg / Delta / Hudi 开放格式 |
| 外部引擎查询 | 需通过 Pulsar broker 读取 | Spark/Flink/Trino 可直接读取对象存储 |
| Schema 信息 | 卸载数据不带 schema | 带 schema，支持 schema evolution |
| 存储成本 | 较低 | 更低（测试称可再降约 5x） |
| 使用方式 | 消息 API 透明访问 | 消息 API + 表/批 API 双模式访问 |

### Pulsar 分层存储配置示例

在 `broker.conf` 中开启分层存储并配置卸载策略：

```properties
# 启用分层存储
managedLedgerOffloadDriver=aws-s3

# S3 配置
s3ManagedLedgerOffloadBucket=company-pulsar-offload
s3ManagedLedgerOffloadRegion=us-east-1
s3ManagedLedgerOffloadServiceEndpoint=https://s3.us-east-1.amazonaws.com

# 卸载触发策略：按大小或时间
managedLedgerOffloadThresholdInBytes=10737418240
managedLedgerOffloadDeletionLagMs=14400000

# 读取缓存与预取
managedLedgerOffloadReadBufferSizeInBytes=1048576
```

> 注意：Pulsar 的分层存储属于"冷数据卸载"，主要解决长期保留成本；Lakehouse Tiered Storage 才是直接把 Pulsar 与 Iceberg/Delta 生态打通的进阶方案。

## 1.31.5 流处理技术选型

MQ 下游最常见的四类流处理技术定位差异明显：

| 维度 | Kafka Streams | Apache Flink | ksqlDB | RisingWave / Materialize |
| ------ | --------------- | -------------- | -------- | -------------------------- |
| **编程接口** | Java/Scala DSL | Java/Scala/Python/SQL | SQL（Kafka 专用） | SQL |
| **部署形态** | 嵌入应用进程 | 独立集群/YARN/K8s | Confluent 组件/独立 | 独立服务/云托管 |
| **状态存储** | 本地 RocksDB + changelog topic | RocksDB/ForSt/远程状态 | 内嵌在 ksqlDB 中 | 自研存算分离状态层 |
| **端到端延迟** | 毫秒~秒级 | 毫秒~秒级 | 毫秒~秒级 | 毫秒~秒级 |
| **Exactly-once** | 支持 | 支持（checkpoint + savepoint） | 支持 | 支持 |
| **SQL 支持** | 无原生 SQL | Flink SQL | 专属 SQL | 标准 SQL 兼容度高 |
| **与 MQ 关系** | 只读 Kafka | 多源（Kafka/Pulsar/RabbitMQ 等） | 只读 Kafka | 多源（Kafka/Pulsar/CDC 等） |
| **典型场景** | 事件驱动微服务、有状态聚合 | 复杂事件处理、大规模实时 ETL | 快速 SQL 探查、流式物化视图 | 实时物化视图、流数据库应用 |
| **运维复杂度** | 低（随应用一起部署） | 高（需管理 checkpoint、状态） | 中 | 中低（云托管更低） |

### 选型建议

- **Kafka Streams**：团队已使用 Java/Scala，且处理逻辑与 Kafka 强绑定、希望把流处理作为微服务的一部分随应用一起部署时优先选择。
- **Apache Flink**：需要复杂窗口、CEP、多源 join、大规模状态、精确一次语义时首选。Flink 2.0 进一步推动了状态与存储分离（ForSt、Disaggregated State），在云原生环境更具弹性。
- **ksqlDB**：业务分析师或数据工程师希望快速用 SQL 在 Kafka 主题上做流式聚合、过滤、物化视图，且深度绑定 Confluent/Kafka 生态时适用。社区活跃度在 Confluent 收购后有所变化，选型前需确认版本支持。
- **RisingWave / Materialize**：希望把流处理当作"流数据库"使用，用 SQL 创建物化视图并直接 serving 查询，适合实时看板、风控特征、运营指标等场景。RisingWave 还内置了 Iceberg compaction 能力，与湖仓集成更紧密。
