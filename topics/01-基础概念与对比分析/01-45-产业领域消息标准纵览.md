## 1.45.1 为什么产业标准与事件契约需要打通

企业事件驱动架构（EDA）跨越组织边界时，必须同时回答两个问题：

1. **业务语义**：事件描述的是哪个产业对象、处于什么生命周期状态？
2. **技术契约**：事件如何在 Kafka、MQTT、NATS 等消息中间件之间传输？

产业标准（ISO 20022、FHIR、EPCIS、OpenADR）解决第一层；CloudEvents/AsyncAPI 解决第二层。二者打通后，企业可在保持行业合规与互操作的同时，避免被单一 MQ 厂商的私有格式锁定。

## 1.45.2 金融：ISO 20022

### 标准权威来源与版本现状

ISO 20022 由国际标准化组织（ISO）与 SWIFT 共同维护，是当前跨境支付、证券交易、现金管理的事实标准。其元模型与报文定义由 [ISO 20022 注册库](https://www.iso20022.org/) 统一发布，支持 XML（MX）与 JSON 两种语法。【定理】

截至 2026-11 核实到的关键版本事实：

| 系统/项目 | 状态 | 来源说明 |
| ---- | ---- | ---- |
| SWIFT CBPR+ | 2025-11 结束 MT/MX 共存，强制 ISO 20022 | SWIFT 官方发布与行业报道 |
| TARGET2 / EURO1 | 2023-03 完成迁移 | ECB / EBA Clearing 公告 |
| CHAPS（英国） | 2023-06 上线 | Bank of England |
| CHIPS（美国） | 2024-04 完成迁移 | The Clearing House |
| Fedwire Funds | 2025-03 起支持；2026-11-16 结构化地址最终强制 | Federal Reserve / ValidateFin |
| FedNow | 2023-07 上线即原生 ISO 20022（pacs.008 / pacs.004） | Federal Reserve |
| TIPS | 已原生 ISO 20022 | ECB |

### 消息/事件模型核心

ISO 20022 采用“业务组件→报文元素→报文”三层元模型。常见报文族：

| 报文族 | 业务含义 | 典型报文 | 事件化场景 |
| ---- | ---- | ---- | ---- |
| **pacs** | Payments Clearing and Settlement | pacs.008（贷记转账）、pacs.002（状态报告） | 支付状态变更事件 |
| **pain** | Payments Initiation | pain.001（客户贷记转账发起） | 发起指令事件 |
| **camt** | Cash Management | camt.053（对账单） | 账户余额/交易入账事件 |
| **auth** | Authorisation | auth.024/025（授权请求/响应） | 授权结果事件 |
| **seev/semt** | Securities | seev.039/040（公司行为通知/取消） | 证券生命周期事件 |

### 契约化路径：支付状态事件化

将 ISO 20022 报文映射到 CloudEvents + AsyncAPI 时，保留原始报文引用并提炼业务事件：

```yaml
asyncapi: '3.0.0'
info:
  title: Payment Status Events
  version: 1.0.0
channels:
  paymentStatusChanged:
    address: payments.status.changed.v1
    messages:
      paymentStatusChangedMsg:
        name: PaymentStatusChanged
        contentType: application/cloudevents+json
        payload:
          $ref: '#/components/schemas/PaymentStatusChangedEvent'
components:
  schemas:
    PaymentStatusChangedEvent:
      type: object
      required: [specversion, type, source, id, time, data]
      properties:
        specversion: { type: string, enum: ['1.0'] }
        type:        { type: string, enum: [iso20022.payments.status.changed.v1] }
        source:      { type: string, example: 'swift/cbpr+/pacs.002' }
        id:          { type: string, format: uuid }
        time:        { type: string, format: date-time }
        data:
          type: object
          required: [originalMsgId, statusCode]
          properties:
            originalMsgId: { type: string }
            statusCode:    { type: string, enum: [ACCP, RJCT, PDNG, ACSC] }
            statusReason:  { type: string }
            iso20022Raw:   { type: string, description: '原始 MX/XML 或 JSON 报文引用/哈希' }
```

映射要点：`type` 建议 `iso20022.<businessArea>.<verb>.v<N>`，与 [2.54](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md) 对齐；`id`/`time` 取自 `MsgId`/`CreDtTm`；`statusCode` 优先使用 ISO 20022 标准代码。

### 选型注意事项

- **MX vs JSON**：银行间清算仍要求 MX；内部微服务事件可优先 JSON。
- **版本治理**：报文版本通过 `xmlns` 与标识中的版本号控制（如 `pacs.008.001.10`）。事件契约应显式声明兼容版本。

## 1.45.3 医疗：FHIR 订阅与事件

### 标准权威来源与版本现状

FHIR 由 HL7 International 维护，是当前医疗数据交换的核心标准。R5（5.0.0）于 2023-03-26 作为 STU 发布；HL7 官方产品页将其列为当前发布版本。【定理：[HL7 FHIR R5 Product Brief](https://www.hl7.org/implement/standards/product_brief.cfm?product_id=491)】

| 版本 | 状态 | 关键差异 |
| ---- | ---- | ---- |
| R4（4.0.1，2019-10） | 广泛监管引用与生产部署 | 支持 Subscription，但 `SubscriptionTopic` 为 R4B/R5 新增概念 |
| R4B（4.3.0，2022-05） | 过渡版本 | 引入 `SubscriptionTopic` 与 topic-based 订阅的 backport 机制 |
| R5（5.0.0，2023-03） | 当前发布版本；STU 状态 | 原生 `SubscriptionTopic` 资源 |
| R6 | 草案投票阶段 | 非稳定发布，不建议新建项目直接采用 |

### 消息/事件模型核心

【定理】FHIR R5 定义 `SubscriptionTopic` 资源声明“何时产生事件”，并通过 `Subscription` 资源配置“如何投递事件”。核心通道类型：

| 通道 | 机制 | 适用场景 |
| ---- | ---- | ---- |
| **rest-hook** | 服务端向客户端 HTTPS endpoint POST 事件包 | 服务器到服务器 |
| **websocket** | 客户端建立 WebSocket，服务端推送通知 | 浏览器/移动端实时场景 |
| **email** | 邮件通知 | 人工工作流、告警 |
| **messaging** | 通过 FHIR Messaging 协议投递 | 兼容传统 FHIR 消息系统 |
| **custom** | 扩展通道（Kafka、MQTT、NATS 等需自行实现） | 事件总线集成 |

`SubscriptionTopic` 通过 `resourceTrigger` 与 `eventTrigger` 定义触发条件。

### 契约化路径：临床事件 CloudEvents 化

将 FHIR 订阅事件映射到 CloudEvents 时，把 `SubscriptionTopic.url` 作为 `type`，`Patient/<id>` 等作为 `subject`：

```json
{
  "specversion": "1.0",
  "type": "org.hl7.fhir.subscriptiontopic.patient-birth.v1",
  "source": "https://fhir.example.com/R5",
  "id": "sub-notification-7a8b9c0d",
  "time": "2026-11-18T08:15:00Z",
  "datacontenttype": "application/fhir+json",
  "dataschema": "https://hl7.org/fhir/R5/patient.html",
  "subject": "Patient/PAT-2026-001",
  "data": {
    "resourceType": "Bundle",
    "type": "subscription-notification",
    "entry": [{
      "resource": {
        "resourceType": "SubscriptionStatus",
        "status": "active",
        "type": "event-notification",
        "eventsSinceSubscriptionStart": "42",
        "notificationEvent": [{
          "eventNumber": "42",
          "timestamp": "2026-11-18T08:15:00Z",
          "focus": { "reference": "Patient/PAT-2026-001" }
        }]
      }
    }]
  }
}
```

R4B backport 机制允许在 R4 环境中使用 `SubscriptionTopic`，但需通过 [FHIR Subscriptions Backport IG](https://build.fhir.org/ig/HL7/fhir-subscription-backport-ig/) 实现。

### 选型注意事项

- **PHI/合规**：医疗事件负载几乎必然包含 PHI，必须与 [1.34](01-34-消息系统许可证与选型合规分析.md) 中的 HIPAA/GDPR 要求对齐。建议事件体加密、通道 TLS 1.2+、订阅权限按资源级 scope 控制。
- **资源版本化**：FHIR 资源支持 `_history`，事件应携带资源版本引用。

## 1.45.4 物流与供应链：EPCIS 2.0

### 标准权威来源与版本现状

EPCIS（Electronic Product Code Information Services）是 GS1 制定的全球供应链事件共享标准，回答“什么产品、何时、何地、为什么、如何”发生状态变化。配套标准 CBV（Core Business Vocabulary）定义业务步骤、处置状态、原因代码等共享词汇。

【定理】EPCIS 2.0 与 CBV 2.0 均于 2022-06 由 GS1 批准发布；EPCIS 2.0 新增 JSON/JSON-LD 语法、REST API 绑定与传感器数据支持。来源：[GS1 EPCIS](https://ref.gs1.org/standards/epcis/)、[GS1 CBV](https://ref.gs1.org/standards/cbv/)。

### 消息/事件模型核心

EPCIS 2.0 定义四类核心事件：

| 事件类型 | 语义 | 典型场景 |
| ---- | ---- | ---- |
| **ObjectEvent** | 单个对象的状态变化 | 扫描、观察、销毁 |
| **AssociationEvent** | 对象之间的聚合/解聚 | 托盘装箱、拆箱 |
| **TransactionEvent** | 对象参与交易/流程 | 订单、发货、收货 |
| **TransformationEvent** | 输入对象转化为输出对象 | 生产、混合、包装 |

每个事件包含五个维度：What（`epcList` 等）、When（`eventTime`）、Where（`readPoint`/`bizLocation`）、Why（`bizStep`/`disposition`）、How（`sourceList`/`destinationList`、`sensorElementList`）。

### 契约化路径：追溯事件流

将 EPCIS 2.0 JSON-LD 映射到 Kafka + CloudEvents：

```json
{
  "specversion": "1.0",
  "type": "gs1.epcis.objectevent.shipping.v1",
  "source": "https://epcis.gs1.example.com/capture",
  "id": "urn:uuid:123e4567-e89b-12d3-a456-426614174000",
  "time": "2026-11-18T10:00:00Z",
  "datacontenttype": "application/ld+json",
  "dataschema": "https://ref.gs1.org/standards/epcis/epcis-schema.json",
  "subject": "urn:epc:id:sgtin:9521141.012345.12345",
  "data": {
    "@context": ["https://ref.gs1.org/standards/epcis/2.0.0/epcis-context.jsonld"],
    "type": "ObjectEvent",
    "eventTime": "2026-11-18T10:00:00Z",
    "eventTimeZoneOffset": "+08:00",
    "eventID": "urn:uuid:123e4567-e89b-12d3-a456-426614174000",
    "epcList": ["urn:epc:id:sgtin:9521141.012345.12345"],
    "action": "OBSERVE",
    "bizStep": "https://ref.gs1.org/cbv/BizStep-shipping",
    "disposition": "https://ref.gs1.org/cbv/Disp-in_transit",
    "readPoint": {"id": "urn:epc:id:sgln:9521141.00001.0"},
    "bizTransactionList": [
      {"type": "https://ref.gs1.org/cbv/BTT-po", "bizTransaction": "urn:epcglobal:cbv:bt:9521141:PO-12345"}
    ]
  }
}
```

设计要点：`type` 使用 `gs1.epcis.<eventType>.<bizStep>.v<N>`；`subject` 使用 EPC URI（如 SGTIN）；Kafka `key` 建议采用 `subject` 中的 EPC，保证同一物流单元的事件顺序。

### 选型注意事项

- **XML vs JSON-LD**：EPCIS 1.x 以 XML 为主；2.0 推荐 JSON-LD，但供应链伙伴间需提前协商 `@context` 版本。
- **CBV 扩展**：企业自定义业务步骤需向 GS1 注册或在 `http://` 私有命名空间下声明，避免与标准 CBV 冲突。

## 1.45.5 能源：OpenADR 3.0

### 标准权威来源与版本现状

OpenADR（Open Automated Demand Response）由 OpenADR Alliance 维护，是电力需求响应（DR）与分布式能源资源（DER）管理的开放标准。OpenADR 3.0 于 2023-11 发布，采用 RESTful API + JSON 替代 2.0 时代的 SOAP/XML；规范以 OpenAPI YAML 作为 normative reference。【定理：[OpenADR 3.0 官方页面](https://www.openadr.org/openadr-3-0)】

| 版本 | 状态 | 说明 |
| ---- | ---- | ---- |
| OpenADR 2.0a/2.0b | 成熟部署 | 2.0b 为当前主流认证版本 |
| OpenADR 3.0 | 2023-11 发布；2025-04 首批产品通过 3.0 认证 | REST/JSON、VTN/VEN 角色保留 |
| OpenADR 3.1 | 2026 年前后已有社区实现 | 与 3.0 不保证向后兼容，需以 Alliance 官方声明为准 |

### 消息/事件模型核心

OpenADR 3.0 保留 VTN（Virtual Top Node，服务端）/ VEN（Virtual End Node，客户端）模型，核心对象：

| 对象 | 作用 | 事件化视角 |
| ---- | ---- | ---- |
| **Program** | 定义 DR 项目规则与参与条款 | 项目注册/更新事件 |
| **Event** | VTN 发布的 DR 信号，含时间区间与目标 | DR 事件 |
| **Signal** | Event 内的具体信号（价格、负荷削减、温室强度等） | 信号变化事件 |
| **Report** | VEN 向 VTN 上报的遥测/基线/状态数据 | 报告提交事件 |
| **Subscription** | VEN 订阅 Event/Report 变更的回调机制 | 订阅生命周期事件 |
| **Resource** | VEN 侧可调度的资产（EV、电池、暖通） | 资源注册/能力事件 |

### 契约化路径：DR 事件与能源物联网桥接

将 OpenADR 3.0 Event 映射到 MQTT/Kafka 事件契约：

```yaml
asyncapi: '3.0.0'
info:
  title: OpenADR 3.0 Bridge Events
  version: 1.0.0
channels:
  demandResponseEvent:
    address: energy.dr.event.v1
    messages:
      drEventMsg:
        name: DemandResponseEvent
        contentType: application/json
        payload:
          $ref: '#/components/schemas/DemandResponseEvent'
components:
  schemas:
    DemandResponseEvent:
      type: object
      required: [eventID, programID, eventName, intervals, targets]
      properties:
        eventID:   { type: string, format: uuid }
        programID: { type: string }
        eventName: { type: string }
        priority:  { type: integer }
        intervals:
          type: array
          items:
            type: object
            required: [start, duration, signalPayload]
            properties:
              start: { type: string, format: date-time }
              duration: { type: string, description: ISO 8601 duration }
              signalPayload:
                type: object
                required: [signalName, signalType, currentValue]
                properties:
                  signalName: { type: string, enum: [LOAD_CONTROL, PRICE, GHG, SETPOINT] }
                  signalType: { type: string, enum: [level, price, setpoint] }
                  currentValue: { type: number }
        targets:
          type: array
          items:
            type: object
            properties:
              type: { type: string, enum: [RESOURCE, GROUP, VEN] }
              value: { type: string }
```

桥接要点：VTN 侧将 OpenADR Event 推送到 Kafka/MQTT topic；`signalName` 优先使用 OpenADR 标准枚举；报告数据可反向由 VEN 发到 `energy.dr.report.v1` topic。

### 选型注意事项

- **实时性**：OpenADR 3.0 支持价格信号、负荷控制等分钟/小时级事件；能源物联网边缘常通过 MQTT 5.0 下发信号，参见 [1.16 MQTT-5.0新特性深度分析](01-16-MQTT-5.0新特性深度分析.md)。
- **认证与合规**：参与电力市场的需求响应项目通常要求 Alliance 认证；自研桥接器需通过官方测试套件。

## 1.45.6 跨域契约化共性模式

### 四步转换法

无论哪个产业域，将领域标准映射到 CloudEvents/AsyncAPI DSL 都可遵循：

```text
领域词汇表 -> event type 目录 -> payload schema -> 治理注册(catalog/registry)
```

1. **领域词汇表→标准术语表**：梳理 ISO 20022 代码、FHIR profile、EPCIS CBV、OpenADR signal type 等权威术语。
2. **event type 目录**：按 `域.实体.动词.vN` 命名（参见 [2.54](../02-场景驱动架构设计/02-54-事件契约模板库与命名规范.md)）。
3. **payload schema**：JSON Schema / Avro / Protobuf，显式引用领域标准 XSD/StructureDefinition/JSON-LD context 版本。
4. **治理注册**：在 Event Catalog 或 Schema Registry 注册，绑定所有者、兼容性规则、退役时间。

### 领域标准特有陷阱表

| 产业域 | 陷阱 | 规避建议 |
| ---- | ---- | ---- |
| **金融 ISO 20022** | 报文版本漂移（pacs.008.001.08 vs .10） | 契约中显式声明兼容版本；升级时按清算系统 deadline 双写 |
| **医疗 FHIR** | R4/R4B/R5 资源结构与 Subscription 语义差异 | 新建系统优先 R5；遗留 R4 系统通过 backport IG 或独立适配器兼容 |
| **物流 EPCIS** | JSON-LD `@context` 版本不一致导致解析失败 | 契约中固定 `@context` URL；变更时走 breaking change 流程 |
| **能源 OpenADR** | 3.0/3.1 不保证向后兼容；认证测试与自研实现差异 | 采购 Alliance 认证产品；桥接代码通过官方 test harness |
