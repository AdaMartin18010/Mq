## 1.29.1 趋势背景：从本地磁盘到对象存储

Kafka 在 2011 年诞生于数据中心场景，其设计假设是：

1. 机架间流量几乎免费；
2. 本地磁盘是最廉价的持久化介质。

这两个假设在公有云中恰好反转：

- **跨 AZ 流量计费**：AWS、GCP、Azure 对跨可用区出站流量按 GiB 收费，典型约 $0.02/GiB。Kafka 的 ISR 三倍副本机制意味着每条消息可能在 AZ 之间复制多次，生产者和消费者与 leader 不在同一 AZ 时还会产生额外读取流量。业界估算，优化良好的云 Kafka 账单中 **~80% 来自跨 AZ 网络费用**[^warpstream-diskless]。
- **块存储昂贵**：以 AWS gp2/gp3 类 EBS 为例，有效成本约 $0.10/GiB·月，且为吞吐和延迟通常保留 40% 以上空闲容量；而 S3 Standard 单副本约 $0.023/GiB·月，且已由对象存储自身完成多 AZ 复制。**对象存储每 GiB·月成本约为块存储的 1/30**[^warpstream-diskless]。
- **弹性需求**：云原生业务需要秒级扩缩容。Kafka 的 Shared-Nothing 架构在扩容时必须做分区重分配（reassignment），数据量大的情况下可持续数小时甚至数十小时。

因此 2023–2026 年出现一条清晰主线：**把持久化卸载到对象存储（S3 / GCS / Azure Blob）**，让计算层尽量无状态。代表路径包括：

- **Kafka 分层存储（KIP-405）**：保留本地热盘 + 异步转储对象存储；
- **Kafka Diskless Topics（KIP-1150）**：在原有 Kafka 集群内新增一种完全基于对象存储的 topic 类型；
- **WarpStream**：完全无磁盘的 Kafka 协议兼容系统，所有数据直写 S3；
- **AutoMQ**：将 Kafka 存储层替换为 S3Stream，对象存储为主、WAL 为辅；
- **Pulsar 分层存储**：将 BookKeeper 中的老 ledger 卸载到 S3；
- **Confluent Tableflow**：把 Kafka topic 物化为 Iceberg / Delta Lake 表，打通流与湖仓。

> 注意：Pulsar 的存算分离架构（1.12 节）与 Kafka 分层存储已在文档其他章节覆盖。本文聚焦 "以 S3 为持久化主存储 / 无磁盘 Kafka" 这一更激进的趋势，并补充已有章节未展开的系统。

## 1.29.2 架构谱系：五种 S3 化路径

下表按 "主存储所在位置"、"计算层状态"、"延迟特征"、"成本模型" 五个维度对比当前主流方案。Kafka 分层存储与 Pulsar 分层存储作为已有技术路线列入，以便与 WarpStream / AutoMQ / Tableflow 对齐。

| 方案 | 主数据落点 | 计算层状态 | 跨 AZ 复制 | 典型 produce 延迟 | 成本模型要点 |
| --- | --- | --- | --- | --- | --- |
| **Apache Kafka + KIP-405 分层存储** | 本地盘（热）+ S3（冷） | 有状态 Broker | 完整 ISR 跨 AZ 复制 | 数 ms | 保留 EBS/本地盘成本；冷数据省存储费 |
| **Kafka Diskless Topics（KIP-1150）** | 对象存储 | 经典 Broker 仍持有元数据/内部 topic | topic 级消除 | 数十–数百 ms | 仍需维护经典 Kafka 集群；部分特性回退到本地盘 |
| **WarpStream** | 对象存储（S3 / GCS / Azure Blob） | 无状态 Agent | 完全消除 | 33 ms（Lightning Topics）/ 105 ms（S3 Express）/ 250 ms（默认）[^warpstream-diskless] | 按未压缩写入量 + 集群分钟数 + 存储量；无 per-core/partition 费用 |
| **AutoMQ** | 对象存储为主，WAL 为辅 | 无状态 Broker | 由云存储服务原生多 AZ 替代 | 个位数 ms（FSx WAL）/ 数十 ms（S3 WAL）[^automq-fsx] | 对象存储费 + 少量 WAL 存储费；开源版仅 S3 WAL |
| **Confluent Tableflow** | 对象存储（Iceberg / Delta Lake 表） | 托管服务 | 取决于底层集群 | ~5 min 表新鲜度[^confluent-tableflow] | 与 Confluent Cloud 计费绑定；省去自建 ETL/Connect 链路 |
| **Pulsar 分层存储** | BookKeeper（热）+ S3/GCS/OSS（冷） | Broker 无状态，Bookie 有状态 | BookKeeper 复制仍存在 | 热数据 ms 级，冷数据受对象存储影响 | 长期 backlog 场景显著降低存储 |

进一步从 "是否真正无磁盘" 的角度细分：

| 类型 | 代表 | 是否完全无本地盘 | 数据路径特征 | 适用场景 |
| --- | --- | --- | --- | --- |
| **Tiered（分层）** | Kafka KIP-405、Pulsar Tiered Storage | 否 | 先写本地/BookKeeper，再异步 offload | 冷热分明、长期保留 |
| **Disk-lite / WAL 混合** | AutoMQ、Redpanda Cloud Topics | 部分 | WAL 缓冲后落对象存储，WAL 可用 EBS/对象存储 | 需要比纯 S3 更低延迟 |
| **Diskless Cluster** | WarpStream | 是 | 写入直接到对象存储，无本地盘 | 成本敏感、可接受 33–250 ms |
| **Stream→Lakehouse 物化** | Confluent Tableflow、Aiven Iceberg Topics | 否（依赖 Kafka） | topic 自动转为 Iceberg/Delta 表 | 实时分析与 AI/ML 管道 |

## 1.29.3 代表系统深度

### WarpStream：无磁盘、协议兼容的 BYOC Kafka

WarpStream 由 Datadog 前工程师基于 "在 S3 上构建 Kafka" 的经验推出，2023 年 7 月发布，2024 年 9 月被 Confluent 收购[^forbes-warpstream]。其核心设计是把 Kafka 拆成三部分：

- **计算**：无状态 Agent，运行在用户 VPC 内；
- **存储**：对象存储（S3 / GCS / Azure Blob），数据桶完全位于用户云账号；
- **元数据**：WarpStream 托管的 sequencer/control plane，只记录 offset→文件映射，不触碰消息内容。

```text
写入路径（WarpStream）
┌──────────┐    ┌─────────────┐    ┌─────────────┐    ┌──────────────────┐
│ Producer │───→│ 无状态 Agent │───→│  对象存储    │←───│  Control Plane   │
│(任意 AZ) │    │ (同 AZ 聚合) │    │ (S3/GCS/..)│    │  offset→file 映射 │
└──────────┘    └─────────────┘    └─────────────┘    └──────────────────┘
```

由于 Agent 不写本地盘，扩容只需拉起新容器，无需分区重分配；故障时客户端切到另一个 Agent 即可，不存在 leader 选举和副本追赶。

**延迟档位**（同一架构内可调）：

| 档位 | 技术手段 | 中位数 / p99 |
| --- | --- | --- |
| 默认 | 标准对象存储 + 批量窗口 | ~250 ms / ~500 ms |
| S3 Express One Zone | 低延迟对象存储 + 更短批处理 | ~105 ms / ~170 ms |
| Lightning Topics | S3 Express One Zone + 激进批处理 | ~33 ms / ~50 ms |

Lightning Topics 的代价是**禁用幂等生产者与事务**；标准 topic 仍支持事务、压缩 topic、Schema Registry[^warpstream-diskless]。

**部署示例（Helm / Kubernetes）**：

```yaml
# warpstream-values.yaml（概念示例，具体以官方 chart 为准）
agent:
  replicaCount: 3
  resources:
    requests:
      cpu: "2"
      memory: "8Gi"
  env:
    # 指向 WarpStream 控制平面
    WARPSTREAM_API_KEY: "${WARPSTREAM_API_KEY}"
    # 数据桶位于用户自己的 AWS 账号
    WARPSTREAM_BUCKET_URL: "s3://my-warpstream-data-bucket"
    # 使用 S3 Express One Zone 降低延迟
    WARPSTREAM_STORAGE_TYPE: "s3_express"

service:
  type: LoadBalancer
  port: 9092
```

```bash
# 安装 Agent（假设已添加 WarpStream Helm repo）
helm upgrade --install warpstream warpstream/warpstream \
  -f warpstream-values.yaml \
  --namespace warpstream --create-namespace

# 客户端只需改 bootstrap URL，无需改代码
kafka-console-producer.sh \
  --bootstrap-server warpstream.mycompany.com:9092 \
  --topic orders
```

**定价要点**：BYOC 按未压缩写入量、Agent 运行分钟数、对象存储量计费；前 50 TiB 写入约 $0.01/GiB，无 per-Agent / per-core / per-partition 费用[^warpstream-pricing]。

### AutoMQ：Shared Storage 与 WAL 缓冲

AutoMQ 采用 **Shared Storage** 架构：把 Kafka 原生的 Log 存储层替换为自研的 **S3Stream** 库，对象存储成为主存储，同时引入 **WAL（Write-Ahead Log）** 作为写入缓冲，以弥补对象存储高延迟、低 IOPS 的不足[^automq-overview]。

```text
AutoMQ 存储分层
┌─────────────────────────────────────────┐
│           Producer / Consumer           │
└───────────────┬─────────────────────────┘
                ↓
┌─────────────────────────────────────────┐
│    无状态 Broker（S3Stream 替换 Log）     │
│  ┌─────────────────────────────────┐   │
│  │  WAL 缓冲（可选 EBS/FSx/S3 WAL）  │   │
│  │  用于快速持久化写入 & 故障恢复     │   │
│  └─────────────────────────────────┘   │
└───────────────┬─────────────────────────┘
                ↓
┌─────────────────────────────────────────┐
│      对象存储（S3 兼容，主数据仓库）       │
│   持久化、弹性、按量计费、云厂商多 AZ 复制   │
└─────────────────────────────────────────┘
```

**与 Kafka 分层存储的本质区别**：

| 维度 | Kafka KIP-405 分层存储 | AutoMQ Shared Storage |
| --- | --- | --- |
| 主存储 | 本地盘 / EBS | 对象存储 |
| ISR 复制 | 需要，产生跨 AZ 流量 | 不需要，由云存储服务原生冗余 |
| 扩容/重分配 | 数小时级 | 秒级，buffer 通常仅数百 MB |
| Broker 状态 | 有状态 | 无状态 |
| EBS 空间 | 随分区数不确定，需预留 | 可预测（如 EBS WAL 每节点 2 GiB）[^automq-diff] |

AutoMQ 开源版（GitHub `AutoMQ/automq`）仅支持 S3 兼容存储作为 WAL，因此是真正的 "S3-only" 部署；商业版可在 AWS FSx、Regional EBS、EFS 等之间选择 WAL 介质，以获得更低延迟[^automq-fsx]。2025 年 5 月 AutoMQ 将许可证从 BSL 转为 Apache 2.0[^automq-alternatives]。

**Docker Compose 快速体验（S3-only）**：

```yaml
# automq-compose.yaml
services:
  automq:
    image: automqinc/automq:latest
    container_name: automq
    ports:
      - "9092:9092"
      - "9999:9999"
    environment:
      # 使用本地 MinIO 作为 S3 兼容存储
      KAFKA_S3_ENDPOINT: "http://minio:9000"
      KAFKA_S3_BUCKET: "automq-data"
      KAFKA_S3_REGION: "us-east-1"
      KAFKA_S3_ACCESS_KEY: "minioadmin"
      KAFKA_S3_SECRET_KEY: "minioadmin"
      # 集群标识
      KAFKA_CLUSTER_ID: "automq-demo-cluster"
    depends_on:
      - minio

  minio:
    image: minio/minio:latest
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"
```

```bash
# 启动本地 S3-only 体验环境
docker compose -f automq-compose.yaml up -d

# 创建 topic 并生产消息（使用标准 Kafka 客户端）
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic events --partitions 6 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic events
```

## 1.29.4 权衡分析

### 延迟 vs 成本 vs 运维简化

| 维度 | 本地盘 Kafka | S3 解耦 Kafka（WarpStream/AutoMQ） |
| --- | --- | --- |
| **Produce 延迟** | 1–10 ms | 33–500 ms，取决于档位 |
| **存储成本** | 高（EBS/本地盘 × 3 副本） | 低（对象存储单副本，云厂商内建冗余） |
| **跨 AZ 流量成本** | 高（~80% 账单来源） | 低/无 |
| **扩容速度** | 小时–天级 | 秒级 |
| **Broker 状态** | 有状态 | 无状态 |
| **运维复杂度** | 分区重分配、磁盘容量、副本平衡 | 对象存储生命周期、API 调用费用、WAL/缓存调优 |
| **生态兼容性** | 完整 | WarpStream/AutoMQ 均保持 Kafka 协议兼容 |

### 何时保留本地盘

- 支付、撮合、实时竞价、高频交易等要求 **个位数毫秒** 延迟的场景；
- 需要强事务且无法放弃幂等生产者（如使用 Lightning Topics 受限时）；
- 现有集群已重度调优，且云厂商给予了大幅跨 AZ 折扣；
- 数据主权或合规要求禁止将原始数据放入对象存储。

### 何时选择 S3 解耦

- **日志/指标/链路追踪**：对延迟不敏感，数据量大，是 WarpStream 的典型生产场景；
- **湖仓入湖 / CDC / ETL**：数据最终进入 Iceberg/Delta 做分析，S3 天然是终点；
- **事件溯源长期保留**：需要 7 天–数年的保留，本地盘成本不可接受；
- **波峰波谷明显的弹性业务**：需要基于 CPU/网络自动扩缩容，无法承受 Kafka 重分配耗时；
- **希望保留 Kafka 生态但降低运维**：WarpStream/AutoMQ 都支持标准 Kafka 客户端。

## 1.29.5 选型决策建议

```text
开始：是否已使用 Kafka 协议/生态？
├── 否 → 可考虑 Pulsar + Tiered Storage、NATS、云托管等，不在本文重点
└── 是 → 延迟是否要求 < 50 ms 且不可妥协？
    ├── 是 → 保留本地盘 Kafka（Kafka 4.x + EBS/本地 SSD，必要时 KIP-405 冷存）
    └── 否 → 是否需要保留自托管、避免 SaaS 锁定？
        ├── 是 → AutoMQ（Apache 2.0，S3-only，可自托管）
        └── 否 → 是否希望 BYOC、数据完全在自有云账号？
            ├── 是 → WarpStream（Confluent 旗下 BYOC，无磁盘 Agent）
            └── 否 → 已经在使用 Confluent Cloud？
                ├── 是 → Tableflow（Kafka→Iceberg/Delta，分析集成）
                └── 否 → 评估 Kafka KIP-405 分层存储或托管 MSK 等渐进路线
```

**综合建议**：

1. **渐进改造**：现有 Kafka 集群先开启 KIP-405 分层存储，把冷数据 offload 到 S3，风险最低；
2. **新集群 / 成本敏感**：优先考虑 AutoMQ（开源、Apache 2.0、协议兼容），特别是对延迟有一定要求时可选择 FSx/EBS WAL；
3. **完全不想运维磁盘**：选择 WarpStream BYOC，按写入量付费，Agent 无状态；
4. **流表一体**：在 Confluent Cloud 上启用 Tableflow，直接把 topic 物化为 Iceberg/Delta Lake 表，省掉 Connect + 调度 + 小文件治理。
