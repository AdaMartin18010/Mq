## 1.72.1 消息大小限制矩阵

消息大小限制是消息系统选型的第一道“硬门槛”。本节给出 Kafka、RabbitMQ、NATS、Pulsar、MQTT、Redis Stream 的默认阈值、配置参数与超限行为，所有默认值均来自官方文档。

### Kafka

Kafka 的消息大小限制是一个“三层漏斗”：生产者请求层、Broker 接收层、消费拉取层必须同时放行，否则消息无法端到端流通。

| 层级 | 参数名 | 默认值 | 说明 |
| ---- | ------ | ------ | ---- |
| Broker | `message.max.bytes` | 1,048,588 字节（约 1 MiB） | 单条 record batch 最大尺寸，按压缩后计算 [Broker Configs](https://kafka.apache.org/41/configuration/broker-configs/) |
| Topic | `max.message.bytes` | 1,048,588 字节 | topic 级覆盖 `message.max.bytes` [Topic Configs](https://kafka.apache.org/41/generated/topic_config.html) |
| Producer | `max.request.size` | 1,048,576 字节 | 单个 Produce 请求的最大字节数 [Producer Configs](https://kafka.apache.org/41/configuration/producer-configs/) |
| Consumer（每分区） | `max.partition.fetch.bytes` | 1,048,576 字节 | 单次 fetch 每个分区最多返回字节数 [Consumer Configs](https://kafka.apache.org/41/configuration/consumer-configs/) |
| Consumer（全响应） | `fetch.max.bytes` | 52,428,800 字节（50 MiB） | 单次 fetch 响应整体上限 [Consumer Configs](https://kafka.apache.org/41/configuration/consumer-configs/) |
| 副本同步 | `replica.fetch.max.bytes` | 1,048,576 字节 | follower 拉取 leader 数据上限，必须 ≥ `message.max.bytes` [Broker Configs](https://kafka.apache.org/41/configuration/broker-configs/) |

**超限行为**：Broker 对超过 `message.max.bytes`/`max.message.bytes` 的 batch 返回 `RecordTooLargeException`；如果消费者 `max.partition.fetch.bytes` 小于实际 batch 大小，Kafka 会优先返回该 batch 以保证进度，但配置不一致会导致内存与重算风险。

```properties
# kafka-server.properties.template 相关片段（引用 topics/config-templates/kafka-server.properties.template）
message.max.bytes=1048588
replica.fetch.max.bytes=1048576
compression.type=producer
```

生产建议：日志/事件类 topic 保留 1 MiB 默认；需要承载大附件时统一上调 Broker、Topic、Producer、Consumer、Replica 五处，并优先使用 Pulsar chunking 或对象存储外链。

### RabbitMQ

RabbitMQ 4.0+ 将默认单消息大小从 3.x 时代的 128 MiB 下调为 16 MiB，避免大消息造成内存与 GC 抖动。

| 参数名 | 默认值 | 说明 |
| ------ | ------ | ---- |
| `max_message_size` | 16,777,216 字节（16 MiB） | 单条消息 payload 上限，最大值 512 MiB [RabbitMQ Limits](https://rabbitmq.com/docs/limits) |
| `frame_max` | 131,072 字节（128 KiB） | AMQP 0-9-1 / AMQP 1.0 / Stream 协议帧大小，不建议修改 |
| `initial_frame_max` | 8,192 字节 | 连接认证前最大帧大小 |

**超限行为**：发布超过 `max_message_size` 的消息时，Broker 关闭 channel 并返回 `406 PRECONDITION_FAILED - message size ... is larger than configured max size`。

```ini
# rabbitmq.conf 片段
max_message_size = 16777216
# frame_max 保持官方推荐的 131072，不建议自行覆盖
```

`frame_max` 与 `max_message_size` 的关系：大消息会被切分为多个 AMQP frame 传输，但 `max_message_size` 仍是 payload 总上限；仅当消息头极大时才可能触发 `frame_max` 相关错误。

### NATS

NATS 以“轻量消息”为设计前提，默认 payload 上限非常小。

| 参数名 | 默认值 | 说明 |
| ------ | ------ | ---- |
| `max_payload` | 1,048,576 字节（1 MiB） | 单条消息 payload 上限，可热重载 [NATS Configuration](https://docs.nats.io/running-a-nats-service/configuration#limits) |
| `max_pending` | 67,108,864 字节（64 MiB） | 单连接缓冲区上限 |

**超限行为**：发布端收到 `-ERR 'Maximum Payload Violation'`；JetStream Object Store 会把大对象切成 128 KiB 的消息块存储 [NATS Object Store](https://docs.nats.io/learn/object-store/)。

```hcl
# nats-server.conf 片段
max_payload: 8MB
max_pending: 64MB
```

官方建议 `max_payload` 不超过 8 MB，最大可设 64 MB；超过时应改用 Object Store 或外部对象存储 + 消息传引用。

### Pulsar

Pulsar 默认单消息 5 MiB，并提供客户端分块（chunking）机制突破该限制。

| 参数名 | 默认值 | 说明 |
| ------ | ------ | ---- |
| `maxMessageSize` | 5,242,880 字节（5 MiB） | broker 允许的最大消息尺寸 [Pulsar Messaging](https://pulsar.apache.org/docs/next/concepts-messaging/) |
| `nettyMaxFrameSizeBytes` | 5,253,120 字节 | Netty 帧大小上限，通常需比 `maxMessageSize` 略大 |

**超限行为**：Broker 拒绝超过 `maxMessageSize` 的消息；启用 producer `enableChunking=true` 后，客户端自动将大消息切片，消费端再聚合（需关闭 batching）。

```properties
# broker.conf 片段
maxMessageSize=5242880
nettyMaxFrameSizeBytes=5253120
```

### MQTT

MQTT 5.0 通过 CONNECT/CONNACK 的 **Maximum Packet Size（0x27）** 属性声明本端可接收的最大报文尺寸；该属性是协议级语义，因此标记为【定理】[OASIS MQTT v5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)。

- 若 CONNECT 未携带该属性，表示发送端不限制接收报文大小；
- Broker 可在 CONNACK 中回显其 `Maximum Packet Size`，客户端必须遵守；
- 整个 MQTT 报文剩余长度上限为 268,435,455 字节（约 256 MiB），由变长整数编码决定；
- 超过对端声明的 Maximum Packet Size 时，接收方发送 `0x95 Packet too large` Reason Code 并断开连接。

MQTT 协议本身不压缩 payload，压缩属于应用层约定，需在 `Content Type` 与 `Payload Format Indicator` 中声明。

### Redis Stream

Redis Stream 的条目由 field-value 对组成，限制继承 Redis 字符串与协议层上限。

| 限制来源 | 默认值 | 说明 |
| -------- | ------ | ---- |
| 单个 value | 512 MB | Redis string 最大值 [Redis Strings](https://redis.io/docs/latest/develop/data-types/strings/) |
| 单条命令输入 | 512 MB | RESP bulk string 默认上限，由 `proto-max-bulk-len` 控制 [RESP Protocol](https://redis.io/docs/latest/develop/reference/protocol-spec/) |
| Stream 节点 | 4,096 字节 / 100 条目 | `stream-node-max-bytes` / `stream-node-max-entries` 控制内部节点切分 |

**超限行为**：超过 `proto-max-bulk-len` 的命令直接返回错误；Stream entry 本身无独立大小上限，但受整条 `XADD` 命令长度限制。生产环境应避免把大对象直接塞进 Stream value，推荐只传对象 ID 或分片后写入外部存储。

```bash
# 生产建议：XADD 承载的是事件元数据或引用，而非原始大文件
redis-cli XADD events:order * orderId 10086 objectUrl s3://bucket/orders/10086.bin
```

### 六系统阈值速查表

| 系统 | 默认单消息/报文上限 | 配置参数 | 超限行为 | 生产建议阈值 |
| ---- | ------------------ | -------- | -------- | ------------ |
| Kafka | ~1 MiB（压缩后） | `message.max.bytes` / `max.message.bytes` | `RecordTooLargeException` | 日志类保留 1 MiB；大消息单独 topic 上调至 ≤10 MiB |
| RabbitMQ | 16 MiB | `max_message_size` | channel `406 PRECONDITION_FAILED` | 任务队列 1-4 MiB；大文件 16 MiB 内或改用 Stream/Object Store |
| NATS | 1 MiB | `max_payload` | `-ERR Maximum Payload Violation` | 核心消息 ≤1 MiB；大对象用 Object Store |
| Pulsar | 5 MiB | `maxMessageSize` | broker 拒绝；可启用 chunking | 普通 5 MiB；需要大消息时启用 chunking 并评估内存 |
| MQTT | 协议未设默认值，最大 256 MiB | `Maximum Packet Size` 属性 | `0x95 Packet too large` | IoT 场景 ≤64 KiB；后端桥接 ≤1 MiB |
| Redis Stream | 512 MB（命令级） | `proto-max-bulk-len` | 命令错误 | 单条 entry ≤1 MiB，大 value 传引用 |

## 1.72.2 序列化/反序列化全谱

序列化决定消息体积、Schema 治理能力、跨语言兼容性与 CPU 开销。本节在 2.26 的基础上做全谱展开。

### 格式对照决策表

| 格式 | Schema 演化 | 类型系统 | 体积 | 序列化/反解析速度 | 可读性 | 跨语言生态 | 典型场景 |
| ---- | ----------- | -------- | ---- | ---------------- | ------ | ---------- | -------- |
| JSON | 弱（靠约定/版本头） | 动态 | 大 | 中 | 高 | 极好 | Web、调试、MQTT 遥测 |
| Avro | 强（Schema Registry） | 静态 schema | 小 | 快 | 低 | 好 | Kafka 大数据管道 |
| Protobuf | 强（字段号演进） | 静态 schema | 小 | 快 | 低 | 极好 | gRPC、微服务、Sparkplug B |
| MessagePack | 弱 | 动态/半类型 | 中 | 快 | 中 | 好 | IoT、边缘、游戏 |
| FlatBuffers | 弱（无内置演进） | 静态 schema | 小 | 极快（零拷贝） | 低 | 好 | 游戏、高频交易 |
| CBOR | 弱 | 动态/半类型 | 小 | 快 | 低 | 中等 | 受限网络、CoAP/MQTT 伴侣 |

上表中的“体积”与“速度”为典型 JSON-like 工作负载下的工程经验值【估算】，实际应以业务数据基准测试为准。

### Schema Registry 协同

- **Confluent Schema Registry**：支持 Avro、JSON Schema、Protobuf；提供 Backward / Forward / Full / None 兼容性级别；序列化时把 schema ID 写入消息前缀，消费端自动反查。当前仍是 Kafka 生态事实标准 [Confluent Schema Registry](https://github.com/confluentinc/schema-registry)。
- **Apicurio Registry**：红帽/Apicurio 社区项目，3.x 为当前主版本线，支持 Avro、JSON Schema、Protobuf、OpenAPI、AsyncAPI、GraphQL 等；兼容 Confluent 的 schema ID 编码格式，也支持自己的artifact/version模型 [Apicurio Registry 3.x](https://www.apicur.io/registry/docs/apicurio-registry/3.4.x/index.html)。

```java
// Kafka + Confluent Schema Registry 示例（引用 2.26 风格）
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
    "io.confluent.kafka.serializers.KafkaAvroSerializer");
props.put("schema.registry.url", "http://schema-registry:8081");
```

### 各系统原生偏好

| 系统 | 原生偏好 | 备注 |
| ---- | -------- | ---- |
| Kafka | Avro + Schema Registry | 事件日志首选；Protobuf 用于 gRPC 桥接 |
| RabbitMQ | 无强制格式 | Python 生态常用 JSON/pickle（生产禁用 pickle）/msgpack |
| NATS | 字节数组，自选 | JSON、Protobuf、MessagePack 均常见 |
| Pulsar | Schema Registry（Avro/JSON/Protobuf） | 多租户场景下 schema 版本隔离清晰 |
| MQTT | JSON/CBOR/二进制 | 5.0 的 `Content Type` 与 `Payload Format Indicator` 可声明编码 |
| Redis Stream | 无强制格式 | 常见 JSON/MessagePack；大 value 应传引用 |

### 与契约语义测试的接口

在 [契约语义测试](../../Testing/06-契约语义测试/) 六层体系中，`contract.yaml` 的 `message.payload` 字段类型最终落地产出就是本节讨论的序列化字节流。换言之：

- AsyncAPI 的 `payload` schema 描述的是“业务消息形状”；
- 生产端把它编码为 Avro/Protobuf/JSON/CBOR 等字节序列；
- 消费端按相同 schema + format 解码；
- 契约语义测试的 `payload schema 是 contract.yaml 字段类型的落地`。

因此，选型时应保证 AsyncAPI 的 schema 演进规则（`backward`/`forward`）与 Schema Registry 的兼容性级别一致，并在 [TEST-14](../../Testing/06-契约语义测试/02-语义矩阵/TEST-C2-通信层语义矩阵与行为断言.md) 的语义矩阵中登记 payload 类型断言。

## 1.72.3 压缩/解压权衡

压缩在消息系统中的收益取决于瓶颈是 CPU、网络带宽还是磁盘 I/O。本节给出常用压缩算法与六系统支持矩阵。

### 压缩算法对照表

| 算法 | CPU 占用 | 压缩率（典型文本） | 解压速度（量级） | 适用场景 |
| ---- | -------- | ------------------ | ---------------- | -------- |
| gzip | 高 | 高（2-5x） | 中等（~100-400 MB/s） | 归档、低频大文件 |
| snappy | 低 | 低-中（1.2-2x） | 很快（~1-2 GB/s） | 历史 Hadoop/Parquet、低延迟 |
| lz4 | 很低 | 低-中（1.5-2.5x） | 极快（~2-5 GB/s） | Kafka 生产者默认候选、实时流 |
| zstd | 中 | 高（2-5x，可调 1-22 级） | 快（~500 MB/s-1 GB/s） | Kafka 新推荐、通用存储 |

上表为单核现代 CPU 上的经验量级【估算】；Kafka 生产者 `compression.type` 支持 `none`、`gzip`、`snappy`、`lz4`、`zstd` [Kafka Producer Configs](https://kafka.apache.org/41/configuration/producer-configs/)。

### 六系统压缩支持矩阵

| 系统 | Broker/服务端压缩 | 传输压缩 | 应用层压缩 | 备注 |
| ---- | ----------------- | -------- | ---------- | ---- |
| Kafka | 支持（按 batch 保留 producer 压缩） | TLS 不压缩；建议应用层不重复压缩 | 支持 | 推荐 lz4/zstd；broker `compression.type=producer` 透传 [Confluent Blog](https://www.confluent.io/blog/apache-kafka-message-compression/) |
| RabbitMQ | AMQP 0-9-1 核心无压缩；Stream 插件支持 gzip/snappy/lz4/zstd | TLS 不压缩 | 支持 | Stream 插件在 segment 落盘时可选压缩 [RabbitMQ Stream Compression](https://www.rabbitmq.com/docs/stream-core-plugin-comparison) |
| NATS | 核心无压缩；JetStream 支持 S2 压缩 | TLS 不压缩 | 支持 | S2 用于 JetStream 文件存储层 [Synadia Insight](https://www.synadia.com/insights/checks/nats-uncompressed-large-stream) |
| Pulsar | 支持（producer 指定 `compressionType`） | TLS 不压缩 | 支持 | 支持 LZ4、ZLIB、ZSTD、SNAPPY [Pulsar Messaging](https://pulsar.apache.org/docs/next/concepts-messaging/) |
| MQTT | 协议未定义 | TLS 不压缩；MQTT over WebSocket 可走 HTTP 压缩代理 | 支持 | 应用层 gzip/CBOR 需双方约定并在 `Content Type` 声明 |
| Redis Stream | 无内置压缩 | TLS 不压缩 | 支持 | 大 value 可在应用层 zstd 后再 `XADD` |

### 典型误区

1. **多层重复压缩**：应用层 gzip 后再让 Kafka producer `compression.type=gzip`，CPU 翻倍而收益极低。正确做法：应用层不压缩，交给 Kafka batch 级压缩；或仅对应用层数据做字典/字段裁剪。
2. **SSL/TLS 之后再压缩**：加密后的数据熵接近随机，压缩率几乎为零。正确顺序：先压缩 payload，再进入 TLS 传输。
3. **小消息强压缩**：小于 1 KiB 的消息启用 zstd 高等级，压缩头开销可能超过收益；JSON 小对象优先选 snappy/lz4 或不压缩。
4. **忽略消费端解压成本**：zstd/gzip 会抬高消费 CPU；在 CPU 受限的边缘节点应选 lz4。

### KIP-405 分层存储指针

KIP-405（Tiered Storage）让 Kafka 将旧的本地 log segment 上传至远程对象存储。压缩与该机制的交互要点：

- 本地 segment 以 producer 选定的压缩格式存储，上传远程时保持原字节不变；
- 远程读取需从对象存储拉取完整 segment，因此 zstd 的高压缩率可直接降低远程存储成本与回拉带宽；
- 分层存储场景下，`max.partition.fetch.bytes` 对远程分区有“单分区单请求”限制（KAFKA-14915），大消息或高压缩 batch 需要协调消费者缓冲区 [Kafka Consumer Configs](https://kafka.apache.org/41/configuration/consumer-configs/)。

```properties
# 启用分层存储的 topic 配置示例
remote.storage.enable=true
local.retention.ms=3600000
local.retention.bytes=1073741824
compression.type=zstd
```

## 1.72.4 组合决策表：大小 × 序列化 × 压缩

| 场景 | 消息大小 | 推荐序列化 | 推荐压缩 | 推荐系统 | 关键检查项 |
| ---- | -------- | ---------- | -------- | -------- | ---------- |
| 小消息高频、低延迟 | <1 KiB | JSON / Protobuf | 不压缩或 snappy/lz4 | Kafka / NATS | batch 大小、端侧 CPU、网络包 overhead |
| 日志/事件高吞吐 | 100 B - 10 KiB | Avro + Schema Registry | zstd / lz4 | Kafka / Pulsar | schema 兼容性、压缩率、消费 lag |
| 大文件/低频附件 | >1 MiB | Protobuf / Avro | zstd（应用层或 batch） | Pulsar chunking / RabbitMQ ≤16 MiB / 对象存储+引用 | 内存峰值、chunking 开关、超时 |
| 金融指令、强一致 | 100 B - 1 KiB | Protobuf / Avro | 不压缩或 lz4 | Kafka / RabbitMQ / Pulsar | schema 版本、幂等、幂等键 |
| IoT 受限网络 | <1 KiB | CBOR / Protobuf | 不压缩或应用层 gzip | MQTT / NATS | packet size、QoS、电池/CPU |
| 实时流处理 | 1-100 KiB | Avro / JSON | lz4 / zstd | Kafka / Pulsar | 反序列化延迟、key 分区、状态存储 |
| 缓存/消息总线 | 可变 | JSON / MessagePack | 不压缩 | Redis Stream / NATS | 内存上限、MAXLEN 裁剪、大 key |

上表为选型启发，具体落地应结合 `topics/config-templates/serialization-config.properties` 与压力测试校准。
