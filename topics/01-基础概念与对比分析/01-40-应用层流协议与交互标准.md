## 1.40.1 为什么需要区分“消息”与“流”

消息队列解决的是**持久化、解耦、削峰填谷**问题；应用层流协议解决的是**在线、低延迟、端到端字节/事件流传输**问题。二者边界常被混淆，导致“用 MQ 做实时推送”或“用 WebSocket 做可靠事件投递”两种反模式。

核心差异：

| 维度 | 消息队列（MQ） | 应用层流协议 |
| ---- | ---- | ---- |
| 核心语义 | 存储-转发、至少一次/恰好一次投递 | 在线字节/消息流传输 |
| 持久化 | Broker 持久化，消费者可离线恢复 | 通常不持久化，断线即丢或需应用层重放 |
| 背压 | 基于分区/队列容量、消费者拉取速率 | 基于连接级流控、HTTP/2 WINDOW_UPDATE、应用 request-n |
| 典型延迟 | 毫秒~百毫秒 | 亚毫秒~数十毫秒 |
| 浏览器支持 | 需 SDK/Bridge | WebSocket/SSE/WebTransport 原生支持 |

【论证】在企业架构中，MQ 与流协议不是替代关系：MQ 负责“把事件可靠地搬到需要它的地方”，流协议负责“把事件低延迟地送到正在运行的客户端”。实际系统常组合使用，例如 MQTT over WebSocket 让浏览器直接订阅 MQTT Broker，Kafka → WebSocket Gateway 把后端事件推送到前端。

## 1.40.2 WebSocket

### 握手与帧结构要点

【定理】WebSocket 协议由 IETF RFC 6455 定义，2011-12 发布为 Standards Track。握手基于 HTTP/1.1 Upgrade 机制，客户端发送：

```http
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

服务端若接受，返回 `101 Switching Protocols` 与 `Sec-WebSocket-Accept` 头，后续通信切换为 WebSocket 帧格式。RFC 6455 定义了帧头 FIN、RSV、Opcode、MASK、Payload length 等字段，并规定客户端到服务端帧必须设置 MASK（掩码）以防范缓存投毒攻击。

HTTP/2/3 上启动 WebSocket 另有规范：RFC 8441（Bootstrapping WebSockets with HTTP/2）和 RFC 9220（Bootstrapping WebSockets with HTTP/3），均使用 Extended CONNECT 与 `:protocol = websocket` 伪头，把 WebSocket 作为单条流复用在 HTTP/2/3 连接上。截至 2026-11，主流浏览器仍以 HTTP/1.1 Upgrade 为主要路径，HTTP/2 WebSocket 在服务端/代理侧逐步普及。

### MQTT/STOMP/NATS over WebSocket

MQTT 5.0 规范明确支持 WebSocket 作为传输绑定。主流 Broker（Eclipse Mosquitto、HiveMQ、RabbitMQ 的 MQTT 插件、EMQX）均支持 `ws://`/`wss://` 监听。WebSocket 子协议协商（`Sec-WebSocket-Protocol: mqtt`）后，帧内直接承载 MQTT 报文。

| 子协议 | 规范/约定 | 典型 Broker | 子协议名 |
| ---- | ---- | ---- | ---- |
| MQTT over WebSocket | MQTT 5.0 / MQTT 3.1.1 | Mosquitto、EMQX、RabbitMQ | `mqtt` |
| STOMP over WebSocket | STOMP 1.2 | RabbitMQ、ActiveMQ Artemis | `v12.stomp` |
| NATS over WebSocket | NATS 2.x 实现约定 | NATS Server 2.x+ | `nats` |

### 反向代理与 LB 注意事项

WebSocket 是有状态长连接，与无状态 HTTP 负载均衡模型冲突：

- **连接黏性**：同一 WebSocket 会话的所有帧必须落在同一后端进程；使用 IP Hash 或 sticky cookie，或在外部维护共享会话状态。
- **心跳超时**：代理/负载均衡器默认空闲超时较短，需配置较长的 `proxy_read_timeout` / `proxy_send_timeout`，并依赖 WebSocket Ping/Pong 保活。
- **HTTP/2 兼容**：若客户端通过 HTTP/2 建立 WebSocket，代理必须支持 RFC 8441 的 Extended CONNECT。

典型 Nginx 反向代理配置：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 443 ssl;
    location /mqtt {
        proxy_pass http://mqtt_backend:8083;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 86400;
        proxy_send_timeout 86400;
    }
}
```

### 与 MQ 桥接场景

【论证】WebSocket 最常见的 MQ 场景是“浏览器/移动端直接消费”：

1. **MQTT over WebSocket**：IoT 或 H5 页面直接订阅 MQTT Broker，避免前端再维护一个 HTTP→MQTT 网关。
2. **Kafka → WebSocket Gateway**：后端 Kafka Consumer 聚合多个 WebSocket 连接，按用户 ID 过滤推送。此时 WebSocket Gateway 是 Kafka 的消费者，不是 Kafka 协议的一部分。
3. **STOMP over WebSocket**：Spring 等框架通过 RabbitMQ/ActiveMQ 的 STOMP 插件，把浏览器作为临时订阅者，适合聊天、通知面板。

## 1.40.3 SSE（Server-Sent Events）

### EventSource 与 text/event-stream

【定理】SSE 由 WHATWG HTML Living Standard 第 9.2 节定义，是浏览器原生 API。客户端创建 `EventSource` 后，服务端以 `Content-Type: text/event-stream` 持续推送文本事件。

```text
data: {"price": 123.45, "symbol": "AAPL"}

event: update
data: {"status": "done"}

id: 42
data: next event
```

每条事件以空行分隔。字段包括 `data:`、`event:`、`id:`、`retry:`。浏览器端：

```js
const source = new EventSource('/events');
source.addEventListener('update', e => console.log(JSON.parse(e.data)));
source.onerror = e => console.error('SSE error', e);
```

### Last-Event-ID 断线续传

【定理】WHATWG 规范要求：断线重连时，若事件源已设置 `last event ID string`，浏览器必须自动在重连请求中携带 `Last-Event-ID` 头。服务端可据此从该 ID 之后重放事件。这是 SSE 相比原始 WebSocket 在**断线恢复**上的原生优势。

### HTTP/2 下的多路复用问题

SSE 基于 HTTP 长连接。在 HTTP/1.1 下，浏览器对同一域名并发连接数有限制（约 6 个）；在 HTTP/2/3 下，多个 SSE 流可共享同一条 TCP/QUIC 连接的多路复用，理论上不再受连接数限制。但【论证】实践中仍有两点需注意：

- **代理缓冲**：某些反向代理或 CDN 会对响应做缓冲，导致 SSE 事件无法及时到达客户端；需关闭缓冲或显式设置 `X-Accel-Buffering: no`。
- **连接总超时**：HTTP/2 连接级超时仍可能一次性关闭多个 SSE 流；生产环境建议结合 `retry` 字段与 `Last-Event-ID` 实现自愈。

### SSE vs WebSocket 选型矩阵

| 对比项 | SSE | WebSocket |
| ---- | ---- | ---- |
| 方向 | 单向（服务端→客户端） | 全双工 |
| 传输 | 纯 HTTP，text/event-stream | 二进制帧，子协议协商 |
| 断线恢复 | EventSource 原生重连 + Last-Event-ID | 需应用层实现 |
| 浏览器支持 | 全现代浏览器（IE 除外） | 全现代浏览器 |
| 防火墙/代理 | 通常直接穿透 | 部分企业代理会阻断 Upgrade |
| 适用场景 | 股票行情、AI token 流、通知 Feed | 聊天、游戏、协同编辑 |

## 1.40.4 WebTransport

WebTransport 是 W3C 提出的浏览器 API，底层基于 IETF WEBTRANS 工作组草案，目前主要实现为 HTTP/3/QUIC 传输，同时也定义了 HTTP/2 降级方案。

【定理】截至 2026-11：W3C WebTransport 规范于 2026-07-30 进入 Candidate Recommendation（CR），标志 API 进入“邀请实现”阶段；IETF `draft-ietf-webtrans-http3` 仍处于工作组草案/Last Call，尚未发布为 RFC。浏览器支持方面：Chrome 97+、Edge 98+、Firefox 114+ 已实现，Safari 26.4（2026-03）加入支持后，WebTransport 达到 Baseline newly available 状态。

WebTransport 提供三类抽象：

- **Bidirectional streams**：类似 WebSocket，但可建立多条，避免队头阻塞。
- **Unidirectional streams**：单向可靠字节流。
- **Datagrams**：不可靠、低延迟数据报，适合游戏状态、实时音视频。

```js
const transport = new WebTransport('https://example.com/endpoint');
await transport.ready;

const stream = await transport.createBidirectionalStream();
const writer = stream.writable.getWriter();
await writer.write(new TextEncoder().encode('hello'));
writer.releaseLock();
```

【论证】与 WebSocket 相比，WebTransport 的核心优势是**消除连接级队头阻塞**（QUIC 多流独立传输）和**支持不可靠数据报**。劣势是标准化尚未完全落地（IETF 协议仍在草案），且企业防火墙对 UDP/QUIC 的放行程度不如 TCP 443。当前适合早期采用者场景：低延迟游戏、实时数据流、WebRTC 替代 ingest。

## 1.40.5 gRPC streaming

gRPC 是 CNCF 毕业项目，默认使用 Protocol Buffers 作为 IDL，基于 HTTP/2 帧传输。它定义四种服务方法：

| 类型 | 说明 | 典型场景 |
| ---- | ---- | ---- |
| Unary | 单次请求-响应 | 普通 API |
| Server streaming | 服务端返回多条响应 | 实时日志、推送 |
| Client streaming | 客户端发送多条请求 | 批量上传 |
| Bidirectional streaming | 双向流 | 语音/视频、AI 对话 |

【定理】gRPC 的流控继承 HTTP/2 的 WINDOW_UPDATE 机制，同时应用层通过生成/消费消息维持背压。截至 2026-11，gRPC Core 最新稳定版约为 1.85.x，grpc-go 1.85.x；不同语言版本号略有差异，但均遵循 [gRFC 流程](https://github.com/grpc/proposal) 演进。

proto 示例：

```proto
service ChatService {
  rpc StreamMessages(stream ChatMessage) returns (stream ChatMessage) {}
}

message ChatMessage {
  string user = 1;
  string text = 2;
}
```

【论证】gRPC streaming 与 MQ 的本质区别：

- **在线 RPC 流**：gRPC 是“调用一个远端方法”的在线语义，断线后当前 RPC 失败，需要客户端重新建立调用；不重放历史消息。
- **持久化消息**：MQ 是“把消息交给 Broker，由它负责投递”，消费者可离线、可重放、可水平扩展。

因此，gRPC streaming 适合服务与服务之间的低延迟 RPC 流；若需要解耦、削峰、持久化、离线消费，应引入 Kafka/Pulsar/RabbitMQ 等 MQ。

## 1.40.6 RSocket

RSocket 是一种面向 Reactive Streams 语义的二进制应用层协议，支持 Request-Response、Fire-and-Forget、Request-Stream、Request-Channel 四种交互模型，可运行在 TCP、WebSocket、Aeron 等传输之上。

【定理】RSocket 协议草案当前版本为 0.2（Major 0, Minor 2），被标记为 1.0 Release Candidate；原 W3C RSocket Community Group 已于 2019-08-13 关闭。Java 参考实现 `rsocket-core` 有 1.1.x 稳定线，但社区活跃度自 2020 年后明显下降。因此 RSocket 目前属于**技术可行但生态谨慎**的选项。

核心机制：

- **帧类型**：SETUP、LEASE、KEEPALIVE、REQUEST_RESPONSE、REQUEST_FNF、REQUEST_STREAM、REQUEST_CHANNEL、REQUEST_N、PAYLOAD、ERROR 等。
- **背压**：通过 `REQUEST_N` 帧实现 credit-based flow control，与 Reactive Streams `request(n)` 语义对齐。
- **Resumption**：可选的会话恢复能力，断线后可通过 Resume Token 在新建传输上恢复未完成的流。
- **Lease**：服务端通过 LEASE 帧主动限制客户端可发起的请求数，实现连接级拥塞控制。

【论证】RSocket 的设计目标（多路复用、背压、跨传输）与 Reactive Streams 高度契合，但生态现实是：Spring 生态主推 Reactor/WebFlux，云原生领域主推 gRPC，RSocket 缺乏大型云厂商背书。除非团队已有 RSocket 资产，否则新系统不宜作为首选。

## 1.40.7 Reactive Streams 规范

Reactive Streams 不是传输协议，而是**异步流处理与无阻塞背压**的最小接口契约。其 JVM 规范由 `reactive-streams.org` 维护，最新稳定版为 **1.0.4**（2022-05-26 发布）。

【定理】规范定义四个核心接口：

| 接口 | 职责 | 对应方法 |
| ---- | ---- | ---- |
| `Publisher<T>` | 发布数据元素 | `subscribe(Subscriber)` |
| `Subscriber<T>` | 消费数据元素 | `onSubscribe`, `onNext`, `onError`, `onComplete` |
| `Subscription` | 连接 Publisher 与 Subscriber | `request(long)`, `cancel()` |
| `Processor<T,R>` | 同时是 Subscriber 与 Publisher | — |

背压协议规则：Subscriber 通过 `Subscription.request(n)` 显式请求 n 个元素；Publisher 未收到请求前不得推送数据（除 `onSubscribe` 外）。这保证了下游不会被上游淹没。

Java 9 将语义等价的接口纳入标准库 `java.util.concurrent.Flow`：Flow.Publisher、Flow.Subscriber、Flow.Subscription、Flow.Processor。reactive-streams.org 提供 Flow 与 RS 接口的适配器。

实现生态（截至 2026-11）：

- **Project Reactor**：Spring 生态核心，当前稳定线约 3.8.x（如 reactor-core 3.8.8），提供 `Flux`/`Mono`。
- **RxJava**：当前稳定主线为 3.x（如 3.1.11）；4.x 处于 alpha，预计 2026-11-30 GA。
- **Akka Streams**：Akka 核心库 2.11.x 已内建 Reactive Streams 实现，可与 RS 接口互操作。
- **其他**：Mutiny（Quarkus）、SmallRye Reactive Streams Operators、Vert.x 等。

```java
SubmissionPublisher<String> publisher = new SubmissionPublisher<>();
publisher.subscribe(new Subscriber<>() {
    private Subscription subscription;
    @Override public void onSubscribe(Subscription s) {
        this.subscription = s;
        s.request(1); // 初始请求 1 个元素
    }
    @Override public void onNext(String item) {
        System.out.println(item);
        subscription.request(1); // 处理完再要 1 个
    }
    @Override public void onError(Throwable t) { t.printStackTrace(); }
    @Override public void onComplete() { System.out.println("done"); }
});
publisher.submit("hello");
publisher.close();
```

【论证】Reactive Streams 是“背压协议契约”，不解决网络传输问题；RSocket/gRPC/WebSocket 是“网络传输协议”。工程上常把二者组合：MQ 消费端用 Reactor 处理拉取到的消息流，WebSocket Gateway 用 RS 控制向客户端推送的速率。

## 1.40.8 选型总矩阵与决策指南

### 六维度总矩阵

| 协议/技术 | 典型延迟 | 持久化 | 背压 | 浏览器原生 | 防火墙穿透 | 运维复杂度 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| WebSocket | 低（亚毫秒~10ms） | 无 | 应用层 request-n / 连接流控 | 是 | 中等（Upgrade 可能被拦截） | 中 |
| SSE | 中低（ms 级） | 无 | 应用层 / TCP 缓冲 | 是 | 高（纯 HTTP） | 低 |
| WebTransport | 低（QUIC 0-RTT） | 无 | 多流 + 应用层 | 是（Baseline 2026-03） | 中低（UDP 可能被拦截） | 中高 |
| gRPC streaming | 低（HTTP/2） | 无 | HTTP/2 WINDOW + 应用层 | 否（需 gRPC-Web/Connect 代理） | 高（TCP 443） | 中 |
| RSocket | 低 | 无 | REQUEST_N + Lease | 否（需库/Wasm） | 高（TCP 443/80） | 高 |
| Reactive Streams | —（库内 API） | 无 | request(n) | 否 | — | 低 |
| MQ（Kafka/Pulsar 等） | 中（ms~100ms） | 有 | 拉取/分区 | 否（需 Gateway） | 高 | 高 |

上表中的“MQ”列作为参照，说明持久化是 MQ 与流协议的分水岭。

### 决策指南

```text
是否需要把事件可靠地保存并供离线/新消费者重放？
├── 是 → 用消息队列（Kafka/Pulsar/RabbitMQ/NATS JetStream 等）
└── 否 → 继续评估

数据流方向是否主要是服务端→客户端、且客户端很少上行？
├── 是 → 优先 SSE（HTTP/2 多路复用、断线续传、运维简单）
└── 否 → 继续评估

是否需要浏览器原生、全双工、低延迟交互？
├── 是 → WebSocket（成熟稳定）
├── 需要消除队头阻塞或不可靠数据报 → WebTransport（前卫，注意标准化未完成）
└── 否 → 继续评估

是否是服务间 RPC 流、已有 Protobuf/服务网格生态？
├── 是 → gRPC streaming（跨语言强、工具链成熟）
└── 否 → 继续评估

是否已深度投入 Reactive Streams 背压语义，且接受小众生态？
└── 是 → 可评估 RSocket
```

【论证】最常见的组合是：**后端用 MQ 做持久化解耦，前端通过 WebSocket/SSE/WebTransport 网关接收实时更新**。网关自身作为 MQ 消费者，负责在线连接的会话管理与速率控制。不要把 MQ 的“至少一次投递”强加给 WebSocket 的在线语义，也不要让 WebSocket Gateway 承担长期事件存储职责。
