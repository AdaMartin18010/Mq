## 1.47.1 定义与理论基础

【论证】事件溯源（Event Sourcing）由 Martin Fowler 在 2005 年提出，其核心思想是：把对象的状态变化捕获为一系列不可变事件，并将这些事件以追加方式持久化为系统的“唯一真相源”（Single Source of Truth）；当前状态不再被直接修改，而是通过重放事件流重建得到。该定义来自 Fowler 的《Event Sourcing》一文，并被后续领域驱动设计（DDD）与微服务架构文献广泛沿用。

事件溯源常与“事件驱动架构”（Event-Driven Architecture，EDA）混用，但二者关注点不同：

| 维度 | 事件溯源（Event Sourcing） | 事件驱动架构 / 消息传输 |
| --- | --- | --- |
| 核心目的 | 以事件流保存状态变更历史，支持审计、重放与重建 | 以异步消息解耦服务、传递通知 |
| 数据保留 | 事件不可变，通常长期保留甚至永久保留 | 消息可按 TTL/retention 过期删除 |
| 消费模型 | 一个事件流可被多个投影/消费者按任意偏移重放 | 消息通常由订阅者按队列或主题消费并确认 |
| 真相归属 | 事件流是领域状态的真相源 | 消息是状态变更的通知或命令载体 |
| 典型系统 | EventStoreDB/KurrentDB、Kafka（有限场景）、PostgreSQL 事件表 | Kafka、RabbitMQ、NATS、Pulsar、Redis Stream |

> 关键结论：事件溯源回答“状态从哪里来”，消息传输回答“通知怎么分发”。一个系统可以同时使用两者——用事件溯源保存聚合状态，用消息中间件把领域事件广播给外部消费者。

## 1.47.2 事件存储机制

事件存储（Event Store）是事件溯源的基础设施，其物理形态必须满足三条约束：

1. **追加写入（Append-Only）**：新事件只追加不修改旧事件，保证历史不可篡改。
2. **流内有序**：同一聚合（aggregate）的事件按写入顺序存储，读取时顺序一致。
3. **全局或分区顺序**：跨聚合通常不提供全局顺序，但可通过分区（stream/category）保证局部顺序。

### 并发控制

多个命令同时修改同一聚合时，需要乐观并发控制（Optimistic Concurrency Control）。典型做法是在写入时携带 `expected_version`：若服务端实际版本与期望值不一致，则拒绝写入并返回并发冲突。

```sql
-- PostgreSQL 风格的事件表（optimistic concurrency control）
CREATE TABLE events (
    stream_id    VARCHAR(255) NOT NULL,
    version      BIGINT       NOT NULL,
    event_type   VARCHAR(255) NOT NULL,
    payload      JSONB        NOT NULL,
    metadata     JSONB,
    occurred_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    PRIMARY KEY (stream_id, version)
);

-- 写入时检查 expected_version
INSERT INTO events (stream_id, version, event_type, payload)
SELECT 'order-123', 3, 'OrderPaid', '{"amount": 100}'
WHERE (SELECT COALESCE(MAX(version), 0) FROM events WHERE stream_id = 'order-123') = 2;
```

```csharp
// EventStoreDB/KurrentDB 风格：append with expected stream revision
var result = await client.AppendToStreamAsync(
    streamName: "order-123",
    expectedState: StreamState.StreamRevision(2), // expected_version = 2
    eventData: new[] { orderPaidEvent }
);
// WrongExpectedVersionError 表示并发冲突
```

### 分区与顺序

【论证】在分布式事件存储中，严格全局顺序会限制写入并发。工程上通常按 `stream_id` 或聚合类型分区：流内全序、流间无序。Kafka 的分区（partition）与此思想一致，但 Kafka 不保证跨分区顺序；EventStoreDB 的 stream 则天然以单个聚合为顺序边界。

## 1.47.3 聚合重建与快照

聚合（Aggregate）的当前状态通过重放其事件流得到：

```text
state(aggregate) = fold(apply, events_from(stream_id))
```

重建算法通常封装在 Repository 中：

```python
class OrderRepository:
    def load(self, stream_id: str) -> Order:
        events = self.store.read_stream(stream_id)
        order = Order()
        for e in events:
            order.apply(e)          # 每个事件调用聚合上的 apply 方法
        return order

    def save(self, order: Order):
        self.store.append(order.stream_id, order.uncommitted_events, expected_version=order.version)
        order.uncommitted_events.clear()
```

### 快照策略

当事件流很长时，每次从头重放代价高。快照是在某一版本上对聚合状态的冻结，常见触发策略：

| 策略 | 触发条件 | 优点 | 风险 |
| --- | --- | --- | --- |
| 每 N 个事件 | 版本 mod N == 0 | 实现简单，重放次数可控 | N 过大仍慢，N 过小快照开销大 |
| 大小阈值 | 快照文件/状态对象超过 X MB | 避免大状态内存膨胀 | 阈值选择依赖业务 |
| 时间窗口 | 每 T 分钟强制一次 | 保证恢复时间上限 | 可能产生大量冗余快照 |
| 手动触发 | 运维或发布前触发 | 灵活 | 易遗漏 |

### 快照与事件一致性

快照本身不是真相源，必须满足：

1. **先写事件后写快照**：事件是权威的，快照只是缓存。
2. **快照带版本戳**：重建时读取版本 `v` 的快照，再重放 `> v` 的事件。
3. **允许快照过期/缺失**：系统应能在无快照时完整重放事件重建状态。

## 1.47.4 投影与读取模型

投影（Projection）是把事件流转换为读模型的过程。读模型通常为去规范化（denormalized）视图，针对查询优化。

```sql
-- 读模型表示例：按订单状态的查询视图
CREATE TABLE order_summary (
    order_id    VARCHAR(255) PRIMARY KEY,
    status      VARCHAR(32) NOT NULL,
    total_amount DECIMAL(18,2) NOT NULL,
    version     BIGINT       NOT NULL,
    updated_at  TIMESTAMPTZ  NOT NULL
);

-- 投影处理器消费事件后 UPSERT 读模型
INSERT INTO order_summary (order_id, status, total_amount, version, updated_at)
VALUES ('order-123', 'PAID', 100.00, 3, NOW())
ON CONFLICT (order_id) DO UPDATE
SET status = EXCLUDED.status,
    total_amount = EXCLUDED.total_amount,
    version = EXCLUDED.version,
    updated_at = EXCLUDED.updated_at;
```

投影故障时，常见恢复手段是**从某一检查点重放事件并重建读模型**。重建期间应暂停该读模型的在线查询，或提供过期数据读取开关。

### 投影滞后监控

| 指标 | 含义 | 建议阈值 |
| --- | --- | --- |
| projection_lag_ms | 读模型最后更新时间 与 最新事件时间 之差 | < 1000 ms（实时视图） |
| events_behind | 投影消费者落后事件存储的条数 | < 1000 条或按业务定 |
| replay_duration_s | 全量重放耗时 | < RTO 目标的 50% |
| failed_projection_count | 投影失败次数/分钟 | = 0 |

> 上表阈值均为【估算】，需按业务 SLO 与数据量调整。

## 1.47.5 事件 schema 演进

事件 schema 会随业务变化。事件溯源要求旧事件长期可读，因此 schema 变更策略比传统 CRUD 更严格。

### Upcaster 模式

Upcaster 在读取旧事件时将其转换为当前 schema，常用于字段新增、重命名或类型扩展。

```python
class OrderCreatedUpcaster:
    def upcast(self, old_event: dict) -> dict:
        # v1: {order_id, amount}
        # v2: {order_id, amount, currency}
        if "currency" not in old_event:
            old_event["currency"] = "CNY"  # 默认值由业务语义决定
        return old_event
```

### 双写迁移

当 schema 发生不兼容变更时，可让发布者在一段时间内同时写入新旧两个版本的事件，消费者逐步迁移。该方法与 [2.35 消息版本兼容设计](../02-场景驱动架构设计/02-35-消息版本兼容设计.md) 中的“版本共存”策略一致。

### 破坏性变更处理

| 变更类型 | 是否允许 | 推荐做法 |
| --- | --- | --- |
| 新增可选字段 | 是 | 使用默认值或 upcaster |
| 字段重命名 | 谨慎 | 双写新旧字段，或 upcaster 映射 |
| 删除字段 | 不建议 | 标记为 deprecated，保留至少 N 个版本 |
| 改变事件语义 | 禁止 | 引入新事件类型，旧事件继续存在 |
| 修改事件类型名 | 谨慎 | 使用别名表或 upcaster 映射 |

> 更系统的 schema 演进与兼容性检查清单见 [03-51 消息版本兼容与迁移指南](../03-架构与运维实践/03-51-消息版本兼容与迁移指南.md)。

## 1.47.6 事件存储技术选型

### 各方案现状（核实至 2026-11）

- **KurrentDB / EventStoreDB**：原 EventStoreDB 已 rebranded 为 KurrentDB。官方 Releases 页面显示当前主线为 26.2（2026-09-30 发布），具备原生 stream、投影、持久订阅、多字段索引与 SQL 访问能力。
- **Apache Kafka**：截至 2026-11，官方当前受支持版本为 4.4.0（2026-10-22 发布）。Kafka 可作为事件日志，但用作事件存储时有明确边界。
- **PostgreSQL**：截至 2026-11，当前稳定主线为 18.x（18.7 于 2026-11-13 发布），19 处于 RC 阶段。以单表/分区表保存事件是常见轻量实现。
- **Redis**：截至 2026-11，Redis 开源最新稳定版为 8.10。Redis Streams（自 5.0 引入）可作为轻量事件日志，适合小流量、短保留、低延迟场景。

### 选型对比

| 维度 | KurrentDB 26.2 | Apache Kafka 4.4 | PostgreSQL 18.x | Redis Streams 8.10 |
| --- | --- | --- | --- | --- |
| 原生事件溯源语义 | 强：stream、expected version、投影 | 弱：需应用层封装 | 弱：需应用层表设计 | 弱：需应用层封装 |
| 流内顺序 | 按 stream 严格有序 | 分区内有序，跨分区无序 | 由主键/自增列保证 | 单 stream 严格有序 |
| 快照支持 | 内置快照与投影 | 应用层实现 | 应用层实现 | 应用层实现 |
| 订阅/投影 | 持久订阅、内置投影 | Consumer Group + Kafka Streams | 触发器、CDC、应用轮询 | 消费者组 XREADGROUP |
| 长期保留 | 支持，可配置保留策略 | 受 retention/存储成本限制 | 强，关系库备份成熟 | 受内存/持久化容量限制 |
| 运维复杂度 | 中等，专用事件存储 | 高，需管理集群与 topic | 低，团队熟悉 | 低，但集群扩展有限 |
| 适用规模 | 中大型核心业务 | 高吞吐事件骨干 | 中小规模、事务型业务 | 小流量、实时轻量 |
| 许可证 | Kurrent 商业/开源双许可 | Apache-2.0 | PostgreSQL License | SSPL/RSALv2/AGPLv3 |

> 上表“适用规模”列为【估算】，需结合具体吞吐、保留周期与团队能力评估。

### Kafka 作为事件存储的适用边界

【论证】Kafka 的 append-only log、分区顺序与高吞吐使其常被用来“近似”事件存储，但 Kafka 缺少以下事件存储原语：

1. **按聚合的 expected-version 并发控制**：需应用层在消息 key 或外部表中维护版本。
2. **全局/跨分区顺序保证**：Kafka 只在分区内保序。
3. **原生快照机制**：快照需在外部数据库维护。
4. **事件不可删除但可过期**：Kafka 的 retention 与 compaction 会导致旧事件丢失，不适合“永久审计”场景。

因此，Kafka 更适合作为**事件传输骨干**或**短期事件日志**，而非长期、强审计要求的唯一事件真相源。
