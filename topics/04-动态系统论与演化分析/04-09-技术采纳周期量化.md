## 4.09.1 阶段模型的可测度化

04-06 将六系统分为 niche、breakout、dominance、renewal、风险态五阶段【论证】。可测度化要求把文字判据转化为可采集、可追踪、可复核的代理指标，并承认其局限（P3 体系）。

阶段判定从“单点快照”转向“多指标时序组合”：

```text
stage(t) = f( star_velocity(t), pull_velocity(t), job_mentions(t),
              so_questions(t), managed_services(t), protocol_clones(t) )
```

其中各代理指标为相对增速或生态存在性，不依赖难以核实的绝对市场份额【论证】。

阶段迁移判据的设计原则：

1. **领先指标优先**：生态位占领（云厂商托管、CNCF 景观、关键集成）通常领先于市场份额；
2. **多源交叉验证**：单一代理易被操纵（如刷星），需至少两个独立来源同向变化；
3. **区分存量与增量**：dominance 阶段看存量规模，renewal 阶段看形态级发布频率。

## 4.09.2 四类代理指标与局限

| 代理指标 | 可测度信号 | 优势 | 局限 |
| ---- | ---- | ---- | ---- |
| **GitHub star 增速** | 月环比/年同比增速；贡献者 PR 数 | 公开、免费、可追溯 | 易被营销事件脉冲；star≠采用；私有仓库不可见 |
| **Docker pulls / 镜像下载** | 官方镜像拉取量趋势 | 反映部署尝试与 PoC | 包含 CI 重复拉取；无法区分生产与实验 |
| **招聘量/职位提及** | 招聘网站关键词出现频次 | 直接关联生产采用与人才需求 | 滞后 6-12 个月；头部公司招聘描述不精确 |
| **Stack Overflow 问题量/标签数** | 新标签问题数、回答率 | 反映开发者活跃度与学习曲线 | 成熟系统问题增速下降不代表衰退，可能是文档成熟 |

四类指标的共同局限：都偏向**英文互联网与开源项目**，对企业内部采购、云托管服务、中国市场采用存在显著抽样偏差【论证】。因此 04-06 的定性判据仍不可被代理指标完全替代。

### 4.09.2.1 指标采集口径示例

为了把四类代理指标落地为可复现的数据集，建议维护如下 TSV 结构【论证】：

```text
# metrics/mq-adoption-indicators.tsv
system date metric value source notes
kafka 2026-10 github_star_delta + api.github.com 月环比方向
kafka 2026-10 docker_pulls_delta + hub.docker.com 仅官方镜像
kafka 2026-10 job_mentions_delta + linkedin/indeed 关键词方向
kafka 2026-10 so_questions_delta - stackoverflow.com 成熟系统问题增速下降
```

采集原则：

1. **方向优先于绝对值**：由于各平台统计口径不同，记录“上升/平稳/下降”比比较跨平台数值更可靠；
2. **标注外生事件**：融资、收购、许可变更、重大发布当月必须加 `event` 标签，避免把脉冲误判为趋势；
3. **季度复核**：每月自动采集，每季度人工审计一次噪声源。

## 4.09.3 六系统 2021-2026 趋势叙述

以下趋势描述基于公开来源与行业景观分析，禁止编造绝对数字；未标注数字处均为方向性判断【论证】。

| 系统 | 2021-2023 态势 | 2024-2026 态势 | 关键证据方向 |
| ---- | ---- | ---- | ---- |
| **Kafka** | 已 dominance，KRaft 推进中 | 进入 renewal：KRaft GA（4.0）、队列语义（KIP-932 EA→GA）、云原生分层存储 | 官方 KIP 列表、行业分析 |
| **RabbitMQ** | dominance（企业队列） | renewal：Streams 日志化、Quorum Queue 成熟、4.x 系列现代化 | 官方发布说明、MQ 生态报告 |
| **Redis Stream** | niche（Redis 生态附属） | 向 breakout 移动：Redis Stack、Valkey 分叉后生态重配 | Redis/Valkey 官方动态 |
| **NATS** | breakout（云原生域） | 逼近 dominance（云原生域）：JetStream 持久化成熟、KEDA scaler、CNCF 景观 | NATS 官方博客、CNCF 景观 |
| **Pulsar** | breakout | 持续 breakout：Oxia 元数据层、存算分离强化，但大众采用增速平稳 | StreamNative 博客、行业景观 |
| **RocketMQ** | dominance（中国交易域） | dominance 维持：阿里云内核化、5.x 发布，国际化程度有限 | Apache RocketMQ 发布记录 |
| **Redpanda** | niche→breakout | breakout 深化：C++ 无 JVM、Kafka 兼容、云产品扩展，但尚未跨出 early-majority | Redpanda 官方发布、融资/收购新闻 |

具体观察【论证】：

- **Kafka**：从“日志平台”向“统一流数据平台”renewal，核心标志是 KIP-932（Queues for Kafka）在 4.2/4.3 中走向生产就绪（[Kafka 2025 Wrapped](https://blog.2minutestreaming.com/p/apache-kafka-2025-recap)）。这一 renewal 是维持 dominance 的必要条件（04-06 §4.06.5）。
- **NATS**：JetStream  persistence 与 MQTT 桥接使其从“微服务消息总线”扩展到“轻量流平台”，在云原生与边缘场景形成独立生态位。
- **Pulsar**：技术特性领先，但 star/招聘/职位提及增速落后于其技术创新速度，显示 breakout 阶段的“技术-市场”时差。
- **Redpanda**：作为 Kafka 兼容者中最具品牌力的一员，其增速受 Kafka 兼容策略囚徒困境约束（04-08），但在无 JVM 与低延迟 niche 中建立了差异化认知。

## 4.09.4 阶段迁移的先行指标

阶段迁移不是突变，而是指标组合跨越阈值的过程。下表给出各阶段迁移的先行信号【论证】。

| 迁移方向 | 先行指标 | 滞后指标 | 典型时间差 |
| ---- | ---- | ---- | ---- |
| niche → breakout | GitHub star 增速持续高于同类；首个生产案例公开；云厂商/集成商支持 | 招聘职位数上升；SO 标签数增长 | 6-12 个月 |
| breakout → dominance | 竞品开始兼容其协议/语义；行业报告将其列为默认选项；书籍/课程涌现 | 大企业招标占比；人才市场渗透率 | 1-3 年 |
| dominance → renewal | 形态级发布（新存储模型/新语义/云原生重构）；自我革命信号 | 旧版本用户迁移率；生态工具更新 | 2-5 年 |
| dominance → 风险态 | 许可变更/收购/社区分裂事件；核心贡献者流失 | 招聘热度下降；迁移咨询增多 | 不确定 |

工程判据【估算】：当“托管服务数量 + 关键集成数量 + 招聘职位增速”三项中至少两项连续两个季度同向变化，可判定阶段迁移进入临界窗口。

### 4.09.4.1 先行指标权重（示例）

不同场景下各指标的预测权重应动态调整【论证】：

| 场景 | GitHub star | Docker pulls | 招聘量 | SO 问题 | 托管/集成 |
| ---- | :---: | :---: | :---: | :---: | :---: |
| 云原生初创项目 | 高 | 中 | 低 | 低 | 高 |
| 企业级成熟项目 | 低 | 低 | 高 | 中 | 高 |
| 中国本土项目 | 中 | 低 | 中 | 低 | 低 |
| 开发者工具型项目 | 高 | 中 | 低 | 高 | 中 |

权重的核心思想：没有普适的“采纳指数”，只有与目标用户画像匹配的组合指标。

## 4.09.5 S 曲线拟合的适用与陷阱

技术采纳生命周期常用 Logistic/S 曲线描述：

```text
N(t) = K / (1 + exp(-r·(t - t0)))

K = 市场容量上限（可随时间变化）
r = 采纳速度参数
t0 = 拐点时间
```

适用场景【论证】：

- 单一技术替代单一旧技术（如 Kafka 替代传统 MQ 的早期阶段）；
- 市场边界清晰、无重大外生冲击；
- 有 5 年以上高质量时间序列数据。

陷阱【论证】：

1. **K 不是常数**：云原生、AI 数据管道、边缘计算不断扩展消息系统的市场边界，K 本身在增长；
2. **多 S 曲线叠加**：Kafka 自身经历“本地部署→K8s→云原生→AI 管道”多波采用，单一 S 曲线会过度平滑；
3. **外生冲击**：IBM-Confluent 收购、Redis AGPL 变更、WarpStream 被收购等事件使曲线断裂；
4. **数据质量**：GitHub star 与 Docker pulls 包含大量噪声，拟合结果对初值敏感。

因此，S 曲线应作为**趋势可视化工具**，而非预测黑箱。工程上更可靠的做法是跟踪先行指标组合，而非拟合单一曲线。

```python
# 示意：用 scipy 拟合 Logistic 曲线的最小代码片段
# 注意：拟合前必须清洗 star/pull 噪声并检查 K 的稳定性
from scipy.optimize import curve_fit

def logistic(t, K, r, t0):
    return K / (1 + np.exp(-r * (t - t0)))

popt, _ = curve_fit(logistic, years, metric, p0=[1e6, 0.5, 2022])
# 拟合后必须做残差诊断与外生冲击标记
```

## 4.09.6 六系统阶段判定更新表

对照 04-06 §4.06.5 的阶段判定，结合 2026-11 可观测信号更新如下。标注 **▲** 表示相对 04-06 升级，**▼** 表示降级/风险上升，**—** 表示基本稳定。

| 系统 | 04-06 判定 | 2026-11 更新判定 | 变化标注 | 关键依据 |
| ---- | ---- | ---- | :---: | ---- |
| Kafka | dominance | dominance→renewal | ▲ | KRaft GA、Queues（KIP-932）生产就绪、分层存储深化 |
| RabbitMQ | dominance→renewal | dominance→renewal | — | Streams/Quorum Queue 现代化持续 |
| Redis Stream | niche→breakout | niche→breakout | — | 增速平稳，仍依赖 Redis 主生态 |
| NATS | breakout→dominance（云原生域） | breakout→dominance（云原生域） | — | JetStream/MQTT 桥接巩固云原生域地位 |
| Pulsar | breakout | breakout | — | 技术创新领先，市场采纳时差未收窄 |
| RocketMQ | dominance（交易域） | dominance（交易域） | — | 中国金融/交易域基本盘稳固 |
| Redpanda | breakout | breakout→dominance（早期） | ▲ | 品牌认知扩大，但仍受 Kafka 兼容策略约束 |

变化解读：

- **Kafka 进入 renewal**：这是 04-06 已预示但未明确标注的变化。renewal 不是衰退，而是为延续 dominance 的自我革命。
- **Redpanda 微升**：从“突破”向“早期主导”移动，但尚未达到跨域 dominance，仍被 Kafka 协议 ESS 锁定（04-08）。
- **Pulsar  stagnant breakout**：技术领先但市场采纳未跨越鸿沟，是 2026-11 最值得关注的“高潜低渗透”系统。

## 4.09.7 对选型与治理的含义

1. **用指标组合而不是单点流行度做选型**：GitHub star 高不意味着生产就绪；招聘职位少不意味着技术落后。
2. **关注 stage 迁移的临界窗口**：breakout→dominance 迁移期是性价比最高的采用窗口（生态足够成熟、竞争定价存在）；dominance→renewal 迁移期是评估旧投资兼容性的关键窗口。
3. **把代理指标纳入技术雷达**：每季度更新 star 增速、托管服务数、KIP/发布路线图三信号，作为 ROADMAP 复核输入。
4. **对 Pulsar 等“高潜低渗透”系统保持观察**：技术特性领先但市场滞后，适合作为风险对冲而非主路径。
5. **建立“反直觉”校验**：成熟系统 SO 问题增速下降常被误读为衰退，实际可能是文档成熟、社区问题已解决；新系统问题量低也可能因为用户基数小。
