## 3.53.1 限流需求

1. **流量控制**：在促销、秒杀或上游系统重放消息时，限制进入消息队列的峰值流量，防止 Broker CPU、内存、网络带宽被瞬间打满，避免下游消费端被压垮。
2. **资源保护**：通过设置 `rate.limit.producer.rate.per.second=1000`、`rate.limit.consumer.rate.per.second=1000` 等阈值，将 CPU 使用率控制在 80% 以下，内存使用率控制在 85% 以下，网络带宽使用率控制在 70% 以下。
3. **公平性保证**：在多租户共享集群中，按租户或用户分配配额，例如 `rate.limit.user.rate.per.second=100`、`rate.limit.user.quota.daily=1000000`，防止单一租户占用全部资源。

## 3.53.2 生产者限速配置

### Kafka Producer 限速

Kafka 生产者主要通过客户端参数实现发送侧限速，通用流控参数还可参考 `flow-control-config.properties`，关键参数如下：

- `max.in.flight.requests.per.connection=5`：限制每个连接的并发未确认请求数，避免网络拥塞。
- `batch.size=16384`：默认批量 16 KB，可增大到 32768 以提升吞吐，但会提高延迟。
- `linger.ms=10`：发送前等待 10 ms 聚合消息，配合 `batch.size` 使用。
- `buffer.memory=33554432`：生产者缓冲区 32 MB，超过后 `send()` 将阻塞。

```properties
# rate-limit-config.properties
rate.limit.producer.enabled=true
rate.limit.producer.strategy=token_bucket
rate.limit.producer.rate.per.second=1000
rate.limit.producer.burst.size=2000
rate.limit.producer.max.in.flight.requests=5
rate.limit.producer.batch.size=16384
rate.limit.producer.linger.ms=10
```

应用层令牌桶示例（Guava RateLimiter）：

```java
RateLimiter rateLimiter = RateLimiter.create(1000.0); // 每秒 1000 条
for (String msg : messages) {
    rateLimiter.acquire();
    producer.send(new ProducerRecord<>("orders", msg));
}
```

### NATS / RabbitMQ Producer 限速

NATS 与 RabbitMQ 生产侧均无原生速率限制，需在应用层通过 `rate.Limiter`（Go）或 `RateLimiter`（Python）在 `Publish` / `basic_publish` 前获取令牌。当 RabbitMQ 连接被流控阻塞时，会发送 `connection.blocked` 通知，应用应监听并暂停发送。

### 生产者限速参数对比

| 系统 | 关键参数 | 推荐值 | 说明 |
| ------ | ---------- | -------- | ------ |
| Kafka | `max.in.flight.requests.per.connection` | 5 | 控制单连接并发请求 |
| Kafka | `batch.size` | 16384-32768 | 批量发送大小 |
| Kafka | `linger.ms` | 10-100 | 聚合等待时间 |
| NATS | `rate.Limiter` | 1000/s | 应用层令牌桶 |
| RabbitMQ | `basic.publish` + 应用层限流 | 1000/s | 应用层令牌桶 |

## 3.53.3 消费者限速配置

### Kafka Consumer 限速

- `max.poll.records=500`：单次 poll 最多拉取 500 条，避免一次处理过多消息。
- `fetch.min.bytes=1`：至少拉取 1 字节才返回。
- `fetch.max.wait.ms=500`：最长等待 500 ms 返回数据。
- `max.partition.fetch.bytes=1048576`：每个分区单次拉取最大 1 MB。

```properties
# rate-limit-config.properties
rate.limit.consumer.enabled=true
rate.limit.consumer.strategy=token_bucket
rate.limit.consumer.rate.per.second=1000
rate.limit.consumer.burst.size=2000
rate.limit.consumer.max.poll.records=500
rate.limit.consumer.fetch.min.bytes=1
rate.limit.consumer.fetch.max.wait.ms=500
rate.limit.consumer.max.partition.fetch.bytes=1048576
```

### NATS Consumer 限速

使用 `SetPendingLimits` 控制订阅缓冲区：

```go
sub, _ := nc.Subscribe("orders.*", func(msg *nats.Msg) {
    processMessage(msg)
})
sub.SetPendingLimits(1000, 10*1024*1024) // 1000 条或 10 MB
```

### RabbitMQ Consumer 限速

通过 `basic_qos` 设置 `prefetch_count`：

```python
channel.basic_qos(prefetch_count=10, prefetch_size=0, global_=False)
```

## 3.53.4 配额管理

### 全局限流

全局限流保护整个集群，模板配置为：

```properties
rate.limit.global.enabled=true
rate.limit.global.strategy=token_bucket
rate.limit.global.rate.per.second=10000
rate.limit.global.burst.size=20000
```

### 分区限流

Kafka 按 Topic 分区限速，可防止热点分区拖垮 Broker：

```properties
rate.limit.partition.enabled=true
rate.limit.partition.strategy=token_bucket
rate.limit.partition.rate.per.second=1000
rate.limit.partition.burst.size=2000
```

### 用户/租户配额

多租户场景下，按用户或租户设置配额：

```properties
rate.limit.user.enabled=true
rate.limit.user.strategy=token_bucket
rate.limit.user.rate.per.second=100
rate.limit.user.burst.size=200
rate.limit.user.quota.enabled=true
rate.limit.user.quota.daily=1000000

rate.limit.multitenant.enabled=true
rate.limit.multitenant.strategy=per_tenant
rate.limit.multitenant.per.tenant.rate=1000
rate.limit.multitenant.shared.rate=10000
rate.limit.multitenant.priority.enabled=true
rate.limit.multitenant.priority.levels=3
```

Kafka 服务端可通过 `kafka-configs.sh` 设置用户配额：

```bash
kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --add-config 'producer_byte_rate=1024000,consumer_byte_rate=1024000' \
  --entity-type users --entity-name app_user_1
```

## 3.53.5 背压处理

背压（Backpressure）是当消费端处理速度低于生产速度时，向上游传递反压信号的机制。

### 背压触发条件

- 消费延迟（Consumer Lag）持续增长，例如 Kafka `kafka_consumer_lag_sum > 100000`。
- 队列消息积压超过阈值，例如 RabbitMQ `rabbitmq_queue_messages > 100000`。
- 应用处理耗时 P99 超过 `timeout.degrade.threshold.ms=5000`。

### 背压处理策略

模板 `rate-limit-config.properties` 提供三种处理策略：

```properties
rate.limit.handling.strategy=wait        # reject/wait/degrade
rate.limit.handling.wait.timeout.ms=1000 # 等待超时 1 秒
rate.limit.handling.degrade.enabled=false
rate.limit.handling.degrade.strategy=skip # skip/retry_later
```

- **reject**：直接拒绝超限请求，返回限流错误码，适用于非关键消息。
- **wait**：阻塞等待直到获取令牌，等待超过 `wait.timeout.ms` 后降级或拒绝。
- **degrade**：将超限消息暂存到本地存储或死信队列，稍后异步补偿。

### 流控监控指标

```properties
rate.limit.monitor.enabled=true
rate.limit.monitor.metrics=rate_limit_rate,rate_limit_rejected,rate_limit_waiting
rate.limit.monitor.alert.enabled=true
rate.limit.monitor.alert.rejected.rate.threshold=0.1
rate.limit.monitor.alert.waiting.count.threshold=1000
```

## 3.53.6 流控测试

### 测试前检查

运行检查脚本：

```bash
bash topics/scripts/rate-limit-check.sh
```

脚本会检查 Kafka、NATS、RabbitMQ 的生产者与消费者限速参数是否符合推荐值。

### 压测命令

使用 `kafka-producer-perf-test.sh` 验证限流效果：

```bash
kafka-producer-perf-test.sh \
  --topic orders \
  --num-records 100000 \
  --record-size 1024 \
  --throughput 1000 \
  --producer-props bootstrap.servers=localhost:9092 \
  --producer-props max.in.flight.requests.per.connection=5 \
  --producer-props batch.size=16384 \
  --producer-props linger.ms=10
```

### 验证指标

- 实际吞吐是否稳定在 `--throughput 1000` 附近。
- `rate_limit_rejected_total` 是否低于 `rate.limit.monitor.alert.rejected.rate.threshold=0.1`。
- `rate_limit_waiting_count` 是否低于 `rate.limit.monitor.alert.waiting.count.threshold=1000`。

## 3.53.7 最佳实践

1. **分层限流**：组合全局、分区、用户三级限流，避免单点流量打满集群。
2. **令牌桶优先**：生产环境优先使用 `token_bucket` 策略，支持突发流量同时保证长期速率。
3. **阈值动态调整与告警联动**：通过配置中心下发 `rate.limit.producer.rate.per.second`、`rate.limit.consumer.rate.per.second`，并将 `rate_limit_rejected` 接入 Prometheus 告警，拒绝率超过 10% 触发 warning，超过 20% 触发 critical。
4. **自动调整兜底**：开启 `rate.limit.auto.adjust.enabled=true` 后，系统每 5 分钟根据目标拒绝率 5% 自动调整限流阈值，范围在 100-10000 之间。

## 3.53.8 限流控制检查清单

### 实施前

- [ ] 明确业务峰值 TPS/QPS，例如峰值 5000 msg/s，设定限流阈值保留 30% 余量。
- [ ] 选择限流策略：`fixed_window`、`sliding_window` 或 `token_bucket`。
- [ ] 确定限流粒度：全局 `rate.limit.global.enabled`、分区 `rate.limit.partition.enabled`、用户 `rate.limit.user.enabled`。
- [ ] 确认背压处理策略：`reject` / `wait` / `degrade`。

### 实施中

- [ ] 配置 Kafka Producer：`max.in.flight.requests.per.connection=5`、`batch.size=16384`、`linger.ms=10`。
- [ ] 配置 Kafka Consumer：`max.poll.records=500`、`fetch.max.wait.ms=500`、`max.partition.fetch.bytes=1048576`。
- [ ] 配置 NATS：`sub.SetPendingLimits(1000, 10*1024*1024)`。
- [ ] 配置 RabbitMQ：`basic_qos(prefetch_count=10, prefetch_size=0, global_=False)`。
- [ ] 配置多租户配额：`rate.limit.multitenant.per.tenant.rate=1000`、`rate.limit.user.quota.daily=1000000`。
- [ ] 部署限流监控指标：`rate_limit_rate`、`rate_limit_rejected`、`rate_limit_waiting`。

### 实施后

- [ ] 运行 `bash topics/scripts/rate-limit-check.sh` 检查配置是否符合推荐值。
- [ ] 使用 `kafka-producer-perf-test.sh --throughput 1000` 验证限流稳定性。
- [ ] 检查 Prometheus 中 `rate_limit_rejected_rate < 0.1` 是否持续满足。
- [ ] 每季度评估限流阈值，结合业务增长调整 `rate.limit.global.rate.per.second`。
