## 3.54.1 降级需求

1. **系统过载**：当 CPU 使用率超过 80%、内存超过 85%、消息队列积压超过 10 万条时，需要触发降级，优先保障核心链路。
2. **服务故障**：下游服务超时或不可用时，例如下游接口 P99 延迟超过 `timeout.degrade.threshold.ms=5000`，应切换为本地存储或异步补偿。
3. **业务降级**：通过功能开关关闭非核心功能，例如关闭消息审计、延迟发送推荐消息，将资源让渡给订单、支付等核心 Topic。

## 3.54.2 降级开关

### 功能开关配置

业务降级通过集中式配置或本地配置文件实现，模板参数为：

```properties
business.degrade.enabled=true
business.degrade.feature.switch.enabled=true
business.degrade.feature.switch.config.file=/etc/mq/feature-switch.json
business.degrade.priority.adjust.enabled=true
business.degrade.priority.levels=high,medium,low
```

### feature-switch.json 示例

```json
{
  "switches": {
    "order_message": { "enabled": true, "priority": "high" },
    "recommend_message": { "enabled": false, "priority": "low" },
    "audit_message": { "enabled": false, "priority": "low" }
  },
  "default_priority": "medium",
  "updated_at": "2026-01-06T00:00:00Z"
}
```

### 动态开关 API

对于 Java 服务，可通过 Actuator 端点暴露开关状态：

```bash
curl -X POST http://app:8080/actuator/degrade \
  -H "Content-Type: application/json" \
  -d '{"feature":"recommend_message","enabled":false}'
```

### 开关类型对比

| 开关类型 | 触发方式 | 恢复方式 | 适用场景 |
| ---------- | ---------- | ---------- | ---------- |
| 手动开关 | 运维平台/API | 手动恢复 | 大促前预案、人工演练 |
| 自动开关 | 熔断器/指标阈值 | 自动/手动 | 系统过载、下游故障 |
| 定时开关 | Cron 表达式 | 定时恢复 | 固定窗口维护、夜间低峰 |

## 3.54.3 熔断配置

### 熔断器参数

模板 `degrade-config.properties` 中的熔断器配置如下：

```properties
circuit.breaker.enabled=true
circuit.breaker.failure.threshold=5          # 60 秒内失败 5 次触发熔断
circuit.breaker.time.window.seconds=60       # 统计时间窗口 60 秒
circuit.breaker.half.open.timeout.seconds=10 # 熔断 10 秒后进入半开状态
circuit.breaker.success.threshold=3          # 半开状态连续 3 次成功恢复关闭
circuit.breaker.state.monitor.enabled=true
```

### 熔断器状态流转

- **Closed（关闭）**：正常调用，持续统计失败次数。
- **Open（打开）**：失败次数达到 `failure.threshold`，所有调用直接走降级逻辑。
- **Half-Open（半开）**：经过 `half.open.timeout.seconds` 后，允许少量探测请求。

### Resilience4j 熔断示例

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)               // 失败率 50% 触发
    .slowCallRateThreshold(80)              // 慢调用率 80% 触发
    .slowCallDurationThreshold(Duration.ofSeconds(5))
    .permittedNumberOfCallsInHalfOpenState(3)
    .slidingWindowSize(10)
    .waitDurationInOpenState(Duration.ofSeconds(10))
    .build();

CircuitBreakerRegistry registry = CircuitBreakerRegistry.of(config);
CircuitBreaker cb = registry.circuitBreaker("messageProducer");

Supplier<String> decorated = CircuitBreaker.decorateSupplier(cb, () -> {
    producer.send(record);
    return "OK";
});
Try.ofSupplier(decorated).recover(throwable -> {
    degradeToLocalFile(record);
    return "DEGRADED";
});
```

### 限流降级与超时降级

```properties
rate.limit.degrade.enabled=true
rate.limit.degrade.threshold=0.8              # 80% 限流触发降级
rate.limit.degrade.priority.enabled=true
rate.limit.degrade.priority.levels=3

timeout.degrade.enabled=true
timeout.degrade.threshold.ms=5000             # 5 秒超时触发降级
timeout.degrade.fast.fail.enabled=true
```

## 3.54.4 优雅降级流程

### 降级处理配置

```properties
degrade.handling.strategy=local_storage       # local_storage/async_compensate/notification
degrade.handling.local.storage.enabled=true
degrade.handling.local.storage.path=/var/mq/degrade
degrade.handling.local.storage.max.size=10GB
degrade.handling.async.compensate.enabled=true
degrade.handling.async.compensate.interval.seconds=60
degrade.handling.notification.enabled=true
degrade.handling.notification.channels=email,slack
```

### 标准降级流程

1. **检测**：监控指标触发阈值（错误率 > 10%、延迟 P99 > 5s、积压 > 10 万）。
2. **决策**：根据 `degrade.trigger.condition` 判断是系统过载、服务故障还是业务降级。
3. **执行**：
   - 关闭低优先级功能开关；
   - 打开熔断器，新请求写入本地存储 `/var/mq/degrade`；
   - 发送降级通知到 `email,slack` 渠道。
4. **补偿**：异步补偿任务每 60 秒扫描本地存储，待服务恢复后重新投递。
5. **恢复**：熔断器半开探测成功 3 次后关闭，或运维手动调用 API 恢复。

### 本地存储 Java 示例

```java
public class LocalDegradeStorage {
    private final Path storagePath = Paths.get("/var/mq/degrade");

    public void save(ProducerRecord<String, String> record) throws IOException {
        String line = String.format("%s\t%s\t%s\n", Instant.now(), record.topic(), record.value());
        Files.writeString(storagePath.resolve("degrade.log"), line,
                          StandardOpenOption.CREATE, StandardOpenOption.APPEND);
    }
}
```

## 3.54.5 容错演练

### 演练目标

验证降级开关、熔断器、本地存储、异步补偿、通知渠道在真实故障场景下按预期工作。

### 演练场景

| 场景 | 注入方式 | 预期结果 |
| ------ | ---------- | ---------- |
| 下游服务超时 | 使用 Chaos Monkey 增加 8s 延迟 | 熔断器打开，消息写入本地存储 |
| CPU 过载 | stress-ng 打满 80% CPU | 低优先级开关关闭，核心链路保持 |
| 队列积压 | 停止消费者 10 分钟 | 触发限流降级，拒绝低优先级消息 |
| Broker 网络分区 | iptables 隔离 Broker | 生产者切换至本地存储 |

### 演练步骤

1. **准备**：确认 `degrade-config.properties` 已加载，熔断器参数为 `failure.threshold=5`、`half.open.timeout.seconds=10`。
2. **基线**：记录正常状态下的吞吐、延迟、错误率。
3. **注入**：使用 Chaos Mesh 或 `tc qdisc` 注入延迟/丢包。
4. **观察**：检查 `degrade_count`、`degrade_rate`、`circuit_breaker_state` 指标。
5. **恢复**：移除故障，验证 30 秒内自动恢复或手动 API 恢复生效。
6. **复盘**：对比基线，确认降级窗口期内无核心消息丢失。

### 演练检查命令

```bash
# 检查降级配置
bash topics/scripts/degrade-check.sh

# 查看熔断器状态
curl http://app:8080/actuator/circuitbreakers

# 查看本地存储积压
wc -l /var/mq/degrade/degrade.log
du -sh /var/mq/degrade
```

## 3.54.6 最佳实践

1. **降级开关与配置中心联动**：将 `feature-switch.json` 接入 Nacos/Apollo，确保秒级生效。
2. **熔断器参数按服务差异化**：核心服务设置更敏感的阈值（`failure.threshold=3`），非核心服务可放宽到 10。
3. **本地存储设置容量上限**：`degrade.handling.local.storage.max.size=10GB`，超过后切换为丢弃并告警。
4. **异步补偿幂等**：补偿任务投递时携带唯一业务键，避免重复消费。
5. **降级即告警**：任何一次自动降级都应通过 AlertManager 通知值班人员，避免静默降级。
6. **定期演练**：每季度至少执行一次全链路降级演练，更新降级预案。

## 3.54.7 降级容错检查清单

### 实施前

- [ ] 梳理核心与非核心功能列表，划分 `high/medium/low` 优先级。
- [ ] 制定 `feature-switch.json` 初始状态，明确哪些功能可降级。
- [ ] 选择降级触发条件：`system_overload`、`service_failure` 或 `business_degrade`。
- [ ] 设计本地存储路径 `/var/mq/degrade` 与容量上限 `10GB`。

### 实施中

- [ ] 配置熔断器：`failure.threshold=5`、`time.window.seconds=60`、`half.open.timeout.seconds=10`、`success.threshold=3`。
- [ ] 配置限流降级：`rate.limit.degrade.threshold=0.8`。
- [ ] 配置超时降级：`timeout.degrade.threshold.ms=5000`、`timeout.degrade.fast.fail.enabled=true`。
- [ ] 启用本地存储：`degrade.handling.local.storage.enabled=true`、`max.size=10GB`。
- [ ] 启用异步补偿：`degrade.handling.async.compensate.interval.seconds=60`。
- [ ] 启用通知渠道：`degrade.handling.notification.channels=email,slack`。
- [ ] 部署监控指标：`degrade_count`、`degrade_rate`、`recovery_count`、`circuit_breaker_state`。

### 实施后

- [ ] 运行 `bash topics/scripts/degrade-check.sh` 验证配置完整性。
- [ ] 演练下游超时场景，确认熔断器 5 次失败后打开。
- [ ] 演练 CPU 过载场景，确认低优先级功能开关关闭。
- [ ] 验证本地存储写入与异步补偿投递的幂等性。
- [ ] 检查 `degrade.monitor.alert.degrade.rate.threshold=0.1` 与 `circuit.breaker.open.duration.seconds=300` 告警是否触发。
- [ ] 每季度复盘并更新 `feature-switch.json` 与演练报告。
