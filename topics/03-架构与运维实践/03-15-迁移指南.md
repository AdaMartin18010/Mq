## 3.15.1 迁移类型与决策矩阵

消息队列迁移按风险与操作对象可分为四类：

| 迁移类型 | 典型场景 | 停机要求 | 风险等级 | 推荐策略 |
| --------- | ---------- | ---------- | ---------- | ---------- |
| **版本升级迁移** | Kafka 2.x/3.x(ZK) → 3.9+ / 4.x(KRaft)；RabbitMQ 3.13 → 4.x | 可滚动 | 中 | 滚动升级 + 元数据迁移工具 |
| **架构迁移** | 单机 → 集群；VM → Kubernetes | 可灰度 | 中 | 新集群双写，老集群逐步下线 |
| **系统间迁移** | RabbitMQ → Kafka；Kafka → Pulsar | 通常需双写过渡期 | 高 | 双写 + 消费者逐步切流 |
| **协议迁移** | MQTT 3.1.1 → 5.0；AMQP 0-9-1 → 1.0 | 可滚动 | 低 | 客户端逐批次升级 |

迁移策略选择需同时评估 **RTO（恢复时间目标）** 与 **RPO（恢复点目标）**【估算：生产系统 RTO 通常要求 <1h，RPO <5min】。

## 3.15.2 迁移前准备

### 前置检查清单

- [ ] 当前版本已记录：`kafka-broker-api-versions.sh --bootstrap-server localhost:9092 | head -3`
- [ ] 元数据已备份：Kafka 备份 `meta.properties`、RabbitMQ 导出 `definitions.json`
- [ ] 客户端兼容性已确认：检查 Kafka `inter.broker.protocol.version`、RabbitMQ 客户端版本
- [ ] 监控与告警已覆盖新旧两套环境
- [ ] 回滚脚本已测试并通过，回滚时间 < RTO 目标
- [ ] 业务低峰期窗口已申请，并通知上下游团队

### 通用备份命令

```bash
# Kafka 元数据与配置备份（ZK 模式示例）
tar -czf kafka-config-backup-$(date +%Y%m%d).tar.gz \
  /opt/kafka/config/server.properties \
  /opt/kafka/logs/meta.properties \
  /opt/kafka/logs/__consumer_offsets-*

# RabbitMQ 定义导出
rabbitmqctl export_definitions rabbitmq-definitions-$(date +%Y%m%d).json
```

## 3.15.3 Kafka ZooKeeper → KRaft 迁移

> **时效声明**: 本文 Kafka 版本事实基于 Apache Kafka 官方发布信息，核实至 2026-11。

Kafka 4.0 已完全移除 ZooKeeper 支持，3.9 是最后一个同时支持 ZK 与 KRaft 的发布线[Apache Kafka KRaft vs ZooKeeper](https://kafka.apache.org/40/getting-started/zk2kraft/)。迁移必须借助官方迁移工具完成，分为五个阶段【论证：Confluent 与 Apache 文档均描述五阶段流程】[Migrate from ZooKeeper to KRaft on Confluent Platform](https://docs.confluent.io/platform/current/installation/migrate-zk-kraft.html)。

### 迁移步骤

1. **环境检查**

   ```bash
   # 确认当前 Broker 版本与元数据状态
   kafka-broker-api-versions.sh --bootstrap-server localhost:9092 | head -1
   ./scripts/version-compat-check.sh kafka
   ```

2. **部署 KRaft Controller 仲裁团**

   ```properties
   # config/kraft/controller.properties 示例
   process.roles=controller
   node.id=1001
   controller.quorum.voters=1001@controller1:9093,1002@controller2:9093,1003@controller3:9093
   listeners=CONTROLLER://:9093
   log.dirs=/var/lib/kafka/controller-logs
   ```

3. **执行元数据迁移**

   ```bash
   # 在 3.5.0+ 中使用 kafka-metadata-migration.sh（3.9 推荐）
   kafka-metadata-migration.sh --bootstrap-server localhost:9092 \
     --zookeeper localhost:2181 \
     --migrate
   ```

4. **验证 KRaft 元数据**

   ```bash
   kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
   kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic __consumer_offsets
   ```

5. **完成迁移并下线 ZK**

   ```bash
   kafka-metadata-migration.sh --bootstrap-server localhost:9092 \
     --zookeeper localhost:2181 \
     --finalize
   ```

### Kafka 迁移检查清单

- [ ] `process.roles` 已设置为 `broker` 或 `controller`，不存在 ZK 依赖
- [ ] `controller.quorum.voters` 为奇数节点（3/5/7）
- [ ] `inter.broker.protocol.version` 已升级至目标版本
- [ ] 所有 Topic 副本状态正常：`UnderReplicatedPartitions == 0`
- [ ] 消费者组位移已完整迁移：`kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list`

## 3.15.4 RabbitMQ 3.x → 4.x 迁移

> **时效声明**: 本文 RabbitMQ 版本事实基于 RabbitMQ 官方发布信息，核实至 2026-11。

RabbitMQ 4.0 已移除 classic queue mirroring，classic 队列在 4.x 中仅作为单节点队列存在；高可用复制队列必须使用 quorum queue[RabbitMQ Quorum Queues](https://www.rabbitmq.com/docs/quorum-queues)。迁移前必须先将 classic mirrored queue 迁移到 quorum queue。

### 迁移步骤

1. **检查是否仍在使用 classic mirroring**

   ```bash
   rabbitmq-queues check_if_cluster_has_classic_queue_mirroring_policy
   rabbitmq-diagnostics list_policies_with_classic_queue_mirroring
   ```

2. **声明 quorum queue 并切换流量**

   ```bash
   # 使用 rabbitmqadmin 声明 quorum queue
   rabbitmqadmin declare queue name=orders.v2 arguments='{"x-queue-type":"quorum"}'

   # 使用 Shovel 插件将 classic mirrored queue 消息 drain 到新队列
   rabbitmq-plugins enable rabbitmq_shovel
   ```

3. **升级至 4.x 并验证**

   ```bash
   # 逐节点滚动升级
   ./scripts/upgrade-check.sh rabbitmq
   rabbitmqctl status | grep "RabbitMQ version"
   rabbitmqctl cluster_status
   ```

### RabbitMQ 迁移检查清单

- [ ] `ha-mode` / `ha-params` / `ha-sync-mode` 策略已清理或废弃
- [ ] 关键队列已声明为 `x-queue-type=quorum`
- [ ] 队列定义文件（`definitions.json`）已更新为 4.x 兼容格式
- [ ] Erlang/OTP 版本满足 4.x 要求（参考官方 compatibility 表）
- [ ] 管理插件与监控指标在 4.x 下正常采集

## 3.15.5 系统间迁移（RabbitMQ → Kafka）

跨系统迁移的核心是**避免单点切换导致消息丢失**，推荐双写过渡方案。

### 实施步骤

1. **部署桥接/双写层**

   ```bash
   # 启用桥接配置（参考 config-templates/bridge-config.properties）
   bridge.source.type=rabbitmq
   bridge.source.rabbitmq.url=amqp://user:pass@rabbitmq:5672
   bridge.target.type=kafka
   bridge.target.kafka.bootstrap.servers=localhost:9092
   bridge.target.kafka.topic.mapping.orders=orders
   ```

2. **启动消费者影子验证**

   ```bash
   # 消费 Kafka 侧消息并与 RabbitMQ 侧对比
   kafka-console-consumer.sh --topic orders \
     --from-beginning --bootstrap-server localhost:9092 \
     > /tmp/kafka-orders.log

   # 对比消息数量与关键字段（示意性命令）
   wc -l /tmp/kafka-orders.log /tmp/rabbitmq-orders.log
   ```

3. **逐步切流**

   | 阶段 | Producer | Consumer | 验证项 |
   | ------ | ---------- | ---------- | -------- |
   | 阶段1 | 仅 RabbitMQ | 双读对比 | 消息顺序、字段一致性 |
   | 阶段2 | RabbitMQ + Kafka 双写 | 双读对比 | 延迟、重复率、幂等性 |
   | 阶段3 | 仅 Kafka | 仅 Kafka | 全量回归测试通过 |

## 3.15.6 迁移后验证

### 功能验证命令

```bash
# Kafka 端到端验证
kafka-producer-perf-test.sh --topic migrate-verify \
  --num-records 100000 --record-size 1024 --throughput 10000 \
  --producer-props bootstrap.servers=localhost:9092

# RabbitMQ 队列健康检查
rabbitmqctl list_queues name messages messages_ready messages_unacknowledged
```

### 验证检查清单

- [ ] 生产/消费端到端延迟 P99 < 目标阈值（如 1000ms）
- [ ] 消息无丢失：源系统与目标系统消息总量偏差 < 0.1%
- [ ] 消费者组 rebalancing 正常，无大面积 rebalance storm
- [ ] 监控告警无异常触发，持续观察 ≥ 1 个业务周期

## 3.15.7 回滚与兜底方案

任何迁移必须预设回滚路径：

- **版本升级回滚**：保留旧版本二进制与配置，使用 `./scripts/restore-all.sh <backup_dir>` 恢复配置
- **双写回滚**：保留旧系统写入开关，遇到异常可切回 `bridge.source.type` 为旧系统
- **数据兜底**：迁移期间对关键 Topic/Queue 开启额外副本或快照备份

```bash
# 快速回滚 Kafka 配置示例
./scripts/restore-all.sh /backup/kafka-config-backup-20261118
systemctl restart kafka
```
