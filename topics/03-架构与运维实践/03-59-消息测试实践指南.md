## 3.59.1 测试需求

消息测试需求应覆盖功能正确性、性能容量、可靠性及持续集成四个维度。功能测试要求对消息发送、消费、路由、过滤、优先级等场景进行验证；性能测试要求在基准负载、压力负载和稳定负载下分别测量吞吐量、延迟和资源占用；可靠性测试要求通过故障注入和混沌工程验证系统在异常条件下的表现；持续集成要求将上述测试接入 CI/CD 流水线，确保每次变更后自动执行。

在制定测试需求时，应参考 `topics/config-templates/test-config.properties` 中的配置项，明确 `test.functional.scenarios=send,consume,route,filter,priority` 的覆盖范围，设定 `test.performance.benchmark.messages.count=100000` 的基准消息量，以及 `test.reliability.fault.injection.probability=0.1` 的故障注入概率。测试环境必须独立隔离，配置 `test.environment.isolated=true`，避免对生产环境产生影响。

## 3.59.2 测试策略

### 3.59.2.1 单元测试策略

单元测试聚焦生产者、消费者、序列化器、路由规则等最小可测试单元。对 Kafka 应验证 `ProducerRecord` 构造、`Future<RecordMetadata>` 返回及异常分支；对 NATS 应验证 `nc.Publish` 与 `nc.Subscribe` 的回调行为；对 RabbitMQ 应验证 `channel.basic_publish` 与 `channel.basic_consume` 的 ACK 机制。单元测试不依赖真实 Broker，可使用内存嵌入式服务或 Mock 对象，执行时间应控制在毫秒级。

### 3.59.2.2 集成测试策略

集成测试验证消息队列与业务系统、数据库、Schema Registry 等外部组件的协同。测试范围包括：Topic/Queue 创建与删除、消息端到端投递、消费者组重平衡、死信队列处理、事务消息一致性。集成测试应在与生产同版本的中间件上进行，使用 `test.environment.type=staging` 标识环境，并在测试结束后启用 `test.environment.cleanup.enabled=true` 清理数据。

### 3.59.2.3 压力测试策略

压力测试通过逐步提升负载至设计容量的 1.5 倍至 2 倍，观察系统是否出现吞吐量下降、延迟陡增或错误率上升。关键参数包括 `test.performance.stress.messages.count=1000000`、`test.performance.stress.duration.seconds=300`。测试中需监控 CPU、内存、网络、磁盘四项资源，记录拐点处的 QPS 与 P99 延迟。

### 3.59.2.4 混沌测试策略

混沌测试模拟真实故障场景，验证系统自愈能力和数据完整性。典型场景包括 Broker 故障、网络分区、磁盘 IO 抖动、时钟漂移。配置 `test.reliability.chaos.scenarios=random_failure,cascading_failure`，并通过 Chaos Mesh 或自定义脚本注入故障。混沌测试应在非生产环境执行，且事先备份关键配置。

| 测试类型 | 测试对象 | 关键参数 | 通过标准 |
|---|---|---|---|
| 单元测试 | 生产者/消费者/路由规则 | 执行时间 < 5 分钟 | 覆盖率 ≥ 80% |
| 集成测试 | 端到端消息链路 | `test.functional.timeout.seconds=30` | 消息不丢不重 |
| 压力测试 | 系统极限容量 | `stress.messages.count=1000000` | 错误率 < 0.1% |
| 混沌测试 | 故障恢复能力 | `recovery.timeout.seconds=300` | 恢复后指标正常 |

## 3.59.3 测试方法

### 3.59.3.1 功能测试方法

功能测试采用黑盒与白盒相结合的方式。黑盒测试不关注内部实现，仅验证输入消息与输出结果是否符合预期；白盒测试覆盖分支路径，如重试逻辑、幂等校验、顺序保证。对 Kafka 可使用 `kafka-console-producer.sh` 与 `kafka-console-consumer.sh` 进行手工验证；对 RabbitMQ 可使用 Management UI 或 `rabbitmqadmin` 工具。

### 3.59.3.2 性能测试方法

性能测试使用 `topics/scripts/benchmark.sh` 执行。以 Kafka 为例，脚本调用 `kafka-producer-perf-test.sh`，参数为 `--num-records $((RATE * DURATION))`、`--record-size 1024`、`--throughput $RATE`、`acks=1 batch.size=16384 linger.ms=10`。NATS 使用 `nats-bench -s localhost:4222 -np 1 -ns 1 -n $((RATE * DURATION)) -ms 1024 -r $RATE`。RabbitMQ 使用 `rabbitmq-perf-test -x 1 -y 1 -u "amqp://guest:guest@localhost:5672" -s 1024 -r $RATE -z $DURATION`。

```bash
# Kafka 基准测试示例（60 秒、10000 msg/s）
./topics/scripts/benchmark.sh kafka 60 10000
```

### 3.59.3.3 可靠性测试方法

可靠性测试通过故障注入与恢复验证完成。对 Kafka 可执行 `kill -9 <kafka-pid>` 模拟 Broker 宕机，观察分区是否切换 Leader 及消息是否不丢；对 NATS 可断开集群节点网络，验证 JetStream 的 Raft 选主；对 RabbitMQ 可停止镜像队列中的一个节点，验证镜像同步。恢复时间应满足 `test.reliability.recovery.timeout.seconds=300` 的要求。

```bash
# 执行全量可靠性测试（功能、性能、可靠性）
./topics/scripts/message-test.sh all
```

### 3.59.3.4 混沌测试方法

混沌测试使用 Chaos Mesh 或自定义脚本。典型步骤为：1）定义稳态指标（吞吐量、错误率、P99 延迟）；2）选择注入故障（Pod 失败、网络延迟、CPU 满载）；3）执行实验并监控指标；4）回滚故障并验证恢复。混沌实验应配置回滚超时，确保实验结束后系统恢复正常。

## 3.59.4 测试环境搭建

### 3.59.4.1 环境规划

测试环境应与生产环境在版本、配置、网络拓扑上保持一致，但资源规模可按比例缩小。建议部署独立的 `test` 命名空间或独立集群，配置 `test.environment.isolated=true`。环境类型通过 `test.environment.type=staging` 区分，禁止直接连接生产 Broker。

### 3.59.4.2 工具链安装

功能测试依赖各消息队列的客户端 SDK；性能测试依赖 `kafka-producer-perf-test.sh`、`nats-bench`、`rabbitmq-perf-test`；可靠性测试依赖 `chaos-mesh` 或 `pumba`；报告生成依赖 JUnit、Allure 或自定义脚本。`test-config.properties` 中配置 `test.tools.jmeter.enabled=false`、`test.tools.k6.enabled=false`、`test.tools.chaos.enabled=false`，可根据需要开启。

### 3.59.4.3 测试数据准备

使用 `test.data.generation.enabled=true` 自动生成测试数据，配置 `test.data.generation.size=1000`、`test.data.generation.format=json`。若启用 Schema 校验，需指定 `test.data.generation.schema.file=/etc/mq/test-schema.json`。测试数据应覆盖正常值、边界值、异常值三种类型。

### 3.59.4.4 自动化流水线集成

在 CI/CD 中配置测试门禁，提交代码后自动触发单元测试与集成测试，合并前自动触发性能基线测试。`test-config.properties` 中设置 `test.automation.enabled=true`、`test.automation.ci.cd.integration=true`、`test.automation.schedule.cron=0 2 * * *`，实现每日凌晨两点自动执行全量回归。

## 3.59.5 验收标准

### 3.59.5.1 功能验收标准

- 消息发送成功率 ≥ 99.99%；
- 消息消费不丢失、不重复（开启幂等后重复率 ≤ 0.001%）；
- 消息路由规则 100% 命中预期队列或 Topic；
- 顺序消息场景下乱序率 = 0。

### 3.59.5.2 性能验收标准

- 基准测试吞吐量不低于设计目标；
- P99 延迟不超过业务 SLA，通常在线业务要求 P99 < 100ms；
- 压力测试下错误率 < 0.1%；
- 负载测试持续 10 分钟以上，资源利用率保持平稳。

### 3.59.5.3 可靠性验收标准

- 单 Broker 故障后，消息投递中断时间 < 30 秒；
- 网络分区恢复后，无消息丢失或重复消费；
- 磁盘故障场景下，已提交消息不丢失；
- 故障恢复时间满足 `test.reliability.recovery.timeout.seconds=300`。

## 3.59.6 最佳实践

1. **分层测试**：单元测试快速反馈，集成测试验证接口契约，端到端测试验证业务流程，性能与可靠性测试定期执行。
2. **基线管理**：每次重大变更前记录性能基线，将 `test.performance.benchmark.messages.count=100000` 结果与历史数据对比，识别回归。
3. **数据隔离**：测试 Topic/Queue 使用独立前缀，配置 `test.environment.cleanup.enabled=true` 和 `test.environment.cleanup.after.test=true`，防止数据污染。
4. **报告归档**：启用 `test.report.enabled=true`，输出格式 `test.report.format=html`，保留 30 天，包含 throughput、latency、error_rate、resource_usage 四项指标。
5. **持续改进**：根据 `test.coverage.functional.target=80`、`test.coverage.performance.target=100`、`test.coverage.reliability.target=70` 持续补充测试用例。

## 3.59.7 测试检查清单

### 实施前

- [ ] 已确认 `test.functional.scenarios` 包含 send、consume、route、filter、priority；
- [ ] 已配置 `test.environment.type=staging` 且 `test.environment.isolated=true`；
- [ ] 已准备 `test.data.generation.schema.file=/etc/mq/test-schema.json`；
- [ ] 已设定性能基线：`test.performance.benchmark.messages.count=100000`、`test.performance.benchmark.duration.seconds=60`；
- [ ] 已安装 `kafka-producer-perf-test.sh`、`nats-bench`、`rabbitmq-perf-test` 等性能工具；
- [ ] 已配置 CI/CD 门禁：`test.automation.enabled=true`、`test.automation.ci.cd.integration=true`。

### 实施中

- [ ] 单元测试覆盖率 ≥ 80%，且单次执行时间 < 5 分钟；
- [ ] 集成测试覆盖消息端到端投递、重平衡、死信队列；
- [ ] 性能测试使用 `benchmark.sh kafka|nats|rabbitmq [duration] [rate]` 执行；
- [ ] 压力测试消息量达到 `test.performance.stress.messages.count=1000000`；
- [ ] 混沌测试配置 `test.reliability.chaos.scenarios=random_failure,cascading_failure` 并记录稳态指标；
- [ ] 故障注入概率设置为 `test.reliability.fault.injection.probability=0.1`。

### 实施后

- [ ] 测试报告已输出到 `test.report.path=/var/mq/test-reports`，格式为 html；
- [ ] 报告包含 throughput、latency、error_rate、resource_usage 四项指标；
- [ ] 性能基线已归档并与历史版本对比；
- [ ] 发现的问题已修复并复测通过；
- [ ] 测试覆盖率满足 `test.coverage.functional.target=80`、`test.coverage.performance.target=100`、`test.coverage.reliability.target=70`；
- [ ] 已启用 `test.automation.schedule.cron=0 2 * * *` 自动回归。
