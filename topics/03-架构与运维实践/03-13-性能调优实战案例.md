## 3.13.1 Kafka性能调优案例

### 案例1：吞吐量优化

**问题**：Producer吞吐量仅10万TPS，目标100万+TPS

**调优前**（引用 [`config-templates/performance-tune-config.properties`](../../topics/config-templates/performance-tune-config.properties)）：

```properties
performance.tune.producer.batch.size=16384
performance.tune.producer.linger.ms=0
performance.tune.producer.compression.type=none
performance.tune.producer.acks=1
performance.tune.producer.buffer.memory=33554432
```

**调优后**：

```properties
# Kafka producer.properties
batch.size=65536        # 64KB批量
linger.ms=10            # 等待10ms批量发送
compression.type=lz4    # LZ4压缩，低CPU开销
acks=1                  # 平衡持久性与吞吐
buffer.memory=134217728 # 128MB缓冲区
max.in.flight.requests.per.connection=5
```

**效果**：吞吐量提升至120万TPS（提升12倍）

**配套脚本**：使用 [`scripts/performance-tune.sh`](../../topics/scripts/performance-tune.sh) 与 [`scripts/benchmark.sh`](../../topics/scripts/benchmark.sh) 验证。

```bash
# 运行性能基线测试
./topics/scripts/benchmark.sh kafka --throughput 1000000 --duration 300
```

### 案例2：消费延迟优化

**问题**：消费组Lag持续增长，P99延迟>5秒

**调优**：

```properties
# Kafka consumer.properties
fetch.min.bytes=1024
fetch.max.wait.ms=100
max.poll.records=500
max.poll.interval.ms=300000
```

- 增加Consumer实例数至分区数的整数倍
- 优化业务处理逻辑，避免在poll循环中阻塞
- 开启压缩消费（`compression.type=lz4`）

**效果**：P99消费延迟降至200ms以内

## 3.13.2 MQTT性能调优案例

### 案例1：连接数优化

**问题**：单Broker仅支持5万连接，目标10万+

**调优**：

```bash
# 系统级文件描述符
ulimit -n 100000

# 内核TCP参数
sysctl -w net.core.somaxconn=32768
sysctl -w net.ipv4.tcp_max_syn_backlog=65536
```

- 使用连接池复用TCP连接
- 对QoS0大量上报场景启用批量压缩
- 关闭不必要的日志与ACL规则匹配

**效果**：支持12万并发连接

### 案例2：重连风暴防护

```properties
# MQTT客户端配置
mqtt.client.reconnect.max.interval=30
mqtt.client.reconnect.randomization=true
mqtt.client.keepalive=60
```

## 3.13.3 NATS性能调优案例

### 案例1：延迟优化

**问题**：P99延迟500μs，目标<100μs

**调优**：

```conf
# nats-server.conf
max_payload: 8388608
max_pending: 67108864
write_deadline: "10s"
```

- 使用专用网络（同机房）
- 禁用Nagle算法：`TCP_NODELAY=1`
- Go客户端调优：`GOGC=100`、启用并发订阅处理

**效果**：P99延迟降至80μs

### 案例2：JetStream吞吐优化

```conf
# JetStream存储配置
jetstream {
  store_dir: "/data/nats"
  max_memory_store: 2GB
  max_file_store: 100GB
}
```

## 3.13.4 Pulsar性能调优案例

### 案例1：写入性能优化

**问题**：写入吞吐量50万TPS，目标100万+

**调优**：

```properties
# broker.conf
managedLedgerDefaultEnsembleSize=3
managedLedgerDefaultWriteQuorum=2
managedLedgerDefaultAckQuorum=2
numIOThreads=8
```

- 增加BookKeeper线程数
- 使用SSD存储
- 调整Ledger写入策略（`journalSyncData=false`，需容忍fsync风险）
- Producer端启用批量与压缩

**效果**：写入吞吐量提升至120万TPS

### 案例2：读延迟优化

**问题**：Pulsar 消费端 P99 延迟 >500ms，存在 Backlog 堆积。

**调优**：

```properties
# broker.conf
brokerDispatchMaxMessagesPerTimeWindow=1000
brokerDispatchMaxBytesPerTimeWindow=1048576
maxConcurrentLookupRequest=10000
```

- 增加 Consumer 接收队列（`receiverQueueSize=1000`）
- 对 Key_Shared 订阅保证 Key 顺序，避免单 Key 热点
- 使用 `pulsar-admin topics stats` 定位慢订阅

**效果**：P99 消费延迟降至 80ms，Backlog 下降趋势稳定。

## 3.13.5 RabbitMQ性能调优案例

### 案例1：队列性能优化

**问题**：单队列吞吐量1万TPS，目标5万+

**调优**：

```properties
# rabbitmq.conf
vm_memory_high_watermark.relative = 0.6
disk_free_limit.absolute = 2GB
queue_master_locator = min-masters
```

- 对非关键队列使用内存队列（`durable=false`）
- 批量确认：`prefetch_count=100`
- 增加Erlang进程数与节点数
- 新版优先使用Quorum Queue替代经典镜像队列

**效果**：吞吐量提升至6万TPS

## 3.13.6 调优参数决策矩阵

| 目标 | Kafka | MQTT | NATS | Pulsar | RabbitMQ |
| ------ | ------- | ------ | ------ | -------- | ---------- |
| **提升吞吐** | 增大batch.size/linger.ms + LZ4 | 增加连接数、批量发布 | 使用Core模式、批量发布 | 增加分区、BookKeeper线程 | 批量确认、多队列 |
| **降低延迟** | acks=1、减少副本 | QoS0、减少Broker跳转 | 同机房、TCP_NODELAY | 调小Quorum、SSD | 内存队列、减少持久化 |
| **提升可靠性** | acks=all、replication.factor=3 | QoS2、会话持久化 | JetStream Raft | Ensemble=3/Write=2 | Quorum Queue |
| **扩展连接** | 增加Broker/Consumer | 调ulimit与somaxconn | 集群横向扩展 | Broker无状态扩展 | 增加节点 |

## 3.13.7 调优前后检查清单

- [ ] **基线**：调优前使用 [`scripts/benchmark.sh`](../../topics/scripts/benchmark.sh) 记录吞吐、P99延迟、CPU/磁盘IO
- [ ] **单一变量**：每次只修改一个参数，避免多变量导致无法归因
- [ ] **回归验证**：调优后运行相同负载，确认吞吐或延迟目标达成
- [ ] **稳定性**：持续压测≥30分钟，观察GC、内存、磁盘是否有异常
- [ ] **回滚方案**：保留原始配置文件，记录修改参数与对应指标变化
- [ ] **生产灰度**：先在非核心Topic/队列验证，再全量推广
- [ ] **模板对齐**：关键参数已与 [`config-templates/performance-tune-config.properties`](../../topics/config-templates/performance-tune-config.properties) 对齐

**一键压测与对比命令**：

```bash
# 调优前基线
./topics/scripts/benchmark.sh kafka --throughput 1000000 --duration 300 > baseline.json

# 调优后回归
./topics/scripts/performance-tune.sh kafka --config topics/config-templates/performance-tune-config.properties
./topics/scripts/benchmark.sh kafka --throughput 1000000 --duration 300 > tuned.json

# 快速对比
diff <(jq '.summary.throughput' baseline.json) <(jq '.summary.throughput' tuned.json)
```

## 3.13.8 性能调优总结

### 通用优化策略

1. **批量操作**：减少网络往返
2. **压缩**：减少网络传输
3. **连接复用**：减少连接开销
4. **硬件优化**：SSD、高速网络
5. **参数调优**：根据场景调整配置
6. **持续压测**：使用 [`scripts/performance-tune.sh`](../../topics/scripts/performance-tune.sh) 周期性回归
