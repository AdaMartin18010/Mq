## 3.29.1 调优原则

### 调优步骤

1. **性能测试**
   - 建立基准指标（吞吐、延迟、错误率）
   - 使用压测工具识别瓶颈
   - 设定可量化的优化目标

2. **逐步优化**
   - 一次只调整一个参数
   - 每次变更后回归验证
   - 记录参数变化与效果

3. **持续监控**
   - 监控关键性能指标
   - 对比优化前后差异
   - 周期性复核与调优

### 调优方法论

| 层级 | 优化方向 | 典型参数 | 预期收益 |
| ------ | --------- | --------- | --------- |
| **应用层** | 批量、压缩、序列化 | `batch.size`、`compression.type` | 提升 2-5 倍吞吐【估算】 |
| **系统层** | 分区、并发、连接 | `partition.count`、`fetch.min.bytes` | 提升并行度 |
| **基础设施层** | 磁盘、网络、CPU | SSD、万兆网、多核 | 降低 IO 与网络瓶颈 |

## 3.29.2 Kafka 性能调优

### Producer 调优

参考项目性能调优模板 [`topics/config-templates/performance-tune-config.properties`](../config-templates/performance-tune-config.properties)：

```properties
# 批量发送
performance.tune.producer.batch.size=32768
performance.tune.producer.linger.ms=10
performance.tune.producer.compression.type=snappy
performance.tune.producer.acks=1
performance.tune.producer.buffer.memory=67108864
performance.tune.producer.max.in.flight.requests.per.connection=5
performance.tune.producer.retries=3
```

关键说明：

- `batch.size` 与 `linger.ms` 配合，延迟换吞吐
- `acks=1` 平衡性能与可靠性；金融场景用 `acks=all`
- `compression.type=lz4` 在 CPU 充足时压缩比更高

### Consumer 调优

```properties
# 批量拉取
performance.tune.consumer.fetch.min.bytes=1024
performance.tune.consumer.fetch.max.wait.ms=100
performance.tune.consumer.max.partition.fetch.bytes=1048576
performance.tune.consumer.max.poll.records=500
```

关键说明：

- `max.poll.records` 与业务处理耗时匹配，避免 rebalance
- 增加消费实例数至分区数整数倍，避免空闲

## 3.29.3 NATS 性能调优

### Server 调优

```conf
# 连接限制
max_connections=100000

# 内存限制
max_memory=8GB

# 消息大小
max_payload=8MB

# 集群路由
cluster {
  listen: 0.0.0.0:6222
  routes: ["nats-route://n1:6222", "nats-route://n2:6222"]
}
```

### 客户端调优

```go
nc, _ := nats.Connect("nats://localhost:4222",
    nats.MaxReconnects(10),
    nats.ReconnectWait(2*time.Second),
    nats.PingInterval(20*time.Second),
    nats.MaxPingsOutstanding(5),
)
```

关键说明：

- NATS Core 无持久化，适合高频低延迟场景
- JetStream 场景需关注存储目录磁盘 IO 与 Raft 配置
- 合理设置 `max_payload`，避免大消息阻塞

## 3.29.4 RabbitMQ 性能调优

### 队列调优

```python
# 预取数量
channel.basic_qos(prefetch_count=200)

# 批量确认
channel.basic_ack(delivery_tag, multiple=True)
```

关键说明：

- `prefetch_count` 建议 100-500，过小无法并行，过大内存压力大
- 非必要不使用持久化消息，可提升 2-3 倍吞吐【估算】
- 镜像队列适合高可用，但会增加同步开销

### 系统调优

```bash
# Erlang 进程数
+P 1000000

# 内存高水位（达到后触发流控）
vm_memory_high_watermark.relative = 0.6

# 磁盘高水位
disk_free_limit.relative = 1.5
```

## 3.29.5 调优检查清单

### 调优前

- [ ] 建立性能基线（吞吐、P99 延迟、错误率）
- [ ] 识别瓶颈层级（应用/系统/基础设施）
- [ ] 设定可量化的优化目标

### 调优中

- [ ] 每次只修改一个参数并记录
- [ ] 变更后执行压测或回归验证
- [ ] 监控 CPU/内存/磁盘/网络是否出现新瓶颈

### 调优后

- [ ] 性能指标达到目标
- [ ] 稳定性验证通过（无 OOM、无异常重平衡）
- [ ] 配置已同步到配置中心或模板
- [ ] 文档更新，含参数值与生效范围

使用项目脚本 [`topics/scripts/performance-tune.sh`](../scripts/performance-tune.sh) 辅助检查：

```bash
bash topics/scripts/performance-tune.sh
```
