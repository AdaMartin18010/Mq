## 3.39.1 追踪体系

### 追踪ID生成

1. **唯一标识生成**
   - 生产环境建议将 `trace.id.generator` 配置为 `uuid` 或 `snowflake`，`trace.id.format` 统一为 `hex`，`trace.id.length` 固定为 32 位；需要业务语义时可选 `custom`，但须保证全局唯一。

2. **分布式ID**
   - 跨服务传递时使用三元组 `trace-id`、`span-id`、`parent-span-id`，对应模板 `kafka.trace.headers=trace-id,span-id,parent-span-id`。
   - ID 在 Produce、Consume 及业务线程中保持线程安全，禁止异步回调复用同一个 span。

3. **ID传递机制**
   - Kafka 写入 `record.headers().add("trace-id", traceId.getBytes())`；NATS 使用 `msg.Header.Set("trace-id", traceID)`；RabbitMQ 使用 `BasicProperties.headers`。
   - 消息头前缀统一配置为 `trace-`，即 `kafka.trace.header.prefix=trace-`、`nats.trace.header.prefix=trace-`、`rabbitmq.trace.header.prefix=trace-`。

### 追踪数据收集

1. **消息头注入**
   - Producer 端拦截发送逻辑自动注入 trace 头，Header 必须包含 `trace-id` 与 `span-id`。
   - MQTT 5 使用 User Property；MQTT 3.x 可将 trace 信息写入 payload JSON 的 `_trace` 字段。

2. **日志记录**
   - 日志输出 `trace_id` 与 `span_id`，建议采用 JSON 结构化日志，便于 ELK/Loki 按 trace_id 关联；`trace.sampling.rate=0.01` 仅控制 span 采样，错误日志仍需 100% 落盘。

3. **指标收集**
   - 开启 `trace.monitor.enabled=true`，采集 `trace_count`、`span_count`、`error_count`、`latency_p50`、`latency_p95`、`latency_p99`。
   - Collector 指标通过 `/metrics` 暴露给 Prometheus，`prometheus.scrape.interval=15s`，`prometheus.scrape.timeout=10s`。

### 追踪数据存储

1. **追踪数据存储**
   - 模板默认 `trace.storage.type=elasticsearch`，endpoint 为 `http://localhost:9200`，索引前缀 `trace`；高写入场景可换 Cassandra。
   - Jaeger 接收端配置 `trace.tool.endpoint=http://localhost:14268/api/traces`，生产环境替换为 Collector 集群 VIP。

2. **索引优化**
   - Elasticsearch 按天建索引 `trace-YYYY.MM.DD`，对 `trace-id`、`service`、`operation` 建立 keyword 索引。
   - 单分片不超过 30GB，高频查询字段关闭 `_all` 以减少索引膨胀。

3. **保留策略**
   - 设置 `trace.storage.retention.days=7`，同时配置 `monitor.retention.traces.days=3`、`monitor.retention.metrics.days=30`、`monitor.retention.logs.days=7`，合规场景归档到对象存储并缩短线上保留期。

### 追踪配置示例

```properties
# 消息追踪配置片段（来自 trace-config.properties）
trace.id.generator=uuid
trace.id.format=hex
trace.id.length=32

trace.sampling.enabled=true
trace.sampling.rate=0.01
trace.sampling.strategy=probabilistic

kafka.trace.enabled=true
kafka.trace.header.prefix=trace-
kafka.trace.headers=trace-id,span-id,parent-span-id
nats.trace.enabled=true
nats.trace.header.prefix=trace-
nats.trace.headers=trace-id,span-id,parent-span-id
rabbitmq.trace.enabled=true
rabbitmq.trace.header.prefix=trace-
rabbitmq.trace.headers=trace-id,span-id,parent-span-id

trace.tool=jaeger
trace.tool.endpoint=http://localhost:14268/api/traces
trace.tool.sampler.type=probabilistic
trace.tool.sampler.param=0.01

trace.storage.type=elasticsearch
trace.storage.retention.days=7

trace.monitor.enabled=true
trace.alert.enabled=true
trace.alert.latency.p99.threshold.ms=1000
trace.alert.channels=email,dingtalk
```

## 3.39.2 监控指标

### 消息指标

1. **消息发送速率**
   - 通过 Kafka Exporter（端口 `kafka.exporter.port=9308`）采集 `kafka_topic_partition_current_offset` 差值计算每秒生产量，告警阈值参考 `alert.rule.throughput.threshold=1000` 条/秒。

2. **消息消费速率**
   - 使用 `kafka_consumer_lag_sum` 衡量消费健康度，Prometheus 规则设定 `> 100000` 持续 5 分钟触发 `KafkaHighConsumerLag` warning。
   - NATS 通过 `nats_connz_connections` 与 `nats_varz_mem` 监控连接与内存；RabbitMQ 通过 `rabbitmq_queue_messages` 监控队列深度。

3. **消息延迟**
   - 端到端延迟 = 消息进入 MQ 时间戳 - 业务处理完成时间戳，阈值参考 `alert.rule.latency.threshold=1000` ms。
   - Pulsar 使用 `pulsar_storage_write_latency`，Redis Stream 使用 `XLEN` 与 `XPENDING` 估算排队延迟。

### 系统指标

1. **吞吐量**
   - 监控项由 `monitor.metrics.throughput.enabled=true` 统一开启，Broker 级吞吐结合 CPU、网络带宽评估；单机接近网卡 70% 或 CPU 80% 时启动扩容。

2. **错误率**
   - 开启 `monitor.metrics.error_rate.enabled=true`，统计生产失败、消费失败、ACK 超时的总和。
   - 告警阈值 `alert.rule.error_rate.threshold=0.01`（1%），关键业务 Topic 可单独降至 0.1%。

3. **资源使用**
   - 开启 `monitor.metrics.resource.enabled=true`，阈值 `alert.rule.cpu.threshold=0.8`、`alert.rule.memory.threshold=0.8`、`alert.rule.disk.threshold=0.8`。
   - NATS 内存示例：`nats_varz_mem > 8589934592`（8GB）持续 5 分钟触发 warning。

### 业务指标

1. **业务流程完成率**
   - 开启 `monitor.metrics.business.enabled=true`，在 span 中打标 `business.status`，统计成功/失败/超时。
   - 完成率 = 成功流程数 / 发起流程数，低于 99.5% 触发业务告警。

2. **端到端延迟**
   - 在 trace 首尾 span 记录时间戳，计算 P50/P95/P99，模板中 `trace.alert.latency.p99.threshold.ms=1000`。
   - Redis Stream 无原生 tracing，建议在业务代码中埋点，用 `XADD` 与 `XREADGROUP` 时间戳差值作为近似延迟。

3. **业务成功率**
   - 消费端处理完成后上报 `business.success`，失败携带错误码 tag；`trace.alert.error.rate.threshold=0.05` 作为 P99 上限。
   - 该指标与 MQ 错误率解耦：MQ 投递成功但业务处理失败仍算业务失败。

## 3.39.3 追踪工具

### 开源工具

1. **Jaeger**
   - 配置 `trace.tool=jaeger`，Agent 通过 UDP 6831 接收 span，Collector 通过 14268 HTTP 接收；生产环境推荐 Collector 直接写 Kafka/Elasticsearch。
   - 采样策略 `trace.tool.sampler.type=probabilistic`，`trace.tool.sampler.param=0.01`，QPS 极高服务可改为 adaptive。

2. **Zipkin**
   - 轻量级方案，适合中小规模；Collector 端口 9411，存储支持 MySQL/Elasticsearch，与 Spring Cloud Sleuth 集成较直接。

3. **Prometheus + Grafana**
   - Prometheus 配置 `prometheus.enabled=true`、`prometheus.port=9090`、`prometheus.retention.time=15d`。
   - Grafana 配置 `grafana.port=3000`、`grafana.datasource.prometheus.url=http://prometheus:9090`，导入官方 Dashboard。

### 六大系统追踪实现方式对比

| 系统 | 原生 Header 支持 | 推荐追踪方式 | Exporter 端口 | 关键指标 | 典型采样策略 |
| --- | --- | --- | --- | --- | --- |
| Kafka | Headers（0.11+） | OpenTelemetry/Jaeger 拦截器 | 9308 | `kafka_consumer_lag_sum`、`kafka_controller_offline_partitions_count` | probabilistic 1% |
| MQTT | MQTT 5 User Property / MQTT 3 payload 字段 | 业务代码或 HiveMQ Extension | 通常由 broker 插件暴露 | 连接数、消息速率、离线客户端数 | 按 Topic 采样 |
| NATS | Headers | OpenTelemetry NATS 库 + nats-surveyor | 7777 | `nats_connz_connections`、`nats_varz_mem` | probabilistic 1% |
| Pulsar | Properties | Pulsar Functions / OpenTelemetry | 8080（admin）+ 自定义 exporter | `pulsar_storage_write_latency`、`pulsar_entry_size` | adaptive |
| RabbitMQ | Headers | tracing 插件 + OpenTelemetry | 9419 | `rabbitmq_queue_messages`、`rabbitmq_up` | probabilistic 1% |
| Redis Stream | 无原生 Header | 业务代码在 payload 中嵌入 trace-id | 9121（redis-exporter） | `XLEN`、`XPENDING`、内存使用率 | 按 Stream 采样 |

### Prometheus 告警规则示例

```yaml
# Prometheus 告警规则片段（来自 prometheus-alerts.yml）
groups:
  - name: kafka_alerts
    interval: 30s
    rules:
      - alert: KafkaHighConsumerLag
        expr: kafka_consumer_lag_sum > 100000
        for: 5m
        labels:
          severity: warning

      - alert: KafkaBrokerDown
        expr: up{job="kafka"} == 0
        for: 1m
        labels:
          severity: critical

  - name: nats_alerts
    interval: 30s
    rules:
      - alert: NATSHighMemory
        expr: nats_varz_mem > 8589934592  # 8GB
        for: 5m
        labels:
          severity: warning

  - name: rabbitmq_alerts
    interval: 30s
    rules:
      - alert: RabbitMQHighQueueMessages
        expr: rabbitmq_queue_messages > 100000
        for: 5m
        labels:
          severity: warning
```

## 3.39.4 追踪最佳实践

### 追踪设计

1. **统一追踪格式**
   - 全公司统一 `trace-id`、`span-id`、`parent-span-id` 命名与长度，禁止不同团队混用 `request_id`、`correlation_id`。
   - 推荐采用 W3C Trace Context 标准 `traceparent` 与 `tracestate`，与 OpenTelemetry 兼容。

2. **跨系统传递**
   - 消息经过 Kafka→RabbitMQ→NATS 等多跳链路时，每跳新建 span 但保持 `trace-id` 不变。
   - 在消息头中写入 `service.name` 与 `service.version`，便于 Jaeger UI 按服务过滤。

3. **采样策略**
   - 默认 `trace.sampling.strategy=probabilistic`，`trace.sampling.rate=0.01`；核心链路可提升至 10% 或 100%。
   - 错误请求强制采样：Producer 检测到异常时设置 `force.sample=true`，确保异常链路 100% 保留。

### 性能优化

1. **采样率设置**
   - 日活十亿级 span 场景保持 0.1%-1%，超过 1% 需评估 Collector 与存储写入瓶颈。
   - Jaeger adaptive sampling 设置 `lower_bound=0.01`，避免低频服务丢失关键链路。

2. **异步收集**
   - Producer/Consumer 内嵌 tracer 异步批量上报，避免同步 HTTP 阻塞消息处理；Jaeger Agent 本地缓存默认队列 1000。
   - Collector 启用批处理与 gzip 压缩，Elasticsearch bulk 大小建议 5-10MB。

3. **存储优化**
   - 热数据保留 3-7 天，`trace.storage.retention.days=7`；冷数据按天压缩转存到 S3/OSS。
   - 高基数 tag（如 user_id、order_id）做 hash 脱敏或仅对错误 span 保留原始值，防止 ES 索引爆炸。

### 运维管理

1. **追踪数据管理**
   - 每日巡检 ES 索引大小与分片数，单分片超过 30GB 触发 rollover；冷索引设置 `index.codec: best_compression`。
   - 定期清理过期 trace 索引，使用 Curator 按 `trace-YYYY.MM.DD` 模式删除超过 `trace.storage.retention.days=7` 的索引。

2. **性能监控**
   - 监控 Collector CPU、内存、网络及队列积压，队列深度超过 10000 时扩容或降级采样率；对比开启 tracing 前后吞吐与延迟，确保端到端延迟增幅不超过 5%。

3. **告警配置**
   - 使用 Prometheus 规则：`trace.alert.error.rate.threshold=0.05`、`trace.alert.latency.p99.threshold.ms=1000`。
   - 告警通道配置 `trace.alert.channels=email,dingtalk`，关键告警 1 分钟内送达。

## 3.39.5 追踪检查清单

### 实施前

- [ ] 确认 `trace.id.generator` 选定为 `uuid` 或 `snowflake`，`trace.id.length=32` 已落地。
- [ ] 确认采样策略：`trace.sampling.strategy=probabilistic`，默认 `trace.sampling.rate=0.01`。
- [ ] 确认存储后端：`trace.storage.type=elasticsearch` 或 `cassandra`，`trace.storage.retention.days=7`。
- [ ] 确认追踪工具：`trace.tool=jaeger` 或 `zipkin`，`trace.tool.endpoint` 指向生产 Collector。
- [ ] 确认监控体系：Prometheus `prometheus.scrape.interval=15s`、`prometheus.retention.time=15d`，Grafana 数据源已配置。
- [ ] 确认 Exporter 端口规划：Kafka 9308、NATS 7777、RabbitMQ 9419、Redis 9121。

### 实施中

- [ ] Producer 已注入 `trace-id`、`span-id`、`parent-span-id`，Header 前缀统一为 `trace-`。
- [ ] Consumer 已读取 trace header 并创建子 span，异常时设置 `error=true` 并记录 stacktrace。
- [ ] `trace.monitor.enabled=true`，指标包含 `trace_count`、`span_count`、`error_count`、`latency_p99`。
- [ ] Prometheus 已抓取 Kafka/NATS/RabbitMQ exporter，`kafka.exporter.enabled=true`、`nats.exporter.enabled=true`、`rabbitmq.exporter.enabled=true`。
- [ ] 告警规则已生效：`kafka_consumer_lag_sum > 100000`、`nats_varz_mem > 8589934592`、`rabbitmq_queue_messages > 100000`。

### 实施后

- [ ] 抽样验证：在 Jaeger UI 中按 `trace-id` 查询，确认跨服务、跨 MQ 的链路完整。
- [ ] 性能影响评估：对比开启 tracing 前后吞吐与 P99 延迟，增幅控制在 5% 以内。
- [ ] 告警通道测试：`trace.alert.channels=email,dingtalk` 能在触发规则后 1 分钟内收到通知。
- [ ] 存储巡检：`trace.storage.retention.days=7` 过期索引已自动删除，单分片未超过 30GB。
- [ ] 定期复核采样率与保留期，根据业务 QPS 与存储成本动态调整。
