## 3.46.1 安全需求

### 业务需求

1. **认证授权**
   所有消息队列接入必须完成身份认证与最小权限授权。Kafka 应启用 `sasl.enabled.mechanisms=SCRAM-SHA-256/SCRAM-SHA-512` 或 `OAUTHBEARER`，Pulsar 应启用 `authenticationEnabled=true` 并配置 `authenticationProviders`，NATS 应使用 JWT/Token 或账户密码，RabbitMQ 应关闭默认 guest 远程访问并配置用户与 vhost 权限，MQTT Broker 应启用用户名密码或客户端证书认证，Redis Stream 应使用 ACL 或 `requirepass`。

2. **数据安全**
   传输层必须启用 TLS/SSL，Kafka 配置 `security.protocol=SASL_SSL` 或 `SSL`，Pulsar 启用 `brokerServicePortTls=6651`，NATS 使用 `listen: "tls://0.0.0.0:4222"`，RabbitMQ 启用 AMQPS 5671，MQTT 启用 8883，Redis 启用 `tls-port 6380`。存储层建议对日志目录或持久化卷进行磁盘加密，敏感消息可在应用层使用 `security.encryption.algorithm=AES-256-GCM` 加密。

3. **网络安全**
   将消息队列部署在独立 VPC 或子网内，通过安全组/防火墙仅暴露必要端口。Kafka Broker 仅开放 9093（SASL_SSL），Pulsar 仅开放 6651/8443，NATS 仅开放 4222/6222，RabbitMQ 仅开放 5671/15672，MQTT 仅开放 8883/8084，Redis 仅开放 6380。管理面与管理口应限制运维堡垒机或 VPN 访问。

## 3.46.2 安全策略

### 认证策略

生产环境应优先使用强认证机制，避免明文口令。Kafka 推荐 SCRAM-SHA-256/512 或 OAUTHBEARER，测试环境可使用 SASL/PLAIN 但必须配合 TLS。Pulsar 支持 TLS 客户端证书、OAuth2、SASL 等插件，需在 `broker.conf` 指定 `authenticationProviders`。NATS 推荐 JWT + nsc 工具签发账户与用户，Token 仅用于受信内部场景。RabbitMQ 支持 PLAIN、AMQPLAIN、EXTERNAL（TLS 证书）认证，应修改 `default_user` 与 `default_pass`。MQTT 5.0 Broker 支持密码认证与 x509 客户端证书，证书模式需设置 `verify_peer` 与 `fail_if_no_peer_cert=true`。Redis 使用 ACL 用户名密码或 `requirepass`，并关闭危险命令。

```properties
# Kafka：SASL_SSL + SCRAM-SHA-256 示例
listeners=SASL_SSL://0.0.0.0:9093
security.inter.broker.protocol=SASL_SSL
sasl.enabled.mechanisms=SCRAM-SHA-256,SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-256
ssl.enabled.protocols=TLSv1.2,TLSv1.3
ssl.endpoint.identification.algorithm=https

# Pulsar：TLS + 授权
brokerServicePortTls=6651
webServicePortTls=8443
tlsEnabled=true
authenticationEnabled=true
authenticationProviders=org.apache.pulsar.broker.authentication.AuthenticationProviderTls
authorizationEnabled=true
superUserRoles=admin,superuser

# NATS：TLS + Token
listen: "tls://0.0.0.0:4222"
tls {
  cert_file: "/etc/nats/server.crt"
  key_file:  "/etc/nats/server.key"
  ca_file:   "/etc/nats/ca.crt"
  verify:    true
  timeout:   2
}
authorization {
  token: "${NATS_AUTH_TOKEN}"
}

# RabbitMQ：AMQPS + 默认用户
listeners.ssl.default = 5671
ssl_options.cacertfile = /etc/rabbitmq/ca.pem
ssl_options.certfile   = /etc/rabbitmq/server.pem
ssl_options.keyfile    = /etc/rabbitmq/server.key
ssl_options.verify     = verify_peer
ssl_options.fail_if_no_peer_cert = true
default_user = admin
default_pass = admin-secret

# Redis：TLS + ACL
tls-port 6380
tls-cert-file /etc/redis/server.crt
tls-key-file /etc/redis/server.key
tls-ca-cert-file /etc/redis/ca.crt
tls-auth-clients yes
aclfile /etc/redis/users.acl
```

### 授权策略

授权遵循最小权限原则，按资源粒度控制。Kafka 使用 `kafka-acls.sh` 配置 ACL，`authorizer.class.name=kafka.security.authorizer.AclAuthorizer`，并设置 `allow.everyone.if.no.acl.found=false`。Pulsar 通过 `pulsar-admin namespaces grant-permission` 授予命名空间级 produce/consume 权限。RabbitMQ 使用 `rabbitmqctl set_permissions` 配置 vhost 正则权限，并使用 topic 权限控制 exchange/queue。NATS 在账户中配置 `publish` 与 `subscribe` 的 allow/deny 主题模式。MQTT 通过 ACL 规则控制 publish/subscribe 的 topic 范围。Redis 使用 `ACL SETUSER` 限定命令、键模式与通道。

```bash
# Kafka ACL：仅允许 order-producer 写入 orders topic
kafka-acls.sh --bootstrap-server kafka:9093 --command-config admin.conf \
  --add --allow-principal User:order-producer \
  --operation Write --topic orders

# Pulsar：授予角色对命名空间的生产消费权限
pulsar-admin namespaces grant-permission my-tenant/my-ns \
  --role order-service --actions produce,consume

# RabbitMQ：限制用户在 /order-vhost 下只能读写 order.* 资源
rabbitmqctl set_permissions -p /order-vhost order-service \
  "^(order\\..*)" "^(order\\..*)" "^(order\\..*)"

# NATS：使用 nsc 限制用户可发布主题
nsc add user --account orders-account --name publisher \
  --allow-pub "orders.>" --deny-sub ">"

# Redis ACL：允许 order-service 访问 order:* 键
redis-cli ACL SETUSER order-service on >Passw0rd ~order:* \
  +get +xread +xadd -@dangerous
```

### 加密策略

传输加密使用 TLS 1.2 或更高版本，禁用 SSLv3/TLSv1.0/TLSv1.1。Kafka 配置 `ssl.enabled.protocols=TLSv1.2,TLSv1.3`，并设置 `ssl.client.auth=required` 强制双向认证。存储加密建议对 Kafka log.dirs、Pulsar BookKeeper journal/ledger 目录、RabbitMQ Mnesia 与队列目录、Redis AOF/RDB 目录所在文件系统启用 LUKS/BitLocker/VeraCrypt。应用层敏感字段加密使用 `security.encryption.algorithm=AES-256-GCM`，密钥通过 `key.management.provider=vault` 管理，并设置 `key.management.rotation.interval=90d` 与 `security.encryption.key.rotation.interval=90d` 定期轮换。

```bash
# 生成自签名 CA 与 Broker 证书（OpenSSL 示例）
openssl req -new -x509 -days 3650 -keyout ca.key -out ca.crt \
  -subj "/CN=mq-ca" -nodes
openssl req -new -newkey rsa:4096 -nodes -keyout broker.key -out broker.csr \
  -subj "/CN=broker.mq.local"
openssl x509 -req -in broker.csr -CA ca.crt -CAkey ca.key -out broker.crt \
  -days 365 -sha256 -CAcreateserial
```

## 3.46.3 合规要求

### 合规标准

1. **GDPR**
   个人数据在传输与存储中必须加密，默认启用 TLS。数据保留策略按 `compliance.gdpr.data_retention.days=365` 配置，超期数据自动清理或匿名化。用户行使删除权时，需能定位并删除对应 topic/namespace/stream 中的数据。审计日志保留不少于 `audit.retention.days=90`。

2. **HIPAA**
   医疗数据访问必须配置强认证与细粒度 ACL，所有读取/写入/配置变更写入审计日志 `audit.log.file=/var/log/mq-audit.log`，事件至少包含 `login,logout,read,write,delete,config_change`。数据备份脚本应存在且加密，如 `scripts/backup-all.sh`。

3. **PCI DSS**
   支付数据不得明文传输或存储，强制 TLS 1.2+ 与双向证书认证。密钥每 90 天轮换一次，访问控制遵循最小权限，并定期运行合规检查脚本。禁止在消息体中直接包含完整 PAN 等敏感卡信息。

4. **等保 2.0 / ISO 27001**
   身份鉴别、访问控制、安全审计为三级等保基本要求。审计日志本地留存不少于 180 天，关键配置变更需双人复核。管理面启用 MFA，所有默认口令必须修改。

| 合规标准 | 关键控制项 | 建议配置/阈值 | 验证方式 |
| ---------- | ------------ | --------------- | ---------- |
| GDPR | 数据加密、保留期限、删除权 | TLS 1.2+，保留 365 天 | `compliance-check.sh gdpr` |
| HIPAA | 审计日志、访问控制、备份 | 审计 90 天，ACL 启用 | `compliance-check.sh hipaa` |
| PCI DSS | 传输加密、密钥轮换、最小权限 | 密钥 90 天轮换，mTLS | `compliance-check.sh pci` |
| 等保 2.0 | 身份鉴别、日志留存 180 天 | 审计日志 >= 180 天 | 人工 + SIEM 检查 |

```bash
# 运行全量合规检查并输出报告
bash topics/scripts/compliance-check.sh all \
  compliance_check_$(date +%Y%m%d).txt
```

## 3.46.4 安全工具

### 工具选型

1. **认证工具**
   LDAP/AD 用于企业统一身份认证，模板中配置 `auth.type=ldap`、`auth.ldap.url=ldap://ldap.example.com:389`、`auth.ldap.base_dn=dc=example,dc=com`。OAuth2/OIDC 用于云原生与微服务场景，Kafka 使用 `OAUTHBEARER`、Pulsar 使用 OAuth2 认证插件。JWT 在 NATS 中通过 `nsc` 生成 operator/account/user JWT。

2. **加密工具**
   OpenSSL 用于生成 CA、服务端与客户端证书。Vault/KMS 用于密钥托管与自动轮换，模板配置 `key.management.provider=vault`、`key.management.vault.url=http://vault:8200`、`key.management.rotation.enabled=true`、`key.management.rotation.interval=90d`。

3. **审计工具**
   启用系统级审计日志并接入 SIEM。Kafka 通过 log4j 记录授权日志，Pulsar 开启 broker 审计，RabbitMQ 可启用 `rabbitmq_event_exchange` 插件，NATS 启用 `-DV` 调试与日志。定期执行 `topics/scripts/security-audit.sh` 检查 SASL/SSL/ACL/用户配置。

```bash
# 全量安全审计
bash topics/scripts/security-audit.sh all \
  security_audit_$(date +%Y%m%d_%H%M%S).txt

# 输出示例关键项：
# ✅ SASL认证已启用
# ✅ SSL加密已启用
# ✅ ACL授权已配置
# ✅ TLS加密已启用
# ✅ 认证已配置
```

| 系统 | TLS/SSL | SASL | OAuth/OIDC | mTLS | ACL/RBAC | 审计日志 |
| ------ | --------- | ------ | ------------ | ------ | ---------- | ---------- |
| Kafka | SSL/SASL_SSL | PLAIN/SCRAM/GSSAPI/OAUTHBEARER | OAUTHBEARER | `ssl.client.auth=required` | `AclAuthorizer` | log4j 授权日志 |
| Pulsar | 6651/8443 | TLS/SASL/OAuth2 插件 | OAuth2 插件 | `tlsRequireTrustedClientCertOnConnect=true` | 命名空间 RBAC | Broker 审计日志 |
| RabbitMQ | AMQPS 5671 | PLAIN/EXTERNAL | OAuth2 插件 | `ssl_options.verify=verify_peer` | vhost/topic 权限 | event_exchange 插件 |
| NATS | `tls://` | Token/JWT/nkeys | JWT operator | `verify:true` | Accounts + permissions | Server log |
| MQTT | 8883/WebSocket TLS | 用户名密码/x509 | Broker JWT 插件 | `verify_peer` | ACL 规则 | Broker 审计日志 |
| Redis Stream | `tls-port 6380` | ACL 密码 | - | `tls-auth-clients yes` | `ACL SETUSER` | ACL LOG / slowlog |

## 3.46.5 安全检查清单

### 实施前

- [ ] 明确各系统认证方式：Kafka SCRAM-SHA-256/512、Pulsar TLS/OAuth2、NATS JWT、RabbitMQ 证书/PLAIN、MQTT 密码/x509、Redis ACL。
- [ ] 准备 CA、服务端证书与客户端证书，私钥长度不低于 2048 位（推荐 4096 位），证书有效期不超过 365 天。
- [ ] 制定数据保留策略：`compliance.gdpr.data_retention.days=365`，审计日志保留 `audit.retention.days=90`（等保场景建议 >= 180 天）。
- [ ] 评估合规范围：GDPR、HIPAA、PCI DSS、等保 2.0、ISO 27001。
- [ ] 准备密钥管理系统：Vault/KMS，`key.management.rotation.interval=90d`。

### 实施中

- [ ] Kafka 配置 `authorizer.class.name=kafka.security.authorizer.AclAuthorizer` 与 `allow.everyone.if.no.acl.found=false`。
- [ ] Kafka 配置 `sasl.enabled.mechanisms=SCRAM-SHA-256,SCRAM-SHA-512` 与 `ssl.enabled.protocols=TLSv1.2,TLSv1.3`。
- [ ] Pulsar 配置 `authenticationEnabled=true`、`authorizationEnabled=true`、`superUserRoles=admin,superuser`。
- [ ] NATS 配置 TLS `verify:true`，关闭或限制未加密 `4222` 监听，JWT operator 预加载。
- [ ] RabbitMQ 启用 `listeners.ssl.default=5671`，关闭明文 5672 或仅允许本地回环。
- [ ] MQTT Broker 配置 `verify_peer` 与 `fail_if_no_peer_cert=true`，启用 8883 监听。
- [ ] Redis 启用 `tls-port 6380`、`tls-auth-clients yes`，使用 ACL 文件并禁用 `FLUSHALL`、`CONFIG` 等危险命令。
- [ ] 配置审计日志：`audit.log.file=/var/log/mq-audit.log`，`audit.events=login,logout,read,write,delete,config_change`，`audit.retention.days=90`。
- [ ] 配置安全监控：`security.monitor.failed_login.threshold=5`、`security.monitor.failed_login.window=300`，告警通道接入 email/dingtalk。

### 实施后

- [ ] 运行 `security-audit.sh all`，确认 Kafka SASL/SSL/ACL、NATS TLS/认证、RabbitMQ 用户/TLS 均为 ✅。
- [ ] 运行 `compliance-check.sh all`，确认 GDPR/HIPAA/PCI DSS 无 ❌ 高风险项。
- [ ] 验证证书剩余有效期大于 30 天。
- [ ] 验证失败登录告警：5 分钟内失败 5 次触发告警。
- [ ] 执行负向测试：未授权用户尝试读写 topic/queue/stream 应被拒绝。
- [ ] 接入 SIEM/Prometheus + Grafana，监控认证失败、未授权访问、证书到期、审计日志完整性。
- [ ] 每 90 天执行密钥与证书轮换，并更新所有客户端信任库。
