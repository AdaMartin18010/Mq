## 3.61.1 自动化运维需求

消息自动化运维需求应覆盖部署自动化、监控自动化、运维自动化三类。部署自动化要求通过 CI/CD 与基础设施即代码实现一键部署与回滚；监控自动化要求指标采集、告警触发、故障诊断全流程无需人工介入；运维自动化要求扩缩容、备份、恢复等高频操作由脚本或控制器自动完成。

参考 `topics/config-templates/automation-config.properties`，部署工具选择 `automation.deployment.tool=kubernetes`，命名空间 `automation.deployment.kubernetes.namespace=mq`，副本数 `automation.deployment.kubernetes.replicas=3`。CI/CD 工具选择 `automation.cicd.tool=gitlab_ci`，流水线文件为 `.gitlab-ci.yml`。

## 3.61.2 自动化策略

### 3.61.2.1 基础设施即代码策略

所有基础设施配置使用 Terraform、Ansible 或 Pulumi 管理。Kafka、NATS、RabbitMQ 的节点规格、网络配置、存储卷均通过代码定义，避免手动修改导致配置漂移。状态文件使用远程后端，如 `automation.iac.terraform.state.backend=s3`，确保团队协作与版本可追溯。

### 3.61.2.2 CI/CD 集成策略

代码提交后触发单元测试、集成测试、镜像构建、安全扫描，合并到主分支后触发部署流水线。`automation.cicd.gitlab_ci.enabled=true` 时，需在仓库根目录提供 `.gitlab-ci.yml`。部署策略采用滚动更新或蓝绿部署，确保发布过程可回滚。

### 3.61.2.3 自愈与恢复策略

通过健康检查脚本持续探测服务状态，失败时自动重启或切换。`auto-recovery.sh` 对 Kafka、NATS、RabbitMQ 分别执行 `./scripts/health-check.sh <mq_type>`，失败后调用 `./scripts/restart.sh <mq_type>`，最多重试 `MAX_RETRIES=3` 次。超过重试阈值则发送告警通知人工介入。

| 自动化领域 | 关键工具 | 触发条件 | 执行动作 |
|---|---|---|---|
| 部署自动化 | Kubernetes / Helm / GitLab CI | 代码合并或定时触发 | 滚动更新、蓝绿部署 |
| 监控自动化 | Prometheus + Grafana + AlertManager | 指标超过阈值 | 告警、自动诊断 |
| 扩缩容自动化 | Kubernetes HPA/VPA | CPU/内存利用率 > 80% | 水平或垂直扩缩容 |
| 自愈恢复 | `auto-recovery.sh` | 健康检查失败 | 自动重启，3 次重试后告警 |

## 3.61.3 自动化工具与落地配置

### 3.61.3.1 部署工具落地

Kubernetes 部署时，使用 StatefulSet 运行有状态消息队列，配置 `automation.deployment.kubernetes.replicas=3`。Helm 用于管理 Chart 版本与参数覆盖，Docker Compose 用于本地开发验证。Ansible 用于裸金属或虚拟机的软件安装与配置下发。

```yaml
# Kafka HPA 示例：CPU 利用率达到 80% 时扩缩容
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: kafka-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: StatefulSet
    name: kafka
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80
```

### 3.61.3.2 监控工具落地

Prometheus 采集消息队列指标，Grafana 绘制可视化大盘，AlertManager 分发告警。启用 `automation.monitoring.prometheus.enabled=true`、`automation.monitoring.grafana.enabled=true`、`automation.monitoring.alertmanager.enabled=true`，并分别配置访问地址。自动诊断功能通过 `automation.monitoring.auto.diagnosis.enabled=true` 开启。

```yaml
# Kafka 高错误率告警规则
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: kafka-alerts
spec:
  groups:
  - name: kafka
    rules:
    - alert: KafkaHighErrorRate
      expr: rate(kafka_errors_total[5m]) > 0.1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "Kafka 错误率过高"
```

### 3.61.3.3 扩缩容工具落地

HPA 策略配置 `automation.scaling.hpa.min.replicas=2`、`automation.scaling.hpa.max.replicas=10`，CPU 与内存目标利用率均为 80%。VPA 用于调整 Pod 资源请求，手动扩缩容作为兜底方案。扩缩容操作应避开业务高峰，并提前验证新节点数据同步状态。

### 3.61.3.4 备份与恢复工具落地

备份策略选择 scheduled，`automation.backup.scheduled.cron=0 2 * * *` 每天凌晨两点执行，保留天数 `automation.backup.scheduled.retention.days=30`。恢复策略选择 automatic，`automation.recovery.automatic.enabled=true` 开启故障检测与自动切换，`automation.recovery.automatic.switch.enabled=true` 允许自动主备切换。

```bash
# 对所有消息队列执行自动恢复，最多重试 3 次
./topics/scripts/auto-recovery.sh all 3
```

### 3.61.3.5 自动化测试门禁

`automation.testing.enabled=true` 时，需同时开启 `automation.testing.unit.enabled=true`、`automation.testing.integration.enabled=true`、`automation.testing.e2e.enabled=true`、`automation.testing.performance.enabled=true`。每次代码合并前必须全部通过，失败时阻塞发布。

```bash
# 检查自动化运维各项能力是否配置完整
./topics/scripts/automation-check.sh
```

## 3.61.4 最佳实践

1. **GitOps 工作流**：将所有 Kubernetes 清单、Terraform 配置、Ansible Playbook 纳入 Git 版本管理，变更通过 Merge Request 审批后自动同步。
2. **配置分离**：环境相关参数使用 ConfigMap 或 Vault 注入，避免在镜像中硬编码密码与地址。
3. **灰度发布**：新版本先发布到 1 个副本或 5% 流量，观察 `rate(kafka_errors_total[5m])` 等指标稳定后再全量 rollout。
4. **告警降噪**：为告警设置 `for: 5m` 持续触发条件，避免瞬时抖动造成告警风暴。
5. **定期演练**：每季度执行一次故障演练，验证 `auto-recovery.sh` 与 HPA 扩缩容是否按预期生效。
