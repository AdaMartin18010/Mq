## 3.57.1 容量规划需求

容量规划需要在业务上线前完成三类估算：存储容量、计算容量和扩展容量。需求来源通常包括：

- 业务方给出的峰值消息量、消息平均大小、保留周期和副本要求；
- 运维侧对磁盘、内存、CPU、网络带宽和连接数的上限约束；
- 未来 6–12 个月的增长预测，以及突发流量（burst）的预留倍数。

模板 `capacity-plan-config.properties` 将关键变量参数化，便于在不同环境中复用。规划前应确认消息系统类型（Kafka/NATS/RabbitMQ 等），因为副本因子、连接开销和存储格式差异会显著影响结果。

## 3.57.2 容量计算公式

### 3.57.2.1 存储容量

存储容量由消息大小、日消息量、保留天数和副本数决定，同时需要预留突发和系统开销：

```text
总存储(GB) = 消息大小(B) × 日消息量 × 保留天数 × 副本数 × 预留系数 / 1024^3
```

其中预留系数建议取 1.3（30%），用于覆盖索引、压缩损耗、日志清理碎片和突发流量。模板中的对应参数为：

- `capacity.plan.storage.message.size.bytes=1024`
- `capacity.plan.storage.message.count.per.day=1000000`
- `capacity.plan.storage.retention.days=7`
- `capacity.plan.storage.replication.factor=3`
- `capacity.plan.storage.reserve.percentage=30`

示例计算：1 KB 消息、100 万条/天、保留 7 天、3 副本、30% 预留：

```bash
# 使用 capacity-plan.sh 中的示例逻辑
python3 - <<'PY'
msg_size = 1024
msg_count = 1000000
retention = 7
replication = 3
reserve = 1.3
total_gb = msg_size * msg_count * retention * replication * reserve / (1024**3)
print(f"总存储需求: {total_gb:.2f} GB")
PY
```

### 3.57.2.2 计算容量

CPU 核数估算：

```text
CPU 核数 = 峰值吞吐(MB/s) / 单核吞吐能力(MB/s)
```

模板中 `capacity.plan.compute.cpu.throughput.per.core.mbps=10`，即单核约 10 MB/s。若峰值吞吐 100 MB/s，则至少需要 10 核，再叠加 20% 预留。

内存估算：

```text
内存(GB) = 消息缓存大小 + 系统开销 + JVM/运行时开销
```

模板中 `capacity.plan.compute.memory.cache.percentage=70`、`memory.system.overhead.percentage=30`，表示 70% 内存用于缓存，30% 留给系统和运行时。

### 3.57.2.3 网络带宽

```text
带宽(Mbps) = 消息大小(B) × 日消息量 × 8 / 86400 / 1024^2 × 峰值倍数
```

其中峰值倍数通常取 2–3。模板中的 `capacity.plan.reserve.burst.traffic.multiplier=2.0` 即对应此倍数。

## 3.57.3 磁盘/带宽/连接数估算

### 3.57.3.1 磁盘估算

磁盘容量需覆盖消息日志、索引、快照和备份。Kafka 按 Topic 分区独立存储，建议每个分区保留文件数可控；NATS JetStream 使用文件存储时，单个 Stream 的 `max_bytes` 应作为硬上限。磁盘 IOPS 方面，HDD 通常只能支撑数百 IOPS，SSD 可达数万，高吞吐场景必须选用 SSD 或 NVMe。

容量计算示例表：

| 资源项 | 输入参数 | 计算结果 | 备注 |
|---|---|---|---|
| 消息日存储 | 1 KB × 100 万条 | 0.95 GB/天 | 未含副本 |
| 总消息存储 | 0.95 GB × 7 天 × 3 副本 | 20 GB | 未含预留 |
| 含预留存储 | 20 GB × 1.3 | 26 GB | 建议挂载 50 GB |
| 峰值写入带宽 | 0.95 GB/天 × 8 / 86400 × 2 | 约 0.18 Mbps | 业务峰值按 2 倍 |
| 峰值读取带宽 | 3 个消费组同时消费 | 约 0.54 Mbps | 按 3 倍读取估算 |

### 3.57.3.2 带宽估算

网络带宽不仅考虑消息体，还需包含协议头、副本同步流量和管理流量。Kafka 副本同步流量约等于生产流量的 `(副本数 - 1)` 倍。内网环境按峰值计算，公网或跨可用区场景需额外增加 20% 余量。

### 3.57.3.3 连接数估算

连接数 = Producer 实例数 × 每个 Producer 连接数 + Consumer 实例数 × 每个 Consumer 连接数 + 管理/监控连接数。Kafka 中一个 Producer 通常建立与所有 Broker 的连接，Consumer 同理。模板中 `capacity.plan.scale.horizontal.node.count=3` 和 `capacity.plan.scale.horizontal.node.capacity.mbps=50` 用于估算节点数：

```text
节点数 = ceil(总吞吐需求 / 单节点容量)
```

例如 100 MB/s 总需求、单节点 50 MB/s，则至少需要 3 个节点（含 1 个故障域冗余）。

### 3.57.3.4 使用容量检查脚本

`capacity-check.sh` 可对现有集群做容量巡检：

```bash
# 检查 Kafka 磁盘使用率与 Topic 数量
./topics/scripts/capacity-check.sh kafka

# 检查 NATS 内存与连接数
./topics/scripts/capacity-check.sh nats

# 检查 RabbitMQ 队列与消息积压
./topics/scripts/capacity-check.sh rabbitmq
```

脚本输出中，磁盘使用率超过 80% 会提示“较高”，超过 90% 提示“过高”，应结合 `capacity.plan.alert.storage.warning.percentage=70` 和 `storage.critical.percentage=90` 制定告警策略。

## 3.57.4 扩容触发条件

扩容应基于监控阈值而非人工感觉。模板 `capacity-plan-config.properties` 和脚本 `capacity-check.sh` 给出了清晰的触发条件：

- 存储使用率连续 5 分钟超过 `capacity.plan.monitor.storage.usage.threshold.percentage=80`；
- CPU 利用率持续 10 分钟超过 80%，且消息延迟同步上升；
- 网络带宽利用率峰值超过 70%，或跨区复制 lag 超过 60 秒；
- 连接数接近单节点上限（Kafka 默认约 1 万连接/节点，NATS 更高）；
- 消息积压（lag）在消费端未减少且分区已无法继续提升消费并行度。

扩容方式选择：

- 水平扩展：增加节点/分区，适合吞吐不足且单节点资源充足；
- 垂直扩展：升级 CPU/内存/磁盘，适合单节点成为瓶颈；
- 混合扩展：水平扩展优先，垂直扩展兜底，模板中 `capacity.plan.scale.strategy=horizontal` 为默认策略。

自动扩展参数：

```properties
# capacity-plan-config.properties 自动扩展片段
capacity.plan.autoscale.enabled=true
capacity.plan.autoscale.threshold.storage.percentage=80
capacity.plan.autoscale.threshold.compute.percentage=80
capacity.plan.autoscale.scale.up.cooldown.seconds=300
capacity.plan.autoscale.scale.down.cooldown.seconds=600
capacity.plan.autoscale.min.nodes=2
capacity.plan.autoscale.max.nodes=10
```

## 3.57.5 容量规划检查清单

### 实施前

- [ ] 收集业务峰值消息量、消息平均大小、保留天数和副本数需求；
- [ ] 确认现有节点硬件：CPU 核数、内存大小、磁盘类型与容量、网络带宽；
- [ ] 在 `capacity-plan-config.properties` 中填入定量和预留参数；
- [ ] 明确自动扩展上下限（`autoscale.min.nodes` / `max.nodes`）。

### 实施中

- [ ] 按 3.57.2 公式计算存储、CPU、内存、网络四项容量；
- [ ] 磁盘容量预留 30% 突发空间，关键 Topic 单独核算；
- [ ] 网络带宽按峰值 2–3 倍估算，跨区复制单独计算；
- [ ] 连接数按 Producer + Consumer + 管理连接分别估算；
- [ ] 使用 `capacity-plan.sh` 复核计算过程并输出报告。

### 实施后

- [ ] 部署 `capacity-check.sh` 定期巡检，磁盘告警阈值 80%、紧急阈值 90%；
- [ ] 将容量利用率接入监控大盘，至少包含存储、CPU、网络、连接数四项；
- [ ] 每季度复盘容量预测准确率，调整 `capacity.plan.prediction.historical.days`；
- [ ] 当触发 3.57.4 任一条件时，启动扩容流程并保留变更记录。
