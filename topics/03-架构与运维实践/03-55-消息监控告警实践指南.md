## 3.55.1 监控需求

1. **性能监控**：跟踪消息吞吐、端到端延迟、分区/队列积压，确保核心链路满足 SLA。
2. **健康监控**：监控 Broker/节点存活、Exporter 可用性、ZooKeeper/KRaft 控制器状态、集群拓扑变化。
3. **异常告警**：对错误率突增、消费滞后、磁盘剩余空间不足、连接数异常等事件分级告警。

## 3.55.2 告警规则配置

### Prometheus 告警规则

模板 `prometheus-alerts.yml` 已覆盖 Kafka、NATS、RabbitMQ 三类核心告警：

```yaml
groups:
  - name: kafka_alerts
    interval: 30s
    rules:
      - alert: KafkaHighConsumerLag
        expr: kafka_consumer_lag_sum > 100000
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Kafka Consumer Lag 过高"
          description: "Consumer Lag 超过 100,000，Topic: {{ $labels.topic }}"
      - alert: KafkaUnderReplicatedPartitions
        expr: kafka_controller_offline_partitions_count > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Kafka 分区副本不足"
          description: "有 {{ $value }} 个分区副本不足"
      - alert: KafkaBrokerDown
        expr: up{job="kafka"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Kafka Broker 宕机"
          description: "Broker {{ $labels.instance }} 已宕机"
```

### Exporter 配置

```properties
exporter.kafka.enabled=true
exporter.kafka.url=http://localhost:9308
exporter.kafka.scrape.interval.seconds=15

exporter.nats.enabled=true
exporter.nats.url=http://localhost:7777
exporter.nats.scrape.interval.seconds=15

exporter.rabbitmq.enabled=true
exporter.rabbitmq.url=http://localhost:9419
exporter.rabbitmq.scrape.interval.seconds=15
```

### 自定义业务指标

在应用内埋点，补充队列未覆盖的业务监控：

```java
Counter messageCount = Counter.build()
    .name("mq_messages_total")
    .help("Total number of messages")
    .labelNames("system", "topic")
    .register();

Histogram messageLatency = Histogram.build()
    .name("mq_message_latency_seconds")
    .help("Message processing latency")
    .buckets(0.001, 0.005, 0.01, 0.05, 0.1, 0.5, 1.0, 5.0)
    .register();
```

### 核心告警规则对比

| 系统 | 告警名称 | 表达式 | 持续时间 | 级别 |
| ------ | ---------- | -------- | ---------- | ------ |
| Kafka | KafkaHighConsumerLag | `kafka_consumer_lag_sum > 100000` | 5m | warning |
| Kafka | KafkaUnderReplicatedPartitions | `kafka_controller_offline_partitions_count > 0` | 1m | critical |
| Kafka | KafkaBrokerDown | `up{job="kafka"} == 0` | 1m | critical |
| NATS | NATSHighConnections | `nats_connz_connections > 10000` | 5m | warning |
| NATS | NATSHighMemory | `nats_varz_mem > 8589934592` | 5m | warning |
| RabbitMQ | RabbitMQHighQueueMessages | `rabbitmq_queue_messages > 100000` | 5m | warning |
| RabbitMQ | RabbitMQNodeDown | `rabbitmq_up == 0` | 1m | critical |

## 3.55.3 告警分级

### 分级阈值配置

模板 `monitor-alert-config.properties` 定义了 critical、warning、info 三级阈值：

```properties
alert.level.critical.enabled=true
alert.level.critical.threshold.error.rate=0.2      # 20% 错误率
alert.level.critical.threshold.latency.ms=5000     # 5 秒延迟
alert.level.critical.threshold.cpu.usage=0.9       # 90% CPU

alert.level.warning.enabled=true
alert.level.warning.threshold.error.rate=0.1       # 10% 错误率
alert.level.warning.threshold.latency.ms=1000      # 1 秒延迟
alert.level.warning.threshold.cpu.usage=0.8        # 80% CPU

alert.level.info.enabled=true
alert.level.info.threshold.error.rate=0.05         # 5% 错误率
alert.level.info.threshold.latency.ms=500          # 500 ms 延迟
```

### 分级响应标准

| 级别 | 触发条件 | 响应时间 | 通知渠道 | 处理要求 |
| ------ | ---------- | ---------- | ---------- | ---------- |
| critical | 错误率 ≥ 20%、延迟 ≥ 5s、CPU ≥ 90%、Broker/节点宕机 | 5 分钟 | 电话 + 短信 + 邮件 + 钉钉 | 立即介入，启动应急预案 |
| warning | 错误率 ≥ 10%、延迟 ≥ 1s、CPU ≥ 80%、积压 ≥ 10 万 | 15 分钟 | 邮件 + 钉钉 | 值班人员处理，必要时升级 |
| info | 错误率 ≥ 5%、延迟 ≥ 500 ms | 30 分钟 | 邮件 | 记录并观察趋势 |

## 3.55.4 AlertManager 路由

### alertmanager.yml 配置

模板配置示例：

```yaml
global:
  resolve_timeout: 5m

route:
  group_by: ['alertname', 'cluster', 'service']
  group_wait: 10s
  group_interval: 10s
  repeat_interval: 12h
  receiver: 'default'
  routes:
    - match:
        severity: critical
      receiver: 'critical-alerts'
      group_wait: 0s
      repeat_interval: 5m
    - match:
        severity: warning
      receiver: 'warning-alerts'
      repeat_interval: 30m

receivers:
  - name: 'default'
    webhook_configs:
      - url: 'http://localhost:5001/webhook'

  - name: 'critical-alerts'
    email_configs:
      - to: 'admin@example.com'
        from: 'alerts@example.com'
        smarthost: 'smtp.example.com:587'
    webhook_configs:
      - url: 'http://localhost:5001/webhook/critical'

  - name: 'warning-alerts'
    email_configs:
      - to: 'ops@example.com'
        from: 'alerts@example.com'
        smarthost: 'smtp.example.com:587'
    dingtalk_configs:
      - webhook_url: 'https://oapi.dingtalk.com/robot/send?access_token=xxx'
```

### 路由关键参数

- `group_by`：按 `alertname`、`cluster`、`service` 聚合告警，避免告警风暴。
- `group_wait=10s`：首次收到告警后等待 10 秒再发送，便于聚合同类告警。
- `group_interval=10s`：同一组内新增告警的最小发送间隔。
- `repeat_interval=12h`：默认 12 小时重复通知一次；critical 路由缩短为 5 分钟。

### 抑制与聚合

```properties
alert.inhibition.enabled=true
alert.inhibition.rules.file=/etc/mq/inhibition_rules.yml
alert.inhibition.group.by=alertname,instance
alert.inhibition.wait.seconds=300

alert.aggregation.enabled=true
alert.aggregation.group.by=alertname,severity
alert.aggregation.repeat.interval.seconds=3600
alert.aggregation.max.alerts=10
```

抑制规则示例：当 `KafkaBrokerDown` 触发时，抑制该 Broker 上的 `KafkaHighConsumerLag` 告警。

## 3.55.5 告警响应

### 告警响应流程

1. **接收**：AlertManager 根据路由将告警推送至对应接收组。
2. **确认**：值班人员在 5 分钟（critical）/ 15 分钟（warning）内点击确认。
3. **定位**：通过 Grafana 仪表板查看 `monitor.grafana.url=http://localhost:3000`，关联指标曲线。
4. **处置**：
   - Broker 宕机：触发集群切换，检查日志并重启。
   - 消费滞后：扩容消费者或排查消费耗时。
   - 错误率升高：回滚版本或启用降级开关。
5. **恢复**：问题解决后，Prometheus 在 `resolve_timeout=5m` 内自动发送恢复通知。
6. **复盘**：记录告警处置过程，更新 Runbook。

### Runbook 与检查脚本

每个告警都应附带 Runbook，例如 `KafkaHighConsumerLag` 需检查消费组滞后并扩容消费者或优化消费逻辑。

```bash
bash topics/scripts/alerts-check.sh [kafka|nats|rabbitmq|all]
```

## 3.55.6 最佳实践

1. **告警阈值基于基线**：使用过去 30 天 `monitor.storage.retention.days=30` 的 P99 数据设置阈值，避免拍脑袋。
2. **减少无效告警**：通过 `group_by` 与 `inhibition` 抑制关联告警，确保 critical 告警 actionable。
3. **多级通知渠道**：critical 走电话/短信，warning 走钉钉/邮件，info 仅邮件。
4. **告警即文档**：每个告警都附带 Runbook 链接，值班人员无需翻找文档。
5. **定期回顾告警质量**：每月统计告警触发量与误报率，持续优化阈值。
6. **可视化统一入口**：在 Grafana 配置消息队列统一大盘，刷新间隔 `30s`，默认时间范围 24 小时。

## 3.55.7 监控告警检查清单

### 实施前

- [ ] 确定监控系统：`monitor.system=prometheus`。
- [ ] 确定 Exporter 端口：Kafka `9308`、NATS `7777`、RabbitMQ `9419`。
- [ ] 制定三级阈值：critical `error.rate=0.2`、`latency.ms=5000`、`cpu.usage=0.9`；warning `error.rate=0.1`、`latency.ms=1000`、`cpu.usage=0.8`。
- [ ] 设计告警分组：`group_by=['alertname','cluster','service']`。

### 实施中

- [ ] 部署 Kafka Exporter、NATS Exporter、RabbitMQ Exporter， scrape interval 15s。
- [ ] 配置 `prometheus-alerts.yml`，覆盖 Lag、副本、Broker/节点宕机、连接数、内存、队列积压。
- [ ] 配置 `alertmanager.yml`，critical 路由 5 分钟重复，warning 路由 30 分钟重复。
- [ ] 配置邮件、钉钉、Slack 等通知渠道。
- [ ] 配置抑制规则 `inhibition_rules.yml` 与聚合参数 `max.alerts=10`。
- [ ] 在 Grafana 导入消息队列监控大盘，刷新间隔 30s。

### 实施后

- [ ] 运行 `bash topics/scripts/alerts-check.sh all` 验证各组件健康状态。
- [ ] 触发测试告警，验证 AlertManager 路由与通知渠道。
- [ ] 检查 critical 告警是否在 5 分钟内通知到值班人员。
- [ ] 每周 review 告警触发记录，调整误报规则。
- [ ] 每月更新 Runbook，补充新发现的故障场景。
