## 3.56.1 性能调优需求

消息性能调优通常围绕吞吐量、端到端延迟和资源利用率三类指标展开。在动手调优前，必须明确业务侧可接受的 P99 延迟、最低吞吐保证以及高峰持续时间。运维侧常见触发点包括：

- 生产消费速率出现持续倒挂，消息积压（lag）超过阈值；
- CPU 或磁盘 I/O 利用率长期高于 80%，但吞吐未达预期；
- 网络带宽或连接数接近上限，需要定位瓶颈层。

调优目标应写成可量化指标，例如：Kafka 单分区写入吞吐从 5 MB/s 提升到 20 MB/s，P99 延迟从 200 ms 降到 50 ms。目标层不同，优先调整的对象也不同：写入瓶颈先看 Producer 与 Broker，消费滞后先看 Consumer 并行度与分区数。

## 3.56.2 生产者层调优参数

Producer 层调优以批处理、压缩和确认策略为核心。模板 `performance-tune-config.properties` 中给出的关键参数如下：

- `batch.size`：建议设置为 32768 字节以上，高吞吐场景可设为 65536 或 131072；
- `linger.ms`：引入少量发送等待，建议 10–100 ms，与 `batch.size` 配合提升批次填充率；
- `compression.type`：优先使用 snappy 或 lz4，CPU 富余可尝试 zstd；
- `acks`：权衡可靠性，高吞吐设为 1，金融级可靠性设为 all；
- `buffer.memory`：增大客户端发送缓冲，建议 67108864 字节（64 MB）起步；
- `max.in.flight.requests.per.connection`：无顺序强依赖时可设为 5，提升管道并发；
- `retries` 与 `retry.backoff.ms`：失败重试 3 次，退避 100 ms，避免雪崩。

Kafka Producer 配置示例：

```properties
# /opt/kafka/config/producer-perf.properties
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
batch.size=65536
linger.ms=20
compression.type=snappy
acks=1
buffer.memory=134217728
max.in.flight.requests.per.connection=5
retries=3
retry.backoff.ms=100
```

NATS 与 RabbitMQ 的 Producer 侧同样遵循批量刷新原则。NATS 在批量发布后调用 `nc.Flush()`，RabbitMQ 则通过减少 `basic_publish` 的往返次数、按需选择 `delivery_mode=2` 持久化来降低 I/O 开销。

## 3.56.3 Broker层调优参数

Broker 层调优集中在分区/副本布局、网络缓冲和磁盘 I/O。Kafka Broker 常用参数包括：

- `num.network.threads`：处理网络请求的线程数，建议 Broker 上每 1 万连接增加 1 个线程；
- `num.io.threads`：磁盘 I/O 线程数，SSD 盘建议 8–16；
- `socket.send.buffer.bytes` 与 `socket.receive.buffer.bytes`：建议设置为 102400 字节以上；
- `socket.request.max.bytes`：控制单请求大小，默认 104857600 字节（100 MB）；
- `log.segment.bytes` 与 `log.retention.hours`：根据保留周期调整段大小，减少段文件数量；
- `replica.fetch.max.bytes` 与 `replica.socket.timeout.ms`：影响副本同步效率；
- `min.insync.replicas`：配合 `acks=all` 使用，建议设置为 2。

Kafka Broker 配置片段：

```properties
# /opt/kafka/config/server.properties
num.network.threads=8
num.io.threads=16
socket.send.buffer.bytes=102400
socket.receive.buffer.bytes=102400
socket.request.max.bytes=104857600
log.segment.bytes=1073741824
log.retention.hours=168
min.insync.replicas=2
replica.fetch.max.bytes=1048576
replica.socket.timeout.ms=30000
```

NATS JetStream 需关注 `max_memory_store` 与 `max_file_store`，RabbitMQ 则需调整 `vm_memory_high_watermark`（默认 0.4，可提升至 0.6–0.7）和 `disk_free_limit`（建议绝对值 5 GB 以上）。

## 3.56.4 消费者层调优参数

Consumer 层调优重点是拉取批次大小、并发线程数和反序列化效率。Kafka Consumer 关键参数：

- `fetch.min.bytes`：建议 1024–4096，配合 `fetch.max.wait.ms` 减少空轮询；
- `max.partition.fetch.bytes`：单分区单次拉取上限，默认 1048576 字节；
- `max.poll.records`：单次 poll 返回记录数，建议 500–1000；
- `max.poll.interval.ms`：处理耗时任务时适当调大，避免 rebalance；
- 消费者线程数一般与分区数对齐，避免线程空闲或竞争。

Kafka Consumer 配置示例：

```properties
# /opt/kafka/config/consumer-perf.properties
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
group.id=perf-test-group
fetch.min.bytes=4096
fetch.max.wait.ms=200
max.partition.fetch.bytes=2097152
max.poll.records=1000
max.poll.interval.ms=300000
enable.auto.commit=false
```

RabbitMQ Consumer 通过 `basic_qos(prefetch_count=100–500)` 控制预取量，NATS JetStream 使用 `SetPendingLimits` 限制待处理消息，避免 Consumer 内存被打爆。

## 3.56.5 压测验证方法

调优前后必须使用同一压测工具与同一负载模型，避免结果不可比。Kafka 自带 `kafka-producer-perf-test` 与 `kafka-consumer-perf-test`：

```bash
# 生产者压测：1000 万条、每条 1 KB、总吞吐 100 MB/s
kafka-producer-perf-test.sh \
  --topic perf-test \
  --num-records 10000000 \
  --record-size 1024 \
  --throughput 104857600 \
  --producer-props bootstrap.servers=broker1:9092 \
                   batch.size=65536 \
                   linger.ms=20 \
                   compression.type=snappy

# 消费者压测
kafka-consumer-perf-test.sh \
  --topic perf-test \
  --messages 10000000 \
  --threads 10 \
  --broker-list broker1:9092 \
  --group perf-consumer-group
```

NATS 可使用 `nats bench` 命令，RabbitMQ 可使用 PerfTest 工具：`rabbitmq-perf-test -x 10 -y 10 -u test-queue -a`。压测时同步采集 Broker 的 CPU、内存、磁盘 I/O、网络带宽四项指标，才能判断是真吞吐提升还是资源透支。

## 3.56.6 调优前后对比记录

每次调优都应建立对比表，记录基线、调整后指标、资源占用与变更参数。模板 `performance-tune-config.properties` 中的参数可直接作为表项引用。

| 指标 | 调优前基线 | 调优后结果 | 关键变更参数 | 备注 |
| --- | --- | --- | --- | --- |
| 写入吞吐 | 45 MB/s | 120 MB/s | batch.size=65536, linger.ms=20, snappy | 单 Producer 测试 |
| P99 发送延迟 | 180 ms | 42 ms | acks=1, buffer.memory=128 MB | 允许少量副本延迟 |
| 消费吞吐 | 38 MB/s | 95 MB/s | max.poll.records=1000, 10 消费者 | 分区数从 6 扩到 12 |
| CPU 利用率 | 35% | 68% | 压缩启用、并发提升 | 仍在安全水位 |
| 磁盘 I/O | 85 MB/s 读 | 210 MB/s 读 | num.io.threads=16, SSD | 随机读变顺序读 |

对比记录应归档到 `performance-tune-config.properties` 同级目录的 `results/` 中，文件命名格式：`perf-{topic}-{date}-baseline.csv` 与 `perf-{topic}-{date}-tuned.csv`。运维团队据此判断是否还有继续调优空间，或需要扩容。

## 3.56.7 性能调优检查清单

### 实施前

- [ ] 明确吞吐、延迟、资源利用率三类量化目标；
- [ ] 完成基线压测并记录 `kafka-producer-perf-test` / `kafka-consumer-perf-test` 原始结果；
- [ ] 确认当前分区数、副本数、Broker 版本及硬件配置（CPU/内存/磁盘类型）；
- [ ] 备份现有 `server.properties` 与 Producer/Consumer 配置文件。

### 实施中

- [ ] Producer 侧：`batch.size` ≥ 32768，`linger.ms` 设为 10–100 ms，启用 snappy/lz4 压缩；
- [ ] Broker 侧：`num.io.threads` 8–16，`socket.*.buffer.bytes` ≥ 102400，`log.segment.bytes` 按保留周期调优；
- [ ] Consumer 侧：`max.poll.records` 500–1000，`fetch.min.bytes` 1024–4096，消费者线程与分区数对齐；
- [ ] 按系统逐层修改、逐层验证，避免一次性修改过多参数导致无法定位问题。

### 实施后

- [ ] 重新运行压测，对比调优前后吞吐与延迟指标；
- [ ] 监控 CPU、内存、磁盘 I/O、网络带宽是否处于 80% 以下安全水位；
- [ ] 检查是否有消息积压（Consumer Lag）持续增长；
- [ ] 将最终配置写入 `performance-tune-config.properties` 并同步到配置仓库；
- [ ] 安排周期性复测（建议每月一次），根据业务增长持续优化。
