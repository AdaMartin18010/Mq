## 3.51.1 版本兼容与升级场景

### 常见场景

1. **Schema 演进**
   业务消息结构发生字段新增、删除或类型变更时，应通过 Schema Registry 控制兼容性级别。配置文件 `schema.registry.compatibility.level` 可设为 `backward`、`forward`、`full` 或 `none`，默认生产环境建议使用 `backward` 或 `full`，避免直接设为 `none` 导致旧消费者无法解析新消息。

2. **协议与 API 版本升级**
   消息中间件自身升级（如 Kafka 从 3.5 升到 3.7、RabbitMQ 从 3.12 升到 3.13）会引入新的 `inter.broker.protocol.version`、`log.message.format.version` 或客户端 API 版本。升级前必须确认当前集群所有节点已同步到同一协议版本，避免混合协议导致请求失败或副本同步异常。

3. **业务消息版本变更**
   应用层在消息头或消息体中携带版本标识，例如配置 `version.header.name=message-version` 并在生产者中写入 `1.0`、`2.0` 等版本号。消费者按版本路由处理，配置 `version.routing.default.version=1.0` 作为未携带版本头时的兜底版本。

4. **跨系统迁移**
   当业务从 RabbitMQ 迁到 Kafka，或从 MQTT 迁到 NATS JetStream 时，需要双写、流量灰度、数据对账与回滚窗口。配置 `migration.strategy=gradual` 开启渐进式迁移，`migration.gradual.dual.write.enabled=true` 启用双写。

## 3.51.2 滚动升级流程

### 升级前检查

1. **备份配置与元数据**
   升级前备份 `server.properties`、RabbitMQ 的 `rabbitmq.conf`、NATS 的 `nats-server.conf`、Pulsar 的 `broker.conf` 以及 ZooKeeper/KRaft 元数据。Kafka 集群还需导出 topic 分区信息：`kafka-topics.sh --bootstrap-server localhost:9092 --describe > topics-backup-$(date +%F).txt`。

2. **确认当前版本与兼容性矩阵**
   运行脚本 `topics/scripts/upgrade-check.sh [kafka|nats|rabbitmq|all]` 获取当前版本号。Kafka 额外检查 API 版本：`kafka-broker-api-versions.sh --bootstrap-server localhost:9092 | head -20`。

3. **检查集群健康状态**
   Kafka 需确认 `under-replicated-partitions` 为 0、`active-controller-count` 为 1；RabbitMQ 需确认 `rabbitmqctl cluster_status` 无分区告警；NATS 需确认 `nats server report jetstream` 无未同步 stream；Pulsar 需确认 `pulsar-admin brokers list` 全部在线。

### 单节点滚动步骤

以 Kafka 为例，推荐先升级 ZooKeeper（如仍在使用），再逐台升级 Broker；KRaft 模式下直接逐台升级 Controller/Broker。

```bash
#!/bin/bash
# Kafka 单节点滚动升级示例（每升级一台后人工确认再执行下一台）
BROKER=$1
NEW_VERSION_DIR=/opt/kafka_2.13-3.7.0

ssh $BROKER "sudo systemctl stop kafka" || exit 1
ssh $BROKER "sudo cp -r /opt/kafka /opt/kafka-backup-$(date +%F)"
ssh $BROKER "sudo ln -sfn $NEW_VERSION_DIR /opt/kafka"
# 先保留旧 protocol version，仅升级二进制
ssh $BROKER "sudo sed -i 's/^inter.broker.protocol.version=.*/inter.broker.protocol.version=3.5/' /opt/kafka/config/server.properties"
ssh $BROKER "sudo systemctl start kafka"

# 等待该 Broker 重新加入 ISR
until kafka-topics.sh --bootstrap-server localhost:9092 --describe | grep -v "Replica:" | grep -q "Leader:.*$BROKER"; do
  echo "等待 $BROKER 恢复 ISR..."
  sleep 10
done
echo "$BROKER 升级完成"
```

其他系统的关键命令：

- **RabbitMQ**：`rabbitmq-upgrade drain` 先排空节点队列连接，再升级 Erlang/OTP 与 RabbitMQ 包，重启后执行 `rabbitmqctl await_online_nodes 3`。
- **NATS**：替换 `nats-server` 二进制后执行 `nats server upgrade --server-name n1`（若使用 nats-cli 管理）。
- **Pulsar**：逐台替换 broker 包，保留 `brokerServiceTenantAllowedClusterList` 等协议相关配置，启动后观察 `pulsar-admin topics stats` 的 `replicationBacklog`。
- **MQTT Broker（EMQ X/Eclipse Mosquitto）**：先升级单节点并观察 `$SYS/brokers` 主题，集群模式下需确认 `rpc.tcp_server_port` 通信正常。
- **Redis Stream**：升级 Redis 实例时先执行 `CLUSTER FAILOVER` 将主节点切走，替换二进制后重启，确认 `CLUSTER NODES` 状态为 `connected`。

### 升级后验证

1. **协议版本统一生效**
   全部 Broker 升级完成后，再将 `inter.broker.protocol.version` 改到目标版本（如 3.7），并逐台重启。Kafka 验证命令：

   ```bash
   kafka-broker-api-versions.sh --bootstrap-server localhost:9092 | grep "Produce\|Fetch" | head -10
   ```

   输出应包含目标版本支持的 API 关键字。

2. **业务流量回放验证**
   用测试生产者发送带版本头的消息，确认新旧消费者都能正常消费。检查 `version.monitor.metrics=version_count,version_distribution,compatibility_errors` 中兼容性错误为 0。

3. **元数据一致性检查**
   Kafka 运行 `kafka-metadata-quorum --bootstrap-server localhost:9092 describe --status`（KRaft）或 `zookeeper-shell.sh` 检查 `/brokers/ids`；RabbitMQ 运行 `rabbitmqctl cluster_status`；NATS 运行 `nats server report accounts`。

## 3.51.3 协议与 Schema 兼容检查

### Schema Registry 检查

1. **服务可达性**
   执行 `curl -s http://localhost:8081/subjects` 应返回 topic 对应的 subject 列表。若使用 Confluent Schema Registry，默认端口为 8081；Pulsar 内置 Schema Registry 通过 `pulsar-admin schemas get` 访问。

2. **兼容性级别核查**
   对每个 subject 检查配置，确保与 `schema.registry.compatibility.level` 一致：

   ```bash
   for subject in $(curl -s http://localhost:8081/subjects | jq -r '.[]'); do
     level=$(curl -s "http://localhost:8081/config/$subject" | jq -r '.compatibilityLevel')
     echo "$subject: $level"
   done
   ```

   生产环境建议 `FULL` 或 `BACKWARD`，若出现 `NONE` 需人工复核。

3. **Schema 演进校验**
   注册新 Schema 前用测试接口验证兼容性：`curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" --data '{"schema":"..."}' http://localhost:8081/compatibility/subjects/orders-value/versions/latest`。返回 `is_compatible: true` 方可注册。

### 消息格式与版本头检查

1. **版本头必填检查**
   配置 `version.header.required=true` 后，生产者必须在消息头或消息属性中写入 `message-version`。例如 Kafka 使用 `record.headers().add("message-version", "2.0".getBytes())`；RabbitMQ 使用 `properties.headers["message-version"]="2.0"`；MQTT 5.0 使用 User Property；Pulsar 使用 `MessageBuilder.setProperty("message-version","2.0")`。

2. **版本路由检查**
   配置 `version.routing.enabled=true` 与 `version.routing.strategy=header`，消费者根据 `version.routing.header.name=message-version` 路由到对应的处理函数。兜底版本 `version.routing.default.version=1.0` 用于兼容历史消息。

3. **格式检查脚本**
   运行 `topics/scripts/version-compat-check.sh`，脚本会检查 Schema Registry 状态并输出兼容性建议。若输出中出现 `Schema Registry未运行` 或兼容性级别为 `NONE`，必须修复后才能继续迁移。

### API 与协议版本检查

| 系统 | 检查命令 | 关注指标 | 异常处理 |
| ------ | ---------- | ---------- | ---------- |
| Kafka | `kafka-broker-api-versions.sh --bootstrap-server localhost:9092` | API 版本号、broker 版本 | 若客户端 API 高于 broker，升级客户端或回退 |
| NATS | `nats-server -v` | Server 版本、客户端协议 | 旧客户端通常兼容，需关注 JetStream API 变化 |
| RabbitMQ | `rabbitmqctl version` | RabbitMQ 与 Erlang 版本 | 版本矩阵不匹配时无法启动 |
| Pulsar | `pulsar-admin brokers list` / `pulsar version` | Broker 协议版本 | 检查 `protocolVersion` 是否一致 |
| MQTT | 查看 Broker 日志中的 MQTT 协议级别 | CONNECT 报文中的 Protocol Level | 3.1.1 与 5.0 客户端不能混用同一端口需显式配置 |
| Redis Stream | `redis-cli INFO server` | Redis 版本 | 6.2 以下不支持 Stream 部分命令，需提前升级 |

## 3.51.4 双写迁移与回滚预案

### 双写配置

1. **开启双写**
   在 `version-compat-config.properties` 中设置 `migration.gradual.dual.write.enabled=true`。生产端同时向旧 Topic/Exchange/Stream 和新 Topic/Exchange/Stream 写入同一条消息，写入时均携带 `message-version` 头。

2. **保持顺序与幂等**
   双写阶段建议使用相同的消息 Key（Kafka）、Routing Key（RabbitMQ）、Subject（NATS）或 Stream Key（Redis），并开启生产者幂等。Kafka 设置 `enable.idempotence=true`；RabbitMQ 使用 `confirm` 模式并设置 `publisher-confirms=true`；Pulsar 开启 `messageRouter` 保证同一 Key 进入同一分区。

3. **双写示例配置**

   ```properties
   # 双写迁移配置片段
   migration.strategy=gradual
   migration.gradual.dual.write.enabled=true
   migration.gradual.switch.percentage=10
   version.header.name=message-version
   version.header.required=true
   version.routing.enabled=true
   version.routing.default.version=1.0
   ```

   生产端代码需同时调用 `send(oldTopic, record)` 与 `send(newTopic, record)`，并在异常时记录 `dual_write_failures` 指标。

### 灰度切量

1. **按百分比切量**
   配置 `migration.gradual.switch.percentage=10` 表示每批次切换 10% 流量。切量维度可以是租户 ID 取模、用户 ID 尾号、消息 Key 哈希或按 Topic 分区范围。每次切量后观察至少一个完整业务周期（建议 24 小时）。

2. **监控阈值**
   双写期间重点监控 `version.monitor.alert.compatibility.error.threshold=0.01`，即兼容性错误率超过 1% 时暂停切量；消费延迟超过业务 SLA 的 2 倍时回退 10% 流量。

3. **数据对账**
   在旧系统与新系统分别统计单位时间内的消息条数、唯一 Key 数、版本分布，偏差率应小于 0.1%。Kafka 可用 `kafka-consumer-groups.sh` 对比 offset；RabbitMQ 对比队列 `messages_ready` 与消费 ack 数；Redis Stream 对比 `XLEN` 与消费组 `pending` 数量。

### 回滚预案

1. **自动与手动降级**
   配置 `downgrade.strategy.enabled=true`，`downgrade.strategy.type=automatic` 在触发 `compatibility_error` 或 `performance_issue` 时自动切回旧系统；`manual` 模式需要运维人员确认后执行脚本回滚。

2. **回滚窗口**
   旧版本集群在 100% 切量成功后仍需保留 24-72 小时，期间不关闭旧 Topic/Exchange/Stream。保留窗口内，若新版本出现不可修复的兼容性问题，可立即将 DNS/VIP/配置中心指向旧集群。

3. **回滚命令示例**

   ```bash
   # 手动回滚：将流量配置中心切回旧版本
   ./config-center set message.producer.target=legacy
   ./config-center set message.consumer.target=legacy
   # 停止新版本双写任务
   kubectl scale deployment mq-producer-v2 --replicas=0
   # 恢复旧系统消费组到最新 offset
   kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
     --group order-consumer --topic orders --reset-offsets --to-latest --execute
   ```

## 3.51.5 版本兼容检查清单

### 实施前

- [ ] 备份 `server.properties` / `broker.conf` / `nats-server.conf` / `rabbitmq.conf` 与元数据
- [ ] 确认当前版本：`upgrade-check.sh kafka`、`upgrade-check.sh nats`、`upgrade-check.sh rabbitmq`
- [ ] 确认 `schema.registry.compatibility.level` 为 `backward`/`forward`/`full`，非 `none`
- [ ] 确认 `version.header.name=message-version` 并在所有生产者中开启
- [ ] 确认 `version.header.required=true` 对历史消息无影响或已设置兜底版本
- [ ] 检查 `under-replicated-partitions`、`active-controller-count`、RabbitMQ 集群分区告警均为正常值
- [ ] 制定回滚窗口策略：`downgrade.strategy.enabled=true`，旧集群保留 24-72 小时

### 实施中

- [ ] 逐台滚动升级 Broker/Server，每升级一台后等待 ISR/队列同步恢复再继续
- [ ] 升级后先保留旧 `inter.broker.protocol.version`，全部节点升级完再统一提升协议版本
- [ ] 执行 `version-compat-check.sh` 检查 Schema Registry 与兼容性级别
- [ ] 开启双写：`migration.gradual.dual.write.enabled=true`，监控 `dual_write_failures`
- [ ] 按 `migration.gradual.switch.percentage=10` 灰度切量，每批观察 24 小时
- [ ] 兼容性错误率超过 `version.monitor.alert.compatibility.error.threshold=0.01` 时暂停切量
- [ ] 消费延迟达到业务 SLA 2 倍时立即回退 10% 流量

### 实施后

- [ ] 100% 切量完成后持续观察一个完整业务周期
- [ ] 关闭双写并清理旧版本生产者/消费者实例
- [ ] 验证 `version_count`、`version_distribution`、`compatibility_errors` 指标稳定
- [ ] 回收旧集群资源，但保留配置备份与日志至少 30 天
- [ ] 更新运维手册，记录本次升级的协议版本、Schema 版本与回滚操作步骤
