## 3.60.1 成本优化需求

消息成本优化需求应覆盖资源成本、运营成本、云服务成本三类。资源成本包括计算、存储、网络三项直接开销；运营成本包括人工运维、故障处理、容量管理等间接开销；云服务成本包括实例类型、存储分层、网络带宽、预留实例等云厂商计费项。

制定优化目标时，参考 `topics/config-templates/cost-optimize-config.properties` 中的 `cost.optimize.target.reduction.percentage=20`、`cost.optimize.target.resource.reduction=15`、`cost.optimize.target.storage.reduction=30`、`cost.optimize.target.operation.reduction=25`。优化应以不影响业务 SLA 为前提，优先处理利用率低、冗余配置、过期数据三类浪费。

## 3.60.2 成本分析方法

### 3.60.2.1 资源利用率分析

使用 `topics/scripts/cost-analysis.sh` 脚本采集 CPU、内存、磁盘使用率。脚本通过 `top -bn1` 获取 CPU 使用率，通过 `free -h` 获取内存使用，通过 `df -h /` 获取磁盘使用。分析阈值参照 `cost.optimize.resource.cpu.target.usage=0.8` 和 `cost.optimize.resource.memory.target.usage=0.8`，长期低于 50% 的资源应降配，长期高于 80% 的资源应扩容或优化。

```bash
# 生成成本分析报告，默认文件名带时间戳
./topics/scripts/cost-analysis.sh cost_analysis_$(date +%Y%m%d).txt
```

### 3.60.2.2 成本分解

按资源类型分解时，区分计算、存储、网络；按业务线分解时，按 Topic/Queue/Stream 归属团队或产品；按时间维度分解时，识别峰值、低谷和持续增长趋势。`cost.optimize.analysis.breakdown.by=resource` 支持 resource/business/time 三种维度。

| 分解维度 | 适用场景 | 关键指标 | 优化抓手 |
| --- | --- | --- | --- |
| 资源类型 | 识别单项资源浪费 | CPU/内存/磁盘/网络使用率 | 降配、压缩、分层 |
| 业务线 | 责任归属与分摊 | 各 Topic/Queue 资源占用 | 配额管理、归档策略 |
| 时间维度 | 发现趋势与峰值 | 日/周/月成本曲线 | 预留实例、自动扩缩容 |

### 3.60.2.3 成本监控与预测

启用 `cost.optimize.monitor.enabled=true`，监控指标包括 `resource_cost`、`storage_cost`、`network_cost`、`operation_cost`。当成本环比增长超过 `cost.optimize.monitor.alert.threshold.percentage=20` 时触发告警。预测方法使用 `cost.optimize.analysis.prediction.method=historical`，结合容量规划与业务增长进行滚动预测。

## 3.60.3 成本优化策略

### 3.60.3.1 计算资源优化

合理选择实例规格，避免过度配置。对 Kafka 应依据吞吐与分区数计算 Broker 数量；对 NATS 应依据连接数与 JetStream 存储规模选择节点；对 RabbitMQ 应依据队列数与镜像策略选择内存型实例。启用自动扩缩容 `cost.optimize.resource.auto.scale.enabled=true`，配置最小实例数 2、最大实例数 10。

### 3.60.3.2 存储成本优化

启用压缩 `cost.optimize.storage.compression.enabled=true`，Kafka 选择 `compression.type=snappy`，NATS JetStream 选择 `S2Compression`。实施分层存储：`cost.optimize.storage.tiering.hot.storage=ssd`、`cost.optimize.storage.tiering.cold.storage=hdd`。设置保留策略 `cost.optimize.storage.retention.days=7`，并启用定时清理 `cost.optimize.storage.cleanup.schedule=0 2 * * *`。

```properties
# Kafka 生产者压缩与批量配置示例
compression.type=snappy
batch.size=32768
linger.ms=10
log.retention.hours=168
log.segment.bytes=1073741824
```

### 3.60.3.3 网络成本优化

启用批量发送 `cost.optimize.network.batch.enabled=true`，配置 `cost.optimize.network.batch.size=32768`。开启网络压缩 `cost.optimize.network.compression.enabled=true`，类型为 snappy。对跨可用区流量进行优化，尽量将生产者和消费者部署在相同可用区，减少跨区域带宽费用。

### 3.60.3.4 运营成本优化

通过自动化运维减少人工干预：`cost.optimize.operation.automation.enabled=true` 覆盖 deployment、testing、monitoring。使用 Prometheus + Grafana 自动监控告警，减少人工巡检。将重复性操作脚本化，如 `cost-optimize.sh` 定期检查资源、存储、网络、运营成本。

```bash
# 执行成本优化检查
./topics/scripts/cost-optimize.sh
```

### 3.60.3.5 云服务成本优化

长期使用启用预留实例 `cost.optimize.cloud.reserved.instances.enabled=true`，期限 `cost.optimize.cloud.reserved.instances.term=1` 年，可节省 30%–50%。非关键任务可启用 Spot 实例 `cost.optimize.cloud.spot.instances.enabled=false`（默认关闭，需评估可中断性），设置最高价格 `cost.optimize.cloud.spot.instances.max.price=0.1`。存储分层配置 `hot=ssd`、`cold=hdd`、`archive=object_storage`。

## 3.60.4 各系统成本优化落地

### 3.60.4.1 Kafka

Kafka 成本主要来源于 Broker 计算与日志存储。落地时开启生产者压缩 `compression.type=snappy`，设置 `log.retention.hours=168`、`log.segment.bytes=1073741824`，合理规划分区数与副本数，非关键 Topic 可将副本数从 3 降至 2。对冷数据使用分层存储，将旧日志迁移到 HDD 或对象存储。

### 3.60.4.2 NATS

NATS JetStream 成本与 Stream 数量、存储大小、保留时间相关。配置 `Storage: FileStorage`、`MaxAge: 7 * 24 * time.Hour`、`MaxBytes: 10 * 1024 * 1024 * 1024`、`Compression: S2Compression`。复用连接池，控制订阅数量，避免无限制创建 Consumer。

### 3.60.4.3 RabbitMQ

RabbitMQ 成本主要来源于内存与队列数。通过队列参数控制生命周期：`x-message-ttl=3600000`、`x-max-length=10000`、`x-max-length-bytes=1073741824`。合理设置 `basic_qos prefetch_count=100`，避免消费者内存占用过高。对非持久化消息减少磁盘写入。

### 3.60.4.4 Redis Stream

Redis Stream 成本与内存容量直接相关。设置 `MAXLEN` 限制 Stream 长度，配置 `XTRIM` 定时清理。对历史数据使用 Redis 持久化策略 `appendonly yes` 结合 RDB 快照，避免 AOF 无限膨胀。大容量场景可启用 Redis Cluster 分片。

## 3.60.5 云成本对比

在不同云厂商与计费模式之间进行选择时，应综合考虑单价、可用性、可扩展性及运维复杂度。以下对比基于典型消息队列 3 节点 8 核 16GB、1TB SSD 存储、月流量 10TB 的场景估算，实际价格以各云厂商最新报价为准。

| 计费模式 | 适用场景 | 成本节省 | 风险 | 推荐系统 |
| --- | --- | --- | --- | --- |
| 按需实例 | 临时测试、突发负载 | 基准 | 无 | 全部 |
| 预留实例 1 年 | 稳定生产负载 | 30%–50% | 锁定规格 | Kafka、RabbitMQ |
| 预留实例 3 年 | 长期稳定负载 | 50%–65% | 长期锁定 | Kafka 核心集群 |
| Spot/抢占式实例 | 非关键消费端、批处理 | 60%–90% | 可能被回收 | NATS 消费者 |
| Serverless | 波动大、低流量 | 按量付费 | 冷启动、单价高 | 轻量网关 |
| 对象存储归档 | 冷数据、审计日志 | 70%–90% | 取回延迟 | 归档数据 |

选择建议：核心 Broker 使用 1 年或 3 年预留实例保证稳定性；消费端弹性扩容结合 Spot 实例；历史消息与审计日志定期迁移到对象存储归档层。

## 3.60.6 成本优化效果评估

成本优化效果应从资源利用率、成本降幅、业务影响三个维度评估。资源利用率目标为 CPU 与内存达到 `cost.optimize.resource.cpu.target.usage=0.8` 和 `cost.optimize.resource.memory.target.usage=0.8`。成本降幅对照 `cost.optimize.target.reduction.percentage=20` 等目标逐项验收。业务影响通过消息延迟、错误率、可用性指标监控，确保优化未降低 SLA。

评估周期建议为优化实施后第 7 天、第 30 天、第 90 天各一次。第 7 天关注配置生效与告警情况；第 30 天关注账单变化趋势；第 90 天评估长期稳定性与进一步优化的空间。评估报告应包含优化前后对比数据、节省金额、未达标项及后续计划。若未达标，需回滚或调整策略，避免以牺牲可用性为代价换取成本下降。

## 3.60.7 最佳实践

1. **定期成本复盘**：每日生成成本报告 `cost.optimize.monitor.report.frequency=daily`，每周召开成本复盘会议。
2. **资源利用率优先**：将 CPU 与内存使用率目标设定为 80%，既避免浪费，又保留突发缓冲。
3. **存储生命周期管理**：热数据 1 天、冷数据 30 天、归档数据 365 天，通过 `cost.optimize.storage.tiering` 自动迁移。
4. **网络批量与压缩**：生产者配置 `batch.size=32768`、`linger.ms=10`，降低网络请求次数。
5. **预留与 Spot 结合**：核心 Broker 使用预留实例保证稳定性，批处理消费者使用 Spot 实例降低成本。
6. **持续监控**：成本优化不是一次性项目，需持续运行 `cost-analysis.sh` 与 `cost-optimize.sh`，根据业务增长动态调整资源配置。

## 3.60.8 成本优化检查清单

### 实施前

- [ ] 已设定优化目标：`cost.optimize.target.reduction.percentage=20`；
- [ ] 已配置成本分解维度：`cost.optimize.analysis.breakdown.by=resource`；
- [ ] 已启用成本监控：`cost.optimize.monitor.enabled=true`；
- [ ] 已设置告警阈值：`cost.optimize.monitor.alert.threshold.percentage=20`；
- [ ] 已采集基线资源利用率：CPU、内存、磁盘、网络；
- [ ] 已识别可降配或释放的闲置资源。

### 实施中

- [ ] 计算资源利用率目标达到 `cost.optimize.resource.cpu.target.usage=0.8` 和 `cost.optimize.resource.memory.target.usage=0.8`；
- [ ] 已启用存储压缩：`cost.optimize.storage.compression.enabled=true`，类型 snappy；
- [ ] 已配置数据保留：`cost.optimize.storage.retention.days=7`；
- [ ] 已启用批量发送：`cost.optimize.network.batch.enabled=true`、`cost.optimize.network.batch.size=32768`；
- [ ] 已配置自动扩缩容：最小 2、最大 10 实例；
- [ ] 已启用预留实例：`cost.optimize.cloud.reserved.instances.enabled=true`，期限 1 年；
- [ ] 已部署 `cost-optimize.sh` 与 `cost-analysis.sh` 脚本定期执行。

### 实施后

- [ ] 成本降低达到 `cost.optimize.target.reduction.percentage=20`；
- [ ] 存储成本降低达到 `cost.optimize.target.storage.reduction=30`；
- [ ] 运营成本降低达到 `cost.optimize.target.operation.reduction=25`；
- [ ] 资源利用率稳定在 60%–80% 区间；
- [ ] 成本监控告警无异常触发；
- [ ] 已生成成本优化报告并归档。
