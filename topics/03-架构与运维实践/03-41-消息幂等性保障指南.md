## 3.41.1 幂等性需求

### 重复消息来源

1. **网络重传**
   - 生产者发送消息后未收到 ACK，TCP 重传或客户端重试会导致同一条消息被写入多次。
   - Kafka Producer 在 `retries` 大于 0 时可能产生重复消息，需配合 `enable.idempotence=true` 消除。

2. **系统重试与故障恢复**
   - 消费失败触发重试，或 Consumer 处理完业务但提交 offset 前崩溃，都会导致消息被重新投递。
   - 重试间隔超过 `idempotency.cache.ttl.seconds=3600` 后，内存去重可能失效，需依赖持久化去重表。

### 业务幂等场景

1. **订单创建**
   - 同一订单创建请求被多次处理时，必须保证只生成一笔订单。
   - 幂等键建议使用 `biz_type:order:create:{order_no}` 格式。

2. **支付处理**
   - 支付回调可能因网络超时被重复发送，需根据支付流水号去重。
   - 重复回调直接返回成功，避免重复扣款或重复发货。

3. **状态更新**
   - 状态机流转需满足幂等，例如订单从 `PAID` 到 `SHIPPED` 只能执行一次，使用版本号或状态条件更新防止并发覆盖。

## 3.41.2 幂等键设计与去重表

### 键生成策略

1. **消息ID方案**
   - 生产者为每条消息生成全局唯一ID，例如 UUID 或 Snowflake。
   - Kafka 使用 `kafka.transaction.id` 保证跨会话幂等，RabbitMQ 使用 `message_id` 属性。
   - 配置 `nats.idempotence.msg.id.generator=uuid`、`rabbitmq.idempotence.message.id.generator=uuid`。

2. **业务键方案**
   - 以业务唯一字段作为幂等键，例如订单号、支付流水号、用户ID+操作类型。
   - 业务键需稳定不变，避免使用可能重复的本地序列号。

3. **复合键方案**
   - 组合消息ID与业务键：`{biz_type}:{biz_key}:{msg_id}`，适用于同一业务操作由多条消息触发的场景。

### 去重表设计

1. **表结构**
   - 核心字段：`idempotency_key`（唯一索引）、`biz_type`、`biz_key`、`status`、`create_time`、`expire_time`。
   - `status` 区分 `PROCESSING`、`SUCCESS`、`FAILED`，支持并发控制。

2. **存储选型**
   - 内存：适合短周期去重，配置 `idempotency.check.type=memory`。
   - Redis：适合分布式场景，配置 `idempotency.check.type=redis`，TTL 为 `idempotency.check.storage.redis.ttl.seconds=86400`。
   - 数据库：适合长周期强一致场景，配置 `idempotency.check.type=database`。

3. **本地缓存**
   - 配置 `idempotency.cache.enabled=true`、`idempotency.cache.size=100000`，命中率应高于 80%。

## 3.41.3 各系统落地实现

### Kafka 幂等生产者与事务

1. **幂等生产者配置**
   - 开启 `enable.idempotence=true`，必须配合 `acks=all` 和 `retries=2147483647`。
   - `max.in.flight.requests.per.connection` 建议设置为 5，与 Kafka 2.5+ 版本兼容。

2. **事务生产者代码示例**

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-service-tx-1");
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("orders", orderId, payload));
    producer.sendOffsetsToTransaction(consumer.position(consumer.assignment()), consumer.groupMetadata());
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
    throw e;
}
```

3. **Consumer 幂等**
   - 即使开启幂等生产者，Consumer 仍可能因 rebalance 或手动提交失败而重复消费。
   - 消费端必须维护去重表或本地缓存，配置 `idempotency.check.enabled=true`。

### RabbitMQ 应用层幂等

1. **消息ID配置**
   - 发送时设置 `message_id=str(uuid.uuid4())`，delivery_mode=2 持久化。
   - 配置 `rabbitmq.idempotence.enabled=true`、`rabbitmq.idempotence.type=message-id`。

2. **消费端去重代码示例**

```python
processed_ids = set()

def callback(ch, method, properties, body):
    msg_id = properties.message_id
    if msg_id in processed_ids:
        ch.basic_ack(delivery_tag=method.delivery_tag)
        return
    process(body)
    processed_ids.add(msg_id)
    ch.basic_ack(delivery_tag=method.delivery_tag)

channel.basic_publish(
    exchange='orders',
    routing_key='',
    body=message,
    properties=pika.BasicProperties(
        message_id=str(uuid.uuid4()),
        delivery_mode=2
    )
)
```

### NATS 应用层幂等

1. **MsgId 方案**
   - 发布时通过 `nats.MsgId("msg-123")` 设置去重键。
   - JetStream 在 `MaxMsgSize` 范围内对相同 MsgId 自动去重。

2. **消费端去重代码示例**

```go
js.Publish("orders", data, nats.MsgId("msg-123"))
processedIDs := make(map[string]bool)
nc.Subscribe("orders", func(msg *nats.Msg) {
    msgID := msg.Header.Get("Nats-Msg-Id")
    if processedIDs[msgID] {
        return
    }
    process(msg)
    processedIDs[msgID] = true
})
```

## 3.41.4 配置参数与运维命令

### 模板参数说明

| 参数名 | 含义 | 推荐值 | 适用系统 |
|---|---|---|---|
| `kafka.producer.idempotence.enabled` | 是否开启 Kafka 幂等生产者 | `true` | Kafka |
| `kafka.producer.acks` | 生产者确认级别 | `all` | Kafka |
| `kafka.producer.retries` | 发送失败重试次数 | `2147483647` | Kafka |
| `kafka.producer.max.in.flight.requests.per.connection` | 单连接并发请求数 | `5` | Kafka |
| `kafka.transaction.id` | 事务 ID | `my-transactional-id` | Kafka |
| `nats.idempotence.type` | NATS 幂等类型 | `msg-id` / `application` | NATS |
| `rabbitmq.idempotence.type` | RabbitMQ 幂等类型 | `message-id` / `application` | RabbitMQ |
| `idempotency.check.type` | 去重存储类型 | `memory` / `redis` / `database` | 通用 |
| `idempotency.cache.size` | 本地缓存大小 | `100000` | 通用 |
| `idempotency.alert.duplicate.rate.threshold` | 重复率告警阈值 | `0.01` | 通用 |

### 常用运维命令

1. **Kafka 查看生产者幂等状态**
   ```bash
   kafka-configs.sh --bootstrap-server kafka:9092 --entity-type clients \
     --entity-name producer-1 --describe
   ```

2. **Redis 去重键查询**
   ```bash
   redis-cli --scan --pattern "idempotency:order:*" | wc -l
   redis-cli ttl idempotency:order:20240106:001
   ```

3. **数据库去重表检查**
   ```sql
   SELECT biz_type, COUNT(*) AS dup_count
   FROM idempotency_log
   WHERE create_time > DATE_SUB(NOW(), INTERVAL 1 HOUR)
   GROUP BY biz_type;
   ```

## 3.41.5 监控告警与最佳实践

### 监控指标

1. **重复消息率**
   - 指标名 `duplicate_count`，计算单位时间内重复消息数量。
   - 重复率超过 `idempotency.alert.duplicate.rate.threshold=0.01`（1%）时触发告警。

2. **幂等检查耗时**
   - 指标名 `idempotency_check_duration`，按 P50/P95/P99 统计。
   - Redis 场景 P99 应低于 10ms，数据库场景 P99 应低于 50ms。

3. **去重存储容量**
   - 指标名 `idempotency_check_count`，监控 Redis 内存或数据库表增长趋势。
   - 配置合理的 TTL，例如 `idempotency.check.storage.redis.ttl.seconds=86400`。

### 设计建议

1. **多层防护**
   - 系统层：Kafka 开启幂等生产者，RabbitMQ/NATS 设置消息ID。
   - 应用层维护去重表或缓存，数据层使用唯一索引或状态机条件更新。

2. **异常处理**
   - 去重表插入冲突时，先查询状态：若 `SUCCESS` 则直接返回，若 `FAILED` 则允许重试。
   - 处理中状态超过 5 分钟未更新，应视为超时并释放锁。

3. **性能优化**
   - 高频场景使用 Redis + 本地缓存双层结构，`idempotency.cache.size=100000` 命中率高时可降低 Redis 压力。

## 3.41.6 幂等性检查清单

### 实施前

- [ ] 梳理重复消息来源：网络重传、系统重试、故障恢复、rebalance 等。
- [ ] 确定幂等键生成方式：消息ID、业务键或复合键，并配置相应 generator。
- [ ] 选择去重存储：内存、Redis 或数据库，配置 `idempotency.check.type`。
- [ ] 评估重复窗口：根据业务特点设置 TTL，例如 `idempotency.check.storage.redis.ttl.seconds=86400`。
- [ ] 设计并发控制：去重表状态字段或分布式锁，防止并发重复处理。

### 实施中

- [ ] Kafka 配置 `enable.idempotence=true`、`acks=all`、`retries=2147483647`、`max.in.flight.requests.per.connection=5`。
- [ ] Kafka 事务生产者配置唯一的 `kafka.transaction.id`，并正确处理 `commitTransaction`/`abortTransaction`。
- [ ] RabbitMQ 发送消息时设置 `message_id` 并持久化，配置 `rabbitmq.idempotence.enabled=true`。
- [ ] NATS 发布时使用 `nats.MsgId`，配置 `nats.idempotence.check.enabled=true`。
- [ ] 消费端实现去重表插入+状态查询，配置 `duplicate_count`、`idempotency_check_count`、`idempotency_check_duration` 和告警通道。

### 实施后

- [ ] 功能验证：模拟网络中断和 Consumer 重启，确认重复消息只被处理一次。
- [ ] 性能测试：压测下 P99 幂等检查耗时 Redis 低于 10ms、数据库低于 50ms。
- [ ] 重复率巡检：观察 `idempotency.alert.duplicate.rate.threshold=0.01` 是否被触发。
- [ ] 故障演练：重启 Producer/Consumer/Broker，验证事务、TTL 与去重状态一致性。
