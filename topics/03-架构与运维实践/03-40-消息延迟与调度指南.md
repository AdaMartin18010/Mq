## 3.40.1 延迟需求分类

### 业务需求

1. **定时任务**
   - 订单创建后 30 分钟未支付自动取消，需将取消指令延迟投递到下游服务。
   - 会员到期前 7 天、1 天、当天分三次发送续费提醒。
   - 活动开始前 5 分钟向订阅用户推送开始通知。

2. **重试策略**
   - 消费失败时先延迟 1 秒重试，随后按指数退避到 60 秒上限。
   - 最大重试次数达到 10 次后转入死信队列人工介入。

3. **业务场景**
   - 电商订单超时关闭：延迟精度要求分钟级，允许少量秒级偏差。
   - 支付超时关单：延迟消息量可能达到每秒万级，需水平扩展。
   - 预约服务提醒：延迟时间跨度从几分钟到数月不等，需持久化存储。

### 技术指标

1. **延迟精度**
   - 秒级：RocketMQ 延迟级别、RabbitMQ TTL+DLX 通常误差在 1-5 秒内。
   - 毫秒级：RabbitMQ 延迟插件 `x-delay` 可精确到毫秒；Kafka 应用层扫描方案依赖 `kafka.delay.scan.interval.seconds`，默认 60 秒。

2. **吞吐量**
   - RocketMQ 内置延迟级别适合高吞吐，建议单机延迟消息 TPS 不超过 5 万。
   - Kafka 多延迟 Topic 可通过增加分区水平扩展；RabbitMQ 单队列 TTL 堆积超过 100 万时性能明显下降，需分片。

3. **可靠性**
   - 延迟消息必须持久化，`delay.storage.persistent=true` 开启磁盘落盘。
   - 保留时间 `delay.storage.retention.hours` 默认 24 小时，长周期预约场景建议设置为业务最大延迟的两倍。

## 3.40.2 调度策略与选型

### 固定延迟

1. **实现要点**
   - 发送时为消息设置固定延迟时长，例如 `delay.fixed.milliseconds=60000` 表示延迟 60 秒。
   - RocketMQ 使用内置延迟级别，代码中通过 `setDelayTimeLevel(3)` 选择 10 秒级别。
   - 配置文件中 `delay.strategy=fixed` 声明当前集群使用固定延迟策略。

2. **适用场景**
   - 统一超时处理、固定重试间隔、简单定时提醒。
   - 不适合需要每个消息独立指定延迟时间的场景。

### 动态延迟

1. **实现要点**
   - 每个消息携带期望执行时间戳或自定义延迟毫秒数。
   - Kafka 应用层方案通过消息时间戳判断：`record.timestamp() > System.currentTimeMillis()` 则跳过。
   - RabbitMQ 延迟插件通过消息头 `headers={'x-delay': 60000}` 动态指定延迟。

2. **配置项**
   - `delay.strategy=dynamic` 开启动态延迟。
   - `nats.delay.max.seconds=86400` 限制单条消息最大延迟为 24 小时。

### 定时调度

1. **实现要点**
   - 使用 Cron 表达式或绝对时间触发，例如每天 09:00 发送日报。
   - 不推荐用消息队列直接实现复杂 Cron，可配合 Quartz/XXL-JOB 生成延迟消息。
   - 将未来 24 小时内的任务预写入延迟队列，到期后由调度器触发。
   - 定时任务生成消息的 Worker 必须设置唯一锁，防止多实例重复投递。

## 3.40.3 各系统落地实现

### RocketMQ 延迟级别

1. **内置级别**
   - 开源版支持 18 个固定延迟级别：1s、5s、10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h。
   - 商业版支持任意时间精度，通过 `setDelayTimeMs(60000)` 设置。

2. **生产代码示例**

```java
Message msg = new Message("OrderTopic", "TagA", orderId, body.getBytes());
msg.setDelayTimeLevel(4);      // 第 4 级 = 30 秒
producer.send(msg);
```

1. **Broker 配置检查**
   - `messageDelayLevel` 控制级别定义，修改后需重启 Broker。
   - 监控 `SCHEDULE_TOPIC_XXXX` 队列积压，超过 `delay.alert.threshold.count=10000` 时告警。

### Kafka 延迟队列方案

1. **时间戳方案**
   - 生产者发送消息时携带未来时间戳：`record.timestamp(delayTime)`。
   - 消费者 `poll` 后判断 `record.timestamp() > System.currentTimeMillis()`，未到时间则 `pause` 或重新投递。
   - 配置 `kafka.delay.strategy=timestamp`，扫描间隔 `kafka.delay.scan.interval.seconds=60`。

2. **多延迟 Topic 方案**
   - 按延迟时长建立 Topic：`orders-delay-1m`、`orders-delay-5m`、`orders-delay-30m`。
   - 配置 `kafka.delay.topic.prefix=delay-`，后端定时任务到期后转发到目标 Topic。

3. **生产代码示例**

```java
String delayTopic = "orders-delay-5m";
long deliverTime = System.currentTimeMillis() + 5 * 60 * 1000;
ProducerRecord<String, String> record = new ProducerRecord<>(delayTopic, null, deliverTime, orderId, payload);
producer.send(record);
```

### RabbitMQ TTL+DLX

1. **队列 TTL 方案**
   - 声明队列时指定 `x-message-ttl=60000`，队列内所有消息 60 秒后过期。
   - 过期消息路由到 `x-dead-letter-exchange=dlx.orders`，死信队列绑定业务消费者实现延迟消费。

2. **单消息 TTL 方案**
   - 发送消息时通过 `expiration=60000` 设置单条消息 TTL。
   - 注意：RabbitMQ 只对队列头部消息检查过期，非头部消息即使到期也不会立即投递。

3. **延迟插件方案**
   - 安装 `rabbitmq_delayed_message_exchange` 插件。
   - 声明 `x-delayed-message` 类型 Exchange，并设置 `x-delayed-type: direct`。
   - 消息头 `x-delay` 指定延迟毫秒数，最大不超过 `rabbitmq.delay.max.milliseconds=86400000`。

4. **生产代码示例**

```python
channel.exchange_declare(
    exchange='orders-delayed',
    exchange_type='x-delayed-message',
    arguments={'x-delayed-type': 'direct'}
)
channel.basic_publish(
    exchange='orders-delayed',
    routing_key='orders',
    body=message,
    properties=pika.BasicProperties(
        headers={'x-delay': 300000},
        delivery_mode=2
    )
)
```

### 其他系统简配

1. **NATS JetStream**
   - 使用 `nats.Delay(60*time.Second)` 或消息头 `Nats-Delay` 设置延迟，配置 `nats.delay.max.seconds=86400`。

2. **Pulsar**
   - 支持 `deliverAfter` 和 `deliverAt`，例如 `producer.newMessage().deliverAfter(60, TimeUnit.SECONDS).send()`。

## 3.40.4 配置参数与运维命令

### 模板参数说明

| 参数名 | 含义 | 推荐值 | 适用系统 |
| --- | --- | --- | --- |
| `kafka.delay.enabled` | 是否开启 Kafka 延迟消息 | `true` | Kafka |
| `kafka.delay.strategy` | Kafka 延迟策略 | `timestamp` / `delay-topic` | Kafka |
| `kafka.delay.scan.interval.seconds` | 时间戳方案扫描间隔 | `60` | Kafka |
| `nats.delay.max.seconds` | 单条消息最大延迟 | `86400` | NATS |
| `rabbitmq.delay.max.milliseconds` | 延迟插件最大延迟 | `86400000` | RabbitMQ |
| `delay.strategy` | 全局延迟策略 | `fixed` / `dynamic` / `exponential-backoff` | 通用 |
| `delay.fixed.milliseconds` | 固定延迟时长 | `60000` | 通用 |
| `delay.storage.retention.hours` | 延迟消息保留时长 | `24` | 通用 |
| `delay.alert.threshold.count` | 延迟消息积压告警阈值 | `10000` | 通用 |
| `delay.alert.threshold.accuracy.percent` | 延迟精度告警阈值 | `95` | 通用 |

### 常用运维命令

1. **RocketMQ 检查延迟队列积压**

   ```bash
   mqadmin brokerConsumeStats -b broker-a:10911
   # 关注 SCHEDULE_TOPIC_XXXX 各队列的 diff
   ```

2. **Kafka 查看延迟 Topic 消费进度**

   ```bash
   kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
     --describe --group delay-forwarder
   ```

3. **RabbitMQ 查看插件与队列 TTL**

   ```bash
   rabbitmq-plugins list | grep delayed
   rabbitmqctl list_queues name messages messages_ready messages_unacknowledged
   ```

## 3.40.5 监控告警与最佳实践

### 监控指标

1. **延迟消息堆积量**
   - 指标名 `delay_count`，阈值 `delay.alert.threshold.count=10000`。
   - RocketMQ 通过 `SCHEDULE_TOPIC_XXXX` 队列深度判断。
   - Kafka 通过延迟 Topic 的 `records-lag-max` 判断。

2. **延迟精度与分布**
   - `delay_accuracy`：偏差超过 `delay.alert.threshold.accuracy.percent=95` 的样本占比达 5% 时告警。
   - `delay_duration`：按 P50/P95/P99 分位统计，长延迟（>1小时）消息需单独统计。

### 设计建议

1. **选型建议**
   - 高吞吐固定延迟首选 RocketMQ 内置延迟级别。
   - 需要动态任意延迟且消息量可控时选 RabbitMQ 延迟插件或 Pulsar `deliverAfter`。
   - Kafka 适合已使用 Kafka 生态且能接受应用层实现的场景。

2. **可靠性建议**
   - 延迟消息必须开启持久化：`delay.storage.persistent=true`。
   - 保留时间 `delay.storage.retention.hours` 必须大于最大业务延迟，转发任务记录已处理 offset 避免重启重复投递。

3. **性能建议**
   - 单队列消息数超过 100 万时考虑分片，例如按订单尾号散列到 16 个延迟队列。
   - Kafka 多延迟 Topic 数量建议不超过 20 个，避免元数据膨胀。

## 3.40.6 延迟调度检查清单

### 实施前

- [ ] 明确业务最大延迟：例如订单超时 30 分钟、会员提醒 7 天，确认系统支持的最大延迟。
- [ ] 选择延迟策略：固定延迟、动态延迟或指数退避，并在配置中设置 `delay.strategy`。
- [ ] 确认精度与峰值：秒级选 RocketMQ/RabbitMQ 插件，RocketMQ 单机建议不超 5 万 TPS，RabbitMQ 单队列不超 100 万堆积。
- [ ] 设计持久化策略：设置 `delay.storage.persistent=true` 和合适的 `delay.storage.retention.hours`。

### 实施中

- [ ] RocketMQ 配置 `messageDelayLevel` 或商业版 `setDelayTimeMs`，监控 `SCHEDULE_TOPIC_XXXX` 积压。
- [ ] Kafka 配置 `kafka.delay.strategy=timestamp` 或 `delay-topic`，设置 `kafka.delay.scan.interval.seconds=60`。
- [ ] RabbitMQ/NATS 分别安装延迟插件或配置 `nats.delay.max.seconds=86400`，验证 `rabbitmq.delay.max.milliseconds=86400000` 未超限。
- [ ] 部署转发/扫描 Worker 并配置监控项 `delay_count`、`delay_duration`、`delay_accuracy` 和告警通道 `delay.alert.channels`。

### 实施后

- [ ] 功能验证：发送测试消息，确认实际投递时间与期望时间偏差在 5 秒内。
- [ ] 性能测试：模拟峰值 TPS，观察 `delay.alert.threshold.count=10000` 是否触发。
- [ ] 故障演练与精度巡检：重启 Broker/Worker，验证消息不丢失，并统计 P95/P99 延迟精度确保 `delay.alert.threshold.accuracy.percent=95` 达标。
