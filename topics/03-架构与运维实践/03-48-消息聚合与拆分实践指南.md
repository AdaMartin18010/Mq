## 3.48.1 聚合拆分落地场景

### 适用场景

1. **批量聚合窗口**：日志采集、埋点上报、IoT 遥测等高频小消息场景，通过时间窗口或数量阈值将多条消息合并为一批，降低网络往返和 broker 写入压力。
2. **大消息拆分**：单条消息超过 broker 单条限制（如 Kafka `message.max.bytes` 默认 1 MB、MQTT 默认 256 KB）时，按固定大小或业务边界拆分为分片，消费端再重组。
3. **聚合校验**：在聚合或拆分前后校验批次消息数、字节总量、分片顺序与完整性，防止丢消息或重复重组。

## 3.48.2 批量聚合窗口配置

### Kafka 聚合窗口配置

在 `topics/config-templates/aggregation-config.properties` 中，Kafka Producer 侧聚合由 `batch.size`、`linger.ms`、`buffer.memory` 共同决定。运维调整步骤如下：

1. 修改 Producer 配置：
   - `batch.size=16384`：默认 16 KB，达到该阈值或 `linger.ms` 到期后发送；高吞吐场景可提高到 32768–131072。
   - `linger.ms=10`：默认 0，建议设置为 5–100 ms，让 Producer 等待更多记录入批。
   - `buffer.memory=33554432`：32 MB 发送缓冲区，若出现 `RecordAccumulator` 满导致 send 阻塞，可增大到 64–128 MB。
2. Consumer 侧批量拉取：
   - `max.poll.records=500`：单次 `poll()` 最多返回 500 条，聚合处理后再提交 offset。
   - `max.poll.interval.ms=300000`：批量处理时长不能超过 5 分钟，否则触发 rebalance。
3. Kafka Streams 窗口聚合（如 `session`/`tumbling`）需额外设置 `commit.interval.ms` 与 `cache.max.bytes.buffering`，避免频繁写出中间结果。

示例：通过 `kafka-console-producer.sh` 验证批次行为。

```bash
# 查看当前 topic 的 message.max.bytes（决定单条上限）
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name orders --describe

# 压测观察聚合效果：
# batch.size=32768, linger.ms=20, compression.type=snappy
kafka-producer-perf-test.sh --topic orders --num-records 100000 \
  --record-size 256 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 \
    batch.size=32768 linger.ms=20 compression.type=snappy
```

### NATS 聚合窗口配置

NATS Core 不原生支持服务端聚合，需在发布端或 JetStream 消费端实现批量窗口。参考模板参数：

1. 发布端批量 Flush：
   - `nats.publish.batch.size=100`：累计 100 条消息后调用 `nc.Flush()` 统一刷盘。
   - `nats.publish.flush.interval=10`：每 10 ms 强制 Flush，避免窗口无限等待。
2. 订阅端批量消费：
   - `nats.subscribe.batch.size=100`：缓存 100 条后触发业务回调。
   - `nats.subscribe.batch.timeout=100`：100 ms 内未达数量阈值也触发回调。
3. JetStream 场景下，使用 `PullSubscribe` 配合 `Fetch(100, MaxWait(100ms))` 实现受控批量拉取。

### RabbitMQ 聚合窗口配置

RabbitMQ 可通过 `basic.publish` 客户端缓冲或队列批量 Ack 实现聚合：

1. 发布端批量：
   - `rabbitmq.publish.batch.size=100`：每 100 条消息调用一次 `channel.basic_publish_batch` 或手动 flush TCP 帧。
   - `rabbitmq.publish.batch.timeout=10`：10 ms 超时强制发送。
2. 消费端批量：
   - `rabbitmq.consume.batch.size=100`：收集 100 条消息后批量 Ack。
   - `rabbitmq.consume.batch.timeout=100`：100 ms 超时触发部分 Ack。
3. 开启 Publisher Confirm 时，建议按批次 `wait_for_confirms(timeout=5s)`，避免逐条等待。

下表对比三种系统的聚合窗口关键参数：

| 系统 | 数量阈值参数 | 时间窗口参数 | 单批上限/风险 | 推荐监控指标 |
| --- | --- | --- | --- | --- |
| Kafka Producer | `batch.size`（字节） | `linger.ms` | `buffer.memory` 满则阻塞 | `record-queue-time-avg`、`batch-size-avg` |
| NATS Core | `nats.publish.batch.size` | `nats.publish.flush.interval` | 客户端内存堆积 | 发布延迟、Flush 耗时 |
| RabbitMQ | `rabbitmq.publish.batch.size` | `rabbitmq.publish.batch.timeout` | 未确认消息堆积 | `ready`、`unacked` 队列长度 |

## 3.48.3 大消息拆分配置

### 拆分触发条件

当单条消息大小接近或超过 broker 限制时启用拆分。参考阈值：

- Kafka：`message.max.bytes=1048588`（默认约 1 MB），建议超过 800 KB 即拆分；同时 Producer 需设置 `max.request.size` 与 `compression.type=snappy`。
- MQTT：EMQX 默认 `max_packet_size=1MB`，但实际业务建议超过 256 KB 拆分。
- NATS：JetStream `MaxMsgSize` 默认无限制，但建议超过 1 MB 拆分以避免流文件膨胀。

### 分片元数据规范

每条分片必须携带统一元数据，便于消费端重组。推荐在消息 Header 或 Key 中写入：

- `x-msg-id`：原始消息唯一 ID，如 UUID。
- `x-part-index`：当前分片序号，从 0 开始。
- `x-part-total`：总分片数。
- `x-part-size`：本分片字节数（可选）。

示例：Kafka Producer 拆分大消息并写入 Header。

```java
public List<ProducerRecord<String, String>> splitLargeMessage(
        String topic, String key, String largeMessage, int maxSize) {
    List<ProducerRecord<String, String>> records = new ArrayList<>();
    String msgId = UUID.randomUUID().toString();
    int total = (largeMessage.length() + maxSize - 1) / maxSize;
    int offset = 0;
    for (int i = 0; i < total; i++) {
        int end = Math.min(offset + maxSize, largeMessage.length());
        String chunk = largeMessage.substring(offset, end);
        ProducerRecord<String, String> record = new ProducerRecord<>(topic, key, chunk);
        record.headers().add("x-msg-id", msgId.getBytes(StandardCharsets.UTF_8));
        record.headers().add("x-part-index", String.valueOf(i).getBytes());
        record.headers().add("x-part-total", String.valueOf(total).getBytes());
        records.add(record);
        offset = end;
    }
    return records;
}
```

### 重组与超时控制

消费端收到分片后按 `x-msg-id` 缓存，完整后再投递业务层。参考配置：

- `reassembly.enabled=true`：开启重组。
- `reassembly.timeout.ms=60000`：60 秒未收齐则视为超时，可选择丢弃或写入死信队列。
- `reassembly.max.parts=1000`：单条消息最多 1000 个分片，超过直接拒绝。
- `reassembly.storage=memory`：小批量用内存；高可靠场景改为 `redis` 或 `database`。

## 3.48.4 聚合校验

### 数量与大小校验

聚合发送前必须校验批次是否满足预期：

1. 数量校验：批次消息数应落在 `[1, aggregation.count.threshold]` 区间，例如模板中 `aggregation.count.threshold=100`。
2. 大小校验：批次总字节不超过 `aggregation.size.threshold=16384` 字节，且不超过 Producer `max.request.size`。
3. 压缩后大小校验：若开启 `aggregation.optimization.compression.enabled=true` 与 `compression.type=snappy`，需校验压缩后包体不超过 broker 单条限制。

### 顺序与完整性校验

拆分重组阶段必须保证顺序和完整：

1. 顺序校验：按 `x-part-index` 顺序检查，发现缺片或乱序立即触发 `reassembly.timeout` 处理。
2. 完整性校验：收到分片后核对 `x-part-total`，收齐后计算总长度或 CRC32 与发送端一致。
3. 重复校验：使用 `x-msg-id` + `x-part-index` 去重，避免网络重传导致重复重组。

## 3.48.5 聚合拆分检查清单

### 实施前

- [ ] 明确聚合目标：吞吐量提升比例、可接受延迟上限（如 p99 < 200 ms）。
- [ ] 确认 broker 单条大小限制：Kafka `message.max.bytes`、MQTT `max_packet_size`、NATS JetStream `MaxMsgSize`。
- [ ] 选择聚合策略并写入 `aggregation-config.properties`：`aggregation.strategy=time-window|count-threshold|size-threshold|mixed`。
- [ ] 设定阈值：`aggregation.time.window.ms=1000`、`aggregation.count.threshold=100`、`aggregation.size.threshold=16384`。

### 实施中

- [ ] Producer 启用批处理：`batch.size`、`linger.ms`、`buffer.memory` 已按场景调整。
- [ ] Consumer 批量消费：`max.poll.records`、`max.poll.interval.ms` 与业务处理耗时匹配。
- [ ] 大消息拆分携带标准 Header：`x-msg-id`、`x-part-index`、`x-part-total`。
- [ ] 配置重组参数：`reassembly.timeout.ms=60000`、`reassembly.max.parts=1000`、`reassembly.storage` 按可靠性需求选择。
- [ ] 开启压缩：`aggregation.optimization.compression.enabled=true`、`compression.type=snappy`。

### 实施后

- [ ] 运行 `topics/scripts/aggregation-test.sh kafka batch` 验证聚合行为。
- [ ] 监控 `record-queue-time-avg`、`batch-size-avg`、聚合延迟是否低于 `aggregation.monitor.alert.latency.threshold=1000` ms。
- [ ] 压测大消息拆分：单条 5 MB 拆分为 1 KB 分片，验证重组成功率和时延。
- [ ] 检查死信队列/错误 topic，确认无丢片或超时残留。
- [ ] 定期复核阈值：业务流量变化后重新评估 `batch.size` 与 `linger.ms`。
