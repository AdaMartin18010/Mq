## 3.66.1 定位与前置知识

本文档给出用统一框架在可控环境下复现性能数字的操作路径，与既有文档分工如下：

| 文档 | 承担内容 | 本文衔接点 |

| [03-22](03-22-性能测试指南.md) | 通用性能测试方法论与单系统工具链 | 本文聚焦 OpenMessaging Benchmark 跨系统统一框架 |
| [01-63](../01-基础概念与对比分析/01-63-Exactly-once语义全论证.md) | 交付语义与 exactly-once 边界 | 测试断言必须区分协议语义与端到端语义 |
| [TEST-09](../../Testing/00-规范与计划/TEST-09-测试执行计划与环境矩阵.md) | hermes 环境矩阵与执行频率 | 基准用例在 E2 环境每周执行，E3 保留发布前关键集 |

【论证】跨系统性能对比的核心难点不在"跑分"，而在**控制变量**：不同系统的持久化保证、复制语义、ACK 模型、客户端批处理策略差异巨大，直接拿厂商各自发布的峰值数字对比会落入"比较苹果与橘子"的陷阱。OpenMessaging Benchmark（OMB）通过统一 workload、统一消息格式、统一统计口径，把对比收敛到"同一负载模型下的吞吐-延迟曲线"，这是工程上可接受的折中。

## 3.66.2 OpenMessaging Benchmark 构建与驱动支持现状

OMB 官方仓库为 [openmessaging/benchmark](https://github.com/openmessaging/benchmark)，截至 2026-11 的构建基线如下：

- JDK 17
- Maven 3.8.6+
- 默认打包产物：`benchmark-distribution/target/openmessaging-benchmark-*.tar.gz`

### 源码构建

```bash
# 1. 克隆并切换到待测 commit（示例，实际应使用固定 tag 或 commit hash）
git clone https://github.com/openmessaging/benchmark.git
cd benchmark
git checkout <commit-hash>

# 2. 构建分发包（跳过测试以节省时间，但首次建议完整验证）
mvn clean package -DskipTests

# 3. 解压分发包
tar -xzf benchmark-distribution/target/openmessaging-benchmark-*.tar.gz -C /opt/omb
export OMB_HOME=/opt/omb/openmessaging-benchmark-0.0.1-SNAPSHOT
```

## 3.66.3 workload YAML 逐字段注释

workload 文件定义负载模型，是控制变量的关键。以下是一份 1KB 消息、可持续探测吞吐-延迟曲线的典型配置：

```yaml
name: 1KB-1topic-6partition-rate-sweep
topics: 1                                     # 主题数
topicsPerWorkload: 1
partitionsPerTopic: 6                         # 应与目标生产拓扑一致
keyDistributor: NO_KEY                        # NO_KEY/KEY_ROUND_ROBIN/RANDOM
messageSize: 1024                             # 消息体字节数；不含协议头，统计口径需说明
payloadFile: payload/payload-1kb.data         # 预生成负载文件，避免运行时构造开销
subscriptionsPerTopic: 1                      # 每个主题的消费组数
consumerPerSubscription: 3                    # 每个消费组的消费者实例数
producersPerTopic: 3                          # 每个主题的生产者实例数
producerRate: 100000                          # 目标生产速率（msg/s），-1 表示不限速探测极限
consumerBacklogSizeGB: 0                      # 0=不预堆积；>0 可测积压恢复
testDurationMinutes: 10                       # 正式采样时长，不含预热
warmupDurationMinutes: 2                      # 预热时长，用于 JVM/JIT/缓存稳定
rateFrequency: 1000                           # 速率调整粒度（ms）
```

字段设计含义：

| 字段 | 控制变量 | 常见误用 |
| ------ | ---------- | ---------- |
| `partitionsPerTopic` | 并行度与分区/队列数 | 与生产不一致导致吞吐天花板失真 |
| `producerRate` | 负载梯度；-1 用于极限探测 | 未说明目标值则无法复现 |
| `messageSize` | 单条消息体大小 | 未含协议头时需在报告中说明 |
| `warmupDurationMinutes` | 系统进入稳态的预热时间 | 过短会拉高 P99 |
| `testDurationMinutes` | 有效统计窗口 | 过短使置信区间过宽 |

## 3.66.4 五系统驱动部署差异

OMB 采用"驱动 YAML + worker 集群"模式，不同系统的驱动配置差异主要体现在连接地址、认证、topic/queue/stream 创建参数上。

| 系统 | 驱动关键文件 | 部署注意点 |
| ------ | -------------- | ------------ |
| **Kafka** | `driver-kafka/kafka.yaml` | 需配置 `bootstrap.servers`、`topicConfig`（replication.factor/min.insync.replicas）、生产者 `acks`；KRaft 模式无需 ZooKeeper |
| **RabbitMQ** | `driver-rabbitmq/rabbitmq.yaml` | 需配置 AMQP URI、exchange/queue 声明参数、`messagePersistence` 控制持久化；镜像队列模式需额外 policy |
| **NATS JetStream** | `driver-nats/nats.yaml` | 配置 `serverUrls`、stream `subjects`、retention policy（limits/interest/workqueue）、`replicas` |
| **Pulsar** | `driver-pulsar/pulsar.yaml` | 配置 `serviceUrl`/`webServiceUrl`、tenant/namespace、topic 持久化级别、消息去重开关 |
| **RocketMQ** | `driver-rocketmq/rocketmq.yaml` | 配置 `namesrvAddr`、`producerGroup`/`consumerGroup`、topic 队列数、acl 认证 |

以 Kafka 驱动配置片段为例：

```yaml
name: Kafka
driverClass: io.openmessaging.benchmark.driver.kafka.KafkaBenchmarkDriver

# 集群连接与客户端配置
clusterName: kafka-omb-test
bootstrap.servers: kafka-1:9092,kafka-2:9092,kafka-3:9092

# Topic 创建默认参数
topicConfig: |
  min.insync.replicas=2
  replication.factor=3

# 生产者配置（影响吞吐-延迟 trade-off）
producerConfig: |
  acks=all
  batch.size=32768
  linger.ms=10
  compression.type=snappy

# 消费者配置
consumerConfig: |
  auto.offset.reset=earliest
  enable.auto.commit=false
```

【论证】驱动 YAML 中的 `acks=all` 与 `replication.factor=3` 直接决定持久化保证级别；若与 01-18 的【估算】数字做回灌对比，必须保证驱动参数完全一致，否则数字不可比。

## 3.66.5 测试方法论

### 预热与时长

- **预热阶段**：至少 2 分钟，用于 JVM JIT、OS 页缓存、Broker 缓存、连接池稳定。
- **正式采样阶段**：至少 10 分钟；探测吞吐-延迟曲线时每个梯度点至少 3-5 分钟。

### 负载梯度设计

推荐三段式梯度：基线（峰值 20%，验证正确性）、额定（60%-80%，日常曲线）、极限（10% 步进，直到延迟突破 SLA 或错误率 >0.1%）。每个梯度点修改 `producerRate` 并保留参数快照。

### 避免 Coordinated Omission

Coordinated Omission（协同遗漏）指压测工具在等待响应时"遗漏"了本应运送的负载，导致测出的延迟被人为压低。OMB 内部已记录请求发送时间戳，但仍需在测试设计中注意：

- 使用 `producerRate` 固定目标速率，而非让生产者"能发多快发多快"；
- 统计端到端延迟时采用**发送时间戳到消费时间戳**，而不是 worker 内部排队时间；
- 若使用 Kafka `kafka-producer-perf-test` 等独立工具，需额外校验是否报告了"记录未在时限内发送"的计数；
- 对 P99/P99.9 等尾部延迟，要求每个梯度点样本数 ≥ 10^5，避免小样本噪声。

### 结果置信区间

对同一 workload 至少执行 3 次独立运行（每次包含完整预热），记录每次的吞吐与 P99 延迟，然后计算：

```text
平均值  μ = (x1 + x2 + x3) / 3
标准差  σ = sqrt( Σ(xi - μ)^2 / (n-1) )
95% CI = μ ± t(0.975, n-1) * σ / sqrt(n)   # n=3 时 t≈4.303
```

报告格式示例：吞吐 850,000 ± 45,000 msg/s（95% CI，n=3）。若 95% CI 宽度超过均值的 10%，应增加运行次数或检查环境抖动。

## 3.66.7 结果回灌与引用纪律

当实测数字需要替换 01-18 等文档中的【估算】标注时，必须遵守 AGENTS.md §4 的引用纪律：

1. **来源四元组**：每次回灌必须注明 `commit/workload/环境/日期`。示例：

   ```text
   来源：openmessaging/benchmark@a1b2c3d，workload/1KB-1topic-6partition.yaml，E2-omb-2026-11-18，2026-11-18
   ```

2. **置信标注转换**：替换后的数字不再标【估算】，改为【论证：OMB 实测，见 Testing/fixtures/benchmark-result-*.md】；若跨多轮运行且计算了 CI，可进一步标注均值与置信区间。
3. **不可泛化声明**：同一组数字不得在缺少说明的情况下用于不同消息大小、不同副本数、不同 ACK 级别。
4. **联动修正**：回灌 01-18 后，需用 `./topics/scripts/doc-self-check.sh full` 检查是否有其他文档引用了被修改的数字，确保口径一致。
5. **L3 审批**：回灌文档正文属于 hermes L3 内容修复，必须走人工审批并登记 TEST-05 双向修正登记表。

## 3.66.8 hermes 可执行性：命令清单与产物路径

本用例在 TEST-09 环境矩阵中建议归属 **E2 Docker** 或 **E3 K8s**，每周执行一次；E0 仅做配置语法与 TSV 注册表校验。

### hermes 任务包片段

```yaml
plan:
  id: weekly-omb-2026-11-18
  trigger: weekly
  runner: hermes
environments:
  - name: E0
    engine: local-git-bash
    cases:
      - id: TC-BENCH-01
        script: ./topics/scripts/validate-config.sh
        args: [Testing/fixtures/benchmark-result-template.md]
  - name: E2
    engine: docker
    precheck: docker compose version
    cases:
      - id: TC-BENCH-02
        script: ./Testing/scripts/omb-run.sh
        args: [driver-kafka/kafka.yaml, workloads/1KB-1topic-6partition.yaml, kafka]
        artifacts: [results/weekly-omb-2026-11-18/E2-TC-BENCH-02.json]
artifacts:
  base_dir: results/weekly-omb-2026-11-18
  formats: [json, log, md]
```

### 命令清单

```bash
# E0：静态校验
bash -n ./Testing/scripts/omb-run.sh
python -c "import yaml; yaml.safe_load(open('Testing/fixtures/benchmark-result-template.md'))"  # 若模板含 YAML 段
./topics/scripts/doc-self-check.sh quick

# E2：单系统单次运行示例
./Testing/scripts/omb-run.sh \
  driver-kafka/kafka.yaml \
  workloads/1KB-1topic-6partition.yaml \
  kafka

# E2：六系统批量运行（按环境资源串行或隔离并行）
for sys in kafka pulsar rocketmq rabbitmq nats redis; do
  ./Testing/scripts/omb-run.sh \
    "driver-${sys}/${sys}.yaml" \
    workloads/1KB-1topic-6partition.yaml \
    "$sys"
done
```

### 产物路径

```text

└── weekly-omb-2026-11-18/
    ├── E0-TC-BENCH-01.json
    ├── E2-TC-BENCH-02.json
    ├── E2-TC-BENCH-02.log
```
