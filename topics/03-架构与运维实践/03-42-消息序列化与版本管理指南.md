## 3.42.1 序列化格式落地选型

### 格式对比与落地建议

选型时优先参考业务对可读性、体积、Schema 演进的诉求，而非性能单项指标。落地阶段需要把 `serialization.format` 写进统一配置模板，并明确 `serialization.compression.enabled` 与 `serialization.compression.type` 的默认值。

| 维度 | JSON | Avro | Protobuf | 说明 |
| ------ | ------ | ------ | ---------- | ------ |
| 可读性 | 高 | 低（二进制） | 低（二进制） | JSON 适合排查与调试；Avro/Protobuf 需借助 Schema 反查字段 |
| 序列化体积 | 大 | 小 | 最小 | Avro 自带 Schema 演进，Protobuf tag 更紧凑 |
| 性能 | 中 | 高 | 最高 | Protobuf 解析速度通常优于 Avro，但差距在百纳秒级 |
| Schema 演进 | 弱 | 强 | 强 | Avro 依赖 Schema Registry；Protobuf 靠 field number 兼容 |
| 配置复杂度 | 低 | 中 | 中 | JSON 无需额外组件，Avro/Protobuf 需要 `.proto`/`.avsc` 与注册流程 |
| 推荐场景 | 开发调试、日志、小数据量 | Kafka 大数据管道、Schema 频繁迭代 | 微服务 RPC、跨语言高性能传输 | 结合 `serialization.compression.type=gzip/snappy/lz4` 可进一步降低网络带宽 |

1. **JSON 落地要点**
   - 在 `serialization-config.properties` 中设置 `serialization.format=json`，并关闭压缩或按需启用 `serialization.compression.enabled=true`。
   - Kafka 生产者/消费者固定使用 `org.apache.kafka.common.serialization.StringSerializer` 与 `StringDeserializer`。
   - 当消息体大于 1 KB 且 QPS 超过 1000 时，建议切换为 `snappy` 或 `lz4` 压缩；`gzip` 压缩率高但 CPU 开销明显。

2. **Avro 落地要点**
   - 必须启用 Schema Registry，配置 `schema.registry.enabled=true` 与 `schema.registry.url=http://localhost:8081`。
   - Kafka 生产者将 `value.serializer` 改为 `io.confluent.kafka.serializers.KafkaAvroSerializer`。
   - _consumer_ 端配套使用 `KafkaAvroDeserializer`，并设置 `specific.avro.reader=true` 以反序列化为具体对象。
   - 每条消息只需写入 Schema ID（4 字节），因此 Avro 序列化后体积远小于 JSON。

3. **Protobuf 落地要点**
   - 在 `serialization-config.properties` 中声明 `serialization.format=protobuf`，并在构建阶段通过 `protoc` 生成目标语言代码。
   - NATS 可设置 `nats.serialization.format=protobuf`，RabbitMQ 目前模板中仅支持 `json/pickle/msgpack`，Protobuf 需在应用层自行实现 `bytes` 消息体。
   - Protobuf 字段新增必须保留旧 field number，删除字段建议标记 `reserved`，避免未来编号冲突。

4. **性能优化参数**
   - 启用序列化缓存：`serialization.cache.enabled=true`，`serialization.cache.size=10000`。
   - 对象池复用：`serialization.pool.enabled=true`，`serialization.pool.size=10`。
   - 监控指标：`serialization.monitor.enabled=true`，采集 `serialization_count`、`serialization_duration`、`serialization_size`。

```properties
# 示例：Avro + Schema Registry 生产配置（摘自 serialization-config.properties）
kafka.key.serializer=org.apache.kafka.common.serialization.StringSerializer
kafka.value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer
schema.registry.enabled=true
schema.registry.url=http://schema-registry:8081
schema.registry.compatibility.level=backward
serialization.cache.enabled=true
serialization.cache.size=10000
serialization.monitor.enabled=true
serialization.monitor.metrics=serialization_count,serialization_duration,serialization_size
```

## 3.42.2 Schema Registry 部署与配置

### Confluent Schema Registry 部署

1. **部署方式选择**
   - 单机开发环境可直接使用 Confluent 社区版容器，监听 `8081` 端口。
   - 生产环境至少部署 3 节点，并配置 `kafkastore.connection.url`（或 `kafkastore.bootstrap.servers`）指向 Kafka 集群，避免单点故障。
   - Schema Registry 默认将 Schema 元数据写入 Kafka 主题 `_schemas`，该主题需保证高可用，建议 `replication.factor=3`、`min.insync.replicas=2`。

2. **关键配置项**
   - `schema.registry.url`：客户端访问地址，模板中默认 `http://localhost:8081`。
   - `schema.registry.compatibility.level`：全局兼容性级别，可选 `backward`、`forward`、`full`、`none`；生产推荐先设为 `backward`。
   - `kafkastore.security.protocol`：若 Kafka 开启 SASL/SSL，Schema Registry 侧必须同步配置安全协议与证书。

3. **健康检查命令**
   - 检查服务是否存活：`curl -s http://localhost:8081/` 应返回 Schema Registry 版本信息。
   - 列出全部 Subject：`curl -s http://localhost:8081/subjects | jq -r '.[]'`。
   - 查看某个 Subject 的所有版本：`curl -s http://localhost:8081/subjects/orders-value/versions`。

### Schema 注册与版本管理

1. **注册 Schema**
   - 以 `POST` 请求向 `/subjects/{subject}/versions` 提交 Avro Schema JSON。
   - 注册成功后返回 `id`，生产者在序列化时会把该 ID 写入消息头。
   - 同一 Schema 内容多次注册不会新增版本；若内容变化但兼容，则版本号递增。

2. **版本号规则**
   - Schema Registry 内部版本为递增整数（1、2、3…），与业务语义化版本（Semantic Version）分开管理。
   - 业务侧建议维护 `version.format=semantic`，在消息头中写入 `message-version=1.2.0`。

3. **Schema 元数据维护**
   - 每个 Subject 的 `latest` 版本用于生产者写入校验，`{subject}/versions/{id}` 用于历史追溯。
   - 定期导出 Schema：`curl -s http://localhost:8081/subjects/orders-value/versions/latest/schema` 保存到版本库。

```bash
# 示例：注册 Avro Schema 并查看版本（基于 schema-check.sh 中的检查命令）
curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"schema":"{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"orderId\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"double\"}]}"}' \
  http://localhost:8081/subjects/orders-value/versions

# 查看已注册 Schema 列表
SUBJECTS=$(curl -s http://localhost:8081/subjects | jq -r '.[]' | wc -l)
echo "当前 Subjects 数量: $SUBJECTS"
```

## 3.42.3 版本管理策略落地

### 消息版本头

1. **版本头字段**
   - 在 `serialization-config.properties` 中定义 `version.header.name=message-version`。
   - 版本格式由 `version.format` 控制，可选 `semantic`（推荐）、`numeric`、`custom`。
   - 每条消息必须携带版本头，便于消费者按版本路由或降级处理。

2. **版本号写入规范**
   - 语义化版本：主版本.次版本.修订版本，例如 `1.2.0`。
   - 主版本变更代表不兼容协议变化；次版本变更代表向后兼容的新字段；修订版本仅修复描述或默认值。
   - Kafka 中可通过 `RecordHeader` 写入：`record.headers().add("message-version", "1.2.0".getBytes())`。

3. **版本与 Schema ID 的关系**
   - Avro 场景下，Schema ID 由 Schema Registry 分配；业务版本号仍由应用维护。
   - 建议在 CI 流水线中建立映射表：业务版本 `1.2.0` 对应 Schema ID `7`。

### 版本路由与降级

1. **版本路由**
   - 消费者在反序列化前读取 `message-version`，根据版本号分发到不同的解析器。
   - 若使用 Avro，可结合 `KafkaAvroDeserializer` 自动匹配 Schema ID；若使用 JSON/Protobuf，需在应用层实现路由表。

2. **降级策略**
   - 当消费者遇到未知主版本时，默认丢弃并告警，或写入死信队列（DLQ）。
   - 配置 `version.management.enabled=true` 后，应在应用内实现 `VersionRouter`，显式处理 `>=2.0.0` 与 `<2.0.0` 的消息。

3. **灰度发布流程**
   - 先注册新 Schema 并验证兼容性；再部署新版本生产者到 5% 节点；观察 `serialization_count` 与 `serialization_duration` 无异常后全量推广。
   - 回滚时优先回滚生产者版本，保留 Schema Registry 中已注册 Schema 以便数据回放。

## 3.42.4 兼容性策略配置

### 兼容性规则与检查

1. **兼容性级别设置**
   - `schema.registry.compatibility.level=backward`：新 Schema 可被旧 Schema 读取，即新增字段必须带默认值（推荐）。
   - `forward`：旧 Schema 可被新 Schema 读取，即新增字段必须可选且无默认值约束。
   - `full`：同时满足 backward 与 forward，新增字段必须带默认值。
   - `none`：不校验兼容性，仅在受控迁移窗口短期使用。

2. **常见兼容变更**
   - 向后兼容（Backward）：新增可选字段并设置默认值；删除未使用字段。
   - 向前兼容（Forward）：新增可选字段；不删除旧字段。
   - 不兼容变更：字段类型从 `int` 改为 `string`；同一 field number 复用不同含义；删除字段后未标记 `reserved`。

3. **兼容性检查命令**
   - 通过 Schema Registry 自动拦截：注册不兼容 Schema 时返回 HTTP 409。
   - 本地预检可使用 `mvn schema-registry:register` 或 Confluent CLI 的 `schema-registry schema --validate`。
   - 在 CI 中调用 `topics/scripts/schema-check.sh`，检查 Subjects 数量与兼容性配置是否满足基线。

```bash
# 示例：检查 Schema Registry 状态与兼容性配置
bash topics/scripts/schema-check.sh
# 输出示例：
# ✅ Schema Registry运行中
# Subjects数量: 12
```

1. **兼容性故障处理**
   - 若注册失败，先读取 `/subjects/{subject}/versions/latest` 对比差异。
   - 临时绕过：将 `schema.registry.compatibility.level` 改为 `none` 并重新注册，但需在 24 小时内恢复为 `backward`。
   - 对于已经落盘的历史消息，保持旧 Schema 可读，避免消费端无法解码。

## 3.42.5 序列化检查清单

### 实施前

- [ ] 明确 `serialization.format` 取值（`json`/`avro`/`protobuf`/`msgpack`），并记录选型理由。
- [ ] 完成 Schema 设计：Avro 输出 `.avsc`、Protobuf 输出 `.proto`，并经过评审。
- [ ] 确定 `schema.registry.compatibility.level`（生产推荐 `backward`，测试环境可临时 `none`）。
- [ ] 定义 `version.header.name` 与 `version.format`，建立业务版本号与 Schema ID 映射表。
- [ ] 评估消息体大小与 QPS，确认是否需要启用 `serialization.compression.enabled=true` 及压缩算法。

### 实施中

- [ ] 配置生产者 `key.serializer` 与 `value.serializer`，Avro 场景接入 `KafkaAvroSerializer`。
- [ ] 配置消费者反序列化器，Avro 设置 `specific.avro.reader=true` 与 `schema.registry.url`。
- [ ] 部署 Schema Registry，确认监听端口 `8081`，`_schemas` 主题 `replication.factor=3`。
- [ ] 注册初始 Schema，记录返回的 Schema ID，并在 CI 中加入兼容性校验步骤。
- [ ] 开启序列化监控：`serialization.monitor.enabled=true`，采集 `serialization_count`、`serialization_duration`、`serialization_size`。
- [ ] 实现版本路由逻辑，处理未知 `message-version` 的降级或 DLQ 分支。

### 实施后

- [ ] 执行性能测试：单分区吞吐、平均 `serialization_duration`、序列化后字节大小。
- [ ] 验证兼容性：分别用新旧 Schema 消费同一 Topic 数据，确认无解析失败。
- [ ] 检查 `serialization.cache.size=10000` 命中率，低于 80% 时调大缓存或排查消息类型过多。
- [ ] 运行 `topics/scripts/schema-check.sh`，确认 Subjects 数量与兼容性配置符合预期。
- [ ] 建立 Schema 定期审计机制，至少每月导出一次 Schema 并归档到版本库。
- [ ] 持续优化：根据监控数据调整压缩算法、缓存大小与对象池 `serialization.pool.size`。
