## 3.63.1 需求与前置条件

- 环境：K8s（KEDA/HPA 方案）或非 K8s（脚本方案，见 02-49 选型）
- 组件：Prometheus + Alertmanager + Grafana；exporter 与 broker 大版本匹配【论证】
- 模板：`config-templates/prometheus-alert-rules.yml`、`config-templates/keda-scaledobject-kafka.yaml`、`config-templates/alertmanager.yml`、`grafana-dashboard-*.json`
- 工具：`topics/scripts/alert-quality-check.sh`（告警质量周检）

## 3.63.2 监测落地步骤

1. **接通采集**（按系统选一）：

```bash
# NATS：server 自带，开监控端口
nats-server -m 8222 -js
# RabbitMQ：启用 prometheus 插件
rabbitmq-plugins enable rabbitmq_prometheus
# Kafka：部署 jmx-exporter 或 kafka-exporter（社区）
# Redis/MQTT：部署 redis-exporter / broker 自带指标端点
```

1. **配 Prometheus 抓取**（prometheus.yml 增加 job；模板见 config-templates）。
2. **导仪表板**：`grafana-dashboard-kafka/nats/rabbitmq.json` 导入 Grafana 并核对数据源变量。
3. **验证**：每个黄金信号（流量/延迟/错误/饱和度）至少 1 个面板有数据——缺信号的面板就是采集缺口。

**Prometheus 抓取配置样例**（接入 config-templates 告警规则）：

```yaml
scrape_configs:
  - job_name: kafka
    scrape_interval: 30s
    static_configs:
      - targets: ['kafka-jmx-exporter:9404']
  - job_name: rabbitmq
    metrics_path: /metrics
    static_configs:
      - targets: ['rabbitmq:15692']
  - job_name: nats
    static_configs:
      - targets: ['nats:8222']
rule_files:
  - /etc/prometheus/rules/*.yml   # 挂载 prometheus-alert-rules.yml
```

## 3.63.3 告警治理步骤

1. 从 `prometheus-alert-rules.yml` 模板导入按系统规则集（P0-P3 分级预置）。
2. Alertmanager 路由：severity 标签路由到不同接收器（P0→电话，P1→IM，P2→工单）；配置抑制与静默纪律（01-33.3 清单）。
3. 每周质量检查：

```bash
./topics/scripts/alert-quality-check.sh --week
# 输出：告警总数/重复率/无 runbook 告警清单/静默超期清单
```

1. 阈值调参纪律：每次阈值变更记录（旧值/新值/理由），季度回看误报率趋势【估算】。

**规则集导入前的静态校验**：

```bash
promtool check rules topics/config-templates/prometheus-alert-rules.yml
amtool check-config topics/config-templates/alertmanager.yml   # 路由语法校验
amtool config routes test --config.file=alertmanager.yml severity=p0   # 路由模拟
```

**抑制配置样例**（父级故障抑制子级轰炸，alertmanager.yml 片段）：

```yaml
inhibit_rules:
  - source_match: { severity: p0 }
    target_match: { severity: p2 }
    equal: [system, instance]   # broker 宕机（p0）抑制同机 topic 级（p2）告警
```

## 3.63.4 自动伸缩落地步骤

1. **消费者伸缩（KEDA）**：

```bash
# 前置：安装 KEDA（以 keda.sh 官方发布页为准）
kubectl apply --server-side -f https://github.com/kedacore/keda/releases/latest/download/keda.yaml
kubectl apply -f topics/config-templates/keda-scaledobject-kafka.yaml
# 验证：kafka 消费端观察副本数随 lag 变化；KEDA operator 日志无 scaler 错误
kubectl get scaledobject orders-consumer -o yaml | grep -A5 status
```

1. **标定参数**：lagThreshold=可容忍积压时长×消费速率；cooldownPeriod > 一次 rebalance 时长【估算】。
2. **压测验证**：按 TEST-07 TC-OBS-08 阶梯加压，记录扩容时延与正确性。
3. **缩容护栏**：minReplicaCount ≥ 2；非工作时间锁定缩容（可选定时 patch）。

## 3.63.5 自愈 Runbook

按自治级别逐步放开的操作顺序【论证】：

| 顺序 | 动作 | 操作命令（示例） | 前置护栏 |
| ------ | ------ | ------------------ | ---------- |
| 1 | 进程拉起 | systemd `Restart=always` / k8s restartPolicy | 幂等启动 |
| 2 | 磁盘清理 | `./topics/scripts/cleanup-logs.sh --keep 3d` | 白名单路径+保留期 |
| 3 | leader 平衡 | `kafka-leader-election.sh --election-type preferred` | 低峰执行 |
| 4 | consumer 卡死重启 | k8s liveness（stuck N 分钟→restart） | 消费幂等（02-25） |
| 5 | broker 替换 | k8s 节点自动重建 + 副本重分配 | RF≥3、容量冗余 ≥1 节点 |

每条 runbook 必须含：检测信号 → 处置命令 → 验证命令 → 失败升级路径。L3 动作放开前须通过 TEST-07 TC-OBS-09 演练。

**非 K8s 环境的伸缩脚本方案**（无 KEDA 时的最小实现思路）：

```bash
# lag 巡检+扩容脚本核心逻辑（伪代码，接 CI 定时执行）
LAG=$(kafka-consumer-groups.sh --describe --group orders --bootstrap-server <b> | awk 'NR>1{s+=$6}END{print s}')
REPLICAS=$(current_replicas orders-consumer)
[ "$LAG" -gt 10000 ] && [ "$REPLICAS" -lt 30 ] && scale orders-consumer $((REPLICAS+2)) && log "scale-up lag=$LAG"
# 缩容分支：lag==0 且低利用率持续 900s，每次 -1，间隔 ≥300s
```

**自愈审计日志格式**（每条自动动作的留痕要求）：

```json
{"ts":"2026-11-17T10:00:00Z","action":"consumer-restart","target":"orders-consumer-7",
 "trigger":"liveness-stuck-5m","signal":{"poll_idle_sec":312},"result":"restarted",
 "verify":"lag-resume-normal","operator":"autosystem","ticket":null}
```

**GAME DAY 演练流程**（季度）：选定场景（如 broker 宕机）→ 演练窗口通告 → 注入故障（TEST-04 用例）→ 观察自愈处置与留痕 → 复盘（检测时延/处置正确性/误报）→ 更新 runbook 与阈值。

## 3.63.6 验证方法

- 监测：四大信号面板全有数据（步骤 2.4）；`curl localhost:9090/api/v1/targets | grep -c up` 全 up。
- 告警：触发一次测试告警（`amtool` 或手动 fire）验证路由可达接收器：

```bash
amtool alert add alertname=TestAlert severity=p1 system=test \
  --alertmanager.url=http://localhost:9093
```

- 伸缩：TC-OBS-08 用例通过（扩缩容时延与正确性）。
- 自愈：TC-OBS-09 用例通过（注入故障→自动处置→服务恢复→审计留痕）；审计日志查询：`grep '"operator":"autosystem"' /var/log/autosystem/*.log | tail`。

## 3.63.7 检查清单

- [ ] 六系统核心指标至少覆盖 01-33.2 矩阵的全部行（缺行=采集缺口）
- [ ] 每条告警有 runbook 链接；周检重复率与静默超期清零
- [ ] KEDA/HPA 的 lag 阈值与 cooldown 有标定记录
- [ ] 自愈动作 1-5 均有审计日志可查（TEST-07 验证记录归档）
- [ ] L3 自治动作清单经评审且演练通过后才启用
- [ ] 数据面/quorum/脑裂三类场景确认无自动处置规则
- [ ] GAME DAY 演练记录（上季度）已归档并产出改进项
- [ ] alert-quality-check.sh 周检纳入 CI 定时任务
- [ ] 告警接收器（P0 电话通道）每季度实测一次可达性

**指标异常速查（面板异常 → 首要怀疑）**：

| 面板现象 | 首要怀疑方向 |
| ---------- | -------------- |
| 全部指标缺失 | exporter/采集链路（先查 target up） |
| 流量在、延迟飙升 | 饱和度/资源（磁盘 IO、GC） |
| lag 涨、消费速率 0 | consumer 全断或卡死（自愈第 4 步） |
| 单分区延迟突出 | 热点 key/分区倾斜 |
| 错误率尖峰+连接数波动 | 客户端重连风暴（查 auth/网络） |
