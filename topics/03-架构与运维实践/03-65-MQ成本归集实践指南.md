## 3.65.1 从 TCO 到单位成本

03-02 的 TCO 回答"这套 MQ 一年花多少钱"【论证】；成本归集回答"**这笔花费是哪个团队/哪条业务线产生的，每百万条消息值多少钱**"。没有归集的成本优化是无的放矢——砍掉的可能是别人的命根子，也可能是闲置僵尸【论证】。

## 3.65.2 成本归集模型

```text
总成本 = 基础设施（节点/磁盘/网络） + 平台工程（人力摊销） + 许可证/商业支持
分摊维度（三级标签体系）：
  topic/队列  →  归属团队（label/命名前缀/元数据注册）
  消费组      →  归属应用
  租户/命名空间（Pulsar vhost） → 归属业务线
```

标签落地方式【论证】：topic 命名内嵌团队前缀（`orders.` / `pay.`）+ 元数据注册表（血缘目录的附属表，02-52）双轨；消费组按应用名规范（已有 `orders-processor` 式命名即隐含归属）。

## 3.65.3 采集与分摊操作

1. **容量侧采集**（月度脚本化）：

```bash
# Kafka：每 topic 占用（分段大小）+ 流量
kafka-log-dirs.sh --describe --bootstrap-server <b> --topic-list orders.* | grep -E 'Size|topic'
# Pulsar：namespace 级存储与吞吐统计
pulsar-admin namespaces stats my-tenant/orders
# 通用：Prometheus 指标（bytes_in_total × 保留时长 → 磁盘占用推导）
```

1. **成本单价表**（与财务对齐）：节点时价 × 节点分摊 + 磁盘 GB-月价 × 占用 + 流量单价 × 跨区/外网流量【估算口径，按云账单校准】。
2. **分摊计算**：每 topic 月成本 = 磁盘占用成本 + 流量成本 + 平台费按用量权重分摊——输出 chargeback 报表（不用真扣钱，先 showback 公示）【论证】。

## 3.65.4 单位经济指标与基线

| 指标 | 定义 | 用途 |
| ------ | ------ | ------ |
| 元/百万消息 | topic 月成本 ÷ 月消息量（百万） | 跨团队/跨系统横向对比 |
| GB-成本/月 | 存储月成本 ÷ 占用 GB | 保留策略谈判依据（缩短保留=降本） |
| 副本系数成本 | 成本 × (RF-1) ÷ RF | 副本策略的成本可视化 |
| 闲置率 | 无消费者 topic 成本 ÷ 总成本 | 治理靶子（接 02-52 L1 血缘） |

基线用法【论证】：S3 解耦系统（01-29）的单位成本应显著低于本地盘系统——用本指标实证"分层存储降本"主张；偏差 >3 倍时核查（冷热不分/小文件过多等常见因）【估算】。

## 3.65.5 闲置与优化治理

- 闲置识别：连续 30 天无消费且无生产的 topic → 通知 owner → 7 天无响应降级归档/删除（03-34 治理衔接）【估算参数】
- 保留期治理：高 GB-成本 topic 清单 + 保留期缩短建议（业务确认后执行，03-44 备份策略联动）
- 副本治理：非关键 topic RF 3→2 的成本-可用性权衡表（01-19 选型矩阵的成本列实证）
- 月度产出：成本归集报告（top10 成本 topic + 闲置清单 + 优化建议）并入批次报告

## 3.65.6 检查清单

- [ ] 成本标签体系（topic→团队）覆盖率 100%（未标 topic 禁建）
- [ ] 单位成本指标（元/百万消息）已产出并公示 ≥1 个季度
- [ ] 闲置 topic 治理流程（30 天规则）已运行至少一轮
- [ ] S3 解耦/分层存储的成本实证数据已回填 01-29 论证
- [ ] 成本报表与财务口径对账误差 < 15%【估算】

## 3.65.7 数字算例与模板

**分摊算例【估算数字，演示口径】**：

```text
某 Kafka 集群月成本 12 万元（3 节点 4.5 万 + 磁盘 20TB×0.5 元/GB-月=1 万 + 跨区流量 0.5 万 + 平台人力摊销 6 万）
月消息量 300 亿条 → 单位成本 = 120,000 ÷ 300,000(百万条) = 0.4 元/百万条
orders topic 占磁盘 8TB/20TB、流量 40% → 分摊 = 磁盘 0.4万 + 流量 0.2万 + 平台 6万×40% = 2.8 万/月
```

**showback 月报模板（简）**：

```text
# MQ 成本月报（YYYY-MM）
总成本: ¥X；单位成本: ¥Y/百万消息（环比 ±Z%）
TOP5 成本 topic: <名/团队/金额/环比>
闲置候选（30 天无消费）: <名/占用/owner/处置期限>
优化建议: <保留期缩短/副本调整/冷热分层各 N 条>
```

**闲置通知流程（脚本化）**：

```bash
# 1) 生成闲置候选：对比血缘 active_30d 标记（02-52 接口）
python3 cost_idle_scan.py --lineage-dir lineage/ --out idle_candidates.csv
# 2) 通知 owner（7 天期限）→ 无响应进入归档/删除流程（03-34）
# 3) 处置结果回写血缘库（topic 状态=archived）
```

基线沉淀【论证】：连续 6 个月的单位成本序列纳入 03-17 基准模板附录，作为容量规划（03-20/03-57）的成本输入。

### 治理节奏（月度/季度）

| 节奏 | 动作 | 产出 |
|------|------|------|
| 月度 | 成本归集报告（top10+闲置+建议） | 公示 showback 报表 |
| 季度 | 单位成本趋势评审 + 与 01-29 成本论证对账 | 基线更新或异常归因 |
| 半年 | 标签体系审计（新增 team/topic 覆盖核查） | 覆盖率报告 |

### 常见问答

| 问题 | 回答口径 |
| ------ | ---------- |
| "showback 还是 chargeback" | 先 showback 公示半年建立信任，再考虑 chargeback【论证】 |
| "平台人力怎么摊" | 按用量权重（消息量 50%+存储 30%+连接 20%【估算】）或按团队固定费率——选一并公示 |
| "小团队被大 topic 摊到怎么办" | 成本归集到 topic 而非集群——谁的 topic 谁付费，平台费按用量摊 |
| "闲置误删怎么办" | 30 天规则 + 通知 + 7 天宽限 + 归档（非删除）四重缓冲 |

## 3.65.8 与项目论证的联动算例

**S3 解耦成本实证设计（回填 01-29）**【估算框架】：

```text
同一工作负载（10TB 热数据、100 亿 msg/月）：
本地盘方案：SSD 节点 ×12 + 副本 RF3 → 硬件+运维 ¥X/月
S3 解耦：缓存层节点 ×4 + S3 存储 10TB + 请求费用 → ¥Y/月
单位成本比 = Y/X；预期 <0.5（01-29 论断的验证口径）
测量要点：按 03-17 基准模板同负载跑 72h，成本归集方法用本文 3.65.3
```

**与血缘/治理的接口**：闲置识别消费 02-52 的 active_30d 标记；删除归档动作回写血缘状态；成本标签表作为血缘目录的附属表维护（单一数据源原则）。

## 3.65.9 常见问答补充

| 问题 | 回答口径 |
| ------ | ---------- |
| "Serverless MQ 怎么归集" | 云厂商按请求计费天然按资源归集——补的是 topic→团队标签；单位成本=账单÷消息量 |
| "跨系统（Kafka+Redis）怎么统一口径" | 归集到"消息服务"总账，单位成本分系统报；不强行合并不同语义系统的单价 |
| "成本数据给谁看" | 团队 owner（明细）+ 管理层（单位成本趋势）两级报表 |

## 3.65.10 冷启动：首个季度的实施顺序

| 周 | 动作 | 产出 |
| ---- | ------ | ------ |
| W1-2 | 标签体系定义（topic→团队命名规范+注册表）+ 历史 topic 补标 | 覆盖率 ≥95% |
| W3-4 | 采集脚本（3.65.3）+ 单价表与财务对账 | 首份归集报告（误差记录） |
| W5-8 | showback 公示两轮 + 反馈修正口径 | 稳定月报 |
| W9-12 | 闲置治理首轮（30 天规则）+ 单位成本基线入库 | 治理案例 + 基线序列 |

常见阻力与对策【论证】：团队质疑分摊公平性→先 showback 不扣钱+权重公式公示；采集数据缺失→先自动采集能采的，人工补录走轻量表单。
