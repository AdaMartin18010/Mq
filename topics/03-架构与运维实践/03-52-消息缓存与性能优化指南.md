## 3.52.1 缓存需求与场景

### 常见场景

1. **页缓存（Page Cache）优化**
   消息队列 Broker 大量依赖操作系统页缓存来缓存日志、索引与 AOF 文件。合理配置 `vm.dirty_ratio`、`vm.swappiness` 与 Broker 刷盘参数，可显著降低磁盘 I/O，提高吞吐并稳定 P99 延迟。

2. **Last Value Cache（最新值缓存）**
   每个 key/subject/queue 仅保留最新一条消息，用于状态广播、配置下发、实时查询或设备影子。典型实现包括 Kafka `KTable`、NATS KV Store、MQTT Retained Message、Redis 普通 KV 与 Pulsar Key_Shared 消费的本地快照。

3. **消费端缓存**
   消费者在本地缓存热点消息或元数据，避免重复向 Broker 拉取。配置 `cache.max.size=10000` 与 `cache.expire.after.write.minutes=5` 控制容量与过期时间，配合 `cache.type=lru` 自动淘汰冷数据。

4. **元数据缓存**
   缓存 Topic/Subject/Queue 元数据、分区信息、路由表等，参数 `cache.metadata.enabled=true`、`cache.metadata.max.size=1000`、`cache.metadata.expire.after.write.minutes=60`，减少对 Name Server/Metadata Quorum 的请求压力。

## 3.52.2 页缓存优化

### 操作系统页缓存参数

Linux 页缓存参数直接影响 Broker 对日志文件的读写效率。推荐在 `/etc/sysctl.conf` 中配置以下参数：

```ini
# /etc/sysctl.conf 消息队列节点页缓存优化
vm.dirty_ratio=10
vm.dirty_background_ratio=5
vm.dirty_expire_centisecs=2000
vm.swappiness=1
vm.zone_reclaim_mode=0
vm.overcommit_memory=0
```

参数含义与阈值：

- `vm.dirty_ratio=10`：脏页占总内存 10% 时开始强制刷盘，避免突发大量刷盘造成毛刺。内存较大（>128 GB）的节点可降至 5。
- `vm.dirty_background_ratio=5`：脏页达到 5% 时后台开始刷盘，保持页缓存中有足够可用空间。
- `vm.dirty_expire_centisecs=2000`：脏页在内存中保留不超过 20 秒，降低掉电丢数据风险。
- `vm.swappiness=1`：仅在极端内存压力下才使用 swap，避免页缓存被交换出去。
- `vm.zone_reclaim_mode=0`：NUMA 节点内存不足时优先从其他节点分配，而非回收本节点页缓存，适合 Kafka/Pulsar 等大内存 Broker。

应用后执行 `sysctl -p` 生效，并通过 `sysctl -a | grep -E "dirty|swappiness"` 复查。

### Broker 刷盘与内存参数

不同系统的关键参数配置如下：

- **Kafka**：
  - `log.flush.interval.messages=10000`：每 10000 条消息检查刷盘，不建议设为 1 以避免每次落盘。
  - `log.flush.interval.ms=1000`：每秒检查一次刷盘，配合 OS 页缓存使用。
  - `log.segment.bytes=1073741824`：单个日志段 1 GB，避免段文件过小产生大量随机读。
  - `num.recovery.threads.per.data.dir=2`：启动恢复时并行扫描日志，提升重启速度。

- **Pulsar**：
  - `managedLedgerMaxReadsInFlightSizeInMB=100`：限制正在读取的缓存数据量，避免页缓存被大查询冲垮。
  - `managedLedgerMaxEntriesPerLedger=50000`：控制 ledger 大小，保证顺序读友好。
  - `brokerEntryMetadataInterceptors=org.apache.pulsar.common.intercept.AppendBrokerTimestampMetadataInterceptor` 按需开启。

- **RabbitMQ**：
  - `vm_memory_high_watermark.relative=0.6`：内存使用超过 60% 时触发流控，阻止生产者。
  - `vm_memory_high_watermark_paging_ratio=0.5`：超过 50% 时开始将队列消息换页到磁盘。
  - `disk_free_limit.absolute=2GB`：磁盘低于 2 GB 时阻塞发布。

- **Redis Stream**：
  - `appendfsync everysec`：AOF 每秒刷盘一次，兼顾性能与持久化。
  - `maxmemory-policy allkeys-lru` 或 `volatile-lru`：控制键驱逐策略，避免 OOM。
  - `activedefrag yes`（Redis 4.0+）：定期整理内存碎片，保持缓存访问效率。

- **NATS JetStream**：
  - `max_memory_store=1GB` 与 `max_file_store=10GB` 限制 store 大小。
  - `store_dir` 使用独立 SSD 并启用 `noatime` 挂载。

- **MQTT Broker（EMQ X）**：
  - `zone.external.max_mqueue_len=1000` 控制会话消息队列长度。
  - `zone.external.mqueue_store_qos0=false` 避免 QoS0 消息大量落盘。

### 检查命令

1. **页缓存占用检查**

   ```bash
   free -m | awk 'NR==2{printf "used=%sM, buff/cache=%sM\n", $3, $6}'
   cat /proc/meminfo | grep -E "^(Cached|Dirty|Writeback|Buffers)"
   ```

   `Dirty` 持续高于总内存 5% 说明刷盘压力较大，应下调 `vm.dirty_background_ratio`。

2. **磁盘 I/O 检查**

   ```bash
   iostat -x 1 5 | awk '/^[sv]d/ {print $1, $4, $5, $10, $11}'
   ```

   关注 `%util` 是否长期大于 80% 以及 `await` 是否超过 20 ms。

3. **进程缓存与缺页检查**

   ```bash
   pidstat -r -p $(pgrep -f kafka) 1 5
   ```

   观察 `minflt/s`（小缺页）与 `majflt/s`（大缺页），大缺页过多说明页缓存不足或内存被挤出。

## 3.52.3 Last Value Cache 与消费缓存

### Last Value Cache 配置

Last Value Cache 用于保留每个 key 的最新一条消息。配置参数如下：

```properties
# Last Value Cache 配置片段
cache.hotspot.enabled=true
cache.hotspot.max.size=1000
cache.hotspot.expire.after.write.minutes=30
cache.hotspot.hit.rate.threshold=0.8
```

各系统落地方式：

- **Kafka**：使用 `KTable` 或 `GlobalKTable` 将 topic 物化为状态存储，设置 `cache.max.bytes.buffering=10485760`（10 MB）减少状态存储写入。查询时通过 `ReadOnlyKeyValueStore` 读取最新值。
- **NATS**：使用 JetStream KV Store，`nats kv add config --history=1` 每个 key 仅保留 1 条历史，客户端通过 `nats kv get config app` 获取最新值。
- **MQTT**：发布 Retained Message，`mosquitto_pub -t device/shadow -m '{...}' -r`，Broker 保留该 topic 的最后一条消息，新订阅者立即收到。
- **Redis**：直接使用 `SET key value` 或 `XADD` 配合 `XTRIM` 限制 stream 长度，查询时用 `GET`/`XREAD` 获取最新值。
- **Pulsar**：使用 Key_Shared 订阅并开启 `allowOutOfOrderDelivery=false`，或在外部缓存中保存每个 key 的最新消息。
- **RabbitMQ**：通过 `x-max-length=1` 的队列或外部缓存实现 Last Value Cache，消费端读取队首消息。

### 消费端本地缓存

消费端缓存热点消息可降低重复拉取。Java 示例使用 Caffeine：

```java
// 消费端本地缓存示例（Caffeine）
Cache<String, Message> messageCache = Caffeine.newBuilder()
    .maximumSize(10000)                          // 对应 cache.max.size=10000
    .expireAfterWrite(5, TimeUnit.MINUTES)       // 对应 cache.expire.after.write.minutes=5
    .expireAfterAccess(10, TimeUnit.MINUTES)     // 对应 cache.expire.after.access.minutes=10
    .recordStats()
    .build();

// 消费消息时写入缓存
public void consume(String key, Message msg) {
    messageCache.put(key, msg);
    process(msg);
}

// 查询时先读缓存
public Message get(String key) {
    return messageCache.getIfPresent(key);
}
```

Python 示例使用 `cachetools`：

```python
from cachetools import TTLCache
message_cache = TTLCache(maxsize=10000, ttl=300)  # 5 分钟过期
def cache_message(key, msg):
    message_cache[key] = msg
def get_cached_message(key):
    return message_cache.get(key)
```

### 缓存一致性与穿透防护

1. **一致性策略**
   配置 `cache.consistency.strategy=ttl` 时依赖自动过期；设为 `invalidation` 时需要在消息更新时主动失效缓存；设为 `update` 时采用 `cache.consistency.update.strategy=write_through`（写时同步更新缓存）或 `write_back`（异步回写缓存）。

2. **缓存穿透防护**
   配置 `cache.penetration.protection.enabled=true`，类型选择 `bloom_filter` 或 `null_cache`。Bloom Filter 参数为 `cache.penetration.protection.bloom.filter.size=100000` 与 `cache.penetration.protection.bloom.filter.fpp=0.01`（误判率 1%）。

3. **缓存击穿防护**
   配置 `cache.breakdown.protection.enabled=true`，`cache.breakdown.protection.strategy=mutex`，`cache.breakdown.protection.mutex.timeout.ms=1000`。热点 key 过期时只允许一个线程回源，其余线程等待或返回旧值。

## 3.52.4 缓存命中率监控

### 核心指标

缓存命中率直接决定缓存价值。模板 `cache-config.properties` 中定义的关键指标包括：

- `cache_hit_rate`：命中次数 /（命中次数 + 未命中次数），目标 `cache.hotspot.hit.rate.threshold=0.8`（80%）。
- `cache_miss_rate`：未命中次数占比，低于 20% 为健康。
- `cache_size`：当前缓存条目数，接近 `cache.max.size` 的 90% 时触发容量告警。
- `cache_eviction_count`：淘汰次数，突增说明缓存容量不足或 TTL 设置过短。

### 各系统指标获取方式

| 系统 | 命中率指标来源 | 获取命令/接口 | 推荐阈值 |
| ------ | ---------------- | --------------- | ---------- |
| Kafka 状态存储 | Streams `record-cache-hit-ratio` | JMX `kafka.streams:type=stream-record-cache-hit-ratio` | > 0.8 |
| Redis | `keyspace_hits` / `keyspace_misses` | `redis-cli INFO stats` 计算 | hits/(hits+misses) > 0.8 |
| NATS KV | KV 读取命中统计 | `nats server report jetstream` 或自定义客户端埋点 | > 0.8 |
| RabbitMQ | 队列内存命中率 | `rabbitmqctl status` 与 `rabbitmq-diagnostics quorum_status` | 内存队列比例 > 0.7 |
| Pulsar | Broker Cache | `pulsar-admin broker-stats` 中 `cacheHits`/`cacheMisses` | > 0.8 |
| MQTT | 会话消息命中 | Broker 管理 API 或日志 | 依据业务 SLA |

### 告警阈值

模板中定义以下告警阈值，需在 Prometheus/Grafana 或自定义告警平台中配置：

- `cache.monitor.alert.hit.rate.threshold=0.7`：命中率低于 70% 时触发告警，提示缓存失效、容量不足或热点分散。
- `cache.monitor.alert.size.threshold=0.9`：缓存容量使用超过 90% 时触发告警，需扩容或缩短 TTL。
- `cache.hotspot.hit.rate.threshold=0.8`：Last Value Cache 命中率低于 80% 时，检查 key 分布是否倾斜或缓存过期时间是否过短。

Redis 命中率计算示例：

```bash
#!/bin/bash
# Redis 缓存命中率计算
INFO=$(redis-cli INFO stats)
HITS=$(echo "$INFO" | awk -F: '/keyspace_hits/{print $2}')
MISSES=$(echo "$INFO" | awk -F: '/keyspace_misses/{print $2}')
TOTAL=$((HITS + MISSES))
if [ "$TOTAL" -gt 0 ]; then
  RATE=$(awk "BEGIN {printf \"%.2f\", $HITS / $TOTAL * 100}")
  echo "Redis cache hit rate: ${RATE}%"
else
  echo "Redis cache hit rate: N/A (no requests)"
fi
```

## 3.52.5 缓存优化检查清单

### 实施前

- [ ] 评估缓存场景：页缓存、Last Value Cache、消费缓存、元数据缓存
- [ ] 确认 `cache.type=lru` 或 `ttl`，并设置 `cache.max.size` 与 `cache.expire.after.write.minutes`
- [ ] 检查服务器内存规格，确保页缓存可用内存不低于消息热数据集大小的 1.5 倍
- [ ] 配置 OS 参数：`vm.dirty_ratio=10`、`vm.dirty_background_ratio=5`、`vm.swappiness=1`
- [ ] 备份当前 Broker 配置与 `sysctl.conf`

### 实施中

- [ ] 应用 `sysctl -p` 并复查 `vm.dirty_ratio`、`vm.swappiness` 已生效
- [ ] 配置 Broker 刷盘参数：`log.flush.interval.messages=10000`、`log.flush.interval.ms=1000`
- [ ] 配置 `cache.hotspot.enabled=true`、`cache.hotspot.max.size=1000`、`cache.hotspot.expire.after.write.minutes=30`
- [ ] 启用缓存监控：`cache.monitor.enabled=true`，指标包括 `cache_hit_rate`、`cache_miss_rate`、`cache_size`、`cache_eviction_count`
- [ ] 启用穿透防护：`cache.penetration.protection.enabled=true`，Bloom Filter 大小 `100000`、误判率 `0.01`
- [ ] 启用击穿防护：`cache.breakdown.protection.enabled=true`，互斥超时 `1000 ms`
- [ ] 运行 `cache-optimize.sh` 检查配置建议并逐项核对

### 实施后

- [ ] 监控 `cache.monitor.alert.hit.rate.threshold=0.7`，低于阈值时排查缓存失效或容量
- [ ] 监控 `cache.monitor.alert.size.threshold=0.9`，容量超过 90% 时扩容或缩短 TTL
- [ ] 监控 `cache.hotspot.hit.rate.threshold=0.8`，确保 Last Value Cache 命中率达到 80%
- [ ] 检查 `Dirty` 页是否长期超过总内存 5%，超过则下调 `vm.dirty_background_ratio`
- [ ] 检查磁盘 `%util` 与 `await`，确认页缓存优化后 I/O 压力下降
- [ ] 保留缓存优化前后的性能基线对比，更新运维手册
