## 3.44.1 存储需求

### 业务需求

1. **持久化需求**
   - 核心交易消息必须落盘，避免 Broker 重启或异常宕机导致数据丢失。
   - Kafka 通过 `log.dirs` 配置多副本日志目录；RabbitMQ 依赖 `mnesia` 目录与 `delivery_mode=2` 消息持久化；Pulsar 依赖 BookKeeper Ledger 实现多副本持久化。
   - 金融/订单类场景建议消息保留时间 ≥ 7 天，并配合跨机房复制或异地备份。

2. **容量与性能需求**
   - 磁盘选型优先使用 SSD 或 NVMe，Kafka 顺序写场景建议单盘 IOPS ≥ 3000、吞吐 ≥ 500 MB/s。
   - 按日均消息量、消息大小、副本因子计算裸容量：`裸容量 = 日产量 × 保留天数 × 副本数 × 1.2`。
   - 磁盘使用率告警阈值建议为 80%，增长速率超过 10% 时触发容量预警。

3. **成本需求**
   - 热数据保留在本地高速盘，冷数据按 `storage.cleanup.archive.enabled=true` 归档到低成本对象存储；非关键日志类 topic 可启用压缩与更短保留周期。

## 3.44.2 存储策略

以下参数与 `topics/config-templates/storage-config.properties` 中的键值对应，实际部署时按业务调整。

### 保留策略

1. **时间保留（TTL）**
   - Kafka 设置 `log.retention.hours=168`（7 天），超过时间后按 `log.cleanup.policy` 清理。
   - RabbitMQ 队列级 TTL 通过 `message.ttl=86400000`（24 小时）或 `x-message-ttl` 控制。
   - NATS JetStream 使用 `MaxAge=24h`，Redis Stream 使用 `MAXLEN` 或 `MINID` 控制保留。

2. **大小保留**
   - Kafka topic 设置 `log.retention.bytes=1073741824`（1 GB），任一 partition 达到上限即触发清理。
   - RabbitMQ 队列设置 `x-max-length=1000000`、`x-max-length-in-bytes=1073741824`。

3. **数量保留**
   - NATS JetStream 配置 `MaxMsgs=1000000`；Pulsar 命名空间设置 `retention_size_in_mb` 与 `retention_time_in_minutes`。

### 清理策略

1. **自动清理**
   - Kafka `log.cleanup.policy=delete` 按保留策略自动删除旧 segment；`compact` 策略保留每个 key 的最新值。
   - 配置 `storage.cleanup.schedule=0 2 * * *` 在业务低峰期执行清理，避免 IO 抖动。

2. **手动清理**
   - 紧急释放空间时可手动删除 Kafka 已过期 segment 文件，但必须先停止写入并确认副本同步；RabbitMQ 使用 `rabbitmqctl purge_queue queue_name` 清空队列前需确认消息可丢弃。

3. **归档清理**
   - 启用 `storage.cleanup.archive.enabled=true`，将过期 segment 压缩后转存到 `storage.cleanup.archive.dir=/var/archive`。

### 压缩策略

1. **消息压缩**
   - Kafka producer 与 broker 均配置 `compression.type=snappy`（或 lz4/zstd），批量较大时开启可降低网络与磁盘占用。

2. **存储压缩**
   - BookKeeper 可开启 `journalSyncData=false` 与 `dbStorage_directEntryLogger=true` 提升吞吐，但需权衡断电数据风险。
   - 归档文件使用 zstd（`storage.compression.type=zstd`，level 3）可获得更高压缩比。

## 3.44.3 各系统存储配置

### Kafka 存储层

在 `server.properties` 中配置：

```properties
log.dirs=/var/kafka-logs,/var/kafka-logs2
log.retention.hours=168
log.retention.bytes=1073741824
log.segment.bytes=1073741824
log.cleanup.policy=delete
compression.type=snappy
```

- `log.dirs` 建议每个目录挂载独立物理盘；`log.retention.bytes` 按 partition 生效。

### Pulsar BookKeeper

关键配置位于 `bookkeeper.conf`：

```properties
journalDirectories=/var/pulsar/journal
ledgerDirectories=/var/pulsar/ledgers
journalSyncData=false
minUsableSizeForIndexFileCreation=1073741824
```

- `journalDirectories` 与 `ledgerDirectories` 应分盘部署；每个 Ledger 默认写入 `ensembleSize=3`、`writeQuorum=3`、`ackQuorum=2`。

### RabbitMQ 队列持久化

队列与消息均声明为持久化：

```python
channel.queue_declare(queue='orders', durable=True)
channel.basic_publish(
    exchange='',
    routing_key='orders',
    body=message,
    properties=pika.BasicProperties(delivery_mode=2)
)
```

- `durable=True` 持久化队列元数据；`delivery_mode=2` 将消息体写入 `rabbitmq.data.dir=/var/lib/rabbitmq/mnesia`；quorum queue 使用 Raft 日志，默认三副本。

### NATS JetStream 与 Redis Stream

```go
js.AddStream(&nats.StreamConfig{
    Name:     "ORDERS",
    Storage:  nats.FileStorage,
    Replicas: 3,
    MaxAge:   24 * time.Hour,
    MaxBytes: 1024 * 1024 * 1024,
    MaxMsgs:  1000000,
})
```

- `Storage: nats.FileStorage` 启用文件持久化，目录由 `nats.jetstream.store.dir=/var/nats-jetstream` 指定。

```bash
redis-cli XADD orders MAXLEN ~ 1000000 * field value
redis-cli CONFIG SET maxmemory 4gb maxmemory-policy noeviction
```

- `MAXLEN ~` 降低大 stream 修剪开销；`maxmemory-policy` 建议 `noeviction` 或 `volatile-lru`，避免误删未消费消息。

## 3.44.4 备份策略

### 全量备份

全量备份适用于数据量可控、恢复时间要求高的场景：

```bash
# Kafka 全量备份（建议同时做逻辑备份避免文件不一致）
tar -czf /var/backups/kafka_full_$(date +%Y%m%d_%H%M%S).tar.gz \
  /var/kafka-logs /opt/kafka/config

# RabbitMQ 导出定义与数据
rabbitmqctl export_definitions /var/backups/rabbitmq_definitions_$(date +%Y%m%d).json
```

- 物理全量备份 Kafka 时，建议结合 `kafka-console-consumer` 做逻辑备份。
- 全量备份频率建议每天一次，保留 30 天：`storage.backup.retention.days=30`。

### 增量与快照备份

1. **增量备份**
   - Kafka 利用 segment 只追加特性，通过 `rsync -av --delete /var/kafka-logs/ /backup/kafka-incremental/` 仅复制新增文件；频率可提高到每小时一次，但恢复需串联多次备份。

2. **快照备份**
   - 使用 LVM 或云盘快照秒级冻结文件系统状态，适合 TB 级数据快速恢复；快照前执行 `kafka-log-dirs.sh --describe` 确认副本同步。

### 备份方式对比

| 备份方式 | 适用系统 | 备份窗口 | 存储占用 | 恢复复杂度 | 推荐频率 |
| --------- | --------- | --------- | --------- | ----------- | --------- |
| 全量备份 | Kafka、RabbitMQ、Pulsar | 长 | 大 | 低 | 每日 |
| 增量备份 | Kafka（segment）、NATS JetStream | 短 | 小 | 中 | 每小时 |
| 快照备份 | 云盘部署的各系统 | 极短 | 大 | 低 | 每日或事件触发 |
| 逻辑备份 | Kafka、RabbitMQ | 中 | 中 | 中 | 关键 topic 每日 |

## 3.44.5 恢复策略

### 完整恢复

完整恢复用于整集群数据损坏或灾难重建：

```bash
# 停止 Kafka 并清空损坏日志
cd /opt/kafka && bin/kafka-server-stop.sh
rm -rf /var/kafka-logs/*

# 解压最近一次全量备份
tar -xzf /var/backups/kafka_full_20260105_020000.tar.gz -C /

# 启动并检查 under-replicated partitions
bin/kafka-server-start.sh -daemon config/server.properties
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe | grep "UnderReplicated"
```

- 恢复后检查 `UnderReplicatedPartitions` 是否为 0；RabbitMQ 需停止服务后还原 mnesia 目录，再用 `rabbitmqctl import_definitions` 导入元数据。

### 增量与时间点恢复

**增量恢复**在全量基础上按时间顺序应用增量：

```bash
mkdir -p /var/kafka-logs
tar -xzf /var/backups/kafka_full_20260101_020000.tar.gz -C /
for d in /var/backups/kafka-incremental/2026010*; do
  rsync -av "$d/" /var/kafka-logs/
done
```

- 必须严格按备份时间顺序应用，任何一次缺失都会导致数据不连续。

**时间点恢复**依赖快照或基于日志序列号的逻辑备份：

- 找到目标时间点之前的最近一次快照或全量备份。
- Kafka 结合 `kafka-consumer-groups.sh --reset-offsets` 将消费位点调整到目标时间；Pulsar 使用 managed ledger 的 mark-delete 位置回溯。

### 恢复演练

仓库提供了 `topics/scripts/backup-restore.sh` 与 `storage-backup.sh`，可直接用于演练：

```bash
# 备份 Kafka
bash topics/scripts/backup-restore.sh backup kafka

# 备份 RabbitMQ
bash topics/scripts/backup-restore.sh backup rabbitmq

# 全量备份所有支持系统
bash topics/scripts/storage-backup.sh full /var/backups
```

- 演练频率建议每季度一次，验证备份文件可解压、服务可启动、数据可查询。
- 演练记录应包含恢复 RTO（目标 ≤ 4 小时）与 RPO（目标 ≤ 1 小时）实测值。

## 3.44.6 存储检查清单

### 实施前

- [ ] 确认 Kafka `log.dirs` 已配置为独立物理盘路径，并预留 50% 以上冗余空间。
- [ ] 确认 Pulsar `journalDirectories` 与 `ledgerDirectories` 分盘，磁盘吞吐满足峰值写入 × 2。
- [ ] 确认 RabbitMQ `rabbitmq.data.dir=/var/lib/rabbitmq/mnesia` 位于持久化卷，quorum queue 副本数 ≥ 3。
- [ ] 确认 NATS JetStream `store.dir=/var/nats-jetstream` 已挂载，且 `MaxAge`/`MaxBytes`/`MaxMsgs` 已按业务设置。
- [ ] 确认 Redis `maxmemory` 已设置，且 `maxmemory-policy` 不会误删未消费 stream 消息。
- [ ] 制定保留策略：`log.retention.hours=168`、`storage.retention.size.bytes=1073741824`、`storage.retention.count=1000000`。

### 实施中

- [ ] 配置 `log.cleanup.policy=delete` 或 `compact`，并设置 `storage.cleanup.schedule=0 2 * * *` 低峰清理。
- [ ] 开启压缩：`compression.type=snappy`（Kafka）、应用层 gzip/zstd（RabbitMQ）。
- [ ] 部署备份脚本 `storage-backup.sh`，配置 `storage.backup.dir=/var/backups`、`storage.backup.retention.days=30`。
- [ ] 对关键 topic/队列执行一次全量备份，并验证备份文件可成功解压与导入。
- [ ] 配置存储监控：`storage.monitor.metrics=storage_size,storage_usage,storage_growth,storage_cleanup_count`。

### 实施后

- [ ] 每日检查磁盘使用率，阈值 `storage.monitor.alert.threshold.usage=0.8`（80%）。
- [ ] 每周检查存储增长率，超过 `storage.monitor.alert.threshold.growth=0.1`（10%）时扩容。
- [ ] 每月运行 `storage-check.sh` 核对配置与实际路径、保留策略是否一致。
- [ ] 每季度执行一次恢复演练，记录 RTO/RPO，更新恢复操作手册。
- [ ] 每年审计备份保留周期，清理超期备份，验证归档文件可读取。
