## 3.47.1 路由需求

### 业务需求

1. **消息路由**
   需要根据消息内容、键值或规则将消息分发到不同分区、队列或主题。Kafka 通过 `key` 与分区器决定目标分区，RabbitMQ 通过 Exchange 与 Binding 路由到队列，NATS 通过 Subject 层级与通配符匹配，MQTT 通过 Topic Filter 与通配符 `+`/`#` 匹配，Pulsar 通过 Partitioned Topic 与 Subscription 类型分发，Redis Stream 通过 Stream Key 与消费者组划分。

2. **负载均衡**
   在消费者集群中均匀分配消息，避免单点过载。Kafka 依赖 Consumer Group 的 partition assignor，RabbitMQ 通过多个消费者绑定同一队列并设置 `prefetch_count`，NATS 使用 Queue Group，MQTT 5.0 使用 Shared Subscriptions（`$share/{group}/{topic}`），Pulsar 使用 Shared 订阅，Redis Stream 使用 `XREADGROUP` 在同一消费者组内轮询。

3. **路由策略**
   常见策略包括轮询（round-robin）、哈希（key-hash）、优先级（priority）与最小连接（least-connections）。模板中 `load.balance.strategy=round-robin` 为默认值，热点场景可改为 `hash` 或 `weighted`，并通过 `load.balance.monitor.imbalance.threshold=0.2` 设置不均衡告警阈值。

## 3.47.2 路由策略

### 策略类型

1. **基于 Key 路由（Kafka/Pulsar/Redis）**
   Kafka 默认按 `key.hashCode() % partition.count` 路由，相同 Key 进入同一分区，保证分区内顺序。模板配置 `kafka.routing.strategy=key-hash`、`kafka.routing.key.field=id`、`kafka.routing.partition.count=6`。Pulsar 的 `Key_Shared` 订阅同样按 Key 路由到固定 Consumer。Redis Stream 不原生分区，但可通过 Key 前缀（如 `order:events`、`user:events`）实现业务隔离。

2. **基于 Exchange/Subject 路由（RabbitMQ/NATS/MQTT）**
   RabbitMQ Topic Exchange 使用路由键模式 `order.{action}.{priority}`，Binding Key 支持 `*` 匹配一个单词、`#` 匹配零个或多个单词。NATS Subject 模式 `orders.{region}.{priority}` 支持 `*` 和 `>` 通配符。MQTT 5.0 支持 `sensors/+/temperature` 与共享订阅 `$share/group1/sensors/+`。

3. **动态路由**
   通过外部规则文件 `routing.rules.file=/etc/mq/routing-rules.json` 实现运行时调整，配合 `routing.rules.reload.enabled=true` 与 `routing.rules.reload.interval=60s` 热加载。路由计算结果可缓存：`routing.cache.enabled=true`、`routing.cache.size=10000`、`routing.cache.ttl=300`、`routing.cache.eviction.policy=LRU`。

```properties
# 消息路由配置模板（topics/config-templates/routing-config.properties）
# Kafka
kafka.routing.strategy=key-hash
kafka.routing.key.field=id
kafka.routing.custom.partitioner=com.example.CustomPartitioner
kafka.routing.partition.count=6

# NATS
nats.routing.strategy=subject
nats.routing.subject.pattern=orders.{region}.{priority}
nats.routing.queue.group.enabled=true
nats.routing.queue.group.name=workers

# RabbitMQ
rabbitmq.routing.strategy=topic
rabbitmq.routing.exchange.type=topic
rabbitmq.routing.exchange.name=orders
rabbitmq.routing.key.pattern=order.{action}.{priority}
rabbitmq.routing.headers.match=all

# 负载均衡
load.balance.enabled=true
load.balance.strategy=round-robin
load.balance.monitor.enabled=true
load.balance.monitor.metrics=routing_count,routing_distribution,load_balance_ratio

# 动态规则
routing.rules.enabled=true
routing.rules.file=/etc/mq/routing-rules.json
routing.rules.reload.enabled=true
routing.rules.reload.interval=60s

# 路由缓存
routing.cache.enabled=true
routing.cache.size=10000
routing.cache.ttl=300
routing.cache.eviction.policy=LRU
```

### 路由配置命令

```bash
# Kafka：创建 6 分区 topic
kafka-topics.sh --bootstrap-server kafka:9092 \
  --create --topic orders --partitions 6 --replication-factor 3

# Pulsar：创建 6 分区 topic
pulsar-admin topics create-partitioned-topic \
  persistent://my-tenant/my-ns/orders --partitions 6

# RabbitMQ：声明 topic exchange 并绑定队列
rabbitmqadmin declare exchange name=orders type=topic durable=true
rabbitmqadmin declare queue name=vip-orders durable=true
rabbitmqadmin declare binding source=orders destination=vip-orders routing_key="order.*.vip"

# NATS：通过 nats cli 发布到层级主题
nats pub "orders.cn.vip" '{"id":1}'

# MQTT：共享订阅（QoS 1）
mosquitto_sub -h mqtt-broker -t '$share/group1/sensors/+' -q 1

# Redis Stream：按业务 Key 拆分并使用消费者组
redis-cli XADD order:events * order_id 1001 status created
redis-cli XGROUP CREATE order:events order-processors $ MKSTREAM
```

## 3.47.3 负载均衡

### 均衡策略

1. **消息均衡**
   Kafka 的 partition 数量决定最大并行度，建议每分区消息速率不超过 10 MB/s 或 1 万 msg/s。RabbitMQ 单队列单消费者吞吐量约 1-5 万 msg/s，可通过增加队列与消费者横向扩展。NATS Queue Group 自动将同一 Subject 的消息轮询到组成员。MQTT Shared Subscription 按 `$share/{group}` 将消息分发给组内客户端。

2. **消费者均衡**
   Kafka Consumer Group 支持 `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor`，Rebalance 影响更小。RabbitMQ 通过 `basic_qos(prefetch_count=10)` 实现公平分发。Pulsar Shared 订阅将消息轮询到所有 Consumer，Key_Shared 保证同一 Key 进入同一 Consumer。Redis Stream 使用 `XREADGROUP GROUP mygroup consumer1 COUNT 10 STREAMS mystream >` 在消费者组内拉取。

3. **资源均衡**
   Pulsar Broker 内置 LoadBalancer 自动将 Bundle 迁移到负载较低的 Broker。RabbitMQ 集群可配合 HAProxy/Nginx 在节点间分发连接。Redis Cluster 通过 16384 个哈希槽将键分布到多个主节点。监控指标包括 `routing_count`、`routing_distribution`、`load_balance_ratio`，当不均衡度超过 0.2（20%）时触发告警。

### 负载验证命令

```bash
# 运行路由测试脚本
bash topics/scripts/routing-test.sh kafka key
bash topics/scripts/routing-test.sh nats queue
bash topics/scripts/routing-test.sh rabbitmq topic

# Kafka：查看消费者组分区分配是否均衡
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --describe --group order-consumers

# Pulsar：查看 topic 消费统计
pulsar-admin topics stats persistent://my-tenant/my-ns/orders

# RabbitMQ：查看队列与消费者数
rabbitmqctl list_queues name consumers messages ready_unacked

# NATS：队列组订阅
nats sub "orders.*" --queue workers

# MQTT：共享订阅验证
mosquitto_sub -h mqtt-broker -t '$share/group1/sensors/+' -q 1 &
mosquitto_pub -h mqtt-broker -t 'sensors/temperature' -m '25.5' -q 1

# Redis Stream：查看消费者组信息
redis-cli XINFO GROUPS order:events
redis-cli XINFO CONSUMERS order:events order-processors
```

## 3.47.4 最佳实践

### 设计建议

1. **路由键设计**
   路由键应稳定、可读、具备业务语义，例如 `order.created.vip`、`sensors.temperature.room1`。避免使用随机值作为 Kafka Key，否则会导致分区倾斜；也不要使用过度细粒度键，防止热点分区。

2. **性能优化**
   路由计算避免在每次发送时重复解析规则。启用 `routing.cache.enabled=true`，缓存大小 `routing.cache.size=10000`，TTL 300 秒，淘汰策略 LRU。Kafka Producer 可自定义 `partitioner.class` 实现业务路由，但要保证 `partition` 方法幂等且无状态。

3. **运维管理**
   规则文件 `routing.rules.file=/etc/mq/routing-rules.json` 变更前先备份并做 JSON Schema 校验，再触发 60 秒间隔的热加载。监控 `routing_latency`、`routing_errors`、`load_balance_ratio`，当 `load_balance_ratio` 超过 0.2 或任意分区/队列消息数偏差超过 20% 时告警。生产环境建议分区数或队列数为消费者数量的整数倍，便于均衡。

## 3.47.5 路由检查清单

### 实施前

- [ ] 确定 Kafka topic 分区数（如 6）与副本因子（如 3），并规划 `partition.assignment.strategy`。
- [ ] 确定 RabbitMQ Exchange 类型（direct/topic/headers/fanout）与 Binding Key 模式。
- [ ] 确定 NATS Subject 层级（如 `orders.{region}.{priority}`）与 Queue Group 名称（如 `workers`）。
- [ ] 确定 Pulsar Subscription 类型：Shared（轮询）、Key_Shared（按 Key）、Failover（主备）。
- [ ] 确定 MQTT Shared Subscription 组名（如 `$share/group1/sensors/+`）。
- [ ] 确定 Redis Stream 业务 Key 与消费者组名（如 `order:events`、`order-processors`）。

### 实施中

- [ ] Kafka Producer 设置 Key 字段或自定义 `partitioner.class`，模板 `kafka.routing.strategy=key-hash`。
- [ ] 创建 RabbitMQ Exchange 与 Queue，并配置 `routing_key` 与 `x-match`（headers 类型）。
- [ ] NATS 消费者使用 `QueueSubscribe("orders.*", "workers", handler)`。
- [ ] MQTT 客户端订阅共享主题 `$share/{group}/{topic}`，QoS 与发布端一致。
- [ ] Pulsar 创建分区 topic 并指定 Subscription 类型为 Shared 或 Key_Shared。
- [ ] Redis 使用 `XGROUP CREATE` 创建消费者组，`XREADGROUP` 拉取消息。
- [ ] 配置负载均衡策略 `load.balance.strategy=round-robin`，不均衡阈值 `load.balance.monitor.imbalance.threshold=0.2`。
- [ ] 启用动态规则热加载 `routing.rules.reload.enabled=true`，间隔 60 秒。

### 实施后

- [ ] 运行 `routing-test.sh kafka key`、`routing-test.sh nats queue`、`routing-test.sh rabbitmq topic`，确认路由行为符合预期。
- [ ] 使用 `kafka-consumer-groups.sh --describe` 检查分区分配均衡，单个 Consumer 分区数差异不超过 1。
- [ ] 使用 `pulsar-admin topics stats` 检查各分区消息速率差异不超过 20%。
- [ ] 使用 `rabbitmqctl list_queues` 检查队列消息堆积与消费者数量匹配。
- [ ] 使用 `nats sub --queue` 验证队列组内消息轮询分发。
- [ ] 使用 `mosquitto_sub` 多客户端订阅 `$share/group1/sensors/+`，验证消息仅被组内一个客户端接收。
- [ ] 使用 `redis-cli XINFO GROUPS` 与 `XINFO CONSUMERS` 检查消费者组状态，pending 消息数不过高。
- [ ] 监控 `routing_count`、`routing_latency`、`routing_errors`、`load_balance_ratio`，设置不均衡度 > 0.2 告警。

| 系统 | 路由单元 | 路由机制 | 负载均衡 | 顺序保证 |
| ------ | ---------- | ---------- | ---------- | ---------- |
| Kafka | Topic-Partition | Key Hash / 自定义 Partitioner / 指定分区 | Consumer Group + Assignor | 分区级有序 |
| RabbitMQ | Exchange-Queue | Direct / Topic / Headers / Fanout Binding | 多消费者 + prefetch_count | 单队列有序 |
| NATS | Subject | 主题层级 + `*`/`>` 通配符 | Queue Group | 无（Core） |
| Pulsar | Partitioned Topic | Partition + Subscription 类型 | Shared / Key_Shared / Failover | Key_Shared 按 Key 有序 |
| MQTT | Topic Filter | 主题层级 + `+`/`#` 通配符 | Shared Subscription `$share` | 无 |
| Redis Stream | Stream Key | Key 命名 + Consumer Group | `XREADGROUP` 消费者组 | Stream 内按 ID 有序 |
