## 3.58.1 灾难恢复需求

灾难恢复需要覆盖数据丢失、服务中断和重大灾难三类场景。数据丢失场景包括磁盘故障、数据损坏和误删除；服务中断场景包括机房故障、网络中断和系统级故障；重大灾难场景包括自然灾害、人为误操作和安全攻击。

在制定方案前，必须与业务方确认可接受的恢复时间目标（RTO）和恢复点目标（RPO）。不同业务等级对应不同的容灾策略，模板 `disaster-recovery-config.properties` 提供了统一的参数化入口。

---

## 3.58.2 RTO/RPO定义

RTO（Recovery Time Objective）指灾难发生后系统恢复到可接受水平所需的最长时间。RPO（Recovery Point Objective）指灾难发生时可接受的数据丢失时间窗口。

RTO/RPO 等级划分表：

| 等级 | RTO | RPO | 适用业务 | 典型架构 |
| --- | --- | --- | --- | --- |
| 关键业务 | ≤ 15 分钟 | ≈ 0 | 金融交易、核心订单 | 同步双活 + 自动切换 |
| 重要业务 | ≤ 1 小时 | ≤ 15 分钟 | 电商核心链路 | 异步复制 + 半自动切换 |
| 一般业务 | ≤ 4 小时 | ≤ 1 小时 | 日志、统计类消息 | 定时备份 + 手动恢复 |
| 可容忍业务 | ≤ 24 小时 | ≤ 24 小时 | 非关键通知 | 每日全量备份 |

模板中对应参数：

- `disaster.recovery.recovery.rto.target.hours=1`
- `disaster.recovery.recovery.rpo.target.hours=0`

RPO=0 通常需要同步复制，会牺牲一定性能；RPO>0 可使用异步复制，成本和复杂度更低。设定目标后，需在监控中配置 `disaster.recovery.monitor.alert.recovery.time.exceeded.enabled=true` 和 `alert.data.loss.enabled=true`，确保超阈值时立即告警。

## 3.58.3 跨地域复制

跨地域复制是灾难恢复的核心能力。Kafka 使用 MirrorMaker 2 进行跨集群复制，NATS JetStream 使用 Stream 复制，RabbitMQ 使用 Federation 或 Shovel。

### 3.58.3.1 Kafka MirrorMaker 2 配置

```properties
# mm2.properties
clusters=source,target
source.bootstrap.servers=source-cluster:9092
target.bootstrap.servers=target-cluster:9092
source->target.enabled=true
source->target.topics=orders,.
replication.factor=3
sync.topic.acls.enabled=false
```

启动命令：

```bash
connect-mirror-maker.sh mm2.properties
```

监控复制延迟：

```bash
kafka-consumer-groups.sh \
  --bootstrap-server target-cluster:9092 \
  --describe \
  --group mm2-offset-syncs-source.internal
```

模板中 `disaster.recovery.replication.lag.threshold.seconds=60` 即为复制延迟告警阈值。

### 3.58.3.2 NATS JetStream 复制

NATS JetStream 通过 `Replicas` 和 Stream 镜像实现复制：

```go
js.AddStream(&nats.StreamConfig{
    Name:     "ORDERS_BACKUP",
    Subjects: []string{"orders.*"},
    Storage:  nats.FileStorage,
    Replicas: 3,
    MaxAge:   7 * 24 * time.Hour,
})
```

### 3.58.3.3 RabbitMQ Federation

RabbitMQ Federation 配置示例：

```bash
rabbitmqctl set_parameter federation-upstream orders-upstream \
  '{"uri":"amqp://target-cluster","max-hops":1}'
```

跨地域复制需关注带宽、延迟和一致性。同步复制适合短距离低延迟场景，异步复制适合跨区或跨云场景。

## 3.58.4 备份恢复流程

### 3.58.4.1 备份策略

模板 `disaster-recovery-config.properties` 定义了备份频率、类型和保留周期：

```properties
# 备份策略配置
disaster.recovery.backup.enabled=true
disaster.recovery.backup.strategy=incremental
disaster.recovery.backup.frequency=hourly
disaster.recovery.backup.interval.seconds=3600
disaster.recovery.backup.retention.days=30
disaster.recovery.backup.storage.type=remote
disaster.recovery.backup.storage.path=/backup/mq
```

备份类型选择：

- 全量备份：完整复制数据，恢复最快，占用空间最大，建议每周一次；
- 增量备份：仅备份自上次备份后的变化，空间小，恢复需回溯，建议每小时一次；
- 差异备份：备份自上次全量后的变化，恢复较增量快，折中方案。

Kafka 备份可使用 `kafka-console-consumer` 导出到对象存储，或直接备份日志目录（需停止 Broker）。RabbitMQ 使用 `rabbitmqctl export_definitions` 导出元数据，消息体可通过 Shovel 或插件备份。

### 3.58.4.2 恢复流程

恢复流程应写入 `disaster.recovery.recovery.manual.procedures.file=/etc/mq/recovery-procedures.md`，并定期演练。标准步骤：

1. 灾难检测：通过健康检查确认主集群不可用，`disaster.recovery.detection.failure.threshold=3` 表示连续 3 次失败触发；
2. 切换决策：根据 RTO 决定是否自动切换，`disaster.recovery.recovery.strategy=automatic` 或 `manual`；
3. DNS/LB 切换：更新 DNS 或负载均衡指向灾备集群，`disaster.recovery.switch.dns.ttl.seconds=60`；
4. 数据恢复：从备份恢复 Topic/Stream/队列定义及消息；
5. 完整性验证：启用 `disaster.recovery.data.recovery.verification.checksum.enabled=true`，按 10% 采样校验；
6. 业务恢复：通知应用切换 Producer/Consumer 到灾备集群；
7. 事后复盘：记录 RTO/RPO 实际值，更新恢复手册。

### 3.58.4.3 使用恢复脚本

`restore-all.sh` 用于统一恢复 Kafka、NATS、RabbitMQ 的备份：

```bash
# 确认备份目录存在并执行恢复
./topics/scripts/restore-all.sh /backup/mq/2026-01-06
```

脚本会先提示确认，然后依次恢复 `kafka_config.tar.gz`、`nats-server.conf` 和 `rabbitmq_definitions.json`。生产环境执行前必须验证备份文件完整性。

## 3.58.5 DR演练步骤

DR 演练是验证灾难恢复方案有效性的唯一手段。模板中 `disaster.recovery.testing.frequency=monthly` 建议每月演练一次，场景覆盖 data_loss、service_interruption、disaster。

演练步骤：

1. 制定演练计划：明确演练范围、预期 RTO/RPO、回滚方案；
2. 通知相关方：业务、运维、DBA、安全团队；
3. 模拟故障：关闭主集群部分 Broker、断开网络或删除测试 Topic；
4. 执行切换：按恢复手册完成灾备切换；
5. 验证业务：检查消息写入、消费、积压和延迟是否正常；
6. 记录指标：实际 RTO、RPO、切换过程中遇到的问题；
7. 回滚恢复：将业务切回主集群，确认数据一致；
8. 输出报告：保存到 `disaster.recovery.testing.report.path=/var/mq/recovery-test-reports`。

自动化演练可使用脚本 `disaster-recovery-check.sh` 先做基础检查：

```bash
./topics/scripts/disaster-recovery-check.sh
```

该脚本会输出备份类型、RTO/RPO 等级、恢复流程和测试场景，供演练前快速核对。

## 3.58.6 灾难恢复检查清单

### 实施前

- [ ] 与业务方确认 RTO/RPO 等级，并写入 `disaster-recovery-config.properties`；
- [ ] 制定备份策略：全量/增量/差异备份频率和保留周期；
- [ ] 选择跨地域复制方案：Kafka MirrorMaker 2 / NATS JetStream / RabbitMQ Federation；
- [ ] 编写恢复手册 `recovery-procedures.md`，明确每个步骤负责人。

### 实施中

- [ ] 配置主备集群复制，监控复制延迟 `replication.lag.threshold.seconds=60`；
- [ ] 部署备份任务，每小时增量、每周全量，保留 30 天；
- [ ] 配置备份存储到远程或云对象存储，避免与主集群同机房；
- [ ] 设置灾难检测：健康检查间隔 60 秒，连续 3 次失败触发告警；
- [ ] 配置 DNS/LB 自动切换，TTL 建议 ≤ 60 秒。

### 实施后

- [ ] 每月执行一次 DR 演练，记录实际 RTO/RPO；
- [ ] 演练后更新恢复手册和配置参数；
- [ ] 使用 `disaster-recovery-check.sh` 定期检查备份状态和恢复流程；
- [ ] 验证备份文件可恢复性，至少每季度做一次完整恢复测试；
- [ ] 将灾备切换指标接入监控告警：`backup_status`、`recovery_time`、`data_loss`。
