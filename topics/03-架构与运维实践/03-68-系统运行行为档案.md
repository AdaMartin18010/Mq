## 3.68.1 启动序列行为

| 系统 | 启动阶段顺序 | 就绪探针信号 | K8s 探针建议 |
| ------ | ------ | ------ | ------ |
| Kafka | 1. 加载 `server.properties`<br>2. 初始化日志管理器与副本管理器<br>3. KRaft 模式下加入 quorum / 旧模式连接 ZK<br>4. 打开 9092 监听并注册到元数据 | `kafka-broker-api-versions.sh --bootstrap-server localhost:9092` 成功返回；或直接 TCP 9092 + metadata 请求 | readiness：metadata 请求成功；startup：等待 controller 就绪；liveness：进程存活 |
| RabbitMQ | 1. Erlang VM 启动<br>2. Mnesia 数据库加载与集群同步<br>3. 插件（management/prometheus）启动<br>4. 监听 5672/15672 | `curl -f http://localhost:15672/api/health/checks/alarms` 返回 200 且无 alarm | readiness：management API /health 正常；startup：等待 Mnesia 同步完成【估算】 |
| NATS | 1. 解析 `nats.conf`<br>2. 建立 routes/cluster/gateway<br>3. JetStream 初始化存储与 RAFT 元数据<br>4. 打开 4222/8222 | `/healthz` 返回 200；`/jsz` 显示 JetStream 已启用（如使用 JS） | readiness：`/healthz`；startup：等待 cluster 与 RAFT 就绪；liveness：进程存活 |
| Pulsar | 1. Broker 连接 ZooKeeper/Oxia 与 BookKeeper<br>2. 加载 namespace bundle 元数据<br>3. 启动 protocol handler<br>4. 打开 6650/8080 | `bin/pulsar-admin brokers healthcheck` 返回 OK；8080 `/admin/v2/brokers/health` 200 | readiness：brokers healthcheck；startup：等待 bundle 加载；bookie 单独探针 |
| RocketMQ | 1. NameServer 启动（先）<br>2. Broker 加载配置、启动存储层<br>3. Broker 向 NameServer 注册<br>4. Proxy（5.x）启动并连接 Broker | Broker 日志出现 `The broker boot success..`；NameServer 日志出现 `The Name Server boot success..` | readiness：NameServer 端口 9876 可达；Broker 等待注册成功；liveness：进程存活 |
| Redis Stream | 1. 加载 `redis.conf`<br>2. RDB/AOF 数据加载到内存<br>3. 打开 6379 监听<br>4. 集群模式下加入 cluster | `redis-cli PING` 返回 `PONG`；INFO 命令返回 `loading:0` | readiness：`PING` + `loading:0`；startup：等待数据加载完成；liveness：进程存活 |

```bash
# Kafka readiness 探针示例
kafka-broker-api-versions.sh --bootstrap-server localhost:9092 >/dev/null 2>&1

# RabbitMQ readiness 探针示例
curl -sf http://localhost:15672/api/health/checks/alarms | grep -q '"status":"ok"'

# NATS readiness 探针示例
curl -sf http://localhost:8222/healthz

# Pulsar readiness 探针示例
bin/pulsar-admin brokers healthcheck

# Redis readiness 探针示例
redis-cli PING | grep -q PONG
```

启动顺序的通用原则：先元数据/控制层，再存储层，最后无状态代理/接入层。RocketMQ 必须 NameServer 先于 Broker；Pulsar 必须 ZooKeeper/Oxia 与 BookKeeper 先于 Broker；Kafka KRaft 必须保证 controller quorum 在线。

## 3.68.2 故障行为

### 默认故障动作对照

| 故障场景 | Kafka | RabbitMQ | NATS | Pulsar | RocketMQ | Redis Stream |
| ------ | ------ | ------ | ------ | ------ | ------ | ------ |
| 磁盘满 | 写日志失败；若 journal/log 目录满，broker 可能进入不可用状态并触发 FAIL 日志；副本同步停滞 | 触发 disk alarm，默认剩余空间 < 50 MB 时全集群阻塞发布连接，消费者可继续消费 | JetStream 未设 limit 时持续写入直至磁盘满可能拉垮 server；设 limit 后按 Retention 策略丢弃或拒绝 | BookKeeper journal/ledger 目录满导致写入失败；broker 依赖底层存储报错；需监控 bookie 磁盘 | CommitLog 写满后 broker 拒绝写入；ConsumeQueue 索引写失败影响消费进度 | 若 AOF 目录满或 RDB 保存失败，写命令可能报错；`maxmemory` 触发驱逐或 OOM 错误 |
| 网络抖动 | follower 与 leader 失联触发 ISR 收缩；`min.insync.replicas` 不足时生产者收到 NOT_ENOUGH_REPLICAS；consumer 重平衡 | 节点间链路中断可能触发分区；镜像/仲裁队列依赖多数派；发布连接可能收到 connection.blocked | 客户端自动重连；JetStream 集群节点失联触发 RAFT 视图变更；未 ack 消息按 AckWait 重发 | broker/bookie 或 ZK 会话超时触发 bundle unload / ledger 写入失败；客户端重连 | NameServer 与 Broker 心跳超时导致路由信息过期；客户端需更新路由表 | Cluster 节点间通信超时触发 fail-over；Sentinel 模式下主观/客观下线 |
| 副本失联 | 分区 ISR 掉出失联副本；如果 ISR 只剩 leader 且 `min.insync.replicas=1` 仍可写，否则拒绝写 | quorum queue  minority 分区不可写；classic 镜像队列在同步策略下可能阻塞发布 | JetStream stream R=3 时最多容忍 1 节点失联；RAFT 保证多数派可用 | BookKeeper ensemble 写入需 ack quorum；副本不足时 ledger 写入失败 | 同步复制下主从失联后 slave 落后；异步复制下可能丢失未同步消息 | Redis Cluster 分片主节点失联后，副本提升；Sentinel 执行 failover |

### OOM 前典型征兆

| 系统 | 征兆 1 | 征兆 2 | 征兆 3 |
| ------ | ------ | ------ | ------ |
| Kafka | GC 日志出现长时间 Full GC 或分配失败；`kafka.server:type=KafkaServer,name=BrokerState` 异常 | 堆外内存/页缓存竞争导致 produce 延迟飙升 | 日志出现 `OutOfMemoryError`；4.x 默认建议 `-XX:+ExitOnOutOfMemoryError` |
| RabbitMQ | Erlang VM 频繁 GC，日志出现 `memory resource limit alarm` | `mem_used` 逼近 `mem_limit`，消息堆积曲线陡升 | Erlang crash dump 文件生成；节点因内存不足被 OOM killer 终止 |
| NATS | `nats_server_mem` 接近 `GOMEMLIMIT` 或系统上限 | JetStream 内存存储满导致消息拒绝；RAFT 快照/压缩压力上升 | 进程被系统 OOM killer 终止；日志出现 `out of memory` |
| Pulsar | Broker 堆内存 Full GC 频繁；BookKeeper 直接内存不足 | 消息分发线程阻塞，`pulsar_broker_msg_*` 指标掉底 | 2.6 起引入动态 flag 可跳过 broker shutdown on OOM，但需评估风险 |
| RocketMQ | Broker 堆外内存（DirectByteBuffer）使用高；发送队列等待时间长 | `waitTimeMillsInSendQueue` 告警；CommitLog 写入抖动 | Broker 进程因堆外或堆内存不足退出 |
| Redis Stream | `used_memory` 接近 `maxmemory`；写入开始出现 `OOM command not allowed` | AOF 重写或 RDB 保存时 fork 子进程导致内存瞬间翻倍 | 客户端输出缓冲区积压，触发 `client-output-buffer-limit` 断开 |

## 3.68.3 资源模型

### 线程/进程模型

| 系统 | 进程结构 | 关键线程/调度单元 | 备注 |
| ------ | ------ | ------ | ------ |
| Kafka | 单 JVM 进程；KRaft 模式下 controller 可与 broker 合设 | `num.network.threads`（接收/发送网络请求）、`num.io.threads`（处理请求）、replica fetcher 线程、log flusher 线程 | 线程数与分区数、副本数成正比；分区过多易导致线程爆炸 |
| RabbitMQ | 单 Erlang VM 进程；集群节点间通过 Erlang 分布式链路通信 | Erlang schedulers 默认与 CPU 核心数相等；每个连接/队列对应 Erlang process | 高连接数时 Erlang process 数可达数十万，内存消耗与连接数强相关 |
| NATS | 单 `nats-server` 二进制进程（Go） | Go runtime goroutines 处理连接、路由、JetStream RAFT；单进程事件驱动模型 | 单节点可支撑百万订阅；CPU 核心数通过 GOMAXPROCS 利用 |
| Pulsar | Broker 单 JVM + BookKeeper 单 JVM（bookie）+ 可选 ZooKeeper/Oxia | Broker：netty IO 线程、topic lookup、managed ledger 线程；Bookie：journal/sync/entry 线程 | 存算分离使 broker 可快速替换；bookie 是 I/O 密集型进程 |
| RocketMQ | NameServer 单 JVM + Broker 单 JVM + Proxy 单 JVM（5.x Cluster 模式） | Broker：send/pull/query/admin 线程池；CommitLog 顺序写由 MappedFile 线程负责 | 线程池参数（`sendMessageThreadPoolNums` 等）是调优重点 |
| Redis Stream | 单 Redis server 进程 | 主线程串行执行命令；6.0+ 引入 `io-threads` 处理网络 I/O；后台 fork 子进程做 RDB/AOF 重写 | Stream 命令在主线程执行，超高并发写入会受单线程瓶颈限制 |

### 内存构成与页缓存依赖

| 系统 | 内存主要构成 | 页缓存依赖度 | 说明 |
| ------ | ------ | ------ | ------ |
| Kafka | JVM 堆（metadata、请求缓冲）+ 堆外页缓存（log segment） | **高**。读取热 segment 几乎全命中页缓存；建议裸机/大页缓存容器 | 页缓存命中率直接影响消费延迟；避免与内存密集应用混部 |
| RabbitMQ | Erlang VM 堆（消息索引、队列状态、连接状态）+ 内核页缓存 | 中。classic/quorum queue 索引在内存；stream 队列依赖页缓存 | `vm_memory_high_watermark` 默认 0.4/0.5；quorum queue 可 offload 到磁盘 |
| NATS | 进程内存（连接、订阅、JetStream 元数据）+ 文件系统缓存（JetStream file store） | 中。JetStream file store 依赖 OS 页缓存；memory store 全在进程内存 | 设置 `GOMEMLIMIT` 与 `jetstream.max_memory_store` 防止 OOM |
| Pulsar | Broker JVM 堆 + BookKeeper JVM 堆/直接内存 + OS 页缓存 | 高。Bookie 读 ledger 严重依赖页缓存；broker 缓存消息与元数据 | BookKeeper `dbStorage_readAheadCacheMaxSizeMb` 等参数控制内存使用 |
| RocketMQ | Broker JVM 堆 + 堆外内存（MappedFile/Netty）+ OS 页缓存 | 高。CommitLog 与 ConsumeQueue 顺序读写依赖页缓存 | 堆外内存参数 `mappedFileSizeCommitLog` 与刷盘策略影响延迟 |
| Redis Stream | 数据全部在内存；持久化时 fork 子进程共享 COW 页 | 中低。Redis 自身不依赖 OS 页缓存做热点加速，但 AOF/RDB 写盘经过缓存 | `maxmemory` 是硬上限；AOF 重写时 COW 可能导致 RSS 翻倍 |

## 3.68.4 典型观测特征

### 稳态基线形态

正常稳态下，理想曲线应满足：

- **吞吐曲线**：相对平稳，随业务流量潮汐缓慢升降，无尖刺或断崖。
- **消费 lag 曲线**：围绕业务可容忍阈值低位波动，消费速率与生产速率长期一致。
- **延迟曲线**：P50/P99 稳定，P99 与 P50 差距在可接受范围（Kafka 通常 < 100 ms，RabbitMQ 通常 < 50 ms，具体视部署而定）【估算】。
- **资源曲线**：CPU/内存/磁盘 IO 与吞吐呈线性关系，无持续增长趋势。

### 异常曲线模式图谱

```text
# 模式 1：lag 阶梯式上升（消费跟不上生产）
lag
 ^
 |      /|
 |     / |
 |    /  |
 |   /   |_____
 |  /
 +----------------> t
 判读：消费速率 < 生产速率；优先扩容消费者或排查消费逻辑阻塞。

# 模式 2：延迟尖峰后回归（瞬时资源饱和）
latency
 ^
 |       /\
 |      /  \
 |     /    \
 |____/      \____
 +----------------> t
 判读：可能是 GC、AOF 重写、log compaction、bookie journal sync 导致；偶发可接受，频发需优化。

# 模式 3：吞吐断崖式下跌（节点/分区故障）
throughput
 ^
 |_______
 |       |
 |       |
 |       |____
 +----------------> t
 判读：检查 broker/bookie/节点健康、ISR 变化、网络分区、alarm 状态。

# 模式 4：CPU/内存持续线性爬升（内存泄漏或队列无限增长）
memory
 ^
 |    /
 |   /
 |  /
 | /
 |/
 +----------------> t
 判读：若与消息量无关，排查连接泄漏、未确认消息堆积、循环重连；必要时重启或限流。

# 模式 5：连接数锯齿波（客户端重连风暴）
connections
 ^
 | /\ /\ /\ /\
 |/  \/  \/  \\
 +----------------> t
 判读：检查网络抖动、DNS 漂移、认证失败、负载均衡器超时；通常伴随错误率上升。

# 模式 6：lag 与 throughput 同步归零（消费者全部离线）
lag/throughput
 ^
 |    __
 |   |  |
 |___|  |__________
 |
 +----------------> t
```

以上判读需结合具体系统确认：Kafka 优先看 ISR 与 `records-lag-max`；RabbitMQ 优先看 `rabbitmq_queue_messages` 与 connection blocked 通知；NATS 优先看 `/jsz` 中 consumer ack 待处理数；Pulsar 优先看 namespace bundle  unload 与 bookie 写入延迟；RocketMQ 优先看 `rocketmq_consumer_lag` 与 Broker 发送队列；Redis Stream 优先看 `xreadgroup` 待处理条目（PEL）与主线程慢日志。

## 3.68.5 K8s 探针配置样例

以下样例展示如何根据启动序列行为配置 startup/readiness/liveness 探针。实际参数应结合集群规模与启动耗时调整。

```yaml
# Kafka broker 探针示例
startupProbe:
  tcpSocket:
    port: 9092
  failureThreshold: 30
  periodSeconds: 10
readinessProbe:
  exec:
    command:
      - sh
      - -c
      - kafka-broker-api-versions.sh --bootstrap-server localhost:9092 >/dev/null 2>&1
  periodSeconds: 10
livenessProbe:
  tcpSocket:
    port: 9092
  periodSeconds: 10
```

```yaml
# NATS server 探针示例
startupProbe:
  httpGet:
    path: /healthz
    port: 8222
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: 8222
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /healthz
    port: 8222
  periodSeconds: 10
```

```yaml
# Redis 探针示例
startupProbe:
  exec:
    command:
      - sh
      - -c
      - redis-cli PING | grep -q PONG
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  exec:
    command:
      - sh
      - -c
      - "[ \"$(redis-cli INFO | grep loading: | cut -d: -f2 | tr -d '\\r')\" = \"0\" ]"
  periodSeconds: 5
livenessProbe:
  exec:
    command: ["redis-cli", "PING"]
  periodSeconds: 10
```

探针设计原则：

1. **startupProbe 用于保护启动慢的系统**（Kafka、Pulsar、RocketMQ Broker、Redis 数据加载），避免启动期间被 liveness 误杀。
2. **readinessProbe 必须验证业务就绪**，而非仅进程存活；例如 Kafka 需能响应 metadata 请求，Redis 需完成数据加载。
3. **livenessProbe 保持轻量**，避免复杂命令消耗资源；若系统已暴露专用 health endpoint，优先使用 httpGet。
