## 3.45.1 监控需求

### 业务需求

1. **性能监控**
   - 监控消息生产速率、消费速率与端到端处理速率，确保吞吐满足业务峰值。
   - Kafka 重点跟踪 `MessagesInPerSec`、`BytesInPerSec`、`BytesOutPerSec`；RabbitMQ 跟踪 `message_stats.publish`、`message_stats.deliver`。
   - 当生产速率持续高于消费速率时，预示着即将出现积压，需要触发扩容或消费优化。

2. **健康监控**
   - 监控 Broker 进程存活、端口可达、集群元数据一致性。
   - Kafka 关注 `UnderReplicatedPartitions`、`OfflinePartitions`、`ActiveControllerCount`；RabbitMQ 关注节点状态 `rabbitmqctl status` 与镜像队列同步状态。

3. **业务监控**
   - 跟踪关键业务 topic/队列的消息量、消费进度、Consumer Lag。
   - 对订单、支付等核心链路设置业务级 SLA：端到端延迟 P99 ≤ 500 ms，lag ≤ 10000 条。
   - 监控覆盖基础设施层（CPU/内存/磁盘/网络）、中间件层（Broker/topic/队列/连接）、应用层（成功率/处理耗时）与用户层（消息到达延迟/丢失率）。

## 3.45.2 监控指标

### 吞吐量指标

| 指标名称 | 来源 | 含义 | 建议告警阈值 |
| --------- | ------ | ------ | ------------- |
| MessagesInPerSec | Kafka JMX | Broker 每秒接收消息数 | 低于基线 50% 持续 5 min |
| BytesInPerSec / BytesOutPerSec | Kafka JMX | 每秒写入/读出字节数 | 超过带宽 70% |
| publish / deliver | RabbitMQ API | 每秒发布/投递消息数 | 低于基线 50% 持续 5 min |
| msgs_received / msgs_sent | NATS /varz | 每秒接收/发送消息数 | 低于基线 50% 持续 5 min |
| throughput | Redis INFO | 每秒命令处理数 | 超过 capacity 80% |

- 基线应取自过去 7 天同时间段均值，避免固定阈值在业务波动期产生误报。
- 吞吐骤降可能由网络分区、磁盘满、GC 停顿或下游消费阻塞导致。

### 延迟指标

1. **生产延迟**
   - Kafka producer 侧 `record-queue-time-avg`、`request-latency-avg`。
   - 建议阈值：`alert.rule.latency.threshold=1000` ms，P99 超过 1 秒触发告警。

2. **消费延迟与端到端延迟**
   - Kafka consumer `fetch-latency-avg`、RabbitMQ `message_stats.redeliver` 增长。
   - 在消息头中写入发送时间戳，消费端计算 `now() - timestamp`；金融类场景建议 P99 ≤ 100 ms，普通日志类场景可放宽至 P99 ≤ 1 s。

### Consumer Lag 与积压

Consumer Lag 是消息监控中最关键的指标之一：

```bash
# Kafka 查看消费组 lag
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer-group
# 输出中 LAG 列表示未消费消息数
```

- Kafka 使用 Kafka Exporter 暴露 `kafka_consumer_group_lag`。
- RabbitMQ 通过管理 API 获取 `messages_ready` 与 `messages_unacknowledged`。
- NATS JetStream 使用 `nats consumer info` 查看 `AckFloor` 与 `Delivered` 差值。
- 告警阈值建议：`alert.rule.lag.threshold=10000` 条，关键业务可设置为 1000 条。

### 资源与健康指标

1. **资源指标**
   - CPU：`alert.rule.cpu.threshold=0.8`（80%）。
   - 内存：`alert.rule.memory.threshold=0.8`（80%）。
   - 磁盘：`alert.rule.disk.threshold=0.8`（80%）。
   - 网络带宽：超过物理带宽 70% 时预警。

2. **健康指标**
   - Kafka：`UnderReplicatedPartitions > 0`、`OfflinePartitions > 0`、`ActiveControllerCount != 1`。
   - RabbitMQ：`rabbitmqctl status` 中节点状态不是 `running`、镜像队列不同步。
   - NATS：`/healthz` 返回非 200、集群节点数少于配置。

## 3.45.3 可观测性三大支柱

### 指标（Metrics）

1. **Prometheus 指标**
   - 使用 JMX Exporter、Kafka Exporter、NATS Prometheus Endpoint、RabbitMQ Prometheus Plugin 采集指标。
   - 采集间隔 `prometheus.scrape.interval=15s`，数据保留 `prometheus.retention.time=15d`。

2. **自定义与业务指标**
   - 应用埋点：业务消息数、处理成功/失败数、重试次数、端到端延迟。
   - 使用 Prometheus client library 暴露 `/metrics` 端点，按业务标签（topic、tenant、region）聚合。

### 日志（Logging）

1. **系统与应用日志**
   - Kafka：`server.log`、`controller.log`、`state-change.log`；RabbitMQ：`/var/log/rabbitmq/*.log`；Pulsar：`broker.log`、`bookkeeper.log`。
   - 生产/消费端记录消息 ID、topic、partition、offset、处理结果、异常堆栈；生产环境建议 INFO 级别。

2. **日志收集与分析**
   - 使用 ELK（Elasticsearch + Logstash + Kibana）或 Loki + Grafana 收集。
   - 日志保留 `monitor.retention.logs.days=7`，审计日志可延长至 90 天。

### 追踪（Tracing）

1. **分布式追踪**
   - 使用 OpenTelemetry 或 Jaeger 在 producer、broker、consumer 之间传递 trace context。
   - Kafka 消息头中注入 `traceparent`，消费端提取后延续链路。

2. **消息与性能追踪**
   - 记录消息从生产到消费的完整路径：produce time → broker receive → partition assign → consumer poll → process complete。
   - 对每个处理阶段记录 span，识别瓶颈阶段；采样率 `monitor.sample.rate=1.0` 适合低流量关键链路，高流量可降至 0.1。

## 3.45.4 监控工具与配置

以下端口、保留时长、阈值等参数与 `topics/config-templates/monitor-config.properties` 中的键值对应。

### Prometheus 采集配置

仓库模板已提供各系统 scrape 配置，直接复用即可：

```yaml
# topics/config-templates/prometheus-kafka.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'kafka'
    static_configs:
      - targets: ['localhost:9999']
    metrics_path: '/metrics'
  - job_name: 'kafka-exporter'
    static_configs:
      - targets: ['localhost:9308']
    metrics_path: '/metrics'
```

- Kafka JMX Exporter 端口 9999，Kafka Exporter 端口 9308（对应 `kafka.exporter.port=9308`）。
- NATS 监控端口 8222，`metrics_path: '/varz'`（见 `prometheus-nats.yml`）。
- RabbitMQ Prometheus Plugin 端口 15692（见 `prometheus-rabbitmq.yml`）。

### Grafana 仪表板

1. **关键面板**
   - 吞吐量趋势：MessagesIn/Out PerSec；Consumer Lag：按 group、topic、partition 展示。
   - 延迟分布：P50/P95/P99 端到端延迟；资源使用：CPU、内存、磁盘、网络；健康状态：UnderReplicatedPartitions、节点在线数。

2. **模板变量**
   - 使用 `cluster`、`broker`、`topic`、`consumer_group` 变量实现多环境切换，刷新间隔 `dashboard.refresh.interval=30s`。

### 告警规则示例

```yaml
# /etc/prometheus/alert_rules.yml
groups:
  - name: kafka-alerts
    rules:
      - alert: KafkaConsumerLagHigh
        expr: kafka_consumer_group_lag > 10000
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Kafka consumer lag 过高"
          description: "Consumer group {{ $labels.group }} 在 topic {{ $labels.topic }} 的 lag 为 {{ $value }}"

      - alert: KafkaUnderReplicatedPartitions
        expr: kafka_server_replica_manager_under_replicated_partitions > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Kafka 存在未同步分区"

      - alert: MessageLatencyP99High
        expr: histogram_quantile(0.99, rate(message_latency_seconds_bucket[5m])) > 1
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "消息端到端延迟 P99 超过 1 秒"

      - alert: DiskUsageHigh
        expr: (node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.2
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "磁盘使用率超过 80%"
```

- 告警通知渠道配置 `alert.notification.channels=email,dingtalk,wechat`，通过 Alertmanager 路由。
- 告警规则文件路径 `alert.rules.file=/etc/prometheus/alert_rules.yml`。

### 工具选型对比

| 工具 | 负责支柱 | 适用场景 | 关键配置项 |
| ----- | --------- | --------- | ----------- |
| Prometheus | Metrics | 时序指标采集与告警 | `scrape_interval=15s`、`retention=15d` |
| Grafana | Metrics / Logs | 可视化仪表板 | `refresh=30s`、数据源指向 Prometheus/Loki |
| ELK / Loki | Logs | 日志聚合与检索 | `retention.logs.days=7` |
| Jaeger / OTel | Traces | 分布式链路追踪 | `sample.rate=1.0` |
| Kafka Exporter | Metrics | Kafka consumer lag 等指标 | `port=9308` |
| RabbitMQ Prometheus Plugin | Metrics | RabbitMQ 原生指标 | `port=15692` |
| NATS /varz | Metrics | NATS 运行状态 | `port=8222` |

## 3.45.5 监控检查清单

### 实施前

- [ ] 明确监控需求：性能、健康、业务三大维度，列出关键 topic/队列与消费组。
- [ ] 定义指标基线与告警阈值：`alert.rule.lag.threshold=10000`、`alert.rule.latency.threshold=1000`、`alert.rule.error_rate.threshold=0.01`。
- [ ] 选择监控栈：Prometheus + Grafana + Alertmanager 作为指标与告警核心，ELK/Loki 负责日志，Jaeger/OTel 负责追踪。
- [ ] 确认各系统 exporter 端口与账号：Kafka Exporter 9308、RabbitMQ 15692、NATS 8222、Redis 9121。
- [ ] 规划数据保留：`monitor.retention.metrics.days=30`、`monitor.retention.logs.days=7`、`monitor.retention.traces.days=3`。

### 实施中

- [ ] 部署 Prometheus 并加载 `prometheus-kafka.yml`、`prometheus-nats.yml`、`prometheus-rabbitmq.yml`。
- [ ] 部署 Kafka Exporter、RabbitMQ Prometheus Plugin、NATS 监控端口，验证 `/metrics` 可访问。
- [ ] 配置应用端 `/metrics` 暴露自定义指标：端到端延迟 histogram、业务消息数 counter、失败数 counter。
- [ ] 导入 Grafana 仪表板，面板覆盖吞吐、lag、延迟、资源、健康五大类。
- [ ] 编写 `alert_rules.yml`，配置 lag、延迟、错误率、资源、健康五类告警规则。
- [ ] 接入日志收集：Filebeat/Fluent Bit 采集 Kafka/RabbitMQ/应用日志到 ELK 或 Loki。
- [ ] 接入分布式追踪：producer 注入 trace context，consumer 提取并延续 span。

### 实施后

- [ ] 每日检查 Consumer Lag 趋势，确认无持续增长。
- [ ] 每周 review 告警命中率与误报率，优化阈值与抑制规则。
- [ ] 每月验证 Grafana 仪表板数据完整性与告警通道可用性。
- [ ] 每季度进行一次故障演练：模拟 broker 宕机、磁盘满、网络分区，验证监控发现与告警时效。
- [ ] 持续优化采样率与聚合规则，控制监控存储成本：`monitor.compression.enabled=true`、`monitor.aggregation.enabled=true`。
