## 3.62.1 数据治理需求

消息数据治理需求应覆盖数据质量管理、数据生命周期管理、数据合规管理三类。数据质量管理要求验证消息完整性、准确性、一致性；数据生命周期管理要求对消息创建、存储、使用、归档、销毁全过程进行策略控制；数据合规管理要求满足隐私保护、安全加密、审计追溯等法规与内部规范。

参考 `topics/config-templates/data-governance-config.properties`，Schema 管理启用 `data.governance.schema.enabled=true`，数据质量启用 `data.governance.quality.enabled=true`，数据生命周期启用 `data.governance.lifecycle.enabled=true`，合规审计启用 `data.governance.compliance.audit.enabled=true`。

## 3.62.2 数据治理策略

### 3.62.2.1 Schema 管理策略

所有业务消息必须通过 Schema Registry 注册 Schema，URL 配置为 `data.governance.schema.registry.url=http://localhost:8081`。兼容性策略设置为 `data.governance.schema.registry.compatibility.level=backward`，支持向后兼容演进。启用 `data.governance.schema.version.management.enabled=true` 与 `data.governance.schema.validation.enabled=true`，禁止未注册 Schema 的消息进入队列。

### 3.62.2.2 数据质量策略

数据质量检查包括 Schema 校验、业务规则校验、完整性校验。`data.governance.quality.validation.business.rules.enabled=true` 时，需指定规则文件 `data.governance.quality.validation.business.rules.file=/etc/mq/business-rules.json`。清洗策略选择 `data.governance.quality.cleaning.strategy=auto`，异常数据进入死信队列或隔离 Topic。

### 3.62.2.3 数据生命周期策略

保留策略设置 `data.governance.lifecycle.retention.time.days=7`、`data.governance.lifecycle.retention.size.bytes=10737418240`（10GB），任一条件触发即清理。归档策略选择 `data.governance.lifecycle.archiving.strategy=tiering`，热数据保留 1 天，冷数据 30 天，归档数据 365 天。清理任务定时 `data.governance.lifecycle.cleanup.schedule=0 2 * * *` 执行。

| 治理维度 | 核心配置项 | 默认值/示例 | 负责角色 |
| --- | --- | --- | --- |
| Schema 管理 | `data.governance.schema.registry.compatibility.level` | backward | 架构师 |
| 数据质量 | `data.governance.quality.validation.business.rules.file` | `/etc/mq/business-rules.json` | 数据工程师 |
| 生命周期 | `data.governance.lifecycle.retention.time.days` | 7 | 运维工程师 |
| 合规审计 | `data.governance.compliance.audit.logging.path` | `/var/mq/audit-logs` | 安全合规 |

## 3.62.3 数据治理方法

### 3.62.3.1 元数据管理方法

元数据管理通过数据目录实现，字段包括 topic、partition、producer、consumer、schema、retention。启用 `data.governance.catalog.enabled=true`、`data.governance.catalog.metadata.management.enabled=true`、`data.governance.catalog.search.enabled=true`。数据血缘启用 `data.governance.lineage.enabled=true`，追踪生产者、消费者、转换过程。

### 3.62.3.2 数据质量检查方法

数据质量检查分为实时检查与离线检查。实时检查在消费者端或流处理任务中通过 Schema 校验与业务规则校验完成；离线检查通过定时任务扫描历史数据，计算完整性、准确性、一致性得分。监控指标配置为 `data.governance.quality.monitoring.metrics=data_completeness,data_accuracy,data_consistency`。

```bash
# 检查 Schema、数据质量、生命周期管理状态
./topics/scripts/data-governance-check.sh
```

### 3.62.3.3 生命周期管理方法

生命周期管理通过保留时间、保留大小、归档策略、定时清理四要素落地。Kafka 在 `server.properties` 中配置 `log.retention.hours=168`、`log.retention.bytes=1073741824`；NATS JetStream 在 StreamConfig 中配置 `MaxAge=7 * 24 * time.Hour`、`MaxBytes=10 * 1024 * 1024 * 1024`；RabbitMQ 在队列声明中配置 `x-message-ttl=3600000`、`x-max-length=10000`。

```properties
# Kafka 数据保留配置示例
log.retention.hours=168
log.retention.bytes=1073741824
log.segment.bytes=1073741824
```

### 3.62.3.4 合规与审计方法

数据分类启用 `data.governance.classification.enabled=true`，等级分为 public、internal、confidential、restricted。脱敏策略 `data.governance.compliance.privacy.data.masking.strategy=partial` 对机密与受限数据进行部分脱敏。传输与存储加密启用 `data.governance.compliance.security.encryption.enabled=true`，算法 `data.governance.compliance.security.encryption.algorithm=AES256`。审计日志写入 `data.governance.compliance.audit.logging.path=/var/mq/audit-logs`。

```bash
# 生成数据治理检查报告
./topics/scripts/data-governance.sh data_governance_$(date +%Y%m%d).txt
```

### 3.62.3.5 数据目录运营方法

数据目录需定期同步元数据，确保 Topic/Queue、Schema 版本、生产者、消费者、保留策略等信息准确。启用 `data.governance.catalog.search.index.enabled=true` 后，可通过关键词检索数据资产。数据血缘需覆盖消息从产生、流转、转换到消费的完整链路，便于影响分析与故障定位。

### 3.62.3.6 数据血缘追踪方法

数据血缘追踪要求在每个消息或批次中携带溯源标识，包括 producer、timestamp、schema version、transformation chain。启用 `data.governance.lineage.tracking.producer.enabled=true`、`data.governance.lineage.tracking.consumer.enabled=true`、`data.governance.lineage.tracking.transformation.enabled=true`。血缘数据可写入独立的 lineage Topic 或图数据库，支持按消息 ID 查询完整链路。

### 3.62.3.7 治理审计方法

治理审计通过 `data-governance.sh` 脚本生成检查报告，覆盖数据分类、生命周期、数据质量、数据安全四个维度。审计周期建议每月一次，重点检查：Schema 变更是否合规、保留策略是否生效、敏感数据是否加密脱敏、审计日志是否完整。审计报告需归档至少 180 天。审计结果应形成整改清单，明确责任人、完成时间与验收标准，确保治理问题闭环。

### 3.62.3.8 数据质量告警与闭环

启用 `data.governance.monitor.enabled=true` 后，监控指标包括 `schema_count`、`data_quality_score`、`data_retention_usage`、`compliance_violations`。当 `data_quality_score` 低于 `data.governance.monitor.alert.quality.score.threshold=0.8` 或出现合规违规时，触发告警通知数据负责人。告警处理需形成闭环：定位异常来源、修复数据或规则、复盘根因、更新监控阈值或业务规则文件。

### 3.62.3.9 数据治理度量指标

建立数据治理度量体系，定期评估治理成熟度。核心度量指标包括 Schema 注册覆盖率、数据质量平均分、生命周期清理成功率、合规审计通过率、血缘完整率。建议每月生成治理评分报告，对低于目标值的维度制定改进计划。

| 度量指标 | 计算方式 | 目标值 | 采集周期 |
| --- | --- | --- | --- |
| Schema 注册覆盖率 | 已注册 Schema 的 Topic 数 / 总 Topic 数 | 100% | 实时 |
| 数据质量平均分 | (完整性+准确性+一致性) / 3 | ≥ 0.8 | 每小时 |
| 生命周期清理成功率 | 成功清理任务数 / 总任务数 | ≥ 99% | 每日 |
| 合规审计通过率 | 通过审计项 / 总审计项 | 100% | 每月 |
| 血缘完整率 | 已追踪链路的消息数 / 总消息数 | ≥ 95% | 每日 |

## 3.62.4 各系统数据治理落地

### 3.62.4.1 Kafka

Kafka 数据治理通过 Confluent Schema Registry 管理 Schema，设置兼容性 `backward`。在 `server.properties` 中配置 `log.retention.hours=168`、`log.retention.bytes=1073741824`。使用 Kafka Streams 或 Kafka Connect 进行数据质量校验，异常数据写入死信 Topic `*.dlq`。启用 TLS/SSL 传输加密与 ACL 访问控制。

### 3.62.4.2 NATS

NATS JetStream 数据治理通过 StreamConfig 控制生命周期：`MaxAge=7 * 24 * time.Hour`、`MaxBytes=10 * 1024 * 1024 * 1024`、`Compression: S2Compression`。Consumer 配置 `AckPolicy: AckExplicit` 与 `MaxDeliver: 5`，失败消息进入死信 Stream。元数据通过 NATS 账户与 Stream 名称进行管理。

### 3.62.4.3 RabbitMQ

RabbitMQ 数据治理通过队列参数控制生命周期：`x-message-ttl=3600000`、`x-max-length=10000`、`x-max-length-bytes=1073741824`、`x-dead-letter-exchange=orders.dlx`。Schema 校验在发布端使用 JSON Schema 或 Protobuf 校验。敏感数据通过 TLS 传输与队列级访问控制保护。

### 3.62.4.4 Redis Stream

Redis Stream 数据治理通过 `XADD` 时的 `MAXLEN` 参数或定时 `XTRIM` 控制长度。使用 Redis 键空间通知监听消息过期事件。对敏感字段在写入前进行脱敏，传输启用 TLS。定期执行 `BGSAVE` 或 AOF 重写，确保持久化文件大小可控。

### 3.62.4.5 通用落地检查

无论使用哪种消息队列，落地数据治理时均需检查以下共性项：是否启用传输加密、是否配置访问控制、是否设置保留策略、是否建立死信队列、是否开启审计日志。建议每季度使用 `data-governance-check.sh` 执行一次全面检查，并将结果与历史报告对比，识别治理退化。

## 3.62.5 最佳实践

1. **Schema 先行**：新建 Topic/Queue 前必须先注册 Schema，并设置兼容性策略为 backward 或 full，避免生产消费双方解析失败。
2. **质量分数化**：将 `data_completeness`、`data_accuracy`、`data_consistency` 汇总为 0–1 质量分，设置告警阈值 `data.governance.monitor.alert.quality.score.threshold=0.8`。
3. **生命周期自动化**：保留时间与大小双阈值控制，配合 `0 2 * * *` 定时清理，避免存储无限增长。
4. **敏感数据分级**：根据 public/internal/confidential/restricted 四级分类实施差异化加密、脱敏、访问控制。
5. **审计可追溯**：所有 Schema 变更、配置变更、数据清理操作写入审计日志，保留时间不少于 180 天。
6. **治理度量常态化**：每月发布治理评分报告，针对未达标项制定改进计划并跟踪闭环。
7. **跨团队协作**：架构师、数据工程师、运维工程师、安全合规共同维护治理规则，避免单一团队承担全部治理责任。
