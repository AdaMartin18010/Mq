## 3.24.1 架构设计最佳实践

### 设计原则

1. **高可用设计**
   - 生产环境至少 3 个节点，避免单点故障
   - 关键 Topic/Queue 配置多副本（Kafka `replication.factor=3`）
   - 跨机架/可用区部署，故障自动转移

2. **可扩展设计**
   - 水平扩展优先，避免单节点性能瓶颈
   - 分区/分片设计匹配消费并行度
   - 使用负载均衡或客户端多地址发现

3. **容错设计**
   - 故障隔离：按业务域拆分集群或命名空间
   - 降级策略：失败时切换备用通道或缓存
   - 重试机制：配置指数退避与死信队列

### 架构模式选择

| 场景 | 推荐模式 | 关键参数 | 风险点 |
| ------ | --------- | --------- | -------- |
| **高吞吐日志流** | Kafka 分区集群 | `batch.size=32768`、`acks=1` | 单分区热点 |
| **低延迟事件总线** | NATS Core 集群 | `max_payload=8MB` | 无持久化，消息可能丢失 |
| **可靠任务队列** | RabbitMQ 镜像队列 | `ha-mode=all` | 镜像同步延迟 |
| **IoT 设备接入** | MQTT Broker 主从 | `keepalive=60s` | 会话风暴 |

## 3.24.2 性能优化最佳实践

### 优化策略

1. **批量操作**
   - Producer 批量发送：增大 `batch.size` 与 `linger.ms`
   - Consumer 批量拉取：提高 `max.poll.records` 或 `prefetch_count`
   - 减少网络往返，提高吞吐

2. **压缩优化**
   - 启用压缩（LZ4/Snappy），降低网络与存储开销
   - 在 CPU 敏感场景优先选 Snappy，压缩比优先选 gzip

3. **连接复用**
   - 使用连接池管理长连接
   - 配置合理的连接超时与空闲清理策略

### 配置模板引用

项目提供通用性能调优模板 [`topics/config-templates/performance-tune-config.properties`](../config-templates/performance-tune-config.properties)，核心参数如下：

```properties
# 生产者批量与压缩
performance.tune.producer.batch.size=32768
performance.tune.producer.linger.ms=10
performance.tune.producer.compression.type=snappy
performance.tune.producer.acks=1

# 消费者批量拉取
performance.tune.consumer.fetch.min.bytes=1024
performance.tune.consumer.fetch.max.wait.ms=100
performance.tune.consumer.max.poll.records=500
performance.tune.consumer.prefetch.count=100

# 分区与并发
performance.tune.partition.count=10
performance.tune.partition.replication.factor=3
performance.tune.concurrency.consumer.threads=10
```

## 3.24.3 运维管理最佳实践

### 监控告警

1. **关键指标监控**
   - 吞吐量（msg/s）
   - 延迟 P50/P95/P99
   - 错误率与消费积压
   - CPU/内存/磁盘/网络资源使用

2. **告警设置**
   - 阈值基于历史基线，避免噪声
   - 分级告警：P0/P1/P2
   - 每条告警必须附带 runbook 链接

参考项目告警规则模板 [`topics/config-templates/prometheus-alert-rules.yml`](../config-templates/prometheus-alert-rules.yml)：

```yaml
groups:
- name: kafka-warning
  rules:
  - alert: KafkaConsumerLagHigh
    expr: max by (consumergroup, topic) (kafka_consumergroup_lag) > 100000
    for: 15m
    labels: {severity: p2, system: kafka}
    annotations:
      summary: "消费组 lag 超 10 万持续 15 分钟"
      runbook: "runbooks/kafka-consumer-lag.md"
```

### 容量管理

1. **容量规划**
   - 提前 3-6 个月评估增长
   - 磁盘保留 30% 余量
   - 峰值按日常 2-3 倍预留

2. **资源管理**
   - 监控使用率，CPU > 80% 触发扩容评估
   - 定期执行 `capacity-plan.sh` 检查资源瓶颈

## 3.24.4 安全最佳实践

### 安全措施

1. **认证授权**
   - 启用 SASL/PLAIN 或 mTLS 认证
   - 配置 ACL/RBAC 授权
   - 禁用匿名与默认账号（如 RabbitMQ `guest`）

2. **加密传输**
   - TLS/SSL 加密客户端与 Broker 通信
   - 证书有效期监控，90 天前提醒续期
   - 禁用 TLS 1.0/1.1 等弱协议

3. **审计日志**
   - 记录认证、配置变更、Topic 创建等操作
   - 日志集中存储，保留周期 ≥ 90 天
   - 定期审计异常访问

参考安全配置模板 [`topics/config-templates/security-enhanced-config.properties`](../config-templates/security-enhanced-config.properties)：

```properties
# Kafka SASL_SSL 示例
kafka.security.protocol=SASL_SSL
kafka.sasl.mechanism=PLAIN
kafka.authorizer.class.name=kafka.security.authorizer.AclAuthorizer
kafka.allow.everyone.if.no.acl.found=false

# 通用审计
audit.enabled=true
audit.log.file=/var/log/mq-audit.log
audit.retention.days=90
```

## 3.24.5 故障处理最佳实践

### 故障预防

1. **预防措施**
   - 定期运行健康检查脚本
   - 监控容量与关键指标
   - 变更管理：小批量灰度发布

2. **应急预案**
   - 制定故障恢复流程
   - 准备回滚方案
   - 维护应急联系人清单

### 故障处理

1. **快速响应**
   - 告警多渠道通知
   - 使用 [`topics/scripts/troubleshoot.sh`](../scripts/troubleshoot.sh) 快速定位：

```bash
# 全系统快速排查
bash topics/scripts/troubleshoot.sh all

# 单系统排查示例
bash topics/scripts/troubleshoot.sh kafka
```

1. **事后总结**
   - 故障复盘，更新 runbook
   - 改进监控与流程
   - 文档更新与团队培训

## 3.24.6 最佳实践检查清单

### 架构与性能

- [ ] 生产集群节点数 ≥ 3，关键数据副本数 ≥ 3
- [ ] 已配置跨可用区/机架部署
- [ ] Producer `batch.size` ≥ 16384，Consumer 批量拉取已启用
- [ ] 压缩已启用（snappy/lz4/gzip）
- [ ] 连接池与重连参数已配置

### 运维与安全

- [ ] 监控覆盖吞吐、延迟、错误率、资源使用四类指标
- [ ] 每条告警均含 runbook 链接
- [ ] 认证已启用，默认/匿名账号已禁用
- [ ] TLS 已启用，证书有效期 ≥ 30 天
- [ ] 审计日志已开启，保留 ≥ 90 天

### 故障与容量

- [ ] 健康检查脚本已加入定时任务（建议每 5 分钟）
- [ ] 磁盘使用率 < 75%（告警阈值）
- [ ] 应急预案与回滚方案已文档化
- [ ] 每季度执行故障演练
