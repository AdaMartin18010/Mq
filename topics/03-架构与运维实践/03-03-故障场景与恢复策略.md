## 3.3.1 Kafka典型故障场景

| 故障类型 | 影响范围 | RTO | 恢复步骤 | 架构改进 |
| ---------- | ---------- | ----- | ---------- | ---------- |
| **Broker宕机** | 部分分区不可用 | 30秒-2分钟 | 1. Controller选举新Leader<br>2. 客户端重试<br>3. 监控报警 | 增加副本因子至3，跨机架部署 |
| **Controller宕机** | 无法创建Topic/分区重分配 | 10-30秒 | 1. ZK/KRaft触发新Controller选举<br>2. 恢复元数据管理 | 启用KRaft模式（Kafka 3.0+），消除ZK依赖 |
| **ZooKeeper脑裂** | 集群不可用 | 5-30分钟 | 1. 停止所有Broker<br>2. 修复ZK集群<br>3. 重启Broker | ZK与Broker物理隔离，监控ZK延迟 |
| **磁盘满** | Broker拒绝写入 | 即时 | 1. 清理旧日志（`log.retention.ms`）<br>2. 扩容磁盘 | 设置日志保留策略，监控磁盘使用率>75%报警 |
| **分区不均衡** | 热点Broker负载高 | 无自动恢复 | 1. 手动执行分区重分配<br>2. 运行preferred-replica-election | 启用自动均衡（`auto.leader.rebalance.enable=true`） |
| **消费组重平衡风暴** | 消费暂停 | 1-5分钟 | 1. 减少消费者成员变动<br>2. 调整`session.timeout.ms` | 控制消费组规模，使用静态成员（`group.instance.id`） |

**快速检查命令**（引用 [`scripts/cluster-status.sh`](../../topics/scripts/cluster-status.sh)）：

```bash
# 检查Broker、Topic、分区概况
./topics/scripts/cluster-status.sh kafka

# 查看Under-Replicated Partitions
kafka-topics.sh --bootstrap-server localhost:9092 --describe | grep -i "under-replicated"

# 查看消费组Lag
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group <group-id>
```

## 3.3.2 MQTT典型故障场景

| 故障类型 | 影响范围 | RTO | 恢复步骤 | 架构改进 |
| ---------- | ---------- | ----- | ---------- | ---------- |
| **Broker宕机** | 所有连接断开 | 1-3分钟 | 1. 备用Broker接管<br>2. 设备重连<br>3. 会话恢复 | 共享存储+主从模式，设备端实现指数退避重连 |
| **设备重连风暴** | Broker CPU 100% | 5-10分钟 | 1. 限制连接速率<br>2. 扩容Broker<br>3. 清理僵尸会话 | 设备端随机化重连间隔，启用连接限流 |
| **主题订阅爆炸** | Broker内存溢出 | 即时 | 1. 重启Broker<br>2. 限制主题数量<br>3. 清理无效订阅 | 主题白名单策略，监控订阅数阈值 |
| **QoS2消息积压** | 消息延迟增高 | 无自动恢复 | 1. 降低QoS级别<br>2. 扩容Broker<br>3. 清理过期消息 | QoS2仅用于关键指令，普通数据用QoS0/1 |

**快速恢复命令**：

```bash
# 查看当前连接与会话（以EMQX为例）
emqx_ctl conn stats
emqx_ctl session stats

# 清理指定客户端会话
emqx_ctl session clean <clientid>
```

## 3.3.3 NATS典型故障场景

| 故障类型 | 影响范围 | RTO | 恢复步骤 | 架构改进 |
| ---------- | ---------- | ----- | ---------- | ---------- |
| **单节点宕机** | 1/N连接断开 | **0-5秒** | 客户端自动重连到其他节点 | 无需操作，自愈 |
| **网络分区** | 小集群形成 | **秒级** | Gossip协议自动检测并合并 | 配置`cluster.routes`明确网络拓扑 |
| **慢消费者** | 消息投递延迟 | 无 | 监控报警，优化消费者 | 设置`max_pending_msgs`，超过则断开 |
| **内存耗尽** | 新连接被拒绝 | 即时 | 限制最大连接数 | 配置`max_connections`，监控内存使用 |
| **JetStream磁盘满** | 流写入失败 | 即时 | 清理旧消息或扩容磁盘 | 设置`RetentionPolicy`，监控磁盘 |

**NATS集群状态检查**（引用 [`scripts/cluster-status.sh`](../../topics/scripts/cluster-status.sh)）：

```bash
# 检查NATS集群路由与连接数
./topics/scripts/cluster-status.sh nats

# 查看JetStream流状态
nats stream info <stream-name>
nats consumer info <stream-name> <consumer-name>
```

## 3.3.4 Pulsar典型故障场景

| 故障类型 | 影响范围 | RTO | 恢复步骤 | 架构改进 |
| ---------- | ---------- | ----- | ---------- | ---------- |
| **Broker宕机** | 部分Topic不可用 | 1-3分钟 | 1. 客户端自动重连到其他Broker<br>2. BookKeeper继续服务<br>3. 监控报警 | Broker无状态，可快速扩展 |
| **BookKeeper Bookie故障** | Ledger复制延迟 | 5-10分钟 | 1. BookKeeper自动检测故障Bookie<br>2. 自动重新复制Ledger到其他Bookie<br>3. 监控Ledger复制状态 | 增加Bookie副本数，跨机架部署 |
| **ZooKeeper故障** | 元数据管理不可用 | 5-30分钟 | 1. 修复ZooKeeper集群<br>2. Broker自动重连ZK<br>3. 恢复元数据服务 | ZooKeeper与Broker物理隔离，监控ZK延迟 |
| **磁盘满（BookKeeper）** | Bookie拒绝写入 | 即时 | 1. 启用分层存储卸载冷数据<br>2. 扩容磁盘<br>3. 清理旧Ledger | 设置分层存储策略，监控磁盘使用率>75%报警 |
| **Namespace配额超限** | 该Namespace拒绝写入 | 即时 | 1. 调整Namespace配额<br>2. 清理旧消息<br>3. 启用分层存储 | 设置合理的Namespace配额，监控使用率 |

**Pulsar检查命令**：

```bash
# 检查Bookie状态
pulsar-admin bookies racks-placement

# 检查Topic内部统计
pulsar-admin topics stats persistent://tenant/namespace/topic

# 检查Namespace配额
pulsar-admin namespaces get-backlog-quotas tenant/namespace
```

## 3.3.5 RabbitMQ典型故障场景

| 故障类型 | 影响范围 | RTO | 恢复步骤 | 架构改进 |
| ---------- | ---------- | ----- | ---------- | ---------- |
| **节点宕机（镜像队列）** | 队列镜像降级 | 数秒-1分钟 | 1. 剩余镜像自动提升为主队列<br>2. 重启故障节点并重新同步 | 启用镜像队列/仲裁队列（Quorum Queue），保持≥3副本 |
| **内存高水位** | 发布流控/阻塞 | 即时 | 1. 消费积压消息<br>2. 扩容内存或节点<br>3. 调整`vm_memory_high_watermark` | 监控内存使用，设置合理的水位线（默认0.4） |
| **磁盘高水位** | 发布被阻塞 | 即时 | 1. 清理日志与过期消息<br>2. 扩容磁盘 | 监控磁盘使用，设置`disk_free_limit` |
| **分区（Network Partition）** | 集群分裂 | 1-10分钟 | 1. 使用`rabbitmqctl cluster_status`诊断<br>2. 选择一侧重启或执行`forget_cluster_node` | 优先使用Federation/Shovel跨机房，避免WAN集群 |

**RabbitMQ检查命令**：

```bash
# 集群状态与分区诊断
rabbitmqctl cluster_status
rabbitmqctl quorum_status <queue>

# 列出被阻塞的连接（流控）
rabbitmqctl list_connections peer_host peer_port state blocked_reason
```

## 3.3.6 故障恢复对比矩阵

| 故障类型 | Kafka恢复时间 | MQTT恢复时间 | NATS恢复时间 | Pulsar恢复时间 | RabbitMQ恢复时间 | 自动化程度 |
| ---------- | -------------- | ------------- | ------------- | -------------- | ----------------- | ----------- |
| **节点宕机** | 30秒-2分钟 | 1-3分钟 | **0-5秒** | 1-3分钟（Broker无状态） | 数秒-1分钟（镜像队列） | NATS最高 |
| **网络分区** | 5-30分钟 | 需人工干预 | **秒级自动** | 5-10分钟（BookKeeper自动恢复） | 1-10分钟（需人工决策） | NATS自动 |
| **资源耗尽** | 需人工扩容 | 需人工扩容 | **自动限流** | 需人工扩容（但Broker和BookKeeper独立扩展） | 流控自动但需人工扩容 | NATS自动保护 |
| **配置错误** | 需滚动重启 | 需主从切换 | **热加载** | 需滚动重启（多组件） | 部分参数支持热加载 | NATS支持HUP信号 |
| **存储故障** | 需人工恢复 | 需人工恢复 | 无（无持久化） | **自动恢复**（BookKeeper自动重新复制） | 镜像队列自动恢复 | Pulsar自动恢复 |

## 3.3.7 故障恢复操作清单

以下清单用于故障发生后的标准化处置，条目可直接勾选。

- [ ] **发现**：收到P0/P1告警后，5分钟内确认受影响系统与范围
- [ ] **诊断**：运行对应检查脚本
  - Kafka：`./topics/scripts/cluster-status.sh kafka`
  - NATS：`./topics/scripts/cluster-status.sh nats`
  - RabbitMQ：`rabbitmqctl cluster_status`
  - Pulsar：`pulsar-admin broker-stats topics` 与 `bookies racks-placement`
- [ ] **止损**：对写入型故障（磁盘满/内存高水位）先触发流控或降级，避免级联失败
- [ ] **恢复**：按上节矩阵选择自动/人工恢复；优先使用 [`scripts/auto-recovery.sh`](../../topics/scripts/auto-recovery.sh)

```bash
# 自动恢复示例：对Kafka尝试最多3次自愈
./topics/scripts/auto-recovery.sh kafka 3

# 跨系统批量健康检查
./topics/scripts/health-check-all.sh
```

- [ ] **验证**：恢复后确认关键指标回归基线
  - Kafka：`UnderReplicatedPartitions == 0` 且消费Lag下降趋势
  - NATS：`/varz` 中 `connections`、`routes` 正常
  - RabbitMQ：`rabbitmqctl cluster_status` 无分区
  - Pulsar：`pulsar-admin topics stats` 中 `msgBacklog` 不再增长
- [ ] **复盘**：24小时内输出故障报告，更新 [`disaster-recovery-config.properties`](../../topics/config-templates/disaster-recovery-config.properties) 中的RTO/RPO实测值

**灾难恢复配置模板关键项**（引用 [`config-templates/disaster-recovery-config.properties`](../../topics/config-templates/disaster-recovery-config.properties)）：

```properties
# RTO/RPO目标
disaster.recovery.recovery.rto.target.hours=1
disaster.recovery.recovery.rpo.target.hours=0

# 自动切换与复制延迟阈值
disaster.recovery.switch.strategy=automatic
disaster.recovery.replication.lag.threshold.seconds=60
```

### RTO/RPO 决策矩阵

| 业务等级 | 可接受RTO | 可接受RPO | 推荐策略 | 核验命令/配置 |
| ---------- | ----------- | ----------- | ---------- | --------------- |
| **P0 核心交易** | <5分钟 | 0 | 同步复制 + 自动切换 | `disaster.recovery.replication.strategy=synchronous` |
| **P1 关键业务** | <1小时 | 分钟级 | 异步复制 + 自动切换 | `replication.lag.threshold.seconds=60` |
| **P2 普通业务** | <4小时 | 小时级 | 定期备份 + 人工切换 | `disaster.recovery.backup.frequency=hourly` |
| **P3 离线分析** | <1天 | 天级 | 日备份 + 人工恢复 | `disaster.recovery.backup.frequency=daily` |

## 3.3.8 故障预防策略

### Kafka预防策略

1. **定期健康检查**：监控ISR状态、分区分布、磁盘使用率
2. **容量规划**：提前规划分区数和副本数，避免后期调整
3. **监控告警**：设置UnderReplicatedPartitions、Controller选举等关键指标
4. **演练预案**：每季度执行 [`scripts/disaster-recovery-check.sh`](../../topics/scripts/disaster-recovery-check.sh)

### MQTT预防策略

1. **连接限流**：防止设备重连风暴
2. **主题治理**：限制主题数量和层级深度
3. **会话管理**：定期清理过期会话，避免内存泄漏
4. **网络优化**：优化KeepAlive间隔，减少假在线

### NATS预防策略

1. **资源限制**：设置`max_connections`、`max_memory`等限制
2. **慢消费者保护**：自动断开慢消费者，保护系统整体
3. **监控告警**：监控Routes数量、内存使用、SlowConsumers
4. **自动化运维**：利用K8s HPA实现自动扩缩容

### Pulsar预防策略

1. **多组件监控**：监控Broker、BookKeeper、ZooKeeper三个组件
2. **分层存储配置**：提前配置对象存储和卸载策略，避免磁盘满
3. **Namespace配额管理**：设置合理的Namespace配额，避免配额超限
4. **BookKeeper副本数**：设置足够的Bookie副本数（建议≥3），跨机架部署
5. **Broker负载均衡**：启用Broker负载均衡，避免热点Broker

### RabbitMQ预防策略

1. **队列类型升级**：新部署优先使用Quorum Queue替代经典镜像队列
2. **内存/磁盘阈值**：设置`vm_memory_high_watermark=0.4`、`disk_free_limit.absolute=2GB`
3. **分区容忍**：跨可用区部署优先使用Federation，避免跨WAN集群
4. **定期清理**：启用TTL与最大长度策略，防止队列无限增长
