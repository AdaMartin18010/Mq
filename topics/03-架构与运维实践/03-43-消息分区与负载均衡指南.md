## 3.43.1 分区数量规划

### 规划方法与阈值

分区数直接决定单 Topic 的并行度上限，但过多分区会增加文件句柄、内存与再均衡开销。落地规划时以目标吞吐、消费者实例数、历史峰值三项数据为输入，而不是凭经验拍板。

1. **吞吐倒推法**
   - 先测定单分区吞吐上限：在目标硬件上压测得到 `single_partition_tps`。
   - 目标分区数 = `目标总吞吐 / single_partition_tps`，再向上取整并预留 20% 余量。
   - 例如目标 60,000 TPS、单分区 10,000 TPS，则建议分区数 = `(60000/10000) * 1.2 = 7.2`，取 8。

2. **消费者并行度对齐**
   - Kafka 中一个分区只能被一个消费者实例消费，因此 `kafka.partition.count` 应大于等于消费者实例数。
   - 建议 `分区数 = 消费者实例数 × 1.5 ~ 2`，避免未来扩容消费者时无分区可分配。

3. **初始数量阈值**
   - 常规业务 Topic：`kafka.partition.count` 建议 6 ~ 24。
   - 高吞吐日志/埋点 Topic：可设 48 ~ 96，但需确认 `ulimit -n` 与 broker 内存足够。
   - 顺序敏感 Topic：分区数不宜过多，优先通过 `partition.key.field` 保证同一键落入同一分区。

4. **复制因子与最小同步副本**
   - 生产环境必须设置 `kafka.partition.replication.factor=3`，并配置 Topic 级 `min.insync.replicas=2`。
   - 容忍单 broker 故障的同时，保证 `acks=all` 写入不阻塞。

```properties
# 示例：分区规划配置（摘自 partition-config.properties）
kafka.partition.strategy=key-hash
kafka.partition.count=6
kafka.partition.replication.factor=3
partition.key.field=id
partition.key.hash.algorithm=md5
partition.monitor.enabled=true
partition.monitor.metrics=partition_count,partition_size,partition_lag,partition_throughput
partition.alert.enabled=true
partition.alert.imbalance.threshold=0.2
partition.alert.lag.threshold=10000
```

## 3.43.2 分区策略配置

### Kafka 分区策略

1. **Key Hash 分区**
   - 配置 `kafka.partition.strategy=key-hash`，由生产者根据 `key` 的哈希值取模选择分区。
   - 同一业务键（如 `orderId`）始终进入同一分区，天然保证分区内顺序。
   - 注意：若 Key 分布不均（如订单号前缀集中），会导致热点分区；此时可改用 `murmur2` 或自定义分区器。

2. **轮询（Round-Robin）分区**
   - 配置 `kafka.partition.strategy=round-robin`，消息无 Key 时均匀轮询到各分区。
   - 适合无顺序要求、追求最大吞吐的场景；但批量消息会按批次轮询，单条粒度仍均匀。

3. **自定义分区器**
   - 配置 `kafka.partition.custom.class=com.example.CustomPartitioner`。
   - 自定义分区器需实现 `org.apache.kafka.clients.producer.Partitioner`，按业务规则（如地区、租户）分配。
   - 部署后需在 broker 与客户端日志中确认 `partitioner.class` 已生效。

### NATS 与 RabbitMQ 应用层分区

1. **NATS 应用层分区**
   - NATS Core 无原生分区，通过 `nats.partition.strategy=subject-prefix` 实现。
   - 配置 `nats.partition.subject.pattern=orders.partition.{partition}`，将消息散列到不同 Subject。
   - JetStream 场景下使用 Stream 与多个 Consumer 实现类似 Kafka 的并行消费。

2. **RabbitMQ 应用层分区**
   - 通过多个队列实现分区，配置 `rabbitmq.partition.strategy=queue`。
   - 队列命名按模板 `orders-partition-{partition}`，生产者根据 `partition.key.field` 哈希选择队列。
   - 若使用 Quorum Queue，建议每个分区队列的 `x-quorum-initial-group-size=3`，提升可用性。

| 系统 | 原生分区机制 | 策略配置 | 负载均衡方式 | 顺序保证 |
| ------ | ------------- | --------- | ------------- | --------- |
| Kafka | Topic-Partition | `key-hash`/`round-robin`/`custom` | Consumer Group 自动再均衡 | 分区内有序 |
| NATS Core | 无 | `subject-prefix` 应用层分区 | 多个 Subscriber 或 JetStream Consumer | Subject 内有序 |
| NATS JetStream | Stream + Consumer | `stream` 配置分区数 | Consumer 自动分配 | Stream 内有序 |
| RabbitMQ | 应用层队列分区 | `queue`/`exchange`/`custom` | 多个 Queue + Consumer | 单队列内有序 |
| Pulsar | Ledger/Bundle | `hashing`/`round-robin`/`custom` | Broker 与 Subscription 自动负载均衡 | 分区内有序 |
| Redis Stream | Stream + Consumer Group | 应用层键散列 | Consumer Group 自动认领 | Stream 内按 ID 有序 |

## 3.43.3 分区再均衡

### 再均衡触发与配置

1. **触发场景**
   - 消费者加入或退出 Consumer Group。
   - Topic 分区数变更（`kafka-topics.sh --alter --partitions`）。
   - broker 上下线导致 Leader 重新选举。

2. **Kafka 再均衡参数**
   - `session.timeout.ms`：默认 10 秒，消费者心跳超时即触发再均衡。
   - `heartbeat.interval.ms`：建议为 `session.timeout.ms` 的 1/3，即 3 秒。
   - `max.poll.interval.ms`：默认 5 分钟，处理逻辑过长会被踢出 Group。
   - `partition.assignment.strategy`：可选 `RangeAssignor`、`RoundRobinAssignor`、`StickyAssignor` 或 `CooperativeStickyAssignor`；推荐使用 `CooperativeStickyAssignor` 减少再均衡停顿。

3. **扩容分区操作**
   - 只能增加分区数，不能减少；扩容前需评估历史数据是否重新分布（Kafka 不会自动迁移旧数据）。
   - 命令示例：`kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 12`。
   - 扩容后检查分区 Leader 是否均衡：`kafka-leader-election.sh --bootstrap-server localhost:9092 --election-type preferred --topic orders`。

4. **数据迁移与再平衡**
   - 当 broker 上下线导致分区倾斜时，使用 `kafka-reassign-partitions.sh` 制定迁移计划。
   - 迁移带宽由 `throttle` 控制，例如 `--throttle 50000000`（50 MB/s），避免影响生产流量。
   - 完成迁移后执行 `--verify` 确认所有分区 ISR 完整。

```bash
# 示例：扩容分区并执行 Leader 再均衡
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 12

kafka-leader-election.sh --bootstrap-server localhost:9092 \
  --election-type preferred --topic orders

# 示例：运行分区配置检查脚本
bash topics/scripts/partition-check.sh
```

## 3.43.4 跨系统负载均衡策略

### 消息均衡与消费者均衡

1. **消息数量均衡**
   - 目标：各分区消息数差异不超过 `partition.alert.imbalance.threshold=0.2`（20%）。
   - 监控指标 `partition_size` 与 `partition_throughput`，发现热点分区时检查 Key 分布或切换分区策略。
   - 若使用 Key Hash，定期抽样 Key 的 MD5/SHA1 分布，确认无明显倾斜。

2. **消费者负载均衡**
   - Kafka Consumer Group 通过协调器自动分配分区；当消费者数量变化时触发再均衡。
   - RabbitMQ 中通过 `rabbitmq.partition.count` 个队列与同等数量消费者实现均衡，避免单个队列消费者过多。
   - NATS JetStream 中，Consumer 数量建议不超过 `nats.partition.count`，多余消费者会空闲。

3. **资源均衡**
   - 监控 broker/节点 CPU、内存、网络带宽，确认没有节点长期高于 80%。
   - Kafka 中利用 Cruise Control 或 `kafka-reassign-partitions.sh` 定期进行集群级再平衡。
   - Pulsar 通过 Load Manager 自动卸载高负载 Broker 上的 Bundle；Redis Stream 通过 `XINFO GROUPS` 观察待处理条目（PEL）长度。

4. **负载均衡策略选择**
   - `load.balance.strategy=round-robin`：默认轮询，适合请求同质化场景。
   - `load.balance.strategy=least-connections`：按连接数最少分配，适合长连接差异大。
   - `load.balance.strategy=weighted`：按节点权重分配，适合异构硬件。
   - 配置 `load.balance.enabled=true` 与 `load.balance.monitor.enabled=true` 后，需接入告警通道 `partition.alert.channels=email,dingtalk`。

## 3.43.5 分区检查清单

### 实施前

- [ ] 完成分区需求分析：顺序要求、目标吞吐、峰值 TPS、消费者并发数。
- [ ] 确定 `kafka.partition.strategy`（`key-hash`/`round-robin`/`custom`）与 `nats.partition.strategy`/`rabbitmq.partition.strategy`。
- [ ] 规划 `kafka.partition.count`/`nats.partition.count`/`rabbitmq.partition.count`，并确认大于等于消费者实例数。
- [ ] 设定 `partition.alert.imbalance.threshold=0.2` 与 `partition.alert.lag.threshold=10000` 告警阈值。
- [ ] 确认 `kafka.partition.replication.factor=3` 与 `min.insync.replicas=2`，保障高可用。
- [ ] 选择 `partition.key.field` 与 `partition.key.hash.algorithm`（`md5`/`sha1`/`sha256`），避免热点 Key。

### 实施中

- [ ] 创建 Topic 时显式指定分区数与复制因子：`kafka-topics.sh --create --topic orders --partitions 6 --replication-factor 3`。
- [ ] 配置生产者分区键；无顺序要求时启用 `round-robin`，顺序要求时启用 `key-hash`。
- [ ] 配置消费者 `partition.assignment.strategy`，推荐 `CooperativeStickyAssignor`。
- [ ] 部署分区监控：`partition.monitor.enabled=true`，采集 `partition_count`、`partition_size`、`partition_lag`、`partition_throughput`。
- [ ] 配置负载均衡：`load.balance.enabled=true`、`load.balance.strategy=round-robin`、`load.balance.monitor.enabled=true`。
- [ ] 扩容分区时执行 `--alter --partitions`，随后执行 `kafka-leader-election.sh` 均衡 Leader。

### 实施后

- [ ] 验证各分区消息量差异是否低于 `partition.alert.imbalance.threshold=0.2`。
- [ ] 验证消费者 lag 是否低于 `partition.alert.lag.threshold=10000`。
- [ ] 执行 `topics/scripts/partition-check.sh`，检查 Kafka 分区数、NATS Subject、RabbitMQ 分区队列状态。
- [ ] 进行故障演练：停掉一个 broker/consumer，观察再均衡时间与消息堆积恢复情况。
- [ ] 压测验证：目标吞吐下 CPU、网络、磁盘无瓶颈，再均衡期间无显著延迟毛刺。
- [ ] 建立定期审计：每月评估分区数是否满足业务增长，必要时提前规划扩容。
