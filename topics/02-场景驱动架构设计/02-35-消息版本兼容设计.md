### 版本管理

```java
// Schema Registry版本管理
// 注册Schema
Schema schema = new Schema.Parser().parse(schemaString);
SchemaRegistryClient client = new CachedSchemaRegistryClient(
    "http://localhost:8081", 100
);
int schemaId = client.register("orders-value", schema);

// 兼容性检查
CompatibilityLevel level = client.getCompatibility("orders-value");
// BACKWARD, FORWARD, FULL, NONE

// 版本化消息
ProducerRecord<String, GenericRecord> record = new ProducerRecord<>(
    "orders",
    key,
    new GenericRecordBuilder(schema)
        .set("version", "1.0")
        .set("orderId", orderId)
        .build()
);
```

## 2.35.3 NATS版本兼容

### 版本管理

```go
// 消息版本管理
type MessageV1 struct {
    Version string `json:"version"`
    OrderID string `json:"orderId"`
}

type MessageV2 struct {
    Version string `json:"version"`
    OrderID string `json:"orderId"`
    Timestamp int64 `json:"timestamp"`
}

// 版本路由
nc.Subscribe("orders.*", func(msg *nats.Msg) {
    version := extractVersion(msg.Data)
    switch version {
    case "1.0":
        processV1(msg.Data)
    case "2.0":
        processV2(msg.Data)
    default:
        processDefault(msg.Data)
    }
})
```

## 2.35.4 RabbitMQ版本兼容

### 版本管理

```python
# 消息版本管理
def process_message(ch, method, properties, body):
    message = json.loads(body)
    version = message.get('version', '1.0')

    if version == '1.0':
        process_v1(message)
    elif version == '2.0':
        process_v2(message)
    else:
        process_default(message)

    ch.basic_ack(delivery_tag=method.delivery_tag)

# 版本化消息
message = {
    'version': '2.0',
    'orderId': order_id,
    'timestamp': int(time.time())
}
channel.basic_publish(
    exchange='orders',
    routing_key='',
    body=json.dumps(message)
)
```

## 2.35.6 兼容性策略与迁移决策表

【论证】Schema 兼容性策略没有绝对最优，只有与发布节奏、消费者升级能力相匹配的取舍。下表给出四种标准策略及迁移模式：

| 兼容性策略 | 含义 | 适用场景 | 风险点 |
| ------------ | ------ | ---------- | -------- |
| **BACKWARD（向后兼容）** | 新 schema 可被旧消费者读取 | 先升级服务端/生产者，消费者滞后 | 旧消费者可能忽略新增字段，导致默认值处理不一致 |
| **FORWARD（向前兼容）** | 旧 schema 可被新消费者读取 | 先升级消费者，生产者滞后 | 新消费者需为缺失字段提供默认值 |
| **FULL（全兼容）** | 同时满足 backward + forward | 双向独立滚动升级 | 限制最大，禁止删除/重命名字段 |
| **NONE（无兼容）** | 每次变更都视为新 schema | 完全可控的内聚系统 | 需要强制的版本切换窗口 |

迁移模式决策：

| 模式 | 机制 | 停机要求 | 推荐场景 |
| ------ | ------ | ---------- | ---------- |
| **双写共存** | 新旧版本同时生产，消费者按能力选择 | 零停机 | 核心交易链路，无法承担切换风险 |
| **流量灰度** | 按百分比逐步切到新版本 | 零停机 | 互联网业务，具备快速回滚能力 |
| **停机切换** | 维护窗口内统一升级 | 需要停机 | 小规模内部系统 |
| **Schema 别名** | 通过别名字段保持旧名可读 | 零停机 | 字段重命名等“伪破坏性”变更 |

### 版本兼容配置示例

`config-templates/version-compat-config.properties` 中的关键参数：

```properties
# Schema Registry配置
schema.registry.enabled=true
schema.registry.url=http://localhost:8081
schema.registry.compatibility.level=backward
schema.registry.compatibility.check.enabled=true

# 版本管理配置
version.management.enabled=true
version.format=semantic
version.header.name=message-version
version.header.required=true

# 兼容性策略配置
compatibility.strategy=backward
compatibility.forward.enabled=true
compatibility.forward.new.fields.optional=true
compatibility.forward.field.deletion.allowed=false
compatibility.backward.enabled=true
compatibility.backward.old.version.support=true
compatibility.backward.downgrade.enabled=true

# 迁移策略配置
migration.strategy=gradual
migration.gradual.enabled=true
migration.gradual.dual.write.enabled=true
migration.gradual.switch.percentage=10
migration.coexistence.enabled=false
migration.coexistence.max.versions=3
```

## 2.35.7 契约版本治理与跨域对齐

版本兼容不能仅停留在 schema 层面，还需要纳入事件契约治理。【论证】在跨团队、跨产业域的场景下，建议把版本信息写入契约的六层结构（metadata / header / payload / error / compatibility / binding），参见 [2.54 事件契约模板库与命名规范](02-54-事件契约模板库与命名规范.md)。

跨域版本对齐要点：

1. **产业标准字段映射**：ISO 20022、FHIR、EPCIS 等标准本身有版本号（如 `BusinessMessageDefinition` 的版本），桥接到 CloudEvents 时应放入 `datacontenttype` 与自定义 `specversion` 扩展属性中，参考 [1.45 产业领域消息标准纵览](../01-基础概念与对比分析/01-45-产业领域消息标准纵览.md)。
2. **IoT/互联网域状态机事件**：订单、设备等实体状态机事件需要版本与状态字段共同路由，见 [1.46 IoT 与互联网领域消息标准纵览](../01-基础概念与对比分析/01-46-IoT与互联网领域消息标准纵览.md)。
3. **Serverless 函数载荷版本**：函数计算对事件结构敏感，版本切换需同步更新函数触发器与反序列化逻辑，参考 [1.48 Serverless 事件架构与函数消息](../01-基础概念与对比分析/01-48-Serverless事件架构与函数消息.md)。

版本降级与兼容性监控：

| 监控项 | 阈值 | 处理动作 |
| -------- | ------ | ---------- |
| 兼容性错误率 | > 1% | 触发自动降级或告警 |
| 多版本共存数 | > 3 | 推进版本收敛 |
| 灰度切换比例 | 按阶梯 10%→50%→100% | 每阶段观察错误率与延迟 |
