## 2.48.1 契约设计的核心问题

事件驱动系统的隐性成本在于**契约的隐性**：生产者和消费者对消息格式的理解若只靠口头与代码，演进时必然产生"静默破坏"（消费端按旧格式解析新消息）【论证】。契约设计要解决的三个问题：

1. **描述**：消息格式、通道、语义（AsyncAPI 的文档层）
2. **治理**：谁有权改、改了谁审批、如何发现破坏（流程 + Diff 工具层）
3. **兑现**：契约与代码的一致性如何保证（生成/校验层）

三个问题缺一则契约沦为文档摆设：只描述不治理 → 契约过期；只治理不兑现 → 契约与实现漂移【论证】。

## 2.48.2 契约先行 vs 实现先行

| 维度 | 契约先行（design-first） | 实现先行（code-first） |
|------|--------------------------|------------------------|
| 起点 | 先写 AsyncAPI 文档并评审 | 代码注解生成文档（Springwolf/FastStream 等） |
| 适用 | 多团队、契约是协作界面 | 单团队快速迭代、原型期 |
| 一致性保证 | 生成代码 + CI 校验 | 生成文档 + 评审发布 |
| 风险 | 设计脱离实现细节 | 文档随实现漂移、契约视角缺失 |
| 组合用法 | 核心对外契约先行，内部 topic 实现先行 | 两者用 Diff 互为校验 |

选型建议【论证】：跨团队消息链路（如订单事件被 3 个以上下游消费）一律契约先行；团队内部实现细节 topic 允许实现先行，但需纳入同一文档仓库统一治理。

## 2.48.3 设计工作流六步

```text
1 建模: 识别事件/命令/查询三类消息 → 定义 channel 命名规范
2 描述: 写 AsyncAPI 文档（模板见 config-templates/asyncapi-kafka-example.yaml）
3 校验: asyncapi validate + Spectral lint（规则集见 config-templates）
4 评审: PR 评审（清单见 2.48.6）→ 通过后合并入契约仓库
5 发布: bundle 为单一文档 → 生成交互文档挂门户 → 版本打 tag
6 兑现: Modelina 生成模型接入代码；CI 用 Diff 拦截破坏性变更
```

每步的产出物与责任：

| 步 | 产出物 | 责任方 |
|----|--------|--------|
| 1 | 消息分类表 + channel 规范 | 架构/设计 |
| 2 | AsyncAPI 文档 PR | 消息生产者团队 |
| 3 | 校验通过记录 | 提交者（本地+CI 双重） |
| 4 | 评审意见与批准 | 契约 owner + 消费方代表 |
| 5 | 版本化文档 + 门户链接 | 平台/治理 |
| 6 | 生成代码 + 契约一致性报告 | 各实现团队 |

关键设计决策点【论证】：
- **channel 命名**：`<域>.<实体>.<事件类型>`（如 `orders.order.created`），与 02-12 路由策略的 subject/topic 规范对齐。
- **schema 归属**：payload schema 优先放 components.messages，跨 channel 复用走 components.schemas。
- **绑定声明**：每个 channel 必须显式声明 broker 绑定（kafka/mqtt），绑定版本与 broker 版本对应关系需在文档库 README 维护。

契约仓库的推荐目录结构（治理载体）：

```text
contracts/
├── asyncapi/                  # 按域分包
│   ├── orders/
│   │   ├── asyncapi.yaml      # 域内全部 channel
│   │   └── schemas/           # 可拆分 schema（bundle 时合并）
│   └── sensors/
├── .spectral.yaml             # 治理规则集（引用 config-templates 模板）
└── README.md                  # 命名规范、绑定版本对照、评审人清单
```

评审角色（RACI 简化【论证】）：

| 角色 | 职责 |
|------|------|
| 生产者团队 | 起草契约（R）、修正评审意见（R） |
| 契约 owner | 评审组织与批准（A）、命名规范裁决 |
| 消费方代表 | 兼容性影响评审（C→必须意见） |
| 平台组 | 门户发布、工具链维护（R） |

## 2.48.4 版本治理与兼容性

契约版本与消息版本的关系：契约版本管"文档的演化"，消息版本管"线上消息的兼容性"，两者通过 schema 的兼容性规则连接【论证】。

| 变更类型 | 消息 schema | 契约文档 | 治理动作 |
|----------|-------------|----------|----------|
| 加可选字段 | 向后兼容 | minor | 直接合并，通知消费方 |
| 加必填字段 | 破坏旧消费方 | major | 评审 + 双写过渡期（见 02-35） |
| 删字段/改类型 | 破坏 | major | 评审 + AsyncAPI Diff 报告留档 |
| 加 channel/message | 无影响 | minor | 直接合并 |
| 删 channel/message | 破坏 | major | 评审 + 下线公告期 |

与 02-35 版本兼容设计的衔接：schema 演进规则（可选字段优先、字段重命名=新增+废弃）在消息层执行；契约层额外要求"删除走公告期"——因为契约是发现入口，删除通道意味着宣告能力下线【论证】。

**公告期流程（删除 channel/message 的强制路径）**：

1. Diff 报告标注破坏性变更（CI 自动产出）
2. 契约 PR 附《下线公告》：影响消费方清单、替代通道、公告期时长
3. 公告期内旧通道保持可用（双通道并行期）
4. 公告期结束且无活跃消费 → 删除并打 major tag
5. 门户发布变更日志

常见反模式与纠正：

| 反模式 | 后果 | 纠正 |
|--------|------|------|
| 契约只描述 happy path，无 DLQ/retry 通道 | 消费者无从得知失败语义 | 死信/重试通道显式建模（config-templates 模板已含） |
| payload 直接内联在 channel 下 | 重复定义、演进发散 | 收敛到 components 复用 |
| 契约与实现各改各的 | 漂移、联调爆雷 | 双向校验：生成代码 CI 核对 + 框架生成文档与契约 Diff |
| 无 Spectral 规则或规则过松 | 低质量文档入库 | error 级规则最少 3 条（payload/binding/trace-id） |

## 2.48.5 与项目设计模式的衔接

| 模式 | 契约中的表达 |
|------|--------------|
| 02-12 消息路由 | channel 命名与绑定参数 |
| 02-14 消息去重 | header 中的 dedup-key 属性（User Properties / record header） |
| 02-16 消息重试 / 02-17 死信 | 重试 topic 与 DLQ channel 显式建模为独立 channel |
| 02-25 消息幂等 | payload 幂等键 + 文档中的消费语义说明 |
| 02-26 序列化 / 02-35 版本兼容 | payload schema 与兼容性规则 |
| 02-23 消息追踪 | header 中的 trace-id（契约中列为必填 header） |

衔接价值：契约文档成为模式的"可执行索引"——新人从门户文档即可看到 DLQ channel、幂等键、追踪头的存在与语义，不必翻设计文档【论证】。

## 2.48.6 检查清单

契约评审（PR 必查）：
- [ ] 每个 message 有 payload schema（Spectral error 级规则强制）
- [ ] 每个 channel 声明了 broker 绑定（kafka/mqtt/amqp）与对应版本
- [ ] 删除/修改既有 channel 或 message 时附 AsyncAPI Diff 报告
- [ ] 破坏性 schema 变更附双写/迁移方案（衔接 02-35）
- [ ] 追踪头（trace-id）与幂等键在 header 中显式声明
- [ ] 文档通过 `asyncapi validate` + Spectral lint 0 error

治理运行（月度）：
- [ ] 契约仓库全部文档可 validate、bundle 无报错
- [ ] 门户文档与最新 tag 同步
- [ ] 契约覆盖的核心链路清单已更新（与 TEST-03 契约用例对账）

治理对账的快速命令（月度检查脚本化）：

```bash
# 全量校验
for f in contracts/asyncapi/*/*.yaml; do asyncapi validate "$f" || echo "FAIL $f"; done
# 全量 lint（error 即阻断）
spectral lint "contracts/asyncapi/**/*.yaml" --ruleset .spectral.yaml
# 与上一 tag 的破坏性变更扫描
git tag --sort=-creatordate | head -2   # 取最近两个 tag
asyncapi diff "contracts@$(git tag --sort=-creatordate | sed -n 2p)" "contracts" 2>/dev/null || true
```

度量指标（治理健康度，纳入月度回顾）：

| 指标 | 目标 | 采集 |
|------|------|------|
| 契约 validate 通过率 | 100% | CI 每日 |
| Spectral error 数 | 0 | CI 每次提交 |
| 契约覆盖核心链路比例 | ≥ 80%【估算，按业务定】 | 链路清单对账 |
| 破坏性变更评审留档率 | 100% | Diff 报告归档检查 |

契约与 Schema Registry 的关系补充【论证】：两者解决不同层的兼容——AsyncAPI 管"文档与代码"层（生成模型、评审治理），Schema Registry 管"运行时"层（注册校验、演进检查）。工程组合：契约中的 payload schema 作为注册到 Registry 的源（如 Avro JSON 从 schema 导出注册）；CI 同时跑 Spectral（文档质量）与 Registry 兼容检查（运行时兼容），双门禁缺一不可。该组合已在 TEST-03 TC-INT-01 的兼容矩阵用例中落地验证路径。
