## 2.52.1 血缘要解决什么问题

场景【论证】：schema 给 `orders` 事件加一个必填字段——**哪些下游会炸？** 契约（02-48）告诉你格式对不对，血缘告诉你影响面多大。没有血缘的团队靠"群发邮件问谁在用"，漏一个消费者就是一次事故。

血缘的核心查询【论证】：① 上游变更 → 下游清单（影响分析）；② 下游故障 → 上游溯源（根因定位）；③ 数据合规 → PII 流向图（02-50 的索引）；④ 闲置识别 → 无消费者 topic（成本治理，03-65 衔接）。

## 2.52.2 血缘模型：三档精度

| 档 | 粒度 | 数据 | 成本 | 适用 |
| ---- | ------ | ------ | ------ | ------ |
| L1 topic 级 | topic → 消费者组/服务 | 消费者组注册+订阅关系 | 低 | 起步必备 |
| L2 字段级 | schema 字段 → 下游引用字段 | 解析消费代码的字段引用 | 中 | 高频变更域 |
| L3 作业级 | 流作业 DAG（Flink SQL/Connect） | 作业解析 + OpenLineage 事件 | 高 | 数据平台化 |

L1 是 80% 价值【估算】：多数影响分析只需知道"哪些服务消费 orders"；L2 仅在变更密集域按需做【论证】。

## 2.52.3 捕获方式对比

| 方式 | 机制 | 实时性 | 准确性 | 成本 |
| ------ | ------ | :---: | --- | :---: |
| 注册制（目录） | 消费方在事件目录/契约仓登记订阅关系 | 低（靠自觉） | 中（易腐化） | 低 |
| 运行时捕获 | 扫描消费者组/订阅关系（kafka-consumer-groups / pulsar subscriptions / rabbitmq bindings） | 高 | 高（真实消费） | 低-中 |
| 解析制 | 解析 AsyncAPI 文档 + 代码引用（02-48 契约+ AST） | 中 | 高（代码级） | 中 |
| OpenLineage 事件 | 作业运行时发 lineage 事件（Marquez/DataHub 生态） | 实时 | 高 | 高 |

推荐组合【论证】：运行时捕获打底（L1 自动保鲜）+ 契约解析增强（L2 对核心域）+ 目录做查询界面（人读血缘图，机器读 API）。

## 2.52.4 影响分析工作流

```text
1. 变更提出（schema PR，02-48 工作流第 4 步）
2. 血缘查询：受影响 topic 的全部下游服务清单（自动附在 PR 描述）
3. 通知：清单内服务 owner 自动 @（替代群发邮件）
4. 兼容性判定：破坏性变更要求下游确认（02-48 双门禁 + 血缘定向通知）
5. 灰度验证：按血缘选 1 个下游金丝雀先行
6. 归档：影响清单入变更记录（审计+复盘）

### 血缘健康度指标（月度）

| 指标 | 目标 |
|------|------|
| 注册覆盖率 | 活跃消费者 100% 注册（registered=true） |
| 腐化率 | registered≠active 的条目占比 <5%【估算】 |
| 闲置率 | active_30d=false 的消费者占比（喂给 03-65 闲置治理） |
| 影响分析时延 | schema PR 附影响清单的自动生成时延 <5 分钟 |

### 腐化对账输出样例

```
[血缘对账 2026-11-17]
未登记但活跃: orders.order.created ← analytics-etl（owner 通知中）
已登记但闲置: orders.dlq ← legacy-billing（超 60 天，移交闲置流程）
结论: 腐化率 3.1%（达标 <5%）
```text

### 血缘查询界面（消费方式）

血缘数据的三种消费界面【论证】：

1. **PR 机器人**：schema 变更 PR 自动附影响清单（最高频消费，2.52.4 工作流）
2. **目录门户**：按域浏览 topic→服务图谱（人读，新人入职/架构评审用）
3. **审计 API**：合规调阅 PII 流向（02-50 台账的数据源，机器读）

界面实现成本递增【估算】：PR 机器人 1 人周、门户 1 人月、API 随门户附带——按消费频率倒推投入，先 PR 机器人。

### 实施路线（与团队规模匹配）

| 阶段 | 动作 | 退出条件 |
| ------ | ------ | ---------- |
| 1 台账 | Markdown 血缘表 + 运行时脚本对账 | 核心 topic 覆盖 100% |
| 2 自动化 | PR 机器人 + 腐化对账入 CI | 影响清单自动附 PR ≥1 月 |
| 3 图谱 | 门户/API（血缘库选型：DataHub/OpenMetadata） | 跨团队自助查询 |

选型提示【论证】：血缘库优先选支持消息源连接器的主流平台（DataHub 的 Kafka 元数据摄取成熟），避免自研图谱存储。

### 变更记录

2026-11-17 批次24 新建。L1 运行时捕获为最小可信实现，注册制必须带对账。

### 反模式补充

- ❌ 血缘靠架构师脑图维护——离职即腐化；运行时捕获是唯一保鲜源【论证】
- ❌ 血缘粒度一步到位做 L3——多数团队 L1 用半年就值回投入，L3 仅数据平台化后需要
- ❌ 影响分析只在变更时做——故障溯源（下游故障找上游）是同等高频的消费场景

```

腐化治理【论证】：血缘数据每周与运行时真实订阅对账（注册但无实际消费 → 标闲置；实际消费但未注册 → 补登或告警）——对账脚本逻辑可并入 doc-self-check 思路的独立巡检。

## 2.52.5 选型建议

| 团队形态 | 推荐 |
| ---------- | ------ |
| 单团队起步 | 运行时捕获脚本 + Markdown 血缘表（低科技高纪律） |
| 多团队契约治理（已上 02-48） | 契约仓为准 + 运行时对账 + 影响分析入 PR 模板 |
| 数据平台化（Flink/Connect 重度） | OpenLineage + DataHub/Marquez 自建图谱 |

红线【论证】：血缘不能解决"消费方解析了消息却没登记"的问题——L1 运行时捕获是唯一可信源；任何注册制血缘必须带对账机制。

### 血缘数据模型（L1 最小实现）

```json
{
  "topic": "orders.order.created",
  "producers": [{"service": "order-service", "team": "trading"}],
  "consumers": [
    {"group": "payment-processor", "service": "payment-service", "team": "fintech", "registered": true, "active_30d": true},
    {"group": "analytics-etl", "service": "analytics", "team": "data", "registered": false, "active_30d": true}
  ],
  "schema_refs": ["OrderCreated.v1"],
  "pii_fields": ["buyer_phone"],
  "updated_at": "2026-11-17"
}
```

字段约定【论证】：`registered`（注册制登记）与 `active_30d`（运行时实际活跃）双标记——两者不一致即腐化信号（下文对账）。

### 运行时捕获脚本（L1 自动保鲜）

```bash
# 每晨从 broker 拉取真实消费关系，刷新血缘的 active 标记
kafka-consumer-groups.sh --describe --all-groups --bootstrap-server <b> > /tmp/kgroups.txt
# 输出格式即血缘 consumers 列表的来源；解析后 diff 血缘库
python3 lineage_refresh.py --source /tmp/kgroups.txt --lineage lineage/orders.json
# 对账输出：registered=false 且 active=true → "未登记消费者"告警
```

### 影响分析报告模板（PR 自动附件）

```text
变更: OrderCreated.v2 新增必填字段 payMethod
影响范围（血缘查询）:
  - payment-service（p0 破坏性 → 需 owner 确认）
  - analytics-etl（p1 → 通知即可）
  - 无消费组: 无
灰度建议: 先切 payment-service 金丝雀实例
```
