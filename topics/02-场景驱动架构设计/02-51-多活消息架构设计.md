## 2.51.1 多活与主备的本质差异

| 维度 | 主备（ DR ） | 多活（ Active-Active ） |
| ------ | -------------- | -------------------------- |
| 备用侧状态 | 待机（不承接流量） | 全量承接流量 |
| RTO | 分钟-小时（切换） | ~0（流量本就分散） |
| 数据流 | 单向复制 | 双向（环回） |
| 核心难题 | 切换可靠性 | **冲突与一致性** |
| 成本 | 1+ε | 2× 全量 + 冲突工程 |

多数"多活"需求真实形态是**单元化+局部活跃**（每数据分片单主写，跨单元读就近）而非全域双写【论证：业界主流（单元化架构）实践】。

## 2.51.2 三大难题

1. **环回复制（loop）**：A 区消息复制到 B，B 又复制回 A——需 origin 标记/消息去重（02-14）阻断【论证】。
2. **冲突解决**：同 key 双写并发——方案谱系：最后写入获胜（LWW，时钟敏感）→ CRDT（无冲突数据结构，Redis Enterprise 的 Active-Active 即 CRDT 路线）→ 单主分片（规避冲突，Kafka 系默认）【论证】。
3. **全局顺序**：跨区全局有序代价极高——多活应放弃全局序，保分区/实体级有序（02-13 顺序设计的跨区版）【论证】。

## 2.51.3 六系统多活能力对照

| 系统 | 原生多活机制 | 冲突策略 | 成熟度 |
| ------ | -------------- | ---------- | :---: |
| Kafka | MirrorMaker 2（主动-主动拓扑可配） | 无内建冲突解决——靠 topic 命名空间隔离（A.kafka.topic ↔ B.kafka.topic）或单主分区 | ⚠️ 需大量工程 |
| Pulsar | **地理复制内建**（namespace 级 geo-replication，异步多副本） | 无冲突解决——适合"每消息单源生产，多区消费" | ✅ 消费侧多活成熟 |
| RabbitMQ | Federation / Shovel | 无——跨区路由层 | ⚠️ |
| NATS | **Supercluster / Leafnode**（跨集群 subject 路由） | 无持久化多写冲突（Core 无状态；JetStream 跨集群复制为灾难恢复导向） | ✅ 服务层多活成熟 |
| Redis | 社区版无；Redis Enterprise **Active-Active 基于 CRDT** | CRDT（最后写入合并） | ✅（商业版） |
| MQTT | Bridge（broker 间桥接） | 无—— broker 相关 | ⚠️ |

关键判断【论证】：**开源消息系统没有"开箱即用的全域双写多活"**——Pulsar geo-replication 与 NATS supercluster 解决"跨区可达与灾备"，不解决"同 key 并发写冲突"；真正双写多活需应用层单元化/CRDT 或商业方案。

## 2.51.4 参考架构模式

**模式 A：单元化单主（推荐默认）**:

```text
按用户/租户分片 → 每分片指定主区（如 uid%2 → A/B 区）
写：路由层按分片送主区 topic（orders.{region}.{shard}）
读：就近区消费本地副本（异步复制，秒级滞后可接受）
冲突：结构上不存在（每分片单写者）
```

**模式 B：Pulsar 地理复制消费多活**：消息在任一区生产 → geo-rep 同步 → 所有区消费者本地消费（适合全局事件广播类）【论证：Pulsar 官方 geo-replication 语义】。

**模式 C：CRDT 状态多活**（Redis Enterprise）：共享状态用 CRDT 结构（计数器/集合），双写自动合并——适合会话/状态而非事件流【论证】。

**模式 D：NATS Supercluster 服务网格化**：服务请求就近调度，JetStream 数据留在单区（灾备异步复制）——服务层多活+数据层主备的混合【论证】。

## 2.51.5 选型建议

| 场景 | 推荐模式 | 理由 |
| ------ | ---------- | ------ |
| 跨地域业务连续性（容灾导向） | B 或 D | 不需要双写，复制+就近消费即可 |
| 用户就近写入（延迟敏感） | A 单元化 | 唯一无冲突路线；成本在路由层 |
| 全局共享状态（购物车/会话） | C | CRDT 是成熟解（注意许可证：商业版，见 01-34） |
| 全域双写强需求 | 重新审视需求 | 开源 MQ 无内建支持，误用风险极高【论证】 |

红线【论证】：① 不用 MirrorMaker 2 做双向同 topic 复制（环回必现）；② 多活必须先定冲突策略再选技术；③ 跨区延迟（100ms 级）决定同步复制不可用——多活=异步+业务容忍滞后。

### 冲突解决算法对比（展开）

| 算法 | 机制 | 优点 | 代价 |
| ------ | ------ | ------ | ------ |
| LWW（最后写入获胜） | 时间戳比对 | 简单 | 时钟漂移导致误合并；丢更新 |
| CRDT（无冲突数据结构） | 数学上可交换/结合/幂等 | 无冲突自动合并 | 仅适用特定数据结构；状态膨胀 |
| 单主分片 | 每分片唯一写者 | 无冲突概念 | 跨区写延迟；路由复杂度 |
| 仲裁（quorum 跨区） | 多数派确认 | 强一致 | 延迟跨区倍增——多活场景不可行 |

多活场景结论【论证】：跨区延迟使仲裁出局；工程上只有"单主分片（默认）"与"CRDT（限状态类）"两条路——任何"双写+事后合并"的中间态都是技术债。

### 多活故障模式速查

| 现象 | 首要怀疑 |
| ------ | ---------- |
| 两区数据周期性互相覆盖 | 环回复制未阻断 |
| 同一订单状态两区不同 | 冲突策略缺失（双写未走单主/CRDT） |
| 复制延迟尖峰与业务高峰重合 | 链路带宽不足（03-64 扩容判据） |
| 切换后消息重复消费 | 位点未全局对齐（跨区 consumer offset 管理） |

### 模式 A 的路由层设计要点

```text
路由依据：分片键（uid/tenant-id）一致性哈希 → 主区表（配置中心维护）
主区表项：{shard: 0-511, primary: region-a, updated_at, version}
切换流程：主区故障 → 提升幸存区（先对账，再改主区表 version+1）
消费侧：全量消费各区 topic，按主区表过滤非主写副本（幂等兜底）
```

路由层是模式 A 的新增组件（非 MQ 内建）【论证】：其可用性必须高于 MQ 本身（双写配置中心 + 本地缓存兜底）；主区表变更需审计（误切主 = 双主事故）。

### 消费者跨区位点管理

多活消费的核心细节【论证】：各区消费独立位点（不推荐全局位点——跨区同步引入延迟与单点）；消息带 origin-region 头，消费者按主区表决定去重；重放按区独立进行（02-42 灾备衔接）。

### 多活设计评审清单

- [ ] 冲突策略已书面化（不是"先双写看看"）
- [ ] 环回阻断机制经故障注入验证（计数不翻倍）
- [ ] 跨区延迟实测值写入设计文档（RTT 与带宽）
- [ ] RPO 按"复制滞后"而非"零"承诺（业务签字）
- [ ] 切换 runbook 含数据对账步骤且演练过
- [ ] PII 出区审批完成（02-50 联动）
- [ ] 许可证覆盖跨区域部署形态（商业版 CRDT 等，01-34）

## 2.51.5b PACELC 视角的多活权衡

PACELC 框架（有分区时可用性 vs 一致性；无分区时延迟 vs 一致性）在多活的落点【论证】：

| 系统/模式 | 分区时（P） | 正常时（E） | 含义 |
| ----------- | ------------- | ------------- | ------ |
| 单元化单主 | 非主分区拒写 | 主区本地写低延迟 | 常态快、故障分区降级 |
| Pulsar geo-rep | 分区区不可生产（复制中断） | 异步复制低延迟 | 面向灾备非双写 |
| 跨区仲裁 | 少数派分区不可用 | 每次写跨区 RTT×2 | 多活场景不可行（再次验证 2.51.2） |
| CRDT 双写 | 各自继续写（自动合并） | 合并开销常态存在 | 仅状态类数据可接受 |

结论【论证】：多活 = 在 PACELC 上选择"分区时降级可用性、常态保低延迟"的单元化路线为主——任何"分区时也全可用"的承诺都以一致性或延迟为代价。

### 论证示例：订单系统多活

需求：全球用户就近下单、订单中心多区部署【示意性合成案例】。

- 分片键：uid 一致性哈希 → 主区表（模式 A）
- 就近读：各区读本地副本，允许秒级滞后展示订单列表
- 支付回调：按订单主区路由写回（不就近——数据归属优先于延迟）
- 演练：季度注入主区故障，验证提升流程与对账（03-64）

### 反模式补充

- ❌ **就近路由写但没主区表**：靠 DNS/负载均衡随机写——冲突必现；主区表是不可省略的组件【论证】
- ❌ **把 geo-replication 当多活宣传**：它解决灾备，不解决冲突；销售话术与架构现实要分开【论证】
- ❌ **跨区同步副本求 RPO=0**：RTT×2 拖垮写延迟；RPO=0 请走单元化单主（故障分区短暂拒写）【论证】
