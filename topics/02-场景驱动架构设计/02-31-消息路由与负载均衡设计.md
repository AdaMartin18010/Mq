## 2.31.1 路由与负载均衡的本质差异

### 概念边界

【论证】消息路由决定“一条消息该去哪里”，负载均衡决定“同一目的地内的多个消费者如何分担消息”。二者常被混用，但设计目标不同：路由关注消息语义与分区/队列/主题的映射；负载均衡关注消费者实例之间的吞吐公平性。

| 维度 | 消息路由 | 负载均衡 |
| --- | --- | --- |
| 决策对象 | 单条消息 | 消费者实例 |
| 核心问题 | 消息到哪个 topic/partition/queue/subject | 多个消费者如何分配消息 |
| 顺序影响 | 决定顺序边界（如同 key 进同分区） | 不改变顺序边界，只改变实例归属 |
| 可动态性 | 可热更新规则文件或 topic 映射 | 通常由 broker/框架自动重平衡 |
| 典型配置 | `routing.rules.file`、`partitioner.class` | `partition.assignment.strategy`、`prefetch_count` |

路由错误会导致消息进入错误队列、顺序错乱或重复处理；负载均衡失衡会导致部分消费者空闲、部分消费者过载。设计时应先确定路由语义，再为每个路由终点配置合适的负载均衡策略。

## 2.31.2 路由策略选型

### 路由策略决策表

| 业务特征 | 推荐策略 | 适用系统 | 关键风险 |
| --- | --- | --- | --- |
| 需要保证同一业务键顺序 | Key Hash 路由 | Kafka、Pulsar、Redis Stream | 热点 key 导致分区倾斜 |
| 需要按业务维度隔离 | Topic/Subject 拆分路由 | Kafka、NATS、RabbitMQ、MQTT | topic 数量爆炸，元数据管理复杂 |
| 需要按消息内容动态分发 | 内容路由 / 规则路由 | RabbitMQ Topic/Headers、NATS Subject、Kafka Streams | 规则复杂时延迟升高 |
| 需要 VIP/优先级分流 | 优先级路由 + 独立队列 | RabbitMQ、Kafka（自定义 partitioner）、Pulsar | 低优先级队列可能饥饿 |
| 需要就近服务或合规驻留 | 地理位置路由 / 单元化路由 | Kafka MM2、NATS Supercluster、Pulsar geo-rep | 多活冲突与环回，参见 [02-51 多活消息架构设计](02-51-多活消息架构设计.md) |
| 临时实验流量或灰度 | 权重/比例路由 | 应用层网关、Kafka 自定义 partitioner | 需要配合流量镜像与监控 |

【论证】Key Hash 路由是 Kafka/Pulsar/Redis 场景保证分区/Stream 内顺序的基础，但热点 key 会使单个分区成为瓶颈。典型缓解手段：

1. 在 key 后追加“分桶后缀”（如 `orderId#bucket_0..7`），牺牲全局有序换取子桶内有序；
2. 对 VIP/热点 key 单独路由到高吞吐分区或独立 topic；
3. 监控每分区消息速率，偏差 >20% 时触发重分区或业务拆分。

内容路由在 RabbitMQ Topic Exchange 与 NATS Subject 中最为自然。RabbitMQ 的 binding key 支持 `*`（一个单词）和 `#`（零或多个单词），适合 `order.{action}.{priority}` 这类结构化路由键。NATS 的 `>` 通配符匹配多级 subject，适合地理-业务层级如 `orders.cn.vip`。

## 2.31.3 负载均衡策略选型

### 负载均衡策略表

| 策略 | 语义 | 适用系统 | 最佳场景 |
| --- | --- | --- | --- |
| Round-Robin | 依次轮询分发 | Kafka partition assignor、NATS Queue Group、RabbitMQ 多消费者、MQTT Shared Subscription、Pulsar Shared | 消费者同构、处理耗时相近 |
| Key-Sharing / Key_Shared | 同一 key 固定到同一消费者 | Pulsar Key_Shared、Kafka 按 key 分配 | 需要业务键局部顺序且要横向扩展 |
| Least-Connections / 最少未确认 | 优先分发给未确认消息少的消费者 | RabbitMQ `basic_qos` + 多消费者 | 消费者处理速度差异大 |
| Weighted / 加权 | 按实例容量分配权重 | 应用层网关、部分 Kafka 自定义 assignor | 异构实例或灰度比例 |
| Geo-Affinity / 就近优先 | 优先本地消费者，失败跨区回落 | NATS Supercluster Gateway | 多云/边缘联邦，参见 [01-51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md) |

【论证】负载均衡策略的选择应匹配消费者异构程度。同构微服务首选 Round-Robin；处理耗时差异大时，RabbitMQ 的 `basic_qos(prefetch_count=10)` 配合短确认，可近似实现“快者多劳”。Pulsar 的 Key_Shared 在保持同一 key 顺序的同时提供并行度，但要求 key 空间足够分散，否则仍会出现倾斜。

## 2.31.4 六系统路由与负载均衡机制对比

### Kafka

【定理】Kafka Producer 默认使用 `DefaultPartitioner`：若消息指定 key，则按 `murmur2(keyBytes) % partitionCount` 路由；若未指定 key，则按 sticky partition 轮询。

- 路由单元：topic-partition；
- 顺序保证：单 partition 内按写入顺序；
- 负载均衡：Consumer Group 通过 `partition.assignment.strategy` 分配 partition，建议 partition 数为消费者数的 2~4 倍，便于重平衡后仍保持均衡；
- 自定义：实现 `org.apache.kafka.clients.producer.Partitioner` 接口可实现业务路由。

### RabbitMQ

【定理】RabbitMQ 通过 Exchange 与 Binding 实现路由。常见 Exchange 类型：direct、topic、headers、fanout。

- 路由单元：exchange → queue；
- 顺序保证：单队列 FIFO；
- 负载均衡：多个消费者绑定同一队列，通过 `prefetch_count` 控制预取量，实现公平分发；
- 自定义：可声明 topic exchange 并使用 `routing_key` 模式匹配。

### NATS

【定理】NATS Core 通过 subject 层级与通配符 `*`、`>` 匹配订阅者；Queue Group 实现同一 subject 的负载均衡。

- 路由单元：subject；
- 顺序保证：Core NATS 不保证跨订阅者顺序；
- 负载均衡：`QueueSubscribe(subject, queueGroup, handler)` 自动轮询到组成员；
- 自定义：subject 模板 `orders.{region}.{priority}` 天然支持内容路由。

### Pulsar

【定理】Pulsar 通过 partitioned topic 与 subscription 类型（Exclusive、Shared、Failover、Key_Shared）组合实现路由与负载均衡。

- 路由单元：partitioned topic；
- 顺序保证：Key_Shared 订阅保证同一 key 进入同一 consumer；
- 负载均衡：Shared 订阅轮询所有 consumer；Failover 主备切换；
- 自定义：可通过 `MessageRouter` 自定义分区逻辑。

### MQTT

【定理】MQTT 通过 topic filter 与通配符 `+`（单层）、`#`（多层）匹配订阅；MQTT 5.0 引入 Shared Subscriptions `$share/{group}/{topic}` 实现负载均衡。

- 路由单元：topic；
- 顺序保证：MQTT 协议本身不保证跨订阅者顺序；
- 负载均衡：Shared Subscription 将消息分发给组内某一客户端；
- 自定义：主题层级设计 `building/floor/room/sensor` 实现业务路由。

### Redis Stream

【定理】Redis Stream 通过 stream key 与消费者组（consumer group）划分数据；`XREADGROUP` 在组内轮询未处理消息。

- 路由单元：stream key；
- 顺序保证：同一 stream 内按 entry ID 单调递增；
- 负载均衡：消费者组内通过 `XREADGROUP` 竞争读取，pending list 记录已分配未确认消息；
- 自定义：按业务前缀（如 `order:events`、`user:events`）拆分 stream key 实现路由隔离。

## 2.31.5 路由配置与示例

### 引用 routing-config.properties

项目模板 `topics/config-templates/routing-config.properties` 集中定义了六系统的路由与负载均衡参数，设计阶段应直接引用而非自行编造参数名。

```properties
# Kafka 路由：按业务 key 哈希，自定义 partitioner 兜底业务规则
kafka.routing.strategy=key-hash
kafka.routing.key.field=id
kafka.routing.custom.partitioner=com.example.CustomPartitioner
kafka.routing.partition.count=6

# NATS 路由：subject 层级 + Queue Group 负载均衡
nats.routing.strategy=subject
nats.routing.subject.pattern=orders.{region}.{priority}
nats.routing.queue.group.enabled=true
nats.routing.queue.group.name=workers

# RabbitMQ 路由：topic exchange + 结构化 routing key
rabbitmq.routing.strategy=topic
rabbitmq.routing.exchange.type=topic
rabbitmq.routing.exchange.name=orders
rabbitmq.routing.key.pattern=order.{action}.{priority}
rabbitmq.routing.headers.match=all

# 负载均衡与动态规则
load.balance.enabled=true
load.balance.strategy=round-robin
load.balance.monitor.enabled=true
load.balance.monitor.metrics=routing_count,routing_distribution,load_balance_ratio

routing.rules.enabled=true
routing.rules.file=/etc/mq/routing-rules.json
routing.rules.reload.enabled=true
routing.rules.reload.interval=60s

# 路由缓存，降低高频规则计算开销
routing.cache.enabled=true
routing.cache.size=10000
routing.cache.ttl=300
routing.cache.eviction.policy=LRU
```

### 动态路由规则示例

动态路由文件 `/etc/mq/routing-rules.json` 示例：

```json
{
  "rules": [
    {
      "name": "vip-to-fast-lane",
      "condition": { "field": "priority", "op": "eq", "value": "vip" },
      "action": { "target": "orders.vip", "partition": 0 }
    },
    {
      "name": "region-route",
      "condition": { "field": "region", "op": "in", "values": ["cn", "us"] },
      "action": { "target": "orders.{region}" }
    },
    {
      "name": "default",
      "condition": { "field": "*", "op": "always" },
      "action": { "target": "orders.default" }
    }
  ]
}
```

【论证】动态路由适合促销、灰度、合规分流等需要运行时调整的场景，但规则引擎本身会增加延迟。建议在规则稳定后启用 `routing.cache.enabled=true`，并监控 `routing_latency` 与 `routing_errors`。

## 2.31.6 负载均衡设计要点

### 分区/队列并行度规划

【估算】Kafka 单分区建议吞吐上限约 10 MB/s 或 1 万 msg/s；RabbitMQ 单队列单消费者约 1~5 万 msg/s；NATS Core 单 subject 无持久化时可达百万 msg/s，Queue Group 性能随组成员线性扩展。

并行度规划原则：

1. 消费者数量 ≤ 分区/队列数量，否则会有消费者空闲；
2. 分区数为消费者数量的整数倍，重平衡后分配更均匀；
3. 预留 2~4 倍扩容空间，避免未来加消费者时触发大规模重分区。

### 不均衡检测与调整

| 指标 | 告警阈值 | 调整动作 |
| --- | --- | --- |
| `load_balance_ratio` | > 0.2（20%） | 检查 key 热点、增加分区、调整路由规则 |
| 单分区消息速率偏差 | > 20% vs 均值 | 使用 salting 或拆分热点 key |
| 单消费者 pending 消息数 | > 均值 3 倍 | 增加消费者、降低 `prefetch_count`、优化处理逻辑 |
| 跨区流量占比 | 异常升高 | 检查 geo-affinity 配置或路由规则漂移 |

## 2.31.7 路由与负载均衡最佳实践

### 设计建议

1. **先定顺序边界，再定路由**：需要顺序保证的业务键必须路由到同一分区/队列/stream；可接受乱序的场景优先 round-robin，提升并行度。
2. **路由键应稳定且具备业务语义**：如 `order.created.vip`、`sensors.building1.temperature`。避免把随机值作为 Kafka key，否则分区倾斜且无法利用缓存。
3. **避免多级路由嵌套**：在 Kafka Producer 分区器、RabbitMQ exchange、应用层网关中重复做路由决策，会导致调试困难。应把路由策略下沉到单一权威位置（如配置中心或规则引擎）。
4. **负载均衡与背压配合**：Kafka Consumer 配置 `max.poll.records` 与 `max.poll.interval.ms`；RabbitMQ 配置 `basic_qos`；Pulsar 配置 `receiverQueueSize`；防止消费过慢触发重平衡。
5. **跨域/边缘场景优先考虑联邦语义**：多云或边缘部署时，路由不仅是单集群内决策，还涉及“数据是否出区、是否就近服务”。参见 [01-51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md) 与 [02-51 多活消息架构设计](02-51-多活消息架构设计.md)。
6. **流协议桥接时保留路由语义**：当通过 WebSocket/SSE/WebTransport 把后端事件推送到前端时，网关应作为 MQ 消费者参与负载均衡，而不是自行维护第二套路由逻辑。流协议选型参见 [01-40 应用层流协议与交互标准](../01-基础概念与对比分析/01-40-应用层流协议与交互标准.md)。
7. **落地前通过测试脚本验证**：项目提供 `topics/scripts/routing-test.sh`，覆盖 kafka key、nats queue、rabbitmq topic 三种场景，实施前后应运行验证。具体操作与检查清单见 [03-47 消息路由与负载均衡实践指南](../03-架构与运维实践/03-47-消息路由与负载均衡实践指南.md)。
