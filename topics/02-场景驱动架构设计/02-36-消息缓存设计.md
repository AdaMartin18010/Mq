## 2.36.2 Kafka缓存

### 缓存实现

```java
// 消息缓存
// 使用本地缓存缓存热点消息
Cache<String, String> messageCache = Caffeine.newBuilder()
    .maximumSize(10000)
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .build();

// 缓存消息
ProducerRecord<String, String> record = new ProducerRecord<>("orders", key, value);
messageCache.put(key, value);

// 查询缓存
String cached = messageCache.getIfPresent(key);
if (cached != null) {
    return cached;
}

// 元数据缓存
MetadataCache metadataCache = new MetadataCache();
metadataCache.cacheTopicMetadata("orders", topicMetadata);
```

// 消息缓存
var messageCache = sync.Map{}

nc.Subscribe("orders.*", func(msg *nats.Msg) {
    // 缓存消息
    messageCache.Store(msg.Subject, msg.Data)

    // 处理消息

## 2.36.4 RabbitMQ缓存

### 缓存实现

```python
# 消息缓存
from cachetools import TTLCache

message_cache = TTLCache(maxsize=10000, ttl=300)  # 5分钟过期

# 缓存消息
def cache_message(key, message):
    message_cache[key] = message

# 查询缓存
def get_cached_message(key):
    return message_cache.get(key)

# 元数据缓存
metadata_cache = {}

def cache_metadata(queue_name, metadata):
    metadata_cache[queue_name] = metadata
```

## 2.36.6 缓存层次与选型决策表

【论证】消息缓存按位置可分为客户端本地缓存、代理侧缓存、分布式缓存和 CDN/边缘缓存。不同层次在延迟、一致性、容量上差异显著：

| 缓存层次 | 典型实现 | 延迟 | 一致性 | 适用场景 |
| ---------- | ---------- | ------ | -------- | ---------- |
| **L1 客户端本地缓存** | Caffeine、Guava、sync.Map | 最低（微秒级） | 弱，需 TTL/失效 | 热点消息、元数据、重复消费防护 |
| **L2 进程/应用内缓存** | 应用内 Map + TTL | 低 | 弱 | 短生命周期上下文，如会话状态 |
| **L3 分布式缓存** | Redis、Memcached | 中（亚毫秒~毫秒） | 较强 | 跨实例共享热点、排行榜、限流计数 |
| **Broker 侧缓存** | Kafka page cache、NATS JetStream、RabbitMQ queue index | 低 | 强 | 消息重放、历史查询、追读优化 |
| **边缘缓存** | 边缘节点本地存储、eKuiper 规则缓存 | 低 | 弱 | 边缘离线场景、带宽节省 |

选型建议：

- 读多写少的热点消息优先 L1 + L3 分层，命中率目标 ≥ 70%（`cache.monitor.alert.hit.rate.threshold=0.7`）。
- 消息重放/历史查询依赖 broker 持久化层，避免在应用层再缓存全量消息。
- Serverless 函数冷启动频繁，可通过 L1 缓存减少初始化时的元数据拉取，参考 [1.48 Serverless 事件架构与函数消息](../01-基础概念与对比分析/01-48-Serverless事件架构与函数消息.md)。

### 缓存配置示例

`config-templates/cache-config.properties` 中的关键参数：

```properties
# 消息缓存配置
cache.enabled=true
cache.type=lru
cache.max.size=10000
cache.expire.after.write.minutes=5
cache.expire.after.access.minutes=10

# 热点消息缓存配置
cache.hotspot.enabled=true
cache.hotspot.max.size=1000
cache.hotspot.expire.after.write.minutes=30
cache.hotspot.hit.rate.threshold=0.8

# 元数据缓存配置
cache.metadata.enabled=true
cache.metadata.max.size=1000
cache.metadata.expire.after.write.minutes=60
cache.metadata.refresh.interval.minutes=30

# 分层缓存配置
cache.layered.enabled=false
cache.layered.levels=2
cache.layered.l1.max.size=1000
cache.layered.l2.max.size=10000

# 缓存一致性配置
cache.consistency.enabled=true
cache.consistency.strategy=ttl
cache.consistency.update.strategy=write_through

# 缓存穿透防护配置
cache.penetration.protection.enabled=true
cache.penetration.protection.type=bloom_filter
cache.penetration.protection.bloom.filter.size=100000
cache.penetration.protection.bloom.filter.fpp=0.01
```

## 2.36.7 缓存一致性、可观测与跨域场景

消息缓存面临的核心矛盾是**时效性 vs 命中率**。【论证】在事件驱动架构中，消息一旦产生即应被消费，缓存更多是服务于“查询/回放”路径，而非“实时消费”路径。因此一致性策略通常选择 TTL 或显式失效，而非强一致写穿。

一致性策略对比：

| 策略 | 机制 | 适用场景 | 注意事项 |
| ------ | ------ | ---------- | ---------- |
| **TTL** | 固定过期时间后重新加载 | 容忍秒级延迟的配置/元数据 | 设置不当会导致脏读或缓存击穿 |
| **失效通知** | 消息变更时广播失效事件 | 强一致性要求的热点数据 | 需要可靠的消息通道，避免失效丢失 |
| **写穿（Write-Through）** | 写缓存同时写持久层 | 读多写少且写入可控 | 增加写延迟，需处理双写失败 |
| **写回（Write-Back）** | 先写缓存，异步刷盘 | 高吞吐写入 | 故障时可能丢数据，需配合 WAL |

可观测性：

- 命中率、未命中率、驱逐数应接入监控系统。OpenTelemetry 语义约定中对消息系统有 `messaging.cache.hit` 等扩展建议，详见 [1.50 OpenTelemetry 消息语义约定与全链路追踪](../01-基础概念与对比分析/01-50-OpenTelemetry消息语义约定与全链路追踪.md)。
- 建议配置告警：命中率 < 70% 或容量 > 90% 时触发。

跨域/边缘场景：

- 多云联邦场景下，边缘节点带宽受限，可在 Leafnode/边缘网关侧启用本地缓存，参考 [1.51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md)。
- IoT 场景中，Sparkplug 的出生/死亡证书可用于判断设备缓存数据是否新鲜，见 [1.46 IoT 与互联网领域消息标准纵览](../01-基础概念与对比分析/01-46-IoT与互联网领域消息标准纵览.md)。
