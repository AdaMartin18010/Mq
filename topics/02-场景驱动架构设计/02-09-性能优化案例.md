## 2.9.1 Kafka 性能优化案例

### 案例：电商平台订单系统（示意性合成案例）

> 「示意性合成案例」：本节案例为说明性构造，企业与指标均为合成（AGENTS.md §6.3）。

**问题**：Producer 吞吐量仅 50 万 msg/s，目标 200 万+ msg/s；同时 broker CPU 接近饱和。

#### 基线分析

- 消息平均 200 B，峰值 50 万 msg/s ≈ 100 MB/s 原始数据；
- 由于 `batch.size=16384`、`linger.ms=0`，每条消息几乎独立成包，网络小包比例高，broker 端解压/校验开销大；
- `compression.type=none` 导致跨 AZ 流量浪费。

#### 优化前配置

```properties
batch.size=16384
linger.ms=0
compression.type=none
acks=1
buffer.memory=67108864
max.in.flight.requests.per.connection=1
```

#### 优化后配置

```properties
batch.size=131072        # 128 KB 批量
linger.ms=50             # 等待 50 ms 聚合批量
compression.type=lz4     # LZ4 压缩
acks=1
buffer.memory=268435456  # 256 MB 缓冲区
max.in.flight.requests.per.connection=5
```

#### 容量估算与效果

- 批量 128 KB 后，相同 50 万 msg/s 下每秒请求数从约 50 万降至约 4,000，broker 端请求处理开销大幅下降；
- LZ4 压缩率按 2–3 倍估算，网络带宽从 100 MB/s 降至 35–50 MB/s；
- 优化后设计目标吞吐达到 220 万 msg/s（合成设计值），约为基线的 4.4 倍【估算】。

#### 故障场景与应对

| 故障 | 原因 | 应对 |
| ------ | ------ | ------ |
| 内存占用过高 | buffer.memory 256 MB + 大量 inflight | 监控 `buffer-available-bytes`，必要时降低 batch.size 或增加内存 |
| 消息延迟增大 | linger.ms=50 ms 对敏感链路不可接受 | 关键 topic 单独配置 `linger.ms=5` 并启用压缩 |
| 消费者滞后 | 生产速度远超消费速度 | 增加消费组并行度，或按业务优先级拆分 topic |

## 2.9.2 NATS 性能优化案例

### 案例：游戏实时通信系统（示意性合成案例）

> 「示意性合成案例」：本节案例为说明性构造，企业与指标均为合成（AGENTS.md §6.3）。

**问题**：P99 延迟 1 ms，目标 < 200 μs。

#### 基线分析

- 跨可用区部署引入 0.5–1 ms 网络延迟；
- 默认 TCP Nagle 算法导致小消息聚合发送；
- Go GC 压力导致偶发几十毫秒停顿；
- 每条 RPC 新建连接，三次握手开销大。

#### 优化措施

1. **同机房部署**：将 NATS 集群与游戏服务器部署到同一可用区，消除跨 AZ 往返。
2. **禁用 Nagle 算法**：设置 `TCP_NODELAY=1`。
3. **Go GC 调优**：将 `GOGC=100` 调整到 `GOGC=200`，并绑定 CPU 核心减少调度抖动。
4. **连接池复用**：长连接 + 连接池，避免频繁创建 TCP 连接。

#### 关键配置

```yaml
# nats-server.conf
port: 4222
max_connections: 100000
max_payload: 65536
write_deadline: "1s"
```

```bash
# 服务端启动环境
export TCP_NODELAY=1
export GOGC=200
export GOMAXPROCS=16
```

#### 效果

| 指标 | 基线 | 优化后 | 备注 |
| ------ | ------ | -------- | ------ |
| P99 延迟 | 1 ms | 150 μs | 同机房 + TCP_NODELAY |
| 连接建立开销 | 每次 RPC | 复用长连接 | 消除三次握手 |
| GC 停顿 | 偶发 20–30 ms | < 1 ms | GOGC 与 CPU 绑定 |

**故障场景与应对**：若单节点 CPU 饱和，可通过 NATS Queue Group 水平扩展订阅者；若消息丢失不可接受，则将 NATS Core 升级为 JetStream 持久化。

## 2.9.3 RabbitMQ 性能优化案例

### 案例：任务队列系统（示意性合成案例）

> 「示意性合成案例」：本节案例为说明性构造，企业与指标均为合成（AGENTS.md §6.3）。

**问题**：单队列吞吐量 2 万 msg/s，目标 10 万+ msg/s；RabbitMQ 节点 CPU 单核满载。

#### 基线分析

- RabbitMQ 队列是单线程的，单队列上限约 5 万 msg/s；
- 消息持久化导致每次写入都触发 fsync；
- 消费者单条 ack，网络往返频繁；
- 机械盘 IO 成为瓶颈。

#### 优化措施

1. **队列分片**：使用 Consistent Hash Exchange 或 Sharding 插件将流量拆到多个队列；
2. **非持久化消息**：允许任务队列使用 transient 消息，牺牲极端断电场景的可恢复性换取吞吐；
3. **批量确认**：消费者 `prefetch_count=200`，每处理 200 条 ack 一次；
4. **Erlang 进程数**：将 `+P 1000000` 写入 `rabbitmq-env.conf`；
5. **SSD 存储**：将 `rabbitmq_mnesia` 与消息存储迁移到 NVMe SSD。

#### 关键配置

```ini
# rabbitmq-env.conf
SERVER_ADDITIONAL_ERL_ARGS="+P 1000000 +K true +A 128"
```

```properties
# RabbitMQ 客户端
prefetch_count=200
publisher_confirms=false
automatic_recovery=true
```

```bash
# 启用一致哈希交换插件（示例）
rabbitmq-plugins enable rabbitmq_consistent_hash_exchange
```

#### 效果

| 指标 | 基线 | 优化后 | 备注 |
| ------ | ------ | -------- | ------ |
| 单队列吞吐 | 2 万 msg/s | 12 万 msg/s（集群聚合） | 多队列 + transient + 批量 ack |
| 磁盘 IO 等待 | 80 % | < 20 % | SSD + transient 消息 |
| 消费端 RTT | 每次 ack | 每 200 条 ack 一次 | 批量确认 |

**故障场景与应对**：若节点宕机，transient 消息会丢失，因此仅对可重放的日志/任务使用；金融或订单类消息仍需持久化 + quorum queue。

## 2.9.4 优化总结

### 通用优化策略

| 策略 | 适用系统 | 收益 | 风险 |
| ------ | ---------- | ------ | ------ |
| 批量发送/消费 | Kafka、RabbitMQ | 减少网络 RTT，提升吞吐 | 增加延迟与内存占用 |
| 压缩 | Kafka、跨 AZ 流量 | 降低带宽成本 | 增加 CPU 开销 |
| 连接复用 | NATS、RabbitMQ | 降低连接/握手开销 | 连接数过多时 broker 压力上升 |
| 队列/分区拆分 | RabbitMQ、Kafka | 突破单线程/单分区瓶颈 | 增加运维复杂度 |
| 硬件升级 | 所有 | 直接提升磁盘/网络上限 | 成本增加 |
| 参数调优 | 所有 | 针对 workload 榨取性能 | 误调可能降低可靠性 |

### 优化检查清单

- [ ] Producer/Publisher 是否启用批量（`batch.size`、`linger.ms`、`prefetch_count`）？
- [ ] 是否根据网络环境选择压缩算法（`lz4`、`snappy`、`zstd`）？
- [ ] Consumer 是否采用批量拉取/批量 ack，避免单条往返？
- [ ] TCP 参数是否针对低延迟场景调优（`TCP_NODELAY`、`so_sndbuf`）？
- [ ] 存储是否为 SSD/NVMe，磁盘 IO 是否成为瓶颈？
- [ ] 关键 topic/queue 的延迟与吞吐目标是否已量化并监控？
- [ ] 优化是否以牺牲耐久性为代价？若是，是否已评估业务可接受范围？

## 2.9.5 真实性能优化案例（公开来源）

### DoorDash：Kafka 生产者批处理降低 Broker CPU

> 来源：[Building scalable real time event processing with Kafka and Flink](https://doordash.engineering/2022/08/02/building-scalable-real-time-event-processing-with-kafka-and-flink/)（DoorDash Engineering，2022，Iguazu 高吞吐 topic 批处理优化）。

**背景**：DoorDash 的 Iguazu 平台中存在大量无自然 key 的高吞吐量事件 topic，生产者默认 round-robin 分区策略导致每条消息独立成 batch，broker 端 CPU 居高不下。

**优化措施**：

1. 启用 Kafka sticky partitioner（Kafka 2.4+ 默认），将无 key 记录在批次准备好之前固定发送到同一分区；
2. 将 `linger.ms` 从默认值提高到 50–100 ms，积累更大的 batch；
3. 同步评估 `batch.size` 与 topic 吞吐，避免 batch 过大导致延迟超标。

```properties
# DoorDash 高吞吐 null-key topic 优化示例
partitioner.class=org.apache.kafka.clients.producer.internals.DefaultPartitioner
linger.ms=100
batch.size=262144
compression.type=lz4
```

**效果**：受影响的 topic 上，Kafka broker CPU 利用率下降 30–40 %。

### Sophotech：从 RabbitMQ 迁移到 NATS 的延迟与运维优化

> 来源：[How Sophotech Cut Latency by 3x Migrating from RabbitMQ to NATS](https://www.synadia.com/blog/rabbitmq-to-nats-sophotech-migration)。

**背景**：Sophotech 约 50 个微服务运行在单个 Kubernetes 集群中，原使用 RabbitMQ 处理任务队列、pub/sub 事件和服务间 RPC。随着流量增长，RabbitMQ 的集群维护、镜像队列、shovel 配置带来高额运维负担，且突发流量下队列堆积严重。

**优化措施**：

1. 用 NATS Core 的 request-reply 替代 RabbitMQ 的 RPC；
2. 用 NATS subject 替代 exchange/queue 的复杂拓扑；
3. 采用 dual publishing + canary consumers 渐进迁移，最终 cutover。

**效果**：

| 指标 | RabbitMQ 基线 | NATS 优化后 |
| ------ | --------------- | ------------- |
| P99 延迟 | ~150 ms | ~40 ms |
| 每周运维时间 | 数小时 | < 1 小时 |
| 突发流量队列/流滞后 | 数分钟 | 数秒内 |
| 集群组件 | shovels、mirrors、复杂调优 | 单一 NATS 二进制 |

### LinkedIn：TopicGC 清理元数据提升集群性能

> 来源：[TopicGC: How LinkedIn cleans up unused metadata for its Kafka clusters](https://engineering.linkedin.com/blog/2022/topicgc_how-linkedin-cleans-up-unused-metadata-for-its-kafka-clu)（LinkedIn Engineering，2022）。

**背景**：LinkedIn 的最大 Kafka 集群中，长期累积的未使用 topic 导致 ZooKeeper 响应体积膨胀至 0.75 MB，接近 1 MB 的可用性阈值，引发 controller 初始化瓶颈和集群性能下降。

**优化措施**：

1. 开发 TopicGC 服务，自动检测、封存并删除未使用 topic；
2. 删除前做最终使用检查，避免误删；
3. 结合 Nuage 自助门户与 Bean Counter 成本归属，推动业务主动清理。

**效果**：

| 指标 | 优化前 | 优化后 |
| ------ | -------- | -------- |
| 未使用 topic 占比 | — | 下降约 20 % |
| 生产/消费性能 | 基线 | 提升至少 30 % |
| ZooKeeper 响应体积 | 0.75 MB | 回到安全水位 |

**启示**：性能瓶颈不一定在磁盘或网络，元数据膨胀同样会拖垮大规模 Kafka 集群。建立 topic 生命周期治理机制，是长期保持高性能的关键。
