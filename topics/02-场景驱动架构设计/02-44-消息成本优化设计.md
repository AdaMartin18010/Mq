## 2.44.3 NATS成本优化

### 优化实现

```go
// 存储成本优化（JetStream）
js, _ := nc.JetStream()
js.AddStream(&nats.StreamConfig{
    Name:     "ORDERS",
    Subjects: []string{"orders.*"},
    Storage:  nats.FileStorage,
    MaxAge:   7 * 24 * time.Hour,  // 7天保留
    MaxBytes: 10 * 1024 * 1024 * 1024,  // 10GB限制
    Compression: nats.S2Compression,  // 压缩
})

// 计算成本优化
// 合理设置连接数和订阅数
// 使用连接池复用连接
connectionPool := NewConnectionPool(10)  // 10个连接池

// 网络成本优化
// 批量发布
for i := 0; i < 100; i++ {
    nc.Publish("orders", data[i])
}
nc.Flush()  // 批量刷新
```

## 2.44.4 RabbitMQ成本优化

### 优化实现

```python
# 存储成本优化
# 设置消息TTL和队列最大长度
channel.queue_declare(
    queue='orders',
    arguments={
        'x-message-ttl': 3600000,  # 1小时TTL
        'x-max-length': 10000,  # 最大10000条
        'x-max-length-bytes': 1073741824,  # 最大1GB
    }
)

# 计算成本优化
# 合理设置预取数量
channel.basic_qos(prefetch_count=100)

# 网络成本优化
# 批量发布
messages = [f'message {i}' for i in range(100)]
for msg in messages:
    channel.basic_publish(
        exchange='orders',
        routing_key='',
        body=msg
    )
```

## 2.44.6 成本优化策略决策表

【论证】成本优化需要在存储、计算、网络、运维四个维度做取舍，过度优化可能牺牲可用性或延迟。下表列出主要策略与适用条件：

| 优化策略 | 适用场景 | 预期收益 | 主要风险 |
| -------- | -------- | -------- | -------- |
| **消息压缩（snappy/lz4/gzip）** | 大文本/JSON 消息、重复字段多 | 存储与网络降 30%-70% | CPU 开销增加，延迟微涨 |
| **存储分层（热 SSD / 冷 HDD / 归档对象存储）** | 访问冷热不均、合规长期保存 | 存储成本降 40%-60% | 冷数据读取延迟高 |
| **保留周期缩短 / TTL** | 日志、事件溯源快照、可重放场景 | 存储线性下降 | 审计/重放能力受损 |
| **副本数/分区数精简** | 测试环境、可容忍单副本风险 | 存储与网络降 30% | 可用性降低，需配合机架感知 |
| **批量发送与连接复用** | 高吞吐生产端 | 网络请求数降 50%+ | 延迟略有增加 |
| **预留实例 / Spot 实例** | 公有云长期稳定负载 / 可中断任务 | 计算降 20%-70% | Spot 被回收需容错 |
| **Serverless 按调用计费** | 流量波动大、事件驱动函数 | 低峰期成本极低 | 冷启动与并发限制需规划 |

选型建议：

- 核心交易链：优先压缩 + 保留策略，不降低副本。
- 日志/telemetry：保留周期 + 存储分层 + Spot 处理。
- Serverless：参考 [1.48 Serverless 事件架构与函数消息](../01-基础概念与对比分析/01-48-Serverless事件架构与函数消息.md) 评估并发与冷启动成本。
- 多云联邦：跨区复制会产生冗余存储与出口流量，参考 [1.51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md) 做流量成本建模。

### 成本优化配置示例

`config-templates/cost-optimize-config.properties` 中的关键参数：

```properties
# 资源成本优化配置
cost.optimize.resource.enabled=true
cost.optimize.resource.cpu.target.usage=0.8
cost.optimize.resource.memory.target.usage=0.8
cost.optimize.resource.auto.scale.enabled=true
cost.optimize.resource.auto.scale.min.instances=2
cost.optimize.resource.auto.scale.max.instances=10

# 存储成本优化配置
cost.optimize.storage.enabled=true
cost.optimize.storage.compression.enabled=true
cost.optimize.storage.compression.type=snappy
cost.optimize.storage.tiering.enabled=true
cost.optimize.storage.tiering.hot.storage=ssd
cost.optimize.storage.tiering.cold.storage=hdd
cost.optimize.storage.retention.days=7

# 网络成本优化配置
cost.optimize.network.enabled=true
cost.optimize.network.batch.enabled=true
cost.optimize.network.batch.size=32768
cost.optimize.network.compression.enabled=true
cost.optimize.network.compression.type=snappy

# 成本监控配置
cost.optimize.monitor.enabled=true
cost.optimize.monitor.metrics=resource_cost,storage_cost,network_cost,operation_cost
cost.optimize.monitor.alert.enabled=true
cost.optimize.monitor.alert.threshold.percentage=20
```

## 2.44.7 成本优化与跨域和可观测对齐

成本优化不是孤立活动，需要与架构选择联动。【论证】在跨域、Serverless 和可观测化场景中，以下三类成本容易被低估：

1. **跨域/联邦流量成本**：多云、边缘到云端的复制流量通常按出口带宽计费。需要在容量规划阶段把跨区复制因子与带宽一并计入，参考 [1.51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md) 与 [2.41 消息容量规划设计](02-41-消息容量规划设计.md)。
2. **Serverless 函数成本**：函数按调用次数和执行时长计费，消息积压触发 KEDA 扩容后，并发数与冷启动次数会显著影响账单。需要把吞吐需求换算为并发预算与超时策略，参考 [1.48 Serverless 事件架构与函数消息](../01-基础概念与对比分析/01-48-Serverless事件架构与函数消息.md)。
3. **可观测性存储成本**：消息追踪、指标、日志的长期保留会超过消息本身存储。OpenTelemetry 语义约定建议对采样率与保留周期做治理，详见 [1.50 OpenTelemetry 消息语义约定与全链路追踪](../01-基础概念与对比分析/01-50-OpenTelemetry消息语义约定与全链路追踪.md)。

成本监控检查项：

| 检查项 | 阈值/目标 | 处理动作 |
| -------- | ---------- | ---------- |
| 单消息存储成本 | 环比下降 ≥ 5% / 季度 | 评估压缩、分层、TTL |
| 跨区复制流量占比 | < 总流量的 30% | 优化路由、启用边缘聚合 |
| Serverless 冷启动占比 | < 10% 调用 | 调整 KEDA 冷却时间与最小副本 |
| 可观测存储占比 | < 消息存储的 50% | 调整采样率、缩短保留周期 |

落地检查清单与命令见 [03-60-消息成本优化实践指南](../03-架构与运维实践/03-60-消息成本优化实践指南.md)。
