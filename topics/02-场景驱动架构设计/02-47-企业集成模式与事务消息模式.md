## 2.47.1 EIP 概述与项目对齐

### EIP 目录简介

Enterprise Integration Patterns（EIP）由 Gregor Hohpe 与 Bobby Woolf 在 2003 年提出，是企业应用集成领域的事实标准模式语言。EIP 官网的 Messaging Patterns 目录收录 65 个与消息相关的模式，按 Channel、Message Construction、Routing、Transformation、Endpoint、System Management 等维度组织，为 Kafka、RabbitMQ、NATS、Pulsar、Redis Stream、MQTT 等现代消息系统提供了独立于厂商的设计词汇。

EIP 的核心价值在于：

1. **统一术语**：同一方案在不同系统里的名称不同，EIP 提供了跨产品的通用名称（如 Message Router、Dead Letter Channel）。
2. **设计指导**：每个模式描述问题、方案与 trade-off，帮助架构师在消息系统之上做组合设计。
3. **可迁移性**：当业务从 RabbitMQ 迁往 Kafka 或 NATS 时，EIP 词汇可保留，具体实现才替换。

## 2.47.2 Outbox 发件箱模式

### 双写不一致问题

微服务中常见的操作是：更新数据库并发布事件。若先写库再发消息，可能崩溃导致消息丢失；若先发消息再写库，可能消息已发出但事务回滚，产生“幽灵事件”。这就是**双写问题（Dual Write Problem）**：数据库与消息代理无法通过普通 ACID 事务原子化。

传统 2PC（两阶段提交）可解决原子性，但会引入协调者单点、阻塞与跨系统耦合，现代云原生架构通常避免使用。

### 事务性发件箱 + CDC 转发

Outbox 模式的核心思路：把“要发的消息”也作为一条记录写入业务数据库的 `outbox_events` 表，与业务表更新放在**同一个本地事务**中。事务提交后，由 CDC（Change Data Capture）工具读取数据库日志，把 outbox 表变更转发到 Kafka 等消息系统。

参与者角色：

- **Sender**：业务服务，负责在本地事务中写业务表 + outbox 表。
- **Database**：业务数据库，同时保存业务状态与待发送消息。
- **Message outbox**：关系型数据库中的表，或 NoSQL 中文档的一个属性。
- **Message relay**：CDC 进程，将 outbox 记录投递到消息代理。

该方案的优势：

1. 不依赖 2PC。
2. 消息仅在业务事务提交后才会被转发。
3. 同一聚合的事件顺序可由数据库主键或时间戳保证。

### 各系统实现要点

| 实现方式 | 适用数据库/消息系统 | 关键机制 | 特点 |
| --- | --- | --- | --- |
| Kafka + Debezium | PostgreSQL / MySQL → Kafka | 逻辑解码 / binlog + Debezium Outbox Event Router SMT | 生态成熟，自动路由 topic，支持 Avro/JSON |
| PostgreSQL 逻辑复制 | PostgreSQL → 自定义消费端 | `pgoutput` / `wal2json` 解析 outbox 表 INSERT | 灵活但需自研 relay |
| RocketMQ 事务消息 | 任意业务库 → RocketMQ | 本地事务 + 事务消息回查 | 不依赖 outbox 表，利用 RocketMQ 原生事务能力 |
| 自研轮询转发 | 任意关系库 → 任意 MQ | 定时扫 outbox 表并删除已转发记录 | 简单，但有轮询延迟与删除风险 |

> 注：CDC 转发可能因 relay 崩溃重试导致消息重复发布，因此消费端必须幂等（配合 Inbox 模式）。

### 代码示例

以下示例展示 PostgreSQL outbox 表 DDL、业务事务写入，以及 Debezium connector 配置。

```sql
-- outbox 表 DDL（Debezium 默认约定）
CREATE TABLE outbox_events (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregatetype VARCHAR(255) NOT NULL,  -- 用于路由 topic，如 Order
    aggregateid   VARCHAR(255) NOT NULL,  -- Kafka message key，保证分区顺序
    type          VARCHAR(255) NOT NULL,  -- 事件类型，如 OrderCreated
    payload       JSONB        NOT NULL,  -- 事件负载
    created_at    TIMESTAMP    NOT NULL DEFAULT NOW()
);
```

```java
// 业务服务：同一事务写业务表 + outbox 表
@Transactional
public void createOrder(CreateOrderCommand cmd) {
    Order order = orderRepository.save(new Order(cmd));

    OutboxEvent event = OutboxEvent.builder()
        .aggregatetype("Order")
        .aggregateid(order.getId().toString())
        .type("OrderCreated")
        .payload(Json.writeValueAsBytes(order.toEvent()))
        .build();

    outboxRepository.save(event);  // 与 order 同一事务
}
```

## 2.47.3 Inbox 收件箱模式

### 消费端幂等的模式化

消息代理通常提供“至少一次”投递保证，网络重传、消费者重启或发布者重试都可能导致同一条消息被处理多次。Inbox 模式把消费端幂等从“内存 Set”升级为**数据库化的去重表/处理状态机**，是 Outbox 模式的天然搭档。

常见实现策略：

1. **去重表**：以消息唯一 ID 为主键或唯一索引，处理前 INSERT，重复则跳过。
2. **业务唯一约束**：把业务键设为唯一索引（如订单号），让数据库在重复处理时报错或忽略。
3. **处理状态机**：记录每条消息的处理状态（PENDING/SUCCESS/FAILED），结合重试与死信。

> 与 [2.25 消息幂等性设计](02-25-消息幂等性设计.md) 的关系：2.25 侧重各系统原生幂等能力；本文强调跨系统的“收件箱”架构模式。

### 代码示例

以下示例展示 Inbox 去重表 DDL 与消费端幂等处理逻辑。

```sql
-- inbox 去重表
CREATE TABLE inbox_records (
    message_id   VARCHAR(255) PRIMARY KEY,
    source_topic VARCHAR(255) NOT NULL,
    processed_at TIMESTAMP    NOT NULL DEFAULT NOW(),
    status       VARCHAR(32)  NOT NULL CHECK (status IN ('PENDING','SUCCESS','FAILED'))
);

CREATE INDEX idx_inbox_status ON inbox_records(status);
```

```java
@Transactional
public void onOrderCreated(OrderCreatedEvent event, String messageId) {
    // 尝试插入去重记录；重复 key 直接抛出 DuplicateKeyException，外层跳过
    try {
        inboxRepository.insert(messageId, "order-events", "PENDING");
    } catch (DuplicateKeyException e) {
        log.warn("Duplicate message {}, skipped", messageId);
        return;
    }

    try {
        orderService.createOrder(event);
        inboxRepository.updateStatus(messageId, "SUCCESS");
    } catch (Exception e) {
        inboxRepository.updateStatus(messageId, "FAILED");
        throw e;  // 触发消息重试或进入死信队列
    }
}
```

## 2.47.4 Saga 长事务模式

### 编排式 vs 协同式

Saga 模式将跨服务的业务事务拆分为一系列本地事务，每个本地事务提交后通过消息触发下一步；若某步失败，则执行**补偿事务**回滚已完成的步骤。Saga 不依赖 2PC，以最终一致性换取可用性与分区容错性。

协调方式有两种：

| 维度 | 编排式 Saga（Orchestration） | 协同式 Saga（Choreography） |
| --- | --- | --- |
| 控制中心 | 独立的 Saga Orchestrator | 无中心，各服务通过事件触发彼此 |
| 通信方式 | Orchestrator 主动发送命令/调用参与者 | 服务完成本地事务后发布领域事件 |
| 流程可见性 | 高，状态集中在 Orchestrator | 低，流程散落在各服务事件订阅中 |
| 耦合度 | 参与者需知道 Orchestrator 的命令契约 | 参与者需知道彼此的事件契约 |
| 调试难度 | 较低 | 较高，需追踪事件链 |
| 适用场景 | 步骤多、分支复杂、需要长流程控制 | 步骤少、事件驱动、服务自治要求高 |
| 典型工具 | Temporal、Camunda、Netflix Conductor、自研状态机 | Kafka / NATS / RabbitMQ 事件总线 |

### 补偿事务设计

补偿事务不是数据库自动回滚，而是业务上定义的“撤销操作”。设计补偿时应注意：

1. **幂等性**：补偿事务本身可能被重试，必须幂等。
2. **可补偿性**：尽量把不可补偿操作（如已发货）放在 Saga 的最后一步。
3. **语义撤销 vs 业务撤销**：支付场景通常用“退款”而不是删除记录；库存场景用“释放库存”。
4. **失败重试**：补偿事务也可能失败，需记录状态并支持人工介入或定时重试。

### 与 2PC 的取舍

| 特性 | Saga | 2PC |
| --- | --- | --- |
| 一致性级别 | 最终一致 | 强一致 |
| 隔离性 | 无全局隔离，需业务补偿处理异常 | 全局隔离 |
| 可用性 | 高，参与者故障不阻塞整体 | 协调者/参与者故障可能阻塞 |
| 性能 | 好，本地事务 + 异步消息 | 差，多轮网络协调与锁定 |
| 复杂度 | 补偿逻辑复杂 | 协议复杂、运维负担重 |
| 推荐场景 | 微服务、跨库长流程、互联网高并发 | 短事务、强一致金融核心（逐渐被淘汰） |

### 状态机描述

以电商下单为例，Saga 状态机如下：

```
[创建订单 PENDING]
    |
    v
[扣减库存] --失败--> [补偿：恢复库存] -->
    |                         |
    v                         v
[扣减余额] --失败--> [补偿：退款] ----> [订单状态：已取消 CANCELLED]
    |
    v
[订单确认] ----------------------------> [订单状态：已完成 COMPLETED]
```

伪代码实现（编排式）：

```python
class OrderSaga:
    def execute(self, order_id):
        try:
            self.order_service.create(order_id)
            self.inventory_service.reserve(order_id)
            self.payment_service.charge(order_id)
            self.order_service.confirm(order_id)
        except InventoryException:
            self.compensate_inventory(order_id)
            self.order_service.cancel(order_id)
        except PaymentException:
            self.compensate_payment(order_id)
            self.compensate_inventory(order_id)
            self.order_service.cancel(order_id)

    def compensate_inventory(self, order_id):
        retry_until_success(lambda: self.inventory_service.release(order_id))

    def compensate_payment(self, order_id):
        retry_until_success(lambda: self.payment_service.refund(order_id))
```

## 2.47.5 模式选型决策树

当业务需要“更新数据库 + 发消息”或“跨服务长事务”时，可按下述流程选择模式：

1. **是否只需保证“本地事务 + 事件发布”的原子性？**
   - 是 → 使用 **Outbox 模式**（Kafka+Debezium、RocketMQ 事务消息或自研 CDC）。
   - 否 → 进入下一步。

2. **消息消费端是否可能收到重复消息？**
   - 是 → 使用 **Inbox 模式**（去重表/唯一约束/处理状态机）。
   - 否 → 进入下一步。

3. **业务操作是否跨越多个服务数据库？**
   - 否 → 使用本地 ACID 事务即可。
   - 是 → 进入下一步。

4. **是否要求强一致且可接受阻塞与协调者单点？**
   - 是 → 谨慎评估 **2PC**（现代架构通常不推荐）。
   - 否 → 使用 **Saga 模式**。

5. **Saga 流程是否复杂、步骤多、需要可视化与人工干预？**
   - 是 → 选择 **编排式 Saga**（Temporal / Camunda / 自研 Orchestrator）。
   - 否 → 选择 **协同式 Saga**（基于 Kafka / NATS / RabbitMQ 事件驱动）。

6. **是否需要同时保证“发事件原子性”与“跨服务 Saga”？**
   - 是 → Outbox + Inbox + Saga 组合使用：Saga 每一步内部用 Outbox 发事件，消费者用 Inbox 去重。
