## 2.27.1 分区场景与顺序权衡

### 常见场景

1. **负载均衡**
   - 消息分散到多个分区/队列，提升并行处理能力。
   - 避免单节点成为吞吐瓶颈。

2. **顺序保证**
   - 同一业务键（如 `orderId`、`userId`）路由到同一分区，保证局部分区有序。
   - 跨分区并行处理，但不再保证全局顺序。

3. **扩展性与隔离**
   - 按租户、地区、业务线分区，实现资源隔离与独立扩缩容。
   - 多活架构中按区域分区，减少跨区复制流量。

### 分区与顺序权衡

【论证】分区是提升并行度的主要手段，但会牺牲全局顺序。Kafka 保证分区内有序；若业务需要全局有序，必须将相关消息路由到同一分区，或通过应用层排序补偿。

| 需求 | 分区策略 | 结果 |
| ---- | -------- | ---- |
| 高吞吐 + 无顺序要求 | Round-Robin / 随机 | 最大并行度 |
| 高吞吐 + 局部队序 | Key Hash | 同 Key 同分区有序 |
| 全局有序 | 单分区 / 应用层排序 | 并行度最低 |
| 按业务隔离 | 自定义分区器（地区/租户） | 分区即边界 |

## 2.27.2 分区策略选型

### 策略对比决策表

| 策略 | 顺序保证 | 负载均衡 | 适用场景 | 注意事项 |
| ---- | -------- | -------- | -------- | -------- |
| Key Hash | 同 Key 有序 | 取决于 Key 分布 | 订单、用户事件 | Key 倾斜会导致热点 |
| Round-Robin | 无 | 优 | 日志、指标 | 无法保证消息顺序 |
| 自定义分区器 | 可控 | 可控 | 业务规则路由 | 需要充分测试 |
| 按时间/地理分区 | 区间内有序 | 中 | 时序数据、多活架构 | 扩容需重新分区 |

【论证】分区键应优先选择业务上天然分散且需要局部顺序的字段（如 `userId`、`orderId`）。避免选择枚举值、状态码等低基数字段，否则容易产生分区倾斜。

### 分区数量规划

| 场景 | 推荐分区数 | 说明 |
| ---- | ---------- | ---- |
| 常规业务 Topic | 6 ~ 24 | 满足大部分微服务事件 |
| 高吞吐日志/埋点 | 48 ~ 96 | 需确认 broker 文件句柄与内存 |
| 顺序敏感 Topic | 较少（6 ~ 12） | 通过 Key Hash 保证局部队序 |
| 多区域隔离 | 按区域 × 业务键 | 减少跨区复制与冲突 |

分区数倒推公式：目标分区数 = `(目标总吞吐 / 单分区吞吐上限) × 1.2`，并确保大于等于消费者实例数。

## 2.27.3 Kafka 分区

Kafka 通过 `key` 哈希或自定义分区器选择分区：

```java
// Key Hash 分区
ProducerRecord<String, String> record = new ProducerRecord<>(
    "orders",
    orderId,  // Key 用于分区
    orderJson
);

// 自定义分区器
public class OrderPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                        Object value, byte[] valueBytes, Cluster cluster) {
        return Math.abs(key.hashCode()) % cluster.partitionCountForTopic(topic);
    }
}

// 创建 Topic 时指定分区数
// kafka-topics.sh --create --topic orders --partitions 6 --replication-factor 3
```

Kafka 分区数只增不减；扩容后旧数据不会自动迁移，新增消息才会写到新分区。

## 2.27.4 NATS 分区

NATS Core 无原生 Topic-Partition 概念，可通过 Subject 前缀实现应用层分区：

```go
partitionID := hash(orderID) % 6
subject := fmt.Sprintf("orders.partition.%d", partitionID)
nc.Publish(subject, data)

// JetStream 使用 Stream 实现分区语义
js.AddStream(&nats.StreamConfig{
    Name:     "ORDERS",
    Subjects: []string{"orders.partition.*"},
})
```

## 2.27.5 RabbitMQ 分区

RabbitMQ 通过多个队列实现应用层分区：

```python
partition_count = 6
for i in range(partition_count):
    queue_name = f"orders-partition-{i}"
    channel.queue_declare(queue=queue_name, durable=True)

partition = hash(order_id) % partition_count
queue_name = f"orders-partition-{partition}"
channel.basic_publish(exchange='', routing_key=queue_name, body=message)
```

生产环境建议使用一致性哈希，并在扩容时尽量减少数据重分布。

## 2.27.6 Pulsar 与 Redis Stream 分区

Pulsar 通过 Ledger/Bundle 实现分区，支持 `hashing`、`round-robin`、`custom` 三种路由模式：

```java
producer.newMessage()
    .key(orderId)
    .value(payload)
    .send();
```

Redis Stream 通过应用层键散列 + Consumer Group 实现分区：

```bash
# 不同业务键散列到不同 Stream
XADD orders:partition:0 * orderId 1001 status created
XADD orders:partition:1 * orderId 1002 status paid
XGROUP CREATE orders:partition:0 order-consumer $
```

## 2.27.7 多云与边缘场景的分区考量

在多云、边缘联邦架构中，分区不仅是性能手段，也是数据驻留与冲突隔离的基础。参见 [1.51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md)。

| 场景 | 分区策略 | 关键考量 |
| ---- | -------- | -------- |
| 区域数据驻留 | 按区域分区 | 原始 PII 不出区，脱敏后再跨区同步 |
| 边缘上行汇聚 | 按设备/产线分区 | 边缘 broker 本地聚合，eKuiper 过滤后再上云 |
| 多活双写 | 按单元化键分区 | 避免跨区双写冲突，参见 [02-51](../02-场景驱动架构设计/02-51-多活消息架构设计.md) |
| 灾备只读副本 | 主区分区映射到灾备区 | MM2 / Cluster Linking 保持分区结构 |

## 2.27.8 分区最佳实践

### 设计建议

1. **分区键选择**
   - 优先选择高基数、业务上需要局部顺序的字段。
   - 避免低基数字段（如状态码、枚举值）导致热点。
   - 跨租户场景在键前缀加入 `tenantId`，防止租户间相互影响。

2. **分区数量**
   - 常规业务 6~24 个分区；高吞吐场景 48~96。
   - 分区数应大于等于消费者实例数，并预留 1.5~2 倍扩容空间。
   - 顺序敏感 Topic 分区数不宜过多。

3. **负载均衡与监控**
   - 设置 `partition.alert.imbalance.threshold=0.2`，监控各分区消息量差异。
   - 使用 `CooperativeStickyAssignor` 减少 Kafka 再均衡停顿。
   - 定期运行 `partition-check.sh` 检查分区健康。

### 配置模板引用

分区配置统一引用 `topics/config-templates/partition-config.properties`：

```properties
# 消息分区配置模板（引用 topics/config-templates/partition-config.properties）
kafka.partition.strategy=key-hash
kafka.partition.count=6
kafka.partition.replication.factor=3
kafka.partition.custom.class=com.example.CustomPartitioner

nats.partition.enabled=true
nats.partition.strategy=subject-prefix
nats.partition.count=6
nats.partition.subject.pattern=orders.partition.{partition}

rabbitmq.partition.enabled=true
rabbitmq.partition.strategy=queue
rabbitmq.partition.count=6
rabbitmq.partition.queue.pattern=orders-partition-{partition}

partition.key.field=id
partition.key.hash.algorithm=md5

load.balance.enabled=true
load.balance.strategy=round-robin
load.balance.monitor.enabled=true

partition.monitor.enabled=true
partition.monitor.metrics=partition_count,partition_size,partition_lag,partition_throughput
partition.alert.enabled=true
partition.alert.imbalance.threshold=0.2
partition.alert.lag.threshold=10000
partition.alert.channels=email,dingtalk
```
