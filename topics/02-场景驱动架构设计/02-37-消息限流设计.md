## 2.37.2 Kafka限流

### 限流实现

```java
// Producer限流
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("max.in.flight.requests.per.connection", 5);  // 限制并发请求
props.put("batch.size", 16384);  // 批量大小限制
props.put("linger.ms", 10);  // 延迟发送

// Consumer限流
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("fetch.min.bytes", 1);  // 最小拉取字节
props.put("fetch.max.wait.ms", 500);  // 最大等待时间
props.put("max.partition.fetch.bytes", 1048576);  // 分区拉取限制

// 应用层限流
RateLimiter rateLimiter = RateLimiter.create(1000.0);  // 每秒1000条
for (int i = 0; i < messages.size(); i++) {
    rateLimiter.acquire();
    producer.send(new ProducerRecord<>("orders", messages.get(i)));
}
```

## 2.37.3 NATS限流

### 限流实现

```go
// 订阅限流
sub, err := nc.Subscribe("orders.*", func(msg *nats.Msg) {
    processMessage(msg)
})
if err != nil {
    log.Fatal(err)
}

// 设置限流
sub.SetPendingLimits(1000, 10*1024*1024)  // 1000条消息或10MB

// 应用层限流
rateLimiter := rate.NewLimiter(rate.Limit(1000), 100)  // 每秒1000条
for _, msg := range messages {
    if err := rateLimiter.Wait(context.Background()); err != nil {
        log.Fatal(err)
    }
    nc.Publish("orders", msg)
}
```

## 2.37.4 RabbitMQ限流

### 限流实现

```python
# Consumer限流
channel.basic_qos(
    prefetch_count=10,  # 每次最多处理10条消息
    prefetch_size=0,  # 不限制大小
    global_=False  # 仅对当前channel生效
)

# Producer限流
rate_limiter = RateLimiter(max_calls=1000, period=1.0)  # 每秒1000条

def publish_with_rate_limit(message):
    rate_limiter.acquire()
    channel.basic_publish(
        exchange='orders',
        routing_key='',
        body=message
    )

# 应用层限流
from ratelimit import limits, sleep_and_retry

@sleep_and_retry
@limits(calls=1000, period=1)
def publish_message(message):
    channel.basic_publish(
        exchange='orders',
        routing_key='',
        body=message
    )
```

## 2.37.6 限流策略与粒度决策表

【论证】限流算法与粒度的选择直接影响系统的公平性、突发承载能力和实现复杂度。下表给出常见组合：

| 限流算法 | 特点 | 突发支持 | 实现复杂度 | 适用场景 |
| ---------- | ------ | ---------- | ------------ | ---------- |
| **固定窗口** | 按时间窗口计数，窗口边界易突发 | 差 | 低 | 简单配额、日志限流 |
| **滑动窗口** | 平滑统计最近窗口内的请求 | 中 | 中 | API 网关、用户级限流 |
| **令牌桶** | 允许一定突发，速率可控 | 好 | 中 | 消息生产、网络流量整形 |
| **漏桶** | 输出速率绝对平滑 | 无 | 中 | 严格匀速下游保护 |

限流粒度决策：

| 粒度 | 控制对象 | 优点 | 缺点 |
| ------ | ---------- | ------ | ------ |
| **全局** | 整个集群/topic | 防止整体过载 | 无法隔离问题租户 |
| **分区/队列** | 单个分区或队列 | 避免单点热点 | 需要预知分区分布 |
| **用户/租户** | 按客户端身份 | 公平性最好 | 状态多，需分布式计数 |
| **优先级** | 高/中/低优先级流 | 保障关键业务 | 配置复杂，需防止低优先级饿死 |

### 限流配置示例

`config-templates/rate-limit-config.properties` 中的关键参数：

```properties
# Producer限流配置
rate.limit.producer.enabled=true
rate.limit.producer.strategy=token_bucket
rate.limit.producer.rate.per.second=1000
rate.limit.producer.burst.size=2000
rate.limit.producer.max.in.flight.requests=5
rate.limit.producer.batch.size=16384
rate.limit.producer.linger.ms=10

# Consumer限流配置
rate.limit.consumer.enabled=true
rate.limit.consumer.strategy=token_bucket
rate.limit.consumer.rate.per.second=1000
rate.limit.consumer.burst.size=2000
rate.limit.consumer.max.poll.records=500
rate.limit.consumer.prefetch.count=10

# 全局限流配置
rate.limit.global.enabled=true
rate.limit.global.strategy=token_bucket
rate.limit.global.rate.per.second=10000
rate.limit.global.burst.size=20000

# 用户限流配置
rate.limit.user.enabled=true
rate.limit.user.strategy=token_bucket
rate.limit.user.rate.per.second=100
rate.limit.user.burst.size=200
rate.limit.user.quota.enabled=true
rate.limit.user.quota.daily=1000000

# 限流处理策略配置
rate.limit.handling.strategy=wait
rate.limit.handling.wait.timeout.ms=1000
rate.limit.handling.degrade.enabled=false
```

## 2.37.7 自适应限流与跨域配额

静态限流阈值难以应对流量模式变化。【论证】在生产环境中，建议引入自适应限流：根据延迟、错误率、队列深度动态调整令牌发放速率。

自适应限流参数（来自配置模板）：

```properties
# 限流自动调整配置
rate.limit.auto.adjust.enabled=false
rate.limit.auto.adjust.strategy=adaptive
rate.limit.auto.adjust.interval.minutes=5
rate.limit.auto.adjust.min.rate=100
rate.limit.auto.adjust.max.rate=10000
rate.limit.auto.adjust.target.rejected.rate=0.05
```

跨域与 Serverless 场景：

- **多云联邦**：跨集群复制工具（如 MM2、NATS Supercluster）本身会占用出口带宽，需要为复制流量单独设置配额，参考 [1.51 多云与边缘消息联邦技术](../01-基础概念与对比分析/01-51-多云与边缘消息联邦技术.md)。
- **Serverless 函数**：函数并发数、执行时长与消息拉取速率强相关，KEDA  scaler 需要根据消息积压动态调整副本数，避免冷启动雪崩，见 [1.48 Serverless 事件架构与函数消息](../01-基础概念与对比分析/01-48-Serverless事件架构与函数消息.md)。
- **可观测性**：限流拒绝率、等待数应接入监控，建议阈值：拒绝率 > 10% 或等待数 > 1000 时告警，落地细节见 [03-53-消息限流与流量控制指南](../03-架构与运维实践/03-53-消息限流与流量控制指南.md)。
