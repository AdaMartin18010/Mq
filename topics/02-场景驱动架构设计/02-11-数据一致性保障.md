## 2.11.1 一致性模型

### 一致性级别

1. **强一致性**
   - 所有副本同步更新后再确认
   - 高延迟，高可靠性，适合金融交易

2. **最终一致性**
   - 异步复制，主节点确认即可
   - 低延迟，最终一致，适合日志聚合

3. **弱一致性**
   - 不保证一致性，可能丢失消息
   - 最低延迟，适合实时监控埋点

## 2.11.2 Kafka一致性保障

### ISR机制

```properties
# 至少2个副本同步
min.insync.replicas=2

# 生产者确认
acks=all

# 禁止不干净Leader选举
unclean.leader.election.enable=false
```

### 事务支持

```java
// 事务性Producer
producer.initTransactions();
producer.beginTransaction();
producer.send(record);
producer.commitTransaction();
```

Kafka 4.0 继续支持幂等 Producer 与事务 API，KRaft 模式下元数据一致性由 Raft 保证，减少了 ZK 时代的会话超时导致的不确定性【论证】。

## 2.11.3 NATS一致性保障

### JetStream持久化

```go
// 创建持久化Stream
js.AddStream(&nats.StreamConfig{
    Name:     "ORDERS",
    Subjects: []string{"orders.*"},
    Replicas: 3,
})
```

### 消息确认

```go
// 手动确认
msg.Ack()
```

JetStream 通过 Stream Replicas 与 Ack 机制提供至少一次（可配置为恰好一次）投递语义【论证】。

## 2.11.4 RabbitMQ一致性保障

### 持久化配置

```python
# 持久化队列
channel.queue_declare(queue='task_queue', durable=True)

# 持久化消息
channel.basic_publish(
    exchange='',
    routing_key='task_queue',
    body=message,
    properties=pika.BasicProperties(
        delivery_mode=2,  # 持久化
    ))
```

结合 Publisher Confirm 与 Quorum Queue，RabbitMQ 可在 Broker 层面提供更接近强一致的投递保障。

## 2.11.5 最佳实践

### 一致性选择

- **金融交易**：强一致性（Kafka事务）
- **日志聚合**：最终一致性（Kafka异步复制）
- **实时通信**：弱一致性（NATS Core）

### 保障措施

1. **配置正确**：设置合适的副本数和确认机制
2. **监控告警**：监控副本同步状态与未确认消息数
3. **定期验证**：通过对账或幂等消费验证数据一致性

## 2.11.6 一致性保障决策矩阵

### 决策表

| 业务容忍度 | 推荐系统/模式 | 关键配置 | RPO/RTO 估算 |
| --- | --- | --- | --- |
| 零容忍（金融支付） | Kafka 事务 + acks=all | min.insync.replicas=2, enable.idempotence=true | RPO≈0，RTO 秒级 |
| 分钟级不一致（订单） | Kafka acks=all + ISR | unclean.leader.election=false | RPO≈0，RTO 秒级 |
| 秒级不一致（日志） | Kafka acks=1 或 NATS JetStream | replication.factor=3 | RPO 秒级 |
| 可接受丢失（埋点） | NATS Core / Redis Stream | 无持久化或异步持久化 | RPO>0 |
| 传统企业事务 | RabbitMQ 持久化 + 发布确认 | delivery_mode=2, confirmSelect | RPO≈0 |
| 事件溯源写模型 | Kafka 单分区 + 聚合根键 | 聚合根分区键，幂等消费 | RPO≈0 |

## 2.11.7 生产配置示例

### Kafka高一致性配置

```properties
# 引用 config-templates/kafka-producer-config.properties / kafka-server.properties.template
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
transactional.id=my-transactional-id

# Broker 端
min.insync.replicas=2
default.replication.factor=3
unclean.leader.election.enable=false
```

### NATS JetStream配置

```conf
# 引用 config-templates/nats-server.conf.template
jetstream {
  store_dir: "/data/jetstream"
  max_mem_store: 2GB
  max_file_store: 10GB
}
```

### RabbitMQ持久化配置

```python
# 引用 config-templates/rabbitmq-client-config.properties 理念
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
channel.confirm_delivery()  # 启用发布确认

channel.queue_declare(queue='orders', durable=True)
channel.basic_publish(
    exchange='',
    routing_key='orders',
    body=message,
    properties=pika.BasicProperties(
        delivery_mode=2,
        content_type='application/json'
    )
)
```

## 2.11.8 一致性保障与事件溯源

### 聚合根与顺序一致性

在事件溯源架构中，聚合根的状态由一系列有序事件折叠而成。消息系统需保证同一聚合根的事件顺序一致且可重放，否则将出现状态分歧。Kafka 的分区顺序与 NATS JetStream 的 Ordered Consumer 是常见实现载体。

```java
// 以聚合根 ID 作为分区键，保证顺序
String aggregateId = order.getAggregateId();
producer.send(new ProducerRecord<>("order-events", aggregateId, event));
```

事件溯源与一致性设计还需关注快照策略、版本号冲突检测及存储选型，详见 [01-47-事件溯源核心机制与存储选型](../01-基础概念与对比分析/01-47-事件溯源核心机制与存储选型.md)。
