## 2.59.1 消息平台工程定位

平台工程（Platform Engineering）把内部基础设施当作**产品**来建设：识别用户（应用开发者）、定义价值主张、设计用户旅程、度量采用率与满意度【论证】。将其应用于消息基础设施，意味着不再把 Kafka/NATS/MQTT 集群仅当作“运维对象”，而是封装为“消息平台”这一内部产品。

**消息即产品**的核心转换：

| 传统视角 | 平台工程视角 |
| -------- | ------------ |
| Topic 是 broker 上的资源 | Topic/Channel 是平台对外发布的能力条目 |
| Schema 是附属文档 | Schema/契约是产品的 SLA 与兼容性承诺 |
| 申请流程靠工单与人脉 | 申请流程是自助 Golden Path 的用户旅程 |
| 治理靠事后审计 | 治理内嵌到自助流程的自动化门禁中 |

这种转换的价值在于降低应用团队的认知负荷：开发者无需成为 Kafka 分区、MQTT QoS、NATS JetStream 的专家，也能按组织约定安全地发布与消费事件【论证】。平台组则通过标准化接口、配额、命名空间和可观测性，把“每团队各自摸索”变成“可复用的 paved road”。

与 01-37 的衔接：01-37 聚焦事件目录平台的选型与 AsyncAPI 组织级治理；本文聚焦**如何把目录与治理嵌入开发者自助旅程**，即“门户里的消息平台”而非“门户本身选型”。

## 2.59.2 自助服务 Golden Path

Golden Path 是平台工程中的核心概念：为最常见场景提供一条经过验证、受治理、可一键触达的端到端工作流【论证】。消息平台的典型 Golden Path 是开发者从“想发布一个事件”到“生产环境可用”的完整旅程：

```text
1. 发现：在 IDP 搜索已有事件/域，确认是否可复用或需要新建
2. 申请：填写 Topic/Channel 申请表单，选择域、协议、合规等级
3. 契约：提交/关联 AsyncAPI 文档，声明 message schema、binding、owner
4. 校验：CI 自动跑 asyncapi validate + Spectral lint + diff
5. 开通：通过 GitOps/Controller 自动创建 topic、namespace、ACL、配额
6. 接入：开发者拿到 connection string、SDK 示例、监控仪表盘链接
7. 观测：Topic 指标、消费 lag、schema 兼容性在 IDP 中可见
```

每一步都应内嵌最小可用文档与示例，避免开发者离开门户去翻 wiki 或找人问。平台组的目标是让这条路径的前置时间从“天/周”降到“分钟/小时”【估算】，同时不牺牲治理。

与 02-48 设计工作流的衔接：02-48 的六步契约设计流程是 Golden Path 的“契约段”；本文将其扩展为包含平台开通、权限分配、可观测性的完整自助旅程。

## 2.59.3 自助服务等级模型

参考 CNCF 平台工程成熟度模型，自助服务可划分为四个等级。该模型从投资、采用、接口、运营、反馈五个维度评估平台成熟度【论证】。

| 等级 | 名称 | 消息平台特征 | 适用阶段 |
| ---- | ---- | ------------ | -------- |
| L1 手动 | 工单驱动 | 发邮件/工单申请 topic，平台组手工创建；无统一契约仓库 | 初创期、事件化程度低 |
| L2 半自助 | 标准模板 | 提供文档化模板与 Terraform 模块，但仍需人工审批与执行 | 有专门平台组、开始标准化 |
| L3 自助表单 | 门户自助 | IDP 表单 + GitOps 自动开通；Spectral/AsyncAPI CLI 自动校验 | 多团队、中大规模 |
| L4 自助代码/API | 集成服务 | 开发者通过 API/CLI/IDE 插件直接申请，治理完全内嵌，配额与审计自动化 | 平台成熟期 |

演进建议【论证】：

- 不要从 L1 直接跳到 L4。多数组织在 L2→L3 阶段投入产出比最高：先用模板统一，再把模板封装成门户表单。
- 成熟度提升必须与治理同步。L3 的核心不是“表单”，而是表单背后的契约校验、配额自动开通和审计。
- 每一级都要保留逃生通道：特殊场景允许走人工审批，避免平台变成创新的阻塞点。

## 2.59.4 IDP 集成：Backstage 与 EventCatalog

内部开发者门户（IDP）是 Golden Path 的前端。消息平台常见的门户集成有两种路线：复用已有 Backstage 门户，或引入专门的事件门户 EventCatalog。

### Backstage 集成点

Backstage 作为 CNCF Incubating 项目，提供软件目录、TechDocs、Scaffolder、API Docs 等核心能力【论证】。消息平台可复用以下扩展点：

- **Software Catalog**：把每个事件/契约注册为 `API` 实体，`type: asyncapi`，与 `System`、`Domain`、`Owner` 关联，实现所有权与影响面分析。
- **API Docs 插件**：Backstage 的 `@backstage/plugin-api-docs` 原生支持 AsyncAPI 2 与 3 的渲染，底层使用官方 `@asyncapi/react-component`【论证】。
- **API Spectral Linter 插件**：在 API 实体页直接对 AsyncAPI/OpenAPI 运行 Spectral 规则集，把治理前置到浏览阶段。
- **Scaffolder**：把“新建事件契约”封装为软件模板（Software Template），自动在契约仓库创建目录、生成骨架 AsyncAPI、触发 PR。
- **TechDocs**：把事件使用指南、迁移公告、SLO 说明与 API 实体绑定。

Backstage 适合已有门户基础、希望统一 API 发现的组织；其事件能力依赖插件组合，不是开箱即用的事件目录。

### EventCatalog 作为事件门户

EventCatalog 是面向事件驱动架构的专门门户，原生支持 domain / service / message / schema 四级建模，可通过 AsyncAPI 插件从 AsyncAPI 文件自动生成文档与架构图【论证】。

| 维度 | Backstage 路线 | EventCatalog 路线 |
| ---- | -------------- | ----------------- |
| 主要定位 | 通用 IDP，事件是其中一类 API | 专门事件目录与发现平台 |
| AsyncAPI 原生度 | 中（依赖 API Docs / Spectral 插件） | 高（专门 AsyncAPI generator） |
| 团队已有门户成本 | 低（复用已有 Backstage） | 高（新增独立系统） |
| 域/服务/事件建模 | 依赖 Backstage 实体模型 | 原生支持 |
| 适用场景 | 已有 Backstage，追求统一入口 | 事件治理是核心痛点，需专门门户 |

选型建议【论证】：

- 已部署 Backstage 的组织，优先在 Backstage 中注册 AsyncAPI API 实体，用 API Docs 渲染契约，用 Scaffolder 提供自助模板。
- 若事件资产规模大、跨域影响分析需求强，可在 Backstage 之外并行引入 EventCatalog 作为事件目录，二者通过 `catalog-info.yaml` 中的链接互引，避免信息孤岛。
- 中小型组织不必同时维护两套门户，先用 Backstage + AsyncAPI 插件覆盖 80% 场景。

## 2.59.5 治理门禁联动

自助服务不等于无治理。Golden Path 必须在关键节点设置自动化门禁，把 02-56 的契约治理内嵌到平台流程中。

### 契约申请自动校验

开发者提交 AsyncAPI 文档后，CI 应立即运行三层校验：

```yaml
# .github/workflows/message-platform-gate.yaml
name: Message Platform Contract Gate
on:
  pull_request:
    paths:
      - 'contracts/asyncapi/**'
      - '.spectral.yaml'

jobs:
  contract-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Validate AsyncAPI conformance
        run: asyncapi validate contracts/asyncapi/${{ matrix.domain }}/asyncapi.yaml

      - name: Lint governance rules
        run: spectral lint contracts/asyncapi/**/*.yaml --ruleset .spectral.yaml --fail-severity=warn

      - name: Detect breaking changes
        run: |
          git fetch origin ${{ github.base_ref }}
          asyncapi diff contracts/asyncapi/${{ matrix.domain }}/asyncapi.yaml \
            origin/${{ github.base_ref }}:contracts/asyncapi/${{ matrix.domain }}/asyncapi.yaml
```

### 配额与命名空间自动开通

校验通过后，GitOps 控制器（如 Crossplane、Terraform Operator 或自定义 operator）读取 AsyncAPI 中的 binding 信息，自动执行：

- 按租户/域创建命名空间或 topic 前缀（参见 03-38 多租户命名规范）。
- 设置 ACL/账户权限，确保生产者只能写声明的 channel，消费者只能读订阅的 channel。
- 应用配额：吞吐、连接数、topic 数、存储上限（03-38 给出各 broker 的配额配置示例）。

### 审批分级

| 变更类型 | 判定条件 | 审批方式 |
| -------- | -------- | -------- |
| 普通变更 | patch/minor、向后兼容、非敏感域 | 自动合并，通知消费方 |
| 敏感变更 | 涉及 PII/支付/合规域、新增跨租户消费 | 自动校验后，域 owner 人工批准 |
| 破坏性变更 | major、删字段/改类型/改 channel | 必须技术评审 + 消费方影响评审 |

审批分级的目标是让低风险变更快速通过，把人工注意力集中在真正需要判断的变更上。

## 2.59.6 团队拓扑与事件所有权

参考 Team Topologies 方法，消息平台相关团队可分为四类角色：

| 团队类型 | 职责 | 与消息平台的关系 |
| -------- | ---- | ---------------- |
| 平台组（Platform） | 建设并运营消息平台：门户、GitOps 开通、可观测、配额、安全基线 | 产品的 owner，负责 Golden Path 的可用性与治理 |
| 流组（Stream-aligned） | 业务价值流团队，实际生产与消费事件 | 平台用户，通过自助流程申请与维护契约 |
| 赋能组（Enabling） | 架构、安全、合规、数据治理专家 | 制定契约规范、Spectral 规则、审计策略，赋能流组 |
| 复杂子系统组 | 专门处理 schema registry、多活复制、加密等特殊基础设施 | 作为平台能力被封装，流组不直接操作 |

**事件所有权模型**：谁生产事件，谁拥有该事件的契约与生命周期。具体落实：

- AsyncAPI 文档的 `info.contact` 与 Backstage `catalog-info.yaml` 的 `owner` 必须指向生产团队。
- 契约的 major 变更由生产团队发起，但必须征得所有已知消费方代表同意。
- 平台组不拥有业务契约，只拥有平台工具链与治理规则。

反模式警示：若平台组变成所有变更的“审批瓶颈”，通常说明所有权模型不清晰或自助工具不足。

## 2.59.7 平台 KPI 与反模式

### 建议 KPI

| KPI | 定义 | 目标参考【估算】 | 采集来源 |
| --- | ---- | ---------------- | -------- |
| 自助率 | 通过门户/Golden Path 完成的 topic/契约申请占比 | ≥ 80% | IDP 申请日志 |
| 交付前置时间 | 从提交申请到生产可用中位时长 | L3 目标 < 4 小时 | 流程埋点 |
| 契约质量分 | Spectral 规则通过分、必填字段完整度、示例覆盖率 | ≥ 90 分 | CI 与目录平台 |
| 漂移率 | 生产消息与契约不一致的事件占比 | < 5% | 运行时一致性测试 |
| 平台 NPS | 开发者对消息平台的净推荐值 | ≥ 40 | 季度调研 |

### 常见反模式

| 反模式 | 表现 | 纠正 |
| -------- | ---- | ---- |
| 平台组变审批瓶颈 | 所有申请都需人工排队，开发者绕过平台直接找运维 | 把 L1/L2 审批自动化，仅敏感/破坏性变更走人工 |
| 自助无治理 | 表单只收集需求，不校验契约、不控制配额 | 在 L3 阶段必须内嵌 Spectral + diff + 配额自动开通 |
| 门户即终点 | 上线门户后不再迭代，Golden Path 与真实流程脱节 | 建立反馈闭环，每季度复盘前置时间与 NPS |
| 所有权悬空 | 契约 owner 写“platform-team”，业务变更无人负责 | 强制 `owner` 指向生产流组，平台组只维护工具 |
