## 2.53.1 概述：从领域建模到消息契约

事件驱动架构（EDA）的失效往往始于设计阶段：团队对"领域事件""命令""外部系统""策略"没有共同语言，导致 topic 命名、消息拆分、消费边界反复返工【论证】。一套结构化的设计方法论能够把领域知识显式地转化为消息契约与系统边界。

本文档聚焦于五种互补方法：

1. **Event Storming**：快速发现领域事件与热点。
2. **Domain Storytelling**：用用户故事语法补全人员与流程上下文。
3. **C4 模型**：在架构视图中表达 broker、topic、consumer 与消息流。
4. **ADR**：把消息选型/迁移决策留档，便于演进与审计。
5. **DDD Context Mapping**：把限界上下文关系映射为契约所有权与事件目录结构。

这些方法与 [2.48 契约设计工作流与事件 API 治理](02-48-契约设计工作流与事件API治理.md)、[2.47 企业集成模式与事务消息模式](02-47-企业集成模式与事务消息模式.md)、[1.37 AsyncAPI 组织级应用与治理](../01-基础概念与对比分析/01-37-AsyncAPI组织级应用与治理.md) 错位互补：本文讲"如何集体建模并做出决策"，2.48 讲"如何把决策写成 AsyncAPI 契约并治理"，2.47 讲"模式化的集成方案"。

## 2.53.2 Event Storming 事件风暴

Event Storming 由 Alberto Brandolini 提出，是一种通过粘滞便签（sticky notes）让业务、开发、测试共同探索复杂领域的协作建模方法[Event Storming – A practical guide](https://www.rubicon-world.com/resources/event-storming-guide)。其核心产物是按时间线排列的**领域事件（Domain Event）**流，天然对应消息系统中的事件消息。

### 三级工作坊流程

根据 Brandolini 的划分，事件风暴通常分三级递进展开[The Workshop: Event Storming a Process](https://barkingiguana.com/writing/the-workshop-event-storming-a-process/)：

| 级别 | 目标 | 参与者 | 建议时长 | 产出 |
| ------ | ------ | -------- | ---------- | ------ |
| **Big Picture** | 识别端到端业务流程、领域事件与主要痛点 | 业务、架构、开发、测试、运维 | 1-2 天 | 事件时间线、热点（hotspot）清单、待细化问题 |
| **Process Level** | 深入一个选定的流程，补充命令、外部系统、聚合、策略 | 核心相关团队 | 半天-1 天 | 命令-事件-策略链路、候选聚合边界 |
| **Design Level** | 把聚合边界映射为代码/服务结构，产出候选限界上下文 | 开发+架构 | 半天 | 上下文边界、候选服务/模块、消息契约初稿 |

【论证】三级递进避免了"一次工作坊既要抓全局又要落细节"的疲劳：Big Picture 先对齐语言，Process Level 再聚焦热点，Design Level 才把模型交给工程实现。

### 色标约定

颜色约定是事件风暴可读性的关键。通用约定如下[Introducing EventStorming](https://github.com/mariuszgil/awesome-eventstorming/blob/master/README.md)：

| 颜色 | 含义 | 对应消息/设计元素 |
| ------ | ------ | ------------------ |
| 橙色 | 领域事件（Domain Event） | 事件消息，用动词过去式命名，如 `OrderCreated` |
| 蓝色/黄色 | 命令（Command） | 请求变更的命令消息，如 `PlaceOrder` |
| 粉色/紫色 | 实体/聚合（Aggregate/Entity） | 领域对象，决定消息 key 与分区边界 |
| 紫色 | 外部系统（External System） | 第三方/遗留系统，触发或消费事件 |
| 绿色 | 策略/规则（Policy） | 业务规则，决定事件触发条件与补偿路径 |
| 红色 | 热点/问题（Hotspot） | 风险、待确认问题、技术债务 |

> 注：不同资料对命令与聚合的颜色表述略有差异（蓝色命令 vs 黄色命令），团队内部统一即可；关键是**橙色=事件**这一共识最稳定。

### 远程工作坊工具

分布式团队可借助以下工具保持协作体验：

- **Miro / Mural**：无限画布、模板丰富，支持多人同步移动便签。
- **FigJam**：与 Figma 生态一致，适合设计+工程混编团队。
- **Conceptboard / Metro Retro**：专注工作坊 facilitation，内置计时器与投票。

远程的关键不是工具本身，而是**facilitator 的节奏控制**：Big Picture 阶段先"发散"15 分钟只贴事件，再"收敛"10 分钟从左到右梳理时间线，最后用 5 分钟点出红色热点【估算】。

### 从事件风暴到消息契约

事件风暴的产出物向消息契约的转化路径如下：

```text
橙色事件便签        → AsyncAPI messages（事件类型、语义）
蓝色命令便签        → 命令消息或同步 API（OpenAPI / RPC）
粉色聚合便签        → message key / 分区键 / payload 核心实体
紫色外部系统便签    → channel binding 与集成方式（bridge/connector）
绿色策略便签        → 消费规则、重试策略、补偿事件
红色热点便签        → 风险项：顺序要求、幂等要求、合规约束
```

一个可直接落地的衔接动作是：在 Process Level 结束后，由架构师把橙色事件按业务域分组，得到候选 channel 列表（如 `orders.order.created`、`inventory.stock.reserved`），再进入 [2.48](02-48-契约设计工作流与事件API治理.md) 的六步契约工作流。

## 2.53.3 Domain Storytelling

Domain Storytelling 由 Stefan Hofer 与 Henning Schwentner 提出，用"**作为 [角色]，我 [活动] [对象]，以便 [目标]**"的精简语法，把业务流程中的**人、系统、工作对象、活动**画成象形故事图（pictographic story）。

适用场景：

- 业务流程高度依赖人工步骤或审批，事件风暴容易遗漏角色。
- 需要向非技术干系人解释"这条消息由谁触发、谁消费"。
- 作为 Event Storming 的前置：先用 Domain Storytelling 理清流程，再贴事件更高效。

与事件风暴的互补关系：Domain Storytelling 回答"**谁做了什么**"，Event Storming 回答"**发生了什么及为什么**"；两者结合可降低遗漏外部系统或人工触发点的风险。

## 2.53.4 C4 模型在事件驱动系统的应用

C4 模型（Simon Brown）把软件架构视图分为 Context / Container / Component / Code 四级。在事件驱动系统中，它特别适合表达"消息在哪里流动"。

表达建议：

- **System Context 图**：把消息代理（Kafka/NATS/RabbitMQ 等）画成一个外部系统或独立参与者，标注它连接了哪些业务系统。
- **Container 图**：把 broker、topic、consumer group、schema registry、事件门户都作为 container，用带箭头的线表示发布/订阅关系，并用文字标注消息名称。
- **Dynamic / Deployment 图**：用动态图表达一次请求触发的事件链（如 `PlaceOrder` → `OrderCreated` → `StockReserved` → `PaymentCharged`）。

C4 与 Event Storming 的衔接：Big Picture 的事件时间线可直接映射为 System Context 图中的消息流；Process Level 的聚合边界映射为 Container 图中的服务/模块边界。

## 2.53.5 ADR 架构决策记录

消息系统的重大决策（选型、迁移、协议变更、分区策略）应当用 ADR（Architecture Decision Record）留档。ADR 不追求"一次性正确"，而是让团队以后能快速理解决策时的上下文与取舍。

ADR 推荐结构：

```markdown
# ADR-NNN: 标题

## 状态
proposed / accepted / deprecated / superseded by ADR-XXX

## 背景
需要解决什么问题，约束条件是什么。

## 决策
明确选中的方案。

## 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| A    | ...  | ...  |
| B    | ...  | ...  |

## 后果
正面影响、负面影响、需要接受的债务。

## 相关
- 关联 ADR、契约文件、事件风暴产出图
```

示例骨架（选用 Kafka 替代 RabbitMQ）：

```markdown
# ADR-012: 订单域事件总线从 RabbitMQ 迁移到 Kafka

## 状态
accepted

## 背景
订单域日均事件量预计从 10 万增长到 1000 万，RabbitMQ 的 queue 级顺序与横向扩展成为瓶颈；同时团队已具备 Kafka 运维能力。

## 决策
订单域新服务统一使用 Kafka，topic 按聚合拆分（order/invoice/shipment），旧 RabbitMQ queue 在 6 个月过渡期后下线。

## 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| 保留 RabbitMQ + 分片 | 改动小 | 运维复杂度随分片线性增加，无原生分区重平衡 |
| 迁移到 NATS JetStream | 轻量、低延迟 | 当前团队缺乏运维经验，生态工具链不足 |
| 迁移到 Kafka | 分区扩展、生态成熟、CDC 集成丰富 | 运维复杂度高，延迟 P99 相对 RabbitMQ 略大 |

## 后果
- 正面：支持未来 3 年事件量增长；与 Debezium CDC 生态对齐。
- 负面：需要重写 publisher/consumer SDK 包装层；旧 consumer 需双读过渡。
- 债务：过渡期内需维护 RabbitMQ 与 Kafka 双桥接。

## 相关
- 事件风暴产出：orders-domain-eventstorming-2026-11-15.png
- AsyncAPI 契约：../config-templates/asyncapi-contract-skeleton.yaml
- 迁移操作指南：../03-架构与运维实践/03-NN-Kafka迁移指南.md
```

## 2.53.6 DDD Context Mapping 与消息边界

限界上下文（Bounded Context）之间的关系决定了消息契约由谁定义、谁拥有、谁必须兼容。

### 七种关系模式与消息契约对应

| DDD 关系模式 | 消息契约含义 | 典型消息设计 |
| -------------- | -------------- | -------------- |
| **Partnership** | 双方共同演化契约 | 共同维护 AsyncAPI 文档，双方都能提议变更 |
| **Shared Kernel** | 共享通用领域模型与事件 | 共享 schema 包/库，变更需双方 CI 通过 |
| **Customer-Supplier** | 上游优先满足下游需求 | 下游参与上游契约评审；上游保留 major 版本公告期 |
| **Conformist** | 下游完全适配上游 | 下游使用上游发布的 schema，不加修改 |
| **Anti-Corruption Layer (ACL)** | 下游用防腐层隔离上游模型 | 上游事件经 ACL 转换为下游内部模型，topic 名带适配后缀 |
| **Open Host Service** | 上游提供稳定、开放的协议 | 发布标准化事件目录，版本策略保守 |
| **Published Language** | 使用共享、明确的语言描述契约 | 事件名、字段名、版本号全组织统一 |

【论证】Context Mapping 解释了为什么有的团队可以"直接消费上游事件"，而有的团队必须"建一条 topic 做转换"：Conformist 与 ACL 的差异本质上是对"上游模型侵入度"的取舍。

### 事件目录与上下文关系

把 Context Mapping 结果写入事件目录（Event Catalog），可让消息契约的"所有权"一目了然：

```yaml
# 事件目录片段示例
domains:
  order:
    owner: order-team
    context_relationships:
      inventory: Customer-Supplier   # 订单团队是库存团队的下游客户
      payment: Partnership           # 共同演化
      logistics: Conformist          # 物流团队直接适配订单事件
      legacy-crm: Anti-Corruption    # 旧 CRM 通过 ACL 转换
```

该目录可直接作为 [1.37 AsyncAPI 组织级应用与治理](../01-基础概念与对比分析/01-37-AsyncAPI组织级应用与治理.md) 中"事件目录平台"的输入，也可以作为 2.48 契约评审时判断"谁必须参与评审"的依据。
