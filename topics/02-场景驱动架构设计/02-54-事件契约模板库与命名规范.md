## 2.54.1 契约骨架：必备结构

一个可治理的事件契约至少应包含以下六层：

| 结构层 | 作用 | 关键字段 |
| -------- | ------ | ---------- |
| **metadata** | 描述契约自身的版本、所有者、生命周期 | `version`、`owner`、`status`、`createdAt`、`reviewers` |
| **header** | 消息头：追踪、幂等、路由、上下文 | `trace-id`、`idempotency-key`、`correlation-id`、`source-context` |
| **payload / data schema** | 业务负载的数据结构 | 实体字段、事件语义字段、必填/可选声明 |
| **error 事件** | 失败场景的消息结构 | `error.code`、`retryable`、`compensationHint` |
| **兼容性声明** | 版本演进规则 | `compatibility`（backward/forward/none）、`deprecatedFields` |
| **binding 与通道** | 协议特定参数 | broker、topic、partition key、contentType |

完整骨架见 `config-templates/event-contract-template.yaml`。

契约骨架 YAML 示例（聚焦 metadata + header + payload）：

```yaml
eventContract:
  metadata:
    id: urn:events:order:created:v1
    name: OrderCreated
    domain: order
    owner: order-team
    status: active          # active | deprecated | retired
    version: 1.2.0
    compatibility: backward
    reviewers: [inventory-team, payment-team]

  header:
    required: [trace-id, idempotency-key, occurred-at]
    properties:
      trace-id:        { type: string, format: uuid, description: 追踪 ID }
      idempotency-key: { type: string, format: uuid, description: 幂等键 }
      occurred-at:     { type: string, format: date-time, description: 业务发生时间 }
      source-context:  { type: string, description: 触发上下文，如 web/mobile/cdc }

  payload:
    type: object
    required: [orderId, amount, currency, occurredAt]
    properties:
      orderId:     { type: string, description: 订单唯一标识 }
      amount:      { type: number, description: 金额 }
      currency:    { type: string, default: CNY, description: 货币代码 }
      occurredAt:  { type: string, format: date-time, description: 订单创建时间 }
      items:       { type: array, description: 订单行项目 }

  error:
    type: OrderCreationFailed
    code: ORDER_CREATE_FAILED
    retryable: true
    compensationHint: 库存预留回滚接口 /inventory/release
```

## 2.54.2 CloudEvents 信封适配模板

CloudEvents 是 CNCF 毕业项目，提供传输无关的事件元数据标准[CloudEvents specification](https://cloudevents.io/)。
在 Kafka 场景中，CloudEvents 提供 binary 与 structured 两种映射模式；
structured 模式把完整信封作为 JSON payload，便于跨团队与跨协议消费[CloudEvents Kafka Protocol Binding](https://github.com/cloudevents/spec/blob/main/cloudevents/bindings/kafka-protocol-binding.md)。

项目内对应规范分析见 [1.30 事件互操作标准分析](../01-基础概念与对比分析/01-30-事件互操作标准分析.md)。

适配原则：

- `id` → 消息唯一标识，与 `header.idempotency-key` 可一致。
- `source` → 事件源标识，建议格式 `/<org>/<domain>/<service>`。
- `type` → 事件类型，建议 `dev.<org>.<domain>.<entity>.<verb>`。
- `subject` → 具体实体引用，如 `order/ORDER-12345`。
- `time` → 事件发生时间，与 `header.occurred-at` 语义一致。
- `data` → 业务 payload。

完整示例见 `config-templates/cloudevents-envelope-example.json`。

## 2.54.3 命名规范

命名规范是事件目录可检索、可治理的基础。推荐约定如下：

| 元素 | 约定 | 示例 | 说明 |
| ------ | ------ | ------ | ------ |
| **事件名** | 动词过去式，PascalCase | `OrderCreated`、`PaymentRefunded` | 表达"已发生的事实" |
| **topic / channel** | `<domain>.<entity>.<verb>`，kebab-case | `orders.order.created` | 与 2.48 channel 命名对齐 |
| **版本号** | 语义化版本 `v<major>.<minor>` | `v1`、`v1.2` | major=破坏性，minor=兼容 |
| **schema 名** | 事件名 + `Event` | `OrderCreatedEvent` | 与 AsyncAPI `components.schemas` 一致 |
| **错误事件名** | 动词 + `Failed` | `OrderCreationFailed` | 明确失败语义 |
| **header 字段** | kebab-case 或 camelCase 二选一 | `trace-id` / `traceId` | 团队统一即可 |

版本号策略：

- **major**：破坏性变更（删字段、改必填、改类型）。必须走评审 + 双写/过渡期。
- **minor**：向后兼容变更（加可选字段、加新 channel）。可直接合并并通知消费方。
- **patch**：文档修正、注释更新、示例补全，不影响运行时。

> 反例：把 `order.created` 与 `order.create` 混用；把事件名写成 `createOrder`（命令式）而非 `OrderCreated`（事实式）。

## 2.54.4 错误事件契约

错误事件不是异常堆栈的简单包装，而是消费者做补偿、重试、监控的依据。结构应包含：

```yaml
errorEvent:
  metadata:
    id: urn:events:order:creation-failed:v1
    name: OrderCreationFailed
    source: /acme/order-service
  header:
    required: [trace-id, idempotency-key, original-event-id]
    properties:
      original-event-id: { type: string, description: 触发该错误的事件 id }
  payload:
    type: object
    required: [error, originalEvent]
    properties:
      error:
        type: object
        required: [code, message, retryable, severity]
        properties:
          code:        { type: string, description: 机器可读错误码 }
          message:     { type: string, description: 人类可读描述 }
          retryable:   { type: boolean, description: 是否可重试 }
          severity:    { type: string, enum: [warning, error, critical] }
          compensationHint: { type: string, description: 补偿操作指引或 API 路径 }
      originalEvent:
        type: object
        description: 原始事件的引用或快照（最小字段集）
        properties:
          type: { type: string }
          subject: { type: string }
          dataRef: { type: string, description: 原始数据存储位置 }
```

关键设计点：

- **retryable** 明确告诉消费者：值=false 时不要再重试，直接进 DLQ 或人工处理。
- **compensationHint** 给 Saga / 编排式流程提供回滚线索（参见 2.47 Saga 模式）。
- **originalEvent** 保留最小引用，避免错误事件体积膨胀；完整上下文可通过 trace-id 查询可观测系统。

## 2.54.5 版本化与弃用模板

### Deprecation 公告模板

当某个事件/字段进入退役流程时使用：

```markdown
# 事件退役公告：OrderCreated v1

## 影响范围
- topic: `orders.order.created.v1`
- 消费方：inventory-service、payment-service、analytics-service

## 退役原因
v1 的 `amount` 字段缺少 `currency`，无法支撑多币种；v2 已新增 `currency` 并运行稳定。

## 时间表
- 公告日期：2026-11-18
- v1 停止接受新 producer：2027-02-18（3 个月后）
- v1 topic 下线日期：2027-05-18（6 个月后）

## 迁移路径
- 新字段：`currency`（默认 CNY，建议显式填写）
- 替代 topic：`orders.order.created.v2`
- 联系：order-team@example.com
```

### Breaking Change 迁移模板

当必须引入破坏性变更时使用：

```markdown
# Breaking Change 迁移方案：订单金额字段拆分

## 变更内容
- 旧：`amount: number`（隐含 CNY）
- 新：`amount: number` + `currency: string`（必填）

## 兼容性策略
双写过渡期：
1. **Phase 1（4 周）**：producer 同时发送 v1 与 v2；consumer 逐步迁移到 v2。
2. **Phase 2（2 周）**：监控 v1 consumer 活跃度；归零后停止 producer 写 v1。
3. **Phase 3（1 周）**：下线 v1 topic 并归档 schema。

## 检查项
- [ ] v2 schema 通过 backward compatibility 校验
- [ ] v1 consumer 清单已确认
- [ ] 双写期间存储/带宽成本已评估
- [ ] 下线前 AsyncAPI Diff 报告已归档
```

### 与 2.48 的衔接

2.48 的"公告期流程"要求删除 channel/message 必须走强制路径。本文档提供的模板是那条路径的**输入物**：

1. 事件风暴 / 需求评审识别变更 → 2.53
2. 按本文模板写出契约、命名、版本、错误事件 → 2.54
3. 进入 2.48 的六步工作流：校验 → 评审 → 发布 → 兑现
4. 破坏性变更产出公告与迁移模板 → 提交 PR 并进入 CI diff
