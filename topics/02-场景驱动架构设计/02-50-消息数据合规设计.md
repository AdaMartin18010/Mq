## 2.50.1 消息系统的特有合规矛盾

消息系统与合规的冲突点在**不可变性**【论证】：

1. **删除权 vs 追加日志**：GDPR 第17条/个保法第47条要求"被遗忘"；Kafka/Pulsar 的日志是 append-only，删除单条数据与存储模型对立。
2. **审计追溯 vs 数据最小化**：法规同时要求留存证据（审计）与最小化收集——同一消息可能既是审计对象又是过度收集对象。
3. **跨境流动**：地理复制（Pulsar geo-replication、MirrorMaker 2）天然跨区域，触发数据本地化要求【论证】。
4. **消费者黑盒**：消息一经扇出，PII 副本存在于 N 个下游消费者，控制面够不着【论证】。

## 2.50.2 四大合规要求的工程折衷

| 合规要求 | 朴素做法 | 工程折衷（推荐） | 残余风险 |
| ---------- | ---------- | ------------------ | ---------- |
| 删除权 | 物理删除消息 | **crypto-shredding**：PII 字段独立加密，密钥按主体管理，删除=销毁密钥【论证】 | 密钥管理复杂度 |
| 最小化 | 全量消息加密了事 | 消息头/正文分离：正文只放引用键，PII 存侧车存储（DB），消息传键不传值【论证】 | 查询路径多一跳 |
| 留痕审计 | 永久保留原始消息 | 审计层存哈希+元数据，原文设保留期（如 90 天滚动删除）【论证】 | 哈希抗争议性需背书 |
| 跨境合规 | 一刀切禁跨境 | 按数据分类路由：含 PII 的 topic 不启用地理复制；或部署区域级集群+联邦【论证】 | 架构复杂度 |

**crypto-shredding 细节**【论证】：每条消息（或每数据主体维度）用独立 DEK 加密 PII 字段；DEK 由 KMS 托管按 subject 索引；删除请求 → 销毁该 subject 的全部 DEK → 密文永久不可解。追加日志无需改动，"删除"在密码学层面完成。代价：KMS 调用量、密钥轮换设计。

## 2.50.3 方案对比

| 方案 | 删除权 | 最小化 | 实施成本 | 适用 |
| ------ | :---: | :---: | ---------- | ------ |
| A. 物理删除（compaction/tombstone） | ⚠️ 弱（副本/快照残留） | ❌ | 低 | 非严格场景 |
| B. crypto-shredding | ✅ 强 | ⚠️ 中 | 高 | 金融/医疗级 |
| C. 传键不传值（PII 出消息层） | ✅ 强 | ✅ 强 | 中 | 新建系统首选 |
| D. 短保留期+法律持有流程 | ⚠️ 中 | ❌ | 低 | 日志类数据 |
| E. 区域隔离部署 | — | — | 高 | 强本地化行业 |

组合是常态：C（最小化）+ B（删除兜底）+ D（保留纪律）+ 按区域路由【论证】。

### crypto-shredding 密钥设计要点

```text
KMS 主密钥（CMK，按环境/区域隔离）
  └─ DEK（按数据主体维度，如 user-id）
       └─ 加密消息中的 PII 字段（AES-GCM，AAD=topic+时间戳）
删除请求 → KMS DestroyAlias(user-id DEK) → 全部密文不可解
```

工程要点【论证】：DEK 消费者侧缓存设 TTL（性能与吊销时效折衷）；AAD 绑定 topic 防跨 topic 重放；密钥销毁双人中。

### 删除请求处理时序（方案 C+B 组合）

```text
1. 用户提交删除申请 → 控制者审核合法性（法务/DPO）
2. 审核通过 → 触发删除编排（独立于业务消息通道）
3. 侧车存储删除 PII 记录（主记录）
4. KMS 销毁该主体 DEK（密文兜底失效）
5. 向量库/缓存/下游副本删除（台账清单驱动，02-52）
6. 审计事件留痕（不含 PII）
SLA 参考：审核 7 天内，技术执行 72 小时内完成【估算】
```

## 2.50.4 选型建议

| 场景 | 推荐组合 | 理由 |
| ------ | ---------- | ------ |
| 新建订单/用户系统 | C + B | 从源头让 PII 不进消息，删除权靠密钥销毁兜底 |
| 既有系统改造 | A → B 渐进 | 先上短保留期止血，再补加密层 |
| 纯日志/埋点（无 PII） | D | 不必过度工程，但要做 PII 扫描确认（反模式见下） |
| 跨地域业务 | C + 区域路由 | PII 不出区域，消息只跨键 |

与项目既有模式的衔接：本方案与 02-26 序列化（加密字段的 schema 表达）、02-30 安全设计（TLS/ACL 层）、01-34 许可证合规（加密模块的许可证注意）正交，组合使用【论证】。

## 2.50.5 反模式

- ❌ **"消息反正只存 7 天，不用管合规"**：扇出副本在下游、备份/快照、跨区域副本的留存均不受 retention 控制【论证】
- ❌ **全字段加密图省事**：检索/过滤/审计能力全失，且密钥单点——应只加密 PII 字段
- ❌ **删除请求直接删 topic**：影响所有消费者——按 subject 粒度（密钥/侧车记录）处理
- ❌ **把删除权做成消息再发一遍**："删除指令"经由 MQ 传播会留下 PII 痕迹——删除通道与业务通道分离【论证】

### 数据分类分级（合规设计的前置输入）

| 级别 | 例 | 消息策略 |
| ------ | ---- | ---------- |
| 公开 | 商品目录 | 无限制 |
| 内部 | 订单元数据（脱敏） | 标准通道 |
| 敏感 PII | 手机号/身份证 | **禁入消息层**（传键不传值）或强制字段加密 |
| 受监管 | 金融账户/健康数据 | 加密+审计+区域限制（02-51 路由） |

分类动作【论证】：topic 建topic 时定级（命名前缀或元数据），消费者按级鉴权——分类先于加密，加密先于上生产。

### 组织职责（RACI 简化）

| 角色 | 合规职责 |
| ------ | ---------- |
| 数据控制者（业务） | 定级、删除请求的合法性审核 |
| 平台工程 | 加密基础设施、密钥管理、删除通道工程实现 |
| DPO/法务 | 法规解释、删除权例外判断（如审计豁免） |
| 消费者团队 | 自身副本的合规处置（血缘台账 02-52 提供清单） |

### 合规检查清单（设计评审用）

- [ ] PII 字段清单已出且与消息 schema 对账（无"漏网字段"）
- [ ] 删除请求端到端流程演练过（含向量库/对象存储，01-36 衔接）
- [ ] 加密密钥的轮换与销毁流程文档化
- [ ] 消费者副本处置责任写入消费方接入协议
- [ ] 跨境 topic 路由表经审批（02-51 联动）

### 合规审计留痕设计

```json
{
  "audit_id": "uuid",
  "action": "pii.delete | pii.access | key.destroy",
  "subject_ref": "user-id（不含 PII 本身）",
  "legal_basis": "用户请求|合同义务|诉讼保全",
  "operator": "system|dpo@corp",
  "result": "completed|partial|failed",
  "evidence_ref": "各存储层处置回执列表"
}
```

审计链要求【论证】：留痕本身不含 PII（否则审计库成为新的合规目标）；保留期 ≥ 最长法定诉讼时效【估算】；定期抽样验证留痕与实际处置一致（演练方式见 TEST-05 突变测试）。

## 2.50.4b 主要法规速览（工程相关条款）

| 法规 | 工程相关要点 | 对消息系统的影响 |
| ------ | -------------- | ------------------ |
| GDPR（欧盟） | 第17条删除权、第25条隐私设计、第5条存储限制 | 本文方案 B/C 的直接需求来源 |
| 中国个保法 | 第47条删除权、跨境提供需单独同意 | 区域路由（02-51）+ 删除通道 |
| HIPAA（美国医疗） | 传输与静态加密、审计日志 6 年 | 加密字段+审计链是合规底线 |
| PCI DSS（支付） | 卡号不得明文存储/传输 | PII 禁入消息层（方案 C）的典型适用 |

法规共性【论证】：删除权、最小化、加密、审计四件套——本文 2.50.2 的四大折衷即按此抽象，新增法规按四件套映射即可。

## 2.50.4c PII 数据流向登记（合规台账模板）

```text
PII 流向登记（每 topic 一行）：
topic=orders.pii | 字段=phone,address | 级别=敏感
生产者=order-service | 消费者=3（见血缘 02-52）
加密=B 方案（DEK per user） | 保留期=90 天
跨境=否 | 删除通道=已演练（2026-11-17）
```

台账由血缘目录派生（02-52），季度对账一次——PII 流向图是审计调阅的第一份材料【论证】。
