## 2.30.1 安全场景与纵深

### 常见场景

1. **认证授权**
   - 客户端身份认证、按 topic/queue 粒度授权、多租户隔离。
   - 防止匿名访问与越权操作。

2. **数据安全**
   - 传输加密（TLS/SSL）、存储加密、敏感字段级加密。
   - 防止中间人攻击与数据泄露。

3. **网络安全与审计**
   - VPC/子网隔离、防火墙白名单、管理端口限制。
   - 审计日志集中化，保留 ≥90 天。

### 安全纵深

【论证】消息系统安全应遵循“零信任”原则：不信任任何客户端、不暴露管理端口、最小权限访问、全程加密传输、操作可审计。安全设计应覆盖传输层、认证层、授权层、审计层四个纵深。

## 2.30.2 安全机制选型

### 机制对比决策表

| 机制 | 防护对象 | 实现复杂度 | 性能影响 | 适用场景 |
| ---- | -------- | ---------- | -------- | -------- |
| TLS/SSL | 传输链路 | 中 | 低 | 所有生产环境 |
| SASL/PLAIN | 认证 | 低 | 低 | 内网、快速落地 |
| SASL/SCRAM 或 OAuth | 认证 | 中 | 低 | 高安全要求、云原生 |
| ACL/RBAC | 授权 | 中 | 低 | 多租户、细粒度控制 |
| 字段级加密 | 消息内容 | 高 | 中 | 敏感数据、合规要求 |

【论证】传输加密应作为基线默认开启；认证机制优先选择 SCRAM 或 OAuth 而非明文 PLAIN；授权应遵循最小权限原则，按 Topic/Queue/Subject 粒度分配读写权限。

### 六系统认证机制矩阵

| 系统 | 传输层 | 用户名密码 | Token/JWT | OAuth/OIDC | 证书/mTLS | 增强/挑战响应 | 委托令牌 |
| ---- | ------ | ---------- | --------- | ---------- | ---------- | -------------- | -------- |
| Kafka | SSL/SASL_SSL | SASL/PLAIN/SCRAM | — | SASL/OAUTHBEARER + KIP-768 OIDC | 双向 TLS | SASL/GSSAPI | KIP-48 delegation token |
| MQTT | TLS | CONNECT 用户名密码 | — | 5.0 AUTH 承载 OAUTHBEARER | 客户端证书 | 5.0 AUTH challenge-response | — |
| NATS | TLS | 用户名密码 | Token | JWT (account/user) | TLS + NKey | NKey challenge-response | — |
| RabbitMQ | TLS/AMQPS | PLAIN | — | OAuth 2.0 JWT 插件 | 客户端证书 | — | — |
| Pulsar | TLS | — | — | OAuth 2.0 插件 | TLS 插件 | SASL 插件 | — |
| Redis Stream | TLS | ACL 用户名密码 | — | — | — | — | — |

## 2.30.3 零信任消息架构

零信任在消息场景的核心是：无论客户端位于何处，每次连接、每次发布/订阅、每条消息敏感字段都必须经过显式验证与授权。参见 [1.49 消息系统零信任安全体系](../01-基础概念与对比分析/01-49-消息系统零信任安全体系.md)。

| 层级 | 验证内容 |
| ---- | -------- |
| Broker 身份验证 | 客户端验证 Broker 证书/签名，防中间人 |
| 客户端身份验证 | Broker 验证客户端身份，禁止匿名或仅依赖源 IP |
| Topic/队列级授权 | 按最小权限检查对特定 topic/queue 的操作权限 |
| Payload 加密 | 对敏感字段端到端加密，Broker 不可读 |
| 审计 | 记录每次认证、授权、数据访问 |

## 2.30.4 Kafka 安全

Kafka 推荐启用 SASL_SSL + SCRAM-SHA-256/512，并配置 ACL：

```properties
# server.properties
listeners=SASL_SSL://0.0.0.0:9093
security.inter.broker.protocol=SASL_SSL
sasl.enabled.mechanisms=SCRAM-SHA-256,SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-256
ssl.enabled.protocols=TLSv1.2,TLSv1.3
authorizer.class.name=kafka.security.authorizer.AclAuthorizer
allow.everyone.if.no.acl.found=false
```

```bash
# ACL 示例：仅允许 order-producer 写入 orders topic
kafka-acls.sh --bootstrap-server kafka:9093 --command-config admin.conf \
  --add --allow-principal User:order-producer \
  --operation Write --topic orders
```

## 2.30.5 NATS 安全

NATS 2.0+ 推荐基于 operator → account → user 三级层级与 JWT + NKey 的分布式身份模型：

```bash
nsc generate operator --name MyOp
nsc add account --name Payments
nsc add user --account Payments --name payment-svc
```

生产环境应使用 TLS 与 `verify:true`，并通过 account permissions 控制 publish/subscribe 主题范围。

## 2.30.6 RabbitMQ 安全

RabbitMQ 启用 AMQPS 与 OAuth 2.0 插件：

```ini
# rabbitmq.conf
listeners.ssl.default = 5671
ssl_options.verify = verify_peer
ssl_options.fail_if_no_peer_cert = true
auth_backends.1 = oauth2
auth_oauth2.issuer = https://idp.example.com
auth_oauth2.jwks_url = https://idp.example.com/.well-known/jwks.json
```

关闭默认 guest 远程访问，vhost 与 topic 权限按最小权限分配。

## 2.30.7 端到端加密与合规

传输 TLS 与静态加密只能防外部窃听，Broker 本身仍可见明文。端到端 payload 加密才能在多租户或 SaaS Broker 场景下保证“Broker 不可读”。

```python
# KMS 信封加密示例
def encrypt_payload(plaintext: bytes, dek: bytes, aad: bytes) -> dict:
    aesgcm = AESGCM(dek)
    nonce = os.urandom(12)
    ciphertext = aesgcm.encrypt(nonce, plaintext, aad)
    return {
        "ciphertext": base64.b64encode(ciphertext).decode(),
        "nonce": base64.b64encode(nonce).decode(),
        "dek_encrypted": base64.b64encode(kms_encrypt(dek)).decode(),
        "aad": base64.b64encode(aad).decode()
    }
```

合规方面，GDPR/HIPAA/PCI DSS/等保 2.0 对加密、审计、保留期、删除权有明确要求。许可证合规同样属于安全治理的一部分，参见 [1.34 消息系统许可证与选型合规分析](../01-基础概念与对比分析/01-34-消息系统许可证与选型合规分析.md)。

## 2.30.8 安全最佳实践

### 设计建议

1. **默认加密**
   - 生产环境必须启用 TLS 1.2+，禁用 SSLv3/TLSv1.0/TLSv1.1。
   - 管理端口仅允许运维堡垒机或 VPN 访问。

2. **最小权限**
   - 按 topic/queue/subject 粒度授权。
   - 避免使用超级用户运行业务生产者/消费者。

3. **密钥与审计**
   - 使用 Vault/KMS 托管密钥，每 90 天轮换。
   - 审计日志保留 ≥90 天，关键配置变更双人复核。
   - 失败登录监控：`security.monitor.failed_login.threshold=5`。

### 配置模板引用

安全配置统一引用 `topics/config-templates/security-enhanced-config.properties`：

```properties
# 增强版消息安全配置模板（引用 topics/config-templates/security-enhanced-config.properties）
kafka.security.protocol=SASL_SSL
kafka.sasl.mechanism=SCRAM-SHA-256
kafka.sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required username="order-producer" password="***";
kafka.authorizer.class.name=kafka.security.authorizer.AclAuthorizer
kafka.allow.everyone.if.no.acl.found=false
kafka.ssl.enabled.protocols=TLSv1.2,TLSv1.3

nats.tls.enabled=true
nats.auth.enabled=true
nats.auth.user=admin

rabbitmq.ssl.enabled=true
rabbitmq.auth.enabled=true
rabbitmq.auth.default_user=admin
rabbitmq.auth.password_hashing.algorithm=sha256

security.encryption.enabled=true
security.encryption.algorithm=AES-256-GCM
security.encryption.key.rotation.enabled=true
security.encryption.key.rotation.interval=90d

auth.type=oauth2
authorization.type=rbac

audit.enabled=true
audit.log.file=/var/log/mq-audit.log
audit.events=login,logout,read,write,delete,config_change
audit.retention.days=90

security.monitor.enabled=true
security.monitor.failed_login.threshold=5
security.monitor.failed_login.window=300
security.monitor.alert.channels=email,dingtalk

key.management.enabled=true
key.management.provider=vault
key.management.rotation.enabled=true
key.management.rotation.interval=90d
```
