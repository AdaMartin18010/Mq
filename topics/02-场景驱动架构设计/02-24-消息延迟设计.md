## 2.24.1 延迟场景与精度维度

### 常见业务场景

1. **定时任务**
   - 订单创建后 30 分钟未支付自动取消。
   - 会员到期前 7 天、1 天、当天分三次发送续费提醒。
   - 活动开始前 5 分钟向订阅用户推送开始通知。

2. **重试策略**
   - 消费失败时先延迟 1 秒重试，随后按指数退避到 60 秒上限。
   - 最大重试次数达到 10 次后转入死信队列人工介入。

3. **状态超时**
   - 支付超时关单、库存预占超时释放、审批超时转办。
   - 长流程等待外部回调，例如物流签收 7 天后自动结算。

### 延迟精度维度

【论证】延迟消息设计需同时考虑：

- **精度**：秒级、分钟级还是小时级？毫秒级精度通常需要专用延迟队列或插件。
- **规模**：同时等待的消息数量级？单队列堆积超过 100 万时 RabbitMQ 性能明显下降。
- **可靠性**：到期是否必须被消费一次？是否允许重复投递？
- **取消/更新**：是否支持提前取消或修改延迟时间？Kafka 时间戳方案天然支持重新发送覆盖。
- **持久化**：长周期延迟消息必须落盘，避免 Broker 重启丢失。

## 2.24.2 延迟策略决策表

### 固定延迟 vs 动态延迟 vs 定时调度

| 策略 | 精度 | 灵活性 | 运维复杂度 | 典型系统 | 适用场景 |
| ---- | ---- | ------ | ---------- | -------- | -------- |
| 固定延迟 | 中 | 低 | 低 | RocketMQ 延迟级别 | 统一超时、固定重试间隔 |
| 动态延迟 | 高 | 高 | 中 | RabbitMQ 延迟插件、Pulsar `deliverAfter` | 每条消息独立指定延迟 |
| 定时调度 | 高 | 中 | 高 | Quartz + 任意 MQ | Cron 表达式、绝对时间点触发 |
| 指数退避 | 中 | 中 | 中 | 应用层 + Kafka/NATS | 重试场景、避免 thundering herd |

【论证】固定延迟适合高吞吐但时间阶梯固定的场景；动态延迟适合每条消息需要独立延迟时间的业务；定时调度适合绝对时间点触发，但不要把 MQ 当作 Cron 引擎使用，可参见 [1.41 工作流编排系统与消息协同](../01-基础概念与对比分析/01-41-工作流编排系统与消息协同.md) 中的 Timer 语义。

### 系统级选型矩阵

| 方案 | 精度 | 可靠性 | 运维复杂度 | 适用 MQ | 典型场景 |
| ---- | ---- | ------ | ---------- | -------- | -------- |
| 消息时间戳过滤 | 低 | 中 | 低 | Kafka | 简单延迟、可容忍重复扫描 |
| 多级延迟 Topic | 中 | 中 | 中 | Kafka、Pulsar | 固定阶梯延迟 |
| 延迟队列插件 | 高 | 高 | 低 | RabbitMQ | 精确到秒级延迟 |
| 内置延迟级别 | 中 | 高 | 低 | RocketMQ | 高吞吐固定延迟 |
| JetStream 原生延迟 | 高 | 高 | 低 | NATS JetStream | 原生支持、云原生 |
| 外部调度器 | 高 | 高 | 高 | 任意 | 复杂工作流、Cron 表达式 |

## 2.24.3 Kafka 延迟消息

### 时间戳过滤方案

Kafka 原生不支持延迟消息，应用层可在消息时间戳中写入目标投递时间，消费者 `poll` 后判断是否到期：

```java
long delayTime = System.currentTimeMillis() + 60000; // 延迟 1 分钟
ProducerRecord<String, String> record = new ProducerRecord<>(
    "orders",
    null,
    delayTime,  // 目标投递时间戳
    key,
    value
);

ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord<String, String> r : records) {
    if (r.timestamp() > System.currentTimeMillis()) {
        consumer.pause(consumer.assignment()); // 未到时间暂停拉取
        continue;
    }
    process(r);
}
```

【论证】该方案实现简单，但精度受 `kafka.delay.scan.interval.seconds` 制约，且消费者需要处理未到期的消息反复拉取问题。结合 `config-templates/delay-config.properties` 中的 `kafka.delay.strategy=timestamp` 使用：

```properties
# 引用 config-templates/delay-config.properties
kafka.delay.enabled=true
kafka.delay.strategy=timestamp
kafka.delay.scan.interval.seconds=60
```

### 多延迟 Topic 方案

按延迟时长建立多个 Topic，后端转发器到期后转投主 Topic：

```java
String delayTopic = "orders-delay-" + delayMinutes;
producer.send(new ProducerRecord<>(delayTopic, key, value));
```

建议 Topic 数量不超过 20 个，避免 Kafka 元数据膨胀。配置项 `kafka.delay.topic.prefix=delay-` 用于统一前缀管理。

## 2.24.4 RocketMQ 延迟级别

RocketMQ 开源版内置 18 个固定延迟级别：1s、5s、10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h。

```java
Message msg = new Message("OrderTopic", "TagA", orderId, body.getBytes());
msg.setDelayTimeLevel(4);      // 第 4 级 = 30 秒
producer.send(msg);
```

【论证】RocketMQ 延迟级别适合高吞吐固定延迟场景，商业版支持任意毫秒级延迟 `setDelayTimeMs(60000)`。配置中 `messageDelayLevel` 控制级别定义，修改后需重启 Broker；监控 `SCHEDULE_TOPIC_XXXX` 队列积压是运维重点，阈值参考 `delay.alert.threshold.count=10000`。

## 2.24.5 RabbitMQ 延迟消息

### TTL+DLX 方案

通过队列 TTL 与死信 Exchange 实现延迟：消息过期后自动路由到业务队列消费。

```python
# 声明延迟队列并绑定死信 Exchange
channel.queue_declare(
    queue='orders.delay.60s',
    arguments={
        'x-message-ttl': 60000,
        'x-dead-letter-exchange': 'dlx.orders',
        'x-dead-letter-routing-key': 'orders.ready'
    }
)
```

【论证】TTL+DLX 方案简单，但 RabbitMQ 只对队列头部消息检查过期，非头部消息即使到期也不会立即投递；单队列堆积超过 100 万时性能下降明显，需按业务维度分片。

### 延迟插件方案

安装 `rabbitmq_delayed_message_exchange` 插件，声明 `x-delayed-message` 类型 Exchange：

```python
channel.exchange_declare(
    exchange='orders-delayed',
    exchange_type='x-delayed-message',
    arguments={'x-delayed-type': 'direct'}
)

channel.basic_publish(
    exchange='orders-delayed',
    routing_key='orders',
    body=message,
    properties=pika.BasicProperties(
        headers={'x-delay': 60000},  # 延迟 60 秒
        delivery_mode=2
    )
)
```

插件支持每条消息独立延迟，最大不超过 `rabbitmq.delay.max.milliseconds=86400000`（24 小时）。

## 2.24.6 NATS/Pulsar 原生延迟

NATS JetStream 2.x 支持消息级延迟发布，适合云原生场景：

```go
js.Publish("orders", data, nats.MsgId("msg-1"), nats.Delay(60*time.Second))
```

Pulsar 提供 `deliverAfter` 与 `deliverAt` 原生 API，支持任意精度：

```java
producer.newMessage()
    .deliverAfter(60, TimeUnit.SECONDS)
    .value(payload)
    .send();
```

配置上限参考 `nats.delay.max.seconds=86400`。

## 2.24.7 长周期延迟与工作流协同

当延迟跨度达到数天甚至数月（如会员到期提醒、合同续签提醒），单纯依赖 MQ 延迟队列存在以下问题：

1. **保留期风险**：延迟消息需在 Broker 中保留整个延迟周期，配置不当易过期丢失。
2. **取消/更新困难**：业务状态变化后需要取消或修改延迟任务，MQ 原生语义支持有限。
3. **可视化不足**：延迟任务状态分散在多个 Topic/队列中，难以统一审计。

【论证】长周期、可取消、需审计的延迟任务更适合交给工作流编排器处理。编排器提供持久化 Timer、Signal 取消、事件历史查询等能力，MQ 仅作为触发事件通道。参见 [1.41 工作流编排系统与消息协同](../01-基础概念与对比分析/01-41-工作流编排系统与消息协同.md)。

| 场景 | 推荐方案 | 理由 |
| ---- | -------- | ---- |
| 秒级~小时级固定延迟 | RocketMQ 延迟级别 / Kafka 多延迟 Topic | 高吞吐、实现简单 |
| 秒级~小时级动态延迟 | RabbitMQ 延迟插件 / Pulsar `deliverAfter` | 每条消息独立延迟 |
| 天级~月级、可取消 | Temporal / Camunda Timer + MQ Signal | 状态可见、补偿完善 |
| 绝对时间点 Cron | 外部调度器 + MQ | Cron 语义不应由 Broker 承担 |

## 2.24.8 延迟消息最佳实践

### 设计建议

1. **策略选择**
   - 固定延迟优先用 RocketMQ 内置级别或 Kafka 多延迟 Topic。
   - 动态延迟优先用 RabbitMQ 延迟插件或 Pulsar。
   - 长周期/可取消任务优先用工作流编排器 Timer。

2. **可靠性**
   - 开启持久化：`delay.storage.persistent=true`。
   - 保留时间 `delay.storage.retention.hours` 必须大于最大业务延迟。
   - 转发 Worker 记录已处理 offset，避免重启重复投递。

3. **性能**
   - 单队列消息数超过 100 万时考虑分片，例如按订单尾号散列到 16 个延迟队列。
   - Kafka 多延迟 Topic 数量建议不超过 20 个。
   - RocketMQ 单机延迟消息 TPS 建议不超过 5 万。

### 配置模板引用

延迟配置统一引用 `topics/config-templates/delay-config.properties`：

```properties
# 消息延迟配置模板（引用 topics/config-templates/delay-config.properties）
delay.strategy=fixed
delay.fixed.milliseconds=60000
delay.exponential.backoff.initial.milliseconds=1000
delay.exponential.backoff.max.milliseconds=60000
delay.exponential.backoff.multiplier=2
delay.storage.enabled=true
delay.storage.persistent=true
delay.storage.retention.hours=24
delay.monitor.enabled=true
delay.monitor.metrics=delay_count,delay_duration,delay_accuracy
delay.alert.enabled=true
delay.alert.threshold.count=10000
delay.alert.threshold.accuracy.percent=95
delay.alert.channels=email,dingtalk
```
