## 2.33.1 转换适配场景

### 常见场景

【论证】消息转换与适配解决的是“同一件事在不同系统里说法不同”的问题。典型触发点包括：

1. **格式转换**：上游输出 JSON，下游分析平台要求 Avro/Protobuf；遗留系统输出 XML，需要统一为 JSON 进入 Kafka。
2. **协议适配**：MQTT 设备接入后需写入 Kafka 持久化；Kafka 订单流需推送到 RabbitMQ 触发业务工作流。
3. **字段映射与 Schema 治理**：多团队 topic 字段命名、类型不一致，需要字段映射与 Schema Registry 统一版本管理。
4. **数据清洗与增强**：在转换过程中补齐时间戳、单位换算、敏感字段脱敏，并写入目标 topic。
5. **产业/域标准适配**：金融 ISO 20022、医疗 FHIR、物流 EPCIS、能源 OpenADR、工业 Sparkplug、AI Agent A2A 等标准与企业内部事件契约的互转。

转换设计应首先明确“转换发生在哪一层”：

- **Broker 层**：Kafka Connect SMT、Pulsar IO、RabbitMQ 插件；
- **流处理层**：Kafka Streams、Pulsar Functions、NATS JetStream 处理器；
- **应用层**：消费者收到消息后自行转换再生产；
- **网关/桥接层**：跨协议桥接器（MQTT → Kafka、NATS → Kafka）。

## 2.33.2 转换策略选型

### 格式转换决策表

| 源格式 | 目标格式 | 推荐路径 | 关键注意 |
| --- | --- | --- | --- |
| JSON | Avro | Kafka Connect AvroConverter + Schema Registry | 注册 schema，处理 optional 字段 |
| JSON | Protobuf | Confluent ProtobufConverter 或 protoc 模板 | oneof/enum 映射需评审 |
| XML | JSON | 自定义 XSLT 或 JAXB 反序列化后转 JSON | 命名空间与属性可能丢失 |
| Avro | JSON | Kafka Connect JsonConverter (`schemas.enable=false`) | 二进制 decimal 需显式处理 |
| Protobuf | JSON | protobuf-java-util / protoc --json_out | 保留 unknown fields 避免信息丢失 |
| CSV/固定宽度 | JSON/Avro | 应用层解析后写入 topic | 编码与分隔符需前置声明 |

### 协议适配决策表

| 源系统 | 目标系统 | 推荐适配方式 | 关键风险 |
| --- | --- | --- | --- |
| Kafka | RabbitMQ | Kafka Connect RabbitMQ Sink / 自定义桥接 | routing key 映射、顺序保证 |
| NATS | Kafka | 自定义桥接或 NATS Streaming/Kafka Connect | subject → topic 命名空间映射 |
| MQTT | Kafka | MQTT Connector / 自定义网关 | QoS 与 Kafka acks 语义不对等 |
| RabbitMQ | Kafka | Kafka Connect RabbitMQ Source | exchange/binding → topic 映射 |
| Pulsar | Kafka | Pulsar IO Kafka Sink | schema 与 offset 语义差异 |
| Redis Stream | Kafka | 应用层轮询 + Kafka Producer | 无内置 connector，需自研 |

【论证】协议适配的核心风险是**语义不对等**：MQTT QoS 1/2 与 Kafka `acks=all` 的持久化语义不同；RabbitMQ 单队列顺序与 Kafka 分区顺序的边界不同；NATS Core 的 at-most-once 与 Kafka 的 at-least-once 在桥接时需要显式去重与幂等设计。

## 2.33.3 六系统转换适配机制

### Kafka

Kafka 生态的转换主力是 **Kafka Connect + Kafka Streams**。

- **Kafka Connect**：通过 Source/Sink Connector 与 SMT（Single Message Transform）实现格式转换、字段替换、路由、时间戳注入；
- **Kafka Streams**：通过 `KStream.mapValues`、`filter`、`flatMap`、`join` 实现复杂业务转换；
- **自定义 Partitioner / Converter**：实现业务路由键生成或特殊编解码。

```java
// Kafka Streams 简单格式转换示例
KStream<String, String> stream = builder.stream("orders-json");
stream.mapValues(value -> JsonToAvro.transform(value))
      .to("orders-avro", Produced.with(Serdes.String(), avroSerde));
```

### NATS

NATS Core 的转换通常在应用层完成：

- 订阅源 subject，转换后发布到目标 subject；
- JetStream 可通过 consumer + publisher 模式实现持久化转换；
- 跨协议桥接（如 NATS → Kafka）需要自研或采用第三方桥接器。

```go
// NATS 应用层转换示例
nc.Subscribe("input.subject", func(msg *nats.Msg) {
    transformed := transformMessage(msg.Data)
    nc.Publish("output.subject", transformed)
})
```

### RabbitMQ

RabbitMQ 的转换可在消费者或插件层完成：

- 消费者从 input queue 读取，转换后发布到 output exchange；
- 使用 RabbitMQ Sharding、Consistent Hash Exchange 做路由；
- 跨协议桥接（如 MQTT plugin → AMQP queue）由 RabbitMQ 内置插件支持。

```python
# RabbitMQ 消费者转换后转发
def transform_message(ch, method, properties, body):
    transformed = json.loads(body)
    transformed['processed_at'] = datetime.now().isoformat()
    ch.basic_publish(
        exchange='output-exchange',
        routing_key='transformed',
        body=json.dumps(transformed)
    )
    ch.basic_ack(delivery_tag=method.delivery_tag)
```

### Pulsar

Pulsar 提供 **Pulsar Functions** 与 **Pulsar IO** 两种转换方式：

- **Pulsar Functions**：类似 AWS Lambda，对 topic 消息做无状态/有状态处理；
- **Pulsar IO**：Kafka Connect 风格的 connector 框架，支持 source/sink 适配；
- **Schema Registry**：原生支持 Avro/JSON/Protobuf schema 版本管理。

### MQTT

MQTT 协议本身不做消息格式转换，转换发生在 broker 插件或网关中：

- **Broker 插件**：如 HiveMQ 扩展、EMQX 规则引擎可在 broker 内做 topic 重写与 payload 转换；
- **网关层**：MQTT → Kafka/Esper/Kafka 的桥接器通常运行在边缘或云端；
- **Sparkplug B**：工业 MQTT 场景下，payload 使用 Protobuf，网关负责 Sparkplug → CloudEvents 的转换。

### Redis Stream

Redis Stream 的转换完全在应用层：

- 使用 `XREADGROUP` 读取消息，转换后通过 `XADD` 写入新 stream 或推送到其他系统；
- 适合作为轻量级流处理节点，但无内置 connector 生态。

## 2.33.4 字段映射与 Schema 治理

### 映射规则设计

字段映射是转换适配中最容易出错的环节。推荐将映射规则外置为配置文件，并通过版本化治理。

项目模板 `topics/config-templates/transform-config.properties` 定义了转换适配的核心参数：

```properties
# 格式转换配置
transform.format.enabled=true
transform.format.from=json
transform.format.to=protobuf
transform.format.schema.registry.url=http://localhost:8081

# 字段映射配置
transform.content.enabled=true
transform.content.field.mapping.enabled=true
transform.content.field.mapping.file=/etc/mq/field-mapping.json

# 协议适配配置
adapter.enabled=true
adapter.type=kafka-to-rabbitmq
adapter.source.type=kafka
adapter.source.brokers=localhost:9092
adapter.target.type=rabbitmq
adapter.target.host=localhost
adapter.target.port=5672

# 转换性能优化
transform.optimization.enabled=true
transform.optimization.cache.enabled=true
transform.optimization.cache.size=10000
transform.optimization.cache.ttl=300
transform.optimization.batch.enabled=true
transform.optimization.batch.size=100

# 转换错误处理
transform.error.handling.enabled=true
transform.error.handling.strategy=dlq
transform.error.handling.dlq.topic=transform-dlq
```

字段映射文件 `/etc/mq/field-mapping.json` 示例：

```json
{
  "mappings": [
    {"from": "orderId", "to": "order_id", "type": "string"},
    {"from": "amt", "to": "amount", "type": "double", "default": 0.0},
    {"from": "createTime", "to": "created_at", "type": "timestamp", "format": "iso8601"}
  ],
  "remove": ["temp_flag"],
  "add": [
    {"name": "processed_at", "type": "timestamp", "value": "now()"}
  ]
}
```

【论证】字段映射应遵循以下原则：

1. **显式声明字段类型与默认值**，避免隐式转换导致精度丢失；
2. **保留原始字段名作为注释或元数据**，便于问题追溯；
3. **对新增字段使用 `add` 规则**，避免在业务代码中硬编码；
4. **映射文件变更走 breaking change 评审**，并配合 Schema Registry 的兼容性策略。

## 2.33.5 产业与域标准适配

### ISO 20022 / FHIR / EPCIS / OpenADR

产业标准与企业内部事件契约的适配是“语义转换”而非简单格式转换。参见 [01-45 产业领域消息标准纵览](../01-基础概念与对比分析/01-45-产业领域消息标准纵览.md)。

| 产业域 | 关键适配点 | 事件契约映射建议 |
| --- | --- | --- |
| 金融 ISO 20022 | pacs/pain/camt 报文版本与状态码 | `type=iso20022.payments.status.changed.v1`，保留原始报文引用 |
| 医疗 FHIR | R4/R4B/R5 资源结构差异、PHI 合规 | `type=org.hl7.fhir.subscriptiontopic.patient-birth.v1`，subject=Patient/<id> |
| 物流 EPCIS | JSON-LD @context 版本、CBV 业务步骤 | `type=gs1.epcis.objectevent.shipping.v1`，key=EPC URI |
| 能源 OpenADR | VTN/VEN 角色、Signal 类型枚举 | `type=energy.dr.event.v1`，保留 Event/Signal/Report 结构 |

【论证】产业标准适配的核心是“保留权威术语表”。不要在转换过程中把标准代码改写为内部缩写，而应在事件契约中同时保留标准字段与内部字段，通过映射文件维护双向翻译。

### IoT 与互联网域标准

工业 IoT 与互联网场景的标准适配参见 [01-46 IoT 与互联网领域消息标准纵览](../01-基础概念与对比分析/01-46-IoT与互联网领域消息标准纵览.md)。

| 域 | 标准 | 典型转换需求 |
| --- | --- | --- |
| 工业 IoT | Sparkplug B | MQTT Protobuf payload → CloudEvents JSON，主题命名空间 `spBv1.0/...` → 内部 UNS |
| 制造互操作 | OPC UA PubSub | UADP/JSON NetworkMessage → MQTT/Kafka topic，Companion Spec 语义映射 |
| 互联网电商 | 自定义事件契约 | 订单状态机事件 → CloudEvents + AsyncAPI，幂等键/序号/状态机约束 |
| AI Agent | A2A Protocol | Task 状态机事件 → MQ topic，`task-id` 作为 key 与 trace-id |

## 2.33.6 转换适配最佳实践

### 设计建议

1. **转换位置应贴近数据源或数据目标，避免在中间层反复序列化/反序列化**。例如 Kafka Connect 在 ingest 阶段统一格式，比在多个微服务中各转一次性能更高。
2. **Schema 先行**：在引入转换前，先在 Schema Registry 注册源与目标 schema，并声明兼容性策略（BACKWARD/FULL）。
3. **幂等 + 去重**：跨协议/跨系统转换必然伴随重试，必须在目标端配置幂等键与去重窗口，参见 [02-25 消息幂等性设计](02-25-消息幂等性设计.md)。
4. **错误隔离**：转换失败消息应进入 DLQ，而不是阻塞主流程。配置 `transform.error.handling.strategy=dlq`，并监控 `transform_errors`。
5. **性能优化**：启用转换缓存（cache.size=10000、cache.ttl=300）与批量转换（batch.size=100），降低重复解析与网络往返开销。
6. **DSL 化契约管理**：把转换规则与事件契约纳入 AsyncAPI DSL 治理，建立“设计源 → DSL → 实现”的正向链路。参见 [01-43 设计到 AsyncAPI DSL 的转换方法论](../01-基础概念与对比分析/01-43-设计到DSL的转换方法论.md)。
7. **测试验证**：落地前后运行 `topics/scripts/transform-test.sh kafka format` 等脚本，验证格式转换、字段映射、协议适配行为符合预期。具体操作与检查清单见 [03-49 消息转换与适配实践指南](../03-架构与运维实践/03-49-消息转换与适配实践指南.md)。
