## 2.49.1 场景与需求

两类需求触发本设计【论证】：

1. **流量弹性**：业务峰谷差大（如电商大促、IoT 早晚高峰），固定容量要么浪费要么扛不住——需要"量"的自动调节。
2. **故障常态**：节点宕机、磁盘写满、consumer 卡死成为常态而非意外——需要"质"的自动处置，把 MTTR 从小时级压到分钟级。

设计约束：① 消息系统是有状态/半有状态系统，伸缩与自愈动作会影响消息语义（重平衡、重复、顺序）；② 自动化动作本身可能成为故障源（扩容打挂集群、自愈误杀）。

## 2.49.2 自动伸缩方案对比

| 方案 | 机制 | 适用 | 优点 | 风险 |
| ------ | ------ | ------ | ------ | ------ |
| KEDA 按 lag 伸缩 | 消费 lag 超阈值扩 consumer Pod | Kafka/Pulsar/RabbitMQ/NATS JetStream/Redis | 语义直接（lag=待办工作量）、云原生 | 指标延迟；rebalance 抖动 |
| HPA 按 CPU/内存 | 资源饱和度扩缩 | 无状态化后的 consumer | 通用、成熟 | 与消息积压弱相关，滞后【论证】 |
| 定时伸缩（cron） | 按预测峰谷定时调副本 | 峰谷规律强的业务 | 简单可预测 | 应对不了突发 |
| broker 水平扩容+再平衡 | 磁盘/IO 阈值触发加节点 | Kafka/Pulsar 存储层 | 治本 | 再平衡窗口长、有搬迁风险 |
| 分区扩容 | 分区数增加 | 并行度不足 | 提升并行上限 | 只影响新消息顺序域，需规划 |

关键设计决策点【论证】：

- **消费者 vs broker 扩容顺序**：先扩消费者（分钟级、低风险），不够再扩分区/broker（小时级、有搬迁）。判据：分区数 > 当前 consumer 数时扩 consumer 才有效。
- **扩缩不对称**：扩容激进（快速止血），缩容保守（2-3 倍冷却 + lag≈0 + 低利用率三重判据）。
- **lag 阈值标定**：阈值 = 业务可容忍积压时长 × 消费速率【估算】；阈值过小导致频繁伸缩，过大失去意义。

### 扩容触发模型（多指标组合）

单一信号触发容易误动，推荐组合触发【论证】：

```text
扩容 = lag 超阈 AND（处理速率饱和 OR 消费延迟上升）
        AND 分区数 > 当前副本数 AND 处于允许伸缩窗口
缩容 = lag≈0 AND 利用率<30% 持续 900s AND 非重平衡进行中
分区扩容 = 分区打满（produce 延迟升） AND 分区数 < 规划上限
```

### 消费者并行度与分区模型

并行度上限 = min(分区数, 消费者实例数×实例内线程)【定理：Kafka 分区分配语义】；KEDA 的 `allowIdleConsumers=false` 可防止副本数超过分区数时空转。Redis Stream 的并行度上限 = 消费组内消费者数；NATS JetStream 的 push/pull 模型上限语义不同（pull consumer 可多于分区概念）——选型论证时须按系统核对【论证】。

## 2.49.3 自愈方案对比

| 方案 | 机制 | 覆盖场景 | 自治级别 | 风险 |
| ------ | ------ | ---------- | :---: | ------ |
| 平台重启策略（K8s restartPolicy/探针） | 进程消失自动拉起 | 进程崩溃 | L2 | 低（幂等） |
| 磁盘清理机器人 | 阈值触发清理白名单路径 | 磁盘写满 | L2 | 中（误删需白名单+保留期） |
| leader 再平衡 cron | 定时检查触发选举 | leader 倾斜 | L2 | 低 |
| consumer 健康重启 | 有心跳无进展判定卡死后重启 | 消费卡死/死锁 | L2-L3 | 中（需幂等消费兜底） |
| broker 自动替换（K8s 节点+StatefulSet） | 节点故障自动重建 | 节点宕机 | L3 | 中（重建期间容量下降需冗余） |
| 自动降级（切备用链路/关非核心消费） | 故障时切换流量 | 下游故障 | L3 | 高（需预案演练） |
| 自动重投 DLQ | 死信自动回投 | 毒消息 | ❌ 禁止自动 | 极高（循环打挂下游） |

自愈设计三原则【论证】：① **幂等护栏**——所有自动处置必须可安全重入；② **熔断升级**——同一处置连续失败 N 次自动升级人工；③ **审计留痕**——每次自动动作记录触发信号、处置、结果，供 TEST-07 验证与复盘。

### 自愈检测器设计（误报控制）

自愈的信任瓶颈在检测器：误报导致误处置（伤害），漏报等于没有【论证】。检测器设计要点：

| 要素 | 要求 |
| ------ | ------ |
| 信号组合 | 单信号不动作（如"进程消失"须配"非维护窗口"确认） |
| 持续判据 | for 窗口（如连续 3 次探测失败）防瞬时抖动 |
| 去抖与冷却 | 处置后冷却期，防连续触发 |
| 灰度 | 新自愈规则先"仅告警不动作"观察 1-2 周再放动作 |
| 演练 | 每季度 GAME DAY 注入演练（对齐 TEST-07 TC-OBS-09） |

### 典型场景论证

- **电商大促**：峰谷差 10 倍+ → KEDA lag 伸缩 + 定时伸缩双触发；broker 层提前 1 周扩节点（再平衡入演练窗口）。
- **IoT 设备接入**：连接数潮汐明显 → 以连接数/会话数为主要伸缩信号（MQTT broker 水平扩展），消息 lag 为辅【论证】。
- **日志管道**：吞吐稳定但有突发 → HPA CPU 兜底 + lag 阈值宽松（小时级容忍）。

## 2.49.4 选型建议

| 场景 | 推荐方案组合 | 理由 |
| ------ | -------------- | ------ |
| K8s 上 Kafka 消费者 | KEDA（lag）+ HPA（CPU 兜底）+ 定时伸缩（峰谷） | 语义+资源+预测三层触发 |
| 非 K8s 传统部署 | 自研 lag 巡检 + 扩容脚本 + supervisor 拉起 | 无 KEDA 依赖，工程可控 |
| broker 层容量 | 磁盘/IO 阈值 → 加节点再平衡（人工确认窗口） | 数据搬迁风险高，保留人审 |
| 自愈起步 | 先落地 restartPolicy + 磁盘清理 + leader 平衡三件套（L2） | 收益/风险比最高 |
| 自愈进阶 | consumer 健康重启 + broker 自动替换（L3，需幂等消费与冗余容量前提） | 有测试验证（TEST-07）后逐步放开 |

## 2.49.5 边界与反模式

反模式【论证】：

- ❌ 数据面自动"修数据"：任何消息丢失/重复/乱序类问题禁止自动处置（人工裁决）。
- ❌ quorum 丢失自动恢复：可能加剧脑裂，必须人工。
- ❌ DLQ 自动重投：循环风险，必须人工确认根因。
- ❌ 缩容无冷却：重平衡风暴的常见诱因。
- ❌ 以 CPU 作为唯一伸缩信号：消息积压型业务 CPU 可能不高但 lag 爆炸。

与 02-37（限流）/02-38（降级）的衔接：降级是自愈的"高阶形态"（主动止血），建议降级预案纳入自愈矩阵的统一演练（TEST-07 TC-OBS-10）。

### 伸缩/自愈与消息语义的交互（设计时必须评估）

| 动作 | 语义影响 | 缓解 |
| ------ | ---------- | ------ |
| consumer 扩缩 | Kafka 触发 rebalance：短暂停顿、可能重复 | 幂等消费（02-25）+ 扩缩避开事务窗口 |
| 分区扩容 | 新分区无历史顺序保证 | 按 key 路由不变式设计 |
| broker 扩容+再平衡 | 搬迁期间 ISR 压力、延迟升高 | 限流搬迁、低峰执行、RF≥3 |
| 自愈重启 consumer | 未提交消息重投（at-least-once） | 幂等键/去重表（02-14） |
| 自愈替换 broker | 副本重选主、短暂 URP | 充足冗余 + 自动重分配 |

### 成本权衡

自治不是免费【论证】：KEDA/监控/自愈工程每年消耗人力【估算：0.5-1 人年起步】；收益是 MTTR 缩短与容量成本优化。建议以"告警处理人时 × 频率"估算自愈收益，以"峰谷差 × 资源单价"估算伸缩收益——收益 < 成本的业务保持 L1-L2 即可，不必追求 L4。

### 选型决策树（快速收敛）

```text
在 K8s 上？
├─ 是 → 消费端积压型？ ─yes→ KEDA(lag) + HPA(CPU兜底)
│       └─ 否（CPU 型）→ HPA 为主
└─ 否 → 有调度平台（如 Mesos/自研）？ ─yes→ 平台 API + lag 巡检脚本
        └─ 否 → 定时伸缩 + 人工扩容（接受 L1-L2）
自愈成熟度：
  消费是否幂等？ ─否→ 仅 L2（拉起/清理类无状态动作）
  └─ 是 → 冗余容量 ≥1 节点？ ─是→ 可放开 L3（重启/替换）
            └─ 否 → 保持 L2
```

### KEDA 触发器对照（按系统）

| 系统 | scaler 类型 | 关键参数 | 说明 |
| ------ | ------------- | ---------- | ------ |
| Kafka | `kafka` | lagThreshold、offsetResetPolicy | 语义最直接（本库模板） |
| Pulsar | `pulsar` | msgBacklogThreshold | 基于 subscription backlog |
| RabbitMQ | `rabbitmq` | queueLength、protocol | 队列长度触发 |
| NATS JetStream | `nats-jetstream` | lagThreshold（stream/consumer） | 2.x 支持 |
| Redis | `redis` | listLength/pendingEntriesCount | Stream 场景用 pending |

参数标定统一方法：阈值 = 业务可容忍积压时长 × 稳态消费速率；offsetResetPolicy 选 `latest`（避免新组全量回溯打爆扩容）【论证】。

### 缩容安全判据（展开）

缩容的事故率高于扩容【论证】，必须满足全部判据才执行：

| 判据 | 取值建议 | 理由 |
| ------ | ---------- | ------ |
| lag 近零 | lag < 阈值 5% 持续 15 分钟 | 防撤力后积压反弹 |
| 利用率低 | CPU < 30% 持续 900s | 留缓冲应对突发 |
| 冷却期 | ≥ 一次完整 rebalance 时长【估算】 | 防缩容-重平衡-再缩容震荡 |
| 步长 | 每次缩 1-2 副本，间隔 ≥300s | 渐进可回退 |
| 时间窗 | 避开业务高峰窗与发布窗 | 减少叠加风险 |
| 下限 | minReplicaCount ≥ 2（HA 基线） | 保活 |

与 03-07 的关系：03-07 给弹性伸缩概念与多系统概览；本文给出触发模型、判据与决策树的设计论证，03-63 给操作命令与检查清单——三层互链不重复。

### 落地前评审问题清单（设计评审用）

- [ ] 伸缩动作是否评估了与消息语义的交互（rebalance/顺序/事务窗口）？
- [ ] 缩容判据六项是否全部具备（缺一项不上缩容自动化）？
- [ ] 自愈规则是否经过"仅告警观察期"（≥1 周）再放动作？
- [ ] 每个 L3 动作是否有对应的熔断升级路径与人工接管口？
- [ ] 自治收益是否量化（MTTR 缩短/容量节省 vs 工程投入）？
