## 2.26.1 序列化场景与选型维度

### 常见场景

1. **数据交换**
   - 微服务间事件通知，需要跨语言、跨版本兼容。
   - 大数据管道，追求高吞吐与紧凑体积。

2. **存储与回放**
   - 事件溯源日志长期保留，要求 Schema 可演进。
   - 消息审计与合规，需要可读性或标准化信封。

3. **边缘与 IoT**
   - 受限带宽与算力，偏好二进制、无 Schema 自描述开销的格式。
   - 工业协议（Sparkplug、OPC UA）已规定特定编码。

### 选型维度

【论证】序列化选型需综合考虑：

- **可读性**：JSON、XML 便于调试；Avro、Protobuf 为二进制。
- **Schema 演进**：Avro、Protobuf 提供显式 Schema 与兼容性规则。
- **性能**：二进制格式通常序列化更快、体积更小。
- **生态**：Kafka 与 Confluent Schema Registry 对 Avro 支持最成熟。
- **标准合规**：金融、医疗、物流等产业域有既定报文标准。

## 2.26.2 序列化格式选型

### 格式对比决策表

| 格式 | 体积 | 速度 | Schema 演进 | 可读性 | 推荐场景 |
| ---- | ---- | ---- | ----------- | ------ | -------- |
| JSON | 大 | 中 | 弱（需约定） | 高 | 调试、Web 接口、异构系统 |
| Avro | 小 | 快 | 强 | 低 | Kafka 生态、大数据管道 |
| Protobuf | 小 | 快 | 强 | 低 | gRPC、微服务间通信 |
| MessagePack | 中 | 快 | 弱 | 中 | 嵌入式、IoT 场景 |
| XML | 大 | 慢 | 中 | 中 | 传统企业集成、SOAP |

### 按场景快速决策

| 场景 | 推荐格式 | 理由 |
| ---- | -------- | ---- |
| Kafka 大数据管道 | Avro + Schema Registry | 原生支持、紧凑、Schema 可演进 |
| gRPC 微服务通信 | Protobuf | 跨语言、解析快、工具链成熟 |
| 前端/日志/调试 | JSON | 可读性高、无需 Schema 注册 |
| 工业 IoT/边缘 | MessagePack / Protobuf | 体积小、解析快；Sparkplug 已用 Protobuf |
| 金融跨境支付 | ISO 20022 MX/JSON | 行业强制标准，参见 [1.45](../01-基础概念与对比分析/01-45-产业领域消息标准纵览.md) |
| 医疗 FHIR 事件 | FHIR JSON/XML | 监管与互操作要求，参见 [1.45](../01-基础概念与对比分析/01-45-产业领域消息标准纵览.md) |

## 2.26.3 Kafka 序列化与 Schema Registry

Kafka 生产者通过 `key.serializer` 与 `value.serializer` 指定序列化器。Avro 场景需接入 Confluent Schema Registry：

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
    "io.confluent.kafka.serializers.KafkaAvroSerializer");
props.put("schema.registry.url", "http://schema-registry:8081");

KafkaProducer<String, GenericRecord> producer = new KafkaProducer<>(props);
```

【论证】在 Kafka 生态中，Avro 配合 Schema Registry 可实现向后/向前/全兼容的 Schema 演进，是事件驱动架构的首选；Protobuf 更适合 gRPC 服务间通信；JSON 则在对可读性要求高的场景保留。

## 2.26.4 NATS 序列化

NATS 消息体为字节数组，序列化格式由应用决定。常见选择：

```go
// JSON 序列化
import "encoding/json"
data, _ := json.Marshal(order)
nc.Publish("orders", data)

// Protobuf 序列化
import "google.golang.org/protobuf/proto"
data, _ := proto.Marshal(order)
nc.Publish("orders", data)
```

配置中 `nats.serialization.format` 可取 `json`、`protobuf`、`msgpack`。

## 2.26.5 RabbitMQ 序列化

RabbitMQ 同样不限制消息体格式，但 Python 生态常用 JSON、pickle、msgpack。

```python
import json

message = json.dumps(order, ensure_ascii=False)
channel.basic_publish(
    exchange='orders',
    routing_key='',
    body=message.encode('utf-8'),
    properties=pika.BasicProperties(
        content_type='application/json',
        delivery_mode=2
    )
)
```

生产环境应避免使用 `pickle`，因其存在反序列化代码执行风险。

## 2.26.6 产业与 IoT 域序列化考量

产业标准往往已规定报文格式，企业事件契约需在其上做映射：

| 产业域 | 标准格式 | 与 MQ 序列化结合 |
| ------ | -------- | ---------------- |
| 金融 | ISO 20022 MX/JSON | 内部微服务可转 Avro/JSON，但对清算网络保留 MX |
| 医疗 | FHIR JSON/XML | 事件信封用 CloudEvents，payload 保留 FHIR 资源 |
| 物流 | EPCIS 2.0 JSON-LD | Kafka key 用 EPC URI，value 用 JSON-LD |
| 能源 | OpenADR 3.0 JSON | MQTT/Kafka 事件契约直接承载 JSON payload |
| 工业 IoT | Sparkplug B Protobuf | 遵循规范，不可擅自更换编码 |

【论证】IoT 场景参见 [1.46 IoT 与互联网领域消息标准纵览](../01-基础概念与对比分析/01-46-IoT与互联网领域消息标准纵览.md)：Sparkplug B 强制使用 Protobuf，OPC UA PubSub 可选 UADP 二进制或 JSON；互联网电商则更灵活，推荐 Avro + Schema Registry 做版本治理。

## 2.26.7 版本兼容策略

消息 Schema 演进是序列化设计的核心。常用兼容性级别：

| 级别 | 含义 | 适用场景 |
| ---- | ---- | -------- |
| Backward | 新 Schema 可被旧 Consumer 读取 | 生产默认，新增字段带默认值 |
| Forward | 旧 Schema 可被新 Consumer 读取 | 需要新旧并行部署 |
| Full | 同时满足 Backward + Forward | 最严格，新增字段必须带默认值 |
| None | 不校验兼容性 | 受控迁移窗口短期使用 |

Avro 示例：新增可选字段并设置默认值，保证 Backward 兼容。

```json
{
  "type": "record",
  "name": "Order",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "currency", "type": "string", "default": "CNY"}
  ]
}
```

Protobuf 示例：新增字段必须分配新 field number，删除字段建议标记 `reserved`。

```protobuf
syntax = "proto3";
message Order {
  string order_id = 1;
  double amount = 2;
  string currency = 3;
  reserved 4;  // 已删除字段编号保留
}
```

## 2.26.8 序列化最佳实践

### 设计建议

1. **格式选择**
   - Kafka 大数据管道优先 Avro + Schema Registry。
   - gRPC/微服务优先 Protobuf。
   - 调试接口、前端事件优先 JSON。
   - 工业 IoT 遵循 Sparkplug/OPC UA 既定编码。

2. **版本治理**
   - 所有事件契约必须显式携带版本头，如 `message-version=1.2.0`。
   - 业务语义化版本与 Schema Registry 内部版本建立映射表。
   - 生产默认兼容性级别设为 `backward`。

3. **性能与安全**
   - 消息体大于 1 KB 且 QPS 较高时启用压缩（snappy/lz4）。
   - 避免使用不安全的反序列化库（如 Python pickle）。
   - 开启序列化缓存与监控：`serialization.cache.enabled=true`、`serialization.monitor.enabled=true`。

### 配置模板引用

序列化配置统一引用 `topics/config-templates/serialization-config.properties`：

```properties
# 消息序列化配置模板（引用 topics/config-templates/serialization-config.properties）
serialization.format=avro
serialization.compression.enabled=true
serialization.compression.type=snappy

kafka.key.serializer=org.apache.kafka.common.serialization.StringSerializer
kafka.value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer

schema.registry.enabled=true
schema.registry.url=http://schema-registry:8081
schema.registry.compatibility.level=backward

version.management.enabled=true
version.header.name=message-version
version.format=semantic

serialization.cache.enabled=true
serialization.cache.size=10000
serialization.pool.enabled=true
serialization.pool.size=10

serialization.monitor.enabled=true
serialization.monitor.metrics=serialization_count,serialization_duration,serialization_size
```
