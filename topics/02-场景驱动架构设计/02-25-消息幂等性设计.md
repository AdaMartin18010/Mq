## 2.25.1 幂等性场景与边界

### 重复消息来源

1. **网络重传**
   - 生产者发送消息后未收到 ACK，TCP 重传或客户端重试会导致同一条消息被写入多次。
   - Kafka Producer 在 `retries` 大于 0 时可能产生重复消息。

2. **系统重试与故障恢复**
   - 消费失败触发重试，或 Consumer 处理完业务但提交 offset 前崩溃，都会导致消息被重新投递。
   - 重试间隔超过去重窗口后，内存去重可能失效。

3. **业务侧重复提交**
   - 用户重复点击、上游服务超时重试、调度任务重叠执行。
   - 例如支付回调因网络超时被重复发送。

### 幂等性不等于 Exactly-Once

【论证】消息幂等性不等于 Exactly-Once 语义。Producer 幂等性解决的是“同一消息不被重复写入”；Consumer 幂等性解决的是“同一消息不被重复处理”。完整的 EOS 还需要事务性偏移提交与状态更新配合。

| 层级 | 解决的问题 | 典型机制 |
| ---- | ---------- | -------- |
| Producer 幂等 | 单会话内同一条消息不重复写入 | Kafka `enable.idempotence=true` |
| Broker 去重 | 同一消息 ID 在窗口内不重复存储 | NATS JetStream `Nats-Msg-Id` |
| Consumer 幂等 | 同一条消息不重复处理 | 去重表 / 数据库唯一约束 |
| 事务 EOS | 消息消费与状态更新原子一致 | Kafka Transactions、Outbox |

## 2.25.2 幂等键设计

### 键生成策略

1. **消息 ID 方案**
   - 生产者为每条消息生成全局唯一 ID，例如 UUID 或 Snowflake。
   - Kafka 使用 `kafka.transaction.id` 保证跨会话幂等，RabbitMQ 使用 `message_id` 属性。
   - 配置 `nats.idempotence.msg.id.generator=uuid`、`rabbitmq.idempotence.message.id.generator=uuid`。

2. **业务键方案**
   - 以业务唯一字段作为幂等键，例如订单号、支付流水号、用户 ID + 操作类型。
   - 业务键需稳定不变，避免使用可能重复的本地序列号。

3. **复合键方案**
   - 组合消息 ID 与业务键：`{biz_type}:{biz_key}:{msg_id}`，适用于同一业务操作由多条消息触发的场景。

### 键策略决策表

| 策略 | 唯一性保证 | 稳定性 | 可读性 | 适用场景 |
| ---- | ---------- | ------ | ------ | -------- |
| 消息 ID | 高 | 中 | 低 | 通用去重、跨系统追踪 |
| 业务键 | 中 | 高 | 高 | 订单/支付等强业务语义 |
| 复合键 | 高 | 高 | 中 | 同一业务多消息触发 |

## 2.25.3 去重存储选型

### 存储方案对比

| 方案 | 位置 | 一致性 | 存储开销 | 适用场景 | 推荐 MQ |
| ---- | ---- | ------ | -------- | -------- | -------- |
| 原生 Producer 幂等 | 客户端 | 高 | 无 | 单会话内去重 | Kafka |
| 消息唯一 ID + 去重表 | 应用层 | 高 | 中 | 跨会话、跨分区 | 所有 MQ |
| 数据库唯一约束 | 业务库 | 高 | 低 | 状态变更类操作 | 所有 MQ |
| 事件溯源状态机 | 应用层 | 高 | 高 | 复杂业务流程 | 所有 MQ |
| NATS MsgId | Broker | 中 | 低 | JetStream 发布去重 | NATS |
| Redis 去重窗口 | 应用层 | 中 | 低 | 短周期高频去重 | 所有 MQ |

【论证】对于 Kafka，优先启用 `enable.idempotence=true` 解决 Producer 端重复；Consumer 端仍需通过业务 ID 或事件溯源状态机去重。NATS JetStream 的 `Nats-Msg-Id` 提供窗口内的发布去重，适合简单场景。

## 2.25.4 Kafka 幂等性

### Producer 幂等性

Kafka 通过 `enable.idempotence=true` 实现生产者幂等：Broker 为每个 Producer 分配 PID，按 `<PID, SequenceNumber>` 对单分区消息去重。

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

【定理】Kafka 幂等生产者保证：单会话、单分区、同一条消息不会被重复写入。跨会话或跨分区仍需应用层去重。

### Consumer 幂等性

即使开启幂等生产者，Consumer 仍可能因 rebalance 或手动提交失败而重复消费。消费端必须维护去重表或本地缓存：

```java
// 伪代码：使用 Redis Set 做去重窗口
String idempotencyKey = bizType + ":" + bizKey + ":" + msgId;
Boolean isNew = jedis.setnx(idempotencyKey, "1");
if (isNew == 0) {
    log.warn("Duplicate message skipped: {}", idempotencyKey);
    return;
}
jedis.expire(idempotencyKey, 86400); // 24 小时窗口
process(record);
```

## 2.25.5 RabbitMQ 幂等性

RabbitMQ 原生不提供生产者幂等，需在应用层通过消息 ID 或业务键去重。生产环境建议使用 Redis 或数据库替代内存 `set`，避免重启丢失去重状态。

```python
import uuid
import pika

# 发送时设置全局唯一 message_id
channel.basic_publish(
    exchange='orders',
    routing_key='',
    body=message,
    properties=pika.BasicProperties(
        message_id=str(uuid.uuid4()),
        delivery_mode=2
    )
)

# 消费端去重（生产环境用 Redis/DB 替代内存 set）
processed_ids = set()
def callback(ch, method, properties, body):
    if properties.message_id in processed_ids:
        ch.basic_ack(delivery_tag=method.delivery_tag)
        return
    process(body)
    processed_ids.add(properties.message_id)
    ch.basic_ack(delivery_tag=method.delivery_tag)
```

## 2.25.6 NATS 幂等性

NATS JetStream 支持通过 `Nats-Msg-Id` 头在发布窗口内去重；消费端仍需幂等处理，因为 JetStream 的去重只解决“不重复存储”，不解决“不重复投递”。

```go
// 发布侧去重
js.Publish("orders", data, nats.MsgId("msg-123"))

// 消费侧幂等
processedIDs := make(map[string]bool)
nc.Subscribe("orders", func(msg *nats.Msg) {
    msgID := msg.Header.Get("Nats-Msg-Id")
    if processedIDs[msgID] {
        msg.Ack(); return
    }
    process(msg)
    processedIDs[msgID] = true
    msg.Ack()
})
```

## 2.25.7 事件溯源与幂等协同

事件溯源（Event Sourcing）以追加事件为唯一真相源，天然适合幂等消费：同一事件重复投递时，聚合应用事件后状态不变（幂等事件）或按 `expected_version` 拒绝重复写入。参见 [1.47 事件溯源核心机制与存储选型](../01-基础概念与对比分析/01-47-事件溯源核心机制与存储选型.md)。

```sql
-- PostgreSQL 风格事件表：stream_id + version 唯一约束实现幂等写入
CREATE TABLE events (
    stream_id    VARCHAR(255) NOT NULL,
    version      BIGINT       NOT NULL,
    event_type   VARCHAR(255) NOT NULL,
    payload      JSONB        NOT NULL,
    metadata     JSONB,
    occurred_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    PRIMARY KEY (stream_id, version)
);

INSERT INTO events (stream_id, version, event_type, payload)
SELECT 'order-123', 3, 'OrderPaid', '{"amount": 100}'
WHERE (SELECT COALESCE(MAX(version), 0) FROM events WHERE stream_id = 'order-123') = 2;
```

【论证】事件溯源通过“版本号 + 主键唯一约束”把幂等性下沉到存储层，既防止重复写入，又保留完整审计历史。但引入事件溯源需权衡投影复杂度与团队 DDD 能力。

## 2.25.8 零信任下的幂等凭证

在零信任消息架构中，幂等键本身也可能成为安全攻击面：攻击者若可预测或伪造幂等键，可能绕过业务校验。参见 [1.49 消息系统零信任安全体系](../01-基础概念与对比分析/01-49-消息系统零信任安全体系.md)。

| 风险 | 防护措施 |
| ---- | -------- |
| 幂等键被猜测/遍历 | 使用高熵 UUID 或 Snowflake，避免自增序列 |
| 去重表被注入 | 幂等键作为字符串参数绑定，不做 SQL 拼接 |
| 长期去重键泄露隐私 | 对幂等键做哈希或加密后再存储 |
| 跨租户键冲突 | 键前缀包含租户 ID，如 `{tenant}:order:{order_no}` |

## 2.25.9 幂等性最佳实践

### 设计建议

1. **多层防护**
   - 系统层：Kafka 开启幂等生产者，RabbitMQ/NATS 设置消息 ID。
   - 应用层维护去重表或缓存，数据层使用唯一索引或状态机条件更新。

2. **异常处理**
   - 去重表插入冲突时，先查询状态：若 `SUCCESS` 则直接返回，若 `FAILED` 则允许重试。
   - 处理中状态超过 5 分钟未更新，应视为超时并释放锁。

3. **性能优化**
   - 高频场景使用 Redis + 本地缓存双层结构，`idempotency.cache.size=100000` 命中率高时可降低 Redis 压力。
   - 长周期去重使用数据库，并按月/按租户分区控制表大小。

### 配置模板引用

幂等性配置统一引用 `topics/config-templates/idempotency-config.properties`：

```properties
# 消息幂等性配置模板（引用 topics/config-templates/idempotency-config.properties）
kafka.producer.idempotence.enabled=true
kafka.producer.acks=all
kafka.producer.retries=2147483647
kafka.producer.max.in.flight.requests.per.connection=5
kafka.transaction.id=my-transactional-id

idempotency.check.enabled=true
idempotency.check.type=redis
idempotency.check.storage.redis.host=localhost
idempotency.check.storage.redis.port=6379
idempotency.check.storage.redis.ttl.seconds=86400

idempotency.cache.enabled=true
idempotency.cache.size=100000
idempotency.cache.ttl.seconds=3600

idempotency.monitor.enabled=true
idempotency.monitor.metrics=duplicate_count,idempotency_check_count,idempotency_check_duration
idempotency.alert.duplicate.rate.threshold=0.01
```
