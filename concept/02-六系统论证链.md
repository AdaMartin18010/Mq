## 统一五段式骨架

每系统按以下结构展开：

1. **它是什么**: 一句话定义 + 诞生动机。
2. **强在哪**: 旗舰特性 + 证据（官方基准 / Jepsen / 项目内专章）。

4. **证据链**: 关键文档与项目内指针表。
5. **什么时候选它**: 一句判据。

## Kafka

### ① 它是什么

分布式高吞吐持久化日志流平台，诞生于 LinkedIn 统一海量日志管道的需求。

### ② 强在哪

- 顺序分区日志 + 批量/零拷贝，成就高吞吐持久化写入【论证】。
- KRaft 模式逐步替代 ZooKeeper，降低外部依赖【论证：Kafka 3.7+ 默认 KRaft】。
- Tiered Storage 可把冷数据卸载到对象存储，延长保留并降本【论证】。
- 生态最丰富：Kafka Connect、Kafka Streams、ksqlDB、MirrorMaker 2 等。

### ③ 弱在哪

- 消费者组重平衡期间会出现暂停（rebalance storm）【论证】。
- 运维复杂度高：ISR、Leader Election、Controller、Log Segment 均需理解【论证】。
- 延迟尾部较高，对亚毫秒级敏感场景不是最优【估算】。

## RabbitMQ

### ① 它是什么

以 AMQP 协议为核心的消息代理，通过 Exchange + Queue + Binding 实现灵活路由，诞生于企业应用集成场景。

### ② 强在哪

- Exchange/Binding 模型支持复杂路由（direct/topic/fanout/headers）【论证】。
- Quorum Queue 在 RabbitMQ 4.x 成为默认，基于 Raft 提供高可用【论证】。
- AMQP 协议成熟，多语言客户端与企业集成生态丰富【论证】。

### ③ 弱在哪

- 极高吞吐（百万级 TPS）下磁盘 I/O 容易成为瓶颈【论证】。
- Quorum Queue 不支持 TTL、优先级队列等部分 Classic Queue 特性【论证】。
- 集群镜像队列历史上有脑裂与网络分区处理复杂度【论证】。

## NATS

### ① 它是什么

云原生轻量级消息系统：Core NATS 提供高速 Pub/Sub，JetStream 补充持久化与流语义，诞生于连接微服务、IoT 与边缘的需求。

### ② 强在哪

- Core NATS 极简、低延迟、高扇出【论证】。
- JetStream 提供 Stream、Consumer、KV、Object Store，覆盖持久化场景【论证】。
- Leafnode 与 Supercluster 支持边缘到中心的联邦拓扑【论证】。

### ③ 弱在哪

- JetStream 在超大规模持久化与长期保留方面不如 Kafka 成熟【论证】。
- surrounding 生态（监控、Connect 类工具）比 Kafka 少【估算】。
- 强一致性多活写入不是其首要设计目标【论证】。

## Pulsar

### ① 它是什么

云原生分布式流平台，采用 Broker（无状态计算）+ Apache BookKeeper（存储）的存算分离架构，旨在统一队列与流。

### ② 强在哪

- 存算分离可独立扩展计算与存储【论证】。
- 多租户（Tenant）+ 命名空间（Namespace）提供企业级隔离【论证】。
- Geo-Replication 支持跨地域复制，Ledger 模型提供低延迟持久化【论证】。

### ③ 弱在哪

- 组件多：Broker、Bookie、ZooKeeper/Oxia、Proxy，运维复杂度高【论证】。
- 社区生态与 Kafka 相比仍小一圈【估算】。
- 延迟优化需要针对 BookKeeper E/WQ/AQ 精细调参【估算】。

### ⑤ 什么时候选它

**需要存算分离、多租户、统一消息与流，并愿承担更多运维组件时。**

## RocketMQ

### ① 它是什么

阿里开源的分布式消息与流平台，为金融级高可靠顺序消息、事务消息而生。

### ② 强在哪

- 原生支持事务消息、顺序消息、定时/延迟消息【论证】。
- 阿里双十一等大规模场景验证过高可用与顺序能力【论证】。
- NameServer 架构轻量，部署相对简单。

### ③ 弱在哪

- 国际化生态、第三方工具链与 Kafka 比仍有差距【估算】。
- 新版本升级与周边生态（如流处理）复杂度不容忽视【论证】。
- 部分高级功能依赖商业版或特定版本【估算】。

## Redis Stream

### ① 它是什么

Redis 内置的追加式日志结构，让已有 Redis 基础设施的应用“顺便”获得轻量消息队列能力。

### ② 强在哪

- 无额外中间件，低延迟，与 Redis 现有数据结构共用基础设施【论证】。
- Consumer Group、PEL、XACK 模型简洁，适合任务队列【论证】。
- 适合中小规模、高并发、短延迟的消息场景。

### ③ 弱在哪

- 容量受 Redis 单节点/集群限制，不适合海量消息长期堆积【论证】。
- 持久化依赖 AOF/RDB，极端情况下有数据丢失窗口【论证】。
- 缺乏 Kafka 级别的副本一致性协议与生态工具【论证】。

## Redpanda 附注

Redpanda 是 Kafka API 兼容的 C++ 实现，去除了外部依赖（无需 ZooKeeper/KRaft 的额外进程），在延迟与部署简洁性上有优势【论证】。
但其 surrounding 生态（Connector、Streams、云托管成熟度）仍落后于 Kafka 主生态【估算】。
适合“想要 Kafka 兼容协议，但希望简化运维”的场景。详见 [01-28-Redpanda分析](../topics/01-基础概念与对比分析/01-28-Redpanda分析.md)。

## 六系统速览

| 系统 | 核心模型 | 最强项 | 最大痛点 | 一句话判据 |
| ---- | ---- | ---- | ---- | ---- |
| Kafka | 分区日志 | 高吞吐、生态、长期保留 | 运维重、重平衡 | 高吞吐事件流首选 |
| RabbitMQ | Exchange+Queue | 灵活路由、AMQP 生态 | 极高吞吐下磁盘瓶颈 | 复杂路由与企业集成首选 |
| NATS | Pub/Sub + JetStream | 极简、低延迟、边缘联邦 | 超大规模持久化弱 | 云原生/边缘/微服务首选 |
| Pulsar | 存算分离 | 多租户、统一队列与流 | 组件多、生态小 | 多租户统一消息平台首选 |
| RocketMQ | 队列+事务 | 事务/顺序/金融级可靠 | 国际化生态弱 | 金融级事务消息首选 |
| Redis Stream | 内存日志 | 无额外中间件、低延迟 | 容量与持久化受限 | 已有 Redis 的轻量队列首选 |
