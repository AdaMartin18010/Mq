## 1. 五层塔总览

```text
L0 公理层      不可再分的前提（网络分区、节点故障、时钟异步、存储有限…）
    ↓ 推导
L1 语义定律层   协议规范保证的定律（exactly-once 边界、CAP 精确化、幂等必要性…）
    ↓ 形式化
L2 模型层      M/M/1、系统动力学、博弈矩阵、控制回路、S 曲线…
    ↓ 工程化
L3 模式层      DLQ / Outbox / Saga / Claim-check / 幂等键 / 背压…
    ↓ 落地
L4 实例层      8 业务场景 × 契约 × GWT 断言 × 23 verified 用例 × 检查清单
```

五层塔的核心价值：把 `topics/` 与 `Testing/` 的 281 篇文档从"按主题堆放"升级为"按逻辑依赖可推导"。每一层的结论必须能在下一层找到承接，否则就是孤证。全库逐层归档见 [`topics/scripts/doc-layer-archive.tsv`](../topics/scripts/doc-layer-archive.tsv)，生成器为 [`doc-layer-archive.py`](../topics/scripts/doc-layer-archive.py)。

### 1.1 超越扁平阶梯：与 01-概念体系导读.md 的关系

[01-概念体系导读.md](01-概念体系导读.md) 按"消息 → 队列 → 日志 → 语义 → 系统 → 治理"六阶依赖重排 108 个概念，它解决的是**学习顺序**问题。本篇则进一步回答**逻辑强度**问题：

- 六阶地图是**扁平的**：它告诉你先学什么、后学什么，但不告诉你为什么"队列"必须出现在"日志"之前、为什么"exactly-once"不能降为"at-least-once"。
- 五层塔是**可推导的**：L0 公理决定 L1 定律，L1 定律限制 L2 模型，L2 模型指导 L3 模式，L3 模式产生 L4 实例。任何一层内的概念冲突，都可向上溯源到更高层的定律或公理来裁决。

因此，六阶地图适合**第一次进入知识库的人**建立直觉；五层塔适合**需要论证选型决策的人**给出不可推卸的推导链。

## 2. L0 公理层：领域不可再分前提

L0 公理不是"消息队列独有"，而是分布式系统领域无法继续拆解、只能接受的前提。它们共同构成后续所有定律与工程决策的约束空间。

### 2.2 公理准入标准

并非所有"重要前提"都能进 L0。本库采用两条硬标准：

1. **不可由本库其他命题推导**：若一条陈述能从 A1~A12 中推导出来，则它属于 L1 定律或更低层，不能升格为公理。
2. **被 ≥3 篇文档隐式使用**：公理必须渗透在多处论证中，而不是局部假设。上表每条公理都至少出现在 3 篇文档的推理背景里（例如 A1 出现在 exactly-once、选型决策树、集群测试、多活设计等十余篇文档；A11 出现在契约设计、事件 API 治理、IT 通用模式库等文档）。

## 4. L2 模型层：形式与半形式工具

L2 模型把 L1 定律转化为可计算、可模拟、可误用分析的结构。下表给出本库使用的核心模型，每个模型均注明误用前提。

| 模型 | 解释对象 | 输入参数 | 输出结论 | 误用前提 |
| ---- | ---- | ---- | ---- | ---- |
| M/M/1 排队模型 | 单 Broker 队列的延迟与吞吐 | 到达率 λ，服务率 μ | 平均队列长度 ρ/(1-ρ)，ρ=λ/μ | 假设泊松到达与服务时间指数分布；高扇出/批处理场景需改用 M/G/1 或网络模型 |
| 系统动力学因果回路 | 背压、重试风暴、技术债的反馈结构 | 存量、流量、延迟变量 | 正/负反馈主导环与杠杆点 | 把相关性当因果性；忽略非线性阈值 |
| 博弈收益矩阵 | 多 MQ 系统的竞争与互补策略 | 市场份额、迁移成本、差异化收益 | 纳什均衡与演化稳定策略 | 假设完全理性；忽略生态锁定与组织惯性 |
| 控制回路（PID/观测器） | 自动扩缩容、限流、自愈 | 误差信号 e(t)，控制增益 Kp/Ki/Kd | 稳定性条件、超调量、收敛时间 | 测量延迟大或执行器饱和时，需改用模型预测控制 |
| S 曲线（技术采纳） | 新技术替代旧技术的速度与天花板 | 当前采用率 p，创新系数 a，模仿系数 b | Logistic 增长轨迹与拐点 | 假设单一技术竞争；忽略政策/并购等外生冲击 |
| Quorum 共识模型 | 副本一致性与容错边界 | 总副本数 N，读写法定数 W/R | 满足 W+R>N 即可保证读后写一致性 | 忽略网络分区下的可用性权衡；拜占庭场景需 BFT |
| 故障传播方程 | 单点故障如何级联为系统失效 | 故障概率、依赖度、恢复时间 MTTR | 级联半径与韧性指标 | 假设故障独立；实际存在共同模式故障 |

更详细的模型参数表、公式与案例见 [04-01-系统动力学视角](../topics/04-动态系统论与演化分析/04-01-系统动力学视角.md) 至 [04-10-反脆弱架构设计原理](../topics/04-动态系统论与演化分析/04-10-反脆弱架构设计原理.md)。

### 4.1 模型使用示例：从 M/M/1 到背压阈值

以单 Broker 队列为例，若生产者到达率 λ=5000 msg/s，Broker 服务率 μ=6000 msg/s，则利用率 ρ=λ/μ≈0.833。根据 M/M/1 模型：

```text
平均队列长度  L = ρ / (1 - ρ) = 0.833 / 0.167 ≈ 5
平均等待时间  W = L / λ ≈ 5 / 5000 = 1 ms
```

当 λ 涨至 5900 msg/s（ρ≈0.983），L 跃升至约 58，等待时间升至约 9.8 ms。这正是 L5"无背压系统必然崩溃"的定量刻画：ρ 接近 1 时，队列长度对负载变化极度敏感。工程上通常把 ρ 控制在 0.7~0.8 以下，并配置 `max.in.flight.requests` 或 `maxAckPending` 等背压阈值，使系统远离相变点。

该示例同时说明 L2 模型的消费规则：模型给出的是**趋势与阈值**，不是精确预测；实际 Broker 的批处理、批大小、网络抖动会使服务时间偏离指数分布，因此需用 L4 实测校准。

### 5.1 模式选择的判定规则

模式不是"越多越好"，而是由定律与模型共同裁剪后的结果。判定一条业务需求该用哪个模式，可遵循以下三步：

1. **语义维度识别**：从 L1 定律中找出不可回避的约束。若需求要求"不重复处理"，则 L1 已告知端到端 exactly-once 不可达，必须引入 L3 幂等键契约或 Outbox。
2. **模型灵敏度估算**：用 L2 模型估算模式代价。例如引入 Saga 补偿会增加延迟与状态机复杂度，需用控制回路模型评估超时与重试预算。
3. **实例可验证性**：模式必须能在 L4 找到 GWT 断言或 verified 用例。若一个模式无法被 `Testing/06` 或 `test-registry.tsv` 覆盖，则它仍停留在概念层，不能进入生产决策。

这一规则也反向约束文档编写：02 系列每篇设计文档必须在头部声明"它回应了哪条 L1 定律"，03 系列每篇落地指南必须给出"可勾选的检查项"。

## 7. 三条完整推导链演示

### 推导链 1：支付对账的 exactly-once 落地

```text
A1 网络会分区 + A5 传输不可靠
    → L1 跨节点端到端 exactly-once 不可达
        → 01-63 给出系统语义边界 + Jepsen 证据
            → L2 Two Generals / FLP 模型刻画不可能性
                → L3 幂等键契约 + 对账/Outbox 模式
                    → L4 02-payment-reconciliation 场景 + TC-SEM-05/07 验证
```

这条链说明：支付场景追求的"不重复对账"，不能靠消息系统单独完成，必须由"系统内 EOS + 业务幂等 + 日终对账"三段共同保证。

其关键转折在于 L1→L2：Two Generals 不是抽象的哲学比喻，而是支付回调场景的真实约束——支付网关发出回调后，若未收到商户 ACK 则必然重发；商户若在未 ACK 时处理，则可能重复。因此 L3 必须在应用层引入幂等键，L4 必须验证"同一 correlationId 第二次投递被去重"。

### 推导链 2：订单状态的顺序与持久化

```text
A3 时钟不同步 + A4 存储有限 + A2 节点故障
    → L4 副本一致性需要法定数协议
        → L6 日志是分区容错的最小存储抽象
            → L2 Quorum 模型 + 故障传播方程
                → L3 状态机转移 + 事件溯源模式
                    → L4 01-order-lifecycle 场景 + Kafka KRaft 配置实例
```

这条链说明：订单状态机之所以用 Kafka 分区日志 + 事件溯源，不是因为"潮流"，而是因为要在异步时钟、有限存储、节点故障下维持顺序与容错。

其关键转折在于 L2→L3：Quorum 模型给出 W+R>N 的一致性条件，但工程上 W 与 R 的选择会影响可用性。Kafka 的 ISR（In-Sync Replicas）机制实质是 W=R=ISR  majority 的变体，它把 L4 的配置参数（`min.insync.replicas`、`acks=all`）与 L1 的副本一致性定律直接挂钩。01-order-lifecycle 场景因此选择按 `orderId` 分区，使顺序性与容错性同时落在同一分区副本组内。

### 推导链 3：IoT 遥测的背压与限流

```text
A6 速率不匹配 + A8 观测滞后
    → L5 无背压系统必然崩溃
        → L2 M/M/1 排队模型 + 控制回路模型
            → L3 背压声明 + 限流模式
                → L4 05-iot-telemetry 场景 + MQTT QoS/限流配置
```

这条链说明：IoT 场景"允许偶发丢数据，但不能把服务端打崩"的语义选择，是 A6 与 L5 直接推导出的工程结论。

其关键转折在于 L2→L3：M/M/1 模型给出 ρ→1 时的相变风险，但 IoT 设备数量呈长尾分布，突发流量常使 λ 在短时间内远超 μ。因此 L3 不能仅依赖静态背压阈值，而需引入控制回路模型：根据队列深度动态调整 `maxAckPending` 或触发 KEDA 扩容。L4 的 05-iot-telemetry 场景用 MQTT QoS=1 保证至少一次，用限流与背压保证服务端不 OOM，正是 L2 模型在真实约束下的裁剪结果。

### 8.1 层间漂移的触发条件

五层塔不是静态标签，而是动态一致性的检查框架。以下情况会触发"层间漂移"警报，须按 KB_CHARTER §4 上报：

1. **L1 定律被外部证据推翻**：如新 Jepsen 报告发现某系统在某版本下违反既有语义结论，则所有依赖该定律的 L3/L4 文档须重新标注"存疑"。
2. **L3 模式找不到 L1 支撑**：若某设计模式无法追溯到至少一条 L1 定律，则它可能是局部习惯而非通用模式，应降级或删除。
3. **L4 实例与 L3 模式脱节**：若检查清单中的动作无法对应到 L3 模式，则该清单是操作性碎片，应合并或重构。
4. **L0 公理被 ≥3 篇文档外推**：若一条公理只被 1~2 篇文档使用，则它可能只是局部假设，应降级为 L1/L2 的前提条件。

层间映射的用法：

1. **向上溯源**：任何 L3 模式都应能说出"它回应了哪条 L1 定律"；任何 L4 检查清单都应能说出"它来自哪个 L3 模式"。
2. **向下展开**：当 L1 定律更新（如新 Jepsen 报告推翻某语义结论），应能定位到受影响的 L3/L4 文档并触发漂移报告（KB_CHARTER §4）。
3. **Agent 消费**：AI agent 引用本库结论时，优先引用 L1【定理】与 L4 verified 用例；L3 模式须带出处；L2 模型只作灵敏度分析输入。
