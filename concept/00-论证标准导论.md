# 00 论证标准导论：怎么读这个知识库

> 本库不是“结论清单”，而是“可追踪的论证网络”。
> 读完本篇，你会知道：一句结论的置信度从哪里来、形式化资产在哪里、以及如何判断自己是否被忽悠。

P3 标注（【定理】/【论证】/【估算】）是贯穿全库的置信度语言。
学会它，你就能把任何技术结论还原为“证据链”，而不是把权威当信仰。

> **注意**: P3 不是“重要性”标签，而是“可验证性”标签。一个结论可以非常重要但仍是【估算】；也可能很局部却是【定理】。

### P3 标注的边界

- 同一句话里可能同时包含【定理】与【估算】，应拆分标注。
- 【定理】只保证模型/协议，不保证你的部署配置正确。
- 【估算】不是“错误”，而是“需要本地验证”。

## 3. 论证链范式：结论 → 证据 → 反例 → 边界

本库每篇深度文章都建议按四段式组织。下面以“Kafka exactly-once 可用于跨分区事务写”为例示范。

**结论**: 在 Producer 开启幂等且使用事务时，Kafka 可保证跨分区的 EOS（exactly-once semantics）写。

**证据**: Producer Idempotence 通过 PID+Sequence Number 去重【定理】；Transaction Coordinator 管理两阶段提交；KIP-98 引入事务 API。

**反例**: 消费端在业务处理完成后、commit offset 前崩溃，仍可能重复处理；跨会话 Producer 不保证去重；事务超时会导致事务中止。

**边界**: 仅保证 Kafka 内部语义的 EOS；端到端 EOS 仍需业务幂等。详见 [01-63-Exactly-once语义全论证](../topics/01-基础概念与对比分析/01-63-Exactly-once语义全论证.md)。

```markdown
- 结论：...
- 证据：...（带标注）
- 反例：...（打破幻想）
- 边界：...（适用域）
```

## 5. 论证链速查卡

阅读任何一篇技术结论时，可问自己这 5 个问题：

1. **结论是否可证伪？** 能说出“在什么条件下它不成立”吗？
2. **证据是否可追溯？** 能回到官方文档、论文或基准报告吗？
3. **置信度是否标注？** 是【定理】、【论证】还是【估算】？
4. **反例是否被讨论？** 作者是否主动列出限制与失败模式？
5. **边界是否清晰？** 结论适用于哪个版本、哪个规模、哪个部署模式？

| 问题 | 若答案为“否” | 补全动作 |
| ---- | ---- | ---- |
| 结论不可证伪 | 加一句“在 X 条件下会失效” | 查 Jepsen/官方已知 issue |
| 证据不可追溯 | 标注来源链接或改为【估算】 | 用 WebSearch 找官方来源 |
| 未标置信度 | 按 P3 重新标注 | 参考 AGENTS.md §4.1 |
| 无反例 | 补充官方文档的 Limitations 章节 | 查 release notes 与 issue tracker |
| 边界不清 | 限定版本、规模、部署拓扑 | 看 ROADMAP.md 版本基线 |

## 6. 把论证标准用起来

日常阅读与贡献时，可用项目门禁脚本做静态校验：

```bash
# E0 全量静态验证（含 P3 标注与链接完整性检查）
bash topics/scripts/hermes-e0-run.sh

# 文档语义抽检：随机抽取一批断言，人工核对置信标注
bash topics/scripts/doc-semantic-spotcheck.sh

# 论证链完整性自检
grep -R "【估算】" concept/ | head -20
```
